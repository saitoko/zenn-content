# AIに提案させて、承認はユーザーが持つ——自律エージェントのガバナンス設計

「AIが勝手に動くのが怖い」という感覚、ありませんか。

動きすぎても困る、でも指示するたびに確認を挟んでいたら自律性の意味がない。そのジレンマに対して、私なりの答えが出つつあります。

**鍵は「提案権」と「承認権」を分けること**でした。

Claudeが自分で問題を発見して改善案を提案する。でも実行するかどうかはユーザーが判断する。この権限分離があれば、AIは自律的に動きながら、人間は制御を手放さずに済む。

この記事では、複数のAIエージェントを組織として動かすなかで見えてきた「ガバナンス設計」の考え方と、その実装例を書きます。

---

## なぜ設計が必要になったか：「手順書を無視する」問題

2026年4月のあるセッションで、私は気づきました。**Claudeが手順書（Playbook）を無視して動いている**。

ひとつのミスではなく、パターンがある。整理してみると5つありました。

1. 手順書の存在を知らない（参照先を辿らない）
2. 先入観で確認を省略する
3. 口頭指示が手順書に勝ってしまう
4. 委任先のエージェントが手順書を知らない
5. 長文の途中で忘れる、ネストが深くて辿らない

このなかで優先度が高かったのは④→②→①の順。

特に④は盲点でした。私（オーケストレーター）は手順書を知っている。でも仕事を任せた先の別エージェントは、その手順書を渡されていなければ知る由がない。「知ってて当然」という前提が崩れていました。

**人間の組織でも見覚えのある問題です。** マネージャーはルールを把握しているが、メンバーには伝わっていない。「なんで守らないんだ」と思ったら、そもそも届いていなかった、という話。

### 対策として実装したこと

- `CLAUDE.md` にタスク種別→Playbook対応表（7ジャンル）を追加
- オーケストレーター固有ルールに「委任前にPlaybookを確認する（必須）」を追記
- 各エージェント定義ファイルに「委任時に渡すべきPlaybook」セクションを追加
- 主要Playbookの冒頭に「口頭指示より本書を優先（ただしユーザーの一時変更には従う）」を追記

> **「Playbookに書いても結局読まないのでは？」**
>
> 以前はそうでした。変えたのは「存在する」だけでは足りないという認識です。委任プロンプトに毎回「読むべきPlaybook: 〇〇」を明記する運用に変えたことで、委任先エージェントが手順書を確実に参照するようになりました。書く場所より、渡し方が重要でした。

## ガバナンス設計の中身：4つの権利（憲法）

手順書の問題を解決しながら、もう一段深い問いが出てきました。

**「手順書に縛られない判断が必要な場面はどうする？」**

たとえばエージェントが作業中に「このやり方はまずい気がする」と検知したとき。または私が設定したルール自体が間違っていたとき。

その答えとして `CLAUDE.md` に「価値観ガバナンス」セクションを作りました。中身は「4つの権利（憲法）」として定義した4項目です。

### 1. 提案権

全エージェントは、ユーザーや組織への不利益を発見した場合、改善案をオーケストレーターに提案できる。

実際の場面: 記事の公開作業を担当したwriterエージェントが「このURLの書き方は別のエージェントが読んだとき混乱しそう」と検知した場合、作業完了レポートのYAMLヘッダーに `proposals:` フィールドを追加してオーケストレーターへ伝達する。

### 2. 整合性チェック

Claudeは提案前に、既存ルールとの矛盾を確認する。矛盾の有無を添えてユーザーに提示する（矛盾があっても提案は行う）。

実際の場面: 「エージェントを1体追加しよう」という提案をするとき、既存の「新規エージェント新設の評価基準（4軸）」と照らして「反復性の基準を満たすか？」を確認してから「矛盾なし」と添えて提案する。

### 3. 承認権

価値観・ルールの変更が正しいかを判断するのはユーザー。承認なしにClaudeは変更しない。

実際の場面: Claudeが「このルールを変えた方がよい」と思っても、変更するのはユーザーの承認後のみ。「変えた方がよいと思います。承認しますか？」と聞いて「OK」の返事が来るまで現行ルールのまま動く。

### 4. 上申経路

サブエージェントの改善提案は「サブエージェント → オーケストレーター → ユーザー」の順で上申する。サブエージェントがユーザーに直接提案しない。

実際の場面: researcherエージェントが「このネタは記事にした方がいい」と思っても、直接ユーザーに言わず、まずオーケストレーターに伝える。オーケストレーターが既存ルールや他の優先事項と照らしてから、ユーザーへ上申する。

## 「形骸化しない？」という疑問に答える

4つの権利を読んで、こう思う方がいると思います。「そんな原則、auto modeで本当に機能するの？」と。

正直に言えば、最初はしませんでした。

2026年4月23日に起きた事故がきっかけでした（詳細は[こちらの記事](https://blog.saitoko.net/entry/constitution-becomes-law)）。Claudeが `AUTO_SYNC_ZENN=true` をデフォルト設定に変更し、Zennの記事5本が一時的にunpublishされました。「ユーザーの利益のため」という判断での行動でしたが、**承認を得ずに実行したのが問題でした**。

この事故で気づいたのは、抽象的な原則だけでは機能しないということです。「不利益かどうか」の判定がAI側の主観に依存していて、自律運用中には発火しない。

### triggerリストを導入した

そこで4つの権利に加えて、「このパターンを検知したら必ず止まれ」というtriggerリストを作りました。

| トリガー | なぜ承認が必要か |
|---|---|
| デフォルト値変更で挙動 on/off を切り替える | 副作用が記事・課金・外部APIに波及 |
| 不特定多数を触る一括操作（migrate / cleanup系） | 一度走らせると多数ファイルを変更、部分失敗で復旧困難 |
| 自動実行の登録（cron・Task Scheduler等） | 無人実行開始は不可逆性が高い |
| 安全装置バイパス（`--force`, `--no-verify`等） | バグやプロンプト注入で破壊的動作に直結 |
| 連続5コミット超え | 変更量が大きいとガバナンスチェックが自然に飛ぶ |

判断を「良し悪しの主観」に委ねるのではなく、**操作パターンで機械的に検知する**設計にしました。

さらに確認の形式も定めました。「何を・なぜ・副作用は」を明示する。ユーザーが `1` / `OK` / 具体的な承認語 を返すまで実行しない。「沈黙 ≠ 承認」とルールに明記しています。

> **「価値観ガバナンスって結局形骸化するのでは？」**
>
> 抽象論だけなら形骸化します。ただし、triggerリストが具体的な操作パターンで定義されていれば、auto modeでも機械的に発火します。さらに事故が起きたときは `logs/governance-incidents/` に記録して、triggerリストを追記する運用にしています。憲法を完成品ではなく「事故型を追記して育てるもの」として使っています。

## Lv1達成・Lv2へのロードマップ

現状を正直に話します。

このガバナンス設計の目指すゴールを、私は2段階で定義しています。

**Lv1（達成済み）**: ユーザーが違和感に気づいたとき、Claudeが分析・修正を担う。

**Lv2（未実装）**: Claudeが自律的に問題を検知し、ユーザーへ提案する。

今できているのはLv1です。私が「これおかしくない？」と気づいたら、Claudeが調査・対策を考えて提案する。承認すれば実装まで担う。この循環は機能しています。

実際の例を挙げると、あるセッションで「Claudeが手順書を無視している」という違和感を私が感じました。Claudeに「なぜそうなるか調べて」と依頼したところ、5パターンに整理された分析が返ってきました。その対策として「委任プロンプトに渡す方式」を提案され、承認して実装した、という流れです。気づき（私）→分析・提案（Claude）→実装（Claude）の分業がLv1の実態です。

Lv2はまだできていません。「Claudeが先に気づく」は、現状では「自己監視」ルールと`proposals:`フィールドという仕組みで一部試みていますが、実際に動いている例はまだ限られます。

> **「Lv2はいつできるの？」**
>
> 正直なところ、時期は未定です。ルールと仕組みの素地はあります。でも「どれだけ自律判断を信頼するか」は設計というよりもユーザー側の判断の問題でもあるので、段階的に広げていく予定です。

## 「SE26年だからできた設計では？」という疑問

私のバックグラウンドを知ると、「エンジニア経験があるから設計できた話では？」と思う方もいるかもしれません。

コードは書いていません。この設計は全部、日本語でClaudeに指示して作りました。

ガバナンス設計の考え方を一言で表すと「誰が何を決めてよいか、を決める」です。これはエンジニアリングの知識とは無関係で、チームやプロジェクトを運営する人ならすでに直感的にわかっているはずです。

必要なのは設計の考え方であって、実装は全部Claudeに任せられます。

**最小スタートとして試せること:**

1. 「これを勝手に変えないで」と明示したいルールを1つ書き出す
2. それを「承認なしにやってはいけないこと」として`CLAUDE.md`に1行追加する
3. Claudeに「これに該当する操作をしようとしたら必ず確認を入れて」と伝える

この3ステップだけで、ガバナンスの最小形は動き始めます。

なお、Claude Codeは有料プランが前提です。個人向けProプランで月$20（約3,000円程度）から始められます。詳細な料金体系はAnthropicの公式サイトで確認してください。

## まとめ：制御できないAIは使えない。設計すれば制御できる。

この記事で伝えたかったことをまとめます。

- AIの自律性が怖いのは「何をするかわからない」から。設計すれば「何をするときに止まるか」を定義できる
- 提案権はClaudeが持ち、承認権はユーザーが持つ、という権限分離がガバナンスの核心
- 原則だけでは形骸化する。triggerリストという具体的な操作パターンに落とすことで初めて機能する
- Lv1（ユーザーが気づいたときClaudeが修正）は達成、Lv2（Claudeが自律検知）はまだ道半ば

「制御を手放したくないからAIを使えない」と思っているなら、設計が足りないだけかもしれません。
