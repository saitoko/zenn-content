## 今朝の風景

朝、Slack を開いたら3つの通知が来ていた。

- **リサーチャーエージェント**: 10ジャンルのニュース・トレンドをまとめた日次レポートを `content/reports/daily/` に保存済み。「ウイスキー値上げ情報あり、今日の1アクション候補: 記事ネタ検討」という要約も添えてある
- **秘書エージェント**: `/todo` コマンド経由で期限超過タスク5件の通知を GitHub Issues から抽出し、Slack に投稿済み
- **ライターエージェント**: 昨日指示した記事の下書きが `content/drafts/` に出力済み

私がやったのは、指示書を書いて各エージェントに渡すことだけ。あとは就寝中と本職の合間に、エージェントが動いていた。

これが Claude Code を使い始めて6日後の朝の風景です。最初からこうなることを計画していたわけではなく、「試したい」を積み重ねた結果です。

## 3つのエージェントの動き方

### 秘書エージェント ── タスク管理と通知

秘書エージェントは GitHub Issues をバックエンドに使い、GTD（Getting Things Done）のタスクをカスタムスキル `/todo` で管理しています。GTDの考え方については[新装版 はじめてのGTD ストレスフリーの整理術](https://www.amazon.co.jp/dp/B0FQB574SS/)が参考になります。

```bash
# タスクを追加する
/todo next 記事のリライトを実施する @PC --due 明日

# 待ちタスクとして登録
/todo waiting Qiita審査の結果待ち @Qiita

# 完了処理
/todo done 12
```

これに加えて、毎時・毎朝の定期実行で期限超過タスクを Slack に通知する仕組みも動いています。冒頭の「秘書エージェントからの通知」は実際の通知内容をもとにした要約です（期限超過5件は実際の数値）。

エージェントへの指示はこのように書いています:

```markdown
# secretary への指示例
あなたは秘書エージェントです。
GitHub Issues のタスクを確認し、期限が今日以前のものを
Slack の #000-partner チャンネルに通知してください。
```

この指示書を `.claude/agents/secretary.md` に置き、CEO（司令塔）が必要に応じて呼び出します。

### リサーチャーエージェント ── 毎日の情報収集

リサーチャーエージェントは毎朝、10ジャンル（当初11ジャンルで開始し、その後整理）の最新情報を収集して日次レポートを作成します。

ジャンル一覧: AI活用・Claude Code / 筋トレ・ダイエット / ウイスキー・バー / ラーメン / Swift・iOS / 金融・フィンテック / 個人開発 / マーケティング / 資産運用 / Mac・Apple

実際のレポート出力の断片を見せます（これはリサーチャーエージェントが実際に生成したレポートの断片です）:

このレポートを素材に、ライターエージェントへ「今日の記事ネタはこれ」と渡す流れが定着しています。

リサーチャーへの指示書（`ops/playbooks/daily-research.md`）は187行で、Claude Code 自身が初回に書きました。私がやったのは「10ジャンルの最新情報を集めてレポートにまとめて、Slackにも投稿して」と伝えただけです（当初11ジャンルで依頼し、その後整理して現在10ジャンル）。

リサーチャーへの指示はこのように書いています:

```markdown

あなたはリサーチャーエージェントです。
ops/playbooks/daily-research.md の手順に従い、
10ジャンルの最新情報を収集して content/reports/daily/ に保存し、
Slack の #000-partner チャンネルに要約を投稿してください。
```

### ライターエージェント ── 記事下書きからクロスポストまで

ライターエージェントは `content/drafts/` の指示書や `content/reports/` のリサーチ結果をもとに記事の下書きを作成し、Zenn / Qiita / はてなブログへのクロスポストを実行します。

```bash
# Zennに記事をプッシュしてから、Qiita・はてなに展開
bash scripts/crosspost.sh claude-code-first-week --publish --qiita --hatena
```

実際の制作フロー:

1. CEO: ライターに指示書を渡す（記事の方向性、使う事実・数字を明記）
2. ライター: 下書きを `content/drafts/` に出力
3. reviewer: レビューを実施（事実誤認・法的リスク・構成チェック）
4. reader ペルソナ: 読者目線の評価（離脱点・「嘘くさい」箇所の検出）
5. CEO: 修正点をまとめてライターへフィードバック
6. secretary: Zenn へプッシュ、クロスポスト実行、git コミット

ライターへの指示はこのように書いています:

```markdown
# writer への指示例
以下の内容でQiita記事の下書きを作成し、
content/drafts/claude-code-first-week.md に保存してください。

## 記事の方向性
- タイトル: Claude Code マルチエージェント構成の作り方
- ターゲット: Claude Code を触り始めたエンジニア
- 使う事実: /todo 303件テスト、コード2011行→838行（58%削減）、Day5でPro上限到達
```

ライターが出力する下書きの冒頭はこんな感じです:

## 6日間でどうやって作ったか

Day 1-2 はコーディングだけです。ラーメンレビューアプリ（Python / FastAPI / Google Maps API）と銀行システムサンプル（Java 21 / WildFly / PostgreSQL / Docker）を作りました。環境構築、コーディング、テスト、リファクタリング——SE として日々やっていることの全工程が、チャットの指示だけで動いた。

この体験で確信しました。「1つのインスタンスでこれだけ動くなら、複数を役割分担させれば何でもできる」。

Day 2 の夜、司令塔用の新規フォルダで Claude Code を起動して「あなたは司令塔です」と伝えました。Claude Code が自分で CLAUDE.md を作り、ディレクトリ構成を提案してくれました。これがマルチエージェント化の起点です。

Day 3: デイリーリサーチの仕組み化。MCP（外部サービス連携の仕組み）で Slack 投稿を可能にし、指示書を渡したら同日中に初回レポートが生成されました。

Day 4: `/todo` GTD スキル開発。Day 2 の銀行アプリで学んだ「テストを先に書いてリファクタリングを恐れない」パターンを適用。303件のテストで品質を担保しながら機能拡張できる基盤を作りました。

Day 5: Pro プラン（$20/月）の利用制限に達したその場で Max プラン（$100/月）へ切り替え。それくらい手が止められなかった。/todo の大規模リファクタリング（コード 2,011行→838行、58%削減）、Zenn 初期セットアップ、クロスポストスクリプト作成、記事公開を1日でやり切りました。

なぜこの量が1日で可能だったか。Day 1-4 で「エージェントに指示書を渡す→動く」という基盤ができていたからです。

この日、トラブルも起きています。i18n 対応のテスト中、テストスクリプトが `~/.claude/` を丸ごと削除する事故が発生。テストはすべて通過しているのに Claude Code のログイン情報が消える、という不可解な状態が続きました。原因は `HOME` 環境変数の差し替え方でした。詳細は別記事に書いています。

> 📖 [テストが ~/.claude/ を消し飛ばした話 — HOME 差し替えの罠](https://zenn.dev/tottoko_hamu/articles/claude-todo-test-selfdestruct)

Day 6: `/health` スキルを30分で追加。体重・体脂肪・運動記録を GitHub Issues に保存するもので、/todo の構造を流用しました。「コーディングツールではなく、自分の作業を代替するツールだ」という感覚が確定した日です。

## 同じ構成を作る手順

### CLAUDE.md 最小テンプレート

新規フォルダで Claude Code を起動して、以下を `CLAUDE.md` に書くだけです。Claude Code が自分でサブエージェントの定義を作り始めます。

```markdown
# CLAUDE.md — [プロジェクト名]

## このプロジェクトの目的

[1〜2文で目的を書く]

## エージェント構成

CEO（あなた）が全体を指揮し、以下のエージェントに委任する:

- researcher: 情報収集・調査
- writer: 記事・ドキュメント執筆
- secretary: タスク管理・通知

## 基本ルール

- 常に日本語で応答する
- 成果物は [output-dir]/ に保存する
- 重要な決定はメモリに保存する
```

### エージェントの追加方法

`.claude/agents/` フォルダに Markdown ファイルを置くだけです。例: `.claude/agents/researcher.md` に以下の内容を保存します:

```markdown
---
name: researcher
description: 調査・分析を行うリサーチエージェント
tools: Read, Grep, Glob, WebSearch, WebFetch, Write, Bash
---

調査・分析を担当する。

## 担当業務
- デイリーリサーチ（ops/playbooks/daily-research.md の指示に従う）
- テーマ別の深掘り調査

## 出力先
- 調査レポート: content/reports/research/
```

あとは「リサーチャーエージェントに毎朝の情報収集を依頼して」と CEO に伝えれば、指示書の作成から初回実行まで自動でやってくれます。

### 実際に使っているディレクトリ構成

```
プロジェクトルート/
├── CLAUDE.md              # 司令塔の設定
├── .claude/
│   ├── agents/            # 各エージェントの定義ファイル
│   └── rules/             # 共通ルール
├── content/
│   ├── drafts/            # 記事ネタ・下書き
│   └── reports/
│       ├── daily/         # デイリーリサーチ
│       └── research/      # 調査レポート
├── ops/
│   └── playbooks/         # エージェントへの指示書（定例）
└── scripts/               # crosspost.sh 等
```

## コストについて

Pro プラン（$20/月）: Day 1-4 は問題なく動いていました。Day 5 で大量の並列作業をしたときに上限に達しました。6日間でProが上限に達したのは1度（Day 5）のみです。

Max プラン（$100/月）: Day 5 以降はこれで運用中。Max 切り替え後は2026-04-15時点まで上限未達です。Day 5 だけで「/todo 大規模リファクタリング・Zenn初期セットアップ・クロスポストスクリプト作成・記事公開」を並列でこなせたことを考えると、SE 1人分の1日作業を代替した体感です。「月$100 のコストに見合うか」は個人差がありますが、副業・記事制作・ツール開発を複数並列で回すなら十分ペイすると判断しました。

## まとめ: 6日間でわかったこと

Claude Code は「コーディングツール」ではなく「人間の作業者の代替」です。CLAUDE.md で役割を定義し、エージェントファイルで能力を分担すれば、秘書・リサーチャー・ライターが動くチームが作れます。

加速のコツは「仕組みを作る仕組みを先に作る」こと。個別の成果物ではなく、エージェント構成・テスト基盤・記事パイプラインという構造を先に作ったことで、Day 5 の爆発的な生産性が生まれました。

Day 1-4 の地味な基盤整備がなければ、Day 5 の密度は実現できなかった。
