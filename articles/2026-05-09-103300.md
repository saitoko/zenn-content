# マルチエージェントのトークン、どこを削れてどこは削れないか

Claude Codeのマルチエージェント構成では、トークンコストに「削れる無駄」と「削れない必然」の2種類がある。COOの中継や権限の重複は設計ミスとして削れるが、コンテキスト独立性に起因するコストは構造的要件であり削ると動作が壊れる。本記事ではその見分け方を4つの実例で整理する。

---

「エージェントが増えると、トークンが心配で……」

Claude Code でマルチエージェント構成を組み始めたとき、こんな不安を感じたことはないだろうか。複数のエージェントが動くたびにコンテキストを読み込む。同じファイルを何度も参照する。「これ全部お金かかってるよな」という感覚。

この不安は正しい。ただ、「だからすべて削ろう」と進むと、削ってはいけない部分まで削ってしまう。

私は Claude Code で9体のエージェントを使ったマルチエージェント構成を運用している（COO＋8専門エージェント）。規模感は違っても、この記事の考え方は2〜3体構成にもそのまま使える。先日、権限ファイルのメンテナンス中に「削れる無駄」と「削れない必然」が混在していることを実感した。この記事ではその分類を整理する。

---

## マルチエージェントのトークンコスト：3つの種別

マルチエージェントのコストには、3種類がある。

| 種別 | 見た目 | 実態 |
|------|--------|------|
| 削れる無駄 | COOが中継している / 権限が重複している | エージェント権限設計のミス |
| 削れない必然 | 同じファイルを複数エージェントが読む | コンテキスト独立性による構造的要件 |
| 削ると逆効果 | 大きなファイルを分割する | DRY違反か新たな依存連鎖を生む |

この3つを混同して「とにかく全部削ろう」とすると、エージェントが必要な文脈を持てなくなる。

---

## 削れる無駄①：COO（オーケストレーター）が「中継役」になっていたトークン浪費

ある日、レビュー結果が保存されないままセッションが終了するという事故が起きた。

原因を追うと、フローがこうなっていた。

```
reader エージェントがレビューを生成
  ↓
COO がレビューを受け取る
  ↓
COO が content/reviews/ に保存する
```

COO がファイル保存の「中継役」になっていたのだ。このフローには問題がある。COOとのやり取りがトークンを消費するだけでなく、セッションの切断タイミングによっては保存自体が行われない。

解決は単純だった。reader エージェントに `Write(content/reviews/**)` 権限を付与する。すると reader が直接保存するようになり、中継コストがゼロになった。

**学び**: サブエージェントが自分で書けるなら、COOを経由させる理由はない。「誰が保存すべきか」を権限設計に落とし込むことで、中継コストを構造的に排除できる。

---

## 削れる無駄②：権限設定ファイルが30行分肥大化していた——settings.jsonの見直し

今回の整理で最も可視性が高かったのがこれだ。

settings.local.json（Claude Code のエージェント権限ファイル）を精査したところ、以下のような状態になっていた。

- `Bash(cp:*)` というワイルドカードパターンが全 cp コマンドを包含している
- にもかかわらず、`todo-dev/`・`skill-dev/` × Windows形式・MSYS形式・$HOME形式 の組み合わせで、個別の cp コマンドが数十エントリ登録されている

コミット差分で実測したところ、削除できた重複エントリは **30行分**だった（整理前: 469行、整理後: 439行）。

なぜこうなったか。スキル開発のたびに「このコマンドを許可しないと動かない」と追加し続けた結果だ。追加した瞬間は動くようになるが、「これは上位パターンに既に含まれる」というチェックは入らない。

Windows形式・MSYS形式・$HOME形式の列挙はWindows環境固有の話だが、「上位パターンが下位を包含していないか」という発想自体はMac・Linux環境でも同じだ。

**学び**: 権限ファイルは「動かすたびに追加」が積み重なる。追加のたびに既存パターンとの包含関係を確認する習慣が必要だ。定期的な棚卸しは必須と考えた方がいい。

## 削れない必然：同じファイルを3エージェントが参照するコストは避けられない

ここが今回のいちばんの気づきだ。

私の構成では `state-management.md`（299行）という記事管理の共通仕様ファイルがある。このファイルを参照するエージェントを調べると、こうなっていた。

- writer → state-management.md を読む
- secretary → state-management.md を読む
- crosspost 担当 → state-management.md を読む

「同じファイルを3回読むのは無駄では？」と思ってしまう。ここが罠だ。

Agent tool で委任された各エージェントは、**独立したコンテキストウィンドウ**を持つ。COO が writer に渡した情報は、次に呼んだ secretary には届かない。「COO が1回読んでおけば全員に共有できる」は機能しない。

シングルプロセスの発想でコードを書いていると、「同じ変数を2回初期化しているじゃないか」と感じる。しかしマルチプロセスでは、各プロセスが自分のスコープで必要なものを持つのが正しい。これと同じだ。

**学び**: マルチエージェントにおける「重複読み込み」は、コンテキスト独立性による構造的要件であることが多い。削除すると、エージェントが文脈を持てず動作が壊れる。

---

## 削ると逆効果：コンテキストファイルを分割すると逆にトークンが増える理由

「state-management.md が299行もある。writer用・secretary用・crosspost用に分割すれば各エージェントの読み込み量が減るのでは？」

この発想は自然だが、実際に調べると逆効果だった。

ファイルの構成を分析すると、スキーマ定義・禁止事項・APIリファレンスといった共通コアが全体の約60%を占めていた（調査時点）。このコアは3エージェント全員が参照する部分だ。分割するとどうなるか。

- 各ファイルにコアをコピー → DRY違反、メンテナンスコスト増
- コアを別ファイルに抽出 → 新たなチェーン参照が発生、読み込みは減らない

**結論**: 分割の前に「エージェントが本当に使わないセクション」を削る方が効果的だ。

具体的な手順はこうなる。

1. 対象ファイルを開き、各セクションのヘッダーをリストアップする
2. そのファイルを参照するエージェントのPlaybook（または指示書）を確認し、実際に言及されているセクションに印をつける
3. 印がついていないセクションが「使っていない候補」。削除前に `grep -r "セクション名" ops/playbooks/` で他からの参照がないかを確認する
4. 参照がなければ削除または別ファイルへ移動する

これはコードでいう「premature abstraction」と同じ構造だ。「大きいから分割する」の前に「本当に全部使っているか」を確認する。

## 削れるか削れないかを見分ける4つの基準

今回の4つの発見を振り返ると、一つの基準が見えてきた。

**削れるコスト**は、設計上の判断ミスや積み重ねによって生まれる。COO中継・権限の重複がこれにあたる。発見さえすれば削れる。

**削れないコスト**は、マルチエージェントのアーキテクチャそのものから来る。コンテキスト独立性は機能であり、それを支えるコストは払うべきものだ。

「コストを減らしたい」という動機は正しい。ただ、そのためには「なぜそのコストが発生しているか」を先に理解する必要がある。削ってから壊れた経験は、削る前に考えるよりずっと高くつく。

マルチエージェントの設計をもっと体系的に学びたい方には、私自身の実践記録をまとめた本があります。
