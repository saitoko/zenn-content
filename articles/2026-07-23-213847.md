**この記事でやったこと（2026年6月）**: Anthropic が2026年5月6日に発表した Claude Managed Agents の新機能「Dreaming」（Research Preview）と、私が手元で運用している自前のメモリ整理スキル `/dream`（補助スクリプト410行・スキル定義269行）を設計レベルで対比した。結論は「どちらが優れているか」ではなく、両者が「AIにどこまで設計を任せるか」という問いに別の答えを出している、という点にある。試せなくても設計原則は読み解ける——本記事はその実証でもある。なお、Dreaming は API 限定の Research Preview のため、比較は公式ブログ（`claude.com/blog/new-in-claude-managed-agents`）の記載と、自前実装の実測値を根拠とする。

## 「AIが自分のメモリを整理する」機能が来た

AIエージェントを長く使っていると、必ずぶつかる問題がある。エージェントに覚えさせた知識（メモリ）が、だんだん肥大化し、重複し、ときに矛盾する、という問題だ。

私が運用している Claude Code のメモリディレクトリには、現時点で個別のメモリファイルが43本ある（`~/.claude/projects/*/memory/` 配下を実測、複数のClaudeプロジェクトを横断した合計）。「記事の一人称は私」「Opus 使用前に許可を求める」といった運用ルールが1ファイル1テーマで蓄積されている。便利な反面、似たルールが2ファイルに分かれていたり、古い設定値が残っていたりする。これを手で整理し続けるのは骨が折れる。

この課題に対して、Anthropic が2026年5月6日に「Dreaming」という機能を発表した。公式ブログによれば、Dreaming は「エージェントのセッションとメモリストアをレビューし、パターンを抽出し、メモリを整理するスケジュールされたプロセス」だ（出典: `claude.com/blog/new-in-claude-managed-agents`、原文 "Dreaming is a scheduled process that reviews your agent sessions and memory stores, extracts patterns, and curates memories so your agents improve over time."）。

ここで注意したい言い回しがある。「スケジュールされたプロセス（scheduled process）」であって、「アイドル時に勝手に起動する」わけではない。私も当初は「人間が寝ている間にAIが夢を見るようにメモリを整理する」というイメージで受け取っていたが、公式が言っているのはあくまで定期実行のジョブである。この区別は後の対比で効いてくる。

問題は、Dreaming が Claude Managed Agents の API 機能であり、しかも Research Preview だという点だ。申し込みはウェイトリスト制のフォーム（`claude.com/form/claude-managed-agents`）からで、対象資格の要件は公式に明記されていない。サブスクリプション（Pro / Max）では使えず、API 課金の枠組みでのみ提供される（2026年6月8日時点の公式ブログ記載による）。つまり、多くの個人開発者は「発表は読んだが試せない」状態に置かれている。

私もその一人だ。だが、試せなくても設計は読み解ける。そして私の手元には、似た目的で自作したスキルがある。ならば、公式仕様と自前実装を並べて「設計思想の差」を抽出してみよう、というのがこの記事の出発点だ。

## 公式Dreamingの設計を公式記述から読む

まず、公式が何を言っているかを正確に押さえる。私が試せていない以上、ここは断言を避け、公式ブログの記載に限定して書く。

公式ブログから読み取れる Dreaming の設計上の要点は3つある。

1. **定期実行のプロセスである**。前述の通り「scheduled process」と明記されている。トリガーの最小アイドル時間などの詳細条件は公式に記載がない。
2. **セッションとメモリを横断してパターンを抽出する**。単一ファイルの整形ではなく、エージェントが過去のセッションで学んだこと（公式の例では「ファイル形式ごとの回避策」「ツール固有のパターン」）を抽出してメモリに反映する。
3. **反映前のレビューを選べる**。公式は「メモリを自動更新させるか、変更が反映される前にレビューするかを選べる」と書いている（原文 "update memory automatically, or you can review changes before they land."）。つまりレビューは必須ではなく、オプションである。

3点目は私が当初誤解していた箇所だ。「レビュー必須」と思い込んでいたが、公式記述は違う。**自動更新も選べる**——レビューを挟むかどうかは利用者の設定に委ねられている。

効果として、公式は Harvey 社の内部テストで「タスク完了率が約6倍（~6x）」という数字を挙げている。Harvey 社の内部テスト値であり、個人のメモリ整理にそのまま当てはまる数字ではない点に留意したい。

## 自前/dreamスキルの実装

ここからは私が試せる領域だ。私は Claude Code 用に `/dream` というスキルを自作している。目的は同じ——肥大化・重複・矛盾を起こすメモリファイル群を整理することだ。

実装は2ファイルで構成される。スキルの手順を記述したスキル定義（`dream.md`、269行）と、ファイル操作を担う補助スクリプト（`dream.sh`、410行）だ。スクリプトのサブコマンドは `list`（全メモリ内容の出力）・`backup`（バックアップ作成）・`apply`（変更適用）・`restore`（復元）の4つで、意味分析そのものは Claude が担当する。

整理の中身は3つの操作からなる。

- **重複マージ**: 同じ運用ルール・設定値が2ファイル以上に存在する場合、詳細・最新の記述を持つ側に統合し、もう一方を削除候補にする。
- **矛盾・陳腐化の検出**: 同じ設定について異なる値が複数ファイルにある、あるいは「廃止」「旧仕様」とコメントされた記述を検出して更新案を出す。
- **新インサイトの抽出**: 複数ファイルを横断して見える傾向（例: 「feedback系ファイルの多くが委任コストに言及している」）を記述する。

設計上、私が最も重視したのは**書き込みの安全性**だ。`/dream` はデフォルトで dry-run モードで動く。変更案を提示するだけで、ファイルには一切触れない。実際に書き込むには `--apply` を明示的に付け、さらにその後の `yes` 確認を通す必要がある。書き込み前には必ずバックアップを取り（`tmp/dream-backup/YYYYMMDD-HHMM/`）、`restore` サブコマンドでいつでも元に戻せる。

具体的な実行イメージはこうだ。

```bash
# まず変更案だけを見る（デフォルトで dry-run、書き込みなし）
/dream

# 出力例:
# == DREAM 分析結果 ==
# [重複マージ候補] 1件
#   1. feedback_delegation_overhead.md + feedback_secretary_haiku.md
#      理由: 両ファイルとも委任コストについて記述しており重複
#      対応: 前者に統合、後者を削除
# == 適用するには /dream --apply を実行してください ==

# 内容を確認してから、明示的に適用する
/dream --apply
# → バックアップ作成 → yes 確認 → 書き込み
```

つまり「AIが分析し、人間が一件ずつ承認し、人間の承認なしには1バイトも書き換わらない」という設計だ。自動更新の選択肢は、私の実装にはそもそも存在しない。

## 対比: 設計の何が違うのか

両者を並べると、表面的には「メモリを整理する」という同じゴールに見える。だが設計の前提が異なる。

| 観点 | 公式Dreaming | 自前/dream |
|---|---|---|
| 提供形態 | Claude Managed Agents API（Research Preview） | Claude Code 用の自作スキル（ローカル） |
| 起動 | スケジュールされたプロセス | 人間が手動で `/dream` を叩く |
| 分析対象 | エージェントのセッション＋メモリストア横断 | メモリファイル群（任意で直近3セッションのtranscriptも参照可） |
| 反映前レビュー | 自動更新／レビューを**選べる** | dry-run がデフォルト、`--apply` + `yes` で初めて書き込み |
| 復元 | 公式記載なし（未確認） | `backup` / `restore` で常時可能 |

共通点は明確だ。どちらも「AIがパターンを抽出してメモリを整える」という発想に立っている。そして、どちらも人間がレビューする経路を持っている。

相違点の核心は、**レビューがデフォルトでオンかオフか**にある。公式 Dreaming はレビューを「選べる」——裏を返せば、レビューを挟まず自動でメモリを更新させる運用が公式に想定されている。一方、私の `/dream` はレビューを外す手段がない。dry-run を飛ばして書き込む経路を、私はあえて実装しなかった。

この差は、機能の優劣ではない。「AIにメモリ設計をどこまで任せるか」という設計判断の差だ。

## 自前/dreamとDreaming、どちらを選べばよいか？

ここまでの対比を一言にまとめると、両者は「制御を手放す地点」が違う。

公式 Dreaming の自動更新モードは、メモリの整理を AI に委ねる**委譲モデル**だ。人間は方針を設定したら、あとは AI がスケジュールに沿って整える。レビューを挟むこともできるが、挟まない運用も成立する。チームの規模が大きく、エージェントの数が多く、一件ずつのレビューが現実的でない状況では、この委譲は理にかなっている。Harvey 社のように多数のエージェントを運用する組織にとっては、自動でメモリが育つことの価値が、レビューを省くリスクを上回るのだろう。

私の `/dream` は、メモリ設計を人間が握り続ける**管理モデル**だ。AI は分析と提案までを担うが、何を採用するかは必ず私が決める。これは私が個人で運用していて、メモリの一件一件が記事執筆や運用ルールに直結するからだ。「記事の一人称は私」のようなルールが意図せず書き換わると、後続の全成果物に影響する。だから私は、整理の自動化よりも、毎回目を通すコストを選んだ。

どちらが正しいという話ではなく、自分のケースに当てはめる判断軸が3つある。

- **エージェントの数**: 数十以上を同時運用していて全変更を手動レビューするのが現実的でなければ → 委譲モデル寄り
- **メモリ1件の影響範囲**: 1ファイルの書き換えが多数の成果物（記事・ルール・外部送信）に波及するなら → 管理モデルで握り続ける
- **AIの整理結果への信頼水準**: まだ精度を検証中なら → 管理モデルから始めて実績を積んでから委譲を増やす

私の場合は「個人運用・影響範囲が広い・まだ信頼を検証中」なので管理モデルを選んだ。だが将来、Dreaming が使えるようになり、整理の精度を検証できたら、判断は変わりうる。

## 公式DreamingとPlaybookを共存させる設計——GA後に何を任せるか

最後に、両者は二者択一ではないという話をしておきたい。

私が `/dream` で培ったのは、整理機能そのものよりも「どの変更を採用し、どれを却下するか」というレビューの勘所だ。重複マージで詳細な側を残すか、矛盾検出で新しい値を採るか——こうした判断基準は、仮に将来 Dreaming を導入しても無駄にならない。むしろ「Dreaming が候補を出し、私が培った基準で採否を決める」という構図に発展させられる。委譲モデルと管理モデルは、レイヤーを分ければ共存できる。

現時点で何が次の節目かを整理しておく。Dreaming は Research Preview のままで、私はまだウェイトリストの先にいる。GA（一般提供）への移行、あるいはサブスクリプション枠での提供が次の分岐点になる。それまでにできることは、自前 `/dream` でレビューの判断基準を言語化し続けることだ。比較対象を自分の手元に持っておくと、公式機能が来たときに「何を任せ、何を握り続けるか」を即断できる。

試せない機能でも、仕様から原則は読み解ける。そして自前で似たものを作ると、「比較できる」という副産物が手に入る。あなたがもしメモリ管理の仕組みを設計するなら、最初に問うべきは「どの機能を使うか」ではなく、「制御をどこで手放すか」——委譲モデルと管理モデルの、どちらを選ぶかだと思う。

**明日すぐできる1アクション**: `~/.claude/projects/*/memory/` 配下のファイルを `ls` で一覧してみる。ファイル数と内容を眺めるだけでよい。似たルールが書かれたファイルが2本見つかれば、それがあなたの `/dream` 設計、あるいは Dreaming 導入判断の出発点になる。
