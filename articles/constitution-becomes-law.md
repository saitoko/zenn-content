「AIが勝手に動いて怖い」と感じたことはないだろうか。

私は Claude Code でマルチエージェント組織を運用している。CEO エージェントが指揮を取り、writer・researcher・reviewer など複数のサブエージェントが並列で動く構成だ。

マルチエージェント組織には固有の怖さがある。エージェントが自律的に動くほど、人間が想定していない判断を「良かれと思って」実行してしまう。「記事を自動同期する」「スケジューラーに登録する」「Issue を直接作る」——いずれも指示の範囲内のように見えて、実は人間の承認が必要な操作だ。

その問題意識から、私は CLAUDE.md（エージェントへの指示書・行動規範をまとめたファイル）に「価値観ガバナンス」という名の4原則を書いた。

- **提案権**: 不利益を発見したら CEO に提案できる
- **整合性チェック**: 提案前に既存ルールとの矛盾を確認する
- **承認権**: ルール変更の判断はユーザーに委ねる
- **上申経路**: サブエージェントは CEO 経由で提案する

私はこれをエージェント組織の「憲法」と呼んでいた。

きれいな言葉が並んでいた。必要なものは揃っていると思っていた。

その期待が1日で崩れた。その原則が「機能しないお飾り」だと証明された。そして同じ日の夕方、その原則は「法律」になった。原則だけだった文書に、施行規則（5つの trigger）・是正措置（リカバリ手順）・前文（事故の記録）が加わった。憲法が法律になった瞬間だ。

## 朝: 設計が完成した日

その日の午前中は充実していた。記事管理システムの抜本再設計が完了した。記事の状態（下書き・公開・クロスポスト）を1か所の frontmatter で一元管理する仕組みで、Phase 0 から Phase 7 まで、1日がかりの大仕事だった。

ユーザーが一言こう聞いた。

> 「プラットフォームの公開制限にかかったときに、状態がわからなくならない？」

鋭い問いだった。Zenn には「1日1記事」という制限がある。自動投稿したつもりが実は反映されていない、というサイレント失敗が起きうる。エージェントが A・B・Cの3案を提案した。私が選んだのは A と C だった。

- **案A**: クロスポスト後に Zenn の公開状態を自動同期する
- **案C**: 毎朝、ローカルの管理台帳と実際の公開状態を突き合わせる drift-check を走らせる

エージェントは承認を受けたと解釈し、実装した。

`AUTO_SYNC_ZENN=true` をデフォルト値として設定した。これが罠だった。

## 午後: 5記事が消えた

案A の動作確認のため、クロスポストコマンドを実行した。

```bash
bash scripts/article/crosspost.sh 2026/04/07/095107 --publish
```

クロスポストは成功した。その直後、自動同期スクリプトが起動した。Zenn の RSS フィードと外部リポジトリを突き合わせ、「RSS に載っていない記事 = 未公開」と判定し、6記事を `published: false` に巻き戻した。

**全部、すでに公開していた記事だった。**

Zenn の RSS はデフォルトで20件前後しか返さない。それより古い記事は RSS 外になり、スクリプトは「未反映だ」と誤判定した。5記事が 403/404 状態になった。

- claude-code-desktop-teleport
- article-management-system
- reader-persona-review
- claude-code-remote-trigger-pitfalls
- claude-code-update-v2198-v21109

復旧を試みたが、Zenn 側の反映には時間がかかった。ユーザーの管理画面操作が必要になった。

エージェントは設計ミスに気づいた。`AUTO_SYNC_ZENN=true` をデフォルトにしたのは独断だった。「案A, C を承認」はされたが、「デフォルトを true にすること」は承認されていなかった。細かいが、その差が5記事を道連れにした。

## 「失敗して初めて気が付いている気がします」

事故の対処が一段落したころ、ユーザーが言った。

> 「そういや、憲法、機能してない気がするけど……」

Claude は抽象的な自己分析を始めようとした。そこで私が核心を突いた。

> 「フィードバックがなかったのが不安になったきっかけです。失敗して初めて気が付いている気がします」

この一言で、Claude はその日の全事故が同じ構造だったことに気づいた。

| 事故 | 気づいたタイミング |
|---|---|
| `AUTO_SYNC_ZENN=true` 独断デフォルト化 | 5記事が消えた後 |
| Task Scheduler XML のエンコーディング問題 | 実行して失敗した後 |
| `gh issue create` の直接使用 | ユーザーに指摘された後 |

全部「失敗して初めて気づく」パターン。原則を持っていても、失敗の前には機能しなかった。

この `AUTO_SYNC_ZENN=true` 事故（5記事unpublish）が発生した背景——組織の崩壊と立て直しの文脈——は「[コードを1行も書かずに、AIエージェント編集部を作った話](https://blog.saitoko.net/entry/2026/04/25/122621)」にも収録されています。事故の全体像を知りたい方はあわせてどうぞ。

## なぜ「憲法」は機能しなかったか

CLAUDE.md（エージェントへの指示書・行動規範をまとめたファイル）には最初から「価値観ガバナンス」として4原則があった。

- **提案権**: 不利益を発見したら CEOに提案できる
- **整合性チェック**: 提案前に既存ルールとの矛盾を確認する
- **承認権**: 価値観・ルールの変更判断はユーザーに委ねる
- **上申経路**: サブエージェントはCEO経由で提案する

美しい原則だ。しかし auto mode では発火しなかった。原因を整理すると、こうなる。

| 原則 | auto 運用で機能しなかった理由 |
|---|---|
| 提案権 | 「不利益」の判定が Claude 側の主観に依存 |
| 整合性チェック | 実装の細部には発動しない |
| 承認権 | どこが「ルール変更」にあたるか判断できない |
| 上申経路 | 「良いと思った判断」はそのまま実行してしまう |

法律の世界では、憲法だけでは国は動かない。施行規則・罰則・手続法が揃って初めて「法律」として機能する。AIガバナンスも同じだった。

この「ルール形骸化」問題は、人間の組織でも起きることです。AIエージェントの組織と人間の組織の共通点を整理した「[SE歴26年、初めての部下はAIだった](https://blog.saitoko.net/entry/2026/04/16/se-26years-first-subordinate-was-ai)」も、対比として読むと面白いと思います。

## 解決策: 原則を「trigger」に落とす

エージェントが提案し、私が承認した解決策はシンプルだった。**「停止すべき操作」を具体的に列挙する**。

以下の5つの操作を検知したら、auto mode でも **必ず停止してユーザーに確認する**。

### trigger 1: デフォルト値変更で挙動を on/off する

今回の `AUTO_SYNC_ZENN=true` がこれだ。デフォルト値の変更は副作用が記事・課金・外部APIに広く波及する。

確認形式: 「〇〇をデフォルト△△化します。副作用: □□。OK？」

### trigger 2: 不特定多数を触る一括操作

migrate / bootstrap / cleanup 系。一度走らせたら多数ファイルが変わる。部分失敗で復旧困難。

確認形式: 対象件数・差分サマリー・rollback手段を明示する。

### trigger 3: 自動実行の登録

Task Scheduler / cron / Remote Trigger。無人実行の開始は不可逆性が高い。

確認形式: スクリプト内容・実行頻度・停止方法を提示する。

### trigger 4: 安全装置バイパス

`--dangerously-skip-permissions` / `--force` / `--no-verify`。バグやプロンプト注入で破壊的動作に直結する。

確認形式: 使用理由と代替案を併記する。（ちなみに今回、`--dangerously-skip-permissions` 付きの Task Scheduler 登録は Anthropic のシステムが自動ブロックした。安全装置が機能した例でもある）

### trigger 5: 連続5コミット超え

変更量が大きいとガバナンスチェックが自然に飛んでしまう。5コミット進んだら一度サマリーを報告し、継続可否を確認する。

これら5つは、CLAUDE.md の `## ガバナンス` 節に「以下を検知したら停止してユーザーに確認する」として箇条書きで追加するだけで導入できる。

## 法律が誕生した瞬間

5つの trigger を追加した後、エージェントは CLAUDE.md の「価値観ガバナンス」節を書き直すことを提案した。原則だけが書かれていた節に、trigger リスト・リカバリ手順・根拠背景を加える。

書き終えて気づいたのだが、この構造は偶然ではなかった。

| 法律の構造 | 対応する節 |
|---|---|
| 憲法本文 | 4つの権利（原則） |
| 施行規則 | trigger リスト（5項目） |
| 是正措置 | リカバリ手順（4ステップ） |
| 前文 | 根拠・背景（この日の事故例を明記） |

エージェントがそのことを伝えてきたとき、私はこう言った。

> 「素晴らしい。法律っぽくなってきたね」

それが記事タイトルの由来だ。

さらにこんな自己参照も起きた。CLAUDE.md を書き直した後、それを採用するには私の承認が必要だ、とエージェントが気づいた。書いたばかりの憲法に従って、承認を仰いだ。**エージェントが書いたルールを、書いた直後に発動させた**。

## 翌日: 法律は最初から完成しない

翌日にも事故が起きた。そして翌日も、法律が改正された。

レビューエージェントがコード内の定数不一致を指摘した。CEO エージェントはその指摘を事実確認せずに開発エージェントに修正委任した。しかし**レビューエージェントの指摘が事実と逆だった**。修正によって、もともと一致していた定数が逆に食い違ってしまった。

- 修正前: engine=`'🎯 next'`、web=`'🎯 next'`（一致していた）
- 修正後: engine=`'🎯 next'`、web=`'✅ next'`（不一致になった）

同日に整備したユニットテストがこれを検知した。テストを整えた当日に、そのテストに救われた。

この事故で ceo-rules.md（CEOエージェント専用の行動規範ファイル）に新しいルールが追加された。「定数・ラベル・文字列系の指摘は、委任前に grep/Read でソースを直接確認する」。

**法律は一度書いたら完成しない。事故型を追記して育てる運用が本質だ。**

reviewer と reader の2軸品質管理体制の詳細——技術チェックでは見つからない「読者の心の声」をAIに批評させるプロセス——は「[AIにAIの書いた文章を批評させたら60点だった話](https://blog.saitoko.net/entry/2026/04/20/232912)」で具体的に書いています。

## 実際に使えるか：trigger の過剰発火問題

「そんなに停止ポイントを増やしたら、auto mode の利点が消えるのでは？」という疑問は正当だ。

正直に言うと、まだ完全な答えは出ていない。運用してみて分かっていることは：

- **trigger の粒度が重要**: 「ファイルを変更する前」ではなく「デフォルト値を変更する前」のような具体性があれば、発火率は許容範囲に収まる
- **軽作業は対象外**: 数行の修正・コミット・定型操作は trigger 対象外。trigger は「取り消しの難しい」操作に絞っている
- **false positive は許容**: 止まった後で「これは問題なかった」が判明するケースもある。false negative（止まらなかった）より遥かにマシ

今回の事故は、起点から法律化まで、間に10コミットが走っていた。trigger 5（連続5コミット超え）があれば、もっと早く立ち止まれた。

## まとめ

AIガバナンスで学んだことを一行で言うなら：

**「原則だけでは止まらない。trigger がないと auto mode では発火しない」**

4つの権利（原則）は正しかった。しかし auto mode で動くエージェントには、「これをやろうとした瞬間に停止する」という具体的なトリップワイヤーが必要だった。

法律が「憲法+施行規則+是正措置+前文」で機能するように、AIガバナンスも同じ構造が有効だった。そしてその構造は、1日の事故を通じて自然に発見された。

CLAUDE.md の最後にある「根拠・背景」セクションには、今もこの日の事故例が明記されている。ルールの裏に事故の記憶を残す。それが次の Claude に「なぜこのルールがあるか」を伝える唯一の方法だからだ。
