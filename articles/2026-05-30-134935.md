## GTD × AI バッチ型ワークフロー——設計思想の3点

前編（[タスク管理ツールを3つ乗り換えた末に設計した——Claude Code × GTD で「対話ゼロ」のバッチ型ワークフロー](https://blog.saitoko.net/entry/2026/05/19/gtd-ai-batch-workflow-intro)）では、NEXT 肥大化問題の診断とバッチ型ワークフローの設計思想を書いた。

要点は3つだった。

- **対話ゼロ設計**：inbox.md に書いてコマンド1発で AI が仮仕分け、人間はエディタで承認するだけ
- **「判断」から「承認」へ**：タスク分類をゼロから判断するのではなく、AI の下書きを検査する認知シフト
- **NEXT 肥大化への構造的な対処**：Tickler・Today リスト・腐った NEXT の自動検出の3セット

この実装編では、それらをどう GitHub Issues という実行基盤に落とし込むか——具体的なラベル設計・コマンド例・機能の採用判断を書く。

## なぜ GitHub Issues をバックエンドに選んだか

Notion・Obsidian・Todoist など選択肢はいくらでもある。GitHub Issues を選んだ理由は、私が Claude Code ユーザーであることと不可分だ。

**API・CLI が充実している点が決定的だった**。`gh issue create`・`gh issue list`・`gh issue edit` が揃っており、Claude Code スキルからコマンド1発で操作できる。MCP サーバー経由で AI が直接 Issues を読み書きすることもできる（[GitHub MCP Server](https://github.com/github/github-mcp-server)）。「AI から直接操作できるバックエンド」という条件を満たすサービスは、想定より少ない。

**データがベンダーロックインされない点も大きい**。Markdown + JSON でエクスポートでき、変更履歴が全部 git で残る。5年後にサービスが変わっても、データは手元に残る。

| 比較軸 | GitHub Issues | Notion | Todoist |
|--------|--------------|--------|---------|
| CLI/API 完成度 | ◎ | △ | ○ |
| AI直接操作 | ◎（MCP対応）| △（非公式）| △ |
| エンジニアの習慣との重なり | ◎ | △ | × |
| モバイル操作性 | △ | ◎ | ◎ |
| 無料上限 | 実質無制限 | ページ数制限あり | タスク数制限あり |

弱点も正直に書く。**モバイルからの操作性は弱い**。GitHub の公式アプリから Issues を操作する体験はそれほど良くない。移動中にサッとタスクを追加したい場面では、iPhone の Claude アプリから `gh issue create` を経由する方法を取っている——これも完全なソリューションとは言えない。非エンジニアには敷居が高い。ターゲットを「Claude Code を日常的に使っているエンジニア」に絞っていることで、この弱点は許容範囲に収まっている。

## GTD 概念 × GitHub 機能の対応表

GTD のどの概念が GitHub のどの機能に対応するか。これが設計の出発点だ。

| GTD 概念 | GitHub での対応 | 運用状況 |
|---------|----------------|---------|
| **責任領域（Areas of Responsibility）** | リポジトリ | 現在運用中 |
| **プロジェクト（Projects）** | マイルストーン | 現在運用中 |
| **Next Action** | Issue | 現在運用中 |
| **コンテキスト（@場所・@ツール）** | ラベル（`context:pc` / `context:phone` 等）| 現在運用中 |
| **Tickler（日付トリガー）** | ラベル + 朝セッションの手動昇格 | 現在運用中（自動化は実装構想）|
| **Someday/Maybe** | ラベル `someday` + クローズ | 現在運用中 |
| **Waiting For** | ラベル `waiting` + assignee | 現在運用中 |
| **Focus List（今日の3件）** | Pinned Issues | 現在運用中 |
| **週次レビュー（Done 可視化）** | `git log --since` によるコミット履歴参照 | 現在運用中 |
| **週次レビュー（AI 差分レポート）** | AI スキルによる Issue 差分レポート自動生成 | 実装構想 |

「リポジトリ = 責任領域」というマッピングが、最初に腑に落ちた部分だ。GTD の責任領域とは「終わりがない継続的な役割」——仕事・個人・副業・健康、といった区分だ。リポジトリもまた「終わりがなく、継続的にタスクが発生し続ける単位」として機能する。

GTD の用語や5ステップが曖昧な方は、デビッド・アレンの原著日本語訳（[新装版 はじめてのGTD ストレスフリーの整理術](https://www.amazon.co.jp/dp/B0FQB574SS)）を先に読んでおくと、この記事の対応表がより腑に落ちるはずだ。

プロジェクト = マイルストーンも自然にはまった。マイルストーンには締め切りが設定できる。GTD のプロジェクトが「ゴールのある複数ステップの仕事」という定義なので、期限付きマイルストーンが対応する。

## Tickler の実装——NEXT 肥大化の根本解決

前編で「NEXT 肥大化の第1層の原因は Tickler が機能していないことだ」と書いた。Tickler が機能していないと、「今じゃないけど忘れたくない」タスクが全部 NEXT に滞留する。

現在の実装は次のとおりだ（**現在運用中**）。

**ラベル設計**: `tickler:YYYY-MM-DD` 形式のラベルを Issue に付ける。たとえば「2026-06-01 に改めて検討する」なら `tickler:2026-06-01` というラベルを作成して付与する。この Issue は `someday` ラベルも併せて付けてクローズせず保留状態に置く。

```bash
# Tickler ラベルの付いた Issue を日付昇順で確認
gh issue list --label "tickler:2026-05-19" --state open

# 朝セッションで「今日の Tickler」を手動で NEXT に昇格
gh issue edit <issue-number> --remove-label "someday" --add-label "next"
```

**朝セッションへの統合**: 既存の朝セッション（Claude Code スキル）に Tickler チェックのステップを1つ追加している。セッション冒頭で「今日の日付と一致する `tickler:*` ラベルの Issue を列挙して昇格してください」という指示を実行する。新しい仕組みを覚えるのではなく、既存の習慣に1ステップ乗せる形にしたことで定着した。

```
朝のセッション（現在運用中）
  ├── Inbox 確認
  ├── Tickler 日付チェック  ← 追加済み
  │     └── tickler:YYYY-MM-DD → next ラベルに昇格
  ├── Today 選定（NEXT から3件）
  └── Waiting For フォローアップ
```

**将来構想: GitHub Actions による自動昇格**（**実装構想・未実装**）

ラベル検索と昇格をスクリプト化すれば、毎朝 GitHub Actions で自動実行できる。`schedule` トリガーで毎朝6時に起動し、当日日付の `tickler:*` ラベルを検索して `next` に昇格させる——という設計は固まっているが、現時点では手動運用の状態だ。

```yaml
# .github/workflows/tickler.yml（実装構想）
on:
  schedule:
    - cron: '0 21 * * *'  # JST 06:00 = UTC 21:00
jobs:
  tickler:
    runs-on: ubuntu-latest
    steps:
      - name: Promote tickler issues
        run: |
          TODAY=$(date +%Y-%m-%d)
          gh issue list --label "tickler:$TODAY" --state open --json number \
            | jq -r '.[].number' \
            | xargs -I{} gh issue edit {} --remove-label "someday" --add-label "next"
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

手動で十分回っている間は自動化を急がない、というのが今の判断だ。GitHub Actions の設計・運用を体系的に学びたい方には [GitHub CI/CD実践ガイド](https://www.amazon.co.jp/dp/B0D4DBYJJ9) が参考になる。

## Pinned Issues = Focus List

GitHub の「Pinned Issues」機能は、リポジトリのトップページに最大3件の Issue を固定表示できる機能だ。この「上限3件」という制約が GTD の Focus List と相性がいい。

**運用方法**（**現在運用中**）:

1. 朝セッションで `next` ラベルの Issue から「今日やる3件」を AI に選んでもらう
2. 前日のピン留めを外す
3. 今日の3件をピン留めする

```bash
# ピン留めの操作は gh コマンドではなく GitHub CLI 拡張または Web UI が必要
# 現状: 朝セッションで「今日の3件」をリスト表示し、手動でピン留め
gh issue list --label "next" --state open --json number,title,labels \
  | jq -r '.[] | "#\(.number) \(.title)"'
```

「上限3件」は制約ではなく設計だ。3件を超えたら今日の集中対象を決め直す強制力が働く。NEXT リストには30件あっても、「今日の画面」には3件しか映らない——この視覚的な絞り込みが、朝の意思決定を軽くする。

ピン留め操作そのものは現時点では手動だ（`gh` コマンドでピン留めを直接操作する CLI インターフェースは安定していない）。この手間も「今日の3件は何か」を改めて意識させるひと手間として機能しているとも言える。

## GTD 違反の自動検出

GTD のルールを「守り続ける」のが難しい理由のひとつは、違反が静かに積み上がっていくことだ。人間は気づかないが、システムを外から見れば一目瞭然の違反がある。

以下は現在の朝セッションで実行している検出パターンだ（**現在運用中**）。

**朝セッションへの組み込み方**: 私のケースでは、COO の startup playbook（`ops/playbooks/coo-startup.md`）の冒頭に「GTD 違反チェック」ステップとして組み込んでいる。セッション開始直後に `gh issue list -l "next" --state open --json number | jq length` を実行し、件数が30を超えていたら Claude に「Someday に落とせる候補を3件選んでください」と指示する流れだ。新しいコマンドを別途覚えるのではなく、既存の朝セッションのステップ1に差し込む形にしたことで、習慣として定着した。

### パターン1: NEXT 30件超え

```bash
gh issue list --label "next" --state open --json number | jq length
```

30件を超えていたら「Someday に落とせるものを3件以上選んでください」という処理を Claude に依頼する。30という数字に GTD の公式根拠はないが、週次レビューで全件目視できる量として30を基準にしている（私の体感ベースの値だ）。

### パターン2: Waiting For に期限なし

```bash
gh issue list --label "waiting" --state open --json number,title,body \
  | jq '.[] | select(.body | contains("期限") | not) | "#\(.number) \(.title)"'
```

Waiting For（誰かに依頼して返答待ちのタスク）に期限がないと、フォローアップのタイミングを永遠に先送りにする。Issue の本文に「期限: YYYY-MM-DD」の記述がないものを抽出する。

### パターン3: 2週間放置の NEXT を検出

```bash
# Linux
gh issue list --label "next" --state open \
  --json number,title,updatedAt \
  | jq -r '.[] | select(.updatedAt < "'"$(date -d '2 weeks ago' +%Y-%m-%dT%H:%M:%SZ)"'") | "#\(.number) \(.title)"'

# Mac（date -d は使えないため -v-2w を使う）
gh issue list --label "next" --state open \
  --json number,title,updatedAt \
  | jq -r '.[] | select(.updatedAt < "'"$(date -v-2w +%Y-%m-%dT%H:%M:%SZ)"'") | "#\(.number) \(.title)"'
```

2週間以上更新されていない NEXT は、実質的に Someday 化している。「まだやる気がありますか？ Someday に落としますか？」という確認を Claude 経由でリスト表示する。

### パターン4: 抽象的な Next Action

これは自動検出が難しい。コマンドで抽出はできるが、タイトルが「〇〇について考える」「〇〇を改善する」のように動詞が抽象的かどうかを判断するには AI の力が必要だ。

実装構想として: Issue タイトルを全件 Claude に渡して「これは次の具体的な物理的アクションとして適切ですか？」と評価させる処理を朝セッションに組み込むことを考えている（**実装構想**）。

## 週次レビューの AI 支援

GTD の肝は「週次レビュー」だ。毎週一度、全リストを棚卸しして腐ったタスクを整理する習慣がないと、GTD はいずれ崩壊する。私自身がまだ週次レビューを安定して実践できていない——この事実を正直に書く。

設計してある支援の仕組みは以下だ（**実装構想・一部試験運用中**）。

| 工程 | 従来（全部手動） | AI 支援後（設計） |
|------|----------------|-----------------|
| 全リストの棚卸し | 全 Issue 目視 | AI が差分レポート生成 |
| 完了漏れの検出 | 記憶頼り | closed Issue と git log の突き合わせ |
| 腐った NEXT の検出 | 自分で気づく | 2週間放置を自動抽出 |
| Someday/Maybe の見直し | リスト全部読む | AI が「まだやりたい？」と確認 |
| 人間がやること | ↑全部 | **判断だけ（はい/いいえ）** |

**git log を「Done の可視化」に使う**（**現在運用中**）:

```bash
git log --since="1 week ago" --oneline --all
```

コミットログには、その週に何をやったかが記録されている。GTD 的な「完了ログ」がコード変更の副産物として自動生成されている、ということに気づいてから、週次レビューの「今週何を成し遂げたか」セクションをこのコマンド1発で埋めるようにした。手作業でタスクを「完了」に移す作業が要らない。

**差分レポートの自動生成**（**実装構想**）:

前週と今週の Issue 状態を比較して「クローズした Issue 数・新規追加数・2週間放置中のものの変化」をまとめたレポートを自動生成する処理を設計中だ。毎週日曜の夜に GitHub Actions が走り、翌朝の朝セッションでレポートを確認するフローを想定している。

## GitHub 機能の採用/見送り判断

ネタ帳の段階でいくつかの GitHub 機能を検討した。結論をまとめる。

### 採用した機能

| 機能 | GTD での役割 | 採用理由 |
|------|------------|---------|
| **Issues** | Next Action の基本単位 | API/CLI 完備、AI からも操作可能 |
| **Labels** | コンテキスト・状態管理 | 組み合わせ自由、Search でのフィルタが強力 |
| **Milestones** | プロジェクト（締め切り付き） | 期限設定でき、Issue の束として機能 |
| **Pinned Issues** | Focus List（今日の3件） | 上限3件の制約が GTD 的にちょうどいい |
| **Issue Search** | stale 検出・未仕分け抽出 | `label:waiting updated:<7日前` 等の構文が実用的 |
| **コミットログ** | Done の自動可視化 | `git log --since` で週次レビューの完了ログに流用 |

### 採用保留・見送りにした機能

| 機能 | 判定 | 理由 |
|------|------|------|
| **Projects v2** | 採用保留 | 週次レビューのビュー設計には有用。ただし GraphQL API の学習コストが高く、まず Issues + Labels で十分回っている |
| **Sub-issues** | 採用保留 | プロジェクトの Next Action 分解（最大8階層）には便利。ただし筆者確認時点（2026年4月）では REST API が不安定（500エラー報告あり: [cli/cli#10378](https://github.com/cli/cli/issues/10378)）。安定してから評価する |
| **GitHub Actions（Tickler 自動化）** | 実装構想 | 設計は完成、手動運用で十分な間は後回し |
| **Issue Templates** | 採用候補 | 収集フォームや週次レビューのチェックリスト定型化に使える。`gh issue create --template` で CLI からも使えるため、次の改善候補 |
| **Notifications** | 要検討 | 外部依頼を Inbox として処理する入口になれるが、仕事用 GitHub との通知混在が解決できていない |
| **Discussions** | 要検討 | Issue = 行動、Discussion = 思考と分ければ Someday/Maybe の「考える場」として機能するかもしれない。ただし `gh` CLI の Discussions サポートが薄く、AI 連携には不向き |
| **ブランチ** | 見送り | 「作業の分離→マージ」が本質で、タスク管理の粒度には合わない。Issues とラベルで十分 |
| **Issue Types** | 不可 | Organization 限定。個人リポジトリでは使えない |
| **Saved Replies** | 見送り | Web UI のみで API 操作不可。AI 連携に向かない |

## 未実装の4項目——週次レビュー自動化・Tickler Actions・抽象Next Action検出

この記事で紹介した仕組みのうち、「実装構想」と書いたものはまだ動いていない。正直に並べる。

- **週次レビューの自動化**: 設計はあるが習慣化できていない。AI 支援の枠組みを作れば続くという仮説は検証中だ
- **GitHub Actions による Tickler 自動昇格**: 手動チェックで代替しており、自動化を優先するほどの痛みを感じていない（逆に言えば「手動で十分」という証左でもある）
- **GTD 違反の自動検出（抽象 Next Action の判定）**: コマンドで抽出できる4パターンのうち、タイトルの抽象度チェックだけは AI 評価が必要で、まだ組み込めていない
- **Someday/Maybe の定期スキャン**: Someday ラベルの Issue を週1回 AI にレビューさせる処理は設計のみ

「まだできていないこと」を並べると、実装の現在地がわかる。理想の設計と今の運用のギャップが可視化されることで、「次にどこを改善するか」という判断がしやすくなる。

## 今日1つ変えるならこれ

全部を一度に実装しようとすると、どれも続かない。GTD × GitHub の仕組みを試すなら、最小単位から始めるのが現実的だ。

**NEXT 件数チェックを朝のターミナルに1行追加する**のが、最も即効性が高い。

```bash
gh issue list --label "next" --state open --json number | jq length
```

このコマンドを朝の作業開始時に1回打つだけでいい。30件を超えていたら「今日 Someday に落とせるものを3件選んでください」と Claude に頼む——それだけだ。新しい習慣の単位をこれ以上小さくするのは難しい。

Pinned Issues の「3件固定」は、このコマンドで NEXT が30件以下に落ち着いてから始めると整合が取りやすい。Tickler のラベル設計は、Pinned Issues が定着してから導入するのが順当だ。一度に全部ではなく、1つずつ稼働させていく。

## GitHub Issues × GTD 実装の現在地と今後の課題

GitHub Issues × GTD × Claude Code という組み合わせを、設計思想から具体的な実装まで書いてきた。

現時点で確実に動いているのは:

- GTD 概念 × GitHub 対応マッピング（リポジトリ = 責任領域、Issue = Next Action 等）
- Tickler のラベル設計と朝セッションへの統合（手動昇格）
- Pinned Issues による Today の3件固定
- NEXT 30件超え・Waiting For 期限なし・2週間放置 の自動検出（`gh` コマンド）
- `git log --since` による週次レビューの「Done 可視化」

まだ動いていないのは、週次レビューの完全自動化と GitHub Actions による Tickler 自動昇格だ。

GTD の理論はシンプルだが、「続けること」は難しい。AI が補助する部分を増やすことで「続けるコスト」を下げるのが、このワークフローの目指すところだ。週次レビューの習慣化については、また別の記事で実践記録を書く予定だ。
