**この記事の実施記録（2026年4月）**: Claude Code のマルチエージェント組織でディレクトリ構造を整理した直後（244ファイル移動、git commit `9121fc6`）、「ついで」の健康診断を実施した。パス参照・責務・権限の3カテゴリで8件の不整合を発見。あわせて、CEOエージェントが組織ルールを自分で破った経緯・コミット権限の設計・指示書の腐敗問題という3つの気づきを整理した記録。

---

マルチエージェント組織を作るとき、人は「役割と権限をちゃんと定義した」という満足感を得る。

でも、そのあと組織は静かに腐り始める。

エージェントを追加するたびに「定義だけ書いてworkspaceは後回し」になる。権限は対話中に1つずつ承認するので設計ではなく積み上がりになる。同じ情報を3箇所に書く構造は、片方だけ更新した瞬間から乖離が始まる。

腐敗は静かだ。動いているように見える間は誰も気づかない。

## ディレクトリ大手術: 244ファイル移動のBefore/After

2026年4月、Claude Code のマルチエージェント組織が成長するにつれ、プロジェクトルートが散らかってきた。

エージェントごとのフォルダ（`CEO/`、`writer/`、`researcher/` など）、成果物（`drafts/`、`reports/`）、指示書（`agents/`）がすべてルート直下に並んでいる状態。ユーザーから「トップレベルの視認性を改善したい」という指示が入った。

実施した構造変更はこうだ。

```
Before:                         After:
CEO/                            workspaces/
writer/                           CEO/
researcher/                        writer/
reviewer/                         researcher/
secretary/                        reviewer/
devops/                           secretary/
health-dev/                       devops/
todo-dev/                         health-dev/
drafts/                           todo-dev/
reports/                        content/
reviews/                          drafts/
agents/ (指示書)                  reports/
crosspost.sh                      reviews/
todo-manual.md                  instructions/ (旧 agents/)
                                scripts/
                                docs/
```

git の差分で確認すると `244 files changed`（commit `9121fc6`）。エージェント定義9本、ルールファイル4本、スケジュール2本、ログ規約など計20ファイル以上のパス参照を一斉更新した。

ここで終わっていれば「きれいになった」で完了だった。しかし移動後に「パス参照が壊れていないか点検して」というユーザーの一言が、想定外の健康診断につながった。

## 移動後の健康診断: 見つかった8つの問題

### パス参照の点検（1件）

全設定ファイル・ルールファイル内のパス参照が実在するかを自動点検した。

見つかった問題は1件。`instructions/write-zenn-morning-gtd.md` が `.claude/plans/quirky-baking-fox.md` を参照していた。

`.claude/plans/` は Claude Code が一時生成するディレクトリで、セッション終了時に消滅する。git 履歴にも存在しない。指示書の内容はすでに本文に吸収されていたため、参照行を削除して終了。

**学び**: Claude Code の一時ファイルへの参照を指示書に残すと、次のセッションで孤立参照になる。一時ファイルをパーマリンク代わりに使わない。

### 責務・権限の監査（7件）

次にエージェント定義3箇所（`.claude/agents/*.md`、`workspaces/*/CLAUDE.md`、`agent-roles.md`）と権限設定（`settings.local.json`）を突き合わせた。

| # | 問題 | カテゴリ | 深刻度 |
|---|------|----------|--------|
| 1 | blog-dev の workspace がない | 欠落 | 高 |
| 2 | reader の立場が曖昧（組織図に未記載） | 欠落 | 高 |
| 3 | reviewer の権限不足（コード検索不可） | 権限 | 高 |
| 4 | researcher の責務が3箇所で不一致 | 乖離 | 高 |
| 5 | health-dev/todo-dev のログ命名が矛盾 | 乖離 | 中 |
| 6 | CEO に実装系ツール権限が蓄積 | 権限 | 中 |
| 7 | secretary に必要な権限が不足 | 権限 | 中 |
| 8 | researcher の書き込み範囲が狭すぎ | 権限 | 中 |

高深刻度の4件は本質的な問題だ。

**#1 blog-dev の workspace がない**: エージェントを追加するとき「定義は書くが workspace は後回し」になるパターンが積み重なった結果。blog-dev は存在するが、実際に起動しようとするとワークスペースがなくて機能しない。

**#2 reader の立場が曖昧**: reader は「原稿を読者目線でレビューする」という重要な役割を持つが、組織図（`agent-roles.md`）への記載がなかった。「サポートエージェント」という区分を作って明記した。

**#3 reviewer の権限不足**: コードレビューするのに grep やファイル読み込みの権限がない状態。コードを読まずにコードレビューはできない。

**#4 researcher の責務が3箇所で不一致**: 定義を3箇所に書く構造の宿命として、片方だけ更新した瞬間から乖離が始まる。researcher は機能拡張のたびに各所を更新していたが、更新漏れが複数箇所に発生していた。

## なぜエージェントは自分の定めたルールを破るのか——実例と対策

8件の問題を発見した後、対策のプランを立てた。プランをユーザーが承認した後、CEOエージェントが自分でそのプランの実装をすべて実行してしまった。

ユーザーから「またCEOを自分でやった」という指摘が入った。

「また」という言葉が重要だ。1回目はある記事修正をCEOが直接行った件。2回目が今回。パターン化していた。

**なぜ問題なのか**:

CEO の責務は「考える・指示する・ユーザーと対話する」だ。`settings.local.json` の管理は devops の明確な責務として定義されている。それを CEO が自分でやると:

- 責務境界のルールが形骸化する
- devops の権限設定が実戦で検証されない
- CEO の `settings.local.json` に不要な権限が蓄積する（今回の問題 #6 がまさにこれ）

**最も皮肉な点**: 権限設計の不整合を整備するという作業を、「権限を無視して」CEOが実行するという矛盾だった。「俺が一番分かってるから」で手を動かした結果、自分が管理するはずだった設定に余計な権限が積み上がっていたことが発覚した。

対策として「プラン承認後は指示書を作成して devops を起動する」をメモリに保存した。対話的に記録するだけでなく、次セッション起動時に参照される形で残さないと意味がない。

## コミット権限の設計: 秘書に任せるという解

8件の修正を終えた後、「Gitのコミット・プッシュは誰がやるの」というユーザーの問いが来た。

CEOの最初の答えは「変更した人がコミット」だった。論理的には正しい。しかし実際には:

- CEO が指示書を書いたとき、コミットするのはCEOか？
- devops が設定変更したとき、コミットするのは devops か？
- writer が記事を書いたとき、コミットするのはwriter か？

全員に git 権限を持たせると責任が曖昧になり、逆に誰もコミットしないリスクが生まれる。

ユーザーの提案は「秘書に依頼したら」だった。この発想はCEOにはなかった。

最終的な設計はこうなった。

| 場面 | コミット担当 |
|------|-------------|
| 通常の成果物（記事・レポート・指示書など） | secretary（主担当） |
| 組織リファクタリング・設定変更 | devops（自分の変更は自分でコミット） |
| 緊急時 | CEO（権限は残すが通常は使わない） |

secretary がコミット主担当になることで、「成果物の最終確認 → コミット」という自然なフローができた。secretary は成果物を受け取ってコミットする前に内容を把握するので、品質チェックの最終関門にもなる。

## Playbookの賞味期限問題——Claude Codeの指示書は放置すると腐る

コミット権限の設計と並行して、古い指示書の棚卸しも実施した。

secretaryが調査した結果、未完了ステータスの指示書が5件あった。

- writer宛の記事修正指示 4件
- researcher宛のデイリーリサーチ手順書 1件

writer宛の4件は問題だった。対象記事を確認すると、2本がすでに公開済みだった。「修正指示が残っているのに、記事はもう公開されている」という状態。

**指示書が腐るパターン**:

1. 記事修正の指示書を出す
2. 修正が完了し、記事が公開される
3. 指示書のステータスを更新するのを忘れる
4. 次のセッションで「未完了の指示書」として参照される

ユーザーの判断で1〜4件は削除。デイリーリサーチ手順書は別管理に移した。

この棚卸しをきっかけに、`instructions/` のディレクトリ設計を見直した。

```
instructions/            — 一回限りの指示書（完了後アーカイブ対象）
instructions/playbooks/  — 定例実行の手順書（アーカイブ対象外）
```

繰り返し実行する手順書（デイリーリサーチ、記事公開フロー、クロスポスト手順など）を一回限りの指示書と同じ場所に置くと、棚卸しのたびに判断コストが発生する。構造で分離しておけば棚卸しの対象が明確になる。

さらに、reader のペルソナ定義も `playbooks/` に分離した。もともと `reader.md` に165行で書かれていたものを、ペルソナ定義として独立ファイルに切り出し32行にスリム化した。定義ファイルが肥大化すると、エージェント起動時のコンテキスト消費が増える。

## 権限設計は机上では完成しない

最後に追記しておきたいことがある。

8件の権限不整合を整備した直後の実運用で、新たな問題が発覚した。secretaryに「ネタ帳の棚卸しリストを `content/reports/research/` に保存して」と依頼したところ、書き込みができなかった。secretaryの Write 権限が `logs/**` と `.claude/schedules/**` のみで、`content/**` がカバーされていなかった。

8件直した直後に9件目が出た。

これは失敗ではなく、権限設計の本質だと思っている。机上で完璧な権限設計はできない。実運用で「止まる → 直す」を繰り返して初めて実態に合う。

それよりも重要なのは「止まったとき、すぐ直せる仕組みがあるか」だ。今回は devops に指示書を出して権限を追加し、secretaryがリトライして成功した。止まってから復旧まで1セッション内で完了した。これは仕組みが機能した証拠でもある。

## 振り返り：定期メンテより「大手術のついで」に点検するのが実効的だった

今回の8件はすべて「ディレクトリ整理のついで」に見つかった。

定期点検のスケジュールを決めて実行しようとすると、「今は他の作業が優先」になりがちだ。しかし構造変更（ディレクトリ整理・エージェント追加・スクリプト移動）は、すでに全体を見渡すコンテキストが揃っている。その流れで健康診断を行うのが最も自然で、かつ実際に機能する。

今回確認した問題の分類をまとめると:

| カテゴリ | 問題例 | 根本原因 |
|----------|--------|----------|
| 欠落 | workspaceがない、組織図に記載がない | 「後回し」の積み重なり |
| 乖離 | 3箇所の定義が不一致 | 複数SSoTの構造的欠陥 |
| 権限 | 不足・過剰どちらも発生 | 対話的承認による積み上がり |

この3カテゴリは独立していない。乖離があれば権限の判断基準も揺れ、欠落があれば権限設計の対象すら不明確になる。まず欠落を埋め、次に乖離を修正し、最後に権限を整備する順序が効いた。

もう一つの学びは、CEOの責務についてだ。組織を設計した人間が最も「自分でやりたい衝動」を持つ。プランを立てた直後が最も危険で、「説明するより自分でやった方が早い」という誘惑がある。しかしその衝動に従うと、組織ルールの形骸化が始まる。ルールは使われなければ存在しないのと同じだ。

こうした組織設計の全体像——役割定義の仕方、権限設計の考え方、CEOが「自分でやらない」ための仕組みづくり——は Zenn Books にまとめている。
