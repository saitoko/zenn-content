組織を作るのに必要だったのは、コードではなく対話だった。

筆者はSE歴26年だが、この6日間で書いたコードは1行もない。Markdownファイルを日本語で書き、Claude Codeと対話を繰り返した。その結果、8体のエージェントが連携して動くAI組織ができあがった。

この記事が伝えたいのは「どう設定するか」ではない。**人間とAIの間でどんな対話・判断が必要だったか**を、6日間の変遷として追う。組織設計論は[先の記事](https://zenn.dev/tottoko_hamu/articles/claude-code-multi-agent-org)に譲り、ここでは「なぜそうなったか」の意思決定プロセスを書く。

## 6日間の全体像

2026年4月3日から8日にかけて、組織はこう育った。

| フェーズ | 期間 | 出来事 |
|---|---|---|
| Phase 0 | 04-03 | 最初のコミット。CLAUDE.mdに「オーケストレーションハブ」と書いただけ |
| Phase 1 | 04-03 〜 04-04 | `/todo`・`/health`スキル開発。todo-dev・health-devが誕生 |
| Phase 2 | 04-06 〜 04-07 | `.claude/agents/`・`.claude/rules/`整備。組織インフラが整う |
| Phase 3 | 04-08 | reviewer新設、CEO責務分離、devチーム呼称確立 |

1体（CEO）から始まって、6日で8体になった。途中で権限エラーが4回発生し、差し戻しがあり、役割が肥大化して分離した。「最初から完璧な組織を設計して、そこに向かって実装した」わけではない。**対話しながら育てた**というのが正確だ。

## 第1章: ビジョン定義の対話 — CLAUDE.mdは17行から始まった

最初のコミット時、CLAUDE.mdはシンプルだった。

```markdown
# CLAUDE.md — パートナープロジェクト

このプロジェクトはClaude Codeの中心的なオーケストレーションハブです。

## 基本ルール

- 常に日本語で応答する
- 作業ログは `logs/` に記録する
- エージェントへの指示書は `agents/` に保存する
- 重要な決定事項はメモリに保存する
```

「オーケストレーションハブ」という言葉だけが先にあった。何をオーケストレーションするのかは、まだ決まっていなかった。

ここで気づいたことがある。**名前を付けることで役割が決まる**。「CEOエージェント」と書いた瞬間に「ではCEOが何をしないか」が問われる。「devopsエージェント」と書いた瞬間に「開発基盤とは何か」を定義しなければならない。

CLAUDE.mdの変遷を振り返ると、組織の思想が層になって見える。

**第1層（Phase 0）**: コアルールだけ。日本語・ログ・指示書の3本柱。  
**第2層（Phase 2）**: エージェント組織図が出現。7体の名前と役割が並ぶ。  
**第3層（Phase 3）**: `詳細は.claude/rules/agent-roles.mdを参照`という一文が加わる。

第3層の変化が興味深い。CLAUDE.mdに直接書くことをやめて、別ファイルへの参照にした。なぜか。**CLAUDE.mdは全エージェントが毎回読むコア**だから、短ければ短いほどいい。詳細を分離することで、ルート CLAUDE.md は現在も約20行に保たれている。

この「圧縮」の判断は、AIとの対話から来た。researcherに「現状の課題を調べて」と依頼したレポートに「CLAUDE.mdが200行を超えると後半のルールが無視されるようになる」という知見があった。人間だけでは気づかなかった問題を、AIが言語化してくれた。

ビジョン定義の対話パターンはこうだ。

1. 人間がざっくりしたビジョンを出す（「こういう組織にしたい」）
2. AIが現状の問題を言語化する（「この構造だとXXが起きます」）
3. 人間がフィードバックして更新する（「ではこう変えよう」）

このサイクルを何度も回すことで、CLAUDE.mdは育っていった。

## 第2章: 優先度選択の対話 — 「何をやらないか」が人間の仕事

Phase 2の最も重要な対話は、researcherへの調査依頼から始まった。

テーマは「Claude Codeマルチエージェント環境における指示書管理のベストプラクティス」。researcherは公式ドキュメントと実践記事を横断調査し、改善提案を優先度付きで出してきた。

**優先度: 高**
1. `.claude/agents/`にサブエージェント定義を追加
2. ルートCLAUDE.mdのスリム化（参照情報を`.claude/rules/`に分離）
3. 反復ワークフローを`.claude/commands/`にスラッシュコマンド化

**優先度: 中**
4. `.claude/rules/`ディレクトリの導入
5. `CLAUDE.local.md`の活用

**優先度: 低**
6. サブエージェントのモデル分離（sonnet/opusの使い分け）

6項目のうち、筆者が採用したのは3項目だった。

| 提案 | 判断 | 理由 |
|---|---|---|
| `.claude/agents/`定義 | 採用 | 最も効果が大きい |
| CLAUDE.mdスリム化 | 採用 | ルール遵守率に直結 |
| commands/化 | 採用 | 日常のワークフロー改善 |
| `CLAUDE.local.md`の活用 | **見送り** | 「開発者1人のプロジェクトでは不要」 |
| モデル分離最適化 | **見送り** | 「現時点ではコスト問題なし」 |

見送った2項目の理由が重要だ。AIは「こういう手法がある」と提案できるが、「それが自分のプロジェクトに必要かどうか」は文脈を知る人間にしか判断できない。1人プロジェクトに`CLAUDE.local.md`は確かに不要だ。

**「何をやらないか」を決めるのが人間の仕事**。これが優先度選択の対話から学んだことだ。AIは提案を尽くす。人間が選択する。この役割分担がはっきりしているほど、組織はスムーズに動く。

選択のポイントは3つだった。

- **効果の大きさ**: この変更で何が変わるか
- **コスト感覚**: 今やる必要があるか、後回しにできるか
- **プロジェクトの文脈**: 自分の状況に合っているか

ResearcherはAIとして最善の提案を出してくれる。でも「最善」は文脈によって変わる。この対話で、人間が意思決定者であることが改めて明確になった。

## 第3章: 差し戻しの対話 — 「動くけど正しくない」を潰す

Phase 2の終盤、devopsが作成したCLIツールのインストール指示書 `install-cli-tools.md` をCEOがレビューした。結果は差し戻しだった。指摘の詳細は[先の記事](https://zenn.dev/tottoko_hamu/articles/claude-code-multi-agent-org)に譲るが、ここで得たメタな洞察を書いておく。

**指摘を「必須修正」と「要検討」の2段階に構造化した**ことで、修正サイクルが速くなった。必須修正はブロッカーで、これが直らないと先に進めない。要検討は判断を委ねており、devopsが理由を説明して「これでいい」と言えば通る。

この区別があることで、受け取る側は「何がクリティカルで、何が裁量の余地があるか」を即座に把握できる。曖昧な「全部直して」より、構造化された指摘の方が対話品質が高い。これは人間のチームでも変わらない。

「動くけど正しくない」は放置すると後から壊れる。品質ゲートが機能するかどうかが、組織の成熟度を示す。

## 第4章: 役割境界の再定義 — 肥大化したresearcherからreviewerを分離

Phase 3（04-08）で最初にやったことは、組織の整合性チェックだった。

researcherのCLAUDE.mdを見ると、担当業務が2種類混在していた。

- **調査・分析**: デイリーリサーチ、テーマ別深掘り調査、競合分析
- **レビュー（品質管理）**: 指示書レビュー、記事レビュー、スキルレビュー

「調査・分析」と「品質管理・レビュー」は、異なる専門性だ。調査は外部情報を収集して整理する仕事。レビューは成果物の品質を判定する仕事。同一エージェントに両方を持たせていたのは、最初に役割を細かく定義できていなかったからだ。

判断は分離。`reviewer.md`を新設し、researcherからレビュー責務を削除した。

以下のBefore/Afterは、分離前後の状態を追体験として描いたものだ。なお[先の記事](https://zenn.dev/tottoko_hamu/articles/claude-code-multi-agent-org)では researcher がレビューを担当していたが、この記事執筆時点（Phase 3）ではすでに分離済みである。実際の `.claude/agents/researcher.md` にはレビュー関連の記述はなく、調査・分析のみが定義されている。

```
Before（〜Phase 2）:
researcher ── 調査・分析・レビュー（品質管理）

After（Phase 3〜）:
researcher ── 調査・分析
reviewer  ── コードレビュー・記事レビュー（品質ゲート）
```

同じ日に、CEOの責務も整理した。

**問題**: CEOが直接ファイルを編集する場面が増えていた。組織インフラを整備するつもりが、気づけば設定ファイルを自分で書いていた。

**判断**: CEOは要件整理・設計レビュー調整まで。実装（コード・スキル定義・設定等）はdevチームに委任。

この判断はメモリに保存した。概念的に示すと、以下のような内容だ（実際のファイルを簡略化して引用）。

```yaml
# memory/feedback_ceo_devops_separation.md
CEOは要件整理・設計レビューの調整までを行い、
実装はdevチームに委任する。

How to apply:
(1) 要件整理
(2) 設計をdevに依頼
(3) レビューをresearcherに依頼
(4) 実装をdevに委任
```

メモリへの保存が重要な理由がある。Claude Codeはセッションをまたぐと文脈を忘れる。この判断をメモリに残しておくことで、次のセッションでも同じ原則が継続する。**対話で下した判断をメモリに蓄積することが、組織に「記憶」を与える**。

役割境界の再定義の対話パターンはこうだ。

1. 運用の中で「この役割重複してないか」という違和感が生じる
2. 人間が「今の状態でおかしいところはないか」と整合性チェックを依頼
3. AIが問題リストを出す
4. 人間が修正方針を判断
5. devopsが実装して完了

**組織設計は最初に完成させるものではない**。運用しながら育てるものだ。researcherが肥大化したのは、使ってみてはじめてわかった問題だった。

Phase 3 でのこの分離を経て、組織は最終的に8体になった（完成時点の全体組織図は「Phase 3 完成時点の組織図」節を参照）。

## 第5章: ブートストラップの罠 — 「権限を付与するには権限が必要」

Phase 3で最もトリッキーだった問題が、権限のブートストラップだ。

新しいエージェントを追加するとき、4つの権限エラーが発生した。

**ケース1: writerがzenn-contentに書き込めない**

writerに記事を書かせようとした瞬間、こんな応答が返ってきた。

> 「Write ツールの使用が拒否されました。`C:\Users\saito\Documents\zenn-content\articles\` へのアクセス権限がありません」

writerのsettings.local.jsonのスコープが足りなかった。`zenn-content/`パスを追加して解決。

**ケース2: devopsが設定ファイルを作れない**

devops自身のWrite権限が未付与だった。CEOが権限を付与して解決。

**ケース3: devopsの循環依存**

devopsに「自分の設定ファイル（settings.local.json）にWrite権限を追加する」よう依頼したとき、問題が発生した。

> 「私はsettings.local.jsonへのWrite権限がないため、自分の権限ファイルを変更できません」

「自分の権限ファイルを変更する権限がない」——典型的な鶏と卵問題だ。

解決策：CEOが親コンテキストから直接実行してブートストラップした。上位エージェント（またはオーナー）が先に環境を用意する。devopsが「私はここまでしかできない、これをやってほしい」と明示的に伝えてくれたからこそ、問題が可視化された。

**ケース4: reviewerがlogs/に書き込めない**

reviewerがレビュー結果を `logs/` に保存しようとした瞬間、こんな応答が返ってきた。

> 「Write ツールの使用が拒否されました。`C:\Users\saito\Documents\000.パートナー\logs\` へのアクセス権限がありません」

reviewerのEdit権限が未付与だった。CEOが `settings.local.json` に `logs/` を追加して解決。

この4事例から確立したのが「権限昇格は常に上位エージェントが行う」という原則だ。

```
権限付与のフロー:
新エージェント追加 → 権限不足が発生 → CEOが親コンテキストで解消 → 通常運用へ
```

重要なのは、**AIが「できません」と言ったとき、それが組織の設計上の問題である**ことに気づくこと。エラーは障害ではなく、組織の不整合を教えてくれるシグナルだ。

## 第6章: 命名と言語の統一 — 呼び方が組織を作る

Phase 3の最後に、地味だが重要な対話があった。

todo-dev・health-dev・devopsを毎回並べて書くのが冗長になっていた。「devopsとtodo-devとhealth-devに依頼して」という指示を何度もしているうちに、「これ、まとめて呼べないか」という感覚が生まれた。

**判断**: まとめて「devチーム」または「開発チーム」と呼称する。

これもメモリに保存した。概念的に示すと、以下のような内容だ（実際のファイルを簡略化して引用）。

```yaml
# memory/feedback_dev_team_naming.md
todo-dev, health-dev, devops をまとめて「devチーム」と呼称する。

Why: 個別エージェント名を毎回並べるのは冗長。
How: 実装系の指示は「devチームに依頼」で通じるようにする。
```

この判断の背景にあるのは「組織が大きくなると言葉の統一が必要になる」という体験だ。3体を毎回個別に書くのは管理コストだ。グループ名を決めることで、指示が簡潔になり、CEOの認知負荷が下がる。

言葉の統一は、単なる呼び方の問題ではない。**呼び方が概念を固定し、概念が役割を明確にする**。「devチーム」という名前ができたことで、「実装系の仕事はdevチームに」という原則が自然に成立した。

同じパターンが `logs/` の命名規則統一でも起きた。

```
YYYY-MM-DD_{種別}_{トピック}.md
種別: report / session / ideas / handoff / draft
```

この規則ができる前は、ファイル名がバラバラだった。規則を決めた後は、誰が作っても同じ形式になった。「devチームという呼称を決める」と「logs/の命名規則を決める」は、表面上は別の話に見えて、同じ対話パターンだ。**曖昧な概念に名前を付けることで、組織の共通言語が育つ**。命名規則は、エージェント間のコミュニケーション言語だ。

## Phase 3 完成時点の組織図

6日間の対話を経て、最終的に8体の組織になった。

```
CEO ─── オーケストレーション（人間が直接対話）
├── devops ──── 開発基盤・インフラメンテナンス
├── researcher ── 調査・分析
├── reviewer ─── コードレビュー・記事レビュー（品質ゲート）
├── secretary ── 情報整理・GitHub Issue管理・ルーティング
├── writer ───── 記事執筆・Zenn/Qiita/はてな投稿
├── todo-dev ─── /todo スキル開発
└── health-dev ─ /health スキル開発
```

reviewer は Phase 3 で researcher から分離して新設した（第4章参照）。Phase 2 時点では7体だった。

## まとめ: 6つの対話パターン

6日間で交わした対話を分類すると、6つのパターンに整理できる。

| パターン | 対話の内容 | 人間の役割 | AIの役割 |
|---|---|---|---|
| **ビジョン定義** | 何を作るかの言語化 | ざっくりした方向性を出す | 現状の問題を言語化する |
| **優先度選択** | 何をやらないかの決定 | 文脈を考慮して取捨選択 | 優先度付きで提案を尽くす |
| **差し戻し** | 品質ゲートの運用 | 構造化された指摘を返す | 指摘を受けて修正・再提出 |
| **役割再定義** | 肥大化・重複の解消 | 修正方針を判断 | 問題リストを出す |
| **ブートストラップ** | 権限の循環依存を解消 | 上位権限で解消 | 「ここまでしかできない」を明示 |
| **命名統一** | 組織の言語を揃える | 呼称・規則を決定 | 即座にメモリに保存 |

共通しているのは、**人間が方向性・判断・品質を担い、AIが提案・実装・記録を担う**という役割分担だ。

この6日間を通じて感じたのは、知的生産のボトルネックが変わったということだ。以前は「作業量」がボトルネックだった。今は「意思決定量」がボトルネックになっている。調査・実装・記事化はエージェントが担う。人間が集中するのは「何を調べるか」「何を採用するか」「品質は十分か」だ。

最初から完璧な組織を設計する必要はない。対話しながら育てる。壊れたところを直す。それが、この6日間が教えてくれたことだ。
