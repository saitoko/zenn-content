マルチエージェント組織を立ち上げてから3日で、`logs/` に37ファイルが溜まりました。

調査レポート、レビュー結果、記事ドラフト、ネタ帳、引き継ぎログ——全部 `logs/` に突っ込んでいたら、何がどこにあるか分からなくなった。そこで `logs/` を4ディレクトリに分離し、最終的に **logs/ のファイル数を37件 → 7件に分離しました**（logs/ の集中度: 100% → 19%）。

この記事は、別記事「[Claude Code でAIチームを組織した](https://zenn.dev/tottoko_hamu/articles/claude-code-multi-agent-org)」の続編です。マルチエージェント組織の概要は親記事で触れましたが、ディレクトリ設計の詳細と設計思想はここで深掘りします。エンジニアが「自分の組織でも同じことをやる」ための手順として読んでもらえると嬉しいです。

## Before / After

まず結論を先に見てください。

**Before（分離前・プロジェクトルート直下）**

```
logs/                      ← 37ファイルが混在
├── 2026-04-06_handoff_announcement-zenn.md
├── 2026-04-07_report_multi-agent-article-research.md
├── 2026-04-08_review_article-automation.md
├── 2026-04-08_draft_zenn-todo-agent.md
├── 2026-04-07_ideas_multi-agent-org-article.md
└── ...（handoff/report/review/draft/ideas が混在）
```

**After（分離後）**

```
logs/              ← 7ファイル（handoff 5件 + session 2件）
content/
├── reports/
│   └── research/  ← 調査レポート・設計書（15件移動）
├── reviews/       ← レビュー結果（14件移動）
└── drafts/        ← 記事ドラフト・ネタ帳（8件移動）
```

`logs/` を「エージェント間通信専用」に絞り、それ以外を種別ごとのディレクトリに分離しました。

## なぜ3日で37ファイルになったか

問題の根本は、ルールの粒度が粗すぎたことです。

各エージェントの定義（`.claude/agents/*.md`）には「成果物は `logs/` に保存」とだけ書いていました。resarcher が調査レポートを書いても `logs/`、reviewer がレビュー結果を書いても `logs/`、writer がドラフトを書いても `logs/`。全員が同じ場所に書き込む。

人間の組織で言えば、全部署が同じ共有フォルダに成果物を放り込んでいる状態です。ファイルが増えるにつれて3つの問題が顕在化しました。

**横断検索が困難**  
「レビュー結果だけ見たい」「writerへの引き継ぎを探したい」ときに `grep` を使わないと辿り着けない。

**アーカイブの粒度が粗い**  
月次で `logs/YYYY-MM/` に一括移動するルールがありましたが、中身の種別がバラバラで「整理した」とは言えない状態が続く。

**エージェントの出力先が曖昧**  
「自分はどこに書けばいいか」という判断をエージェントがするたびに `logs/` 以外の選択肢がなく、責務の境界がぼやけていた。

## 設計の依頼と初案

CEO（私）は問題を特定した後、設計を devops に委任しました。

devops への依頼はシンプルです。「`logs/` を種別ごとに分離する設計をしてほしい。ファイルの移行計画まで含めて」と伝えました。

devops が返してきた初案は、4ディレクトリ体制でした。

| ディレクトリ | 目的 | 主な書き手 |
|---|---|---|
| `logs/` | エージェント間通信（handoff, session のみ） | 全エージェント |
| `content/reports/research/` | 調査レポート・設計書 | resarcher, devops |
| `content/reviews/` | レビュー結果 | reviewer |
| `content/drafts/` | 記事ドラフト・ネタ帳 | writer, resarcher |

加えて、ファイル命名規則として略語プレフィックスを提案してきました。`ho_`（handoff）、`ss_`（session）、`rr_`（research report）のような形です。

ここで私が「何それ？」とフィードバックしました。

## 人間のフィードバックで変わった点

devops の初案を見た私（人間）が「何それ？」と違和感を言葉にしただけで、2点の修正につながりました。

**1. 種別プレフィックスを廃止する**

devops が `ho_`, `ss_` を提案したのは、「将来ディレクトリ名が変わっても、ファイル名からログの種別が追跡できるようにしたい」という意図からでした。ただ、私が「何それ？」と返したのに対して devops は「ディレクトリ名がすでに種別を表しているのでプレフィックスは不要です」と即座に解釈し直しました。`logs/` にあれば handoff か session、`content/reviews/` にあればレビュー結果、それだけで分かる。ファイル名に種別を重複して書くのは冗長です。

修正後の命名規則は `YYYY-MM-DD_{トピック}.md` に統一。既存ファイルの `review_`, `report_`, `draft_` などのプレフィックスは移行時に除去します。

**2. ネタ帳の `id_` プレフィックスだけは残す**

例外として、`content/drafts/` 内のネタ帳ファイルは `id_` プレフィックスを維持しました。`content/drafts/` にはドラフト（執筆中の記事）とネタ帳（アイデア段階）の両方が入るため、ファイル名だけで区別できる必要があります。

この2点の修正で設計が確定しました。

## なぜこの4分割にしたか

「なぜ4つか」という設計根拠を整理します。

**分割の判断軸は「書き手」と「消費サイクル」**

| ディレクトリ | 書き手 | 読み手 | 保持期間 |
|---|---|---|---|
| `logs/` | 全エージェント | 次のエージェント | 引き継ぎ完了後アーカイブ可 |
| `content/reports/research/` | resarcher, devops | writer, CEO | 永続保持（調査資産） |
| `content/reviews/` | reviewer | writer | 記事公開後に削除可 |
| `content/drafts/` | writer | reviewer, CEO | zenn-content push後に削除可 |

`content/reports/research/` だけがアーカイブしない設計です。調査レポートは「書いて終わり」ではなく、後から参照する資産として扱います。記事を書くたびに過去の調査を引き出せる状態を維持することが目的です。

**`logs/` を「エージェント間通信専用」に絞った理由**

`logs/` には引き継ぎヘッダー（`from/to/status`）の運用が集約されています。「誰から誰へ、今の状態は何か」が分かるファイルだけが残るべき場所です。調査レポートやドラフトは「誰かに渡す」ものではなく「参照される」ものなので、別の場所に出すのが自然です。

**4以上にしなかった理由**

当初「`content/reports/daily/`（デイリーリサーチ）は別扱いにすべきか」を検討しました。しかし既に `content/reports/daily/` は別ルールで管理されていたため、新たに分割は不要でした。既存の分離を尊重して、実際に問題が起きているところだけ手を入れるのが正しい判断です。

## エージェント定義に出力先を書く

この設計を機能させる鍵は、各エージェントの定義ファイル（`.claude/agents/*.md`）に出力先を明示することです。1行書くだけで、エージェントはそのディレクトリに成果物を書き込むようになります。

```markdown
# resarcher エージェント（抜粋）
## 出力先
- 調査レポート・設計書: `content/reports/research/`
- ファイル名: `YYYY-MM-DD_{トピック}.md`
```

出力先が定義にあれば、エージェントは「どこに書けばいいか」を毎回判断する必要がなくなります。逆に定義がないと、全員が `logs/` に書き込むという今回の問題が再現します。

## 実装：53ファイル変更を1コミットで

設計が確定したら、devops が実装しました。「37ファイルを手順書通りに移動するだけ」と思っていたのですが、プレフィックス除去や各エージェント定義の書き換えを含めると、触るファイルが一気に膨らみました。移行の全体像は以下の通りです。

| 移動元 → 移動先 | 件数 | 内容 |
|---|---|---|
| `logs/` → `content/reviews/` | 14件 | レビュー結果（factcheck, readability, final等） |
| `logs/` → `content/reports/research/` | 15件 | 調査レポート・設計書 |
| `logs/` → `content/drafts/` | 8件 | 記事ドラフト・ネタ帳 |
| `logs/` に残留 | 7件 | handoff 5件 + session 2件 |

ファイル移動以外に、同時に更新したものがあります。

- **エージェント定義** 4件（`.claude/agents/` の resarcher, reviewer, secretary, writer）の出力先パスを更新（devops は出力先が `logs/` のまま変更不要のため対象外）
- **各エージェントの CLAUDE.md** 4件（resarcher, reviewer, secretary, writer）の参照パスを更新
- **weekly.md**: アーカイブタスクを `logs/` のみ → `logs/`, `content/reviews/`, `content/drafts/` の3ディレクトリに拡張
- **README** 4件: `logs/`（更新）+ `content/reports/research/`, `content/reviews/`, `content/drafts/`（新規）
- **`.gitignore`**: `**/worktrees/` を追加（worktree残骸の混入防止）

コミット結果は `53 files changed, 757 insertions, 33 deletions`。

### git mv を使う理由

ファイル移動には `git mv` を使いました。`mv` だと「削除 + 新規追加」として記録され、`git log --follow` での履歴追跡ができなくなるためです。

```bash
# 移動とリネームを1コマンドで
git mv logs/2026-04-08_review_article-automation.md \
        content/reviews/2026-04-08_article-automation.md
```

移動と同時にプレフィックスも除去するため、1ファイル1コマンドです。実行中に devops から「`review_` プレフィックスを取り除くと、ファイル名が日付+トピックのみになって検索しやすくなる」というコメントが返ってきて、設計時の意図を現場で確認できた瞬間でした。

## 検証

実装後、devops に4項目（アーカイブタスク、エージェント間フロー整合、アクセス権限、その他懸念点）の検証を依頼しました。結果は全項目OK。残課題は軽微な2件——`content/reports/daily/README.md` が未作成（README を1枚追加するだけ）と、`secretary/.claude/` に worktree 残骸が残っている（`.gitignore` に1行追加するだけ）——でした。

「致命的ではないが、積み重なると気になる」という種類の課題として記録し、次のセッションで対処しました。

## 定量的な効果

| 指標 | Before | After |
|---|---|---|
| `logs/` のファイル数 | 37件 | 7件 |
| logs/ の集中度 | 100%（37/37件） | 19%（7/37件） |
| 種別混在 | handoff/report/review/draft/ideas が混在 | handoff/session のみ |
| レビュー一覧取得 | `grep` 必須 | `ls content/reviews/` で完結 |
| アーカイブ粒度 | 全部まとめて月別 | 種別ごとに月別 |

「`ls content/reviews/`」だけでレビュー一覧が見えるのは、地味ですが認知負荷の差として体感できます。

## 設計を終えて感じたこと

今回の作業を通じて改めて気づいたのは、「エージェントの出力先をどこにするか」という問いは、「そのエージェントの責務は何か」という問いと同値だということです。

ディレクトリが責務を体現する。`content/reviews/` に書けるのは reviewer だけ、`content/reports/research/` に書けるのは resarcher と devops だけ——このルールを設ければ、ファイルを開かなくてもディレクトリ名から「誰が書いたか」「何の目的で書いたか」が分かります。

人間のソフトウェア開発では、パッケージ構成やモジュール分割が「設計の見える化」として機能します。マルチエージェント組織でも同じことが起きます。ディレクトリ構成はエージェントの責務分担を物理的に表現したものです。

「とりあえず `logs/` に全部入れる」から始めること自体は悪くありません。ただし、エージェント数が増えてファイルが溜まってきたら、出力先を種別で分けることを検討してください。

次のステップとしては、ディレクトリ単位でのアクセス権限制御（どのエージェントがどのディレクトリに書けるか）や、成果物の保持期間ポリシーの自動化が考えられます。ディレクトリ構成を固めたことで、そういった発展的な制御の土台が整ったと感じています。
