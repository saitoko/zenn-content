# 第3部 届ける——書くだけでは届かないと知った日々

書く段では、素材を自分の文章にするまでの装置を扱った。第2部の出口に立っているのは、著者ペルソナの最終通読を通過した記事——「これは自分の文章だ」と最低限言える状態の原稿——だ。

第3部は、その原稿を世に出す段の話だ。

ここで扱うのは、公開の順序、SNS告知のタイミング、GA4で何を見るか、の3点に集約される。書く段が「自分の文章を保つための装置」の話だったとすれば、届ける段は「読者の前に存在させるための現場」の話になる。

Vol.2 では、書く装置（品質ゲート・writer・reviewer）の設計図までを描いた。届ける段の SNS告知・クロスポスト・GA4 は「自動化が止まったときの手動フォールバック例」として一覧されたが、設計レベルでは扱われなかった。第3部は、その一覧の手前にある「届ける段の設計」を、装置を通過した原稿に対して組み立て直す現場の記録だ。公開フローの設計図ではなく、設計図を毎日の運用に落として、つまずきながら整えていったときに見えてきた現場の輪郭——告知を忘れた一件、タイトル候補の選び方、はてなを先に出す理由、GA4 を3指標に絞る判断——を、5章で書いていく。

この段でつまずいたとき、書く段の手応えは消えやすい。「いい記事を書いた」という感触があっても、誰の目にも届いていなければ、書き続ける動機は静かにすり減る。逆に、届けるサイクルが回り始めると、公開後のデータが次の仕込みの素材として返ってくる。第4部「回収する」が成り立つのは、第3部で公開後のデータが取れる状態を作ったからだ。

第3部の終わりに渡したいのは、その「公開後のデータ」だ。次の段では、その数字を見て終わりにしない話をする。

## 第1章: ローンチ初日PV33の沈黙

ここから先は、書いた記事を世界に出す段だ。第2部で「自分の文章」として通した原稿を、誰かに届ける流通の話に入る。

第2部で、品質を担保する装置を毎日使い続ける運用に入った。reviewer がファクトを照合し、reader がペルソナで読者感情を測り、著者ペルソナが「自分の文章か」を最終確認する。三層のゲートを通過した記事が、手元に積み上がっている状態だ。

では、その記事を世の中に届けるために、次に何をするか。

「公開する」という言葉は、一言だが、実際には複数の工程の束だ。どのプラットフォームに、どの順序で、いつ、どんな形で出すのか。アフィリエイトリンクは誰が入れるのか。SNS告知はいつ、どこに投稿するのか。記事が読まれたかどうかは、どうやって把握するのか。

この工程のいずれかを誤ると、書いた記事の価値が半減する。公開順序を間違えると、SEO上の問題が起きる。アフィリエイトリンクの挿入を忘れると、収益化の機会が消える。告知のタイミングを外すと、記事は投稿直後に埋もれる。

第3部では、この「書いた後の全工程」を設計する。書くことよりも、届けることのほうが設計が必要だ。それを実感したのは、1冊目のローンチ当日のことだった。

### ローンチ当日の沈黙

2026年4月27日、1冊目の本を公開した。

書くことに関しては、準備ができていた。原稿は2日で完成し、reviewer と reader が多段でチェックし、著者ペルソナが最終通読を終えていた。品質には自信があった。

その日の GA4 を夕方に確認したとき、数字が並んでいた。

全体 PV: 33、総セッション: 57。direct 流入が52%を占め、検索からの流入は6セッションのみ。

そして Zenn の販売ダッシュボードには、「0」という数字があった。

書くことへの準備は万全だった。でも、届けることへの設計が追いついていなかった。

この経験が、第3部の出発点だ。

### PV=1の朝——「告知すらしていなかった」と気づく

ローンチから1週間ほど経った、2026年5月3日の朝のことだ。

その前日、私は自分なりに自信のある記事を1本公開していた。「Claude Codeの憲法を書いたら、1日で法律になった話」——AI組織のガバナンス設計について、自分が一番伝えたかったテーマの記事だ。

公開翌日、COO に向かって私はぼやいた。

「我ながらいい記事書いてると思うんだけどなぁ、読まれてないね」

このときの私は、原因をコンテンツ側に置いていた。テーマがニッチすぎるのかもしれない、タイトルが弱いのかもしれない、シリーズ化の設計が足りないのかもしれない——そういう仮説が頭の中で並んでいた。COO も同じ路線で、「テーマの独自性」「タイトルの再検討」「シリーズ化の設計」といった中長期の改善案を返してきた。

その流れの途中で、私は GA4 のデータを取ってみることにした。「数字を見てから話そう」というだけの軽い動機だった。

analytics-mcp で記事単体の指標を取り出した。

ページビュー: **1**。セッション: **1**。エンゲージメント率: **0%**。平均滞在時間: **0秒**。流入元: はてな新着枠から1セッションのみ。

PV=1。これは「読まれていない」ではない。「**誰の前にも存在していない**」状態だった。

同時期に公開した別の記事（Evernoteを3年放置していたら…）は PV=25。同じ運用者、同じプラットフォーム、ほぼ同じタイミングの公開で、25倍の差があった。

データを見たあと、私は短く呟いた。

「告知してなかったかなぁ」

これが、原因を自認した瞬間だった。

その記事は、はてなブログに公開しただけで、X にもFacebookにもThreads にも何も投稿していなかった。COO に告知を頼んでもいなかったし、自分でも手を動かしていなかった。「公開＝届ける」だと、どこかで無意識に思っていた。

恥ずかしい話だ。書く前のリサーチには時間をかけ、reviewer と reader を通し、ファクトチェックも済ませて出した記事だった。その全工程の労力が、一番最後の「告知する」という一行のせいで読者にゼロに近い状態で届いていた。

書いていた本人の中での「いい記事」と、世界に存在している記事は、別のものだった。

### 流通の最低限を確認する、というロジック

この事件のあと、私が COO と一緒に作ったのは、新しいコンテンツ論ではなかった。

`ops/playbooks/article/publish.md` という公開フローのPlaybookに、「即時SNS告知」のステップを追加した。コミット履歴に残っているこの1行の修正（コミット 5675b74）が、PV=1事件の唯一の構造的成果だ。

更新内容は3点に整理できる。

1. 公開順序ルールを「はてな → 即時SNS告知 → クロスポスト（24時間後にZenn/Qiita）」と明文化した
2. writer の手順に「SNS告知文（X/Threads/Facebook 各媒体向け）の作成」を加えた
3. blacktwist MCP が Threads/Bluesky にしか対応していないため、X と Facebook はユーザー手動投稿、という担当分担を明記した

この修正が示しているのは、コンテンツ論より先に確認しないといけない順序があるということだ。

「いい記事を書いているのに読まれない」と感じたとき、最初に手を伸ばすべきはタイトルでもサムネでもシリーズ化でもない。**流通の最低限が成立しているか**を確認することだ。具体的には次の3点に絞れる。

1. 主要なプラットフォームに公開されているか（公開ステータスが draft のまま放置されていないか）
2. SNS告知が、最低でも自分が運用している媒体のうち1つで行われているか
3. 公開後24時間以内に、GA4 で1セッション以上の流入が観測されているか

この3点が整っていない状態でコンテンツ論を始めると、「PV=1の記事のテーマ設計を半日かけて議論する」のような、原因とずれた場所で時間を消費することになる。私と COO はまさにそれをやりかけていた。

データを取らずに仮説で話すと、AI も人間も同じ方向に引きずられる。COO が中長期施策を提案してきたのは、私が「コンテンツが問題かもしれない」という前提で問いを投げていたからだ。最初に GA4 を見ていれば、議論はもっと早く「告知してましたか？」の方向に着地していたはずだ。

PV=1事件で学んだのは、コンテンツの話の前に流通の話、ということだけだ。ただ、そのたった1行のロジックを、私は自分の運用に組み込めていなかった。

### 公開から読者に届くまでの全工程

PV=1事件のあと、記事が読者に届くまでの工程を、改めて整理した。

```
① 原稿完成(draft)
    ↓
② プラットフォーム公開(はてなブログ)
    ↓
③ アフィリエイトリンクの挿入確認
    ↓
④ SNS告知(Threads / X / Facebook)
    ↓
⑤ クロスポスト(24時間後: Zenn / Qiita)
    ↓
⑥ GA4でのPV計測・検証
    ↓
⑦ 結果のネタ帳フィードバック
```

このうち、①の出口に立っている記事は、第1部「仕込む」（素材化）と第2部「書く」（著者ペルソナの最終通過）で作った原稿だ。第3部は②から⑦の話、つまり「書いた後の世界」を扱う。②③のうちタイトル候補生成とサムネ運用は第2章で、はてな先行公開とアフィリエイト挿入は第3章で、④SNS告知は第4章で、⑥GA4計測は第5章で、それぞれ実装レベルまで掘り下げる。⑤クロスポストは第3章後半で公開順序とセットで扱う。⑦ネタ帳フィードバックは第4部第1章へ送る。

多くの個人ブロガーやコンテンツクリエイターが、②で止まっている。公開しただけで「世に出た」と感じる。しかし、公開と到達は別物だ。特に、複数のプラットフォームに展開する場合、公開後の工程が複雑になる。

### チームが担うべき範囲はどこか

この工程のうち、チームが担える部分と、人間の判断が必要な部分がある。

| 工程 | 担当 | 理由 |
|------|------|------|
| ② プラットフォーム公開 | COO + スクリプト | 機械的処理だが、初回の設定・確認はCOO |
| ③ アフィリエイトリンク挿入 | writer | 執筆時に埋め込む（後付けより確実） |
| ④ SNS告知 | COO（Threads）/ ユーザー手動（X・FB） | ツール制約あり（後述） |
| ⑤ クロスポスト | スクリプト（crosspost.sh） | 自動化済み、ただし順序に注意 |
| ⑥ GA4計測 | COO + analytics-mcp | 週次ルーティン化 |
| ⑦ ネタ帳フィードバック | COO + writer | 第4部第1章で扱う |

このうち、「なぜはてなが先か」という順序の設計、アフィリエイトリンクの挿入ルール、SNS告知の設計、GA4の見方の4点が、特に知らないと損をする。以下の章でそれぞれを実装レベルまで掘り下げる。

### 「公開後のチェックリスト」を持つ

ローンチ初日とPV=1事件の経験から、公開後のチェックリストを作ることにした。

記事を公開した後、次の事項を順番に確認する。

1. はてなブログの記事URLが正常に表示されるか
2. アフィリエイトリンクが正しく機能しているか（クリックしてAmazonに飛ぶか）
3. SNS告知文の草稿をCOOに準備させ、即時（公開当日）に投稿する
4. frontmatterの `platforms.hatena.status` が published になっているか
5. 翌日のクロスポストに向けて `crosspost.sh` の実行予定をメモする

このチェックリストは最初は口頭確認でも構わない。ただ、記事本数が増えると記憶では管理できなくなる。Playbook として文書化することで、COOに「公開後チェックリストを確認して」と一言指示するだけで動いてくれる。

告知後、GA4のリアルタイム画面で流入が来ているかを10〜15分後に確認するのも習慣にしている。数字が動いているかどうかが、告知が届いたかどうかの即席フィードバックになる。

### あなたのチームでは

「書いた後の工程」を意識したことはあるか。公開して終わりになっていないか。

プラットフォームが複数ある場合、それぞれに公開する順序と理由を言語化することが、最初のステップだ。順序に理由がない場合、最も覚えやすかったものや、使い慣れたものが先になる。それが意図した設計とは限らない。

もし月1〜2本しか書けていないとしたら、一度「公開後の工程で詰まっていないか」を確認してほしい。書き終わった後の処理が重い・よく分からない・誰にどう頼めばいいか曖昧、という状態が続くと、「また書いても同じ手間がかかる」という無意識の抵抗感が生まれる。公開後の工程を整えることが、書く気力を取り戻す直接の処方になる。

あなたの「公開後チェックリスト」は何項目あるか。ゼロなら、まず3項目から書いてみることを勧める。

> **3体構成なら**: writer に告知文を5案出させる——それだけでも届く確率は変わる。「記事の核心を一言で」「読者が自分ごとと感じる問いかけ」「記事URL」の3点を含めて5本、と指示するだけでいい。自分で1本選んで貼る。書くと届くの間に1工程入るだけで、PV=1の朝はだいぶ遠ざかる。

## 第2章: タイトル候補5本の中から自分で選んだ理由

### タイトルが「届く確率」を決める

記事の品質がどれだけ高くても、タイトルで読者の目を止められなければ意味がない。

SNSのタイムラインも、はてなブックマークの新着も、Zennのトレンドも——読者が記事に出会う場所では、タイトルとサムネイルが「開くかどうか」の判断材料になる。記事の本文は、クリックした後の世界だ。

同じ原稿でも、タイトルが変わればクリック率は変わる。これは個人の感覚論ではなく、多くの実践者が経験していることだ。私自身も、同じ記事の告知文のバリエーションをいくつか試した経験から、タイトルの言葉の選び方で読者の反応が変わることを実感している。

もう一つ重要なのは、タイトルは**公開前に確定させる**という原則だ。公開後にタイトルを変更すると、はてなブログはURLが変わらないが、SNS告知済みのURLと記事タイトルの乖離が生まれる。Zenn・QiitaはフロントマターのSlugと紐づいているため、クロスポスト済みのタイトルをあとから変えると不整合が起きる。SEO観点でも、検索エンジンがインデックスした後のタイトル変更は評価の再計算を引き起こすリスクがある。

タイトルは「書いた後の設計」の最初の関門だ。書き終わった安堵感の中で、ここに手を抜かない。

### タイトル設計の原則——著者が実際に使っているもの

私がタイトルを考えるときに使っている原則を、実践レベルで書く。

**1. 読者の「自分ごと化」を起点にする**

「〜した人に向けて」という視点ではなく、「〜に詰まったことがある人」という視点で設計する。

前者は著者目線だ。後者は読者目線だ。

「Claude Code を使ったブログ運用の記録」と「Claude Code でブログチームを作ったら、一人なのに出力が3倍になった話」では、後者のほうが「自分にも当てはまるかも」と感じさせる確率が上がる。自分の現状や悩みに引っかかるタイトルは、読まれる。

**2. 数字・固有名詞・対比構造のうち1つは入れる**

三択のうちどれでも良い。ポイントは「具体性を持たせること」だ。

- 数字: 「3つの原則」「月3万字」「1か月で8本」
- 固有名詞: 「GA4」「Claude Code」「はてなブログ」
- 対比: 「書くのではなく届ける設計」「AIに書かせるのではなく考えさせる」

具体性があると、読者は「これは自分に関係があるかどうか」を判断しやすくなる。「ブログ運用について」という抽象タイトルは、誰にも当てはまるようで誰も読まない。

**3. 「何が得られるか」ではなく「何が変わるか」を示す**

「GA4の使い方」より「GA4でPVを見たら、次に書く記事が自然に決まるようになった」のほうが強い。前者は知識の提供で止まっている。後者は状態の変化を約束している。

読者が知識を求めているのではなく、変化を求めている——という前提でタイトルを設計すると、言葉の選び方が変わる。

**4. COOにタイトル候補を複数出させて自分で選ぶ**

私の実際の運用は、こうだ。

記事を書き終えたタイミングで、COOに「この記事のタイトル候補を5本出して」と指示する。候補が5本返ってきたら、自分で選ぶ。

選ぶのは必ず自分がやる。なぜか。「自分の言葉かどうか」の判断は、著者にしかできないからだ。COOが生成したタイトルがどれだけ論理的に正しくても、「なんか違う」という感覚を持っているのは書いた本人だ。それを言語化するのは難しいが、5本の候補の中から選ぶ作業なら、「どれが一番しっくりくるか」という感覚で選べる。

COOとのやり取りの実例を示す。

```
ユーザー: この記事のタイトル候補を5本出して。

COO: 以下の5案を提案します。

1. 【数字】Claude Codeチームに任せても、公開本数が増えない——3つの設計ミス
2. 【固有名詞】はてな・Zenn・Qiita を同時に運用して気づいた「クロスポスト設計」の要点
3. 【対比】記事は書くだけでは届かない——公開後の設計で変わる読者との距離
4. 【対比】AIに書かせるか、AIと届けるか——出力量より到達設計が先だった話
5. 【数字】公開フローを整えたら月3本が月8本になった——チーム運営のビフォーアフター

ユーザー: 3を採用。「記事は」を「ブログ記事は」に変えて。
```

この選択プロセス自体がタイトル設計だ。COOが考えて、私が判断する。分業として機能している。

### COOに任せる範囲と自分で判断する範囲

この章を通じて言いたかったことを整理する。

| 作業 | 担当 | 理由 |
|------|------|------|
| タイトル候補の生成 | COO | 複数案を短時間で出すのはCOOが得意 |
| タイトルの最終選択 | 著者（自分） | 「自分の言葉か」の判断は著者にしかできない |
| 公開判断 | 著者（自分） | タイトルが「これでいい」の最終判断 |

タイトルは、記事が世界に出ていく前の最後の関門だ。COOに生成を任せながら、選ぶのは自分——この分業が機能すると、「何を書くかは自分が決め、どう形にするかはチームが担う」という構造が、届けるフローにも貫かれる。

### あなたのチームでは

タイトルを決めるのに、どのくらい時間をかけているか。

「タイトルは最後に決めればいい」と思っていたとしたら、一度逆順を試してみてほしい。仮タイトルを最初に決め、原稿を書き終えたタイミングで改めてタイトルを磨く——この2段階設計のほうが、タイトルの質が上がりやすい。

COOに候補を5本出させて、自分で選ぶ。この作業が習慣になると、タイトルが「考える作業」から「選ぶ作業」に変わる。選ぶほうが速く、決断も軽くなる。

COOが返してきた5本の候補を画面に並べた。【数字】案、【固有名詞】案、【対比】案——それぞれが違う角度で同じ記事を切り取っている。最後に「3」に丸をつけた。手を動かしたのはこの1文字の選択だけだ。それでも、候補を5本出すのと「3」に丸をつけるのとでは、責任の重みが違う——その重さがちゃんと自分の側に残っている感触があった。

> **3体構成なら**: writer にタイトル5本を依頼し、自分で1本選ぶ。考える側ではなく選ぶ側に立つことが、書き続けるための分業のかたちだ。

## 第3章: はてなを先に出すと決めた理由

### この章は誰のための章か

本章は「複数プラットフォーム（はてな・Zenn・Qiita・noteのいずれか2つ以上）を運用している、あるいは近いうちに運用する予定の読者」向けの設計の話だ。

note だけ・はてなだけ・Zenn だけ——1プラットフォーム運用の読者は、この章は読み飛ばして第4章「Threadsだけ自動・X手動と決めた朝」へ進んで構わない。クロスポストは将来必要になったタイミングで再訪してほしい。それでも届ける段の全体ループのなかで本章が占める位置だけ1行で受け取っておくとすれば、「複数の場所に出すなら、どこを正規（プライマリー）に置くかを先に決めておく」——この一点だけだ。これさえ決まっていれば、2つ目を増やすときに迷わない。

### クロスポストの基本とSEO上のリスク

同一の記事を複数のプラットフォームに掲載することを、クロスポストと呼ぶ。

私の場合、1本の記事をはてなブログ・Zenn・Qiita の3プラットフォームに展開している。3つに出すのは、それぞれが異なる読者層・流入経路を持っているためだ。ただし、同じ記事を3つに出す場合、「どの順序で出すか」が重要になる。

Googleを含む検索エンジンは、同一内容が複数のURLに存在する場合、どちらが「オリジナル」かを判断しようとする。判断を誤ると、意図していないほうのURLが検索結果に表示されるか、あるいは両方の評価が下がる可能性がある。これを防ぐ理想的な手段が **canonical タグ**（「このページのオリジナルはここです」と検索エンジンに伝えるメタタグ）だが、Zenn・Qiita はともに CLI/frontmatter から canonical タグを設定できないのが現状（2026年5月時点）だ。Zenn では設定要望が2020年からIssueとして上がっているものの、未対応のままとなっている。そのため、本書の運用では **「はてな先行公開（24時間ルール）」と「クロスポスト時に挿入されるはてな記事へのフッターリンク」**の組み合わせで、SEO上の正規参照をはてなに置こうとしている。完全な解決策ではないが、現状の制約のなかで最善を尽くしている運用だ。

### なぜはてなブログをプライマリーにするのか（24時間ルールの理由）

はてなブログを第一公開先に選んだ理由は、SEO対策だけではない。アフィリエイトリンクの挿入が主要因の一つだ。

Zenn と Qiita は基本的にアフィリエイトリンクを記事に挿入することができない（Zennは規約上の制約、Qiitaは広告掲載の制約）。一方、はてなブログは通常のHTMLリンクとして Amazon アフィリエイトリンクを設置できる。収益化を意識した場合、アフィリエイトリンクを含む版を「プライマリー」として先に公開し、Zenn・Qiita にはリンクを除いたバージョンをクロスポストするのが自然な設計だ。

| プラットフォーム | 役割 | アフィリエイト |
|------|------|------|
| はてなブログ | プライマリー（先に公開） | 挿入あり |
| Zenn | クロスポスト（24時間後） | 除去済み |
| Qiita | クロスポスト（24時間後） | 除去済み |

クロスポストが「24時間後」なのには3つの理由がある。1つは、はてながGoogleにインデックスされるまでの時間（数時間〜1日）を確保するため。インデックス前に全プラットフォームに出すと、どれがオリジナルか判断が分散する。2つめは、はてな版での告知・SNS拡散を先行させることで、はてな版に一定の流入を作るためだ。3つめは、プラットフォーム側のレートリミット対策だ。Zenn は1日1投稿の公開制限があり、Qiita は連続して複数記事を publish しようとすると HTTP 429 が返る仕様になっている（2026年5月時点の実測）。複数記事を同日にクロスポストする場合、24時間以上の間隔を空けると制限に当たりにくい。`crosspost.sh` スクリプトがアフィリエイトリンクの除去も含めてクロスポストを処理するため、人間が手動で削除する必要はない。

### アフィリエイトリンクの設計——収益化の仕込み

「はてなをプライマリーにする理由はSEOだけではない」と前節で述べた。もう一つの理由が、アフィリエイトリンクの設計だ。ここをもう少し掘り下げておく。

**何を入れているか**

私が記事に入れているのは、ほぼ Amazon アソシエイトの書籍リンクだ。Claude Code 関連の書籍、GTD・生産性系の書籍、ライティング本など、記事の文脈で自然に言及できるものだけを選んでいる。商品を売ることより「この本、気になった」と思わせることの方が先にある。押し売りにはしない、というのが唯一のルールだ。

リンクの形式はシンプルなMarkdownリンクで書く。

```
[『はじめてのGTD』](https://www.amazon.co.jp/dp/XXXXXXXX/?tag=saitokohamu1-22)
```

はてなブログはHTMLリンクをそのまま描画するため、Amazon アソシエイトIDを含むURLは問題なく機能する。

**挿入のタイミング——「後から入れよう」は毎回忘れる**

一度、公開後にアフィリエイトリンクを入れようとして、2本続けて忘れた。

公開直後は SNS 告知・frontmatter の状態確認・クロスポストの予約で手が埋まる。「あとでリンク入れよう」がリストに入らないまま翌日になり、翌日には別の記事のことを考えている。結果、アフィリエイトリンクなしで記事が完成した状態が固定される。

この経験から、リンクの挿入は執筆時——writer が原稿を書くタイミング——に埋め込むルールにした。COO の担当表でも「③ アフィリエイトリンク挿入 | writer | 執筆時に埋め込む（後付けより確実）」と明記してある。原稿が完成した段階でリンクも入っている状態にする。公開フローにリンク挿入の工程を残さない。

**crosspost.sh が自動で除去する仕組み**

はてなブログ版にアフィリエイトリンクを入れると、Zenn・Qiita へのクロスポスト時に問題が起きる。Zenn は規約上、Qiita は広告掲載の制約で、アフィリエイトリンクを含む記事を出せない。

この問題を解決しているのが `crosspost.sh` スクリプトの `strip_affiliate_links` 関数だ。これは私が書いたコードではない——COOが内部処理として書いてくれたスクリプトだ。以下はそのアフィリエイトリンクを除去する処理の主要部分だ。仕組みを確認したい方は読んでほしい。コードが苦手な方は読み飛ばして構わない——「人間が手動でリンクを削除する必要はない」「COOがクロスポスト実行時に裏側で除去してくれる」という結果だけ覚えておけば十分だ。

```bash
# crosspost.sh 内の処理（主要処理の抜粋）
# ?tag=saitokohamu1-22 パラメータだけを除去し、リンク先URLは残す
body=$(printf '%s\n' "$body" | \
  sed -E 's/\?tag=[A-Za-z0-9_-]+-[0-9]{2}(&)/?\1/g' | \
  sed -E 's/\?tag=[A-Za-z0-9_-]+-[0-9]{2}([) "])/\1/g' | \
  sed -E 's/&tag=[A-Za-z0-9_-]+-[0-9]{2}//g')
```

`tag=saitokohamu1-22` というアソシエイトIDパラメータだけを削除し、Amazonへのリンク自体は残す。Zenn・Qiita の読者も Amazon のページへ飛べるが、アソシエイト経由ではない。はてなブログの読者が踏めば収益になる。

なお、この正規表現は `?tag=saitokohamu1-22` のような通常の長いURLパラメータを対象としており、`amzn.to` や `amzn.asia` 等のAmazonショートURLには対応していない（2026年5月時点）。ショートURLを記事に使うと、クロスポスト時にアソシエイトIDが残る可能性がある。原稿には通常の長いAmazon URLを使うことを推奨する。

この仕組みがあるため、原稿にアフィリエイトリンクを入れたまま公開フローを走らせれば、プラットフォームごとに適切な形で出力される。人間が手動でリンクを削除・復元する必要はない。私の側でやることは「アフィリエイト付き原稿のまま COO にクロスポストを依頼する」だけで、Zenn・Qiita 用にリンクを差し替えた別バージョンを自分で作る作業は一切発生しない。

アフィリエイトリンクが含まれる原稿をはてな向けに維持しつつ、クロスポスト版は自動的にクリーンな状態になる——これが「はてなプライマリー」の運用と組み合わさって機能している。

**現状の収益実態（正直に書く）**

アフィリエイト収益は、月に数百円から数千円の範囲に収まっている（2026年4月〜5月の実測。月による変動あり）。

生活費を賄うことを目的にした設計ではない。

私がこの設計を最初に作ったのは「収益化の仕組みを設計しておくこと」が目的だった。SEO 検索流入が育つのには3〜6か月かかる。記事が積み上がって検索に引っかかり始めたとき、アフィリエイトリンクが入っている記事と入っていない記事では結果が変わる。仕組みを後から入れようとしても、すでに公開済みの記事を遡ってリンクを修正するコストは大きい。

「今は稼げなくても、仕組みを先に作る」という考え方だ。SEO の長期育成と組み合わせて、じわじわ機能するものとして設計している。

収益化を目的にブログを始めているわけではないが、仕組みがあれば「書いた記事が何らかの形で還元される」という感覚が生まれる。それが書き続けるモチベーションの一部になっている。

### 流入構造と各プラットフォームの特性

実際の運用データ（2026年4月7日〜5月5日（29日間）のGA4集計）を見ると、各プラットフォームの流入構造は大きく異なる。

| プラットフォーム | Direct | Organic Social | Organic Search |
|------|---:|---:|---:|
| Qiita | 86% | 1% | 10% |
| Zenn | 68% | 5% | 17% |
| はてな | 25% | 66% | 3% |

Qiitaは86%がプラットフォーム内からの流入（タグ・Trending経由）、Zennはプラットフォーム内発見と検索の両輪、はてなはSNS拡散が66%で流入の主力だ。

1記事あたりのPV効率も異なる。

- Zenn（12本、466 PV）: **38.8 PV/記事**
- Qiita（22本、575 PV）: **26.1 PV/記事**
- はてな（50本、639 PV・2ドメイン合算）: **12.8 PV/記事**

はてなは1記事あたりの到達数が最も少ない。にもかかわらずプライマリーに置くのは、アフィリエイト収益の設計とSEO上の位置づけという理由があるためだ。「PV効率が高いZennをプライマリーにすればいいのでは」という疑問は自然だが、Zennにアフィリエイトを入れられない制約と、はてな先行公開による検索流入の長期的育成という観点で、はてなを軸にしている。

### 実装レベルでの運用

公開フローを手順として明示する。

```
[Day 0 - はてな公開当日]
1. はてなブログに原稿を投稿（アフィリエイトリンク挿入済み）
2. SNS告知（18時ごろ：後述）
3. hatena-publish.sh の実行時に platforms.hatena.status が自動的に published に更新

[Day 1 - クロスポスト日]
4. crosspost.sh を実行（アフィリエイト除去→Zenn/Qiita へ）
5. crosspost.sh がフッターにはてな記事URLへのリンクを自動挿入（SEOの正規参照補完）
6. crosspost.sh の実行時に platforms.zenn.status / platforms.qiita.status が自動的に published に更新
```

手順は `ops/playbooks/article/publish.md` に記載されており、COOはPlaybookを読んでから実行する。過去に一度、直前に開いていたZennの下書きをそのまま公開してしまった事故があった。「公開して」という指示を受けたとき、コンテキストに引きずられてZennを先に動かしてしまった。この経験から、公開指示を受けたらPlaybookを読むというルールを加えている。

### あなたのチームでは

複数プラットフォームに展開する場合、あなたの「プライマリー」はどこか。その理由は言語化されているか。

プラットフォームごとの特性（読者層・流入構造・収益化の可否）を整理し、どの順序でどのURLを正規とするかを決めることが最初のステップだ。使っているプラットフォームが1つだけなら、この設計は不要だ。ただ、2つ目・3つ目を追加する前に、この設計を持っておくと混乱が防げる。

> **3体構成なら**: まず1プラットフォームで運用し、流入が安定してから2つ目を検討する。複数展開・クロスポスト・canonical の設計は、流通の最低限が回り始めてからの宿題でいい。1つ目で「書いて、告知して、読まれた」のサイクルを20本ぶんくらい回したあと、本章に戻ってくれば十分間に合う。

## 第4章: Threadsだけ自動・X手動と決めた理由

### 「書いたら告知する」が機能しない理由

記事を公開したら、SNSに告知する。これは多くの人がやっていることだ。

ただ、告知の仕方には設計が必要だ。多くの場合、公開直後に即投稿するか気が向いたときに投稿するかのどちらかだ。私のチームが採用しているのは「毎日18時ごろに、公開記事から一番読んでほしい1本を選んで告知する」という方針だ。

### 18時の1本だけルール

具体的には次のように運用している。

- 告知タイミング：毎日18時ごろ
- 告知本数：その日の公開記事から「一番読んでほしい1本」を選ぶ
- 複数公開日：COOがピックアップ案を提示し、ユーザーが最終選定

「18時」という時刻は、仕事が終わる時間帯・夕食前の時間帯に投稿が読まれやすいという一般的な経験則から選んでいる。自分のデータでの検証はまだできていない。

「1本だけ」にする理由は、分散を避けるためだ。同日に複数記事を告知すると、どの記事を読むかが拡散者側も受け手側も迷う。1本に絞ることで、シェアが一点集中する。

### プラットフォームごとの担当分担と流入実績

SNS告知の設計で最初にやることは、「自動化できる部分と手動でやる部分を明確に分ける」ことだ。最初から分けて設計するから、告知フローが止まらない。

私のチームでは次の分担になっている。

| 媒体 | 担当 | 手段 |
|------|------|------|
| Threads | COO | blacktwist MCP の `create_post` |
| X（旧Twitter） | ユーザー手動 | blacktwist 不対応 |
| Facebook | ユーザー手動 | 個人アカウント |

補足として、ツールの制約に触れておく。blacktwist MCP は Threads と Bluesky のみ対応しており、XへのCOO自動投稿はできない。ただし、これは「Xを諦める」という話ではない。自動化できる部分（Threads）と手動でやる部分（X・FB）を最初から分けた設計にしておけば、制約があってもフローは止まらない。

実際の流入実績（2026年4月7日〜5月5日（29日間））を見ると、SNSからの流入にはっきりした傾向があった。

はてなブログへの流入の66%がOrganic Social（SNS経由）だった。3つのプラットフォームの中で、はてなはSNS拡散への依存度が飛び抜けて高い。この29日間の実測で、流入元の内訳を見ると、Facebook系（139セッション）がX（4セッション）を大きく上回っていた。Threadsは GA4 計測上ほぼゼロだが、これはThreadsアプリ内ブラウザがreferrer情報を落とすケースが多く、direct流入に分類されるためで、告知効果がゼロという意味ではない。ツールが整っていないからといって後回しにすると、最も効く流入経路を捨てることになる。

### 告知文の作り方と管理

告知文は、COO が事前に草稿を作り、ユーザーが内容を確認してから投稿する。構成要素は「記事の核心を一言で」「読者が自分ごとと感じる問いかけ」「記事URL」の3点だ。「新しい記事を書きました」と「チームを持ったのに記事が増えていない——その原因が公開フローの設計にあることが分かりました」の差は、読者への問いかけがあるかどうかだ。過剰な煽りや誇張は避ける。

告知文は `tmp/sns-announce/YYYY-MM-DD_<slug>.md` に保存する。PVが突出した記事の分析や「この記事は告知したっけ」という記憶の曖昧さを解消するためだ。

記事URLは「読者の感情が最も動く文の直後」に置くのが原則だ（CTAの位置はSNS告知でも同じ）。ハッシュタグは媒体によって効果が異なる（Threadsは限定的、Xは発見効果あり）。

### あなたのチームでは

SNS告知を「記事を公開したら都度投稿する」パターンで運用している場合、複数記事の公開日に告知が分散していないか。

告知頻度を下げ、1回の告知に力を集中させることで、到達数が増える場合がある。投稿の「量」よりも「質と集中」が、SNS告知の設計原則だ。

あなたのSNSで最も流入が多いのはどの媒体か。データを確認せずに「Xが一番だろう」と感じているとしたら、一度GA4の流入元をプラットフォーム別に分解して確認することを勧める。思い込みと実態が違う発見があるかもしれない。

> **3体構成なら**: SNS は1媒体だけ・18時1本だけ、を最小ルーティンにする。X しか使っていないなら X だけでいい。「毎日18時に、その日の記事から1本だけ貼る」ルールを守るだけで、告知忘れによる PV=1 はだいぶ起きなくなる。媒体を増やすかどうかは、1媒体で告知が習慣化してから考えれば間に合う。

## 第5章: GA4 で3つの指標だけを見ると決めた

PVを確認することの目的は「次の行動を決める」ことだ。多く読まれた記事のテーマを次のネタ帳に転記する、少ししか読まれなかった記事の告知・タイトルを改善する、プラットフォームごとの流入構造を把握する——このアウトプットが出せないなら計測は意味がない。

本章は、GA4 を「すでに接続している前提」で、毎週どう読むかの運用ルーティンを書く。analytics-mcp の接続設定そのもの（GCP の API 有効化、認証情報の準備、MCP サーバー登録）は、本文の流れを乱すため章末「付録: GA4 + analytics-mcp の接続手順」に分離した。まだ接続していない方は、運用イメージを先に読んでから付録に進んでも構わないし、付録を先に済ませて戻ってきても構わない。本文だけで「毎週何を見て、次に何をするか」は理解できる構造になっている。

### 毎週見るべき3つの指標

GA4のデータは多岐にわたるが、最低限見るべき指標を3つに絞る。

**指標1: 記事別PV（先週分）**

どの記事が先週最も読まれたか。「読者が求めているテーマ」の実データになる。出力をそのままネタ帳候補として使える。「PVが多かった記事のテーマを深掘りする」は、最もデータに基づいた次の一手だ。

**指標2: 流入元の比率**

Direct / Organic Social / Organic Search の3区分を確認する。

- Direct が高い → プラットフォーム内の読者・ブックマーカーが増えている
- Social が高い → SNS告知が機能している
- Search が低い → 検索流入が育っていない（初期は正常。3〜6か月後に再確認）

はてなブログはSNS依存が高いため、Socialが高いのは正常状態だ。ただし、Search が継続的にゼロなら、タイトルやメタ情報の改善を検討する。

**指標3: 週次セッション数の変化**

先週と今週のセッション数を比較する。増加 / 横ばい / 減少のいずれかを把握する。絶対値より変化の方向が重要だ。

「なぜ減ったか」を告知の有無・テーマの性質・更新頻度と照合することで、次週の行動が決まる。

### ルーティンとして設計する

この3点のチェックを、週次ルーティンとして固定する。週に1回（例：月曜朝）、COOに「先週のGA4レポートをまとめて。記事別PV・流入元比率・セッション変化の3点で」と指示するだけだ。GA4 の画面を私が直接開く必要はない——COO が analytics-mcp 経由でデータを取得し、3指標に整形して返してくる。私は出てきた数字を眺めて、次の行動を決める側に回る。これを週次タスクとして登録しておけば確認漏れが防げる。

ポイントは「データを見て終わり」にしないことだ。サマリーの末尾に「次週のアクション」を1点入れる——例えば「最多PV記事のテーマを深掘りした記事をネタ帳に追加する」——この習慣が、データを行動につなげる。

### Zennのデータと数字の読み方

同一のGA4プロパティにzenn.devのデータも集計されており、`hostName` フィルタでZenn単体の分析が可能だ。注意点として、プロパティ名が「はてなブログ」であってもZenn・Qiitaのデータを含むため、プラットフォームごとに絞る場合はフィルタが必須だ。

実測（2026年4月〜5月）では、Zenn Bookのページも章単位で計測でき、トップページから序章・第1章…と進むにつれて読者が減少するファネルがGA4上で可視化される。「どこで読むのをやめたか」が章単位で分かるのは、改訂の優先度を決める上で有用だ。

数字を見慣れない場合の参考値として、私の運用初期（2026年4月）の1記事あたりPV効率を示す（Zenn: 約38.8・Qiita: 約26.1・はてな: 約12.8 PV/記事）。「先月と比べてどう動いたか」「告知した記事としていない記事の差」という**相対的な変化を読む**ことが、GA4活用の最初のステップだ。

### あなたのチームでは

アクセス解析ツールを接続しているか。接続しているとしたら、毎週確認できているか。

確認する指標が3つに絞られていなければ、GA4を開いても何を見るか迷い、確認が重くなって継続しにくくなる。まず「毎週この3点だけ見る」と決めることが、計測ルーティン化の最初の一手だ。

接続自体は付録に手順をまとめてある。最初の1日だけを「セットアップの日」と決めて、付録に従って GCP の API 有効化と MCP 登録に集中するのが確実だ。「いつかやろう」のままでいると、何百本記事を出しても届いているかどうか分からないまま運用が続く。

> **3体構成なら**: 接続待ちでも始められる。今週公開した記事の流入元（はてなのアクセス解析・Zennのダッシュボード等、各プラットフォーム標準の管理画面で十分）と、先週との新規記事PVだけを週1で眺める——それだけでも「回収する段」は始まる。3指標の完全版（記事別PV / 流入元比率 / 週次セッション変化）は、後から analytics-mcp を入れた日に切り替えればいい。

### 付録: GA4 + analytics-mcp の接続手順

ここから先は、これから GA4 を接続する読者への接続メモだ。すでに接続済みの方は読み飛ばして構わない。本文の運用ルーティンだけ理解できていれば、第3部としては十分だ。

正直に書いておくと、私自身も2026年4月12日に詰まった。GCP コンソールの「API とサービス」画面を開いて、それらしいボタンを押して「有効化済み」の表示が出たので終わったつもりでいたら、リアルタイムレポートに何も流れてこなかった。エラーログを Claude Code 側で出してもらったら「Data API が有効化されていません」と書いてあり、初見では何のことか分からなかった——私が押したのは Admin API のほうだけで、Data API という別物がもう1つあったのだ。COO が「これは2つ別々に有効化が必要です。もう一度コンソールに戻ってこのボタンを押してください」と画面遷移ごとに案内してくれて、ようやくリアルタイム計測に数字が流れ始めた。

私のチームでは、GA4 のデータを analytics-mcp（MCP サーバー）経由で Claude Code から直接取得している。2026年4月12日のその1セッション（約1日）で、API セットアップからリアルタイム計測の確認まで完了した。私自身は GCP コンソールを開いて API ボタンを押した記憶はあるが、何を押せばいいかの手順は全て COO が画面遷移ごとに案内してくれた。接続設定そのものの管理（認証情報の保管、MCP 起動コマンドのメンテナンス）も COO 側に置いてあり、私は「先週の GA4 を見せて」と一言指示するだけで数字が返ってくる状態だ。

**接続に必要な4ステップ**

COO の案内に従って操作した手順を、自分のためのメモとして残しておく。

```
1. GCP で「Google Analytics Admin API」を有効化
2. GCP で「Google Analytics Data API」を有効化  ← 詰まりポイント
3. analytics-mcp を MCP サーバーとして登録
4. はてなブログに GA4 の測定IDを設定
```

**詰まったポイント: API は2つある**

冒頭でシーンとして書いた通り、Admin API と Data API は**2つを別々に**有効化する必要がある。片方だけでは動かない。セットアップは「リアルタイムレポートで実際の数値が見えた」状態を確認して完了とする。ここを通れば、あとは MCP 登録と測定ID設定の2手だけだ。

**コードを書けなくても進める**

私自身はコードを書ける人間ではないが、COO に「analytics-mcp を接続したい。手順を案内して」と頼めば、画面遷移単位でナビゲートしてくれる。GCP コンソールのどの画面のどのボタンを押すか、エラーが出たらどう読むか——その逐次案内があれば、ノンプログラマーでも1日で接続まで届く。「自分には早い」と感じても、最初の1日だけ COO と並走すれば本文の運用ルーティンに合流できる。

第3部では、書いた記事を世に出すための現場の設計を扱った。

ローンチ初日の沈黙とPV=1事件から、流通の最低限を確認するというロジックを取り出した。タイトルはCOOに5本出させて自分で選ぶ。はてなをプライマリーに置き、24時間後にZenn・Qiitaへ展開する理由を、SEOとアフィリエイト設計の両方から組み立てた。SNS告知は、自動化できるThreadsと手動が必要なX・Facebookを分けて、18時の1本だけルールで集中させる。GA4は3つの指標——記事別PV、流入元比率、週次セッション変化——だけを毎週見る。

これらの工程が揃ったとき、手元には公開後のデータが残る。記事別PV、流入元、セッションの推移、エンゲージメント。届ける段の出口にあるのは、その数字の束だ。
