# 第2部 書く——自分の文章であり続けるために

書くことは、AIに書かせれば終わる話ではなかった。

第1部では、書く前の段——気づきを拾い、受け皿に置き、ready 状態の素材ファイルを溜めるまでの工程を扱った。素材は手元にある。チームも回っている。なのに、その素材を記事にしようとした瞬間、別の壁が立ち上がる。「書き出しから詰まる」「AIに書かせると、どこか他人の文章になる」「自分が書いている感覚が消える」——拾うことと書くことは、別の段だった。

ここからは、書く段の話をする。素材を「自分の文章」にするための、現場の運用記録だ。

この段で扱うのは、書き始める前の対話で切り口を定めるところから、AIに書かせる前に組み立てておく4つの仕掛け、書き上がった原稿を最後に「これは自分か？」と問う装置、生の言葉が writer に届く構造、そして主軸を変えずに別ジャンルを並走させて自分の輪郭を保つ話まで——「自分の文章であり続ける」ための設計と運用の5章分だ。

ここで一つ、Vol.2との関係を置き直しておく。Vol.2 では、品質ゲートを設計図として書いた。第2部第4章「writer が数字を『創作』した」事件から創作禁止6項目を起こし、第3部第4章で著者ペルソナ最終通読を「自分の文章か」を最後に問う層として組み上げ、reviewer の差し戻し理由を `writing-guidelines.md` に翻訳して writer に読ませる——その全体像を、Vol.2 は**装置の設計図**として描いた。一方、対話の生の言葉が writer に届く素材レイヤーや、主軸を変えずに別ジャンルを並走させる書き手の維持機構は、Vol.2 の射程には入っていなかった。第2部はその空白を埋めながら、装置を毎日使い続けたら現場で何が起きたかを書いていく。

著者ペルソナが朝の通読で同じ違和感を3章まとめて拾ってきた朝、writer が「v2.1.117」という存在しないバージョン番号を補完した日、対話の生の言葉が `writing-guidelines.md` に届かないと気づいた水曜の夜、ウイスキーを note に逃がして主軸を保ち直した1か月——どれも、設計図のとおりに装置が動いたあとで初めて出てきた問題だ。装置は確かに動く。でも、装置を使う側の人間が「これは自分の文章か？」と問い続けないと、装置の出力は他人の言葉のままになる。設計図が動くことと、毎朝その装置の前に座って自分の文章を仕上げ続けることは、別の話だった——その「別の話」を、これから5章かけて書いていく。

第1部から受け取るのは、ready 状態の素材ファイル群と、著者の「気づきの得意パターン」だ。次の段（届ける）に渡すのは、著者ペルソナ通読を通過した記事——「これは自分の文章だ」と書いた本人が頷ける状態に整えた原稿だ。

書き始めから書き終わりまで、装置の隣に座って書き続けたときに何が起きたかを、ここから書いていく。

## 第1章: 「実施筆」とタイポしたまま投げた

第1部で受け皿を作った。第2部では、拾った素材を「自分の文章」にする段に入る。本章はその入口、対話で切り口を定める話だ。

第1部第4章で見た「対話が発酵装置になる」仕組みを、本章では使う側に回って起動する。発酵が勝手に起きるのを待つのではなく、こちらから話しかけて切り口を定めにいく。書き始めるための入口の対話だ。

### 完璧な問いを用意しなくていい

第1部第4章で見たように、対話はネタを発酵させる装置だ。しかしその対話を「どうやって始めるか」で詰まる人は多い。

「何から話しかければいいか分からない」「問いをうまく言語化できない」——この詰まりは、「完璧な問いを用意してから話しかけなければならない」という思い込みから来る。

実際にはその逆だ。

私が「ブログ記事のネタ作りから実施筆までの工程を記事にしたい」とClaude Codeに送ったとき、「執筆」を「実施筆」とタイポしたまま投げていた。テーマの輪郭も定まっていない。それでもこの一言が起点となり、最終的に7工程を扱う記事が生まれた。

問いは未完成で構わない。むしろ未完成のほうが対話で転がる余地が大きい。完成した問いは、すでに答えの形が決まっている。転がる方向がない。

この感覚は第1部第1章の「採掘しに行くのではなく気づく」という話と地続きだ。気づいた瞬間に作業の流れを止めてメモを取るのが面倒なら、そのままの状態でClaude Codeに投げてしまえばいい。「今のこれ、記事のネタになる？」その一言でいい。整理は話しかけた後にやる。

### 返ってくる質問に答えるだけで方向が定まる

話しかけると、大抵の場合は質問が返ってくる。

私の場合、「汎用ノウハウ記事にしたい」「頭の中にある工程を伝えたい」と返した後、COOは次の問いを投げてきた。

> 「方向性が見えてきた」の中身は、読者が定まる／切り口が定まる／構成が定まる、のどれに近いですか？

私はこう返した。

> 切り口が定まるが多い。コレが決まると構成案はclaude codeが考えてくれる

この一文は、質問に答える過程で出てきた言葉だ。「こう言おう」と用意していたわけではない。COOに「切り口が定まることが核になりそうですね」と返ってきて、そこで初めて自分でも「ああ、確かにそこが核なのか」と気づいた。

答えることで思考が整理される。これは「受け身」に見えて、実は能動的な思考作業だ。問いを受け取り、自分の中で照合し、選び取って返す——その一連の動きを自分がやっている。AIが切り口を提示してくれたのではなく、AIの問いに自分が答える過程で、自分の中にあった切り口が言葉になって表に出てきた。

対話の目的は何かを「書いてもらうこと」ではない。**切り口を定めること**だ。切り口が決まるまで話し続ける。切り口が決まった瞬間から、『書かせる』が機能し始める。

返ってくる質問の4つの軸を知っておくと、答えやすくなる。

- **角度**: 自分の実運用フロー紹介か、汎用ノウハウか、ケーススタディか
- **読者**: 誰に向けて書くか
- **素材**: 手持ちの素材があるか、これから集めるか
- **ボリューム**: 短めか、長めか

この4つのどれかに答えられれば、対話は前に進む。全部答えられなくても構わない。

### 「わからない」と返すのは弱さではなく戦略だ

ここが、多くの人がやっていないことだと思っている。

AIから質問が返ってきて「うまく答えられない」となったとき、無理に答えようとするか、対話を閉じるかの二択になりがちだ。私はその対話の中で第三の選択肢を使った。COOに問われて、そのまま正直に返した。

> 答えにくい場合は「わからない」と言ってしまう

こう返したとき、何が起きるかも確認した。私の答えはこうだ。

> 質問切り口を変えるか、「例えばこんなことです」とか言ってくる

どちらも実際に経験している。「わからない」と返すと、AIは問いの角度を変えてくれる。あるいは「例えば〇〇のようなことですか？」と具体例を出して、「この方向ですか？あの方向ですか？」という選択肢に変換してくれる。

「AIの問いには答えなければいけない」という思い込みを外すと、対話がむしろ深まる。詰まった箇所で正直に「わからない」と返すことで、AIが角度を変えてくれ、気づかなかった切り口が見えてくる。詰まりが突破口になる。

「わからない」という言葉は、思考の終わりではなく**再起動の合図**だ。

### 「わからない」が使えるタイミング

実際に使えるのは、どんな場面か。

**自分の感情や動機が言語化できないとき**。「なぜこのネタに興味を持ったのか」「この体験のどこが重要なのか」——自分でも腑に落ちていないことを問われたとき。

**複数の選択肢から選べないとき**。AIが「A方向とB方向、どちらが近いですか？」と聞いてきたとき、どちらとも言えない感覚があれば「わからない、どちらでもある気がする」と返せばいい。

**問い自体の意味が理解できないとき**。質問の前提が分からず、そもそも何を聞かれているのかピンと来ない場合。「その質問の意図が分からない」と返すと、別の言い方で聞き直してくれる。

「わからない」以外にも、似た効果を持つ返しがある。「うまく言えないが、なんとなくこういう感じがする」「その方向ではなく、むしろ反対かもしれない」——答えの断片を出すだけでいい。完成した答えでなくても、その断片が次の問いの材料になる。

### 切り口が決まるまで話し続ける

一度の往復で切り口が決まることは少ない。何度か行き来して、徐々に輪郭が絞られていく。

私の場合、最初に「気になったことを話しかけることで解像度が上がる」という観察を出した。COOがそれを「話しかける→質問が返ってくる→答えていると方向性が見えてくる」という構造に整理して返してきた。私はそこで「あ、そういう骨格になるのか」と初めて気づいた。

この「気づき」は一人で考えていたら出てこなかった。話しながら整理されたものだ。自分の頭の中にあったものが、対話を経て輪郭を持った。

**切り口が定まるサインは、「そう、それが言いたかった」という感覚だ。**

COOが構造を整理して返してきたとき、反論したくなるか、「そう」と感じるか。「そう」と感じたなら、その切り口が正しい。反論したくなったなら、「違う、どちらかというと〇〇のほうが近い」と返せばいい。その返しが、次の絞り込みになる。

「どうやって対話を終わらせるか」を心配する必要はない。切り口が定まると、自然に「ここから先は書いてもらおう」という気持ちになる。話すことへの空腹感が満たされた感覚とでも言えばいいか。そのタイミングで「じゃあここから書いて」と委任すればいい。

ちなみに対話の時間は長い必要はない。私が7工程の記事の切り口を定めた対話は、約10往復で終わった。「気になったことを話しかける→質問に答える→『わからない』を使う→切り口が絞られる」この流れが回れば、5分もかからないことも珍しくない。

### あなたのチームでは

完璧な問いは必要ない。「なんとなくこういうことを書きたい」「最近気になっていること」「うまく言えないけどこんな違和感がある」——その状態のまま話しかけてほしい。

返ってくる質問の4軸（角度・読者・素材・ボリューム）のうち答えられるものだけ答える。詰まったら「わからない」と正直に返す。AIが切り口を変えてくれる。「そう、それだ」という瞬間まで話し続ける。

切り口が決まってから初めて、『書かせる』が機能する。最初から書かせようとするのは、工程の逆転だ。

どんなに精密な文章生成ツールを持っていても、何を書くかが決まっていなければ機能しない。「わからない」と正直に返せる対話の場があれば、その「何を書くか」は対話の中から自然に浮かんでくる。

> **3体構成なら**: 「この素材で何が書けそうか、切り口を3つ出して」と writer に一言投げるだけでいい。角度が返ってきたとき「そう、それだ」と感じるものを選ぶだけで、切り口の対話と同じ効果が得られる。

## 第2章: 自分の文章じゃないと感じた瞬間

### 読み返して「これ自分じゃない」と感じた朝

昨晩の原稿を読み返した。

前夜寝る前、writer に Vol.1 のある章のリライトを投げて、そのまま寝てしまった。起きたら章まるごと書き上がっていた。事実関係は合っている。論旨も通っている。ファクトチェックも通っている。reader レビュー（想定読者ペルソナ）も合格を出した原稿だ。

なのに、3段落ほど読み進めたところで手が止まった。

これは、自分の文章じゃない。

主張の中身は自分が言いそうなことだ。並んでいるエピソードも自分が体験したものだ。それでも、文章のどこかに「自分が書いた」と頷けない手触りがある。語尾の選び方なのか、段落の畳み方なのか、読者への語りかけの距離感なのか——一カ所を指せない。でも、違う。

最初に確認したのは、自分のメモではなく writer の差分ログだった。「どこかで writer が暴走して創作したのでは」と疑った。違った。事実は引いている。引用も合っている。それなのに違和感が残る——この種類の違和感を初めて言葉にした朝だった。

本章はその先——AIが原稿を書き上げたあとに、「これは自分か？」を最後に問う段の話だ。第1章で書いた「書き始めの対話で切り口を定める」とは正反対の方向、書き終わったあとの最後の関門の話になる。

### 5層レビューの最後の関門

Vol.2 では、5層の品質ゲートを設計した話を書いた。writer が書いた原稿を、reviewer（ファクトチェック）と reader（想定読者ペルソナの感情レビュー）が並行して見る。横断整合チェックで複数章の矛盾を拾う。書籍ならそこに CEO 判断記録が積み上がる——そういう装置だ。

その最終層に、「著者ペルソナ最終通読」というレイヤーがある。

reader が、想定読者ではなく**著者本人**を演じて全章を通読する。Vol.1 を作っていたとき、ある朝の通読で「これは自分か？」という違和感が3章まとめて出てきたのが直接の引き金だった。想定読者には見えないが、著者が読むと気になる種類のズレ——「盛り」「経験との食い違い」「過剰演出」「文体の不自然さ」「自己言及の頻度」——これらを最後に拾うための装置を、その日の夕方までに設計した。`ops/playbooks/article/reader-personas/author.md` に著者プロフィールを書き、`reader-review.md` の末尾に専用工程として組み込んだ。

ペルソナファイルにはこう書いてある。

> SE歴26年。Claude Code ではコードを自分で書かず、日本語指示でエージェントに実装させるスタイル。新しいツール・手法を試すのが好き。ただし「面白いから」ではなく「事業に使えるから」で判断。ベテランとしての審美眼がある。浅い記事・嘘くさい記事にはすぐ気づく。

そして、原稿を読むときの視点としてこう続く。

> 「これ、自分が書いた記事として恥ずかしくないか？」
> 「26年の経験に基づいて、この主張は正しいと言えるか？」
> 「自分の体験が正確に反映されているか？ライターが勝手にストーリーを作っていないか？」

reviewer は外部の事実と本文を照合する。reader（想定読者）は感情の流れと離脱箇所を見る。著者ペルソナは、その両者が触れない層を見る——「この文章を自分の名前で出して恥ずかしくないか」という、最終関門だ。

### 7〜8分で何が拾われるか

この装置を Vol.1 全章で初めて回したのが、2026-04-26 の朝だった。

体感としては7〜8分で初稿レビューが返ってくる。実測の総量はもう少し多くて、Vol.1 の場合は全章通読で「気になった箇所」が章別に1〜3件ずつ積み上がっていた（`content/reviews/2026-04/2026-04-26_author-review-final.md`）。最終的に優先度高として整理されたのが4件、優先度中が3件、優先度低が1件。重要度の高い指摘は、感覚的にも3〜5件のレンジに収まる。

何が拾われたか。具体例で書く。

ひとつめは、**「7〜8分で初稿が上がる」「reviewer が3〜5件の指摘を出してくる」という数字**そのものだった。Vol.1 第2部の本文中に出てきたこの数字に対して、著者ペルソナはこう指摘してきた。

> 実測値か体感値か不明。実際には記事の長さや researcher の調査量によって大きく変動するはず。「体感として」などの断り書きを加えるか、「数分〜十数分程度」のような幅のある表現に変えた方が正直。

ファクトチェックは通る。事実として「そのくらいの時間がかかった日」は確かにある。でも「平均値として書いていいか」が別問題だった。著者本人が読むと「これ、いつでもこうとは限らないよな」と気持ちが引っかかる。引っかかるなら、読者にも引っかかる可能性がある——それを言語化できるのが著者ペルソナだった。

ふたつめは、**「SE歴26年」の自己言及頻度**だ。

reader（想定読者ペルソナ）レビューは「SE歴26年」を「信頼性の裏付け」として評価し、問題視しなかった。ところが著者ペルソナの通読では、序章・第2部冒頭・第4部冒頭・付録と、合計4箇所で同じフレーズが出ていることが拾われた。本人が読むと「自分はそんなに何度も経歴を出さない」という違和感がある。出すぎている。

この指摘から、`ops/playbooks/article/writing-guidelines.md`（Vol.2で設計した執筆ガイドライン、writerが毎回読む指示書ファイル）に1行が増えた。

> 「SE歴26年」を前面に出しすぎない: タイトル・冒頭・見出しで「SE専用の話では？」という壁を作る。経験年数は信頼性の裏付けとして使うにとどめ、読者の課題や共感から入ること

3つめは、**「翌朝には全11章のドラフトが上がっていました」というエピソードが、序章と第2章でほぼ同文・2回登場していた**ことだ。横断整合チェックでも拾われそうな案件だが、実際に拾ったのは著者ペルソナだった。読者ペルソナは「いい話だ」と素直に受け取る。著者本人は「同じ話を2回している、書き手として体裁が悪い」と感じる——その温度差が拾うかどうかを分けた。

### 装置が運用フェーズに入るまで

ペルソナを設計しただけでは、この装置は機能しない。

Vol.2 で「著者ペルソナファイルを書いて、reader-review の末尾に専用工程を組み込んだ」というところまでは設計の話だ。Vol.3 の本章で書きたいのは、その装置を**毎日の運用フェーズに入れたあと、何が起きたか**のほうだ。

運用フェーズに入ってから3か月、この装置は週に2〜3本ペースで通読を回している（体感ベース、記事公開頻度から逆算した概算値）。記事1本あたりの稼働時間は7〜8分で安定した。1回の通読で出てくる重要度高の指摘は、Vol.1 のときから減ったわけではない。3〜5件レンジが続いている。

ただ、**指摘の中身は変わった**。

運用初期に多かったのは「数字の体感／実測の区別」「自己言及の頻度」「重複エピソード」のような、誰の文章でも起きうる構造的な問題だった。これは writing-guidelines に吸い上げられて、writer の側のチェック項目になった。差し戻されるまでもなく writer が自分で直してくるようになった。

代わりに、運用フェーズの今は「**この記事は、私のどの体験から書かれているのか**」「**この語尾は、私が普段書く語尾か**」のような、もう一段内側の指摘が増えた。例えば最近の通読で著者ペルソナが拾ってきた指摘で印象的だったのはこれだ。

> 体験談の核心部分は正確だが、感情描写・時系列の一部に過剰演出の疑いあり

事実は合っている。でも、その日の自分の気持ちはこんなに劇的じゃなかった——という温度の指摘だ。ここで一つ、本書のために用意した模式例を出す。たとえば writer が書いた原稿に「キーボードを打つ手が震えた」という一行があったとする。事故記事だ。事実として手は動かしにくかったが、震えてはいない。著者ペルソナの指摘を受けて「キーボードに置いた手が一度止まった」に直す——そういう温度補正だ。同じ事象を指している。劇度だけが、自分の実感に合う水準まで下がる。

もう一パターン、AI が書くと出やすい「まとめ口調」の温度差を示す。writer がセクション末尾に書いた原稿。

> **Before（AI特有のビジネスライクなまとめ口調）**: 「以上のことから、著者ペルソナ最終通読は品質向上に有効な手段であると言える。継続的な運用によって、より高精度なアウトプットが期待できる。」

> **After（著者らしい内省的なトーン）**: 「装置が正しかったかどうかは、今でも分からない。ただ、あの朝より自分の文章に近いものが出るようになった、という手触りはある。」

前者は論旨として間違っていない。後者は「書いた本人が言いそうなこと」になっている。著者ペルソナが見ているのは、論旨の正しさではなく、「この著者が、こういう言い方をするか」という問いだ。実際の差し戻しはもっと細かい語尾や副詞のレベルで起きていることが多いのだが、紙面で見せるなら、これくらい振り幅のある例のほうが装置の働きが伝わる。

こういう指摘は writer のチェックリストでは捕まらない。著者本人を演じて読み返す層がないと、原稿のまま世に出てしまう。

もう一つ印象的だったのが、語尾の指摘だ。writer が「〜と言える」「〜と考えられる」を多用していた箇所がある。事実上の意味は変わらないが、自分が普段書くときは「〜だ」「〜だった」と言い切るほうが多い。著者ペルソナがそこを拾って「断定の温度が著者と違う」と指摘してきた。`writing-guidelines.md` の語尾セクションに反映するほどの一般則ではないが、その記事に限ってはトーンを直した。装置が回るたびに、こういう「その記事だけの微差」が1〜2件ずつ出てくる。

### 装置を信じすぎないこと

ここで一つ正直に言っておきたいことがある。

**この装置の出力を、そのまま採用してはいけない。**

著者ペルソナは「著者本人」を演じる reader だが、本人ではない。`author.md` に書いてあるプロフィールと、現在の自分の気持ちは、必ずしも一致しない。3か月前に書いたペルソナ定義が、今日の自分のトーンと微妙にずれていることもある。装置の指摘を読んで「いや、今日の自分はこう感じない」と思ったら、その違和感のほうが正しい。

実例を一つ。Vol.1 のある章で、著者ペルソナが「『コードを書けない』という自己卑下が3章で連続している。読者に過剰なへりくだりとして伝わる」と指摘してきたことがある。指摘自体は筋が通っていた。だが、その朝の自分は「これは卑下ではなく、コードを書けない立ち位置を毎章で明示しているだけで、本書全体の前提だ」と判断した。指摘を採用せず、3章とも原文のまま残した。レビューファイルに「指摘は受け止めたが、本書のテーマ上、意図的に残す」と1行書き添えて先に進んだ。

著者ペルソナの役割は、**判断を代行することではなく、判断のテーブルに案件を並べること**だ。並べられた案件の中から「これは直す」「これは残す」「これは保留して時間をおく」を選ぶのは、毎回、書いた本人がやる。装置が3〜5件の指摘を返してきても、全部直す必要はない。1件だけ採用して、残りを「指摘は受け止めたが今回は残す」と書き添えて先に進む朝もある。

それでも、装置があることと、ないことの差は大きい。装置がない時期の自分は、原稿を読み返して「なんか違う」と感じても、その違和感を1件1件の指摘に分解できなかった。違和感はモヤのまま消えて、原稿は「まあいいか」で公開ボタンを押した。

著者ペルソナ最終通読は、モヤを項目に変換する装置だ。項目になれば、採用と却下を選び取れる。選び取った時点で、その原稿は「自分の文章」になる。逆に言えば、装置を通さない原稿は、自分のものなのか他人のものなのか、自分でも判定できないまま流れていく——それが、本章の冒頭で書いた「これは自分の文章じゃない」という朝の正体だった。

> **3体構成なら**: 著者ペルソナのファイル（`reader-personas/author.md`）を用意しなくても、「自分がこれを書いたとして恥ずかしい箇所はどこか」と writer か reviewer に問うだけで代替できる。1週間でいいので試してみてほしい。

## 第3章: AIに『書かせる』前に4つの仕掛けを作った話

ここで書くのは、AI に原稿を書かせる前の「準備の話」だ。4つの仕掛けとは、AIが知らないことを勝手に補完しないように、書く前に整えておく4つの土台を指している。

きっかけは1件の事故だった。writer が原稿を返してきた——週次の changelog 記事だ。価格・バージョン番号・存在しないコマンドの3点が、元レポートにない情報として書かれていた——詳細は Vol.2 第2部第4章にある。

writer は嘘をついたつもりはない。「事前知識からそれっぽい数字とコマンドで補完」しただけだ。本人の提出報告には「数値創作なし: 実測またはドキュメント引用のみ」と書いてある。**補完が「創作」だと、writer 自身は認識していなかった**。

本章で書きたいのは、その先だ。あの事故のあと、私は「次に同じことが起きないように、書かせる前の段で何を整えておけばいいか」を考え始めた。書いている最中に止めるのではない。書く前に、創作が起きにくい状態を作っておく。その積み上げが、4つの仕掛けになった。

仕掛けは最初から4つの体系として設計したわけではない。事故が1件起きるごとに、reader レビューが繰り返し同じ指摘を返してくるたびに、1つずつ足していった。気がつくと、ペルソナ・疑いの先渡し・差し戻し蓄積・創作禁止——この4つが揃っていた。

俯瞰しておくと、4つの仕掛けは**書く前の2つ**（ペルソナの強化／疑いの先渡し）と、**書いた後から書く前へ戻る2つ**（差し戻し理由の蓄積／創作禁止ルールの明文化）から成る。書く瞬間の品質は、これら4つが作る土台の上に乗る。すべては「次に書く前の状態」を底上げする方向に向いている——書かせる前に整えるとは、執筆と執筆のあいだの時間に何を積むかという話だ。

順に書く。

### 1. 架空ペルソナは都合よくなる

最初に作った仕掛けは、reader ペルソナだった。

writer が書いた原稿を、想定読者の視点で読み返すエージェントが要る——という発想自体は素直なものだ。年齢・職業・スキル・動機を書いたファイルを用意して、その人物像になりきって原稿を読ませる。読みやすさ・離脱箇所・感情の流れを返してもらう。

最初に設計したのは架空ペルソナだった。48歳・中小IT企業の取締役。Claude Code に関心はあるが、コードは自分では書かない——という設定だ。`ops/playbooks/article/reader-personas/` の下に Markdown ファイルとして置いた。

ところが、このペルソナのレビューが**妙に好意的だった**。

最初は「うちのペルソナは温厚なのかな」と思った。違った。架空ペルソナを設計するとき、私は無意識のうちに「この記事に反応してくれそうな人」を作っていた。記事のテーマに興味を持ちそうな職業、記事の主張に共感しそうな動機、記事の文体を好みそうな年齢層——そういう人物像を組み立てていた。

本当にリアルな読者なら、そもそも記事にたどり着かないし、たどり着いても「AIの話か」で3秒で閉じるし、最後まで読んでも「面白いね」で終わって何もしない。架空ペルソナはそういう「3秒で閉じる動き」を持っていなかった。

対比として、別の日に「友人のマーケティングコンサル経営者」をベースにしたペルソナを作って同じ原稿を読ませたら、指摘の質が違った。「ミンツバーグの使い方が違う」と即座に専門観点で突っ込み、「研修で使えるか？」という独自の評価軸を持ち、それでも「友人だから最後まで読む。ただし忖度はしない」という自然な動機があった。架空では出てこなかった角度の指摘が並んだ。

ここから、ペルソナファイルに4つの項目を足した。

- 「この記事を読まない理由」（読む理由より重要）
- 「どこで知るか」という導線
- 「いつ・どこで読むか」のシチュエーション
- 「最初に浮かぶ最大の疑い」

特に最後の「最初に浮かぶ疑い」が、次の仕掛けにつながった。

### 2. 疑いの先渡し

ペルソナの「疑い」を、書き終わってから受け取るのではなく、**書き始める前に writer に渡す**。

これが2つ目の仕掛けだ。コミット `b7d628a`（2026-04-14 火曜の夕方）で `article-production-flow.md` に Step 5.5 を1段追加した。

書く順序が変わる。

```
従来:
  Step 5  writer 執筆 → Step 6 reviewer ファクトチェック → Step 7 reader 感情レビュー

変更後:
  Step 5    reader ペルソナの「疑い」リストを生成
  Step 5.5  writer が疑いリストを受け取って執筆開始
  Step 6    reviewer ファクトチェック
  Step 7    reader 感情レビュー
```

疑いリストには、想定読者が記事に対して最初に浮かべそうなネガティブな反応が並ぶ。「SE歴26年だからできたんでしょ？」「ノンプログラマー向けと言いつつ、結局CLIが必要じゃないか」「料金は最低額しか書いていないけど、現実のコストは別では？」——こういう疑念だ。

writer は執筆開始時にこのリストを受け取り、各疑いに対する答えを記事の構成に**自然に織り込む**。本書 `.claude/agents/writer.md` には、このルールがこう書かれている。

> 疑いへの回答は防御的な弁明ではなく、具体的な事実・数字・失敗談で示す

「弁明ではなく、失敗談で示す」というのが、この仕掛けの肝だ。疑いに反論しようとすると守りの文章になる。代わりに「その疑い通り、実際に私はこういう失敗をした」という具体例を本文に置けば、疑いは消えるのではなく**読者の共感に変換される**。

書き終わってからレビューで疑いを潰すより、書く前に疑いを受け取って構成に織り込むほうが、原稿の解像度が一段上がる。これは運用してみて初めて分かった効果だった。

### 3. 差し戻し理由を蓄積する

一つだけ先に断っておく。4つのうち**この3つめだけは、書いている最中・書いた後の作業から「書く前」へフィードバックする工程**だ。書く前の仕掛けそのものではない。だが、書く前の仕掛けを成長させる装置として4つの中に含めている。差し戻しを単発で消化して捨てれば、次に writer が書き始める前の「状態」は何も変わらない。蓄積してルール化することで、次の執筆開始時点の writer の足場が一段上がる——その意味で、これは「次回の書く前」を作る工程だ。

3つ目の仕掛けは、reviewer/reader からの差し戻し理由をその場で消化せず、**ルールとして蓄積していく**ことだった。

最初に作った `writing-guidelines.md` は、コミット `b7d628a` で書いた5セクションだった。

1. 数字の根拠
2. バランス
3. 構成
4. 再現性
5. 創作禁止

このファイルは、執筆前に writer が必ず読むルール集として置いた。最初は5項目だけだった。

ところが、運用していくと、このファイルが**勝手に増えていく**。

差し戻しが繰り返されるたびに、その理由を抽象化して1項目追加する。例えば「クレオソート」「ヨード」のような専門用語を文脈なく登場させて読者の離脱を生んだ事故があれば、「専門用語・技術用語の扱い」というセクションが増える。GA4の数字を引用するときに「2026-05-05 に全12ページ確認、合計約280件」のような調査日と範囲を書き漏らした記事があれば、「数字・日付・出典の扱い」に1行が追加される。

執筆時点で `writing-guidelines.md` を改めて数えてみたら、セクション数は21まで増えていた（更新履歴を含む）。最初の5から、約3か月で16セクション増えている。「更新履歴」を遡ると、直近では同じ1週間に 2026-05-05 / 2026-05-09 / 2026-05-10 と立て続けに追加されており、その週だけで合計6件が積まれている。

増え続けるのは、書き手としては気が滅入る話に見える。実際は逆だ。**増えていることが、ガイドラインが生きている証拠**だった。

差し戻しを単発で消化していたら、同じ理由で何度も差し戻される。ルール化しておけば、次の writer は同じ事故を起こさない。「数字には根拠を添える」「経過日数は逆算する」「サービスの料金プランは最低額だけ書かない」——これらは、すべて事故が1件起きたあとに追加されたものだ。各セクションの末尾に「（出典: 2026-05-09 〇〇 reviewer 🔴）」のように、起源の事故が書き添えてある。

ガイドラインは設計書ではなく、**事故ログを翻訳した運用記録**になっている。

### 4. 創作禁止6項目（事故から増えたルール）

4つ目の仕掛けは、3つ目の延長で生まれた。

差し戻し理由を蓄積していたら、ある時期から「同じ事故が型として見えてきた」段階に来た。writer が「事前知識から推測で補完する」という型だ。バージョン番号、価格、コマンド、運用期間——元データに書かれていなくても、文脈から確からしい数字を入れてしまう。

事故の事例として一番分かりやすかったのが、Vol.2 第2部第4章で書いた週次changelog記事の3件の創作だった。あの事故の翌日、writer エージェント定義（`.claude/agents/writer.md`）に**創作禁止の6項目**を明記した（その後、ルールの主体は前節の `writing-guidelines.md` 側へ移し、現在の writer.md には「創作禁止」一行と `writing-guidelines.md` 遵守の指示だけが残っている。事故対応の起源としては writer.md に書かれたが、運用の中で「執筆前に必ず読むファイル」を一本化したほうが事故抑止に効くと分かったためだ）。当時のコミット `b7d628a` の差分から1行ずつ書き写すと、こうなっている。

1. 事実に基づかないエピソード・数字・会話の創作を禁止する
2. 過去記事・ログ・git履歴・ユーザーの発言に裏付けがない主張は書かない
3. ソースが確認できない情報を書く場合は「未確認」と明記する
4. 数字には根拠を明記する（実測値 / usage画面からの概算 / 体感）
5. 推測・意見は「〜だろう」「〜かもしれない」と明示し、事実と混在させない
6. 「〜と言われている」「一般的に〜」のような曖昧な権威付けを使わない。出典を示すか、書かない

特に効くのが3番目の「ソースが確認できない情報を書く場合は『未確認』と明記する」だ。writer に「書くな」と言うだけでは足りない。`[要確認]` というマーカーを残して先に進む経路を一緒に用意しておかないと、writer は「ここの数字どうしよう」で詰まる。そして詰まると、補完が始まる。

`[要確認]` を残せば、執筆は止まらず、reviewer が後段でそこを拾える。書かせるルールと、止まらないための逃げ道——この2つはセットで初めて機能する。

### 5. 4段が揃ったときの差し戻し率の変化

ここで一つ、正直に言っておく。

「4つの仕掛けを揃えたら、差し戻しが半減した」という綺麗な数字を、私は持っていない。差し戻し率を継続的に計測する仕組みは、執筆時点では運用されていない。書き手としてはそういう数字があった方が話の収まりがいいが、ないものはない。

代わりに、運用していて手触りとして変わったことを3つ書く。

ひとつ。**差し戻しの中身が「単発の事故」から「微妙なトーン」に移った**。運用初期に多かった差し戻しは、「数字の根拠が不明」「料金プランの最低額しか書いていない」のような、構造的な抜けだった。今は writer 自身が書きながらガイドラインに照らして潰してくるため、こういう抜けは初稿段階で少ない。代わりに残るのは「この語尾は著者っぽくない」「自己言及がやや多い」のような、微差の指摘になった。

ふたつ。**writer が「補完しそうな箇所」を自分で `[要確認]` として残してくるようになった**。創作禁止6項目を読んだ writer は、不明な数字や日付に手を出さなくなる。代わりに `[要確認]` でフラグを立てて、後段で確認する経路に乗せる。執筆中の流れは止まらないが、事故は手前で止まる。

みっつ。**ガイドラインの追加ペースが、月に4〜5件で安定した**。初期は1セッションで5〜6件のルールが増える勢いだったが、運用が安定してくると追加は減速する。それでも追加がゼロにはならない。新しい型の事故は、運用していると必ず出てくる。ガイドラインが増え続けることそのものが、書き続けている証拠だ。

書きながら思うのは、この4つは順番にも意味があったということだ。

まずペルソナを設計する。次にペルソナの疑いを書き始める前に渡す。書いた原稿の差し戻し理由を蓄積する。蓄積から型が見えてきたところで創作禁止を明文化する。**仕込み→使う→学ぶ→明文化**の4つが、書く前の準備工程として揃った。

書いている最中の品質は、書いている最中の努力では決まらない。書く前にどれだけ仕掛けを積み上げたかで決まる。AIに書かせるなら、なおさらだ。

:::message
**3体構成なら**: 4つの仕掛けを自動化なしで手動実行する場合の、最小手順を書いておく。

**疑いの先渡し（手動版）**: 記事のネタが決まったら、書かせる前に ChatGPT か Claude にこう投げる。
```
読者は「○○（テーマ）」に詳しくない。この記事を読む前に浮かべそうな疑いを5個挙げて。
```
返ってきた疑いリストを、記事の冒頭に「この記事ではこういう疑問に答えます」という形で置いておくか、writer への指示文に添付する。書き終えた後で指摘を受けるより、書き始める前に疑いを知っている方が、構成が一段安定する。

**創作禁止ルール（手動版）**: 書かせる前の指示文に次の1行を必ず加える。
```
数字・コマンド・固有名詞は私が指定したもの以外は使わない。不明な場合は[要確認]と書いて止めること。
```
この1行で補完創作の大半は防げる。ルールを毎回書くのが面倒なら、テキストエディタのスニペット（定型文）に登録しておくと一発で入る。

4つ全部でなくていい。この2点から始めれば、初稿の差し戻し回数は確実に減る。
:::

## 第4章: AIが書く記事が薄かった本当の理由

### 「writerが書く記事が薄い」という発見

ある日、Vol.2 第2部のレビューが返ってきた。reviewer の指摘は事実関係には触れていない。reader の指摘も離脱箇所ではない。**「生の言い回しが消えている」**——その一言だった。

最初は意味が取れなかった。事実は引いている。構成も通っている。論旨も繋がっている。何が消えているのか。

原稿を読み返してみて、ようやく分かった。記事の中に出てくる「セリフ」が、全部きれいすぎる。私が普段Claude Codeに話しかけるときの、ちょっと崩れた言い回し、語順の入れ替わり、タイポを直さずに送った一行——そういうものが、書き起こされた原稿の中では全部、整った日本語になっていた。たとえば「正直、writer に渡す前に自分でもっと素材整理しとくべきだったわ」のような発話（これは仮の言い方）を整えると、「素材整理の重要性に気づいた」になる。意味は同じだ。でも、温度が違う。

writer が書いた原稿が薄かったのは、書き方の問題ではなかった。**素材の問題だった。**

writer が読みに行く先は `content/writing/netacho/` のネタ帳と、`content/reports/research/` のリサーチレポートだけだ。私が対話の中で発した生の言葉、COOとの応答のリズム、設計を詰めていく途中の「言いかけ」——そういう「生のテキスト」は、ネタ帳に転写されない限り、writer から見えない場所で消えていく。整っていない言葉は、整理されないと記録に残らない。整理された時点で、もう生の言葉ではなくなっている。

本章は、その「素材の構造問題」を、1セッションで対話アーカイブとして解決した記録だ。

### 書き方ではなく素材問題

ここで一つ、前章との関係を整理しておきたい。

前章（第3章）で書いた4つの仕掛け——ペルソナ・疑いの先渡し・差し戻し蓄積・創作禁止——は、「**書かせ方**」の設計だった。書き始める前に writer に何を渡し、書いている最中にどう振る舞い、書き終わった原稿をどう差し戻すか。書き手の動きを設計する4つだ。

本章で書く対話アーカイブは、その**前段**にある問題を扱う。書き手が「上手に書く」前に、書き手が**読める素材**がそもそも何で構成されているか、という話だ。

| レイヤー | 設計対象 | 該当章 |
|---|---|---|
| 書き方の設計 | writer の動き（ペルソナ・疑い・差し戻し・創作禁止） | 第3章 |
| 素材の設計 | writer に何が見えているか（対話アーカイブ） | 本章 |

書き方をいくら磨いても、素材が薄ければ厚みは出ない。ネタ帳は writer が読む素材の骨格になるが、整理された段階で、対話の生々しさは抜けている。「私はそう思った」と書かれていても、「『そう、それだ』って思った」と発した生の声は、ネタ帳には残らない。残らないものは引けない。引けないものは原稿に出ない。

この構造に気づいた瞬間が、対話アーカイブの起点だった。

### 3案から「ユーザートリガー型」を選んだ理由

2026-05-06、水曜日の夜だった。エヴァ記事のZenn公開状態更新を済ませた直後、私はCOOにこう投げた。

> User: 別の話題だけれど、Writerが執筆するときに、私やCOOの実際の過去の発言が参照できていない。このことで記事の厚みがでないので、何とかしたい。

COOが3案を提示してきた。

1. **入口で拾う案**: COOがネタ採掘時に対話の生引用をネタ帳へ必ず転載する → 私とCOOが毎回意識する人力運用 → 数週間で形骸化する → 却下
2. **物理保存案**: 発言を構造化して保存し、writer が grep できる引用素材データベースを作る → 過去全部を救える → 採用候補
3. **執筆時参照案**: writer プロンプトに「対話引用を最低N件含める」を必須化 → 引用元のデータベースが先に要る → 単独では成立しない → 却下

私の返事は、迷う暇のない一文だった。

> User: ２，私が保存してといったときだけでいい

選んだ2の中でも、本来は「全自動・全ターン保存」という重い設計もありえた。COOが提案した案2の説明にも「実装重め」と書いてあった。だが、それを「ユーザートリガー型」に絞った。**「私が保存してといったときだけでいい」**。

理由は単純だった。全自動で全ターンを保存すれば、意味のない応答もしょうもない打ち間違いも、全部 grep の検索結果に出てくる。それは「素材の厚み」ではなく「ノイズの厚み」だ。**全自動だと、薄い素材で原稿が薄くなる**。

代わりに、私が「これは保存したい」と思った瞬間のターンだけを残す。判断は私がやる。設計判断、行き詰まり、突破口の一言、「そう、それだ」と感じた瞬間——そういう塊だけが、テーマ別のファイルに溜まっていく。一手間多いが、そのひと手間が素材の純度を決めていた。

ここまで「対話アーカイブ」「architect 委任」「.gitignore 例外設定」と書いてきたが、これは「はじめに」で紹介した 9体のチーム（writer・reviewer・reader を中心に、調査・設計・運用を担う他のエージェントを揃えた編成）を前提にした実装の話だ。3体のチームを動かしている人にとっては、まず「セッション終わりに ChatGPT/Claude にこの対話の論点と判断軸を3行で書き出して」と依頼してテキストファイルへ保存するだけでも、生の言葉が次に書く writer に届く仕組みは始まる。装置は段階的に育てればいい。本章の核は「ユーザーが意志を持って『これは残す』と手を挙げる」という思想のほうにある。

### 1セッションで設計→実装まで通した記録

決まったあとの動きは速かった。

COOが追加で2点を詰めてきた。「保存範囲は直前1ターンか、話題塊か、範囲指定か」「保存先は日付単位か、テーマ単位か、ネタ帳混在か」。私はどちらも推奨案——話題塊・テーマ単位ファイル——に乗せた。理由は「writer が grep で『あの話どこだっけ』を引けるから」だった。

> User: 推奨通り

ここから architect に設計が委任された。architect は `ops/playbooks/dialogue-archive.md` を1本書き上げてきた。ディレクトリ構造、保存フォーマット、5系統のトリガーパターン（「保存して」「対話保存して」「これ保存して」「アーカイブして」「この会話保存しておいて」）、既存システムとの棲み分けまで、Playbook 1本に詰まっている。

設計書を受け取ったあと、COOが実装案を出してきた。READMEとPlaybook本体、エージェント定義への追記など、5ファイルへの追記が要る。COOは「writer.md は skill-dev に委任しましょうか」と慎重に提案してきた。エージェント定義ファイルへの編集は影響範囲が大きいためだ。だが私はこう返した。

> User: 5も COOで

5ファイルとも、編集自体は数行〜十数行のシンプルな追記だ。委任のオーバーヘッドのほうが大きい。COOの責務に「数行レベルの軽微なファイル修正」が含まれている以上、ここは委任しないほうが速い。

COOが5ファイルを並列に書き換える。10分ほどで「全5ファイル完了。状態確認します」と返ってきた。そして次の一言が、この設計でもっとも面白い瞬間になった。

> COO: 問題発見。`/knowledge/` が `.gitignore` でブロックされています。

Zettelkasten 系のディレクトリはローカル運用にする設計で、`/knowledge/` 全体が gitignore されていた。新設した `knowledge/dialogue/` も巻き添えで git 管理外になっていた。

ここでCOOが A: 例外化 / B: 現状維持 の判断を求めてきた。私は A と返した。`.gitignore` の差分は `/knowledge/` を `/knowledge/*` に変更し `!/knowledge/dialogue/` を1行追加する、それだけだ。だがこの1行が**設計の思想を確定させた**。「対話は消えてはいけない」「writer が grep で引ける場所に置く」「時間とともに価値が増す資産として残す」——`.gitignore` の1行が、それを宣言した。

この日の作業は、設計から実装、障害発見、解決、初回稼働まで、すべて1セッション・1コミットで通っていた。5ファイルを skill-dev に委任していたら、設計書を受け取って、要件を伝えて、レビューして、修正依頼を出して、確認して——という委任ループが回る。間違いなく日をまたぐ。1セッションでは終わらない。軽微な機械作業をエージェントに渡さず、COOがその場で書く——この判断が、設計と実装の間にある摩擦を消した。

### 設計議論自体が最初の保存対象になった

実装が終わったあと、COOが「動作確認」を提案してきた。

> COO: 動作確認として「保存して」と発言いただければ、本セッションの直近対話塊からテストできます。今回の対話アーカイブ設計議論そのものを最初の保存対象にすると POC スタートになります。

これは綺麗に組まれた提案だった。新しい装置を作ったら、その装置が動くかを確認する。普通は別の何かを保存対象にしてテストする。でも、いま目の前にある「対話アーカイブを作ろう」という対話そのものが、最も自然な最初の保存対象だ。

> User: この対話を保存して

COOは slug を提案してきた。`dialogue-archive-design`、タイトルは「対話アーカイブシステムの設計と実装をめぐる対話」。私が「はい」と返すと、`knowledge/dialogue/dialogue-archive-design.md` が作成された。frontmatter には `created_at: 2026-05-06`、`speakers: User / COO`、tags に `meta` `poc` が入っている。

本文には、それまでの私とCOOのやり取りがそのまま並んでいた。「２，私が保存してといったときだけでいい」「推奨通り」「5も COOで」「A」「この対話を保存して」——タイポも語順の崩れもそのまま、写されていた。整理されていない。整えていない。だからこそ、後から writer が grep して読んだときに、私がそのとき「どういう温度で何を選んだか」が分かる形で残った。

これがメタな結びだった。**対話アーカイブの最初の蓄積は、対話アーカイブを作るという対話そのものだった**。装置を作ると、装置の初稼働の素材は装置の設計議論になる。設計と運用が同じ瞬間に成立した。

ここで一つ、本章にとって重要な開示をしておきたい。

**本章でここまで引用してきた私の発言——「２，私が保存してといったときだけでいい」「推奨通り」「5も COOで」「A」「この対話を保存して」——は、すべて `knowledge/dialogue/dialogue-archive-design.md` から引いている。**writer は本章を執筆するために、ネタ帳の構成を骨格として読んだ。そして、生の発言は対話アーカイブから grep で引いた。本章の生々しさは、対話アーカイブが運用フェーズに入ったから出せた厚みだ。

装置を作った日の対話が、装置が動いた初日に保存された。6日後、その保存ファイルから、装置を作った話を記事として書き起こす素材が引かれた。**装置が、装置自身を素材として書く構造**になっている。書きながら気づいたのは、この章のメタ構造そのものが、対話アーカイブの設計が正しかったことの最初の証拠になっていることだった。

実装が正しかったかどうかは、運用してみないと分からない。本章が成り立ったこと、それ自体が運用初日からの蓄積の結果だ。

> **3体構成なら**: 対話アーカイブのディレクトリを作る前に、「今日のこの会話を保存しておいて」と一言 writer か COO に頼むだけでいい。行き先があれば、発言は消えない。仕組みは後から育てる。

## 第5章: ウイスキーの記事を並走させてみた

本章は、AI執筆に一本足打法で頼り続けることによる著者性の枯渇を防ぐための、冗長設計の話だ。Claude Code で記事を書き続けるほどに、「Claude Code の話」のフィルターが自分の全出力に掛かるようになる。そのフィルターを一時的に外せる別ジャンルを持つことが、書き手自身の維持機構として機能する——という設計論でもある。

### Claude Code 一本足の限界

Vol.1 を書き上げたあと、私は「次に何を書くか」で詰まった。

素材は溜まっていた。運用ログ、エージェント設計、Playbook 増殖の事故、ネタ帳、リサーチレポート——どれもが Claude Code の話だ。机に向かうと指が止まる時期があった。

「これ、ぜんぶ Claude Code の話だ」

「Claude Code で AI チームを動かすノンプログラマー」という旗を立てて、Vol.1 を出した。次の本もブログも同じ旗の下に書いている。テーマが揃っているのは強みのはずだった。

でも、その旗の下にずっと立ち続けていると、書く側の自分が痩せていく感覚があった。書くたびに「Claude Code の話としてどう成立するか」というフィルターが先に立つ。フィルターを通らない素材は、たとえ自分が面白がっていても、書く前に捨てる。捨て続けると、自分が何を面白がる人間だったかが薄れる。

書き続けるという課題は、ネタが続くかどうかの話だと思っていた。違った。**書き手の中に「Claude Code 縛りじゃない自分」が残っているかどうか**の話だった。

### ラフロイグ10年の夜

2026-05-09 の夜、行きつけのバーのカウンターに座っていた。

記事を書く予定はなかった。ただバーに来ただけだ。棚に並ぶ緑のボトル——ラフロイグ。アイラ島のシングルモルト、「正露丸みたい」と避けられがちな銘柄だ。「ストレートで」と頼んだその一言は、Claude Code のことでも、エージェント設計のことでもなかった。

その夜、薄暗い照明の下でスマホに短い感想を書き留めた。「ピートの煙の向こう側に洋梨のようなフルーツの甘みが感じられて美味しかった」「さすが王様のお酒」。それだけだ。翌日、そのメモをネタ帳に転記し、裏取りが必要な項目（度数や価格帯、Royal Warrant の授与年など）を脇に並べた。骨格はネタ帳に置いた。あとは writer に渡せば書ける——その日のうちに記事は ready で並んだ。

書きながら、おかしなことに気づいた。**Claude Code を書いているときよりも、文章が軽い**。指が止まらない。語尾の選び方に迷わない。「煙の向こう側に洋梨がある」と書いて、その一文に何の身構えもない。Vol.1 の章を書くときは「これは事実か」「裏取りは済んだか」「他の章と矛盾しないか」を毎段落で確認しながら進むが、ラフロイグの記事には装置の重さが要らなかった。中心にあるのは私が飲んだ夜の記憶で、「煙の向こうの洋梨」は私の舌が記録したものだ。誰の Playbook にも依存しない。

書き終わって、もう一つ気づいた。**この夜の記憶は、Claude Code 縛りのフィルターを通っていない**。書くつもりがなかったから、純粋に体験として残った。フィルターを外した自分が、自然に拾い上げてきた素材だった。

### note 単独配信を選んだ理由

ウイスキーの記事は、すべて note 単独で配信している。2026-04-07 から 2026-05-10 までの約1か月で6本書いた。「最初の一杯」「燻酒」「アイラ9蒸留所の個性マップ」「SOGAINI」「ジャックダニエル」「ラフロイグ10年」。frontmatter を確認すると、5本が `primary: note`、1本（最初の first-glass）が `primary: hatena` で `state: archived` だった。途中から運用を切り替えて、note 単独配信に統一している。

note 単独にした。理由は2つある。

ひとつめは、クロスポスト（はてなから 24 時間後に Zenn・Qiita へ自動転載する運用）を除外したかったから。Claude Code 系の記事は、SEO とアフィリエイトリンクの設計を組み合わせた装置を Vol.1〜Vol.2 で固めて、その経路に乗せている。ウイスキー記事を同じ装置に乗せると、Zenn のフォロワーには「Claude Code の人が突然ウイスキー？」というノイズになる。Qiita はそもそも技術記事のプラットフォームだ。クロスポスト先のコンテキストを壊さないために、note だけに置く。

ふたつめは、アフィリエイトリンクの扱いだ。ウイスキー6本のうち、Amazon アソシエイトリンク（`saitokohamu1-22`）を挿入したのは4本（燻酒、アイラ9蒸留所、SOGAINI、ジャックダニエル）で、本章の中心エピソードであるラフロイグ10年と、最初の一杯には入れていない。ネタ帳の段階で「note 向けは挿入しない」とポリシーを明示している。読み物として読まれる記事は商品リンクを置かない、レビュー寄りの記事は1本だけ置く——同じ note の中でも濃淡を分けた。ラフロイグの章にリンクが要らなかったのは、あの夜の記憶を商品紹介に変質させたくなかったからだ。

note 単独配信は、運用上の都合だけではなく、**「別ジャンルは別ジャンルとして閉じる」という思想の表れ**でもあった。1つの装置にすべてを通そうとすると、ジャンル横断のために装置が肥大化する。出口を分けておけば、書き手の中の「Claude Code の自分」と「ウイスキーの自分」が別々に並走できる。主軸はあくまで Claude Code だ。ただ、軸の外側で別ジャンルの自分が呼吸できる場所を確保しておく。それが note のディレクトリだった。

### 別ジャンルが主軸を強化する逆説

不思議なことがあった。

ウイスキー記事を6本書いた1か月、Claude Code 系の記事は減っていない。むしろ、Vol.2 の執筆ペースは上がった。Vol.3 の構成設計もこの時期に詰まった。「別ジャンルを書いている時間があるなら本業に集中したほうがいい」という直感は、運用してみると裏切られた。

理由を3つに分けて言葉にする。

ひとつ。**素の感覚が鈍らない**。Claude Code 側は装置に守られて書いている。reviewer・reader・著者ペルソナが回って、原稿が「自分の文章」になっているかを最後に問う。ウイスキー記事には装置の負荷が要らない代わりに、書き手の素の感覚で「これは自分の語り口か」を毎回判断する必要がある。先日、ウイスキー記事の初稿で「香りが立ち上がる」という他人の言い回しが混ざっていて、自分で却下した。その感覚のまま Claude Code 側に戻ると、reader が出してきた表現を採用するか却下するかの判断が早くなった。

ふたつ。**「Claude Code の自分」の輪郭がはっきり見えるようになった**。ウイスキー記事を書いている自分は、SE 歴 26 年でもノンプログラマーでもない。バーカウンターで知らないボトルに反応する1人の客だ。その自分と、Claude Code を書いている自分との差を毎週感じることで、何を旗印にしているかが鮮明になった。輪郭は、別の自分との対比でしか見えない。一本足で立っていると、立っている本人には自分の輪郭が見えない。

みっつ。**書き続けるルーティンが、ジャンルをまたいでも止まらない設計になった**。ある週は Claude Code が書けなくても、ウイスキーが書ける。ウイスキーが書けない週は、Claude Code に戻れる。書く対象が複数あることが、書き続ける装置の冗長性になった。逃げ道は本流から外れる経路だが、別ジャンルの並走は、本流とは別の本流として動いている。

設計書を書いているとき、第5章をこのテーマで置くべきかどうか迷った。「Claude Code の本にウイスキーの章は混ぜないほうがいい」という声も自分の中にあった。それでも書き続けるという課題の射程を考えると、**主軸を変えずに別ジャンルを並走させる構造そのものが「書き続けるための装置」の一部**だった。書く題材の話ではなく、書き手の維持機構の話だ。

### 著者性は「何を書くか」だけでなく「何を書かないか」も含む

ウイスキー記事を書きながら、決めたことがいくつかある。

ひとつ。**Claude Code をウイスキー記事に持ち込まない**。AI を使ってテイスティングノートを生成する、AI でバーを検索する、AI でラベルを翻訳する——そういう Claude Code 的な切り口は、書ける材料が手元にある。それでも書かない。書いたら、ウイスキー記事の純度が落ちる。「結局この人 Claude Code の話に戻すんだな」と読者に思われた瞬間、別ジャンルとしての並走は終わる。

ふたつ。**Claude Code 系記事にウイスキーを持ち込まない**。本章は「書き続けるための装置」を語る構造論の章なので、ウイスキーを主軸と並べる形で例外的に登場させた。それ以外の通常運用の Claude Code 系記事には、ウイスキーを比喩としても出さない。「ピートの強いウイスキーのように、エージェントの個性も……」という書き出しは書ける。書けるが、書かない。読者は Claude Code を読みに来ている。

書かないことを決めると、書くものの輪郭がはっきりする。著者性は「何を書くか」のリストだけで成り立つものではなかった。**「これは書かない」と決めた領域の存在が、書くものの強度を決めている**。

Vol.1 を書いていたときの自分は、「Claude Code について書ける人」になろうとしていた。Vol.2 を書きながら、「Claude Code でチームを回す人」になった。Vol.3 のこの章を書き終える頃には、**「Claude Code を書くために、別の場所でウイスキーを書く人」**になっている。書く対象が増えたわけではない。書く対象を分けて、それぞれの場所で書き続けられる構造を持つ人になった。

書き続けるための「別の自分」は、書き手それぞれに違うはずだ。私の場合はウイスキーだった。料理かもしれない、走ることかもしれない、子どもとの会話かもしれない。何でもいい。**主軸を変えずに、主軸の外側で呼吸できる場所を1つ持っておく**——それが、書き続けるための装置の最後の部品だった。

> **3体構成なら**: 別ジャンルを試すとき、writer への指示から「Claude Code の記事として書く」という制約を外して書かせてみてほしい。主軸ジャンルの制約が外れたとき、writer のトーンはどう変わるか——その差分が著者性の輪郭を浮かび上がらせる。
