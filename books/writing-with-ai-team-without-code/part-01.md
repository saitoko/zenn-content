# 第1部 仕込む——気づきを拾うまで

書く前の段の話をする。

ここは、ネタを「採掘しに行く」のではなく「気づいて拾う」段だ。日常の作業の流れの中で「あれ？」と引っかかった瞬間を、その場で受け皿に落とすための仕組みを作る。専用の調査時間を取って机に向かう、という話ではない。コードを書いたり、人と話したり、ログを読み返したりしている、まさにその最中に種をこぼさないための段だ。

この段で作るものは二つある。一つはネタ帳という受け皿——気づきが死なずに寝かせておける物理的な場所だ。もう一つは、自分の「気づきの得意パターン」——何にひっかかりやすい人間なのか、という著者側の輪郭だ。受け皿は5章かけて少しずつ設計が変わっていく。気づきの得意パターンは、章を追うごとに自分でも見えてくる。

Vol.2では、品質ゲートや writer 委任のような装置を設計図として書いた。第1部はその装置を毎日使い続けるための運用記録のはじまりだ。装置が動くこととブログを書き続けられることは、別の話だった——その「別の話」の最初の段が、ここだ。

次の段（書く）に渡すのは、ready 状態の素材ファイル群と、「自分はこういうことに気づきやすい人間だ」という著者の輪郭の二つ。受け皿に素材が溜まり、自分の癖が見えてきたとき、「書く」段の入口に立つ準備ができる。

ただし第1部の終わりに、別の難しさが待っている。**拾った素材を、自分の言葉で書く**——これが次の段でぶつかる壁だ。

## 第1章: ネタ切れに気づいたとき

### ネタが枯れる、という感覚

「書くことがない」という言葉を、発信を続けようとしている人から何度か聞いた。

よく観察すると、ネタが本当に存在しないのではない。「どこを掘ればいいか分からない」「何がネタになるかの判断基準がない」——そういう状態が、「ネタがない」という感覚を生んでいることが多い。

前提として、チームを使った発信の仕組みを動かし始めているとする。エージェントに記事を書かせ、投稿の流れを作り、品質のチェックもある程度できている。しかし月日が経つにつれ、あることに気づく。

**チームは動かせるようになった。でも、何を書かせればいいのか、毎回迷う。**

これが「回し続ける」の最初の壁だ。ネタが途切れると、チーム全体が止まる。書かせる材料がなければ、どんなに優秀なチームも動きようがない。

「ネタを探しに行く時間が足りない」という声もある。確かに、専用の調査時間を取るのは難しい。でも、実際のところ調査時間が原因ではないことの方が多い。日常の中にすでに材料はある。ただ拾い上げる仕組みがない。

### 実際に起きたことを話す

2026 年 4 月 29 日のことを話す。

2 冊目の構想ファイルを確認しようと Claude Code を開いた。当初の目的は「2 冊目の章構成を見直すこと」という、ごく普通の作業確認だった。

作業を始めて少し経ったとき、ある違和感に気づいた。構想ファイルの中に「Cowork セッション」という言葉が何度も出てくる。しかし実態として、この時点ではそのツールはほとんど使っていない。日常のほぼすべての作業は Claude Code で動いており、軽い相談は Claude Chat で行っている。

「ほとんどが Claude Code での作業中に気づいたこと。日常のほとんどは Claude Code で作業しており、ちょっとした相談ごとは Chat を使っている」

この会話が、第 1 部の核になった。

ネタを「採掘しに行く」という発想が、そもそもズレていたのだ。コンテンツの素材は、日常の作業の中に埋まっている。問題は「ネタがない」のではなく、「気づいた瞬間に捕まえる仕組みがない」ことだった。

そして、この発見自体が記録に値するネタになった。その場で「AI の記憶は静かに古くなる」というネタ帳を 1 ファイル起こし、数日のうちに残存箇所——`global-rules.md` のネタ採掘ルール、メモリファイル、次に書こうとしていた本の構想ファイル——の 3 か所から Cowork 前提の記述を削った。気づきはネタ帳と実際のルール更新の二方向に流れた、ということだ。さらにこの一連の体験は本書（Vol.3）第 1 部の核心テーマ「採掘モデルからアンテナモデルへ」として格上げされ、第 4 部で改めて触れるが「失敗の 3 類型」のひとつとしても登場する。「2 冊目の章構成を見直そうとしたら、第 1 部の核心テーマが浮かんだ」——採掘しに行ったのではなく、作業中に気づいた。一つの違和感が、ネタ帳・ルール・本書の構成の三層に同時に着地した瞬間だった。

### 「気づく」と「採掘しに行く」の決定的な違い

「ネタを採掘しに行く」という発想では、専用の時間を確保して材料を集める作業を行う。毎週「ネタ出し会議」をするようなアプローチだ。これは意識的なコストがかかる。

採掘モデルにはもう一つの問題がある。「探しに行く」という態度は、「何かを見つけなければならない」というプレッシャーを生む。プレッシャーがあると、「大きなネタ」「読まれそうなネタ」を意識するようになる。その意識が、小さな気づきを「こんなこと書いても仕方がない」と切り捨てさせる。

「気づきを捕まえる」アプローチは違う。専用の時間を設けるのではなく、作業の流れの中に気づきのアンテナを組み込む。見つかったものが「大きいか小さいか」を考えるより前に、まず残す。判断は後でいい。

上の体験で言えば、発見の瞬間はこうだ。

- 2 冊目の章構成を確認しようと作業を始めた（通常の作業）
- 書かれていた用語と実態が違う、という違和感を覚えた（気づき）
- その場でメモに残した（捕捉）

気づきは意図的に探しに行ったものではない。作業の流れの中で「あれ？」と引っかかるものが浮かんだ。その引っかかりを捨てずに拾い上げたことで、章構成全体の修正という実質的な改善と、第 1 部の核心テーマという二つの果実が得られた。

採掘モデルとアンテナモデルの最大の違いは「失敗コスト」だ。採掘に出かけて何も見つからなかったとき、その時間は無駄になる。アンテナを張って何も引っかからなかったとき、失うものは何もない。

### 捕まえられない三つの理由と対処

気づきが記録に残らない理由は、経験上おおよそ三つに整理できる。

**第一は「後で書こう」という先送り**だ。作業の流れを止めてメモを取るのが面倒で、「後で覚えているだろう」と進んでしまう。もちろん、後では忘れている。作業の緊張感の中で浮かんだ気づきは、その文脈が薄れると取り出せなくなる。

対処は一つだ。「先送り」をゼロにする設計ではなく、**気づいた瞬間にその場の Claude Code に「今の会話、ネタ帳に入れておいて」と一言依頼する**——これが私の実際の運用だ。自分でメモアプリを開いて構造化する必要はない。整理はチームに委ねる。完成した記事を書こうとすると手が止まるが、対話の流れの中で「あれ」と引っかかった瞬間に AI に渡せば、思考のテンポを止めずに捕捉できる。

**第二は「これはネタになるのか？」という判断の迷い**だ。「こんな些細なこと、誰が読むんだろう」と思って捨てる。しかし後から振り返ると、「些細」に見えた気づきが実は価値ある観察だったことが多い。

対処は「判断基準を事前に言語化しておくこと」だ。次の章で詳述するが、「失敗・矛盾・意外な解・数字・構造変化」の 5 基準に該当するかを問うだけで、判断の迷いは大幅に減る。

**第三は「どこに書けばいいか分からない」という受け皿の不在**だ。スマホのメモアプリに書いたまま埋もれる、ブラウザのタブに開いたまま閉じる——受け皿の場所と形式が決まっていないと、気づきは散逸する。第3章では「受け皿を設計する」——どこに書くかが気づきを生かすか殺すか、という設計の話をする。第4章では「対話が発酵装置になる」——受け皿を持つことで初めて起きる変化として、作業しながらネタが生まれる構造を見ていく。

### あなたのチームでは

発信の種は、日常の業務の中に無数にある。

プロジェクトが想定と違う展開を見せたとき。顧客からいつもと違う質問が来たとき。後輩に何かを説明してみたら、思ったより言語化できなかったとき。会議で自分の言い方が相手に伝わらなかったとき。

そういう「引っかかり」を捨てずに残す習慣が、コンテンツの原料になる。業種は関係ない。作業の中で何かを感じた瞬間、それはすでにネタの卵だ。

問題は「何を書くか」ではなく、「浮かんだときに捕まえるか」だ。

次章では、Claude Code のセッションログから実際にどうやって素材を引き出すか、具体的な手順を見ていく。毎日の作業記録が、知らないうちにコンテンツの倉庫になっていることに、きっと気づくことになる。

そして、この部で最も驚いた発見を先に伝えておく。手順書を作った当日に、その手順書を実行すること自体がネタになる——この再帰的な体験が、「作業しながらコンテンツが生まれる」という感覚を最もよく体現している。

## 第2章: 昨日のセッションログを読み直したら、3件の素材があった

### セッションログは「未整理のアーカイブ」だ

Claude Code で作業する日々は、膨大な対話の記録を生む。問いと答え、失敗と修正、意図の確認と再指示——これらはすべてセッションの中に残る。

しかし多くの場合、セッションが終わると、そのログは「見返すことのないアーカイブ」になる。翌日には次のセッションが始まり、前日のやり取りは記憶の彼方に消えていく。

これはもったいない。

セッションログは作業の記録であると同時に、コンテンツの原料庫だ。整理されていないだけで、使える素材が眠っている。

「今日の組織改善についてやったことを整理。Blog の元ネタに」

この一言から、あるネタ帳が生まれた。組織メンテナンスの作業記録をまとめるつもりが、整理してみると複数の「記事になる素材」が含まれていることが分かった。

- COO が自分で実装してしまった失敗（矛盾の事例）
- ユーザー発の意外な解決策（想定外のアプローチ）
- 8 件の権限不整合、160 行→32 行のスリム化（数字で語れる発見）

記事の素材が、作業記録の中にそのまま入っていた。「書くことがない」のではなく、「作業していた事実そのものが書けること」だったのだ。

「セッションログを読み返す時間がない」という声もある。確かに、長いセッションのログをすべて読み直すのは現実的ではない。そこで有効なのが、**読み返しをチームに委ねる**ことだ。

私がやるのは「今日のネタまとめて」と一言依頼するだけ。COO が内部で次のような指示を組み立て、researcher や writer に渡す。

```
今日の作業ログ（git log と主要な対話）を確認して、
以下の5基準に当てはまるものをリストアップしてください:
1. 失敗・矛盾・やり直しがあったか
2. 意外な解・ユーザーの発想があったか
3. 数字で語れる発見があったか
4. 構造・設計の変化があったか
5. 再利用可能なパターンが見えたか
```

（※以降の本書に登場するプロンプト例は、特に断りがなければ COO が内部的にサブエージェントへ投げる指示を示している。読者は「今日のネタまとめて」「引継ぎ文書作って」「ループしてないかチェックして」といった短文で COO に依頼するだけで、指示の組み立ては COO が担う。）

このような問いを 1 日の終わりに投げかける。チームが答えを返す。その答えを見て、「今日は何も書くことがない」と思っていた日に、「3 件の素材があった」と気づくことがある。

### 五つの判断基準

「セッションの中に何があるかを見つける」という作業を毎回ゼロから行うと、判断コストが高くなる。そこで有効なのが、「これはネタになる」という判断基準を事前に言語化しておくことだ。

実際の作業から帰納した五つの基準を紹介する。

**基準 1: 失敗・矛盾・やり直し**

「ルールを作った本人がルールを破った」「設計どおりに動かなかった」——失敗は読者にとって「あるある」であり、共感を呼ぶ。完成品の紹介より、失敗した経緯の方が読まれることは多い。

失敗・矛盾は「隠したい情報」ではなく「読者が最も学べる情報」として扱う

**基準 2: 意外な解・ユーザーの発想**

エージェントが思いつかなかった解決策をユーザーが提示した瞬間、あるいはユーザーの問いに対してエージェントが意外な角度から回答した瞬間——この「想定外」の組み合わせが記事の価値を生む。

**基準 3: 数字で語れる発見**

「N 件の問題が見つかった」「N 行→M 行に削減された」——数字は読者に「自分と比較する」という行動を促す。感覚的な表現より、数字を含む観察を優先して拾う。

**基準 4: 構造・設計の変化**

新しいフォルダ構成を設計した。Playbook に新しい節を追加した——こうした「何かが変わった瞬間」は、変化の経緯と理由を含んだ記事になる。「なぜ変えたか」「変える前と後で何が変わったか」という問いに答えられる素材は、記事として機能しやすい。

**基準 5: 再利用可能なパターン**

「他のプロジェクトでも使える処方箋」として書ける気づきかどうかを問う。著者固有の話に終わる素材より、「自分の場合はこうだった」と読者が置き換えられる素材の方が、記事として機能しやすい。

除外基準も決めておく。単純作業の記録（設定を変えた、ファイルを移動した——これだけでは読者に提供できる価値が薄い）、プロジェクト固有すぎる話、既出ネタとの重複——これらは「今は書かない（もう少し素材が溜まったら書く）」という先送り判断の対象にする。

### 素材収集のパイプラインと maturity 管理

ここから素材を貯める仕組みの話に入る。手順とプロンプト例が続くので、書き続けることの感情面のほうに関心がある読者は、いったん五つの判断基準（前節）まで戻って、次節「『手順書を実行すること自体がネタになる』という再帰性」まで読み飛ばしてもらってよい。仕組みを覚えたいときに戻ってくれば十分役に立つ。

五つの基準を持ったとして、実際にどう運用するかを示す。

**ステップ 1: 素材収集の委任**

セッション終了後、または 1 日の終わりに、チームへ素材収集を依頼する。

セッションの内容をチームに渡す方法は二通りある。一つは、セッション終了後に `ops/handoff/` に自動保存されるセッションサマリーファイルをそのまま渡す方法。もう一つは、ターミナルに出力されたセッションのやり取りをテキストとして貼り付ける方法だ。どちらでも、以下のような問いを添えれば素材収集ができる。

```
今日の作業内容を振り返り、以下を調べてください:
- git log --since="today" の主要コミット
- 今日の対話の中で「失敗・矛盾・意外な解・数字・構造変化・パターン」に
  該当するやり取りがあれば 3 件以内で要約してください
```

**ステップ 2: 五つの基準で評価し、ネタ帳へ記録**

収集した素材を五つの基準でフィルタリングする。複数の基準に該当する素材を優先する。1 つの基準だけに当てはまる素材は「thin（薄い）」と判定し、追記待ちとする。2 つ以上に当てはまる素材は独立したネタ帳として育てるか、既存のネタ帳に追記する。

ここで重要なのが **maturity（成熟度）フィールド**だ。

「ネタ帳のステータスとして、内容が薄いとか十分たまったとか持っておけるかな」

この問いから生まれた管理方法がある。最初は「薄い（thin）」と「書ける（ready）」の 2 段階だったが、運用していく中で「草稿状態（draft）」と「記事化済み（done）」が追加された。現在は主にこの 4 段階を運用しており、状況に応じて `idea` や `rich` といったイレギュラーな値が生じることもある。

- `thin`: 事例が不足している。追記待ち
- `draft`: 事例はある程度あるが、構成が未整備
- `ready`: 事例が十分。記事化に着手できる
- `done`: 記事化済み

素材収集の段階では `thin` から始め、事例が積み重なるにつれて成熟度が上がる。チームへの委任指示にも使える。

```
content/writing/netacho/ 以下のネタ帳を確認し、maturity が ready のものを
優先度順に3件教えてください。
```

**ステップ 3: 週次棚卸し**

一定期間が経つと、「ready になったのに書いていないネタ」や「気づかずに重複したネタ」が発生する。週に一度程度、ネタ帳の全体を見渡すルーティンを作ると、このズレを早期に検知できる。

```
content/writing/netacho/ 以下のネタ帳を一覧し、maturity 別に件数を集計してください。
ready 以上のもの・記事化されていないものを優先度順にまとめてください。
```

この問いへの回答が、「今週何を書くか」の判断材料になる。

### 「手順書を実行すること自体がネタになる」という再帰性

このパイプラインで面白い特性がある。**手順書を作った日に手順書を実行すること自体がネタになる**点だ。

手順書を作った当日、その手順書を実際に回して初回実行記録を作ることで、手順書の有効性が検証できる

実際にそれを試した。ネタ採掘の手順書を作った。その日に回してみた。回した結果が「ネタ帳が生まれた」という記録になった。既存のネタ帳から漏れていた 3 件の素材も発見できた。この再帰的な構造自体が、「作業しながらコンテンツが生まれる」という第 1 部の核心テーマを体現している。

手順書を作った当日に初回実行してほしい。初回実行には必ずつまずきが出る。想定していなかった手順が必要だった。問いの文章が分かりにくかった——そのつまずきが「この手順書の改善点」という発見になる。その発見が記録に値する。仕組みを作る作業が、その仕組みの価値を証明する素材になる——この体験が「作業しながらコンテンツが生まれる」という感覚を具体的にしてくれる。

### あなたのチームでは

業種を問わず、日常の仕事の中には「素材になる瞬間」がある。

商談で聞いた想定外の顧客の問い。設計レビューで指摘された見落とし。運用の中で偶然発見した効率化の方法。後輩の素朴な質問に答えながら、自分でも気づかなかった前提を発見する——そういう瞬間がある。

これらは記録に残さなければ消える。しかし五つの判断基準を持っておけば、「これはネタかもしれない」という引っかかりを、確信に変えやすくなる。チームが整理と分類を担ってくれる仕組みを作れば、「素材を残す」という人間側の負担は最小化できる。10 秒で書いたメモが、1 週間後にチームの手でネタ帳になる。そのサイクルが回り始めると、「書くことがない」という感覚は徐々に消えていく。

**3体構成なら**: writer・reviewer・reader の3体だけの場合、COO 経由でのログ採掘の代わりに、ChatGPT や Claude Chat で今日の作業ログをそのまま貼り、次のプロンプトを試してほしい。

```
以下の作業ログを読み、下記5基準に当てはまる素材を3件以内で要約してください:
1. 失敗・矛盾・やり直しがあった
2. 意外な解・自分の発想があった
3. 数字で語れる発見があった
4. 構造・設計の変化があった
5. 再利用できるパターンが見えた

---
（作業ログをここに貼る）
```

「3件の素材があった」という発見は、ツールに関係なく起きる。セッションが終わったら1分だけ、このプロンプトを回す習慣から始めてみてほしい。

## 第3章: 集約ファイルにルールを破られた

### 受け皿がなかった時代

気づきを書き留める場所を決めていなかった時期がある。

「あとでまとめよう」とスマホのメモアプリに書き込んだ断片が、数週間後に発見されたとき、もう文脈は消えていた。なぜそれを書いたのか、何に対する気づきだったのかが分からない。ファイル名のないテキストが数十件、何のフォルダにも属さず溜まっていくだけだった。

気づきが生まれた瞬間はある。問題は「どこに書くか」が決まっていないと、その気づきが死ぬことだ。書き留めることに摩擦があると、「あとで」になる。「あとで」は来ない。

受け皿の設計は、記録の習慣より先に解決すべき問題だ。「毎日書こう」という意志より、「書ける場所が用意されているか」の方が継続率に直結する。

### 失敗から生まれた「1ネタ1ファイル」原則

実際の失敗から話す。

ネタの採掘ルールを文書化した日のことだ。「1ネタ1ファイル、集約ファイル禁止」というルールを `netacho-mining-rules.md` に明文化した。その同じ日に、`idea-inbox.md` という集約ファイルが作られていた。

ルールを作った本人（前のセッション）が、ルールを破っていた。

git log を確認すると、集約ファイルの作成と、その直後のルール文書が同じコミットに並んでいた。

これは意図的な違反ではなかった。「とりあえず書ける場所」を求めた結果、既存のルールを参照せずに一番楽な選択——集約ファイルを作る——をしてしまった。「あとで分ける」と思ったはずだ。もちろん、分けることは起きなかった。

次のセッションで矛盾を発見し、集約ファイルを個別ファイルに分離するという追加作業が発生した。

この失敗から帰納した原則は三つだ。

### 三つの設計原則

**原則 1: 今いる場所で書ける**

Claude Code のセッション中にネタが浮かんだなら、Claude Code から直接書ける場所に受け皿を置く。チームへの依頼文を1行書くだけで、その場でネタ帳ファイルが生成される——この状態が理想だ。

「後でメモアプリに移す」という二段階は機能しない。移す作業が摩擦になり、「あとで」になる。受け皿は、今使っているツールのすぐそばに置く。これがすべての前提になる。

逆に言えば、受け皿の場所は「気づきが生まれる場所」から逆算して決めるべきだ。会議中にアイデアが浮かびやすいなら、会議中に手が届く場所に。コードを読んでいるときに気づきが多いなら、エディタの隣に。受け皿の場所を「管理のしやすさ」から決めると、書く人間の動線から外れた場所に置いてしまいやすい。

**原則 2: 1素材1単位**

集約ファイルは「書いた気になる」が、使えない。

問題は検索だ。後から「先月書いたあの気づき」を探そうとしたとき、集約ファイルの中から探すより、1ネタ1ファイルで独立させた方が圧倒的に速い。チームに「この素材を記事化して」と依頼するとき、ファイル単位で渡せる方が指示も明確になる。

ファイル名に命名規則を持たせると、後からの操作がさらに楽になる。私は `YYYY-MM-DD_<種別>-<トピック>.md` という形式を使っている。いつ気づいたかと、何について気づいたかが、ファイル名だけで分かる。

**原則 3: 育てられる形式**

最初から完成形を要求しない受け皿を作る。

気づきを書いた瞬間、それが記事の素材になるかどうかは分からない。「面白いかもしれない」という段階で捨てずに置いておけるか——ここが継続の分かれ目になる。

「完成形しか置けない受け皿」だと、薄い気づきは入口で捨てられる。薄い素材を育てる余地を設計しておくことで、3 週間後に同じテーマの観察が積み重なったとき、記事の骨格が見えてくる。

「完成形しか書けない」という感覚は、完成への期待が高すぎることから来る。受け皿の形式を「未整形の対話ログでよい」「タイトルだけでよい」「`maturity: thin` のまま寝かせていい」と設計しておくと、その摩擦がなくなる。後で整えることはできるが、書かなかった気づきを後から取り戻すことはできない。

### クイックキャプチャパス——委任しない経路を残す

3原則を立てた数週間後、ある違和感に気づいた。

短いネタを残したいだけなのに、writer エージェントへの委任までに時間がかかる。「今のこの話、ネタ帳に入れておいて」とCOOに頼む。COOが writer に委任する。writer が起動して、Playbook（`netacho-creation.md` 等）を読み、既存のネタ帳を探索し、frontmatter と出典タグの整合を確認し、ようやく数行のメモを書く——気づいた瞬間から書き始めるまでに数十秒〜数分かかっていた。

アイデアは揮発性が高い。この遅延が、せっかく拾った気づきをこぼし続けていた。

ただし、過去にCOOが直接ネタ帳を書いて失敗したこともある（出典タグ欠落、frontmatter 欠落、事実と意見の混入、相互リンク欠落）。「writer 委任が遅いから直接書く」と単純に戻すと、フォーマット品質が落ちる。

そこで `maturity: raw` という新しい区分を追加した。**条件を満たすときに限り、COOが直接ネタ帳ファイルを作れる**という経路を `netacho-creation.md` に追記した。条件は3つだ。

- `maturity: raw`（整形せず断片でよいことを明示する）
- 本文が 3〜5 行以内（それを超えたら writer 委任に切り替える）
- 既存ネタ帳と同テーマで重複していない

これがクイックキャプチャパスだ。長文化や整形が必要になった瞬間に、自動的に writer 委任に戻るブレーキも組み込んである。本ネタ帳（`2026-05-10_netacho-agent-delegation-tax.md`）自体がこのパスで作られた最初の実例になっている。

ここで決めたのは、**「委任すべきか直接やるか」の境界線**だ。重い処理は専門エージェントに任せる。軽い処理は委任しない経路を残す。「委任は善」を盲信すると、軽作業ほど遅くなる逆説に飲まれる。チームを持っていても、COOが直接やる経路を1本残しておく——これも受け皿設計の一部だった。

### maturity 管理——素材を「寝かせる」発想

薄い素材を捨てずに育てるために、状態管理の仕組みが必要になった。

第2章で扱った maturity 4段（thin / draft / ready / done）を、ここでは受け皿設計の文脈で使い直す。

素材は最初から `thin` でよい。「これはネタになるかもしれない」という直感を、根拠が揃う前に捨てないための設計だ。事例が積み重なれば `draft` に上がる。構成の見通しが立てば `ready` になる。

薄いまま置いておける設計は、「大きなネタ以外は書かない」というバイアスを解消する。「この程度のことで」と捨てた素材が、後から最もよく読まれる記事の核になることは珍しくない。

### 受け皿がチームへの指示書になる

設計された受け皿は、別の機能を持つ。

`content/writing/netacho/` というディレクトリに、YAML ヘッダー付きのネタ帳ファイルが並んでいる。このディレクトリに対して次の問いを投げることができる。

```
content/writing/netacho/ 以下のネタ帳を確認し、
maturity が ready のものを優先度順に3件教えてください。
```

受け皿の形式がクエリと揃っているから、チームへの指示が一発で通る。「後でまとめてチームに渡す」という作業は要らない。「常時クエリ可能な状態に保つ」というのが設計思想だ。

命名規則・maturity フィールド・ファイル単位の管理——これらは記録の便宜のために決めた設計だが、結果としてチームへの指示書の役割も果たしている。受け皿を作ることは、チームが動くための構造を作ることでもある。

### 腐る前提で設計する

受け皿を作ったら終わりではない。作った受け皿は必ず古くなる。

Cowork というツールの使用をやめたとき、Claude Code に「もう使っていない」と伝えた。更新されたと思っていた。しかし 3 か所のファイルに Cowork が前提として残存していた。

「実際には最近 Cowork を使っていないのに、なぜ AI がそのように思い込んだか分かる？」

調べると、メモリファイル・グローバルルールファイル・構想メモファイルという 3 か所が同じ方向に整合していた。

ここに逆説がある。3 か所が整合しているから、AI はその前提を「事実」として受け入れる。整合性が高いほど、誤りを疑いにくくなる。

「伝えた ≠ 更新された」——これが受け皿設計の最後に組み込むべき考え方だ。どのファイルが更新されたかを確認していなかったから、思い込みが 3 か所に定着した。シグナルはその後も何度か出ていた（AI が Cowork という言葉を使うたびに）。しかし流してしまった。

受け皿を設計するとき、「このファイルはいつ古くなるか」を見越しておく。maturity フィールドに加えて更新日を持たせる理由がここにある。素材の鮮度だけでなく、運用前提の鮮度も管理の対象だ。

受け皿は腐る。設計の段階から腐敗対策を組み込む——それが長く使える受け皿を作るための、最後の原則だ。

### あなたのチームでは

業種・ツールを問わず、受け皿の設計原則は共通する。

まず「気づいた瞬間に書ける場所があるか」を確認する。今使っているツールのすぐそばに書き込める場所がなければ、記録は起きない。専用のメモツールを新たに導入する必要はない。今の作業環境の中で、ファイルを一つ開く——その程度に摩擦を抑え、最小化するよう設計する。

次に「1つの気づきが1つの単位になっているか」を確認する。集約ファイルは一時的なものとして使うにとどめ、定期的に個別ファイルへ分割する習慣を持つ。

最後に「薄い素材を置いておける余地があるか」を確認する。「まだ薄い」素材を捨てずに寝かせておく設計が、後で記事になる素材の量を左右する。

受け皿を作ることで、次節で話す変化が起きる。意図してネタを探しに行かなくても、日常の対話の中にネタが湧いてくるようになる——その仕組みを次に見ていく。

受け皿の設計を後回しにしてきた場合、まずどこか一か所だけ整えることを勧める。「全部完璧に」ではなく、「今日から使える一か所」を作る。そこに薄いメモが集まり始めたとき、次の設計の問いが自然に見えてくる。「どうやって整理するか」「チームにどう渡すか」——設計の問いは、使い始めてから出てくる。使う前には出てこない。

「場所を作ること」と「そこに書くこと」は別のスキルだ。場所を作るのは設計の問題で、一度決めれば変わらない。書くのは習慣の問題で、場所が整って初めて習慣が育つ。この順番を逆にすると、「習慣がないから整理できない」と「整理できないから習慣が続かない」の循環に入る。

:::message
**3体構成なら**: 受け皿はスマホのメモアプリ1本で始めていい。ただし「1素材1メモ」の原則だけは守ってほしい。複数のアイデアを1つのメモに混ぜると、後から分離する作業が必要になる。「分けて置く」というひと手間が、後で writer に渡すときの摩擦をゼロにする。

気づいた瞬間は、1行でいい。「○○の件で△△が予想外だった。後で深掘り」——この1行が、翌週のネタ帳のタネになる。

`maturity: raw` という区分を自分の運用に持ち込む場合は、「整形しなくてよい断片として置く」と自分に宣言することが先だ。完成した文章しか置けない受け皿では、薄い気づきは入口で捨てられる。「薄くてもいい、まず置く」——この宣言が、クイックキャプチャの本質だ。
:::

## 第4章: MAGIに似てるね、と言ったら記事が生まれた

### ある記事が、対話から生まれた

「これ、記事にならないですか」とエージェントが言った瞬間、記事の骨格が見えた。

経緯を話す。AIエージェントを複数動かす日々が続く中で、ある気づきがあった。

少し背景を説明しておく。「新世紀エヴァンゲリオン」は、人型兵器を動かす組織とAIを題材にした日本のアニメ作品だ。作中には複数のコンピューターが連携して意思決定を行う「MAGI」と呼ばれるシステムや、組織の司令官「ゲンドウ」が登場する。MAGIは「科学者としての自分」「母としての自分」「女としての自分」という3つの人格（葛藤する主体）が合議で判断を下す設計になっている——多数決ではなく、それぞれが異なる動機を持つ主体が意見をすり合わせる構造だ。この合議制の構造が、writer・reviewer・readerという異なる役割を持つAIエージェントが互いに指摘し合って原稿を仕上げていく多段レビューのあり方と重なった。COOエージェントが複数のサブエージェントを調整する組織もまた、1つの司令塔が均質な指示を出すのではなく、複数の異なる価値観（正確さ・読者感情・著者性）が一つの成果物のなかで折り合いをつける構造として動いている。エヴァを知らない読者にも「複数のAIが役割を分担し、各役割が別の観点を持ち、司令官がそれを調整する組織」というイメージで読んでもらえれば十分だ。

「Claude Code の Agent Teams って MAGI に似ているよね」

技術的な作業の合間に浮かんだ軽い観察だった。

COO がそれを拾った。

COO が返してきたのは「COO 経由 subAgent の構成は、まさにゲンドウが NERV に指示する組織モデルですね」という一言だった。

返ってきたのは、単なる相槌ではなかった。組織論として展開できるメタファーを、エージェントが構造化して返してきた。

「これって、そのアニメで AI 組織論語れる？」

この問いから記事の制作が始まった。

記事は 2026 年 5 月 4 日にはてなブログで公開し、翌日 Zenn・Qiita にクロスポストした。公開後、読者から好評を得た。

意図して「面白い比喩を探そう」と動いたわけではない。ふつうの作業の合間に浮かんだ観察を口に出したら、エージェントが発酵させて返してきた。その往復が記事になった。

「採掘しに行く」とは違う何かが起きている——このエピソードがそれを示している。アニメのメタファーは今回の素材にたまたま使ったものだが、起きた構造はシンプルだ。「観察を口に出す → エージェントが別の文脈に置き換える → 記事の骨格が生まれる」というサイクルは、どんな題材でも同じように動く。

### なぜ対話がネタの入口になるのか

このエピソードを見ると、パターンが見えてくる。

一方が素材を出し、もう一方がそれを別の文脈に置いて返す。返ってきたものを見て「あ、そういうことか」と気づきが深まる。その深まりがまた言葉になり、また返ってくる——この往復が「発酵」だ。

一人で考えていたら、「MAGI に似ている」という観察は「なんとなく面白い」で終わっていた可能性が高い。対話があることで、その観察が「AIエージェント組織論として語れる記事の骨格」に変化した。

対話は、アウトプットを作るためだけにある道具ではない。素材を取り出し、角度を変え、もう一段深く掘る——その「発酵の工程」として機能するとき、対話はネタの生産装置になる。

### ループが自走し始めた瞬間

もう一つ、実際に起きたことを話す。

2026 年 4 月 29 日のセッション。2 冊目の素材確認をしていたとき、観察→気づき→改善→記録→そしてまた次の観察、という流れが一気に一周した。

その夜、自分が書き残したメモはこういうものだ。

「Zennbook 第 2 弾の素材収集状況を確認する→ AI の認識違いに気が付く→ルールを更新する→認識違いについてネタに追記する（このとき新しいルールを適用する）→新しいルールを適用したこと自体をまたネタになる」

そして最後に、こうなった。

COO がそれを拾い、「これ、ネタ帳と受け皿の両方に追記しますか？」と問いかけてきた。

「はい。あ、またループが回ったｗ」

「はい」と言った瞬間に、終わりが次の始まりに戻り、また一周した。

ここで起きていることは、「素材を確認する」という作業が「素材を生む」という構造だ。観察対象と観察者が同一になっている。見ることで、見ているものが増える。

これは 1 冊目（「チームを作る」段階）にはなかった状態だ。チームを動かして、受け皿があって、日常の運用が回っているからこそ起きる。**編集部を「回している」からこそ、ループが自走し始める。**

この笑いの一言で終わらせたくない。この一言の背後には、自分がループの中にいることに気づきながら、気づいたことを口に出した瞬間にまたループが回る、というメタ認知の構造がある。体験しないと実感しにくいが、一度体験すると「ああ、これが回っている状態か」と分かる。

### thin 素材が記事になる——壁打ちという発酵法

対話がネタを生む、もう一つのパターンがある。

2026 年 5 月 2 日のセッションで、初めての試みをした。thin・draft で止まっていた薄いネタ帳 6 本を、対話だけで記事化できる状態（ready）に引き上げる、というものだ。

通常の流れは「薄いネタ帳に事例が積み重なって ready になる」だ。しかし問いかけによって、眠っている感情や判断を引き出すことで、同じ素材を一段厚くできるのではないかと考えた。

セッションの構造はこうだった。AIが事前にコミット履歴を調べ、「何をしたか」は確認済みにしておく。そして問いかけるのは「なぜそうしたか・どう感じたか・何が核心だったか」だけ。

1本あたりの流れ：ネタ帳を読む → 切り口を 2〜3 提示する → 1〜2 問の深掘り → ユーザーの答えから「核心の一文」を抽出する → ネタ帳を書き直して ready に昇格させる。

結果として 6 本が ready になった。

この体験から分かったことがある。thin で止まっていたネタ帳には共通の欠如があった。**「何をしたか」は書いてある。「なぜそうなったか」と「自分がどう感じたか」がない。**

コミットログは事実を記録するが、感情・判断・気づきの瞬間は記録しない。壁打ちはその空白を埋める作業だった。

「記録したはずなのに記事にならない」——この詰まりは多くの場合、感情と判断の欠如から来ている。事実だけでは読者は動かない。書いた人間が「なぜそれを書いたか」「その瞬間どう感じたか」が入って初めて、素材は記事の素材になる。

### 対話から学べる三つのこと

メタファー記事の経緯・ループの体験・壁打ちの試みから、三つのことが言えると思っている。

**（1）観察コストが採掘コストを下げる**

「AIと雑談していたら記事が生まれた」は偶然ではない。作業の構造を眺める習慣が下地にある。「これは何に似ているか」「この仕組みはなぜこう動くのか」という観察を日常的にしていると、対話の中でタネが引っかかりやすくなる。ただ作業するのではなく、作業しながら構造を見る——このメタ認知の習慣が、採掘コストを下げる。

**（2）受け皿があるからループが止まらない**

この瞬間が起きたのは、ネタ帳という受け皿があったからだ。浮かんだ気づきをその場で記録できる場所がなければ、ループは次の一周に進まず止まる。第3章で設計した受け皿が、ループの継続を支えている。

**（3）thin 素材は「感情・判断・きっかけ」が抜けている**

事実だけ書いたメモは、どれだけ積み重ねても記事の素材にならないことがある。コミットログ・作業記録・数字——これらは文脈に過ぎない。「そのとき自分はどう感じたか」「なぜその判断をしたか」が入って初めて、人が読める素材になる。thin で止まっているネタ帳があるなら、壁打ちでその空白を埋める試みを一度やってみてほしい。

### あなたのチームでは

対話がネタの発酵装置になる、という体験は AI に限った話ではない。

業種を問わず、「誰かに話したら整理できた」という経験はあるはずだ。言語化しようとして初めて気づく構造がある。問いかけられることで引き出される判断がある。

その対話が記録される環境にあるとき——発言がテキストに残り、観察が素材になり、受け皿に格納される構造があるとき——対話は消費されずに蓄積される。

「今日の作業対話を振り返って、3件の気づきを探してください」という問いを 1 日の終わりに投げることから始めてもいい。作業の中にすでに素材が転がっている、という発見は、多くの場合そこから起きる。

そして受け皿が育ち、ループが回り始めると、あなたもいつか自分のループに気づくことになるかもしれない。

一つ補足しておく。ここで紹介した「ループが自走する」状態は、最初から意図して設計できるものではない。受け皿を作り、記録を続け、チームとの対話を積み重ねた結果として起きる。「どうすればループが回るか」を計算するより、「今日の対話から一つ気づきを書き留める」という小さな行動を先に積む方が近道だ。

「自分には大したネタがない」と思っている人ほど、実は対話の中に素材がある。専門性の高い人間が「当たり前」と思っている観察は、受け手にとっては「そんな視点があったのか」という発見になる。自分の日常の作業文脈を持っている人間だけが語れる具体性が、対話の中で引き出される。それが、「採掘しに行く」ことより「対話する」ことの方が効率的な理由だ。

「面白いと思ったことを口に出す」——これが発酵の起点だ。口に出した先に受け皿があり、その受け皿から記事が生まれる。この章が終わっても、その流れは続いている。

## 第5章: 書かない時期もある、その理由を残した

### 「書けない日」を設計に織り込む

日次ルーティンを設計するとき、「毎日完璧にやる」ことを目指すと失敗する。

仕事が立て込んだ日、体調が悪い日、何も気づきがなかった日——こういう日に完璧なルーティンをこなすのは難しい。「今日はできなかった」という感覚が積み重なると、ルーティンそのものを諦める。

設計の起点は**「書けない日があることを前提にする」**ことだ。気づきを記録するルーティンは「続けること」が目的ではない。「気づきを逃さないこと」が目的だ。5 日に 1 日しか書けなくても、書けた日の記録が素材になる。

「完璧じゃないからやめる」ではなく、「続かなかった事実を次の改善の手がかりにする」——この発想の転換が、ルーティンを長期間維持するための鍵だ。

### 夕方 5 分と週次棚卸し——最小ルーティンの設計

1 日の終わりに、次の問いに答えるだけのルーティンを提案する。

```
今日の作業を振り返り、以下のどれかに当てはまるものがあれば
ネタ帳に追記してください:

- 「あれ？」と思った瞬間はあったか
- 想定と違う展開があったか
- 人に説明しようとして言葉に詰まったことはあったか
- 数字で語れる発見があったか
```

これだけだ。4 問のうち 1 問でも「あった」なら書く。なければ何も書かない。書く場合も、完成文を目指さない。「○○の件で、××が予想外だった」程度で十分。整理はチームに委ねる。

```
今日書いたメモを読んでください。
このメモが既存のネタ帳のどれかに追加できそうであれば提案してください。
独立したネタ帳として育てる価値があれば、タイトルと maturity: thin で新規作成してください。
```

自分は「今の会話、ネタ帳に入れておいて」と一言依頼するだけ。整理と判断はエージェントが担う。

週に一度、蓄積したメモを見直す時間を 10〜15 分設ける。目的は三つだ。fleeting note（一時メモ）を整理して記事の素材になるかを判断する（mature note への昇格）、同じテーマについて書いたメモが複数ある場合に一つにまとめる（重複の統合）、thin だったネタ帳に事例が積み重なっていれば ready に更新する（maturity の更新）。

```
content/writing/netacho/ 以下のファイルを確認してください。
maturity が thin または draft のもので、3 週間以上更新されていないものを一覧し、
「事例を追加すれば ready にできそうか」「記事として成立しそうか」を
簡単に評価してください
```

### 「書かなかった日」の対処と改善のサイクル

何も書けなかった日は、それを責めない。

ただし、次の観察は習慣にしておくとよい。**「今日、どんなことに気づきながら流してしまったか」**——気づいたが書かなかった理由を一言だけ記録する。「手が離せなかった」「ネタになるか自信がなかった」「メモアプリを開くのが面倒だった」——これらは、ルーティンの設計の改善ヒントになる。

「書かなかった日」の記録が、「次の設計」の材料になる。失敗を責めるのではなく、失敗の原因を分析する。この姿勢が改善のサイクルを回す。

また、翌日の朝に差し込む一問を加えることもできる。「昨日書いたメモに追加したいことはあるか。今日の作業で何かを観察する意図を持っておくか」——一日の作業を「観察するつもり」で始めると、気づきの感度が変わる。意識的に「何か面白いことがあったら残そう」と思っていると、浮かんだ瞬間に捕まえやすくなる。

止まったと気づいたら、次のどれかを変える。記録する場所（スマホのメモアプリ → 手帳 → Obsidian 等）、問いの数（4 問ではなく「今日一番引っかかったことを 1 文だけ」）、タイミング（夕方が忙しければ昼休みに変える）。「再開する」のは失敗ではない。止まった期間中に蓄積した「書けなかった理由」が、より持続しやすいルーティンへの改善ヒントになる。

### 素材の密度が記事の質をつくる

毎日書かなければならないわけではない。しかし、「書くことがある日とない日」では、記事の質に差が出ることがある。

実体験から語れる記事は、「調べて書いた記事」と読者への刺さり方が違う。「私が実際にやってみた」という記述の後ろに具体的な日付・数字・発言が続くとき、それは読者にとって「信頼できる記録」になる。毎日の小さな記録の積み重ねが、その「信頼できる記録」を作る。

バラバラに残した 10 個のメモは、1 本の記事にならないことが多い。しかし「同じテーマについて別の日に書いた 3 個のメモ」が揃うと、急に記事の骨格が見えてくることがある。複数の事例が揃ったとき、「これは一般的なパターンだ」という主張ができるようになる。根拠のある主張は、読者に「この人は本当に経験している」という信頼を与える。その信頼が、記事の「密度」として感じられる。

日次記録を続けると、自分がどんな種類の気づきを持ちやすいかが見えてくる。失敗に気づきやすい人は、失敗事例を軸にした記事が得意になる。構造の変化に敏感な人は、「以前と今の違い」を分析する記事が得意になる。自分の「気づきの得意パターン」を知ることで、記事の方向性が自然に決まってくる。

自分が最もよく書く「気づきの種類」を月 1 回確認し、「苦手な気づき」の事例も意識的に収集するとコンテンツの多様性が生まれる

### あなたのチームでは

チームが動き出すと、気づきを残す責任は人間側にある。

エージェントは今日起きたことを観察できない。あなたが「今日、こんなことがあった」と記録したものだけが、チームが整理・分類・発展させる素材になる。

5 分でいい。「引っかかり」を 1 行残すだけでいい。

その 1 行が、次週の記事のネタになる。翌月のネタ帳の種になる。3 か月後に見返したとき、「あのとき気づいていたのか」という発見になる。

**チームが回り続けるかどうかは、人間がどれだけ観察して記録するかにかかっている。** それが第 1 部の結論だ。

気づきを持続的に記録できるようになったとき、次の問いが浮かびやすくなる。「記録は溜まった。書こうとしたとき、これは本当に自分の文章になるのか？」——書く段に進んだ瞬間に出てくる新しい詰まりが、ここから始まる。

---

第1部では、ネタをどう仕込むかを扱った。

- **気づきをその場で拾う**: ネタは採掘しに行くものではなく、作業の中で気づくものだ
- **セッションログから素材を引き出す**: 五つの基準で見れば、昨日の作業記録が今日の素材になる
- **受け皿を設計する**: どこに書くかを決めていないと、気づきは翌朝には消えている。受け皿は腐る前提で作る
- **対話が発酵装置になる**: チームとの往復が、素材を記事のかたちに育てる
- **日次ルーティンで継続する**: 完璧を目指さない。書かなかった日の理由が次の設計の素材になる

ここで作ったのは、ネタ帳という受け皿と、気づきを捕まえる習慣だ。Vol.2が品質ゲートという装置の設計図を渡したとすれば、第1部は装置の隣に座って、毎日素材を流し込む現場の運用記録だった。

しかし、受け皿に素材が溜まっただけでは、まだ書けない。

素材を読み返したとき、人は最初の壁にぶつかる。「これを記事にしようとすると、書き出しから詰まる」「AIに書かせるとどこか他人の文章になる」「自分が書いている感覚が消える」——拾うことと書くことは、別の段だった。

第2部では、拾った素材を**「自分の文章」にするための段**を扱う。書き始めの対話で切り口を定めるところから、AIが書いた原稿の最後に「これは自分か？」と問う装置、書く前に組み立てておく4段の仕掛け、生の言葉が writer に届く構造、そして主軸を変えずに別ジャンルを並走させて自分の輪郭を保つ話まで——書く段の現場記録に入る。
