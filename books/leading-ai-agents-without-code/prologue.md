# 序章: コードを書けない私が、AIに「チーム」を持たせるまで


## Mac miniを衝動買いした

Claude Codeを初めて触ったのは、「どんなもんだろう」という軽い好奇心からでした。

最初の日は近所のラーメン屋を検索するアプリを作ってもらいました。「へえ、なかなかやるな」程度の感想でした。

翌日、調子に乗って本格的な業務システムを試してみました。「Javaで銀行システムのサンプルを作ってほしい」と指示文（プロンプト）を打つと、複雑な依存関係を自動で解消しながら、実際に動くシステムが完成した。プログラムを書いたのは自分ではないのに。

**本当にびっくりしました。「こりゃすごいな」と思った。**

その感動のまま、Mac miniを注文しました。「Claude Code専用の作業環境が欲しい」という、完全に感情で動いた判断です。

ところが——世界的な人気で在庫が薄く、届くのは1ヶ月以上先とのこと。

つまりこの本で話す内容は**すべて、メモリ8GBのWindows PCで実現したこと**です。高性能マシンが必要だったわけじゃなかった、というオチです。こういうことは、後になってから気づくものです。

## でも私は、コードを書けない

衝動買いをしておいて恐縮ですが、自己紹介をさせてください。

今の仕事はチームリーダーやPM中心で、自分でコードを書く機会はほとんどありません。技術的な判断や設計を担うのがメインです。もともとSEとしてキャリアを始めて、気づけば26年になりました。

「AIを使って何か作りたい」と思っても、コードが書けるわけではない。だから「プロンプトだけで動いた」という感動は本物でしたが、同時にこう思いました。

「本業で使うには社内規程がある。勝手には導入できない」

では何のために使うか。そこで最初に作ったのがGTD（タスク管理の方法論）のコマンドラインツールでした。『はじめてのGTD ストレスフリーの整理術』という本の方法論を、自分専用のツールに落とし込む、という実験です。

この「本業では使えないから、自分のために使う」という方向転換が、この後の展開を大きく変えました。

同じような状況の人は多いと思います。管理職になって久しい。コードは書けないわけではないが、もう書かない。「AIで何か作りたい」と思っても、手が動かない。——この本は、そういう人のために書いています。

これはまさに、チームリーダーやPMが毎日やっていることです。要件を整理して、役割を決めて、成果を確認して、問題があれば修正指示を出す。そのスキルがそのまま使えます。


## 10日後には、9体のチームが動いていた

結論から言います。

Claude Codeを初めて触ってから10日後には、担当業務を持つAI（本書ではこれを**エージェント**と呼びます）9体が連携して記事を制作する「編集部」ができていました。

- 記事の企画・調査を担うresearcher
- 原稿を書くwriter
- 事実確認を担うreviewer
- 読者視点でのレビューを担うreader
- スケジュール管理・GitHub Issue管理を担うsecretary
- スクリプト開発を担うskill-dev
- 開発基盤・環境整備を担うdevops
- コードと設計の調査・仕様策定を担うarchitect
- それらを束ねるCOO

私がやることは、COOに指示を出すだけ。COOが仕事を各エージェントに割り振り、成果物が返ってくる。

ある日、ブログ記事を書いてもらったのに続いて「技術書のたたき台を作って」と指示したところ、翌朝には全11章のドラフトが上がっていました。その原稿は後にボツになりましたが、本書はそこから生まれています。人間（私）が発言した回数は、合計約15回。「次」「はい」「１」が大半を占める一言返答でした。AIの出力は約2,000行です。

これは「ツールの使い方記事」ではありません。**どう組織を設計し、どうルールを作り、どう壊れたかを直していったか**という、実際の経過です。


## この本で持ち帰れること

本書の構成を簡単に案内しておきます。

**第1部「コードを書けないは不利ではない」** では、エンジニアリングスキルがなくても始められる理由と、必要な思考の切り替えを説明します。

**第2部「役割設計の考え方」** では、どんなエージェントを揃えるべきか、組織設計の基本を扱います。「最初から9体揃えなくていい」も、ここで説明します。

**第3部「最小構成で始める」** では、実際にゼロから動かすための手順と、使うツール・コストの現実を書いています。「無料で始められる」という話ではない点も、ここで正直に説明します。

**第4部「組織を育てる」** では、最小構成から徐々にエージェントを増やしていく過程と、そこで起きた失敗を記録しています。

**第5部「間違える・散らかる・それでも続ける」** では、AIは間違える・組織は散らかる・コストは積み上がる、という三つの現実を正直に記録しています。それでも続ける理由についても書いています。

**第6部「自分のチームを設計する」** では、業務の棚卸しから始まり、業務別の構成例と最初の30日プランを提示します。本を閉じた瞬間から動けることを目標にした実践ガイドです。

準備として必要なのは、Claude Codeを契約することだけです。コードを書く環境は不要で、むしろWindowsのメモ帳でも始められます。


## ブログ以外の仕事にも使える話です

本書の具体例はブログ記事制作が中心です。でも設計の考え方は、業種を問わず使えます。

PMなら「要件定義・レビュー・議事録」の担当を分ける設計に、経営者なら「調査・提案書・スケジュール管理」の分業に、事務職なら「定型文書の作成・確認・整理」の自動化に直接応用できます。第2部では法務・マーケティング・経営企画への置き換え例も扱います。「ブログの話だから自分には関係ない」とは、ひとまず判断しないでください。

## 一つだけ、最初に伝えたいこと

読み始める前に、一つだけ言わせてください。

**コードを書けないことは、もう不利ではありません。**

少なくともAIエージェントを動かす文脈においては、「自分が書けるかどうか」より「何を作るか」「誰に何をやらせるか」「品質をどう担保するか」の方がずっと重要です。

「SE26年だからできた」と思われたくなくて、この点は強調したいのですが——むしろ私が感じたのは逆です。「設計を考えるのは自分、コードを書くのはAI」という構造は、プログラムを書けるエンジニアの人にとっては慣れが必要な分離かもしれません。でも、最初からコードを書かない立場の人間には、違和感なく受け入れられる。

後から調べて知ったのですが、私がやっていたことには名前があります。AIに渡す情報を設計する技術を、「コンテキストエンジニアリング」と呼びます。「プロンプトをうまく書く」よりも、「何を・どの形で・いつ渡すか」をシステムとして設計することが本質だ——2025年に登場したこの概念は、エンジニアの間で急速に広まっています。コードを書かなくても、それは立派なエンジニアリングです。

「やれる人がいる」ではなく「今の私がそのままやれる」という感覚が、この10日間の一番の発見でした。

さあ、始めましょう。
