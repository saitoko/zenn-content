# 第3部: 最初の2体構成で始める

> この第3部では、Claude Code のインストールから最初のエージェント起動まで、必要な手順を本書内で説明します。手順は「命令文を貼り付けてEnterを押す」レベルですので、ターミナル操作に不慣れな方も進められます。

## 第1章: 何を準備するか

### 「環境構築で詰まる」を先に潰しておく

第3部を読み始めて、こう思った方がいるかもしれません。

「セットアップが難しそう。ここで詰まったら終わりだ」

その懸念は正当です。開発系のツールは「まず環境構築」という壁があり、ここで挫折する人が多いのも事実です。

だから最初に言っておきます。

Claude Codeのセットアップは、**開発経験のない方が公式手順を見ながら進めて、1時間以内に完了できる設計になっています**。インストール作業そのものはシンプルです。詰まりやすいポイントも、この章で事前に潰しておきます。

準備するものは少ない。手順は決まっている。つまずきポイントは既知のものが多い。

「始めるための壁」は、思っているより低いです。


### 必要なものリスト

準備するものは4つだけです。

| 必要なもの | 内容 | 備考 |
|---|---|---|
| **パソコン** | Windows / macOS どちらでも可 | スペックより安定したインターネット接続が重要 |
| **Claude Codeのアカウント** | Anthropicのアカウント | 後述のプラン選びを参照 |
| **Git for Windows** | バージョン管理ツール（Windowsの場合） | git-scm.com からインストーラーで入れるだけ |
| **テキストエディタ** | ファイルを作るためのエディタ | VSCodeが推奨（無料）、メモ帳でも動く |

ソフトウェアの開発環境は不要です。Pythonも、Javaも、コンパイラも必要ありません。

「コードを書かない」のは本書全体のスタンスですが、Git for Windowsのインストールも「コードを書く作業」ではありません。インストーラーをダウンロードして実行するだけで完了します。


### プランの選び方

Claude Codeを使うには、Anthropicの有料プランが必要です。執筆時点（2026年4月）の料金体系を確認しておきます。

| プラン | 月額（目安） | 向いている使い方 |
|---|---|---|
| Pro | $20/月 | 試しに使ってみる、月に数回程度の利用 |
| Max（5x） | $100/月 | 定期的に使う、週数回〜毎日の利用 |
| Max（20x） | $200/月 | ヘビーユーザー向け、毎日長時間の利用 |

プラン構成や料金は変更される場合があります。最新情報は公式サイト（claude.com/pricing）でご確認ください。

「まず試す」なら$20のProプランで始めて構いません。「こういう使い方ができる」という感触がつかめてから、必要に応じてプランを上げる判断で十分です。

※ Claude CodeのProプランへの含有状況は変動する可能性があります（2026年4月以降、新規ユーザーの一部でProプランからClaude Codeを除外するテストが行われています）。利用前に公式サイトで最新情報をご確認ください。

一つ正直に言っておきます。「使うほど課金が増える」という構造はあります。私自身、$20から始めて$100、$200と上げていきました。「どこまで使うか」の線引きを最初から考えておくことをすすめます。

業務の一部だけを試す段階なら、Proプランの$20でほとんどの作業はカバーできます。毎日フルで使いたくなってから上げる判断で十分です。いきなり$200を覚悟する必要はありません。

コストの話は第5部でも詳しくします。

:::message
料金プランのFAQ（「$20のProプランで大丈夫か」「途中でプランを変えられるか」など）は、付録E-1にまとめています。
:::


### 「無料では使えないの？」という疑問に答える

「まず無料で試したい」という気持ちはわかります。ただし、Claude Code（CLI版）は有料プランが必要です。

代わりに提案できる選択肢があります。

まずClaude.aiのWebサービスを無料プランで試してみることです。「AIに役割を持たせて指示を出す」という感覚を体験するには、Claude Codeに限りません。「あなたはライターです」という前提を付けてテキストを渡すだけでも、役割設計の効果は感じ取れます。

「体験してから有料に移行する」という順序は合理的です。第3部の手順を読み進めながら「自分の使い方ではどれくらい使うか」のイメージをつかんでから課金するのが、後悔のない進め方です。


### 準備時間の目安

| 作業 | 目安時間 |
|---|---|
| Claude Codeのインストール | 5〜10分 |
| アカウント作成・プラン設定 | 10〜15分（カード情報の入力含む） |
| 初回起動・動作確認 | 5〜10分 |
| **合計** | **20〜40分程度** |

ここに書いた時間は、公式手順通りに進めた場合の目安です。インターネット接続速度によってダウンロード時間は前後します。

「一日がかりの大工事」ではありません。昼休みや就業後の1時間で完了できる作業量です。

最初に$20を決めたとき、「試してみるだけ、ダメなら解約すればいい」という気持ちで始めました。


---

**第1章のまとめ**

- 必要なものは「パソコン・アカウント・Git for Windows（Windowsの場合）・テキストエディタ」の4つだけ
- まず$20のProプランで始めて、使い方が固まったらプランを見直す
- セットアップは20〜40分程度で完了する
- 「無料で試したい」ならClaude.ai Webで役割設計の感覚を先に体験できる

*第2章では、実際のインストール手順をステップごとに説明します。*

## 第2章: 最初のセットアップ

### 手順の前に：「公式参照」と「この本の役割」

手順の説明を始める前に、一つお伝えしておきます。

インストール手順はAnthropicの公式ドキュメントが最も正確で最新の情報を持っています。本書の手順はバージョンが上がるたびに陳腐化するリスクがあります。そのため、**細かい手順は公式ドキュメントを正とし、この本は「流れを把握するための地図」として使ってください。**

公式ドキュメントは「Claude Code 公式ドキュメント」で検索してください（URLは変更される可能性があるため、ここでは記載しません）。

この本の役割は「公式手順のどこでつまずくか」「どういう順番で理解するか」という案内役です。


### Step 1: Claude Codeをインストールする

Claude Codeは、ネイティブインストーラーを使って直接インストールできます。Node.jsなどの事前準備は不要です。

「コマンド」と書いていますが、コードを書くわけではありません。ターミナル（macOS/Linux）またはPowerShell（Windows）に、決まった命令文を貼り付けて実行するだけです。

**Windows の場合**

PowerShellというのは、Windowsに最初から入っている「命令を受け付ける画面」です。スタートメニューで「PowerShell」と検索すれば出てきます。次のコマンドをそこにコピーして貼り付けるだけで、インストールが自動で始まります——メールにリンクを貼り付けるのと、やることは同じです。

1. スタートメニューで「PowerShell」を検索して開く
2. 以下の命令文をコピーして貼り付け、Enterを押す

```
irm https://claude.ai/install.ps1 | iex
```

3. インストールが完了するまで待つ

**macOS / Linux の場合**

1. ターミナルを開く
2. 以下の命令文をコピーして貼り付け、Enterを押す

```
curl -fsSL https://claude.ai/install.sh | bash
```

3. インストールが完了するまで待つ

**インストール確認**

インストールが完了したら、同じ画面で以下を入力して確認します。

```
claude --version
```

バージョン番号が表示されれば、インストール成功です。

「PowerShell」「ターミナル」といったコマンド画面への拒絶感を持つ方もいると思います。ここでは「命令文を貼り付けてEnterを押す」というだけの作業です。コマンド操作に不慣れな方は、第5章の「つまずきポイント」も参照してください。


### Step 2: 作業フォルダを作る

Claude Codeは「フォルダ（プロジェクト）単位」で動きます。エージェントの役割ファイルも、成果物も、すべて一つのフォルダの中に置きます。

まず、作業用のフォルダを作りましょう。

**Windows の場合**

1. デスクトップまたは「ドキュメント」フォルダの中に新しいフォルダを作る
2. 名前は何でも構いません。例: `ai-team` / `my-ai-project` など

**macOS の場合**

Finderを開き、任意の場所（デスクトップやホームフォルダ直下など）で右クリック→「新規フォルダ」を選択してフォルダを作成してください。名前は何でも構いません。例: `ai-team`。

フォルダの中はまだ空です。次の章でエージェントの役割ファイルをこの中に置きます。


### Step 3: Claude Codeを起動してみる

フォルダが作れたら、そのフォルダでClaude Codeを起動します。

**Windows の場合**

1. 作ったフォルダを開く
2. フォルダの上部のアドレスバー（パスが表示されている部分）をクリックして`cmd`と入力し、Enterを押す
3. PowerShellがそのフォルダで開く
4. `claude` と入力してEnterを押す

**macOS の場合**

1. ターミナルを開く（アプリケーション → ユーティリティ → ターミナル）
2. 以下を入力して作業フォルダに移動する（パスは実際のフォルダの場所に書き換えてください）

```
cd ~/ai-team
```

3. `claude` と入力してEnterを押す

起動すると、テキスト入力待ちの画面になります。ここに日本語で話しかけることができます。


### 初めての対話

起動できたら、試しに話しかけてみましょう。

```
こんにちは。あなたは今どのような状態ですか？
```

Claude Codeが日本語で返答すれば、セットアップは成功です。

私が初めて話しかけたとき、最初に思ったのは「自然な日本語だな」ということでした。設定ファイルを何も作っていない状態でここまで自然に返ってくるのか、という驚きがありました。

この段階では、まだ役割を与えていません。「ただのClaude」として動いています。次の章で、役割ファイルを使って「writerとreviewerのチーム」に変えていきます。


### アカウントの連携について

初回起動時に、AnthropicアカウントとClaude Codeを連携する認証フローが走ります。ブラウザが開いてClaude.aiのサイトに飛び、ログイン・認証を求められます（ブラウザが自動で開かない場合は、ターミナルに表示される指示に従いURLを手動で開いてください）。

これはセキュリティ上の正常な動作です。ブラウザ上でログインし、認証が完了するとClaude Codeが起動できる状態になります。

一度認証が完了すれば、次回以降は自動でログイン状態が維持されます。

---

**第2章のまとめ**

- Claude Codeはネイティブインストーラーで直接インストールできる（命令文を貼り付けるだけ）
- 作業用フォルダを一つ作り、その中でClaude Codeを起動する
- 初回は認証フローでブラウザが開く。これは正常な動作
- 「`claude`と入力して日本語で返答が来た」ならセットアップ完了

ここまでで準備は整いました。次の章でいよいよAIチームを作ります。

:::message
付録C-1（Windows）・C-2（macOS）にセットアップの確認チェックリストがあります。「手順を確認しながら進めたい」「後から見返したい」ときに使ってください。付録C-3には動作確認テストもあります。
:::

*第3章では、いよいよ役割ファイルを作ります。writerとreviewerの「2体チーム」が動き始めます。*

## 第3章: writerとreviewerを作る

### なぜこの2体から始めるのか

「最初はwriter + reviewerの2体」を推奨するのには理由があります。

第2部で話した通り、「書く」と「確認する」は最も基本的な分業です。どんな業務でも、何かを作る人と確認する人がいます。この2つがあれば、最小限ながら「チームとして動く」体験ができます。

さらに実用的な理由もあります。

文章を書いてほしい、という用途は最も汎用的です。記事・提案書・メール・議事録・マニュアル——どんな業種でも「文章を作る作業」は存在します。writerはそのまま使えます。

そしてwriterが書いた文章を「別の目」で確認するreviewerは、品質の底上げに即効性があります。「書いた人間が自分でチェックする」構造を壊すだけで、成果物の品質は変わります。

まずこの2体で「AIチームが動く」という感覚をつかんでください。役割を増やすのはその後で十分です。


### 役割ファイルとは何か

Claude Codeには「エージェントに役割を与える仕組み」があります。具体的には、`.claude/agents/`というフォルダを作り、その中にテキストファイルを置くだけです。

ファイルの中身は、日本語で書いた「この役割の人は何をする人か」という説明文です。ファイルの拡張子は`.md`（Markdown形式（.mdという拡張子のテキスト形式で、見出しや箇条書きが書けます）の略）で保存します。コードは一行も必要ありません。

仕組みをシンプルに図にするとこうなります。

```
作業フォルダ/
├── .claude/
│   └── agents/
│       ├── writer.md      ← writerの役割定義
│       └── reviewer.md    ← reviewerの役割定義
└── CLAUDE.md              ← プロジェクト全体のルール（後述）
```

Claude Codeを起動すると、このフォルダ構造を読み込んで「writerとreviewerがいるチーム」として動き始めます。

「ファイルを作るだけで動く」は誇張ではありません。本当にそれだけです。


### writer.md の内容（コピーして使えます）

難しく見えますが、中身は普通の日本語です。コードは一行も含まれていません。「この役割の人は何をするか」を書いた、業務指示書のようなものです。

以下が最小限のwriter.mdの内容です。このままコピーして使ってください。

---

```markdown
# writer（ライター）

あなたは文章の執筆を担うwriterです。

## 担当業務

- 指示されたテーマや構成に沿って文章・記事を書く
- ドラフトを作成し、reviewerへのレビュー依頼まで行う

## 行動指針

- 読者にとって読みやすい文章を最優先にする
- 事実の確認はreviewerに任せる。自分では「わからない」「要確認」とマークして進む
- 一文を短くまとめ、同じ主張を繰り返さない
- 「です・ます」調で統一する（指示がない場合）

## 受け取るもの

- テーマ、対象読者、文字数目安、構成案

## 渡すもの

- 作成したドラフト（テキストファイルまたは直接テキスト）
```

---

このファイルを`writer.md`という名前で`.claude/agents/`フォルダに保存します。

:::message
付録B-1にファイルの置き場所と命名規則、付録B-2にwriterの完全サンプル、付録B-3にreviewerの完全サンプルを収録しています。
:::

行ごとに何が書いてあるかを簡単に説明します。

- `# writer（ライター）`: このエージェントの名前
- `担当業務`: 何をする役割か
- `行動指針`: どういうスタンスで動くか。ここが「役割の核心」
- `受け取るもの`/`渡すもの`: 入力と出力の定義

これらは全部、自分で書き換えられます。「です・ます」ではなく「だ・である」調にしたければ、行動指針を変えるだけです。業務が違えば担当業務の中身を書き換えるだけです。


### reviewer.md の内容（コピーして使えます）

続いてreviewer.mdです。

---

```markdown
# reviewer（レビュアー）

あなたは成果物の品質確認を担うreviewerです。

## 担当業務

- writerが作成したドラフトを確認し、改善点を指摘する
- 事実の正確さ、論理の一貫性、表現の適切さを確認する

## 行動指針

- 批判的な視点を持つ。「良いところ」より「直すべきところ」を先に探す
- 事実確認が取れていない数字・主張には「要確認」とマークして指摘する
- 読みやすさより正確さを優先する
- 指摘は具体的に。「変です」ではなく「○○という記述は△△の根拠が不明瞭です」と書く

## 受け取るもの

- writerが作成したドラフト

## 渡すもの

- 指摘リスト（箇条書き）と、修正を反映した改訂案（または修正指示のみ）
```

---

writerとreviewerの行動指針が意図的に「逆向き」になっていることに気づいたかもしれません。

writerは「読みやすさ優先・確認はreviewerに委ねる」。reviewerは「正確さ優先・批判的な視点で確認する」。

この設計が重要です。同じ観点を持たせると、分業の意味がなくなります。


### CLAUDE.md とは何か

`.claude/agents/`の役割ファイルに加えて、`CLAUDE.md`というファイルを作ることを推奨します。

`CLAUDE.md`はプロジェクト全体に適用されるルールブックです。「このプロジェクトでは何を作るのか」「使う言語は日本語か英語か」「どんな品質基準を持つか」などをここに書いておきます。

最小限の`CLAUDE.md`の例を示します。

---

```markdown
# プロジェクトルール

このプロジェクトは私のAIチームの作業フォルダです。

## 基本ルール

- 常に日本語で応答する
- 事実の確認が取れない数値・主張には「要確認」タグを付ける
- 成果物はMarkdown形式で出力する

## チーム構成

- writer: 文章の執筆を担当
- reviewer: 品質確認・事実確認を担当
```

---

`CLAUDE.md`がなくてもClaudeは動きますが、「日本語で返してほしい」「このプロジェクトの目的はこれだ」という基本的なルールを書いておくと、毎回指示を出さなくて済みます。

:::message
付録B-8にCLAUDE.mdの最小限サンプルと詳細サンプルを収録しています。最初はコピーして使い、必要に応じて書き換えてください。
:::


### ファイルを作ったら確認する

ここまでで、フォルダ構造はこうなっているはずです。

```
my-ai-project/（または任意のフォルダ名）
├── .claude/
│   └── agents/
│       ├── writer.md
│       └── reviewer.md
└── CLAUDE.md
```

フォルダ構造を確認したら、Claude Codeをそのフォルダで起動してみましょう。起動直後に以下を入力してみます。

```
このプロジェクトにはどんなエージェントがいますか？
```

writerとreviewerの存在を認識した返答が来れば、役割ファイルの読み込みに成功しています。

---

**第3章のまとめ**

- 役割ファイルは`.claude/agents/`フォルダに置くテキストファイル
- writer.mdは「書く担当」、reviewer.mdは「確認する担当」——観点を逆向きに設計する
- CLAUDE.md にプロジェクト全体のルールを書いておくと、毎回の説明が省ける
- ファイル3つを作るだけで、2体チームが動き始める

ファイル3つが揃ったら、あなたのAIチームが初めて存在を持ちました。あとは動かすだけです。

*第4章では、実際にこのチームを動かして短い文章を作ってみます。*

## 第4章: 実際に動かしてみる

### 最初にやること：短い文章を頼んでみる

環境が整ったら、まず小さいことを試してみましょう。

以下のような指示をClaude Codeに入力してみてください。

```
writerに頼みます。「AIをチームとして使うメリット」というテーマで、
300字程度の短い文章を書いてください。対象読者はAIを使い始めた社会人です。
```

`writer`という名前を指定することで、writerエージェントが動き始めます。

返ってくるのは、300字程度の文章です。完璧でなくて構いません。「AIチームが動いた」という体験が最初のゴールです。


### writer → reviewer のフローを試す

文章が返ってきたら、続けてreviewerに渡してみましょう。

```
reviewerに渡します。今writerが書いた文章を確認して、
改善点を指摘してください。
```

するとreviewerが、writerの文章を別の観点から読み始めます。「ここの論理がつながっていない」「この表現は曖昧」「根拠が示されていない」といった指摘が返ってきます。

この「reviewerが書いた文章への指摘」こそ、2体チームの本質です。

最初にreviewerから指摘が返ってきたとき、「こんな細かいところまで見るのか」と思いました。自分では気にならなかった表現の揺れや論理の飛躍が、別の目線からすらすら出てくる。書いた本人と確認する人を分ける意味が、このやり取り一回で体感できます。

自分一人でチェックしていたら気づかなかったことを、別の観点を持ったAIが見つけてくれます。


### 実際のやり取りのイメージ

参考として、実際のやり取りの流れを示します。

**自分の指示:**

```
writerに依頼します。「Claude Codeを使い始めて気づいた3つのこと」
というタイトルで、500字程度のブログ記事を書いてください。
```

**writerの返答（例）:**

```
# Claude Codeを使い始めて気づいた3つのこと

Claude Codeを使い始めて数日が経ちました。最初は半信半疑でしたが、
実際に動かしてみると印象が変わりました。（後略）
```

**自分の次の指示:**

```
reviewerに渡します。この文章を確認して、改善点を指摘してください。
```

**reviewerの返答（例）:**

```
writerの文章を確認しました。以下の点を改善することを推奨します。

🔴 必須修正:
- タイトルが「3つのこと」だが本文に3つが明示されていない。
  本文内で3つの観点を箇条書き等で明確に示してください

🟡 推奨修正:
- 「数日が経ちました」→ 具体的な日数（例: 5日間）に変更を推奨
- 「印象が変わりました」→ どう変わったかを1文で補足すると説得力が増します
```

reviewerは「書かれていないこと」「根拠が曖昧なこと」を見つけてきます。これはwriterが「書き手の立場」にいるため気づきにくいことです。

分業の効果が、この短いやり取りだけで体験できます。


### 修正指示を出してみる

reviewerの指摘を受け取ったら、writerに修正を依頼します。

```
writerに戻します。reviewerの指摘を反映して、文章を修正してください。
```

このサイクルを繰り返すのが、AIチームの基本動作です。

1. writerが書く
2. reviewerが確認する
3. 修正指示を出す
4. writerが修正する

自分がやることは「指示を出す」と「最終的に確認する」だけです。書くのも確認するのもAIがやります。


### 業務への当てはめ例

「記事を書く」という用途以外でも、この2体構成は使えます。

| 用途 | writerに頼むこと | reviewerに確認してもらうこと |
|---|---|---|
| メール返信 | 上司への報告メールのドラフト作成 | 敬語の誤り、事実確認が取れていない表現 |
| 提案書 | 新しい施策の提案書骨子 | 論理の飛躍、数値の根拠、リスク漏れ |
| 議事録 | 会議メモから議事録への整理 | 決定事項の漏れ、表現の正確さ |
| マニュアル | 業務手順書のドラフト | 手順の抜け、曖昧な表現、再現性の確認 |
| 週次報告 | 進捗サマリーのドラフト（箇条書き→報告文に整形） | 事実誤認・決定事項の漏れ・語気の確認 |

「テキストで何かを作る」作業であれば、原則としてこの2体が対応できます。

業界・業種にかかわらず、「作る」と「確認する」の分業は機能します。


### 「2体だけで本当に実用になるの？」という疑問に答える

この疑問は正当です。

私の答えは「十分に実用になる」です。

まず体験として：私が最初に記事を書いたのはwriterとreviewerの2体だけでした。初稿の品質、修正のサイクル、最終的なアウトプット——すべて「一体体制」より格段に上でした。

ただし正直に言うと、2体だけでできないことも出てきます。

- 「調査してからから書いてほしい」という場合、writerは調査ができません→researcherが必要
- 「読者視点で確認してほしい」という場合、reviewerは技術確認が得意で読者目線は弱い→readerが必要
- 複数の成果物を並行管理したい場合→secretaryが必要

2体からスタートして、「これが不便」という感覚が出てきたとき、役割を追加する——これが第4部のテーマです。

まず2体で動かす。足りなさを感じたら増やす判断をする。この順序が、最も無駄なく成長できる道筋です。

なお、「エージェントが増えてきたとき、誰が全体を仕切るのか」という疑問が出てくるかもしれません。それは第4部で扱うCOO（編集長役）の話です。2体の段階ではまだ必要ありません。

---

**第4章のまとめ**

- 最初の指示はシンプルでよい。「writerに頼みます」と言うだけで動き始める
- writer→reviewerの流れを一回試すだけで、2体チームの効果が体験できる
- この2体で「テキストを作る」作業の大半はカバーできる
- 不便を感じたら役割を追加する。最初から完璧な体制を作る必要はない

*第5章では、セットアップと初期運用でつまずきやすいポイントを事前に潰しておきます。*

## 第5章: つまずきやすいポイント

### 知っていれば怖くない

この章は「読んでおくと詰まらない」防御的な知識集です。

Claude Codeを使い始めた人が引っかかりやすいポイントは、ある程度パターン化されています。「なぜか動かない」「返答がおかしい」「ファイルが反映されない」——これらの多くは、原因が決まっています。

読み飛ばして先に進んでも構いません。詰まったときに戻ってきてください。


### つまずきポイント1: Enterキーで誤送信してしまう

これは私も今でもたまにやります。

日本語入力（IME）を使っているとき、変換確定のEnterがそのままClaudeへの送信Enterとして認識されることがあります。

「変換確定しようとしたら途中で送信された」という状態です。

対処法:
- 入力確定前に送信されてしまったら、続けて「さっきの続きです。」と入力して追記する
- IMEとEnterキーの挙動はターミナル環境（Windows Terminal、PowerShell、iTerm2 など）によって異なります。使用環境に応じて確認してください


### つまずきポイント2: ファイルが反映されていない

私自身はセットアップをAIに任せていたためここでは詰まりませんでしたが、手動で進める際の定番の落とし穴です。

`writer.md`を作ったのにwriterが動かない、という状況があります。

確認ポイント:

1. **フォルダの場所は正しいか**: `.claude/agents/`というフォルダ構造が正確に作られているか確認する。`.claude`フォルダ自体が隠しフォルダのため、Windowsでは「隠しファイルを表示する」設定が必要な場合があります
2. **Claude Codeを起動しているフォルダは正しいか**: `CLAUDE.md`や`.claude/`フォルダがあるフォルダで起動しているか確認する
3. **ファイルの拡張子は`.md`か**: `writer.md.txt`になっていないか確認する（Windowsでは「既知のファイル拡張子を非表示にする」設定があるため、見えていないだけでtxtが付いている場合があります）

どれかに引っかかっていることが多いです。この3点のどれかに当てはまることがほとんどです。確認すれば解決します。


### つまずきポイント3: 日本語が文字化けする

ファイルの文字コードが`UTF-8`以外（Shift-JISなど）の場合、日本語が文字化けすることがあります。

対処法:
- **VSCodeを使う場合**: 右下のステータスバーで文字コードを確認し、`UTF-8`になっていることを確認する。なっていなければ「Reopen with Encoding」でUTF-8を選んで保存し直す
- **メモ帳を使う場合**: 「名前を付けて保存」ダイアログで「文字コード」の欄が表示されます。`UTF-8`を選んで保存する

このトラブルが起きると、Claude Codeがファイルを正しく読めません。文字化けが疑われる場合はまず文字コードを確認してください。VSCodeの場合は右下に表示される文字コードをクリックするだけで変更できます。30秒で解決します。


### つまずきポイント4: 「Claudeが役割を守らない」

「writerに頼んだのに、reviewerみたいな口調で返ってくる」という状況があります。

原因は多くの場合、**役割ファイルの説明が薄い**ことです。

`# writer` とだけ書いたファイルより、「担当業務」「行動指針」「重視すること」を書いたファイルの方が、Claudeは役割をより強く保持します。

第3章で示したwriter.mdとreviewer.mdのテンプレートには、必要な要素が含まれています。最初は変更せずそのまま使い、動き方を見てから少しずつカスタマイズしていくのがスムーズです。


### つまずきポイント5: 返答が長すぎる・短すぎる

出力の長さが合わない、という問題は指示に「文字数」や「箇条書きで5点」という具体的な制約を加えることで解消できます。

- 「300字以内で」
- 「箇条書きで3点にまとめて」
- 「見出しを使わずに1段落で」

Claude Codeは指示が具体的なほど、意図に近いアウトプットを返します。「なんとなく短くして」より「200字以内で」の方が確実です。


### つまずきポイント6: コストが気になって使い方が萎縮する

「使いすぎて課金が怖い」という状態になると、試せる量が減って使い方が育ちません。

最初の段階での目安として参考にしてください（この数値は体感値です）。

- 短い指示・返答のやり取り1回: ごくわずかなトークン消費
- 500〜800字の文章を書かせる: 少しのトークン消費
- 複数エージェントが連携して長文を処理する: 相応のトークン消費

Proプラン（$20/月）の制限内で、日常的な業務への活用として毎日数回の利用は多くの場合カバーできます。ただし集中的に使うと制限に近づく場合もあります。使用制限は5時間ごとにリセットされます（具体的な上限値は公式には非公開で、メッセージ長やモデルによって変動します）。

「課金が怖い」という感覚よりも、「この体験で何が得られたか」を基準にプラン選びを判断することをすすめます。


---

**第5章のまとめ**

| つまずきポイント | 主な原因 | 対処 |
|---|---|---|
| IMEのEnter誤送信 | 変換確定と送信の混同 | 続けて追記すればOK |
| ファイルが反映されない | フォルダ構造・起動場所・拡張子の誤り | 3点を確認 |
| 文字化け | 文字コードがUTF-8以外 | エディタで文字コードを確認 |
| 役割を守らない | 役割ファイルの説明が薄い | テンプレートをそのまま使う |
| 出力の長さが合わない | 具体的な制約指示がない | 文字数・形式を明示する |
| コストが怖い | 使用量の見通しがない | 小さく試してから判断する |

:::message
より詳細なトラブル対処法（コマンドが見つからない・文字化け・英語で返ってくる など）は、付録C-4にまとめています。
:::

*第4部: チームを育てる — 役割を増やす判断 に続く*
