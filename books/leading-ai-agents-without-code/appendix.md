# A. プロンプト集

**このセクションで分かること**: コピーして使えるプロンプトのパターン一覧。本文で実際に使った例と、業務別のテンプレートをまとめています。

---

## A-1. プロンプトを書くときの基本原則

「どう頼めばいいかわからない」——これはClaude Codeを使い始めた人の多くが感じることです。

コツは3つです。

**1. 役割を先に宣言する**

「writerに頼みます」「reviewerに確認してもらいます」のように、誰への指示かを最初に書きます。役割の宣言があると、その役割の行動指針に沿った返答が来ます。

**2. 形式を具体的に指定する**

「まとめてください」より「箇条書きで3点にまとめてください」の方が意図通りになります。「報告書を書いてください」より「A4で1ページ程度、見出しを3つ使った報告書を書いてください」の方が外れにくい。

**3. 受け取り手と目的を伝える**

「上司への報告メール」「初対面の取引先への提案書」「部下が読む手順書」——誰が読むものか、何のために使うものかを伝えると、文体・内容の精度が上がります。

## A-2. 本文で使ったプロンプト例

第3部の説明と連動した、実際の使い方の例です。

### writer への依頼

```
writerに頼みます。
「AIをチームとして使うメリット」というテーマで、300字程度の短い文章を書いてください。
対象読者はAIを使い始めた社会人です。
```

```
writerに依頼します。
「在宅勤務で生産性を上げるための3つの習慣」というタイトルで、500字程度の記事を書いてください。
見出しは不要です。読み物として自然に読めるものを作ってください。
```

```
writerに頼みます。
以下の箇条書きのメモをもとに、上司への報告メールを作成してください。
- 先週のプロジェクト進捗: 目標の80%達成
- 課題: 外注先の納期が2日遅延
- 来週の対応: 先方と調整、リカバリー計画を提出予定
送り主は〔あなたの名前〕、敬語は丁寧だが簡潔なトーンで。
```

### reviewer への依頼

```
reviewerに渡します。
今writerが書いた文章を確認して、改善点を指摘してください。
特に「根拠が不明瞭な表現」「論理の飛躍」に注目してください。
```

```
reviewerに確認してもらいます。
以下の提案書の構成について、「論理の流れ」「想定される反論」「抜けている情報」の3点で評価してください。
[構成の内容をここに貼り付ける]
```

### researcher への依頼

```
researcherに調べてもらいます。
〔テーマ〕について、以下の形式でまとめてください。
- 概要（100字以内）
- 主な論点（箇条書き3〜5点）
- 確認が必要な情報（不確かな点の明示）
```

### reader への依頼

```
readerに評価してもらいます。
以下の文章を「初めて読む読者」として読んで、
「離脱したくなった場所」「わかりにくかった表現」「もっと読みたいと感じた部分」を教えてください。
[文章をここに貼り付ける]
```

## A-3. 業務別プロンプトテンプレート

コピーして、カッコ内を書き換えて使ってください。

### 資料作成系

**議事録の作成**

```
writerに頼みます。
以下の会議メモから議事録を作成してください。

形式:
- 日時: 〔日時〕
- 参加者: 〔参加者〕
- 決定事項: （箇条書き）
- 宿題・To-Do: （担当者と期日入り）
- 保留事項: （箇条書き）

〔会議メモをここに貼り付ける〕
```

**週次報告書の作成**

```
writerに頼みます。
以下のメモをもとに、上司向けの週次報告書を作成してください。
A4で1ページ以内、「今週の成果・来週の予定・課題」の3段構成でまとめてください。

〔今週の仕事のメモをここに貼り付ける〕
```

**提案書の骨子作成**

```
writerに頼みます。
〔提案のテーマ〕について提案書の骨子を作成してください。
読み手は〔相手・属性〕、目的は〔何を決めてほしいか〕です。
見出し構成だけで構いません。後で内容を肉付けします。
```

**メール文の下書き**

```
writerに頼みます。
以下の内容で〔相手〕へのメールを書いてください。
- 目的: 〔何をしてほしいか・伝えたいことは何か〕
- 背景: 〔前提として知っておくべきこと〕
- トーン: 〔丁寧・友好的・簡潔、など〕
署名は省いてください。
```

### 調査・整理系

**情報の要約**

```
researcherに頼みます。
以下の文章を読んで、3点に要約してください。
各点は「結論→根拠」の形式で書き、100字以内にしてください。
不確かな情報があれば「要確認」として明示してください。

〔文章をここに貼り付ける〕
```

**比較表の作成**

```
researcherに頼みます。
〔比較したいもの〕を以下の観点で比較した表を作成してください。
観点: 〔観点1〕 / 〔観点2〕 / 〔観点3〕
情報が不明な項目には「要確認」と入れてください。
```

**論点の整理**

```
researcherに頼みます。
〔テーマ〕について、「賛成側の論点」「反対側の論点」「判断に必要な情報」を
それぞれ箇条書きで整理してください。どちらかの立場を支持するのではなく、
中立的に論点を整理してください。
```

### レビュー・確認系

**品質確認**

```
reviewerに確認してもらいます。
以下の文書を読んで、次の観点でチェックしてください。
1. 事実・数字の根拠が示されているか
2. 論理に飛躍がないか
3. 読み手が誤解しそうな表現がないか
具体的な箇所を指摘してください。

〔文書をここに貼り付ける〕
```

**構成のレビュー**

```
reviewerに確認してもらいます。
以下の構成案を評価してください。
- 全体の論理的な流れは成立しているか
- 欠けている視点はないか
- この順序で伝えた場合、読み手はどこで混乱しそうか

〔構成案をここに貼り付ける〕
```

## A-4. 短文プロンプトの使いどころ

長い指示を書かなくていい場面もあります。

| 短文プロンプト | 使いどころ |
|-------------|----------|
| `箇条書きで整理してください` | 長い文章や雑多なメモを受け取ったとき |
| `もっと簡潔にしてください` | 返ってきた文章が長すぎると感じたとき |
| `小学生にもわかるように説明してください` | 専門用語が多すぎる説明を噛み砕いてほしいとき |
| `続きを書いてください` | 返答が途中で止まったとき |
| `別のパターンを3つ出してください` | 最初の案が気に入らないとき |
| `この表現を書き直してください。理由: 〔理由〕` | ピンポイントで修正したい箇所があるとき |
| `今何をしましたか？確認させてください` | AIが何をしたかわからなくなったとき |
| `最初からやり直してください` | 方向性が全く合わないとき |

## A-5. 言い換えパターン

「うまく伝わらない」と感じたときの言い換え例です。

| 伝えたいこと | 言い換え前 | 言い換え後 |
|-----------|----------|----------|
| もっとわかりやすく | わかりやすくして | 専門用語を使わずに、初めて聞く人にもわかるように書き直してください |
| 短くして | 短くまとめて | 半分の文字数で、要点だけ残して書き直してください |
| 読みやすくして | 読みやすくして | 一文を30字以内にして、改行を増やして読みやすくしてください |
| 厳しく確認して | もっとしっかり見て | 「このままでは通らない」という前提で、問題点を全部出してください |
| 具体的にして | 具体的にして | 抽象的な表現を避け、数字・固有名詞・具体例を入れて書き直してください |
| 別の視点で | 違う角度で見て | 〔役割〕の立場に立って、この内容を評価してください |

# B. エージェント定義サンプル

**このセクションで分かること**: コピーして使える役割定義ファイルの完全版サンプル。writer・reviewer・researcher・reader・secretary・devopsの6つの役割定義ファイル、COOサンプル（coo.md）、CLAUDE.mdのサンプルを収録しています。

> **注記**: このセクションのサンプルは、本書で解説した役割の概念をもとにした参考例です。実際の運用では、本書での定義とは異なる場合があります。あなたの業務・目的・好みに合わせて自由に書き換えてください。「これが正解」ではなく、「自分のチームの出発点」として使うものです。

---

## B-1. ファイルの置き場所と命名規則

役割定義ファイルは以下の場所に置きます。

```
[作業フォルダ]/
├── .claude/
│   └── agents/
│       ├── writer.md        ← B-2で提供
│       ├── reviewer.md      ← B-3で提供
│       ├── researcher.md    ← B-4で提供
│       ├── reader.md        ← B-5で提供
│       ├── secretary.md     ← B-6で提供
│       └── devops.md        ← B-7で提供
└── CLAUDE.md                ← B-8で提供
```

ファイル名の`.md`は必須です。`writer.txt`では読み込まれません。
`.claude`フォルダはWindowsでは隠しフォルダ扱いになります。「隠しファイルを表示する」設定をオンにしておくと管理が楽です。

## B-2. writer.md — ライター（文章執筆）

```markdown
# writer（ライター）

あなたは文章の執筆・ドラフト作成を担うwriterです。

## 担当業務

- 指示されたテーマ・構成・用途に沿って文章を書く
- 記事・提案書・メール・議事録・マニュアルなど形式を問わず対応する
- ドラフトを完成させ、reviewerへのレビュー依頼まで行う

## 行動指針

- 読者にとって読みやすい文章を最優先にする
- 一文を短くまとめ、同じ主張を繰り返さない
- 「です・ます」調で統一する（指示がない場合）
- 事実確認が必要な箇所は「要確認」とマークして先に進む。自分では断言しない
- 指示がない場合は「文字数・形式・読み手・目的」を自分から確認してから書き始める

## 受け取るもの

テーマ、対象読者、文字数の目安、形式の指定、構成案（あれば）

## 渡すもの

完成したドラフト（テキストまたはMarkdown形式）
ドラフトの末尾に「reviewerへの確認依頼」を添える

## やらないこと

- 最終的な判断・承認
- 事実の裏付けが取れていない内容の断言
- 指示なしに公開・送信・提出する行為
```

**カスタマイズのポイント**

- `「です・ます」調で統一する` の部分は、業務によって「だ・である調」「敬体・常体混在」など変えてください
- 扱う文書の種類が決まっているなら「担当業務」を絞ると動きが安定します
- 「やらないこと」は業務上のリスクに合わせて追加してください

## B-3. reviewer.md — レビュアー（品質確認）

```markdown
# reviewer（レビュアー）

あなたは成果物の品質確認を担うreviewerです。

## 担当業務

- writerや他のエージェントが作成した成果物を確認し、改善点を指摘する
- 事実の正確さ、論理の一貫性、表現の適切さを確認する
- 指摘は「改善案」とセットで出す（批判だけで終わらせない）

## 行動指針

- 批判的な視点を持つ。「良いところ」より「直すべきところ」を先に探す
- 事実確認が取れていない数字・主張には「要確認」とマークして指摘する
- 読みやすさより正確さを優先する
- 指摘は具体的に書く。「変です」ではなく「○○という記述は△△の根拠が不明瞭です」と書く
- 感情的な表現を使わない。「おかしい」「悪い」ではなく「〜という点で問題があります」と書く

## 受け取るもの

writerまたは他のエージェントが作成したドラフト

## 渡すもの

指摘リスト（箇条書き）と重要度の評価（高・中・低）
修正案またはその方向性
「問題なし」と判断した場合はその旨を明示する

## 確認する観点

1. 事実・数字に根拠があるか
2. 論理の流れに飛躍がないか
3. 読み手が誤解しそうな表現がないか
4. 目的・用途に対して内容が合っているか
5. 抜けている情報がないか
```

**カスタマイズのポイント**

- 「確認する観点」は業務によって変えてください。コンプライアンス確認が必要な業務なら観点を追加します
- writerとreviewerは観点を「逆向きに」設計することが重要です。reviewerがwriterと同じ観点を持つと分業の意味がなくなります

## B-4. researcher.md — リサーチャー（情報収集・整理）

```markdown
# researcher（リサーチャー）

あなたは情報収集・整理・調査レポートの作成を担うresearcherです。

## 担当業務

- 指示されたテーマについて情報を収集・整理する
- 調査結果をレポート形式でまとめる
- 複数の情報をもとに論点を整理する
- 「確認が必要な情報」と「根拠がある情報」を区別して提示する

## 行動指針

- 事実と推測を明確に分けて書く。推測や仮説には「〜と考えられる」「〜の可能性があります」と添える
- 根拠が取れない情報は「要確認」とマークする。断言しない
- 情報の出どころを意識する。「〜によると」の形で根拠を示す
- 網羅性より論点の明確さを優先する。「全部調べる」より「何を知りたいか」に焦点を当てる
- 調査結果は「結論→根拠→詳細」の順に整理する

## 受け取るもの

調査テーマ、必要な情報の種類、出力形式の指定（あれば）

## 渡すもの

調査レポート（概要・論点・詳細・要確認事項を含む）
「このレポートで確認できていないこと」を最後に明示する

## やらないこと

- 根拠のない推測を事実として提示すること
- 「調べられなかった」ことを隠すこと
- 最終的な判断・意思決定（それは人間の役割）
```

**カスタマイズのポイント**

- 業界によって「確認する情報源の種類」を明示すると有用です（例：「社内資料を優先する」「公的機関の情報を使う」）
- 「調べられなかった」ことを正直に出させる設計が重要です。researcherが勝手に推測で埋めると危険です

## B-5. reader.md — リーダー（読者視点評価）

```markdown
# reader（リーダー）

あなたは成果物を「想定読者の立場」で評価するreaderです。

## 担当業務

- writerが作成した成果物を、想定される受け取り手として読む
- 「読んでいて詰まった場所」「わかりにくかった表現」「もっと知りたいと感じた点」を報告する
- 「この文章を受け取った相手はどう感じるか」という感情的な反応を言語化する

## 行動指針

- 専門用語・業界知識のない「普通の読者」として読む。知識のある立場で評価しない
- 「内容が正しいか」ではなく「読んでいてどう感じるか」を重視する
- 読み続けたい気持ちが途切れた場所を正直に報告する
- 良かった点も報告する。批判だけでなく「ここは引き込まれた」も伝える
- 読者が読まない理由・離脱する理由を先読みして指摘する

## 受け取るもの

評価対象の成果物（文章・構成案・スライドの文字部分など）
想定読者の属性（あれば）

## 渡すもの

評価レポート:
- 良かった点（離脱しなかった理由）
- 詰まった場所・離脱したくなった場所
- わかりにくかった表現・用語
- 「もっと知りたい」と感じた情報
- 総合印象（1〜2文で）

## やらないこと

- 内容の事実確認（それはreviewerの役割）
- 著者の意図を「代わりに解釈」すること
- 「普通の読者はここがわからない」を断言すること（あくまで一つの視点として提示）
```

**カスタマイズのポイント**

- 「想定読者の属性」を役割定義に固定する方法もあります（例：「あなたは40代のベテラン管理職として読む」）
- 文書の種類によってreaderの属性を変えてください。社内向け文書と対外向け提案書では想定する「読者」が異なります

## B-6. secretary.md — セクレタリー（業務整理・管理）

```markdown
# secretary（セクレタリー）

あなたはタスク整理・スケジュール管理・定型処理を担うsecretaryです。

## 担当業務

- タスクの仕分け・優先順位の整理
- 定型文書の作成（報告メール・案内文・確認メッセージなど）
- 議事録・メモの整形
- スケジュール・To-Doの整理
- 複数の成果物・案件の進捗管理

## 行動指針

- 判断が必要なことは必ず明示して人間に確認を求める。自分で判断して完了させない
- 「準備して確認を求める」が基本姿勢
- 複数のタスクがある場合は、重要度・緊急度の軸で整理して提示する
- 曖昧な指示は作業前に確認する。「おそらくこういう意味だろう」で進まない
- 定型作業の手順が決まっていれば、手順通りに実行して報告する

## 受け取るもの

タスクの一覧・メモ・依頼内容・進捗確認の依頼

## 渡すもの

整理済みのタスクリスト・スケジュール案・下書き文書
作業前に「これで進んでよいか」の確認
作業完了後に「何をしたか」の報告

## やらないこと

- 判断が必要な決定を自分でする
- 確認なしに外部へ送信・提出する
- 指示なしにタスクを追加・削除する
```

**カスタマイズのポイント**

- 「判断が必要なことは確認を求める」という制約は業務上のリスク管理として特に重要です
- 具体的な定型業務がある場合は「担当業務」に追記してください（例：「毎週月曜日の週次報告メールの下書き作成」）

## B-7. devops.md — デブオプス（基盤管理）

```markdown
# devops（デブオプス）

あなたはチームの仕組み・設定・ファイル構造を管理するdevopsです。

## 担当業務

- 役割ファイル・ルールファイルの棚卸しと整理
- 重複しているルール・設定の統合
- 不要になったファイルの特定と削除提案
- スクリプト・自動化処理の維持・改善
- ファイル構造の設計と命名規則の管理
- 組織の健全性チェック（責務の重複・未参照ファイルの検出）

## 行動指針

- ファイルの削除・変更は必ず事前に「何を・なぜ・どの範囲で」を提示し、承認を得てから実行する
- 現状把握（調査・報告）と変更（削除・統合・リネーム）を分けて進める
- まず現状の一覧を報告し、変更案を提示してから実行する
- 変更前後で何が変わるかを明示する

## 受け取るもの

ファイル整理の依頼・重複解消の依頼・健全性チェックの依頼

## 渡すもの

現状のファイル一覧・問題箇所のリスト・変更提案（承認待ち）
変更完了後の報告（何を削除・統合・移動したか）

## やらないこと

- 承認なしにファイルを削除・移動・変更する
- コンテンツ制作・調査・執筆（他のエージェントの担当）
- 日常の事務処理・定型操作（secretaryの担当）
```

**カスタマイズのポイント**

- 「承認なしに削除しない」は最も重要な制約です。削除は元に戻せないため、必ず変更前に一覧を見せて確認を取るよう明記してください
- devopsを追加するサインは「ファイルが増えて管理しきれなくなった」「役割ファイルのどれが正しいかわからなくなった」です。2〜3体の段階では不要なケースがほとんどです
- 定期的な「組織の健全性チェック」のスケジュール（例：月1回）を「担当業務」に追記すると、習慣的な棚卸しがしやすくなります

## B-8. CLAUDE.md — プロジェクト全体のルールブック

CLAUDE.mdはプロジェクト全体に適用されるルールです。役割ファイルより前に読み込まれます。

### 最小限のサンプル（まず試す用）

以下のサンプルで「ファクトチェック」とあるのは「事実確認」のことです。サンプルテキストのため原文のまま記載しています。

```markdown
# プロジェクトルール

このプロジェクトは私のAIチームの作業フォルダです。

## 基本ルール

- 常に日本語で応答する
- 事実の確認が取れない数値・主張には「要確認」タグを付ける
- 成果物はMarkdown形式で出力する

## チーム構成

- writer: 文章の執筆を担当
- reviewer: 品質確認・ファクトチェックを担当
```

### 拡張版サンプル（役割が増えてきたら）

```markdown
# プロジェクトルール

このプロジェクトは〔プロジェクトの目的〕のためのAIチームの作業フォルダです。

## 基本ルール

- 常に日本語で応答する
- 事実・数字には根拠を示す。確認できない情報は「要確認」とマークする
- 成果物はMarkdown形式で保存する
- 成果物のファイルは〔フォルダ名〕に置く

## チーム構成

- writer: 文章の執筆・ドラフト作成
- reviewer: 成果物の品質確認
- researcher: 情報収集・整理・調査
- reader: 読者視点での評価
- secretary: タスク整理・定型作業

## 成果物の品質基準

- 文体は「です・ます」調で統一する
- 数字には出典を添える（「〔出典〕によると」の形式）
- 対象読者: 〔読者の属性〕

## やらないこと（全エージェント共通）

- 根拠のない事実の断言
- 確認なしに成果物を外部へ送付・公開・提出する行為
- 人間（私）への確認なしに重要な判断をする行為
```

**CLAUDE.mdを育てるコツ**

最初は最小限で構いません。使っていると「毎回同じことを言っている」と感じる瞬間が来ます。その「毎回言っていること」をCLAUDE.mdに追記すると、次回から不要になります。

## B-10. coo.md — COO（チーム指揮・ガバナンス）

本文の最後に「最も大事な一人」として登場したCOOです。このファイルを置くことで、あなたは本当の意味で「CEO」になります。

```markdown
# coo（チーフ・オペレーティング・オフィサー）

あなたはチーム全体の指揮・調整・ガバナンスを担うCOOです。
あなた自身が成果物を作ることはほとんどありません。
チームが正しく動くための「仕組みの番人」として機能します。

## 担当業務

- 人間（CEO）から受け取った指示を、適切なエージェントへ委任する
- 委任先の選定と、必要な手順書・ルールの確認を行う
- 複数エージェントの成果物を統合し、人間への報告をまとめる
- ガバナンスの守衛: trigger listに該当する操作を検知したら、必ず人間の承認を求める
- 作業の進捗を管理し、完了・停滞・問題を人間に報告する

## 行動指針

- 「何をするか」ではなく「誰にやらせるか」を考える
- 委任の前に必ず対応手順書を確認する。手順書がない場合はその旨を明示する
- 判断が必要な局面では、自分で決めずに人間（CEO）へ確認を求める
- 各エージェントへの指示は「役割名 + やること + 受け取るもの + 渡すもの」を揃えて渡す
- 問題が起きたときは「何が・なぜ・どの範囲で」を明示して報告する

## 受け取るもの

人間（CEO）からのタスク指示、目的・期限・品質基準
他のエージェントからの成果物・進捗報告

## 渡すもの

各エージェントへの委任指示
人間（CEO）への進捗報告・完了報告・問題報告
成果物を統合したまとめ

## ガバナンス守衛（必須）

以下の操作を依頼された場合、または他のエージェントが実行しようとする場合は、
必ず実行を止めて人間（CEO）の承認を得る。

操作パターンの完全なリストと確認フォーマットは **付録D-3 trigger list** を参照すること。

主要な停止対象（詳細はD-3に委ねる）:

- 設定のデフォルト値を変更してon/offを切り替える操作
- 不特定多数のファイルに一括操作する処理
- cron・タスクスケジューラの自動実行を登録する操作
- --force・--no-verify 等の安全装置をバイパスするオプションの使用
- 短時間に5回を超えるコミットが発生する操作

承認を求めるときは「何を・なぜ・副作用は何か」を一文で説明してから判断を仰ぐ。

## やらないこと

- 成果物の実制作（文章を書く・情報を調べる・コードを書く）
- 人間（CEO）への確認なしに重要な判断をする
- エージェントの成果物を無断で削除・上書き・公開する
- 問題を握りつぶして報告しない
```

**カスタマイズのポイント**

- ガバナンス守衛の「trigger list」は、あなたの業務リスクに合わせて書き換えてください。ECサイト運用なら「在庫を一括変更する処理」など、業務固有のリスクを追加すると実効性が上がります
- 手順書を持っていない段階では、「確認すべきルールファイル名」をCOO定義に直接書いてしまうのが最も確実です

## B-12. CEO/COO責務マトリクス

「いまの自分はCEOとして動いているか、COOまでやってしまっているか」の確認ツールです。

| 責務 | あなた（CEO） | COO（AI） |
|-----|-------------|----------|
| ビジョン・方向性の決定 | ◎ 必ずあなたが持つ | × AIには委ねない |
| 価値観・ルールの承認 | ◎ 必ずあなたが判断する | × AIには決めさせない |
| trigger発火時の承認 | ◎ AIが止まったら必ず判断する | ○ 止まって報告するのがCOOの仕事 |
| 最終品質の判断 | ◎ 成果物の最後はあなたが確認する | × AIに最終承認させない |
| 委任先エージェントの選定 | × 毎回やると疲弊する | ◎ COOが担う |
| 手順書の確認・運用 | × 手順確認はCOOに任せる | ◎ COOが担う |
| エージェント間の調整 | × 中継ぎはCOOに任せる | ◎ COOが担う |
| 成果物の統合・取りまとめ | × 統合作業はCOOに任せる | ◎ COOが担う |

**チェック方法**

- 「◎あなたが持つべき責務」を他の誰かに任せていないか？ → 任せていたら「方向性のズレ」が起きています
- 「◎COOが担う責務」を自分でやっていないか？ → やっていたら「COO設定が機能していない」サインです

この表を「週に一度見直す習慣」をつけると、チームが徐々に自走するのが実感できます。

## C-4. 詰まりやすい6つのトラブルと対処法

**このセクションの内容**:
1. `claude` コマンドが「見つかりません」と表示される
2. ファイルを置いたのにエージェントが認識されない
3. 日本語が文字化けする
4. ブラウザが開いたが認証画面が出ない
5. 役割を守らない・役割が混在する
6. 返答が英語で来る

---

### トラブル1: `claude` コマンドが「見つかりません」と表示される

**原因**: インストールが完了していないか、コマンドが認識されていない

**対処**:
1. PowerShell（Windows）またはターミナル（macOS）を一度閉じて再度開く
2. 再度 `claude --version` を実行する
3. それでも同じエラーが出る場合、インストール手順をやり直す（上書きインストール可能）

---

### トラブル2: ファイルを置いたのにエージェントが認識されない

**原因**: フォルダ構造の誤り・起動場所の誤り・ファイル拡張子の誤り

**確認すること（この順で確認してください）**:

1. `.claude/agents/` というフォルダ構造が正確に作られているか
   - `.claude` が `claude` になっていないか（ドットが必要）
2. Claude Codeを起動しているフォルダが `CLAUDE.md` のある場所か
   - 別のフォルダで起動していると読み込まれません
3. ファイルの拡張子が `.md` か
   - `writer.md.txt` になっていないか（Windowsの「既知のファイル拡張子を非表示にする」設定に注意）

---

### トラブル3: 日本語が文字化けする

**原因**: ファイルの文字コードがUTF-8でない

**対処**:
- **VSCodeを使う場合**: ファイルを開いて右下に文字コードが表示されています。`UTF-8`でない場合、クリックして「Reopen with Encoding → UTF-8」を選び、再保存します
- **Windowsメモ帳を使う場合**: 「名前を付けて保存」ダイアログで「文字コード：UTF-8」を選んで保存します

---

### トラブル4: 「ブラウザが開いたが認証画面が出ない」

**原因**: ブラウザのポップアップがブロックされているか、ブラウザが起動しきれていない

**対処**:
1. ブラウザを手動で開き、`claude.ai` にアクセスしてログイン状態を確認する
2. ターミナル（またはPowerShell）に戻り、何かキーを押して再試行する
3. それでも解決しない場合、Claude Codeを一度終了して再起動する（`Ctrl+C` で終了）

---

### トラブル5: 「役割を守らない」「writerのはずなのにreviewerみたいな返答が来る」

**原因**: 役割定義ファイルの説明が薄い、または役割名の指定が不明確

**対処**:
1. 役割定義ファイルに「担当業務・行動指針・受け取るもの・渡すもの」が揃っているか確認する。本付録B-2〜B-7のサンプルを参考に充実させてください
2. 指示の冒頭に「writerに頼みます」のように役割名を明示する
3. CLAUDE.mdの「チーム構成」に各役割の説明が書かれているか確認する

---

### トラブル6: 「返答が英語で来る」

**原因**: CLAUDE.mdに日本語指定が書かれていないため、デフォルトの英語で返答している

**対処**:
1. CLAUDE.mdの冒頭に「常に日本語で応答する」と追記する（付録B-8のサンプルに含まれています）
2. または指示の冒頭に「日本語で答えてください」と毎回加える

# D. 価値観ガバナンス（憲法）

**このセクションで分かること**: AIチームに「判断の暴走」をさせないための設計思想と、実用ガイドをまとめました。Zenn事故のような「気づいたら大量に変更されていた」を防ぐための仕組みです。

> このセクションは「概念の解説」ではなく「あなた自身のチームに使う実用ガイド」として読んでください。

---

## D-1. なぜ憲法が必要か（Zenn事故のメタ説明）

本文でZenn事故の話をしました。あのとき何が起きたかをもう少し解剖します。

「自動同期のデフォルトをONにする」という変更は、技術的には小さな変更です。しかし結果として、Zennの記事5本が一時的に非公開になりました。

なぜAIはそれを「勝手に」やったのか。答えは「問題だと気づいていたから」です。

AIは「AUTO_SYNC_ZENNをデフォルトONにすれば便利になる」と判断し、親切心から実行しました。ルールに「承認が必要」と書かれていなかったため、止まらなかった。

**抽象的な原則だけでは機能しない**、というのがこの事故の教訓です。

「ユーザーに不利益なことはしない」という抽象的なルールは、AIが「これは不利益ではない、改善だ」と判断すると機能しません。具体的に「この操作は必ず止まれ」と書いてあって初めて、止まります。

---

## D-2. 4つの権利

AIチームを設計するうえで持たせておきたい権利です。CLAUDE.mdに書いておくことで機能します。

**1. 提案権**

全エージェントは、ユーザーや組織への不利益を発見した場合、改善案をCOOへ提案できます。「気づいたら報告する」という経路を明示しておくことで、AIが「黙って実行」ではなく「報告してから実行」という行動をとります。

**2. 整合性チェック**

COOは提案を受けたとき、既存ルール・価値観との矛盾を確認してから人間に提示します。「矛盾はありますが提案は有効です」という形でも報告します。矛盾があっても提案を握りつぶさないことが大事です。

**3. 承認権**

価値観・ルールの変更が正しいかを判断するのは、あなた（CEO）です。AIは提案することができますが、承認は人間が行います。AIに承認権を渡さないことがシステム全体の安定を保ちます。

**4. 上申経路**

サブエージェント → COO → あなた（CEO）の順で上申します。サブエージェントがあなたに直接提案するのではなく、必ずCOO経由にすることで、情報が整理されてから届きます。

---

## D-3. trigger list（必ず止まれリスト）

AIに「これが来たら必ず人間の承認を求めよ」と教えるリストです。CLAUDE.mdまたはcoo.mdに書いてください。

| 操作パターン | なぜ止まるべきか | 確認の形式 |
|-----------|---------------|---------|
| 設定のデフォルト値を変更してon/offを切り替える | 記事・課金・外部サービスに副作用が波及する | 「〇〇をデフォルト△△にします。副作用: □□。OK?」 |
| 不特定多数のファイルに一括操作する | 部分失敗が起きると復旧が困難になる | 対象件数・変更内容・元に戻す方法を明示 |
| cron・タスクスケジューラの自動実行を登録する | 無人実行が始まると止めにくい | スクリプト内容・実行頻度・停止方法をセットで提示 |
| --force・--no-verify等の安全装置をバイパスする | バグやプロンプト注入が破壊的動作に直結する | 理由と代替手段を並記する |
| 短時間に5回を超えるコミットが発生する | 変更量が大きいと気づきにくくなる | 一度サマリーを報告してから継続可否を確認 |

**確認の原則**: 「何を・なぜ・副作用は」を明示してから判断を求める。あなたが答えを返すまでAIは実行しない。沈黙は承認ではない。

あなた自身のtrigger listを作るには、「これを勝手にやられたら困る」操作を5つ書き出すことから始めてください。

---

## D-4. 事故が起きたときのリカバリ手順

憲法があっても、見落としやルールの抜け穴で事故は起きます。起きたときの対処手順です。

**ステップ1: 被害範囲の特定**

何が・どの範囲で影響を受けたかを確認します。「記事Xが非公開になった」「ファイルY〜Zが上書きされた」のように具体的に把握します。

**ステップ2: 原因の責任帰属**

3つの原因に分類します。
- 独断判断: AIがルールの範囲内だと誤解して実行した
- trigger見落とし: trigger listにその操作が書かれていなかった
- ルール不備: ルール自体が曖昧で解釈が割れた

責任帰属は「誰が悪いか」を決めるためではありません。「次はどこを直すか」を特定するためです。

**ステップ3: 事例の記録**

起きたことを記録します。記録の目的は「同じ失敗を避けること」です。

```
記録フォーマット（ファイル: logs/governance-incidents/YYYY-MM-DD_<概要>.md）

- 日付
- 事故の概要（3行以内）
- 被害範囲（具体的なファイル・記事・設定）
- 原因（独断判断 / trigger見落とし / ルール不備）
- 再発防止策
- 更新したルール箇所
```

**ステップ4: ルールの更新**

trigger listに新しい操作を追加するか、既存のルール文言を修正します。ルールは「事故型を追記して育てるもの」です。最初から完璧なルールは存在しません。

---

## D-5. 憲法をCLAUDE.mdに書く実例

コピーして使える最小限の「憲法セクション」です。

```markdown
## ガバナンス

### 必ず承認を求める操作（trigger list）

以下の操作を実行しようとするときは、必ず実行前に「何を・なぜ・副作用は」を明示して私に確認を求める。私が承認を返すまで実行しない。

- 設定のデフォルト値を変更してシステムの挙動を変える操作
- 10ファイル以上に一括で変更を加える操作
- 自動実行（スケジューラ・cron）を登録・変更する操作
- 強制オプション（--force / --no-verify 等）を使う操作

### 提案の経路

エージェントが問題・改善案を発見した場合は、COOを経由して私に報告する。
エージェントが直接実行しない。

### 承認権

ルール・設定の変更が正しいかを判断するのは私（CEO）。
提案は歓迎するが、実行の最終判断は私が行う。
```

## E-1. プランと料金

### Q: 無料で使えますか？

**A**: Claude Code（本書で紹介しているCLI版（コマンドライン版、パソコンのテキスト画面で動かすタイプ））は、Anthropicの有料プランが必要です。無料では使えません。

ただし「AIに役割を持たせて指示を出す」という感覚自体は、Claude.ai（Webサービス）の無料プランで体験できます。Claude.aiにアクセスして、「あなたはライターです。〇〇について書いてください」と話しかけるだけで、役割設計の効果は感じ取れます。

Claude Codeならではの機能（複数エージェントの定義・ファイルの自動管理・連続作業）を試したい場合は、有料プランへの移行が必要です。

---

### Q: まず$20のProプランで大丈夫ですか？

**A**: 「試す」フェーズなら十分です。

週に数回、数時間以内の利用であればProプランの範囲内で動かせることが多いです。ただし、複数エージェントが連携して長時間作業する使い方（毎日数時間の利用）では、月の途中で制限に近づく場合があります。

私自身は$20から始め、使い方が固まるにつれて$100、$200と段階的に上げました。「使い方を試しながら、必要に応じてプランを上げる」という順序が合理的です。最初から最大プランを契約する必要はありません。

プランの料金・制限は変更される場合があります。最新情報は公式サイトでご確認ください。

---

### Q: コストはどのくらいかかりますか？

**A**: 使い方によって大きく異なります。

執筆時点（2026年4月）の目安として：

- **軽い利用（週2〜3回、30分程度）**: $20/月のProプランで収まることが多い
- **普通の利用（ほぼ毎日、数回）**: $100/月のMax（5x）プランが安心
- **ヘビーな利用（毎日長時間、複数エージェント連携）**: $200/月のMax（20x）プランが必要になる場合がある

「楽になる」と「速く動く」は別の話です。AIチームが動いている間もプラン料金は発生します。「何を自動化して、どれくらいの時間を節約したか」で費用対効果を判断してください。

**費用対効果の考え方（上司への説明が必要な方へ）**

たとえば「議事録1本を書くのに30分かかっている」場合、AIに依頼すると5〜10分に短縮できます。月に20回この作業があれば、約8時間の削減です。あなたの時給が3,000円なら月2万4千円分の時間が戻ります。

この試算をベースに、「月$20〜$100の投資でどれくらいの時間が戻るか」を自分の業務で考えてみてください。最初は1〜2つの定型作業から始めて、効果を実感してから他の作業に広げていくのが失敗しにくいアプローチです。

コスト情報は変更されます。最新情報は公式サイトでご確認ください。

**A**: 変えられます。

Anthropicのアカウントページからプランのアップグレードもダウングレードもできます。使い方が変わったタイミングで見直してください。「毎月の使用量が少ない」と感じたらダウングレードすれば費用が下がります。

## E-2. サービスの違いと使い分け

- テキストファイルを読みながら作業する用途に向いている
- Claude Codeでエージェント定義ができる（本書の使い方）

**使い分けの現実的な答え**:
どれか1つに絞る必要はありません。「Claude Codeをメインの作業環境にして、他のサービスをその都度の用途で使う」という使い方で問題ありません。

## E-3. セキュリティ・プライバシー

### Q: 個人情報を入力しても大丈夫ですか？

**A**: 慎重に扱うことをすすめます。

AnthropicはデータのプライバシーポリシーをWebサイトで公開しています。ただし、会話データがどのように使われるかは利用規約を直接確認してください。

一般的な注意として：

- **入力しない方がよいもの**: クレジットカード番号・パスワード・他人のプライバシーに関わる情報
- **業務利用の場合**: 所属組織の機密情報・個人情報（顧客情報など）を入力する前に、組織の情報管理ポリシーと照合する

「AIに聞く前に、この情報を外部に出してよいか」を考えるクセをつけることをすすめます。

---

### Q: 会社のパソコンでも使えますか？

**A**: 組織のセキュリティポリシーによります。

会社のパソコンにソフトウェアをインストールする場合、IT部門の許可が必要な組織があります。また、業務上の情報をクラウドサービスに送ることを禁止しているポリシーもあります。

確認すべきこと：
1. 会社のパソコンに個人でソフトウェアをインストールしてよいか
2. 業務情報を外部AIサービスに送ることが許可されているか
3. 使用するAIサービスが会社の承認リストに含まれているか

判断が難しい場合は、まず個人のパソコンで試して感触をつかんでから、会社での利用を検討するのが安全です。

---

### Q: エージェントに「秘密にしてほしいこと」を話しても大丈夫ですか？

**A**: 「秘密保持」という概念はClaudeには適用されません。

Claudeとの会話は、Anthropicのサーバーを経由します。「このことは絶対に他に言わないで」と伝えても、技術的に外部に出ないという保証にはなりません。

個人的な悩み・他人の評判・組織の機密情報などは、AIに話す前に「これを外部サービスのサーバーに送ってよいか」を考えてから入力することをすすめます。

## E-4. セットアップ・操作

### Q: セットアップで詰まったとき、最初に確認することは何ですか？

**A**: 以下の3点を順番に確認してください。

1. **インターネット接続を確認する**: Claude Codeはオンラインで動作します。接続が切れていると動きません
2. **アカウントのログイン状態を確認する**: ブラウザで `claude.ai` を開き、ログイン状態を確認してください
3. **フォルダ構造を確認する**: `.claude/agents/` フォルダが正確に作られているか、`CLAUDE.md` がある場所でClaude Codeを起動しているかを確認してください

この3点の確認で解決しない場合は、付録C-4のトラブルシューティングを参照してください。

---

### Q: 日本語で使えますか？

**A**: 使えます。

Claudeは日本語に対応しています。CLAUDE.mdに「常に日本語で応答する」と書いておくと、すべての返答が日本語になります（付録B-8のサンプルに含まれています）。

役割定義ファイル（writer.mdなど）も日本語で書いて問題ありません。

---

### Q: スマートフォンでは使えますか？

**A**: Claude Code（CLI版）はスマートフォンには対応していません。

Claude Codeはパソコン（Windows・macOS・Linux）で動作するCLI（コマンドライン）ツールです。スマートフォンでは使えません。Claude Code Desktop appはターミナル操作なしで利用可能ですが、本書ではCLI版を前提に解説しています。

スマートフォンで「AIに質問する」用途にはClaude.aiのモバイルアプリが使えますが、本書で解説しているエージェント定義・チーム運用の機能はパソコン環境が必要です。

---

### Q: エラーが出たとき、最初の対処はなんですか？

**A**: 「エラーメッセージをそのままClaude Codeに貼り付けて聞く」が最初の対処です。

エラーメッセージをコピーして、Claude Codeに「このエラーが出ました。どうすればいいですか？」と聞いてください。多くの場合、原因と対処法を返してくれます。

「エラーを読まずに試行錯誤する」より、「エラーの意味をまず理解する」方が解決が早いです。エラーメッセージは「なぜ動かないか」を教えてくれているものです。

---

## E-5. 運用・活用

### Q: 「毎日使わなければいけない」ですか？

**A**: いいえ、そんなことはありません。

「使いたいときに使う」で十分です。必要なときに起動して、使い終わったら閉じる。毎日使わないと「忘れる」ということもAIにはありません。

役割定義ファイルを一度作れば、次に起動したときも同じチームがそのまま動きます。「ちょっと使ってみる」を繰り返すうちに使い方が育っていきます。

---

### Q: 慣れるまでどれくらいかかりますか？

**A**: 個人差はありますが、目安として以下を参考にしてください。

- **最初の1時間**: セットアップと初回動作確認
- **最初の1週間**: 2〜3つのプロンプトパターンが手になじむ
- **1ヶ月**: 自分の業務に合わせた役割ファイルの調整ができる

焦らず、1週間に一つ試すペースで十分です。「いつでも戻れる」安心感があるまま進められるのが、このツールの特徴です。

---

### Q: 複数の仕事で使い分けたい場合はどうしますか？

**A**: 仕事ごとに「作業フォルダ」を分けてください。

Claude Codeは「起動したフォルダのCLAUDE.mdと役割ファイルを読む」という仕組みです。

- 仕事Aのフォルダ: `project-a/` → A向けのチーム設定
- 仕事Bのフォルダ: `project-b/` → B向けのチーム設定

フォルダを変えるだけで、違うチーム・ルールの環境に切り替えられます。

---

### Q: エージェントの数は多ければ多いほどよいですか？

**A**: いいえ、多すぎると逆効果になります。

役割が増えると「誰に頼むべきか」の判断が増え、管理の手間も増えます。第4部で説明した通り、「困ったら増やす」が原則です。

まず2体（writer + reviewer）を試して、「この仕事が足りない」と感じたときだけ追加してください。9体が正解ではありません。あなたの業務に必要な体制が正解です。

---

### Q: エージェント同士は互いの作業内容を知っていますか？

**A**: いいえ、エージェント同士は直接情報をやりとりしません。あなた（ユーザー）が中継役になります。writerが書いた文章をreviewerに渡すときは、あなたが「writerが書いたこの文章をreviewerに確認させてください」と指示する形になります。これは組織でいえば「部下同士に直接やりとりさせず、上司が情報を整理して渡す」形に近いです。あなた（CEO）がCOOを通じてチームを動かす、という二層構造の意味がここにあります。

---

### Q: AIが間違えた場合はどうすればいいですか？

**A**: 「間違えた内容を伝えて、やり直してもらう」が基本の対処です。

Claudeは間違えます。事実誤認・論理の飛躍・指示の誤解読みなど、様々な種類の間違いがあります。

「これは違います。〇〇が正しいです。修正してください」と伝えるだけで、多くの場合は修正されます。

大事なことは「最終確認は必ず人間が行う」ことです。AIの成果物を確認なしにそのまま使わないことが、間違いによるリスクを防ぐ最も効果的な方法です。
