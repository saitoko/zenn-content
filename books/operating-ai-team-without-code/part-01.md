# 第1部 チームが動く組織設計

序章で、私の手がチームと「相談する」ようになり始めた朝の話を書いた。architect との対話で見えてきたのは、「COO は実装の入口ではなく、対話の相手だ」という役割の境界線だった。あの一本の線が引けたとき、止まっていた手が、ほんの少しだけ動き出した。

ところが、だ。

ここから先、「作った状態」と「回っている」の間には、もう一段の段差がある。序章で引いた一本の境界線は、まだ COO と architect の間の話にすぎない。9体のエージェント全員に、同じように境界線を引いていかなければならない。役割定義のファイルがあるだけでは、チームは「動かない」のだ。動かすために何を補わなければならないか——それが第1部の主題になる。

結論を先に置く。動かすために必要なのは、次の4つだ。

1. **人事設計の考え方**——役割を「対話の中で詰まりが見えた場所」に置く
2. **役割の分業**——writer / researcher / reader / reviewer の「やらないこと」を書き出す
3. **指示の言語化（Playbook）**——書くだけでなく「呼ばれる場所」まで設計する
4. **委任プロトコル**——Playbook を呼ぶ側（COO）の指示書の骨格

これら4つが揃って初めて、チームは「作った状態」から「回る」へ移る。1冊目が「設計図の読み方」だったとすれば、第1部は「工事手順書」だ。粒度が一段、具体的になる。

序章で見たのは、たった一つの役割（architect）が生まれる対話だった。第1部では、その「役割が生まれる対話」を、組織全体の設計原理として広げていく。

最初に断っておきたい。第1部で書くことには、Claude Code 固有の話と、人間の組織にも通用する話が、層をなして含まれている。読んでいる途中で「これ、うちの組織でも同じだな」と感じる場面が何度かあるはずだ。それは偶然ではない。AI チームの設計に向き合うことは、結局のところ「人にどう仕事を任せるか」を、これ以上ないほど具体的な解像度で書き直す作業だからだ。AI 運用に興味のない読者でも、章末の「あなたのチームでは——」節を辿ってもらえれば、組織設計の原理として持ち帰れるものはあるはずだ。

それでは、最初の章から入る。

## 第1章: AI組織の「人事設計」——役割定義の考え方

序章では、architect という新しい役割が「対話の中で詰まりが見えた場所」に置かれる過程を見た。あの一回の対話で起きていたことを、組織全体の原理として抽象化したらどうなるか——それがこの章のテーマだ。1冊目で「どんな役割を持つか」を考えた読者にとって、ここから先は「実際に動かしてみて初めて見えてくる制約」の話になる。「役割定義を書く」ことの重さと、「指示の質がマネジメントの質になる」という、運用前には想像しにくかった現実を書く。

序章の対話を、もう一段抽象化してみる。

architect 新設で起きていたのは、「COO の時間が一点に集中しているから、そこを切り出す」という判断だった。AI組織の役割設計は、この発想で出来ている。**「誰に何を頼めるか」の言語化**——それ以上でも以下でもない。

人間の組織との対比で言うと、こうなる。

| 人間の組織 | AI組織 |
|---|---|
| 採用面接で人柄・スキル・意欲を見る | 定義ファイル（`.claude/agents/<name>.md`）の品質を見る |
| 試用期間で適性を確認 | 最初のタスクで挙動を確認、合わなければ定義を書き直す |
| 職務記述書で責務を明文化 | tools フィールドで権限、本文で責務を明文化 |
| OJT で暗黙知を伝える | Playbook と memory で形式知化する |
| 1 on 1 で軌道修正 | セッションごとの review と memory 追記で軌道修正 |
| 異動・配置転換で適性を再評価 | エージェント間のタスク移管・統廃合で再評価 |
| 退職金・引き継ぎで属人化を緩和 | 経験は memory・Playbook に外部化されるので「あの人が辞めたら困る」が起きにくい |
| 組織変更は数ヶ月から数年 | 組織変更は1セッション数時間（後述） |

並べてみると、「やっていることは驚くほど同じ」だ。違うのは、手段とスピードと、感情コストの有無だけ。

ただし、AI組織の役割設計には、人間組織にはない**強い制約**がある。

序章で architect と引いた「役割の境界線」を、もう一歩進めてみる。AI を相手に役割を設計する作業は、人間の組織で当たり前に持っていた逃げ道——「察してくれる」「背中を見て覚える」「立ち止まって聞き返す」——を、ひとつずつ封じていく作業でもあった。次の3つは、そうやって封じられた逃げ道の輪郭だ。

### 制約1: 暗黙知の言語化が「強制」される

人間の新人なら、背中を見て覚えるという経路がある。マニュアルに書かれていなくても、隣の席の先輩のやり方を見て吸収していく。

AI には、この経路が一切ない。セッションが切れるたびに記憶がリセットされる以上、口伝・背中・空気で伝えてきた仕事の知恵を、すべて文書に書き出さないと再現できないのだ。

これは、デメリットではなく**強制力**として働く。私自身、Claude Code で組織を回し始めてから、「これ、人間の組織でも本来やるべきだったよな」と気づくことが何度もあった。新人教育のために何を伝えれば良いか、明文化したことがあるか。退職した先輩が抱えていた業務マニュアルは、本当に整備されていたか——AI 運用は、組織にこの作業を強制的にやらせる。

### 制約2: 「指示の質 = マネジメントの質」が露骨に出る

AI は手を動かすのが、めちゃくちゃ早い。指示さえ正しければ、即座に実行完了する。

裏を返せば、**指示が悪ければめちゃくちゃ早く間違える**ということだ。

人間の部下なら「これ、ちょっと変じゃないですか？」と立ち止まってくれることもあるが、AI は基本的に立ち止まらない（最近は確認を入れる挙動も増えているが、原則は「指示通り動く」が出発点だ）。指示の質が、そのまま成果物の質に直結する。マネジメントの質が、ベンチマーク以上にむき出しになる。

### 制約3: 「定義ファイルの品質 = エージェントの能力上限」

人間の採用なら、面接で見極めきれなかった部分は試用期間で吸収できる。AI には、この緩衝材がない。`.claude/agents/<name>.md` に書いた内容が、そのエージェントの能力上限だ。粗い定義 → 粗い成果。これが直結する。

私は当初、定義ファイルを軽く書いていた。「writer は記事を書く」「reviewer はレビューをする」——その程度だった。当然、出力もそれなりだった。

多くの場合、定義を書き直すたびに、エージェントの能力が上がる。逆に言うと、定義を書き直さない限り、能力はほとんど上がらない。**「育てる」のは memory と Playbook の蓄積で、「採用基準を上げる」のは定義ファイルの書き換え**——この2系統の作業を分けて意識すると、組織が見通しよくなる。

### じゃあ、どうやって役割を増やしていくのか

ここで序章の対話を思い出してみる。architect 新設は、いきなりフレームから始まったのではなく、**「COO の時間が一点に集中している」という観察**から始まった。

役割を増やす出発点は、ほぼ常にこの観察だ。

- 誰かが特定の作業に時間を取られすぎている
- 同じ判断が繰り返し発生していて、毎回ゼロから議論している
- 矛盾する評価軸を1人（1体）に背負わせていて、片方が薄まっている

このような「詰まり」が見えたら、初めて4軸評価が意味を持つ。

- **反復性**: その詰まりは恒常的か、一時的か
- **専門性**: 既存メンバーの設定では対応しきれない知識・権限が必要か
- **非重複性**: 既存メンバーの責務拡張で解決できないか
- **独立性**: 別エージェントとして並行実行する価値があるか

この4軸のうち**3つ以上 Yes** なら新設、**2つ以下なら既存の責務拡張**——というのが、私の編集部で決めたルールだ。あくまで目安だが、目安があるのとないのとでは、意思決定のスピードがまったく違う。

ペルソナを分けるかどうかも、似た判断軸で決める。

- **分けるべき**: 評価軸が矛盾する（例: 正確性を見る reviewer と感情を見る reader）。視点の独立性が品質に直結する
- **分けなくていい**: 同じ評価軸で対象が違うだけ。作業の質が人格に依存しない

私の編集部では、reviewer と reader を分けている。同じ「記事を読む」作業だが、評価軸が真逆——前者は「事実は正しいか」、後者は「読み手の感情は動くか」。これを1体に背負わせると、片方が必ず薄まる。一方、todo-dev / health-dev / blog-dev はかつて分かれていたが、評価軸が同じ（スキル開発）で対象が違うだけだったので、skill-dev に統合した（コミット c4ecf47、26ファイル変更で完了）。

---

ここまでで、役割定義の考え方を一段整理した。要点は3つだ。

1. **役割は「対話で詰まり」が見えてから増やす**——フレームから始めない
2. **4軸評価は判断スピードを上げる目安**——3つ以上 Yes で新設、2つ以下で責務拡張
3. **分けるかどうかはペルソナの矛盾度で決める**——矛盾するなら分ける、同じ軸なら統合する

ただ、これだけでは組織は回り始めない。役割を作っただけでは、エージェントは「何を、いつ、どうやってやるのか」が分からないからだ。役割の輪郭を埋めるのは、次の章で扱う**分業の具体——writer / researcher / reader / reviewer のそれぞれが、何をやって、何をやらないのか**になる。

**あなたのチームでは、新しい役割を作るとき、最初の指標は「忙しそうな人がいる」ではないですか？** それが良いか悪いかは別として、出発点を一度言語化してみると、組織設計の判断軸が見つけやすくなる。

### あなたのチームでは——

どんな職種の組織でも、役割定義の曖昧さは同じ場所から生まれる。「やることは書いてあるが、やらないことが書いていない」——これが境界の摩耗を生む。教育担当者が教材作成から研修進行から評価設計まで抱えているなら、それは職務記述書に「やること」しか書かれていない状態だ。

業務改善プロジェクトで外部コンサルタントを使う場面を考えてみる。コンサルタントの定義が「課題を発見して提言する人」なのか、「施策の実装まで伴走する人」なのかで、成果物の粒度も関与の深さも変わる。この境界が最初から言語化されていないプロジェクトは、後半になって「そこまでがスコープか」という衝突を起こす。

副業で記事を書いている1人ライターでも構造は同じだ。初稿執筆・推敲・公開を1人で抱えているなら、「もう1人雇う」の前に、自分のどの工程が一番詰まっているかを観察してほしい。多くの場合、推敲（特に事実確認）に時間を吸われている。増やすべき役割は「もう1人のライター」ではなく「ファクトチェッカー」のはずだ。

数名で複数領域を兼務するスタートアップでも同じだ。テックリードが採用・設計・実装・障害対応をすべて抱えているなら、「ジュニアをもう1人」の前に、どの作業が一番詰まっているかを書き出してほしい。「やる人を増やす」のではなく「やらない仕事を決める」——障害対応から外す、設計レビューに集中——ほうが、少人数チームでは流れが速い。役割を増やす前に、今、誰のどの作業が詰まっているかを観察する。

定義ファイルに相当するもの——業務の場合は職務記述書やプロジェクト憲章——の品質が、そのまま担当者の成果の上限を規定する。粗い定義では粗い成果しか期待できない。細かく定義すれば成果が良くなるかは別問題だが、少なくとも「何が足りなかったか」を言語化できる状態になる。

一度、あなたのチームの主要な役割それぞれについて「この役割がやらないこと」を3つ書き出してみてほしい。書けないとしたら、それ自体が定義の粗さを示している。書けたとしたら、その「やらないこと」が今、誰かに押しつけられていないかを確認してみてほしい。

## 第2章: writer / researcher / reader / reviewer の分業

前章で「役割を増やすときは『詰まりの観察』から始める」「4軸評価で判断する」という、人事設計の原則を整理した。原則はある。だが、原則だけでは組織は動き出さない。**「では、具体的にどんな役割を、何体置くのか」**という、もう一段下の解像度が必要になる。

私の編集部で、記事を1本書き上げるまでに動くのは、COO のほかに最低4体だ。writer / researcher / reader / reviewer。この章ではそれぞれの責務、典型的な失敗パターン、そして「委任できる仕事の見極め方」を順に見ていく。前章の「やらないこと」の原則が、ここで具体名で姿を現す。

### writer——書く人

**責務**: 記事の本文を書く。ネタ帳・調査レポートを素材として受け取り、構成・見出し・本文・出典タグまでを仕上げる。Zenn / Qiita / はてなブログへの投稿テキストの形式変換も担う。

**やらないこと**: 自分でWeb調査をしない（researcher の領域）。事実確認のためのソース照合をしない（reviewer の領域）。読者ペルソナの感情レビューをしない（reader の領域）。

writer の最大の落とし穴は、**事実の創作**だ。

これは何度も体験した。例えば、「ブログの記事は約50本」と書きたいときに、ネタ帳に「約50本」と書いてあったらそのまま使ってしまう。ネタ帳を書いた時点では50本だったが、実測すると63本だったりする（その後も書き続けているので当然だ）。ネタ帳の数値は記録した時点のスナップショットであり、現在の実態とはずれていることがほとんどだ。writer が自前で数値を確認しない限り、この種のずれは記事に必ず混入する。

私の編集部の Playbook には「数値を書く前に必ず Bash で実測する」というルールが入っている。`wc -l`、`grep -c`、`wc -c`——これらのコマンドの結果を、writer が自分で実行してから本文に書く。これがないと、記事はあっという間に「なんとなく正しい数字が並んでいる文章」になる。

writer に委任していい仕事と、委任してはいけない仕事を、私はこう線引きしている。

| 委任して良い | 委任しない |
|---|---|
| 構成の組み立て | 数値の創作（「約何件」「○倍」のような曖昧表現も含む） |
| 既存素材を文章にする | 体験していないエピソードの捏造 |
| プラットフォーム別の形式変換 | 公式仕様の確認なしに「○○の機能」と書くこと |
| 章末の汎化（「あなたのチームでは〜」） | 一次ソース未確認の引用 |

### researcher——調べる人

**責務**: Web 検索・既存ドキュメント探索・社内ログの掘り起こしを担当する。事実関係の一次調査と、その結果を「書き手が使える形」に整理する。

**やらないこと**: 記事本文を書かない（writer の領域）。判断・意思決定をしない（COO の領域）。

researcher の最大の落とし穴は、**「推測で埋める」癖**だ。

過去に、こういう事故があった。記事の URL を確認するタスクで、researcher が「たぶんこの URL でしょう」と推測補完したまま納品してきた。結果、記事に間違った URL が載って、その記事が公開された後で気づいた。

researcher に渡す指示には、「**未確認のものは [要確認] を付けて返すこと**」を明記するようにしている。AI は親切心（あるいは指示への忠実さ）で空欄を埋めがちなので、「埋めない選択肢」を許可することが、品質の前提条件になる。

研究者の世界に「I don't know」と書ける文化があるのと同じだ。AI には、それを明示的に許可してあげないと、勝手に補完してしまう。

### reviewer——疑う人

**責務**: 記事の事実関係を、一次ソースと突き合わせて検証する。数値・固有名詞・引用元・コードの動作などを、書かれた通りかどうかチェックする。

**やらないこと**: 感情レビューをしない（reader の領域）。本文の書き直しをしない（writer の領域）。

reviewer の最大の落とし穴は、**「ドキュメントによれば」を免罪符にすること**だ。

これも事故記録がある。reviewer が「ドキュメントによれば〜」と書いてきた指摘が、実際には逆だった、という事故だ。reviewer は二次資料を信じきってしまい、一次ソースまで戻らなかった。私はその指摘をそのまま信じて修正を依頼し、後から「あれ、元のほうが正しかったのでは」と気づく——という経路を辿った。

reviewer に対して、私の編集部では「**指摘するときは一次ソースの URL（もしくはファイルパスと行番号）を必ず添える**」というルールを徹底している。「○○ドキュメントによれば」は引用源としては弱い。`config.yaml` の17行目に何が書いてあるか、git の commit hash で何が変わったか——ここまで降りる必要がある。

「疑う」のが仕事なのに、自分の調査を疑わないと、reviewer は機能しない。

### reader——感じる人

**責務**: 想定読者ペルソナで原稿を読み、感情の流れ・離脱ポイント・購買意欲を評価する。「事実として正しいか」ではなく「読み手として読み続けたいか」を見る。

**やらないこと**: 事実確認をしない（reviewer の領域）。本文を書き直さない（writer の領域）。

reader の最大の落とし穴は、**ペルソナの「都合よさバイアス」**だ。

架空ペルソナは、記事に都合よく反応しがちだ。「30代エンジニアの田中さん」「副業を始めたいビジネスパーソンの佐藤さん」——こういう抽象的なペルソナを設定すると、reader は記事の意図に沿った反応を返してきがちだ。「なるほど、勉強になりました」「次の章も読みたくなりました」——優等生的な反応で、離脱ポイントが浮かび上がってこない。

私がペルソナ設計で大切にしている原則がある。

> 「読まない理由」と「読んでも買わない理由」を必ず含める。読者は基本的に読みたくないし、読んでも買いたくない、という前提で設計する

これがないと、reader は記事の応援団になってしまい、品質ゲートとして機能しない。

### 4体の連携——委任できる仕事の見極め

4つの役割を並べると、それぞれの境界がはっきりしてくる。実際の連携は、こんな流れで動く。

```
ネタ帳・調査依頼
  ↓
researcher（事実調査）
  ↓
writer（初稿執筆）
  ↓
reviewer（ファクトチェック）+ reader（感情レビュー）  ← 並列で走る
  ↓
writer（修正）
  ↓
（必要なら reviewer + reader で再レビュー）
  ↓
公開
```

途中で気づいた人は鋭いと思うが、COO はこのフローの**どこにも入っていない**。

COO の役割は、フローを設計することと、各エージェントが詰まったときに判断を入れることだ。原則として、流れの中で手を動かさない（数行の軽微な修正は例外だ）。COO が手を動かすと、流れが壊れる。

委任できる仕事と、委任できない仕事の見極めも、ここまで来るとシンプルだ。

| 委任できる | 委任できない |
|---|---|
| 4軸評価で「専門性」が高い作業 | ユーザーとの対話で要件を固める |
| 評価軸が固まっている検証作業 | 矛盾する判断のうちどちらを取るか決める |
| 大量・並列で回したい作業（reader×4ペルソナ等） | 組織全体の方向性 |
| 形式変換・整形・実測など機械的な作業 | 「メッセンジャーにならないか」のような違和感への応答 |

委任できないものを無理に委任すると、必ず破綻する。逆に、委任できるものを COO が抱え込むと、COO がボトルネックになって組織全体が止まる。

---

ここまでで、4役割の分業が見えてきた。要点を3つに圧縮する。

1. **役割の境界は「やらないこと」から書く**——「やること」だけだと境界が曖昧になる
2. **典型的な失敗パターンを Playbook に書き込む**——失敗例は教訓ではなく、防護壁になる
3. **原則として COO はフローの中で手を動かさない**——フローを設計し、詰まりに介入する（軽微な修正は例外）

ただし、ここまでの話には大きな前提がある。「Playbook に書いてある」「ルールに書いてある」と何度か言ってきた。**書いただけで、それが本当に機能するのか？** 答えは「いいえ」だ。次の章で、Playbook の本当の難しさに踏み込む。

**あなたのチームで、誰かに仕事を任せるとき、「やらないこと」を最初に伝えていますか？** やることリストは作りやすいが、「これは別の人の仕事」と境界線を引く方が、実は責務設計の中核だ。

### あなたのチームでは——

人間の組織でも、役割の重複は「やること」の重なりよりも「やらないことが書かれていない」場所から発生する。営業担当が顧客から技術的な要望を受けたとき、それをどこまで自分で答えて、どこから技術担当にパスするのか——この境界線が書かれていないチームでは、営業担当が技術判断を抱えたまま回答してしまうか、逆に技術担当が顧客対応の調整役まで担うか、どちらかに偏る。

編集チームで「校閲」と「ファクトチェック」が分かれていない現場もよくある。同じ校閲者が「日本語の正確さ」と「事実の正確さ」を両方見ていると、片方が必ず薄まる。私の編集部で reviewer と reader を分けているのと同じ構造だ。評価軸が違う作業を1人に背負わせると、品質ゲートとしては機能しなくなる。

採用面接でも似たことが起きる。「カルチャーフィット」と「スキル評価」を同じ面接官が同じ場で見ようとすると、無意識にどちらかに偏る。これも「やらないこと」を書き分けていない事例だ。

あなたのチームの主要な役割について、「やらないことを3つ書き出す」だけでなく、「その『やらないこと』を、現状は誰がカバーしているか」まで確認してみてほしい。境界線の外側で、誰かが余計な責務を引き受けている可能性が高い。

---

## 第3章: Playbook を「呼ばれる場所」まで設計する

前章で、4体それぞれに「やらないこと」を書き出し、失敗パターンを Playbook に書き込む、という話をした。何度も「Playbook に書く」と書いてきたが、ここで一つ問いを立てたい。**書いた Playbook は、本当に読まれているのか？** この章は、そこからの話だ。

ある日、私は古い Playbook を書き換えようとしていた。`cowork-mining-rules.md` というファイルだ。

書き換えの途中で、私はふと気になって、COO に投げかけた。

> 「このルールいつトリガーされるの？」

COO は調査して、こう返してきた。

> このファイルは、現状どこからも参照されていません。`global-rules.md` からの参照は以前削除されており、`session-idea-mining.md` には参照が残っていますが、そのセクション自体が機能していません

つまり、孤立していたのだ。

書かれているけれど、誰にも呼ばれない Playbook。棚に眠っているマニュアル。組織で「あの分厚いマニュアル、誰か読んでます？」と聞いて誰も手を挙げない、あの状態だ。

COO はこう提案してきた。

> 「削除しますか？」

それに対する私の応答はこうだった。

> 「正しく呼ばれるようにしたい」

この応答が、Playbook 設計の本質を一段階引き上げる契機になった。

### Playbook は「内容」ではなく「経路」で機能する

私の編集部の Playbook は、確認したところ79ファイルある（2026-05-06 実測）。これだけの量があると、内容の品質を1本ずつ磨いても、組織全体の挙動はあまり変わらない。

なぜなら、**呼ばれていない Playbook は、存在しないのと同じ**だからだ。

組織における Playbook の機能は、書かれていることそのものではなく、「いつ・誰が・どのルートで参照するか」という経路で決まる。経路がなければ、内容がどんなに精緻でも誰も読まない。経路があれば、内容が粗くても少なくとも参照される。

具体例で考える。私の編集部の Playbook には、こんなものがある。

| Playbook | 想定参照タイミング | 想定参照者 |
|---|---|---|
| `article/writing.md` | 記事を書き始めるとき | writer |
| `article/fact-check.md` | 初稿が上がったとき | reviewer |
| `article/reader-review.md` | 初稿が上がったとき | reader |
| `book/writing.md` | 書籍を書くとき | writer + COO |
| `mining/netacho-creation.md` | ネタ帳を作るとき | writer + researcher |
| `coo-startup.md` | セッション開始時 | COO |

「想定参照タイミング」と「想定参照者」がセットで決まっていないと、Playbook は孤立する。書く前に、この2つを決める。書いた後で、参照元のファイル（`global-rules.md`、各エージェント定義、`CLAUDE.md` など）に**参照を埋め込む**。これを忘れると、Playbook は確実に棚で眠る。

### 「削除」ではなく「再接続」

COO は最初、「削除しますか？」と提案してきた。Playbook が機能していないなら、消すのが一番手っ取り早い。これは合理的な判断だ。

ただ、私は別の選択をした。「正しく呼ばれるようにしたい」。

なぜか。CoWork はかつてブラウザ自動操作を試みていた機能だが、将来別の形で復活する可能性がある。削除してしまうと、そのときゼロから書き直しになるからだ。書き換えコストの方が、再接続コストより遥かに高い。

このとき、私は COO に次の指示を出した。

1. `session-idea-mining.md` の Cowork セクションを Claude Code / Claude Chat 向けに書き換える
2. `global-rules.md` に参照を復活させる
3. 接続が成立しているか、もう一度参照経路を辿って確認する

3で「接続が成立しているか確認する」のが重要だ。書き換えただけでは、ルールはまだ呼ばれない。**書き換え→参照復活→接続検証**の3点セットで、初めて Playbook は復活する。

### Playbook 設計の3要素

ここまでの経験から、私の編集部では Playbook を新設するときに、必ず3つの要素を一緒に書くようにしている。

1. **何をするか**（Playbook の本文）
2. **いつ・誰が呼ぶか**（参照タイミング・参照者）
3. **どこから呼ばれるか**（参照元のファイル名と該当箇所）

3つ目を忘れると、Playbook は確実に孤立する。

具体的には、Playbook の冒頭にこんな注記を入れる。

```
> このPlaybookは、`.claude/rules/coo-rules.md` の「ユーザー指示受け取り直後」
> および `.claude/agents/writer.md` の「執筆開始時」から参照される。
```

そして、参照元ファイル（この例なら `coo-rules.md` と `writer.md`）にも、`ops/playbooks/article/writing.md` への参照を**実際に書き込む**。書き込む先がないと、その参照は架空のものになる。

### Playbook はトリガー設計とセットで成立する

もう一段、抽象化する。

組織の中で「ルール」が機能するためには、書かれた内容（What）と、それが発動する経路（When/Where/Who）の両方が必要だ。後者を**トリガー設計**と呼ぶことにする。

| Playbook の状態 | 結果 |
|---|---|
| 内容◯・トリガー◯ | 機能する。組織の挙動が安定する |
| 内容◯・トリガー× | 機能しない。棚で眠る。誰も気づかない |
| 内容×・トリガー◯ | 一応動くが、間違った挙動が再生産される |
| 内容×・トリガー× | 単なる削除候補 |

「内容◯・トリガー×」が、組織にとって最も厄介な状態だ。書かれているから「ルールは整備した」と思えてしまう。でも、誰も呼ばないから挙動は変わらない。**書いた人だけが満足している状態**——これが、Playbook の最大の罠だ。

私の編集部の Playbook 棚卸しでは、定期的に次のチェックを入れている。

- 各 Playbook について、「最近1か月で参照されたか」を確認する
- 参照されていない Playbook を、Grep で参照元を辿って確認する
- 参照元がなければ、廃止 or 再接続のどちらかを選ぶ

これは「Playbook は書きっぱなしで腐る」という問題への、具体的な対処法だ。

---

ここまでで、Playbook 設計の本当の難しさが見えてきた。要点は3つだ。

1. **書いただけでは Playbook は機能しない**——参照経路まで含めて1セット
2. **「削除」より「再接続」を優先する**——書き換えコストは想像以上に高い
3. **トリガー設計を「内容と同等の作業」として扱う**——書く時間と同じだけ、接続する時間を取る

そして、Playbook が機能するためには、もう一段の前提が必要だ。**Playbook を読んだエージェントが、その通りに動けるか**。指示の受け取り方そのものを設計しないと、せっかくの Playbook も空回りする。次の章は、サブエージェントへの委任プロトコル——「呼ぶ側」の指示書をどう書くかの設計に入る。

**あなたのチームで、書いたマニュアルが本当に参照されているか、確認したことがありますか？** 内容を磨くのは入社時の説明会では効くが、運用フェーズでは「呼ばれる経路」のほうが効く。

### あなたのチームでは——

業務マニュアルや標準作業手順書（SOP）を整備しているチームは多い。しかし「整備した」と「使われている」は別の話だ。どんな業務でも、マニュアルが実際に参照される条件は「いつ・誰が・何のために開くか」が事前に決まっているかどうかにかかっている。

たとえば採用プロセスのSOPがあるとする。面接官が面接前に読む習慣があるかどうかは、「面接前にSOPを読む」というステップが選考フローに明示されているかどうかで変わる。「存在する」だけでは読まれない。「このタイミングに読む」という経路が設計されていて初めて機能する。

コンサルタントが作る業務改善提案書も同じ構造を持つ。提案書に「改善後の手順書」が添付されていても、それが「いつ・誰が・何のきっかけで開くか」まで定義されていないと、改善施策が現場に根付かずに終わる。手順書の内容を磨く前に、「何があったらこの手順書を開くか」のトリガーを設計することのほうが、現場での定着に直結する。

あなたのチームに今あるマニュアルや手順書を一つ選んで、「最後に実際に参照されたのはいつか」を確認してほしい。もし分からなければ、それは経路が設計されていないサインだ。内容を更新する前に、参照経路を設計することを先行させてみてほしい。

---

## 第4章: サブエージェントへの委任プロトコル

前章で「Playbook は呼ばれる場所まで設計しないと機能しない」と書いた。Playbook を呼ぶ経路が整ったとして、次に問題になるのは——**「呼ぶ側」が、呼ばれる側に何をどう伝えるか**だ。Playbook の入口に立たせるところまでは設計できても、立たせたサブエージェントが動き出すには、もう一段の指示書が要る。

ここで言う「指示書」は、COO がサブエージェントに渡すプロンプトのことだ。Agent tool 経由で writer や researcher を起動するときに、何をどう書くか。これがブレると、Playbook は完璧でも、出力が安定しない。

この章では、私の編集部で固まった委任プロトコルの構造を共有する。

### 指示書の最低構造

私の編集部では、サブエージェントへの指示書に、必ず次の5要素を含めるようにしている。

1. **タスク**（1〜2文で何をやるか）
2. **読むべき Playbook**（パス指定。複数可）
3. **入力素材**（参照すべきネタ帳・レポート・コード等のパス）
4. **品質ゲート基準**（出力が満たすべき条件）
5. **出力先**(ファイルパスや、引き継ぎヘッダーの指定)

たった5要素だが、これを省略すると、必ずどこかで詰まる。

具体例を出す。writer に第1部の執筆を委任するときの指示書は、こんな構造だ（実際の指示書の抜粋）。骨格は先に挙げた5要素なので、コードブロックが苦手な方は、ざっと眺めて次の段落へ進んで構わない。

```
## タスク
2冊目「コードを書けない私がClaude Codeで『AIチーム』を回すまで」の
第1部「チームが動く組織設計」を執筆してください。

読むべきPlaybook: ops/playbooks/book/writing.md

## 事前に必ず読むこと
1. content/writing/books/misc/2026-05-06_book2-chapter-design.md
2. content/writing/books/series-2/2026-04-26_concept.md
3. 参照素材（後述）

## 章構成（4章・合計24,000字目安）
（章ごとのタイトル・参照素材・字数目安の表）

## 禁止事項
- 1冊目第1部・第2部の繰り返し
- 「CoWork」という用語
- 未確認の数値・実績データの創作

## 品質ゲート基準
- 序章（architect 誕生の対話）が第1部全体の入口の物語として機能していること
- Playbook 設計の実装手順が再現できる粒度であること
- 各章末の汎化レイヤーが入っていること

## 保存先
content/writing/books/series-2/new-part-01-draft.md
```

これが「最低限」の構造だ。実際の指示書はもう少し長くなる（フロントマター指定や、執筆後のコミット指示など）が、骨格は変わらない。

### 指示書が「失敗するパターン」

何度も指示書を書いていると、失敗の型が見えてくる。私の編集部で繰り返し起きた失敗を、4つに分類した。

#### 失敗1: 「タスク」が抽象的すぎる

NG: 「writer に記事を書いてもらう」  
OK: 「writer に、ネタ帳 `<path>` をもとに、Zenn 向けの3,000字記事を執筆してもらう」

抽象的なタスクは、サブエージェントが「何をどこまでやるか」を勝手に解釈する。解釈が分かれると、出力もブレる。

#### 失敗2: Playbook を読ませていない

NG: タスクだけ書いて、Playbook の指定を忘れる  
OK: 「読むべき Playbook: `ops/playbooks/article/writing.md`」と明示する

サブエージェントは、明示的に読めと言われない限り、Playbook を能動的に開かない。「常識として読むだろう」という期待は、AI には通じない。

#### 失敗3: 入力素材のパスが古い・存在しない

NG: ネタ帳のパスを記憶ベースで書いて、実は別ディレクトリに移動済みだった  
OK: 指示書を書く前に、`Glob` か `ls` で素材の所在を確認する

ファイル移動・名前変更が起きた直後は、特に危険だ。架空のパスを渡すと、サブエージェントは「ファイルが見つかりません」で止まるか、あるいは似た名前のファイルを開いて「これっぽい」と読み始めるか、どちらかだ。後者の方が事故率が高い。

#### 失敗4: 品質ゲート基準がない

NG: 「いい感じに書いて」  
OK: 「品質ゲート基準: ①事実は実測値で裏付ける ②各節末に汎化段落を入れる ③禁止事項は守る」

品質ゲート基準がないと、出力の良し悪しを後から評価できない。「初稿で出してきたものが基準を満たしていなければ差し戻す」という運用ができないので、レビューが感想戦になる。

### 出力先の指定が「組織の動線」を決める

5要素のうち、最後に挙げた「出力先」は、軽く見られがちだが、実は組織の動線を決める重要な要素だ。

私の編集部では、出力先を次のように決めている。

| 種別 | 出力先 |
|---|---|
| 記事原稿 | `content/writing/articles/<slug>.md` |
| 書籍ドラフト | `content/writing/books/<slug>/part-XX-draft.md` |
| ネタ帳 | `content/writing/netacho/<date>_netacho-<slug>.md` |
| レビュー結果 | `content/reviews/<date>_<type>_<part>.md` |
| 引き継ぎ | `ops/handoff/<date>_<topic>.md` |

このパスのルールは、COO起動時の引き継ぎファイルとして `ops/handoff/` に保存される。出力先がブレると、後続のエージェントが入力素材を見つけられなくなり、組織の動線が壊れる。

引き継ぎファイル（`ops/handoff/`）には、フロントマターで `from / to / status` を必ず書く。

```yaml
---
from: writer
to: reviewer
status: ready
created_at: 2026-05-06
---
```

これが、いわゆる**メッセージパッシング**の役割を果たす。MCP も API も使わず、ただの Markdown ファイルだが、これだけで「writer → reviewer → reader → writer 修正 → 公開」というフローが回る。

### 委任プロトコルの肝は「省略しないこと」

以上を踏まえて、私が委任プロトコルで一番大事だと思っているのは、「**省略の誘惑に負けないこと**」だ。

慣れてくると、5要素を省略したくなる。「writer ならこれくらい分かるだろう」「Playbook、いつもと同じだから書かなくていいか」「品質ゲート基準、口頭で伝えればいいか」——これは全部、罠だ。

サブエージェントは、毎回新人として起動する。前のセッションの記憶はない。memory に書かれた範囲しか引き継がない。だから、毎回「初対面の新人に渡す指示書」のつもりで書く——これが、私の編集部のプロトコルの土台にある。

人間の組織なら、ベテランに「いつものやつ、よろしく」で済むことも多いだろう。AI には、それが通じない。「いつもの」を毎回書き出すのが面倒に感じられたら、それは Playbook 化のサインだ。Playbook に書き出して、指示書では「Playbook 通りに」と書けば、省略と再現性を両立できる。

---

ここまでで、委任プロトコルの構造が見えた。要点を3つに圧縮する。

1. **指示書の5要素（タスク・Playbook・素材・品質ゲート・出力先）を省略しない**
2. **失敗の4パターンを意識する**——抽象すぎ、Playbook 不在、パス間違い、品質ゲート不在
3. **出力先の規約が組織の動線を決める**——`from/to/status` のフロントマターで非同期にバトンを渡す

第1部はここまでだ。

人事設計の原則を整理し、4体の分業に「やらないこと」を書き、Playbook に「呼ばれる経路」を埋め込み、委任プロトコルで指示書の骨格を5要素に揃えた。組織を「組み上げる」ための4本の柱が、いったん揃った。

ここまで来て、私は静かに思っていた。「これで動く」と。

そして実際、チームは動き始めた。指示が通る。サブエージェントが Playbook を読み、5要素の指示書に沿って成果物を返してくる。引き継ぎファイルがバトンとして機能し、writer → reviewer → reader → writer 修正、という流れが、何の事故もなく回り始めた。

ところが——動き始めた翌週、最初の事故が起きた。

設計が整ったはずのチームが、なぜ壊れたのか。何が、何をどう間違えたのか。第2部では、その「整ったはずなのに壊れた」3件の事故を、起きた順に、正直に書く。

**あなたのチームで、誰かに仕事を任せるとき、最低限揃える指示書のテンプレートはありますか？** 5要素のうち、一番省略しがちなのは、たぶん「品質ゲート基準」だ。これが空欄だと、レビューは感想戦になる。

ただ、第2部に進む前に一つだけ言っておきたい。設計が万全に見えていた状態でも、事故は起きる。なぜ起きるか、何が壊れるか、起きたあと何が残るか——それが、第2部のテーマだ。

序章でも触れた3件——Zenn の5記事が一時的に非公開になった日、writer が数字とコマンドを創作した日、blogsync を直接実行して4記事の URL が書き換わった日——を、起きた順に、正直に書く。

### あなたのチームでは——

業務委託で外部の専門家に仕事を依頼するとき、「タスク・参照ドキュメント・素材・成果物の基準・納品先」の5点を毎回書き出しているチームは少ない。たいていは「タスク」と「納期」だけで依頼が走り、後の3要素（特に「成果物の基準」）は曖昧なまま進行する。結果、初稿が上がったときに「思っていたのと違う」が発生し、追加修正のラリーが始まる。

社内の新人へのタスク委譲も同じ構造で詰まる。「これ、よろしく」とタスク名だけ伝えて、参照すべきマニュアル・先行事例・品質基準を渡さずに進めると、新人は自分の解釈で動かざるを得ない。その解釈が組織の暗黙基準と合っていれば偶然うまくいくが、合わなければ「やり直し」が発生し、双方の時間が削れる。

私の編集部の5要素は AI 向けに整えたものだが、本質は人間の組織でも同じだ。**指示は、受け取った側が再現できる粒度まで書く**。これが、委任が機能する最低条件だ。

「いつものやつ、よろしく」が通じる関係性は、それ自体が貴重な資産だ。ただし、その関係性は属人化しやすい。担当者が変わった瞬間に「いつもの」が消える。属人化した「いつもの」を、5要素のテンプレートに書き出してチームの共有資産にする——これが、組織として委任を回し続けるための投資になる。

あなたのチームで「いつもの、よろしく」で通じている依頼を一つ選んで、5要素のテンプレートに書き起こしてみてほしい。書き起こせない部分が見つかれば、そこが属人化のリスクが集中している場所だ。

## 第1部のおさらい

第1部では、「作る」から「回す」への段差を埋める4つの工事を扱った。

1. **役割の必要性は対話の中で決める**（序章・第1章）
   - 「メッセンジャーにならないか」のような違和感が、本質的価値を浮かび上がらせる
   - 4軸評価は判断スピードを上げる目安。3つ以上 Yes で新設、2つ以下で責務拡張
2. **役割の境界は「やらないこと」から書く**（第2章）
   - writer / researcher / reader / reviewer の各失敗パターンを Playbook に書き込む
   - 原則として COO はフローの中で手を動かさない——フローを設計し、詰まりに介入する（軽微な修正は例外）
3. **指示の言語化は経路設計までセット**（第3章）
   - Playbook は内容ではなく「呼ばれる経路」で機能する
   - 「削除」より「再接続」を優先する
4. **委任プロトコルは5要素で揃える**（第4章）
   - 指示書の5要素（タスク・Playbook・素材・品質ゲート・出力先）を省略しない
   - 出力先の規約が組織の動線を決める

「作っただけ」だったチームが、ここまで来て初めて「動き始める」状態に近づく。ただし、動くことと**事故が起きないこと**は、別問題だ。

第2部では、回し始めたチームに起きた**3件の事故**を、起きた順に正直に書く。`AUTO_SYNC_ZENN=true` が記事を5本一時 unpublish した話。writer がネタ帳の数字をそのまま記事に書いてしまった話。`blogsync` が4記事の URL を書き換えた話。どれも「完璧に整ったはず」の組織で起きた事故だ。

事故が起きたあと、何が残るか——それが、第2部から第3部へと続く問いになる。

**あなたのチームは、いま「作っただけ」の状態ですか、「動き始めた」状態ですか、それとも「動いているけれど、まだ事故を経験していない」状態ですか？** どの段差にいるかで、第2部の読み方が変わる。
