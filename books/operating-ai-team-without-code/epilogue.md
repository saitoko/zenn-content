# 終章 もう手は止まらない

ある朝、Claude Code を開いた。

そのまま、しばらく手が止まらないことに気がついた。

---

序章で書いたあの朝の話を、覚えているだろうか。

チームが完成した翌朝、画面の前でぼうっとしていた話。9体のエージェントが定義通りに待機しているのに、何の指示も出てこなかった話。前夜の興奮が、画面を開いた瞬間に蒸発していた話。

その後、私はいろいろなことを学んだ。第1部で組織の輪郭を整え、第2部で事故を経験し、第3部で事故を学習に変える仕組みを設計した。本書はその記録だ。

そして、いつの間にか——「翌日、手が止まる」は、消えていた。

---

正確に言えば、ある日突然「回り出した」わけではない。気がついたら、回っていた、というのが近い。

その朝、Claude Code を開いたとき、画面はもう静かではなかった。

昨日「6本同時にレビューしてほしい」と依頼していた記事が、画面に並んでいる。私が承認のサインを出す。reviewer が動き出す。1本目のレビューが返ってくる。「1 OK」と返す。すると次の作業——reader による6本×2ペルソナの読了レビュー、researcher による記事内スペルミス61箇所の一括修正——が連鎖して動き始める。

「1 OK、2 OK、3 に ch 表記の追加修正」。

短文で承認していくだけで、6本の記事が公開ラインに向かっていく。判断が必要なところだけに、私の目が向くようになっていた。

「楽になった」とは、少し違う。うまく言えないが、判断の質が変わった、というのが一番近い。

以前の私は、「次の一手を探す」ことに大半の時間を使っていた。何を書くか、誰に頼むか、どう指示を出すか——それを毎回ゼロから考えていた。今は違う。チームが届けてくれる選択肢の中から、「これでいく」「もう少し待つ」「この方向に変える」を選ぶ。考える対象が、「探す」から「選ぶ」に変わっていた。

そして気がついた。

もう手は、止まらない。

止めようとしても、止まらない。チームが次の素材を持ってくる。判断を求めてくる。気づけば、私は朝の最初の10分で、今日一日の判断を終えている。

---

ただ、正直に言っておきたいことがある。

「回っている」状態には、少しの寂しさがある。

「全部自分でやらなくてよい」というのは、別の言い方をすれば「自分がやる必要が、ほとんどなくなった」ということでもある。前夜のうちに reviewer がレビューを終わらせている、と書いた。それは事実なのだが、その事実の裏には、「自分でレビューしなくてよくなった」という喪失感が、わずかに存在する。

ブログを書き始めた頃の私は、深夜まで原稿を直していた。誤字を一つ見つけるたびに、自分の作品との距離が縮まる感覚があった。今は、reviewer が代わりにそれをやってくれる。確かに品質は上がった。確かに時間は浮いた。でも、原稿との「距離が縮まる」感覚は、以前より少し遠ざかった。

これは「楽になった」とだけ書いて済ませてはいけない、と思った。

チームが回るというのは、自分の関与が薄まることでもある。それを寂しいと感じるかどうかは、「見張る」のか「見守る」のかによって決まる、というのが今の私の結論だ。

「見張る」のは、心配からの行為だ。「壊れていないか」「間違っていないか」を、絶えず確認しに行く。緊張が続く。疲れる。

「見守る」のは、信頼の上に立つ行為だ。チームの仕事を、最後の一線で受け止める準備をしている。緊張は持続的ではない。必要なときに、必要なだけ、集中できる。

「見張る」から「見守る」への移行は、関与の量が減ることではない。関与の質が変わることだ。

---

そして、ここが最後の一点だ。

「見守る」は、放任ではない。

triggerリストが発動するとき、proposals が届くとき、reviewer が「🔴必須」を付けるとき——その瞬間に気づいてあげることが、今の私の仕事だ。

たとえば、writer から `proposals:`（成果物に添える「気になった点」のメモ欄）が付いた成果物が上がってきたとき。それは writer が作業中に違和感を覚え、ルールとの矛盾を発見し、改善案を添えてきた合図だ。気づかなければ、その違和感は流れていく。気づけば、ルールが一行アップデートされる。

たとえば、ある朝 trigger リスト（「次に同じ事故を起こさないためのチェックリスト」）に新しい1行が増えていたとき。それは前日の事故から、サブエージェントが「これは次回防ぐべきだ」と提案してきた印だ。私が承認すれば、それは明日のチームを少しだけ強くする。

「見守る」は、ゆるやかで、でも集中している。

「見張る」のように常時警戒しているのではない。チームが日常を回している間、私は別の仕事をしていてもいい。読みたい本を読んでもいい。コーヒーを淹れに席を立ってもいい。けれど、チームから「ここを見てほしい」というサインが届いたときに、それを受け止められる距離にいる。

Human in the loop の実態は、「介入しない」ではなかった。「適切なタイミングで介入できる状態でいる」ことだった。

そして、介入の形にも、選択がある。

私は、軽い間違いでも、自分で直さない。AI に「ここが間違っている」と指摘するだけにしている。タイポも、表記揺れも、わずかな違和感も。自分で直したほうが、その場では速いのに、それでも指摘する側を選んでいる。

理由はシンプルだ。自分で直してしまうと、「なぜそれが間違いだったか」が、AI 側にも、自分の中にも残らない。指摘するから、AI は理由を踏まえて修正し、その理由は次の作業に流れ込んでいく。一度の指摘が、複数回分の改善になる。

「気づいてあげる」とは、自分で代わりにやることではない。間違いを言葉にして、AI がそこから理由を立ち上げ、自分のルールを更新する——その流れを支える役割だ。

これが、本書のすべての設計が向かっていた場所だ。

---

序章で、あなたに一つの問いかけをした。覚えているだろうか。

**「あなたのチームは今、『作っただけ』の状態ですか。それとも『回っている』状態ですか。」**

ここで、もう一つ問いを置きたい。

**あなたのチームは今、見張っていますか。それとも、見守っていますか。**

「回っている」状態にたどり着くと、この問いに答えられるようになる。そしてその答えは、たいていの場合、最初は意外だ。「見守っている、と書きたかったが、まだ見張っているのかもしれない」と気づくことから、本当の「見守る」が始まる。

あの朝、私の手は止まっていた。

今朝、私の手は止まらない。けれど、止まる必要があるとき——チームがそれを求めるとき——私はちゃんと、止まれる。

それが、私のチームと、私の、新しい関係だ。
