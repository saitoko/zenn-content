# 序章 翌日、手が止まった

> 本書は Claude Code を使って AIチームを運用している方向けに書かれている。

---

## チームを作った翌日、手が止まった

チームが完成した夜、私は少し興奮していた。

`.claude/agents/` ディレクトリの中に、writer、researcher、reviewer、reader——そしてそれらを束ねる COO や、サポート役のエージェントが並んでいる。全部で8体。それぞれに役割が書かれている。私が指示を出せば、誰かが動く。設計図としての「編集部」が揃った。私がブログ記事を書き続けるために Claude Code で組んだチームの、呼び名だ。

明日からはチームと一緒に動ける。そう思いながら、コーヒーを冷ましたまま、その夜は PC を閉じた。

その翌朝のことだ。

Claude Code を開いた。そのまま、しばらく動けなかった。

8体のエージェントが、定義通りに、静かに待機している画面。私の指示を待っている画面。なのに、その指示が、こちらから何も出てこない。

何を、誰に、頼めばいいのか。

記事を書きたいわけではなかった。かといって、何かを調査したいわけでもない。「これからチームを回す」と決めたのは自分のはずなのに、その「回す」が、どこから始まるのか分からなかった。

頭の中が、奇妙に静かだった。

何かを考えているわけではない。何も考えていない。前夜の興奮が、嘘のように引いていた。達成感は、Claude Code を開いた瞬間に蒸発していた。代わりに残っていたのは——なんと言えばいいだろう。空白に近い感覚だった。

手が止まっていることに気づくまで、しばらくかかった。

正確には、止まったというより、動かす理由が見つからなかった。指示を打つカーソルの点滅を眺めながら、自分が何のためにそこに座っているのかが、一瞬わからなくなった。

「チームを作った」はずなのに、「回っている」感じがまったくしない。

そして奇妙だったのは、「動かしたい」という気持ちすら、湧いてこなかったことだ。前夜まで「これで毎日記事が出せる」と興奮していた自分が、翌朝には、画面の前でぼうっとしていた。

達成と空白が、同時にそこにあった。

今なら分かる。あの静けさの正体は、「作る」と「回す」の違いだった。設計図を手に入れただけで、工場の稼働には何も手をつけていなかった。稼働ボタンがどこにあるか、誰も教えてくれなかったのだ。

この体験は、おそらくチームを作った多くの方が経験することだろう。設計図を手に入れたあとの、あの静けさ。工場が完成したのに、最初の一手が分からない感じ。

よく考えてみれば、当たり前だった。

チームを「作る」ことと、チームを「回す」ことは、別の技術なのだ。

「作る」は一度きり、「回す」は毎日。採用して組織図を描いただけで事業が回り出さないのと同じことが、AIのチームにも起きる。設計図（名詞）を持っているだけでは、工場の稼働（動詞）は動かない。

そしてあの朝の私は、止まった手をどうするか分からないまま、ただ画面の前にいた。

---

## COO に、こう投げかけてみた

しばらく画面を眺めたあと、私は一つだけ確信していたことがある。

新しいタスクが来るたびに、COO（オーケストレーター）に同じことを頼んでいた、ということだ。「要件を整理してほしい」「コードベースを調べてほしい」「devチームに渡せる指示書を作ってほしい」。会話のキャッチボールを何往復もしてから、ようやく実装に進む。COO の時間がそこに集中していた。

手が止まったまま、私は COO にこう投げかけた。

> 「Agent へ指示を出すまでの COO の時間を削減できないかが気になりました」

具体的な答えを期待していたわけではない。ただ、自分の中で言語化できていない違和感を、誰かに投げてみたかった。後から振り返ると、この一言が「チームに新しい役割を迎え入れるための面接」の始まりだった。何を任せ、何を任せないか——新しい人を採用するときと同じ問いが、ここから始まる。

COO の応答は、思っていたより具体的だった。

現状のフローは、

要件整理 → コードベース調査 → 設計 → 指示書作成 → devチームへ委任

の5段だ、と整理してきた。そして最後の「指示書作成」が異常に重い、と指摘した。

そこで COO は、こう提案してきた。

> 「設計者エージェントを新設する案はどうかな？」

これが、後に architect と呼ぶことになるエージェントの始まりだった。

COO は4軸評価のフレームを当てて分析を返してきた。

| 軸 | 評価の問い | 今回の評価 |
|---|---|---|
| 反復性 | その作業は繰り返し発生するか | Yes（毎タスクで設計フェーズが必要） |
| 専門性 | 専用の指示書・ルールが必要か | Yes（コード調査→設計書化の専門性） |
| 非重複性 | 既存の責務拡張だけでは足りないか | Yes（COO が抱えると判断と設計が混ざる） |
| 独立性 | 並行実行する価値があるか | Yes（設計と実装を並行できる） |

4軸すべて Yes。新設の判断は揺るがない、と COO は言った。

私の中で、止まっていたものが少し動き出した感覚があった。手は依然として動いていなかったが、画面の向こうで何かが進み始めていた。

ただし、と COO は懸念を出してきた。

> 「COO がメッセンジャーにならないか？」

これは COO 自身が出した懸念だった。設計エージェントを新設したら、COO の役割は「ユーザーの言葉を設計エージェントに伝えるだけ」の中継地点に痩せていくのではないか。チーム全体から見て、COO は何を残すのか。

それを読みながら、私は少しドキッとした。

新しい役割を作ろうとしている当の COO が、自分の存在意義を心配している。AIのエージェントが「自分は何のためにいるのか」を問いかけてきた、という構造だった。

私は即答した。

> 「メッセジャーにはならないよ、私の相談相手になってるじゃん」

書きながら、自分でも気づいていなかったことを言葉にしていた。

COO は、実装の入口ではなかった。対話の相手だった。

要件整理は、COO と私の対話の中でしか固まらない仕事だった。何を作るか（What）を決めるのは、COO が私に質問を投げ、私が答え、COO がそれを再構成する——この往復の中で初めて見えてくるものだ。設計エージェントが引き取れるのは、What が固まった「後」の仕事——コードベース調査と設計書化（How）——だった。

ここで役割の境界が、対話の中ではっきり言語化された。

- **COO**: ユーザーとの対話で要件を固める。意思決定する。違和感に応える
- **新エージェント**: COO から受け取った What を、devチームが実行できる How（設計書）に変換する

役割が固まったので、次は名前だ。COO は5つの候補を提示してきた。architect、designer、planner、lead-dev、tech-lead——どれもエンジニア組織で耳にする肩書きだ。

候補リストから選ぶのではなく、私は問い直した。

> 「役割をもう一度考えよう」

肩書きを先に決めたくなかった。「COO から受け取った What を How に変換する」という本質を確認したうえで、私はこう言った。

> 「architect でいいかな。指示出すイメージないけど、指示を出しているのは本質的には COO だよね」

architect は設計者であって、指示者ではない。指示を出すのは、最後まで COO の仕事として残す。役割名がそのまま境界線になった瞬間だった。

その後、モデルとツールを決めて、`.claude/agents/architect.md` を新設してコミットした。最初のテストは失敗した（セッション中に追加したエージェントは Claude Code が再起動まで認識しない仕様だった）。次のセッションで architect は無事に応答してきた。

ここまでで、何が起きたかを整理しておく。

新しい役割を作るプロセスは、技術的な作業に見えて、実は対話そのものだった。4軸評価という「フレーム」はあるが、それだけでは決まらない。「メッセンジャーにならないか」という違和感が、COO の本質的価値（対話相手）を浮かび上がらせた。役割名は候補から選ぶのではなく、「何を担うか」を言語化してから決めた。

そして、何より——

止まっていた私の手が、対話の中で少しずつ動き始めていた。

朝のあの静けさから、私を引き出したのは指示の書き方ではなかった。チームと「相談」する、という新しい関係性だった。

「作る」と「回す」の段差は、まだ目の前にあった。でも、その段差を一人で乗り越えるのではなく、チームと一緒に登っていけるかもしれない——そんな感覚が、その朝、初めて生まれていた。

---

## この本で持ち帰れること

本書は3部構成と終章で組まれている。AIチームの概念とセットアップは前作『コードを書けない私がClaude Codeで「AIチーム」を作るまで』を参照してほしい。

前作は、コードを書けない私が、Claude Code で8体のエージェント（writer / researcher / reviewer / reader 等）を「対話だけで」設計した記録だ。役割定義ファイル（`.claude/agents/<name>.md`）の書き方、エージェント間の責務分担、最初のチームを立ち上げるまでの試行錯誤を扱った。本書（Vol.2）は、その「作った」チームをどう「回す」かに焦点を当てる。

- **第1部 チームが動く組織設計**（戸惑い → 納得）: architect との対話で見えた「役割の境界」を、チーム全体に広げる。人事設計、4体（writer/researcher/reader/reviewer）の分業、Playbook 設計、委任プロトコル。
- **第2部 走り出すと何が起きるか**（衝撃 → 後悔 → 学び）: チームを回し始めた翌週から起きた3つの事故を、起きた順に書く。「完璧に回るチーム」はない。問題は、事故が起きたあと、何が残るかだ。
- **第3部 事故から育つ仕組み**（前進 → 確信）: 事故を「反省文」で終わらせない仕組み。Human in the loop、reviewer × reader × 著者ペルソナの三層、そして事故ログを trigger リストに変換する仕組み。
- **終章 もう手は止まらない**（静かな着地）: 序章の「翌日、手が止まった」は、ある朝、「手が止まっていない」に変わっていた。その静かな景色を共有する。

---

本書を読み終えたとき、あなたの手元には「チームを回し続けるための設計図」があるはずだ。

しかし一つ、最初に問いかけさせてほしい。

**あなたのチームは今、「作っただけ」の状態ですか。それとも「回っている」状態ですか。**

この問いに答えられない方も、答えが「作っただけ」だった方も、本書はそこから先へ一緒に進む。

あの朝、私の手が止まったように、あなたの手が今日止まっているなら——本書はそこから始まる。
