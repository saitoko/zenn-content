# 第11章 Agent Skills—再利用可能なスキルを設計する

第3章で、よく使う作業を `/` で呼び出すカスタムコマンドを作りました。便利ですが、ひとつ面倒があります。「いま PR サマリーを作りたい」と思ったとき、自分で `/pr-summary` と打たなければ動きません。呼ぶのを忘れたら、その手順は使われないままです。

もし「コミットの直後に PR サマリーが必要だ」とか「テストのないコードに気づいたらテストを足したい」といった文脈を、Claude Code 自身が判断して必要な手順を呼び出してくれたら——それが **Agent Skills** です。この章では、カスタムコマンドとの違い、スキルの定義ファイル構造、1人開発での使いどころ、そしてスキルを Claude Code 自身に作らせる方法を扱います。読み終えたとき、あなたは自分の繰り返し作業をスキルとして切り出し、「呼び出しを意識せずに使える手順」を1つ持てる状態になっています。

---

## Agent Skills とは何か—カスタムコマンドとの違い

Agent Skills は、特定の作業手順・知識・補助ファイルをひとまとめにして、Claude Code が**文脈から自律的に呼び出せる**ようにする仕組みです（2026年6月時点の機能）。

第3章のカスタムコマンドと並べると、違いがはっきりします。

| 軸 | カスタムコマンド（第3章） | Agent Skills |
|----|----------------------|-------------|
| 誰が呼ぶか | 人が `/コマンド名` で明示的に呼ぶ | Claude Code が文脈から自律的に呼ぶ |
| 呼ぶきっかけ | あなたがタイプしたとき | 会話の内容がスキルの説明文と合致したとき |
| 中身 | 手順を書いた Markdown 1枚 | 手順 + 参照ファイル・スクリプトをまとめたフォルダ |
| 向いている用途 | 「いつ使うか」を自分で決めたい定型作業 | 「この状況なら使ってほしい」と任せたい作業 |

カスタムコマンドが「リモコンのボタン」だとすれば、Agent Skills は「条件を伝えておくと勝手に動く家電」に近いものです。Claude Code はスキルの `description`（説明文）を読み、いまの会話がその説明に当てはまると判断したときにスキルを呼び出します。

呼び出しの判断材料が `description` なので、説明文の書き方がスキルの実用性を左右します。これは後の節で詳しく扱います。

> **補足: カスタムコマンドを置き換えるものではない**
>
> Skills が登場したからといって、カスタムコマンドが不要になるわけではありません。「自分のタイミングで確実に呼びたい作業」はカスタムコマンドのほうが向いています。`/pre-commit` のように「いま実行する」と決まっている作業は、自律呼び出しに任せるより自分で打ったほうが確実です。両者は使い分けるものです。

## スキルの定義ファイル構造

スキルは1枚のファイルではなく、**フォルダ単位**で定義します（2026年6月時点）。

### 配置場所とフォルダ構造

```
your-project/
└── .claude/
    └── skills/
        └── pr-summary/
            ├── SKILL.md        # スキル本体（必須）
            └── template.md     # 補助ファイル（任意）
```

`.claude/skills/<スキル名>/` というフォルダを作り、その中に `SKILL.md` を置きます。スキル名はフォルダ名になります。補助ファイル（テンプレート・参照資料・スクリプト等）を同じフォルダに同梱でき、`SKILL.md` から参照できる点がカスタムコマンドとの構造的な違いです。

カスタムコマンドと同様、配置場所で有効範囲が変わります。

| 配置場所 | 有効範囲 |
|---------|---------|
| `~/.claude/skills/<name>/` | すべてのプロジェクトで使える |
| `<project>/.claude/skills/<name>/` | そのプロジェクトのみ |

### SKILL.md の中身

`SKILL.md` は YAML フロントマター + Markdown 本文という構造です。サブエージェント定義（第7章）やカスタムコマンドと同じ形です。

```markdown
---
name: pr-summary
description: コミット済みの変更内容から PR の説明文を生成する。変更のサマリー・PR本文・レビュー依頼文を作りたいときに使う
---

このスキルは、直近の変更から PR 説明文を生成します。

1. `git diff` で変更内容を確認する
2. 変更の目的を1〜2文でまとめる
3. 同フォルダの `template.md` の形式に沿って PR 本文を生成する
4. レビュアーに伝えたい設計上の判断を別項目で添える
```

フロントマターは最小で `name` と `description` の2つです。

- `name`: スキルの識別子（フォルダ名と一致させる）
- `description`: **このスキルが何をするか・いつ使うか**を書く。Claude Code はこの文を読んで呼び出すかどうかを判断するので、「どんな状況で使ってほしいか」を具体的に書くほど精度が上がります

本文には、スキルが実行する手順を書きます。サブエージェント定義の「システムプロンプト」と同じ要領で、普通の業務指示書として書けば十分です。

> **注記: 仕様は変化が速い—公式ドキュメントを正典に**
>
> Agent Skills は新しい機能で、ディレクトリ構造・フロントマターの必須フィールド・読み込みの挙動は更新が続いています（本書執筆時点で 2026年6月）。本書では「カスタムコマンドとどう違うか」「1人開発のどこで使うか」という変わりにくい部分に絞って解説します。`SKILL.md` の正確なフィールド名や最新の置き場所は、[公式ドキュメント](https://code.claude.com/docs)を確認してください。「`/help` でスキル関連のコマンドを調べる」「Claude Code 自身に『このバージョンのスキルの書き方を教えて』と聞く」のも、最新仕様に追従する確実な方法です。

## 1人開発での使いどころ—3つの例

スキルが効くのは「**特定の状況で繰り返し発生するが、自分では呼ぶのを忘れがちな作業**」です。1人開発でよくある3つを挙げます。

### 1. コードレビュースキル—評価基準セットの再利用

第7章で reviewer サブエージェントを作りました。サブエージェントは「別プロセスで批判的に読む」役割でしたが、スキルとしてレビュー基準を切り出しておくと、メインのセッションで作業しながら「この変更、いつもの基準で見て」という文脈に応じて呼び出せます。

レビュー観点（セキュリティ・命名・テストカバレッジ・既存規約との整合など）を `SKILL.md` に一度書いておけば、毎回プロンプトに観点を並べ直す必要がなくなります。`description` を「コードの変更をレビューしてほしいとき・指摘がほしいときに使う」と書いておくと、「これ問題ないか見て」と頼んだときに自動で基準が適用されます。

### 2. PR サマリー生成スキル

コミットを積んだあと、PR の説明文を書くのは地味に手間です。変更の目的・触ったファイル・レビュアーへの注意点を毎回まとめ直すことになります。

この手順をスキルにし、出力フォーマットを補助ファイル（`template.md`）として同梱しておくと、フォーマットが常に揃います。「PR の説明文を作って」と言えば、`git diff` を見て、テンプレートに沿った本文を返します。チーム標準の PR フォーマットがある場合も、テンプレートを差し替えるだけで全プロジェクトに反映できます。

### 3. テスト生成スキル

「実装は書いたがテストがない」という状況は1人開発で起きがちです。テストの書き方（使うフレームワーク・命名規則・境界値を必ず含める方針・モックの方針）をスキルにしておくと、「この関数のテストを書いて」という依頼に対して、毎回同じ品質基準でテストが返ります。

`description` を「実装したコードにテストを追加したいとき・テストが不足しているときに使う」と書いておけば、テストのないコードを書いたあとの文脈で呼び出されやすくなります。

> **事例: 「呼ぶのを忘れる」問題が消えた**
>
> 私はカスタムコマンドで PR サマリー生成を作っていましたが、いざコミットを終えると `/pr-summary` を打つのを忘れ、結局手書きで雑な説明文を書くことが何度もありました。同じ手順をスキルに移し、`description` に「コミット後に PR を作るとき」と書いたところ、「PR 出したい」と言うだけでサマリーが提案されるようになりました。手順そのものは変えていません。変えたのは「自分で呼ぶ」から「文脈で呼ばれる」への一点だけです。

## スキルを Claude Code 自身に作らせる

ここまで `SKILL.md` の構造を説明しましたが、第7章のサブエージェント定義と同じく、**スキルもエディタで一から書く必要はありません**。

スキルもエージェント定義と同じく、**メインの Claude Code に自然言語で頼んで作成・改善できます**。スキルを作りたいときは、こう頼むのが最短です。

```
PR サマリーを生成するスキルを作ってください。

やること: コミット済みの変更から PR の説明文を生成する。
出力: 変更の目的・触ったファイル・レビュアーへの注意点を含める。
いつ使ってほしいか: コミットを終えて PR を作る段階。
```

こう頼むと、`.claude/skills/pr-summary/SKILL.md` のフォルダ構造・フロントマター・本文を一通り生成してくれます。特に重要な `description`（呼び出し判定に使われる文）も、「いつ使ってほしいか」を伝えれば適切な形に整えてくれます。

`description` は呼び出し精度を直接左右するので、生成後に「もっと呼ばれやすくしたい」「逆に呼ばれすぎるので絞りたい」と感じたら、その旨を伝えて調整できます。「テストの話題のたびに呼ばれてしまうので、テストが不足している場面に限定して」といった微調整も自然言語で済みます。

> **補足: 作るのも直すのも自然言語に閉じる**
>
> スキルの「生成→説明文の調整→補助ファイルの追加」は、第7章のサブエージェント定義と同じく、ほとんどが自然言語で完結します。フォルダ構造や YAML の正確な書式を暗記する必要はありません。覚えておくべきは「スキルとは何で、いつ使うものか」という考え方のほうです。

## スキルとサブエージェント定義—どちらに書くか

ここまで読むと、「この手順はスキルにすべきか、サブエージェント定義（第7章）にすべきか」と迷う場面が出てきます。両者は似た形（フロントマター + Markdown）をしていますが、役割が違います。判断軸を整理します。

| 問い | サブエージェント | スキル |
|------|----------------|--------|
| 独立したコンテキストで動かしたいか | はい（別プロセス・別の会話履歴） | いいえ（メインの文脈の中で動く） |
| ツール権限を絞りたいか | はい（`tools` で制限できる） | 権限分離が主目的ではない |
| 何を切り出すか | **役割**（「レビューする人」「実装する人」） | **手順・知識**（「PR サマリーの作り方」） |
| 呼び出し方 | `@` メンション / 委譲 | 文脈から自律呼び出し |

判断の目安はこうです。

- **「別の目」「別の人格」が欲しい** → サブエージェント。たとえば reviewer は、メインの実装コンテキストに引きずられず、独立した立場で批判的に読んでほしい役割です。コンテキスト分離と権限分離が要点になります（第7章）
- **「いつもの作業手順」を再利用したい** → スキル。PR サマリー・テスト生成・レビュー基準のように、「やり方」を切り出して文脈に応じて呼び出したいなら、独立プロセスは要りません

両者は排他ではありません。reviewer サブエージェントに「レビュー基準スキル」を参照させる、といった組み合わせも成り立ちます。まずは「役割を分けたいのか、手順を切り出したいのか」を自問してください。それが最初の分岐点です。

## 「あなたの開発では」—最初の1つを切り出す

スキルは、いきなり何個も作る機能ではありません。まず1つ、効果が分かりやすいものから始めるのが現実的です。

**おすすめの最初の1つ: PR サマリー生成スキル**

理由は3つあります。第一に、効果が即座に分かること——コミット後に「PR 出したい」と言うだけでサマリーが返るようになります。第二に、出力フォーマットを補助ファイルとして同梱でき、スキルの「フォルダ単位」という構造の利点を体験できること。第三に、毎回必ず発生する作業なので、「呼ぶのを忘れる」問題からの解放を実感しやすいことです。

作り方は1ステップです。メインの Claude Code に「PR サマリーを生成するスキルを作って。コミット後に PR を作る段階で使ってほしい」と頼むだけです。生成された `SKILL.md` を読んで、`description` が「自分の使いたい場面」を表しているか確認してください。呼び出し判定はこの文に依存します。

副業でプロダクトを作っている場合は、限られた作業時間の中で「前回どこまでやったか」を素早く復元することが重要です。「セッション開始時に直近のコミットと未完了タスクをまとめるスキル」を作っておくと、作業再開のたびに状況を立て直す時間を削れます。これも `description` に「作業を再開するとき」と書いておけば、文脈に応じて呼び出されます。

## 章末まとめ

- Agent Skills は、作業手順・知識・補助ファイルをまとめ、Claude Code が**文脈から自律的に呼び出す**仕組み（2026年6月時点）
- カスタムコマンド（第3章）は人が `/` で呼ぶ、スキルは Claude Code が `description` を見て自律的に呼ぶ。両者は使い分けるもので、置き換えではない
- スキルは `.claude/skills/<name>/SKILL.md` というフォルダ単位で定義する。補助ファイルを同梱できる点がカスタムコマンドとの構造差
- `description` が呼び出し精度を決める。「いつ使ってほしいか」を具体的に書く
- 1人開発の使いどころは「コードレビュー基準」「PR サマリー生成」「テスト生成」など、繰り返すが呼び忘れがちな作業
- スキルはエディタで書かず、Claude Code 自身に自然言語で頼んで生成・調整できる
- 「役割を分けたい」ならサブエージェント、「手順を切り出したい」ならスキル
- 仕様の更新が速い機能なので、正確な書式は公式ドキュメントと `/help`、Claude Code 自身への質問で確認する

---

スキルとサブエージェントで「手順」と「役割」を切り出せるようになりました。ただ、複雑な実装にいきなり着手すると、設計の見落としが後から効いてきます。次章では、実装の前に方針を検証する Plan mode と、複数の作業を並列で進める仕組みを、1人開発で「設計と実装を分ける」効果として扱います。
