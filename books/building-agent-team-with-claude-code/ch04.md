# 第4章 なぜ1体のAIには限界があるのか

第1〜3章で、`CLAUDE.md` を整え、スラッシュコマンドで作業を速くし、1体の Claude Code をうまく動かす土台ができました。それでも、ある段階で「うまく動かしているはずなのに、なぜか品質が落ちる」場面に出会います。長いセッションで的外れな実装が返ってくる、レビューを頼んだのに甘い指摘しか返らない——こうした詰まりには共通の原因があります。

この章では、1体の Claude Code を使い続けると何が起きるか、なぜ `/compact` や `/clear` だけでは解決しないのか、そして「役割を分ける」というアプローチが何を解決するのかを整理します。読み終えたとき、次章以降で扱うサブエージェントを「なぜ使うのか」が腑に落ちている状態になります。

---

## 1体で使い続けると起きる3つの劣化

Claude Code を1体（1つのセッション）で使い続けると、作業が進むにつれて次の3つが起きます。

### 1. コンテキスト汚染

セッションが長くなると、会話履歴に「今の作業に関係ない情報」が溜まっていきます。さっき直したバグの議論、試して捨てた設計案、別ファイルの調査結果——これらは全部コンテキストに残り続けます。

LLM は、コンテキストにある情報を「考慮すべき文脈」として扱う傾向があります。そのため、関係ない情報が増えるほど、今の指示に対して「さっきの議論」を引きずった応答が混ざりやすくなります。私の体験でも、「もう捨てたはずの設計方針に沿った実装が返ってくる」「前の話題の用語が紛れ込む」といったことが起きました——これがコンテキスト汚染です。

### 2. 役割の混在

1体に対して、あなたは無意識に複数の役割を同時に求めています。実装してほしい、同時にレビューもしてほしい、調べ物もしてほしい。ところが「実装する観点」と「批判的にレビューする観点」は反対向きです。

私の体験では、書いた直後のセッションに「今のコードをレビューして」と頼むと、甘い指摘しか返らないことが多くありました。これはあくまで私の仮説ですが、そのセッションが「このコードを通す」文脈に最適化されていて、自分が書いた実装を否定する方向に頭が回りにくいのだと考えられます。人間が自分のコードをセルフレビューしたときに起きる現象とよく似ています。

### 3. 品質の劣化

コンテキスト汚染と役割の混在が積み重なると、結果として品質が落ちます。指示への追従が弱くなり、的外れな変更が増え、レビューは形式的になります。「最初のうちは調子が良かったのに、作業が進むと精度が落ちる」という体感は、能力の問題ではなく、1体に文脈と役割を詰め込みすぎた構造の問題です。

---

## `/compact` と `/clear` だけでは解決しない

第3章で、コンテキストが詰まったら `/compact`（要約圧縮）や `/clear`（全リセット）を使う、と説明しました。これらはコンテキスト汚染への対処になります。ですが、対処であって解決ではありません。

`/clear` は会話履歴を全部消します。汚染は消えますが、今の作業に必要だった文脈も一緒に消えます。設計方針も、確認済みの前提も失われ、次のプロンプトでまた説明し直すことになります。

`/compact` は要約して残しますが、何を残し何を畳むかはモデルの判断です。重要な決定が要約で抜け落ちることがあり、圧縮後に「さっき決めたことが反映されていない」状態が起きます。

そして決定的なのは、**`/compact` も `/clear` も「役割の混在」には何もしない**点です。リセットしても圧縮しても、同じ1体が「実装もレビューも調査も」を引き受ける構造は変わりません。コンテキストを綺麗にしたところで、書き手の文脈に最適化されたセッションが自分のコードを厳しくレビューできないのは同じです。

つまり、コンテキスト管理は「汚染」を一時的に薄めますが、「役割の混在」という構造そのものは手つかずです。ここに、コマンドでは越えられない壁があります。

---

## 役割の分離—サブエージェントが解決する2つの問題

この壁を越えるアプローチが「役割の分離」です。1体に全部を背負わせるのをやめ、役割ごとに別のサブエージェントを立てます。

サブエージェントは、メインのセッションとは独立して起動する、もう1人の Claude です。独自のシステムプロンプト（行動指針）と、独自のツール権限を持ち、独立した会話履歴で動いて、結果だけをメインに返します。詳しい定義ファイルの構造は次章で扱いますが、ここでは「役割を持った別プロセスを呼べる」という点を押さえてください。

役割の分離は、前節で挙げた2つの問題をそれぞれ直接解決します。

**問題1（コンテキスト汚染）への解決:コンテキストが分離する**

サブエージェントは、メインのやり取りを引き継ぎません。依頼時に明示的に渡した情報（ファイルパス・意図など）だけを手元に、まっさらな状態から作業を始めます。メイン側にどれだけ古い議論が溜まっていても、サブエージェントはその汚染を受けません。「捨てた設計案を引きずる」が構造的に起きなくなります。

**問題2（役割の混在）への解決:役割の指示書が常に効く**

サブエージェントは、起動のたびに自分の行動指針（システムプロンプト）が適用されます。レビュー担当のサブエージェントは、常に「批判的に読む」モードから始まります。毎回プロンプトに「厳しくレビューして」と書く必要がなく、書き手の文脈に引きずられることもありません。「役割を切り替える」のではなく「役割の人を呼ぶ」操作になるため、観点が反対向きでも干渉しないのです。

加えて、役割を分けると副次的な効果が1つ生まれます。**並列で動かせる**ことです。独立したプロセスなので、調査担当に調べ物をさせている間に実装担当に別の作業をさせる、といった同時進行が可能になります。たとえば調査に30分、実装に30分かかる作業を1体で順番にやれば合計60分ですが、調査担当と実装担当を同時に走らせれば（互いに依存しない部分なら）合計30分前後で終わります。1体では順番にやるしかなかった作業を、役割の数だけ並べられます。

## 概念を最小例で確認する

役割の分離が何を変えるかを、最小の対比で示します。

1体に全部頼む場合、1つのセッションに依頼が積み重なります。

```
（同じセッション内で続けて頼む／以下は概念的な手順）
→ このAPI クライアントを実装して
→ （実装が返る）
→ じゃあ今のコードをレビューして
→ （甘い指摘が返る。実装した文脈を引きずっているため）
```

役割を分ける場合、実装とレビューが別プロセスになります。なお、以下は実際のコマンド構文ではなく、何が起きるかを示した概念的な手順です（具体的な呼び出し方は次章以降で扱います）。

```
（メインから2つの役割を呼ぶ／以下は概念的な手順）
→ writer に API クライアントの実装を依頼
→ （writer が実装を返す）
→ reviewer に今の変更のレビューを依頼
→ （reviewer は実装の文脈を持たず、批判的に読んで指摘を返す）
```

後者では、reviewer は「このコードを通したい」文脈を持っていません。だから「null のときに落ちる」「テストが実装に合わせてずらされている」といった、書き手が見落としやすい指摘が返ってきます。コードレビューでレビュアーを別の人に頼むのと同じ効果を、1人開発でも作れる——これが役割の分離の核心です。

なお、ここで `writer` / `reviewer` という名前を使っていますが、これは本書での呼び方です。実装担当・レビュー担当に役割が伝われば、`coder` や `checker` のような名前でも機能します。

## 「あなたの開発では」—詰まりを役割の問題として捉え直す

あなたが日々の開発で次のような症状を感じているなら、それは1体に役割を詰め込みすぎているサインかもしれません。

- 長いセッションで、的外れな実装や「前の話題を引きずった」応答が増えてきた → コンテキスト汚染。`/clear` で薄められるが、根治には役割の分離が要る
- 「レビューして」と頼んでも甘い指摘しか返らない → 役割の混在。実装と同じセッションでレビューさせている限り解決しない
- 調査・実装・レビューを1つのセッションで往復していて、どれも中途半端になる → 1体に複数役割が同居している

これらを「Claude Code の限界」と捉えると手詰まりですが、「1体に背負わせすぎた構造の問題」と捉え直すと、打ち手が見えます。打ち手は1つ——役割を別のサブエージェントに分けることです。

特に1人開発では、レビュアーも調査担当も自分1人が兼ねています。その兼務をそのまま Claude Code に持ち込むと、AI 側でも同じ兼務の弊害が起きます。まずは「実装」と「レビュー」という最も反対向きの2役だけでも分けてみてください。次章以降で、その具体的なやり方を扱います。

サブエージェントの定義は次章ですが、その効果は今日のセッションで半歩だけ先取りできます。次に何かを実装したら、いったん `/clear` でコンテキストを切り、まっさらな状態で「このコードをレビューして」と別プロンプトで頼んでみてください。実装の文脈を引きずらないぶん、同じセッションで頼むより指摘が辛口になるはずです。役割の分離が効くという感覚を、定義ファイルを書く前に体験できます。

---

## 章末まとめ

- 1体の Claude Code を使い続けると、コンテキスト汚染・役割の混在・品質の劣化という3つの劣化が起きる
- `/compact`・`/clear` はコンテキスト汚染を一時的に薄めるが、「役割の混在」という構造そのものには何もしない
- 役割の分離（サブエージェント）は2つの問題を直接解決する。コンテキストが分離するので汚染を受けず、役割の指示書が常に効くので観点がぶれない
- 副次効果として、独立プロセスなので役割を並列に動かせる
- だから本書は「1体を完璧に使う」より「2体に役割を分ける」を勧める。まず実装とレビューという最も反対向きの2役から分ける

---

役割を分けるべき理由が見えたら、次は「サブエージェントとは具体的に何で、どう定義するのか」です。次章では `.claude/agents/<name>.md` というファイルの構造——名前・役割・ツール権限・モデル指定——を1つずつ見ていきます。
