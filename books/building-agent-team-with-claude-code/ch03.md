# 第3章 スラッシュコマンドとカスタムコマンド

Claude Code のセッションが長くなると、応答が遅くなり始めます。前の指示が薄まってきた感覚が出てきます。「ここでいったん整理したい」と思っても、何をすればいいか分からない——そういう場面でどうするか。

また、「毎回同じプロンプトを書いている」と気づいた作業はありませんか。「コミット前にこのファイルを確認してから実装の要点を箇条書きでまとめて」——この手順を毎回タイプするのは非効率です。

この章では、Claude Code のセッションをコントロールする**ビルトインコマンド**と、繰り返す作業を登録する**カスタムコマンド**の2つを扱います。読み終えたとき、セッション管理の手が速くなり、よく使う作業を `/` 1文字で呼び出せる状態になっています。

---

## ビルトインコマンドの基本

Claude Code のプロンプト欄で `/` を入力すると、利用可能なコマンド一覧が表示されます（実際の件数は `/help` で確認できます）。その中でも特によく使う6つを紹介します。

### `/clear`—コンテキストをリセットする

現在のセッションの会話履歴を全部消去します。Claude Code はリセットされた状態になり、次のプロンプトから新しいセッションとして動きます。

**使うタイミング:**

- 作業トピックが完全に変わるとき（「さっきフロントエンドをやっていたが、次はAPIの設計をしたい」）
- 前のやり取りが次の作業の邪魔になりそうなとき
- Claude Code が「前に言ったこと」に引きずられていると感じるとき

`/clear` のデメリットは「全部消える」ことです。途中まで決めた設計方針・確認済みの前提も消えます。消えては困る情報は、先に `CLAUDE.md` や別ファイルに書き出してから `/clear` するのがよい習慣です。

### `/compact`—コンテキストを要約する

会話履歴を要約してコンテキストを圧縮します。`/clear` がリセットなのに対し、`/compact` は「大事なことは残しつつ、詳細を畳む」操作です。

**使うタイミング:**

- セッションが長くなって応答が遅くなってきたとき
- コンテキストをゼロにはしたくないが、軽くしたいとき
- 次のフェーズに入るときに前フェーズの詳細を畳んで全体像だけ残したいとき

`/compact` 後に重要な情報が落ちていないか確認することを推奨します。要約の粒度によっては、細かい決定事項が省略されることがあります。

> **補足: コンテキストの状態を確認する**
>
> `/context` コマンドを使うと、現在のコンテキスト使用量を視覚的に確認できます。コンテキストが詰まってきたタイミングを把握するのに役立ちます。

### `/help`—コマンド一覧を確認する

使えるコマンドとその説明の一覧を返します。「こんな操作ができるコマンドはあるか」と思ったときの最初の確認先です。Claude Code のバージョンによって使えるコマンドが変わるため、インストールしているバージョンの実際のコマンドリストは `/help` が最も正確です。

### `/model`—使用モデルを切り替える

セッション中に Claude Code が使うモデルを変更できます。

**使うタイミング:**

- 長い設計検討は精度の高いモデルで、単純な実装は軽いモデルで——とコスト感覚を持って使い分けたいとき
- 月の後半に利用枠の残りが少なくなってきたとき

### `/cost`—コストを確認する

現在のセッションで消費したコスト概算を確認できます。「このセッションどのくらい使ったか」を確認する手段です。

### `/init`—`CLAUDE.md` の初期化を補助する

新しいプロジェクトで `CLAUDE.md` を作りたいとき、`/init` を実行するとプロジェクト構造を調べて初期 `CLAUDE.md` の雛形を生成してくれます。第2章で紹介した最小テンプレートを手動で書く代わりに使えます。

## カスタムコマンドの作り方

ビルトインコマンドは Claude Code が提供するものですが、**カスタムコマンド**はあなた自身が定義するコマンドです。よく使う手順を Markdown ファイルとして書いておくと、`/` で呼び出せるようになります。

### ディレクトリ構造

```
your-project/
└── .claude/
    └── commands/
        ├── pre-commit-check.md     # /pre-commit-check で呼び出し可能
        └── generate-types.md      # /generate-types で呼び出し可能
```

個人のすべてのプロジェクトで使いたいコマンドは `~/.claude/commands/` に置きます。特定プロジェクトだけで使うものは `.claude/commands/` に置きます。

| 配置場所 | 有効範囲 |
|---------|---------|
| `~/.claude/commands/<name>.md` | すべてのプロジェクトで使える |
| `<project>/.claude/commands/<name>.md` | そのプロジェクトのみ |

### ファイルの書き方

カスタムコマンドのファイルは Markdown で書きます。ファイル名が `/` で始まるコマンド名になります（`pre-commit-check.md` → `/pre-commit-check`）。

**最小構成の例:**

```markdown
コミット前の確認作業を行います。

1. 変更ファイルを確認し、実装の変更内容を箇条書きでまとめる
2. テストが通っているか確認する（`npm test` を実行）
3. TypeScript の型エラーがないか確認する（`npm run type-check` を実行）
4. 以上の結果を「何を変更したか / テスト結果 / 型チェック結果」の形式でまとめる
```

このファイルを `.claude/commands/pre-commit-check.md` として置いてセッションを再起動すると、`/pre-commit-check` と入力するだけでこの手順が実行されます。

> **注記: セッション再起動が必要**
>
> `.claude/commands/` に新しいファイルを追加したとき、反映には Claude Code のセッション再起動が必要です。起動中のセッションにはすぐ反映されません。

### `$ARGUMENTS` で引数を受け取る

コマンドに引数を渡したい場合は `$ARGUMENTS` プレースホルダーを使います。

**例: 特定の Issue 番号をコンテキストに含めるコマンド**

```markdown
GitHub Issue #$ARGUMENTS の内容を確認し、実装方針をまとめます。

1. Issue のタイトル・説明を読む
2. 関連するコードを探して、変更が必要な箇所を特定する
3. 実装のステップを番号付きリストで提案する
```

このファイルを `plan-issue.md` として置き、`/plan-issue 123` と入力すると、`$ARGUMENTS` が `123` に置き換えられて実行されます。

### YAML フロントマターで詳細設定する（任意）

コマンドに説明・ツール制限を付ける場合は、YAML フロントマターを追加できます。

```markdown
---
description: コミット前の品質確認。lint・テスト・型チェックを一括実行します
---

コミット前の確認作業を行います。

（以下、手順を記述）
```

フロントマターはオプションです。シンプルなコマンドには不要で、本文だけで動きます。

## カスタムコマンドの実践例

自分のプロジェクトで効果が出やすいカスタムコマンドをいくつか紹介します。

### コミット前チェック

```markdown
---
description: コミット前の品質チェック（lint・テスト・型チェック）
---

以下の順番でチェックを実行してください。

1. `npm run lint` を実行。エラーがあれば内容を表示する
2. `npm test` を実行。失敗したテストケースを列挙する
3. `npm run type-check` を実行。型エラーを列挙する
4. すべてパスした場合: 「✅ コミット準備完了」と出力する
5. 何かパスしなかった場合: 「❌ 〇〇件の問題があります」と出力し、修正の優先順位を提示する

注意: ファイルの自動修正は行わない。問題の報告と提案のみ。
```

ファイル名: `pre-commit.md`。`/pre-commit` で呼び出せます。

### API 型定義の生成

```markdown
---
description: OpenAPI spec から TypeScript 型定義を生成するガイド
---

`$ARGUMENTS` で指定された OpenAPI spec ファイルを読んで、以下を実行してください。

1. スキーマを確認し、既存の型定義ファイル（`src/types/api.ts`）と比較する
2. 新規・変更されたスキーマを列挙する
3. 生成すべき TypeScript の型定義を提案として出力する（自動書き込みはしない）
4. 承認を求めてから `src/types/api.ts` を更新する
```

ファイル名: `gen-types.md`。`/gen-types openapi.yaml` のように使います。

### 実装の要点サマリー

```markdown
直近の変更（変更済みファイルをリストアップして確認）をもとに、以下の形式でサマリーを作ってください。

## 変更サマリー

**変更の目的:**（1〜2文）

**変更したファイル:**
- `src/xxx.ts`: 〇〇を追加
- `src/yyy.ts`: △△を修正

**テスト:**
- 追加: 〇件
- 修正: △件

**レビュアーに伝えたい判断:**（実装で迷った点・設計上の選択）
```

ファイル名: `change-summary.md`。「reviewer へのコンテキスト渡し」として使えます。

## Agent Skills という上位概念

カスタムコマンドの上位版として、Claude Code は **Agent Skills** という仕組みも持っています。カスタムコマンドが「人間が `/` で呼び出す」のに対し、Agent Skills はメインの Claude Code が文脈から自律的に呼び出す点が異なります。詳細は第11章で扱います。今の段階ではカスタムコマンドで十分です。

---

## 「あなたの開発では」—今日試すこと

この章で紹介した内容から、まず1つ試してほしいことがあります。

**今日から使えるもの:** `/compact` の使い所を意識する

次に長いセッションを続けているとき、「応答が遅くなってきた」と感じたら `/compact` を試してください。全部消すのが嫌なら `/compact`、完全にリセットしたいなら `/clear`——このコンテキスト管理の感覚が体に入ると、長い作業で詰まる頻度が減ります。

**少し時間を取って試してほしいもの:** コミット前チェックのカスタムコマンドを1つ作る

`.claude/commands/pre-commit.md` を自分で書く必要はありません。「このプロジェクトのテストコマンドは〇〇、型チェックは〇〇です。コミット前チェック用のカスタムコマンドを作ってください」と Claude Code に依頼すれば、ファイルを生成してくれます。次のコミット前に `/pre-commit` を呼ぶだけで、手順を覚え直す時間がゼロになります。

副業でプロダクトを作っている方は特に、「週に数時間しかない作業時間の中でコンテキストを素早く復元する」ことが重要です。前回セッションの要点を保存するカスタムコマンドを作っておくと、「どこまでやったか思い出す時間」が短縮できます。

## 章末まとめ

- Claude Code には多数のビルトインコマンドがあり、`/` 入力で一覧を確認できる（実際の一覧は `/help` で確認）
- セッション管理で特に使うのは `/clear`（全リセット）と `/compact`（要約圧縮）。用途で使い分ける
- `/help`・`/context`・`/model`・`/cost` も状況確認・設定変更でよく使う
- カスタムコマンドは `.claude/commands/<name>.md` に Markdown で書くだけ。ファイル名が `/` で始まるコマンド名になる
- `$ARGUMENTS` を使うとコマンドに引数を渡せる
- カスタムコマンドを追加したらセッション再起動が必要
- より高機能な Agent Skills（`.claude/skills/`）はカスタムコマンドの上位概念。第11章で扱う

---

第1〜3章で、Claude Code の動かし方・`CLAUDE.md` によるプロジェクト記憶・コマンドによる作業効率化の3つを手に入れました。これらはあくまで「1体の Claude Code をうまく使う」ための話です。ただ、依頼が大きくなるほど、1体での限界を感じる地点が必ず来ます。次章（第4章）では、その限界が何から来るのか——コンテキスト圧縮の限界・役割の混在が招く品質劣化・並列処理という発想——を、サブエージェントを使い始める前の前提として整理します。
