# 終章 チームを育てる視点

序章を開いたとき、あなたは「なんとなく使っている」状態にいました。`CLAUDE.md` も書いておらず、サブエージェントという言葉は知っていても、自分の開発フローにどう組み込むかは見えない——そういう地点です。今、この終章を読んでいるあなたはどうでしょうか。

本書を通って、何が変わったでしょうか。サブエージェントという言葉は、もう抽象的なものではなくなったはずです。すでに手を動かしてみた人なら、コミット前にレビュアーを回し、「あ、これはうちのプロジェクトの決まりごとだ」と気づくたびに規約が一行ずつ溜まっていく——あの手応えを、もう少しだけ知っているかもしれません。

まだ読んだだけで、これから動かす人も、心配はいりません。本書が描いてきたのは、たった2体のサブエージェントから始められる、ごく小さな一歩だからです。少し前まで一人で抱えていた作業を「誰か」に手渡せる——その安心感は、最初の1コミットから手に入ります。

「1体のチャットボット」だったものが「役割で動くサブエージェントのチーム」になる。本書での変化を一言にすれば、この一点です。この終章では、ここから先、そのチームをどう育てていくかという時間軸の話を、肩の力を抜いてしておきます。

---

## サブエージェントを「足す」のは詰まってからでいい

本書が一貫して勧めてきた進め方は、「2体で始めて、詰まりを感じたら1体足す」というものでした。最初から5体のチームを設計しようとすると、役割の境界を引くだけで疲れてしまい、肝心の「動く」を体感する前に手が止まります。

積み上げの順序は、おおむねこうなります。

- **最初の2体**: writer + reviewer。「作る」と「確かめる」の分業です（本書では第7章で2体の作り方を扱いました）
- **3体目**: 調査が増えたら researcher、エンドユーザー視点が欲しければ user、インフラを触るなら devops。役割の選び方は第8章で詳しく述べました
- **それ以降**: 同じ作業を3回繰り返したと気づいたとき、その作業を担う役割を1つ足す

大事なのは、役割を足す判断を「機能の網羅」ではなく「自分の不便」から始めることです。reviewer を入れたくなったのは、隣にレビュアーがいなかったからでした。3体目も同じで、あなたの開発で実際に詰まっている症状が、次の1体を決めます。私自身、いつか使うだろうと先回りして用意した役割は、結局ほとんど呼び出さないまま `.claude/agents/` に残っていました。不便という実感が伴っていなかったぶん、どんな指示を渡せばいいかも詰められず、宝の持ち腐れになっていたのです。

## チームは1週間・1ヶ月・半年で育つ

「チームを育てる」と言うと、メンバーを増やしていく話に聞こえるかもしれません。でも、ここで言う「育てる」はそうではありません。新しく雇い入れた同僚に、最初は一つひとつ説明していたことが、何度か一緒に仕事をするうちに「いつものやつ、お願い」で通じるようになる——あの感覚に近いものです。同じ2体でも、1週間後のチームと半年後のチームは、まるで別の相棒になります。育つのは数ではなく、エージェントに渡す**指示書（システムプロンプトと `CLAUDE.md`）の精度**、そして「この子にはこう頼めば伝わる」というあなた自身の呼吸です。

私自身がたどってきた道のりと、相談を受けた人たちの様子から、あなたの数ヶ月先を時間軸で覗いてみましょう。あくまで一例で、進み方には個人差がありますが、おおまかな景色のスケッチとして読んでください。

- **1週間後のあなた**: writer + reviewer が動き出しています。初めて reviewer がコミット前に指摘を返してきたとき、「ひとりで書いていたはずなのに、隣に誰かいる」という、ちょっと不思議な手応えを感じるはずです。その指摘を見ながら「あ、これは自分のプロジェクトの規約だ」と気づき、`CLAUDE.md` に1行書き足す。最初の1行です
- **1ヶ月後のあなた**: reviewer の的外れな指摘が目に見えて減っています。「前にも同じこと言われたな」が起きなくなり、規約が `CLAUDE.md` に静かに溜まっていく。よく使う作業にはスラッシュコマンドが2〜3個でき、コミット前に reviewer を回すのが歯磨きのように当たり前になっています。「育ってきたな」と初めて思えるのが、だいたいこのあたりです
- **半年後のあなた**: 自分にとって過不足のない構成に、いつのまにか落ち着いているはずです。開発用途に絞って使う場合、このあたりで2〜4体に落ち着くことが多いようです（後述するように、私自身は用途が開発以外へ広がって増えましたが、それは例外です）。委任の指示書（第9章で扱った型）が手になじみ、新しいリポジトリを始めるとき、前のリポジトリの `.claude/` を迷わずひな形としてコピーする自分がいる。半年前、`CLAUDE.md` の最初の1行を書いたときには想像もしなかった景色です

半年後のチームが頼もしいのは、エージェントが勝手に賢くなったからではありません。あなたが「どの役割に何を渡せば良い成果が返るか」を、運用の手触りを通じて少しずつ覚えていったからです。reviewer に渡す規約を一行書き足すたび、委任の指示書を直すたびに、あなた自身の中にも「この作業はこう頼めば通る」という勘所が静かに積もっていきます。育っているのは、チームと、それを使うあなたの両方なのです。

## 「あなたの開発では」—現在地を一段だけ進める

ここまで読んだあなたが次にやることは、たぶん1つだけで十分です。**まだ `.claude/agents/` を作っていないなら、writer と reviewer の2体を置いて、次の1コミットでレビュアーを回してみる**。それだけです。

具体的には3ステップです。(1) `.claude/agents/` フォルダを作り、`writer.md` を置く（「コードを実装する」の1行でOK）。(2) 同フォルダに `reviewer.md` を置く（「コードをレビューする。ファイル書き込みはしない」の1行でOK）。(3) 次のコミット前に Claude Code に「reviewer を呼んで変更内容をレビューして」と頼む。この3ステップ、5分もあれば完了します。最初の reviewer の指摘が返ってきたとき、「隣に誰かいる」という手応えが生まれます。

すでに2体を動かしているなら、問いはこう変わります。「直近1週間で、同じ作業を3回以上繰り返さなかったか？」もし繰り返していたなら、それが3体目の候補です。調査だったら researcher、動作確認だったら user——症状から役割を選んでください。

逆に、いま不便を感じていないなら、無理に足す必要はありません。2体のまま `CLAUDE.md` を育てるのも、立派な「チームを育てる」です。あなたの開発フローが教えてくれる不便だけを、信号として拾ってください。

> **事例: 私のチームの現在地**
>
> 参考までに、本書の著者である私自身のチームの現在地を書いておきます。2026年6月時点で、私のチームは8体です。writer / reviewer / user / researcher に加え、設計を任せる architect、インフラを見る devops、タスクを仕分ける secretary、スキルを作る skill-dev——この8体を日常的に動かしています。
>
> 本書が「2〜4体に落ち着く人が多い」と言ったそばから8体なのは、私が Claude Code を開発だけでなく、記事執筆や運用そのもののハブとして使うところまで広げたからです。最初からこの数だったわけではありません。
>
> ここに至るまでに、いくつもの事故を経ています。
>
> - 勝手にコードを書き換えるレビュアーを作ってしまった（この事故は第5章で詳述しました）
> - 存在しないAPIを平然と書くエージェント——いわゆるハルシネーション——を止められなかった（第13章で扱いました）
>
> 半年前の私のチームは、いまよりずっと不器用で、数も少なく、私はその不器用さに何度もため息をつきました。それでもチームは、事故と、その後の指示書の手直しを一つずつ繰り返すなかで、ここまで育ってきました。
>
> だから、あなたのチームも、最初から完成している必要はまったくありません。むしろ不器用なところから始めた人ほど、育てる楽しさを長く味わえます。

## 章末まとめ

- Claude Code を「なんとなく使っている」状態から、サブエージェントで「役割で動くチーム」へ——本書での変化はこの一点に集約される
- 増やし方の原則は「2体で始めて、詰まりを感じたら1体足す」。先回りして増やさない
- 「チームを育てる」とは数を増やすことではなく、指示書（システムプロンプト・`CLAUDE.md`）の精度を運用で上げること
- 1週間→1ヶ月→半年の時間軸で育つのはチームだけではなく、どの役割に何を渡すかという運用知もあなたに蓄積される
- 次の一手は1つで十分。2体を置いて次のコミットで回すか、繰り返した作業から3体目を選ぶか

仕組みは、本書ですべて渡しました。育て始めるスイッチは1つ——**この本を閉じた後、ターミナルを開くこと**です。1週間後、reviewer の最初の指摘に驚くあなた。1ヶ月後、コミット前のレビューが当たり前になっているあなた。半年後、新しいリポジトリに迷わず `.claude/` をコピーしているあなた。その入り口は、今あなたの手元にあります。あなたのチームに、幸あれ。
