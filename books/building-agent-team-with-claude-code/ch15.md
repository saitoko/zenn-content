# 第15章 業務別構成例—3パターン

ここまでで、Claude Code を使った writer + reviewer の最小2体（第7章）・3体目の足し方（第8章）・委任プロトコル（第9章）・Hooks（第10章）・Agent Skills（第11章）・Plan mode（第12章）を扱い、さらに1人運用で実際に起きる失敗（第13章）とコスト・ROIの考え方（第14章）まで見てきました。第7〜14章を通じて、道具と判断材料は揃いました。では、自分の業務ではどう組み合わせればいいのか——ここが最後の壁です。

この章では、代表的な3つの開発スタイルについて「役割を何体・Hook と Skill を何に・1週間をどう回すか」を具体例として示します。読み終えたとき、あなたは自分の業務に最も近いパターンを起点に、最初の構成を組み立てられる状態になっています。完成形をコピーするのではなく、「このパターンのどこを自分用に差し替えるか」で考えてください。

---

## パターン1: フロントエンド開発（TypeScript / React）

最初は、自社開発企業でフロントエンドを担当し、業務外の個人開発・副業で Claude Code を使う開発スタイルです。スタックは TypeScript / React / Next.js。

### 役割構成—writer + reviewer の2体

この業務では、第7章の最小2体構成がそのまま中核になります。Claude Code で writer と reviewer のサブエージェントを2体立て、足すなら reviewer の観点を厚くします。

- **writer**: コンポーネント・ロジック・テストの実装（Read / Write / Edit / Bash / Grep / Glob）
- **reviewer**: 型・テスト・アクセシビリティの3観点でレビュー（Read / Grep / Glob / Bash。書き換え権限は渡さない）

フロントエンドで reviewer に持たせたい観点は、サーバーサイドとは少し違います。型の網羅（`any` 逃げの検出）、テストが「描画される証明」になっているか、そして **アクセシビリティ**（`alt` 属性・キーボード操作・コントラスト比など）です。アクセシビリティは1人開発で最も抜けやすい観点なので、reviewer.md の行動指針に明示的に1行入れておくと拾ってもらえます。

### 使う Hook—コミット前の型チェック

このパターンで最初に仕込む Hook は「コミット前の型チェック」です。第10章で扱ったとおり、Hooks は特定のタイミングで自動的にコマンドを走らせる仕組みです（2026年6月時点）。型エラーが残ったままコミットされる事故を、人間の注意力ではなく仕組みで止めます。

考え方としては、コミット操作の前に `tsc --noEmit`（型チェックのみ実行）を走らせ、エラーがあればコミットを止める、という流れです。具体的な設定キーや書式は更新が速いので、最新は公式ドキュメントを正典にしてください。設定そのものも「コミット前に型チェックを走らせる Hook を作って」と Claude Code に自然言語で依頼すれば、雛形が返ってきます。

### 「コンポーネント数20超えたら reviewer 常設」という判断基準

小さなプロジェクトでは、reviewer を毎回呼ばず「気になったときだけ」で十分です。問題は、どこから常設に切り替えるかです。経験的な目安として、**画面を構成するコンポーネントが20を超えたあたり**が切り替えどきです（著者の運用から得た目安であり、厳密な閾値ではありません）。

理由は、コンポーネントが増えると「既存の似たコンポーネントとの重複」「props の型の不整合」「共通スタイルからの逸脱」が人間の目では追えなくなるからです。著者の運用経験では、このあたりから reviewer を常設し、コミット前に必ず1回通す運用に切り替えると、後半の重複・逸脱の蓄積（=設計の崩れ）が目に見えて減りました。

### 1週間の使い方フロー

平日の隙間時間で個人開発を進める場合のイメージです。

- **平日（実装日）**: writer に機能単位で実装を依頼 → コミット前に Hook の型チェック + reviewer を1回
- **週末（まとめ）**: 1週間分の変更を reviewer に通しでレビューさせ、🔴 指摘だけ翌週の頭に回す（第7章のとおり、reviewer の指摘は🔴必須・🟡推奨・🟢良い点の3段階に分かれます。🔴はマージ前に必ず潰すべき指摘で、🟢は維持したい設計判断としてまとめられます。週末は🔴を確実に拾うのが目的です）

> **事例: アクセシビリティ観点は明示しないと拾われない**
>
> 私が個人プロジェクトで reviewer を回していたとき、最初はロジックと型の指摘ばかりで、アクセシビリティの指摘がほとんど出ませんでした。reviewer.md の行動指針に「画像の代替テキスト・キーボード操作・色のコントラストを必ず確認する」と1行足したところ、それ以降は `alt` 属性の欠落やフォーカス順序の問題を拾うようになりました。観点は「書いておけば効く」一方で「書かないと黙る」のが、サブエージェント運用の基本性質です。

## パターン2: 副業プロダクト開発（週10時間）

次は、副業で個人プロダクトを開発するスタイルです。本業とは別に、週10時間という限られた時間で、設計から実装・公開まで1人で回す。ここでは「限られた時間をどう配分するか」が構成設計の主題になります。

### 役割構成—writer + reviewer + user の3体

副業プロダクトでは、第8章で扱った3体目として **user（エンドユーザー視点）** を足すと効きます。1人開発では「作る人」と「使う人」が同じなので、ユーザー視点が抜け落ちやすいからです。

- **writer**: 実装
- **reviewer**: コード品質のレビュー
- **user**: エンドユーザーになりきって、UI・導線・エラーメッセージの分かりにくさを指摘（Read / Grep / Glob。書き換えはしない）

user は「このボタンが何をするか初見で分かるか」「エラー時に次に何をすべきか伝わるか」といった、コードの正しさとは別の軸を見ます。

### Plan mode の活用—週初めの設計確認

週10時間しかないとき、実装に入ってから「設計を間違えていた」と気づくのが最も痛い時間の浪費です。ここで第12章の Plan mode が効きます。Plan mode は、Claude Code が実装に入る前に計画だけを立て、こちらの承認を待つモードです（2026年6月時点）。

週の最初のスロットで、その週に作る機能を Claude Code の Plan mode にかけます。「この機能を追加したい。まず実装計画だけ立てて」と頼み、返ってきた計画を読んで方針を確定させてから、残りのスロットで writer に実装させます。設計の手戻りを、実装に着手する前に潰す使い方です。

### 「週のスロットを設計・実装・レビューに割り振る」

週10時間を、おおまかに3つのスロットに分けて考えると回しやすくなります。

| スロット | 配分の目安 | 何をするか |
|---|---|---|
| 設計 | 2時間 | Plan mode でその週の機能の実装計画を確定 |
| 実装 | 6時間 | writer に機能単位で実装を依頼。コミット前に reviewer |
| レビュー・検証 | 2時間 | user にユーザー視点の確認を依頼し、🔴 を次週設計へ繰り越し |

私の場合はこの配分に落ち着きました。数字そのものより、重要なのは「設計を最初のスロットに固定する」ことです。実装から始めると、Plan mode を飛ばして手戻りを生みやすくなります。

> **事例: 設計スロットを飛ばした週は、必ず後半で崩れた**
>
> 副業の作業で「今週は時間がないから、いきなり実装でいこう」とした週がありました。その週は writer がそれらしいコードを返してくるので最初は進んだ気になりますが、後半で「そもそもデータ構造が違った」と気づいて作り直す、という展開を何度か繰り返しました。Plan mode に最初の2時間を使うほうが、結果的に総作業時間は短くなります。時間がない週ほど設計スロットを削らない、というのが私の運用ルールになっています。

## パターン3: データ分析・機械学習（参考）

最後は、データ分析・機械学習のスタイルです。ここまでの2パターンが「アプリを作る」のに対し、こちらは「データから何かを明らかにする」のが目的で、構成も少し変わります。

このパターンは、データ分析を業務でやっていない方にとっては**参考程度**で構いません。ここで見てほしいのは個々の手法の中身ではなく、**目的が変わると、同じ writer + reviewer の骨格に足す役割が入れ替わる**という一点だけです。この「目的に合わせて役割を差し替える」発想は、次節でフロントエンド開発にもそのまま持ち帰れます。

### 役割構成—researcher + writer + reviewer

このパターンでは、第8章で扱った researcher が主役級になります。Claude Code で researcher・writer・reviewer の3体を役割分担させます。

- **researcher**: データソースの調査・手法の文献調査（Read / Grep / Glob / WebSearch / WebFetch）
- **writer**: 前処理・集計・可視化などの分析コードの実装
- **reviewer**: 分析ロジックの妥当性チェック

データ分析で reviewer に見てほしいのは、コードの綺麗さよりも **ロジックの妥当性** です。たとえば「予測に使ってはいけないはずの未来の情報が、うっかり学習データに混ざっていないか」「平均と中央値を取り違えていないか」「相関を因果と混同していないか」——これらは動くコードでも結論を壊します。reviewer.md に「分析ロジックの妥当性を最優先で検証する」と1行書いておくと拾ってもらえます。

### Skill と Notebook の組み合わせ

分析は同じ手順を繰り返すので、Agent Skills（第11章）と相性が良いです。「分布はヒストグラム、相関は散布図」のような定番の可視化手順を Skill にまとめておくと、分析の質が「その日の気分」に左右されず、毎回同じ品質で回せます。

Jupyter Notebook（セル単位でコードを対話的に試せる実行環境）を使っているなら、あわせて活用できます。Notebook で試行錯誤して固まった処理を、Claude Code に「これを関数として整理して」と渡し、再利用可能なコードに落とす——Notebook は探索、Claude Code は整理と検証、という分担です。

## 「あなたの開発では」—自分のパターンを起点にする

3つのパターンを並べましたが、あなたの業務がどれかにきれいに収まるとは限りません。フロントエンドをやりながらデータも触る、副業で機械学習プロダクトを作る——重なるのが普通です。

ここで意識してほしいのは、**3パターンに共通する骨格はすべて writer + reviewer の2体だ**ということです。パターン1はそこに Hook を、パターン2は user と Plan mode を、パターン3は researcher と Skill を足しているだけです。つまり、どのパターンも第7章の2体から始めて、自分の業務で詰まった観点を1つずつ足して育てたものです。

大事なのは、完成形を真似ることではなく、自分が詰まった不便を起点に1つずつ足すことです。この順番だけは、どのパターンでも変わりません。だからこそ、最初にやることはたった1つに絞れます——3パターンのうち自分の業務に最も近いものを選び、**まず2体（writer + reviewer）だけ置いて、今週1週間回してみてください**。その週に「ここが抜けた」「この観点が欲しかった」と感じた箇所が、あなたが次に足すべき3体目・Hook・Skill を、本のどんな指示よりも正確に教えてくれます。

## 章末まとめ

- 3パターンとも骨格は **writer + reviewer の2体**。違いは「何を足すか」だけ
- **フロントエンド開発**: 2体 + コミット前型チェック Hook。reviewer に型・テスト・アクセシビリティの3観点を持たせる。コンポーネント数20超えで reviewer を常設に切り替える（著者の目安）
- **副業プロダクト開発**: 2体 + user。週初めに Plan mode で設計を固め、週10時間を設計2・実装6・レビュー2のスロットに分ける。時間がない週ほど設計スロットを削らない
- **データ分析・機械学習（参考）**: researcher + writer + reviewer。reviewer はコードの綺麗さよりロジックの妥当性を検証。定番の可視化を Skill 化し、Notebook を使っているなら探索・Claude Code は整理と検証で分担する
- どのパターンも、本書が繰り返し伝えてきたとおり、まず2体で1週間回し、詰まった観点を起点に足していく

3パターンを読み比べて気づくのは、覚えることはほとんどないという事実です。骨格は writer + reviewer の2体で固定、あとは自分の不便に合わせて足すだけ。あなたが今いちばん近いと感じたパターンは、もう頭の中にあるはずです。本を閉じたら、その1つを今週試してください。動かしてみた1週間は、読んだだけの3章分よりも雄弁にあなたの構成を教えてくれます。
