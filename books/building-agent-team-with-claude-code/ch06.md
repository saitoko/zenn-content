# 第6章 役割を考える4つの軸

サブエージェントの定義ファイルは前章で書けるようになりました。すると次に出てくるのは「では、どの役割を作ればいいのか」という問いです。reviewer は欲しい。researcher もあると便利そう。tester、devops、planner——役割名はいくらでも思いつきます。しかし思いつくたびにファイルを作っていくと、すぐに使われないエージェントが並ぶことになります。

この章では、「このタスクにエージェントを作るべきか」を判断する**4つの軸**を扱います。反復性・専門性・非重複性・独立性の4つです。読み終えたとき、あなたは新しい役割を思いついたときに、勘ではなくチェックリストで「作る・作らない」を判断できる状態になっています。役割を増やす判断と、増やさない判断の両方ができることが、この章のゴールです。

---

## なぜ「軸」が必要なのか

サブエージェントは作るのが簡単です。前章で見たとおり、自然言語で「〇〇エージェントを作って」と頼めば雛形が返ってきます。作るコストが低いからこそ、判断基準がないと際限なく増えます。

役割が増えすぎると、3つの問題が起きます。

- **どれに頼めばいいか分からなくなる**: writer と coder と implementer が並んでいると、毎回「どれを呼ぶんだっけ」と迷います
- **メインの Claude Code が誤った委譲をする**: 役割の説明（`description`）が似ていると、メインが意図しないエージェントに作業を振ります
- **メンテナンスが追いつかない**: 役割ごとに行動指針を書いてあるので、方針を変えるたびに複数ファイルを直すことになります

逆に、役割が少なすぎても問題です。1体のエージェントに「実装もレビューも調査もやって」と詰め込むと、観点が混ざって品質が落ちます（この理由は第4章で扱いました）。

つまり判断には基準が要ります。その基準が、これから説明する4つの軸です。**4つすべてに Yes と言える作業だけ、新しい役割にする価値があります**。1つでも No があれば、新設は見送るか、既存エージェントの責務拡張で済ませます。

---

## 軸1: 反復性—その作業は毎回発生するか

最初の軸は反復性です。問いはシンプルで、「その作業は繰り返し発生するか」です。

サブエージェントは、システムプロンプト（行動指針）を一度書けば、それ以降は毎回その指針で動きます。この「一度書けば再利用できる」という性質は、繰り返す作業に対してだけ効果が出ます。

- **Yes の例**: コードレビューは、機能を実装するたびに発生します。毎回やる作業なので、reviewer を1体作っておけば、その都度プロンプトに「批判的に読んで」と書かなくて済みます
- **No の例**: 「このライブラリのライセンスが商用利用可能か一度だけ調べたい」という作業は、1回きりです。専用エージェントを作るより、メインの Claude Code にその場で聞くほうが速いです

判断のコツは、「この作業を今後10回やるか」を想像することです。10回やるなら、行動指針を1回書くコストは10回分の指示の手間で回収できます。1〜2回しかやらないなら、毎回手で頼んだほうが安上がりです。

---

## 軸2: 専門性—特化したシステムプロンプトが有効か

2つ目の軸は専門性です。問いは「その作業には、特化した行動指針を書く価値があるか」です。

サブエージェントの価値の一つは、独立したシステムプロンプトを持てることです。reviewer なら「直すべき点を先に出す」「好みではなく規約に照らして指摘する」といった専門的な振る舞いを仕込めます。この振る舞いが作業の質を左右するなら、専門性が高いと言えます。

- **Yes の例**: コードレビューは、「何をどの順で指摘するか」「どこまで踏み込むか」という観点設計が品質を大きく変えます。指針を書く効果が高いので、専門性は Yes です
- **No の例**: 「ファイルを別ディレクトリに移動する」のような機械的な作業は、特化した指針を書いても結果はほとんど変わりません。専門性は低いです

専門性を見分けるには、「この作業を上手い人と下手な人にやらせたら、結果に差が出るか」を考えます。差が出る作業ほど、行動指針で「上手いやり方」を固定する価値があります。差が出ない作業は、誰がやっても同じなので専門化の意味が薄いです。

---

## 軸3: 非重複性—他エージェントと守備範囲が被らないか

3つ目の軸は非重複性です。問いは「その役割は、既存のエージェントと守備範囲が被らないか」です。

新しく作ろうとしている役割が、すでにあるエージェントの仕事と重なっているなら、新設ではなく既存の責務を少し広げるほうが整理されます。

- **Yes の例（新設すべき）**: writer（実装担当）がいるところに reviewer（レビュー担当）を足す場合、両者の観点は反対向きです。「作る」と「確かめる」は守備範囲が被りません
- **No の例（新設すべきでない）**: writer がいるところに coder を足そうとする場合、どちらも「コードを書く」役割です。守備範囲がほぼ同じなので、2体に分ける意味がありません

重複を見分けるには、2つの役割の「禁止事項」を並べてみると分かりやすいです。禁止事項がほぼ同じなら、同じ仕事をしています。reviewer の禁止事項は「ファイルを書き換えない」、writer の禁止事項は「スコープ外をいじらない」——禁止事項が違うのは、守備範囲が違う証拠です。

> **事例: 似た役割を2つ作って混乱した話**
>
> 私は個人プロジェクトの初期に、`writer` とは別に `fixer`（バグ修正専門）を作ったことがあります。意図は「新規実装と既存バグ修正で頭の使い方が違うから分けたい」でした。しかし運用してみると、メインの Claude Code が「これは新規実装か、修正か」の判定に迷い、毎回どちらに振るか曖昧になりました。両者の禁止事項を並べたら9割同じで、結局 fixer を廃止して writer に統合しました。守備範囲が被る役割は、分けるほど判断コストが増えるだけでした。

---

## 軸4: 独立性—他エージェントの作業結果に依存しないか

4つ目の軸は独立性です。問いは「その役割の作業は、他のエージェントと並行して進められるか」です。

サブエージェントの強みの一つは、メインや他のエージェントと独立したプロセスで動けることです。独立して動ける作業ほど、並行実行やコンテキスト分離の恩恵を受けます。逆に、常に他のエージェントの出力を待つ作業なら、独立した役割にする意味は薄くなります。

- **Yes の例**: researcher（外部ライブラリの調査）は、writer が実装している間に並行して調べられます。実装の完了を待つ必要がありません
- **No の例**: 「writer の出力を受け取って、そのまま整形するだけ」の役割は、writer なしには何もできません。独立性がないので、writer の責務の一部として扱うべきです

独立性は「並行できるか」だけでなく「コンテキストを分けたいか」という観点でも測れます。reviewer は writer の出力を受け取りますが、**あえて writer のやり取りを引き継がず、まっさらな目で読む**ことに価値があります。これは依存ではなく、意図的な分離です。「結果を受け取る」ことと「過程に依存する」ことは違う、と区別してください。

---

## 判断チェックリスト

4つの軸を、新しい役割を思いついたときに当てるチェックリストにまとめます。

```
□ 反復性:   この作業は今後も繰り返し発生するか？（10回やるか）
□ 専門性:   特化した行動指針を書くと結果の質が上がるか？
□ 非重複性: 既存エージェントと守備範囲・禁止事項が被らないか？
□ 独立性:   他エージェントと並行できる／コンテキストを分けたいか？
```

使い方は単純です。

- **4つすべて Yes** → 新しい役割を作る価値がある
- **どれか1つでも No** → 新設は見送る。理由別に次のように対処する
  - 反復性が No → その場でメインに頼む（役割化しない）
  - 専門性が No → 機械的作業なのでカスタムコマンドやスクリプトで済ませる
  - 非重複性が No → 既存エージェントの責務を少し広げる
  - 独立性が No → 既存エージェントの作業の一部として組み込む

「作らない」という判断を明示的にできることが、このチェックリストの価値です。役割は増やすより、増やさないほうが難しい——その難しさを、4つの問いで肩代わりします。

---

## チェックリストの適用例1: なぜ writer が適合するのか

最初の2体（次章で実際に作ります）を、このチェックリストに通してみます。まず writer（実装担当）です。

| 軸 | 評価 | 理由 |
|---|---|---|
| 反復性 | Yes | 機能追加・バグ修正は開発のたびに発生する |
| 専門性 | Yes | 「スコープを限定する」「テストは動く証明として書く」など指針で質が変わる |
| 非重複性 | Yes | 「コードを書く」役割は他にない（最初の1体なので当然） |
| 独立性 | Yes | 実装中、reviewer や researcher と並行できる |

4軸すべて Yes です。writer は新しい役割として作る価値があります。

---

## チェックリストの適用例2: なぜ reviewer が適合するのか

次に reviewer（レビュー担当）です。

| 軸 | 評価 | 理由 |
|---|---|---|
| 反復性 | Yes | レビューは実装のたびに発生する |
| 専門性 | Yes | 「直すべき点を先に出す」「規約に照らす」など観点設計が品質を左右する |
| 非重複性 | Yes | writer（作る）と reviewer（確かめる）は観点が反対向きで被らない |
| 独立性 | Yes | writer の出力を受け取るが、過程は引き継がず独立した目で読む |

reviewer も4軸すべて Yes です。とくに非重複性と独立性が効いています。writer と reviewer は「作る／確かめる」という反対向きの観点を持ち、別プロセスで動かすからこそ「書いた直後の自分には見えないバグ」を別の目が拾えます。同じセッション内で「次はレビュー視点で」と切り替えるのと結果が違う理由は、この独立性にあります。

---

## チェックリストの適用例3: 設計役（architect）を足すかどうか

役割が増えてきた段階で、「設計専門のエージェントを足すべきか」という判断が出てきます。実装の前に、コードベースを調べて設計方針をまとめる役です。これもチェックリストに通します。

| 軸 | 評価 | 理由 |
|---|---|---|
| 反復性 | Yes | ある程度の規模の機能追加では、毎回「設計を固める」フェーズが発生する |
| 専門性 | Yes | 既存コードの調査→設計方針の言語化には専用の指針が効く |
| 非重複性 | Yes | writer が設計まで抱えると「考える」と「書く」が混ざり、判断が雑になる |
| 独立性 | Yes | 設計フェーズと実装フェーズを分け、設計が固まってから writer に渡せる |

4軸すべて Yes なので、規模の大きい開発をするなら architect を足す価値はあります。ただしここで注意したいのは、**4軸が Yes でも「今のあなたに必要か」は別問題**だという点です。小さな機能追加しかしない段階では、設計フェーズがそもそも発生しません。反復性の評価は「将来やるか」ではなく「今の自分の開発で実際に繰り返し起きているか」で見てください。チェックリストは「作れる役割」を判定しますが、「今作るべき役割」は自分の開発の詰まりから選びます。

> **補足: 4軸は「足し算の判断」と「引き算の判断」の両方に使える**
>
> このチェックリストは、役割を足すときだけでなく、すでに作った役割を見直すときにも使えます。たとえば、しばらく使っていないエージェントがあれば、4軸を当て直してみてください。「反復性が実は No だった（思ったほど発生しなかった）」と分かれば、廃止の判断ができます。役割は一度作ったら固定ではありません。

---

## 「あなたの開発では」—役割を増やす前に1問だけ

新しい役割を思いついたとき、ファイルを作る前に1つだけ自問してください。「**この作業、今週すでに何回やったか**」です。

これは4軸のうち反復性を、いちばん早く確認する問いです。今週0回なら、その役割は「あったら便利そう」という想像で、まだ実際の詰まりになっていません。想像で作った役割は、たいてい使われずに残ります。

副業や個人開発で時間が限られているなら、なおさら役割の数は絞ったほうが効率的です。おすすめの進め方は、**まず writer + reviewer の2体で開発を回し、「これを毎回手で頼むのが面倒だ」と感じた作業が出てきたら、その作業を4軸に通す**という順序です。詰まりが先、役割が後です。

たとえば「毎回ライブラリの最新の使い方を調べてからコードを書いている」と気づいたら、それは researcher の出番かもしれません。4軸に通して、4つとも Yes なら足す。1つでも No なら、その場でメインに聞くか、カスタムコマンドにする。この判断が習慣になれば、役割は「必要な分だけ」に保てます。

---

## 章末まとめ

- 新しい役割を作るかどうかは、**反復性・専門性・非重複性・独立性**の4軸で判断する
- **4軸すべて Yes のときだけ新設する**。1つでも No なら、その場で頼む／カスタムコマンド化／既存責務の拡張、で代替する
- writer も reviewer も4軸すべて Yes。とくに reviewer は「作る／確かめる」の非重複性と、独立した目で読む独立性が効いている
- 4軸が Yes でも「今の自分の開発で実際に繰り返し起きているか」は別問題。役割は詰まりから選ぶ
- 4軸は役割を足すときだけでなく、使っていない役割を廃止するときの見直しにも使える
