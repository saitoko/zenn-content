# 第10章 Hooks—自動化トリガーを仕込む

第7章で、reviewer に Write 権限を渡さないことで「レビューのつもりが勝手に書き換えられる」事故を防ぎました。一方、writer の `.claude/agents/writer.md` には「`package.json` を勝手に編集しない」という禁止事項を本文に書いただけで、権限としては Write を渡したままでした。あの禁止事項は「お願い」であって「強制」ではありません。たいてい守られますが、たまに破られます。

この章で扱うのは、その「たまに」をゼロにする仕組みです。Hooks は、Claude Code の特定のイベント（ツールを実行する直前・直後など）に反応して、あなたが書いたコマンドを**決定論的に・必ず**実行します。AI の判断に委ねず、機械的に走ります。読み終えたとき、あなたは `settings.json` に最小1つの Hook を仕込み、「ファイルを変更したら自動で型チェックが走る」「テストが落ちたままコミットさせない」といった守りを自分の開発に組み込める状態になっています。

ただし先に断っておくと、本章で扱うのは2026年6月時点の仕様です。Hooks は更新が速い領域なので、設定キーやイベント名の最新は公式ドキュメントを正典としてください（本章末尾で改めて触れます）。なお、Hook の設定には `settings.json` への JSON 記述が必要な部分があります。本書でここまで「自然言語で完結する」と説明してきた操作の、数少ない例外です。設定ファイル自体も Claude Code に生成させることができます。

---

## Hooks とは何か—「お願い」ではなく「強制」

本書ではここまで、サブエージェントの定義も `CLAUDE.md` の禁止事項も「自然言語で伝えれば効く」と説明してきました。これらは強力ですが、性質としては**運用ルール**です。Claude Code は禁止事項を読んだ上で「今回は例外的に必要だ」と判断して破ることがあります。多くの場面ではそれで十分ですが、「絶対に踏ませたくない地雷」には別の層が要ります。

Hooks はその別の層です。Hooks は Claude Code の**イベント**に紐づけて、シェルコマンドを自動実行する仕組みです。

- イベントの例: 「ツールを実行する直前」「ツールを実行した直後」「Claude Code が通知を出すとき」
- 実行されるもの: あなたが `settings.json` に書いたシェルコマンド（任意のスクリプト）
- 重要な性質: AI の判断を経由せず、条件に合致すれば**毎回必ず**走る

つまり Hooks は「Claude Code に〇〇してとお願いする」のではなく、「Claude Code が△△しようとしたら、必ず〇〇を実行する」という配線です。お願いは破られることがありますが、配線は破られません。

第7章の補足で「より強制的に止めたければ Hooks でファイルパス単位にブロックできる」と予告したのは、この性質を指していました。禁止事項（運用ルール）で入り口は十分、絶対防ぎたい1点だけ Hooks（強制）で固める——これが1人開発での現実的な使い分けです。

## Hook の種類（2026年6月時点）

Hooks にはいくつものイベント種別がありますが、1人開発でまず押さえるべきは次の3つです。

| イベント | 発火タイミング | 代表的な用途 |
|---|---|---|
| `PreToolUse` | Claude Code がツールを実行する**直前** | 危険な操作のブロック・実行前の差分確認・コミット前テスト |
| `PostToolUse` | ツールの実行が**完了した直後** | ファイル変更後の型チェック・エラーの自動ログ記録 |
| `Notification` | Claude Code が通知を出すとき（許可待ち・入力待ちなど） | デスクトップ通知・音で「手が空いた」を知らせる |

3つの中で最も強い力を持つのが `PreToolUse` です。これだけはツールの実行を**止められます**（ブロック）。`PostToolUse` は実行が終わったあとに走るので止めることはできませんが、結果を見て「型エラーが出ている」と Claude Code に差し戻すことはできます。`Notification` は実行の流れには干渉せず、「あなたに知らせる」ための通知系です。

この3つ以外にも、ユーザーがプロンプトを送信したとき・Claude が応答を終えたとき・コンテキスト圧縮の前・セッション開始時など、複数のイベントが用意されています（2026年6月時点）。まずは上の3つで Hooks の感覚をつかみ、必要になったら公式ドキュメントで他のイベントを確認するのが効率的です。

## `settings.json` での Hook 設定方法

Hooks は `settings.json` に書きます。まずは構造を読めるようになっておきましょう。

### どこに書くか

設定ファイルは3か所に置けます。用途で使い分けます。

| 配置場所 | 有効範囲 | 用途 |
|---|---|---|
| `.claude/settings.json` | そのプロジェクト（git 管理対象） | チームで共有したい Hook |
| `.claude/settings.local.json` | そのプロジェクト（git 管理外） | 自分だけの Hook・実験的な設定 |
| `~/.claude/settings.json` | すべてのプロジェクト | どのリポジトリでも効かせたい Hook |

1人開発で試すなら、まず `.claude/settings.local.json` から始めるのが安全です。git にコミットされないので、うまく動かなくても影響がそのリポジトリの手元だけに収まります。

### 基本構造

Hooks は `hooks` キーの下に、イベント名 → マッチャー → 実行コマンド、という入れ子で書きます。最小の例として「ファイルを書き換えたら型チェックを走らせる」設定を示します。

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          {
            "type": "command",
            "command": "npm run type-check"
          }
        ]
      }
    ]
  }
}
```

読み方は次の通りです。

- `"PostToolUse"`: いつ走らせるか（ツール実行の直後）
- `"matcher": "Write|Edit"`: どのツールに反応するか。ここでは Write か Edit。`|` で複数指定でき、`"Bash"` のように1つだけでも、すべてに反応させることもできます
- `"type": "command"` / `"command": "..."`: 実際に実行するシェルコマンド

この設定だけで、Claude Code がファイルを書き換えるたびに `npm run type-check` が自動で走ります。あなたが「型チェックして」と頼まなくても、毎回必ず走ります。

### Hook にはツールの情報が JSON で渡る

Hook で実行されるコマンドには、標準入力（stdin）から JSON が渡されます。中身には「どのツールが・どんな引数で呼ばれたか」「（`PostToolUse` なら）その結果はどうだったか」といった情報が含まれます。コマンド側でこの JSON を読めば、「Bash で `git commit` を実行しようとしたときだけ反応する」のような細かい制御ができます。

JSON の正確なフィールド名・構造は更新されることがあるため、ここでは断言を避けます。実装するときは公式ドキュメントの Hooks ページで現在のスキーマを確認してください。

### 終了コードで「止める」を表現する

`PreToolUse` の Hook は、コマンドの**終了コード**で Claude Code の動きを制御します（2026年6月時点）。

- 終了コード `0`: 問題なし。ツールはそのまま実行される
- 終了コード `2`: ブロック。ツールの実行が止まり、コマンドが標準エラー出力（stderr）に書いた内容が Claude Code に差し戻される
- それ以外の非ゼロ: ブロックはしないが、エラーとして扱われる

終了コード `2` が Hooks の「強制力」の正体です。「この条件なら止める」を、AI の判断ではなくコマンドの終了コードで決められます。

## 1人開発での使い所—具体例3つ

抽象論だけでは使いどころが見えにくいので、1人開発で効く3つの例を、簡単なものから順に示します。

### 例1: ファイル変更時の型チェック（PostToolUse）

先ほどの基本構造そのものです。Claude Code がファイルを書き換えるたびに型チェックを走らせます。

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          { "type": "command", "command": "npm run type-check" }
        ]
      }
    ]
  }
}
```

型チェックがエラーを返したとき、その出力を Claude Code に差し戻して直させたい場合は、ラッパースクリプトを噛ませて、エラー時に終了コードと stderr を返す形にします。「ファイルを変更 → 型が壊れたら即その場で気づく」というループが、あなたが何も言わなくても回り続けます。1人開発では「型エラーに後から気づいてまとめて直す」ことが多いので、この即時フィードバックは地味に効きます。

### 例2: エラー検出時の自動ログ記録（PostToolUse）

Claude Code が Bash でコマンドを実行し、それが失敗したときに、内容をログファイルへ追記する例です。あとから「どこで何がコケたか」を振り返れます。

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          { "type": "command", "command": ".claude/hooks/log-error.sh" }
        ]
      }
    ]
  }
}
```

`log-error.sh` は、stdin で渡る JSON を読み、実行結果がエラーだったときだけログファイルに1行追記する、という短いスクリプトにします（おおよそ以下のイメージです。JSON のフィールド名は公式ドキュメントで確認してください）。

```bash
#!/usr/bin/env bash
# stdin の JSON からコマンドと結果を取り出し、失敗時のみ記録する
input=$(cat)
# jq で必要なフィールドを抜き、エラーなら .claude/error.log に追記する
# （フィールド構造の詳細は公式ドキュメントの Hooks ページを参照）
echo "$input" | jq -r '. as $x | "..."' >> .claude/error.log
exit 0
```

`PostToolUse` は実行を止めないので、ここでは記録に徹し、終了コードは `0`（問題なし）を返します。ログを残すだけなら Claude Code の動きを邪魔しません。

### 例3: コミット前の自動テスト実行（PreToolUse）

3つの中で最も強力な例です。Claude Code が `git commit` を実行しようとしたら、その**直前**にテストを走らせ、落ちていればコミットをブロックします。

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          { "type": "command", "command": ".claude/hooks/pre-commit-test.sh" }
        ]
      }
    ]
  }
}
```

`pre-commit-test.sh` のロジックはこうです。

```bash
#!/usr/bin/env bash
input=$(cat)
# 実行されようとしているコマンドを JSON から取り出す
cmd=$(echo "$input" | jq -r '.tool_input.command // ""')

# git commit でなければ何もしない（素通り）
case "$cmd" in
  *"git commit"*) ;;
  *) exit 0 ;;
esac

# テストを実行し、落ちたら終了コード 2 でブロックする
if ! npm test --silent; then
  echo "テストが失敗しています。コミットをブロックしました。" >&2
  exit 2
fi
exit 0
```

ポイントは2つあります。第一に、`matcher` は `Bash` 全体に反応させ、その中で「`git commit` のときだけ」をスクリプト側で絞っています。Bash で打つコマンドは無数にあるので、マッチャーで大きく拾ってスクリプトで絞り込むのが定石です。第二に、テストが落ちたときに終了コード `2` を返すことで、コミットそのものを止めています。stderr に書いたメッセージは Claude Code に差し戻されるので、Claude Code は「テストが落ちているからコミットできない」と認識し、修正に動けます。

これは Git の `pre-commit` フックと似ていますが、対象が「Claude Code がコミットしようとした瞬間」である点が違います。AI に開発を任せるからこそ、AI が踏みやすい操作の手前に関門を置けるわけです。

## Hook を使う前の注意

Hooks は強力なぶん、雑に使うと自分の足を撃ちます。導入前に2点だけ理解しておいてください。

### 注意1: 無限ループに気をつける

Hook の中でファイルを書き換える処理を入れると、その書き換えがまた `PostToolUse` を発火させ……と連鎖する可能性があります。たとえば「`Write` のたびに自動フォーマッタを走らせ、そのフォーマッタがファイルを書き換える」設計は、ループの温床です。

対策はシンプルです。

- Hook の中で、その Hook が反応する対象を**書き換えない**（型チェック・テスト・ログのような「読むだけ・別ファイルに書くだけ」の処理に留める）
- 書き換えが必要なら、書き換えた結果が同じ Hook を再発火させない経路を確保する

迷ったら「この Hook が走った結果、同じ Hook がもう一度走る条件が生まれないか」を一度自問してください。

### 注意2: Hook は任意のコマンドをあなたの権限で実行する

これが最も重要な注意点です。Hook に書いたコマンドは、**あなたのユーザー権限で・確認なしに・自動で**実行されます。`settings.json` に書いた瞬間から有効になります。サブエージェントの `tools` フィールドのような権限の絞り込みは効きません。Hook は権限の外側で走る仕組みだからです。

したがって、

- Hook のコマンドは、自分が中身を理解できるものだけにする
- 出所の分からない `settings.json` の `hooks` 設定を、内容を読まずにコピーして使わない（任意コード実行のリスクがある）
- まずは `.claude/settings.local.json`（git 管理外）で試し、挙動を確認してから共有設定へ昇格させる

公式ドキュメントも Hooks のページで、任意コマンドが自動実行される点を明確に警告しています。便利さと危険さは同じコインの裏表だと理解した上で使ってください。

### 設定そのものは Claude Code に頼める—ただし中身は理解する

`settings.json` の編集も、実は Claude Code に依頼できます。「Write/Edit のたびに型チェックを走らせる Hook を `.claude/settings.local.json` に追加して」と頼めば、設定を書いてくれます。ただし Hooks に関しては、生成された設定を**自分で読んで理解してから**有効にしてください。Hooks の価値は「決定論的に必ず走る」ことであり、その走るものが何かを把握していないのは、上の注意2の警告そのものに当たります。Agent 定義は「とりあえず動かして直す」でよくても、Hooks は「理解してから仕込む」が原則です。

## 最新機能なので、公式ドキュメントを正典に

繰り返しになりますが、Hooks は更新が速い領域です。本章で示したイベント名（`PreToolUse` / `PostToolUse` / `Notification`）・`settings.json` のキー構造・終了コードの意味・stdin に渡る JSON のフィールドは、いずれも2026年6月時点の仕様です。設定キーが増えたり、JSON の構造が変わったりすることは十分あり得ます。

実際に仕込む前には、公式ドキュメントの Hooks ページ（`https://code.claude.com/docs` 配下）で現在の仕様を確認してください。また、対話的に Hook を設定・確認できる `/hooks` コマンドも用意されています（2026年6月時点）。手で `settings.json` を書く前に `/hooks` で全体像を見ると、いま使えるイベントの一覧を取りこぼさずに済みます。

## 「あなたの開発では」—まず1つだけ仕込む

3つの例を見て「全部設定したい」と感じたかもしれませんが、最初は1つだけにしてください。おすすめは**例1の型チェック**（PostToolUse）です。ブロックを伴わないので暴発しても作業が止まらず、Hooks の「勝手に走る」感覚を安全に体験できます。

手順はこうです。まず `.claude/settings.local.json` を開き（なければ作り）、`Write|Edit` に反応して型チェック（あなたのプロジェクトのコマンド。`npm run type-check` でも `tsc --noEmit` でも）を走らせる Hook を1つ書きます。設定を書いたら Claude Code のセッションを再起動して反映させ、適当なファイルを1つ Claude Code に書き換えてもらってください。型チェックが自動で走れば成功です。

それが体に入ったら、次は「絶対に守りたい1点」を `PreToolUse` のブロックで固めます。1人開発で踏みやすいのは「テストが落ちたままコミットする」「`main` ブランチに直接 push する」「`.env` を書き換える」あたりです。あなたの開発で「これだけは AI に勝手にやられたくない」という操作を1つ挙げ、その手前に終了コード `2` の関門を置いてみてください。運用ルール（禁止事項）で広く守り、Hooks で1点だけ強制する——この二層構造が、1人で AI に任せる開発の安心感を一段引き上げます。

## 章末まとめ

- Hooks は Claude Code のイベントに反応してシェルコマンドを**決定論的に・必ず**実行する仕組み。`CLAUDE.md` の禁止事項（破られうる「お願い」）に対して、Hooks は破られない「強制」の層
- まず押さえる3イベントは `PreToolUse`（実行直前・唯一ブロックできる）・`PostToolUse`（実行直後・差し戻しは可能）・`Notification`（通知系）。他にも複数のイベントがある
- 設定は `settings.json`（共有は `.claude/settings.json`、自分用は `.claude/settings.local.json`、全プロジェクトは `~/.claude/settings.json`）に `hooks` → イベント → `matcher` → `command` の入れ子で書く
- `PreToolUse` は終了コード `2` でツール実行をブロックし、stderr を Claude Code に差し戻せる。これが Hooks の強制力の中心
- 注意は2点。無限ループ（Hook が反応対象を書き換えない）と権限（Hook は確認なしにユーザー権限で任意コマンドを実行する。中身を理解したものだけ仕込む）
- 仕様は更新が速い。イベント名・キー構造・JSON フィールドは2026年6月時点のもの。実装前に公式ドキュメントと `/hooks` で最新を確認する

---

Hooks が「イベントに反応して決まった処理を走らせる」配線だとすれば、次に欲しくなるのは「文脈に応じて呼ばれる、再利用可能な作業のかたまり」です。第11章では Agent Skills を扱います。第3章のカスタムコマンドが「人が `/` で呼ぶ」ものだったのに対し、Agent Skills は Claude Code が文脈から自律的に呼び出します。1人開発でよく使うパターンを、再利用できる形に設計していきます。
