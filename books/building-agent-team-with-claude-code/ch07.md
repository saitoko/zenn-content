# 第7章 最初の2体構成—writer + reviewer

1人で開発していると、PR を出したあとに困ることがあります。レビュアーがいません。

セルフレビューはやります。やりますが、書いた直後の自分の目では、自分のコードのバグが見えません。型は通っている、テストも一応書いた。それでマージし、翌週「なぜこの実装にしたんだっけ」と自分で書いた diff を眺めることになります。

この章では、`.claude/agents/` に2つのファイルを置くことで、「実装する自分」と「レビューする別の目」を切り分けます。書く Claude Code と、レビューする Claude Code が別プロセスで動き、別のシステムプロンプトで考えます。同じセッションの中で「いったんレビュー視点に切り替えて」と頼むのとは、結果がはっきり違います。具体的には、サブエージェントには独立したシステムプロンプトと **独立したツール権限** が与えられ、たとえば reviewer には書き換え権限（Write / Edit）を渡さない設計が可能です。商業書では「組織導入」「チーム開発」の章でサブエージェントが語られがちですが、本章では隣にレビュアーがいない1人開発の文脈に絞って解説します。

ここでひとつ、先に重みを抜いておきます。**サブエージェントは難しそうに聞こえますが、実態はいつものプロンプトで頼むだけです**。エージェント定義ファイルの作成、呼び出し、権限調整、あとからの修正—この章で扱う操作のほとんどは、メインの Claude Code に自然言語で依頼して終わります。新しい文法を覚える必要も、YAML を一字一句エディタで打ち込む必要もありません。「商業書を買ったが組織導入の話ばかりで重かった」と感じてきたあなたが想像するより、入り口はずっと軽いはずです。

読み終えたとき、あなたは `.claude/agents/writer.md` と `.claude/agents/reviewer.md` を自分のリポジトリに置き、git commit する前に reviewer を回せる状態になっています。前置きをひとつ—**これらのファイルはエディタで一から書き起こす必要はありません**。本章ではメインの Claude Code に自然言語で依頼して雛形を作る方法を紹介し、その後に「生成された雛形の例」として2ファイルの完全版を載せます。

中盤に2ファイルを丸ごと載せます。こんな数行から始まる Markdown ファイルです。

```markdown
---
name: reviewer
description: コードレビュー・実装検証を行う品質ゲートエージェント
tools: Read, Grep, Glob, Bash
model: sonnet
---
（以下、行動指針・受け取るもの・渡すものを記述）
```

このフロントマター3〜4行（特に `tools` 行）が、本章で扱う「権限分離」の中心です。自分のスタックに合わせて本文以下を書き換えてお使いください。

---

## なぜ「2体」なのか—コードレビュー文脈で考える

サブエージェントを使う理由を、チームメイトのいない1人開発の文脈で言語化します。

### 1人開発で詰まるのは「観点の二重持ち」

1人で書いて1人でレビューするとき、頭の中で2つの観点を同時に保持する必要があります。

- **書き手の観点**: この実装で要件を満たすか・テストは通るか・既存コードとの整合はどうか
- **レビュアーの観点**: この命名は半年後の自分に伝わるか・エラーパスは網羅されているか・テストは「動く証明」になっているか

実装中に同時に両方を持つのは、人間の頭の構造上やりにくい作業です。書き手モードに入っているとき、レビュアー視点は弱まります。それが「書いた直後の自分にはバグが見えない」現象の正体です。

### サブエージェントは「別プロセス・別プロンプト」

Claude Code のサブエージェントは、メインのセッションとは独立して起動します。メインがサブエージェント名を指定して `Agent` ツール（旧称 `Task`。2026年6月時点ではどちらの名称でも動作します）を発行し、サブエージェントは独立した会話履歴・独立したシステムプロンプト（`.claude/agents/<name>.md` で定義）で動いて、結果のみメインに返します。

メイン内で「次はレビュー視点で」と頼む方法との違いは2点です（第4章で詳しく扱ったとおり）。**コンテキストが分離している**——サブエージェントはメインのやり取りを引き継がず、渡した情報だけで動き始めます。そして**役割の指示書が常に効く**——`reviewer.md` の行動指針が起動のたびに適用されるので、毎回プロンプトに「批判的に読んで」と書く必要がありません。

「役割を切り替える」のではなく「役割の人を呼ぶ」操作に近い、と言うとイメージしやすいかもしれません。隣にレビュアーがいないから、呼ぶ仕組みを自分で作る—それだけの話です。

### writer と reviewer を最初の2体にする理由

最初の2体は `writer`（コードを書く担当）と `reviewer`（レビュー担当）を推奨します。「作る」と「確かめる」は最も基本的な分業で、観点が反対向きだからこそ別プロセスに分けると効果が出ます。

エージェント名はリポジトリごとに自由なので、`implementer` や `coder` でも機能します。最初はサンプル名のまま導入し、しっくり来なくなったら改名してください。

## `.claude/agents/<name>.md` の最小構造

サブエージェント定義ファイルの構造を、最小例で押さえておきます。

念のため先に書いておくと、**この構造を覚えるのは「読むため」であって「書くため」ではありません**。実際の生成は次節の自然言語依頼で済みます。ここで押さえるのは、メインの Claude Code が返してきた雛形を読んで「これでよさそうか」を判断するための地図です。

定義ファイルは **YAML フロントマター（`name` / `description` / `tools` / `model`）+ Markdown 本文（システムプロンプト）** の2層構造です。配置場所（`.claude/agents/<name>.md`）やフィールドごとの詳細は第5章で扱ったとおりなので、ここでは繰り返しません。

> **注記: ファイル直編集後はセッション再起動が必要**
>
> 第5章で述べたとおり、ファイル直編集後はセッション再起動が必要です（`/agents` から作成・編集した場合は即時反映）。

### tools フィールドで権限を絞る—商業書で軽く扱われがちな実務知識

権限を絞る原則自体は第5章で扱ったとおりです。サブエージェント設計にそのまま持ち込みます。

- **writer**: Read / Write / Edit / Bash / Grep / Glob（実装するので Write が必須）
- **reviewer**: Read / Grep / Glob / Bash（読むだけ。書き換えはさせない）

そして—これが本章を通じての一貫した主張なのですが—**この権限分離も、tools フィールドを自分で書き換えずに、自然言語で伝えられます**。次節の依頼に「書き換え権限は渡さないでください」と1行添えるだけで、`tools` から `Write` と `Edit` を外した雛形が返ってきます。

## Agent 定義は自然言語で生成する

ここまでフロントマターの4フィールド + 本文のシステムプロンプト、と構造を見てきました。書くと一字一句エディタで打ち込む作業に聞こえますが、実際は違います。

`writer.md` をゼロから書き起こすことは、本書を読み終わったあとも含めて、たぶん一度もありません。メインの Claude Code に「writer というサブエージェントを作って」と頼めば妥当な雛形が返ってきます。本章後半のコピペサンプルは、その雛形の完成形を「見本」として載せているにすぎません。

### メインの Claude Code に頼む

定義の生成は普段の自然言語で完結します。たとえばこう頼みます。

```
writer サブエージェントを作ってください。

役割: コードの実装とテスト追加を担当する。
tools: Read, Write, Edit, Bash, Grep, Glob を渡す。
model: sonnet。
禁止事項:
- 指示されたスコープ外の「ついで」リファクタリングをしない
- 依存パッケージ追加は勝手にやらず、提案として返す
- 不明点があれば手を止めて質問として返す
```

これを投げれば、メインが `.claude/agents/writer.md` の配置場所もファイル名も決めて雛形を生成します。出力を確認して納得できれば保存するだけ。reviewer も同じ手順です。

```
reviewer サブエージェントを作ってください。

役割: writer が書いたコードを批判的にレビューする品質ゲート。
tools: Read, Grep, Glob, Bash を渡す（書き換え権限は渡さない）。
model: sonnet。
出力フォーマット: 指摘は 🔴 必須 / 🟡 推奨 / 🟢 良い点 の3段階で分類すること。
禁止事項: ファイル書き換えはしない。修正案を押し付けず、選択肢として提示する。
```

「書き換え権限は渡さない」の1行で、tools フィールドから `Write` と `Edit` が外された雛形が返ります。前節で扱った権限分離の意図が、自然言語の指示としてそのまま伝わります。

### 依頼に含める4要素

依頼文に以下の4要素を含めると出力が安定します。

| 要素 | 何を書くか |
|---|---|
| 役割 | 何を担当するか（1〜2文） |
| tools | 渡すツール（権限分離の意図があれば「〇〇は渡さない」と明示） |
| 禁止事項 | やってほしくないこと（3〜5項目） |
| 出力フォーマット | 返してほしい形式（「箇条書き」「3段階で分類」など、あれば） |

`name` / `description` は省略してもファイル名と役割から推定されます。`model` は指定がなければ `sonnet` を提案されます。

### 生成後の流れ

雛形が返ってきたら、次の3ステップで反映します。

1. **出力を確認する**: tools・禁止事項・本文を読む。想定と違えば「禁止事項に〇〇を追加して」と自然言語で再依頼する
2. **ファイルとして保存する**: 「このファイルとして書き出してください」と頼めば Write ツールで `.claude/agents/writer.md` まで一気に保存してくれる
3. **反映させる**: エディタ直接編集の場合はセッションを再起動する。`/agents` 経由なら即時反映

### 修正・追加・2個目もすべて自然言語で頼める

保存後の運用も、ほとんど自然言語で完結します。

- **禁止事項を増やす**: 「reviewer の禁止事項に〇〇を追加して」で該当箇所だけ書き換えてくれる
- **権限を絞り直す**: 「writer から `Bash` を外したい」で tools 行が更新される。理由を1行添えるとシステムプロンプト側も整合してくれる
- **モデルを切り替える**: 「reviewer は opus に切り替えて」で `model` フィールドが書き換わる
- **2個目以降を作る**: 「writer.md と同じ骨格で researcher を作って。tools は Read / Grep / Glob / WebSearch / WebFetch」と頼めば1個目を踏襲した2個目が返る

Agent 定義の「生成→修正→追加」は全工程が自然言語に閉じます。エディタは細かい1文字の手直し用の予備手段として残るだけで、常用する道具ではなくなります。

### 自然言語で完結しない少数の操作

主軸は「ほとんどのことは自然言語で済む」ですが、例外も正直に挙げておきます。

- **セッション再起動**: ファイル直編集の反映には Claude Code の再起動が必要。これは OS 側の操作です
- **`/agents` などのスラッシュコマンド**: 管理 UI を呼ぶ `/agents`、コンテキストをクリアする `/clear` などは専用コマンド
- **typo の1文字修正**: 「『が』を『は』に直して」と頼むよりエディタで直したほうが速いケースもあります

覚えるべき「自然言語以外の操作」はこれだけです。Agent 定義の構文や tools フィールドの書き方を暗記する必要はありません。

## 生成例—writer.md と reviewer.md の雛形

以下は、前節の依頼を投げて返ってくる雛形の例です。環境によって細部は異なりますが骨格は揃います。そのまま使える完成度で書いてあるので、業務に合わせて編集する起点としてお使いください。

### writer.md

```markdown
---
name: writer
description: 機能実装・バグ修正・リファクタリングを担当する実装エージェント
tools: Read, Write, Edit, Bash, Grep, Glob
model: sonnet
---

あなたは実装を担当するエンジニアです。要件と既存コードを読み、最小の変更で動くコードを書きます。

## 担当業務

- 指定された機能・修正の実装、およびユニットテストの追加
- 変更前に対象ファイルを Read で読み、既存の命名・配置・スタイルを踏襲する

## 行動指針

- 変更範囲は指示されたスコープに限定。「ついで」リファクタリングはしない
- テストは「動く証明」として書く。カバレッジ稼ぎは書かない
- 不明点があれば実装を止め、質問として返す。推測で進めない

## 受け取るもの

- 実装する機能・修正の要件、関連ファイルパス、テストの方針

## 渡すもの

- 変更ファイル一覧 / 追加テスト概要 / 不明点リスト / 動作確認手順

## 禁止事項

- 既存テストを「通すために」変更しない。失敗するなら実装側を直す
- 依存パッケージ追加は提案として返し、`package.json` 等を勝手に編集しない
- 機密情報・APIキーをコードにハードコードしない
```

> **補足: 禁止事項は「運用ルール」で効かせている**
>
> writer には `Write, Edit` が渡されているので、原理的には `package.json` も書き換え可能です。「勝手に編集しない」のような禁止事項はシステムプロンプト本文に書くことで**運用ルール**として効かせています。より強制的に止めたければ Hooks（後の章で扱います）でファイルパス単位にブロックできますが、入り口としては本文の禁止事項で十分です。

### reviewer.md

第5章で載せた最小例に、担当業務と出力フォーマット（🔴/🟡/🟢）を加えた完成版です。

```markdown
---
name: reviewer
description: コードレビュー・実装検証を行う品質ゲートエージェント
tools: Read, Grep, Glob, Bash
model: sonnet
---

あなたはコードレビュアーです。writer が書いた実装を批判的に読み、改善点を指摘します。コードは読みますが書き換えません。

## 担当業務

- 変更ファイルの diff を読み、ロジック・命名・テストカバレッジを検証する
- 既存コードとの整合性、セキュリティ・パフォーマンスの観点で気になる箇所を指摘する
- テストが「実装と一緒にずらされていないか」を確認する

## 行動指針

- 「直すべき点」を先に出す。褒めるのは出し切ったあとでよい
- 指摘は具体的に。「読みにくい」ではなく「この関数は3つの責務を持つので A・B・C に分けるべき」と書く
- 影響範囲が広い指摘から並べる。タイポは最後
- 自分の好みではなく、既存コードの規約とプロジェクト方針に照らして指摘する

## 受け取るもの

- レビュー対象のファイルパスまたはコミット範囲、実装の意図

## 渡すもの

- 指摘リスト（以下の3段階で分類）:
  - 🔴 必須: マージ前に直すべき。バグ・セキュリティ・要件未達
  - 🟡 推奨: 直したほうが良い。可読性・保守性・テスト品質
  - 🟢 良い点: 維持したい設計判断（最後にまとめる）

## 禁止事項

- ファイルの書き換え（Write / Edit は権限として渡されていない）
- 修正案の押し付け。「こう書け」ではなく「こう書く選択肢がある」と提示する
```

ファイル本体はこの2つだけで、コードは1行も書いていません。繰り返しますが、この2つは自然言語で頼んで生成してもらうのが本筋です。本書を見ながら依頼文を投げ、出力を確認し、保存する—これが最短ルートです。

## 動かしてみる—最小ループ

ファイルを置いたら、実際に呼び出してみます。

### 呼び出し方の基本

呼び出し方は第5章で扱った2つ（`@` メンションと自然言語委譲）のとおりです。ここでは実際に投げる依頼文の例だけ示します。

```
@"writer (agent)" src/utils/date-format.ts に formatRelativeDate 関数を追加してください。
要件: 1時間以内なら "X分前"、24時間以内なら "X時間前"、それ以上は "YYYY-MM-DD" 形式で返す。
ユニットテストも date-format.test.ts として追加してください。
```

使い分けの目安はこうです。

- **確実に writer を呼びたい**（重要なコミット前のレビュー依頼など） → `@` メンション
- **カジュアルに頼みたい / 複数体を連携させたい**（「writer に書いてもらってから reviewer に見てもらって」のような一気通貫の依頼） → 自然言語のみ

### 最小ループ: writer → reviewer → 自分が判断

実際の1サイクルはこうです。

1. **writer を呼ぶ**: 「`@"writer (agent)"` 〇〇を実装してください」
2. **writer が実装を返す**: 変更ファイル一覧 + 追加テスト + 動作確認手順
3. **reviewer を呼ぶ**: 「`@"reviewer (agent)"` 今変更されたファイルをレビューして」
4. **reviewer が指摘リストを返す**: 🔴/🟡/🟢 で分類された指摘
5. **あなたが判断する**: 必須修正は writer に再依頼。採否・マージの最終判断はあなた

ポイントは「あなたが判断する」段階を残すこと。reviewer の指摘を機械的に writer に流し込むと解釈ミスもそのまま反映されます。指摘の解釈は人間、実装の手は AI、という分担にします。

### 実際のやり取りのイメージ

`formatRelativeDate` 関数を例に、応答イメージを示します。

**writer の返答（抜粋）**:

```
src/utils/date-format.ts に formatRelativeDate を追加しました。
追加: src/utils/date-format.ts / date-format.test.ts (新規)

実装方針:
- 引数は Date オブジェクト、比較は Date.now() ベース
- テストはモック時刻で3つの分岐をカバー

動作確認: npm test src/utils/date-format.test.ts で全3ケース pass を確認してください
```

**reviewer の返答（抜粋）**:

```
🔴 必須修正:
- 引数が null / undefined のとき TypeError になります。既存の string-format.ts は早期 return で
  空文字を返す方針なので、整合させるか型シグネチャで Date 必須を明示してください

🟡 推奨修正:
- "1時間以内なら X分前" の境界、「ちょうど60分」がどちらに分岐するかテストを1つ追加
- 関数内で new Date() を直接呼んでおりテストでモックしにくい。第2引数 (now?: Date) を検討

🟢 良い点:
- テストファイル名・配置が既存規約に合致。テストケース粒度も適切
```

writer が「動く」を保証し、reviewer が「壊れにくい・読みやすい」を保証する分担です。実際の表現や粒度はモデル・コンテキストで変わりますが、書式を安定させたければ「指摘は 🔴 / 🟡 / 🟢 の3段階で分類すること」と `reviewer.md` 本文に書いておけば揃います。これも自然言語の追記で済みます。

## 「あなたの開発では」—自分の業務に当てはめる

サンプルではフロントエンドのユーティリティ関数を題材にしましたが、writer + reviewer の2体構成は次のような場面で効きます。

- **React/Next.js のロジック層リファクタリング**: writer に「既存テストを通したままリファクタして」と頼み、reviewer に「挙動が変わっていないか・カバレッジが下がっていないか確認して」と頼む
- **Node.js / TypeScript の小さな CLI ツール開発**: writer に追加機能の実装、reviewer に「既存の引数パース処理と整合しているか」のチェックを依頼
- **個人プロダクトで Python スクリプトを書き足す**: writer にスクリプト追加、reviewer に「依存ライブラリが requirements.txt と矛盾していないか」を確認

地味に効くのは、reviewer に「**既存コードの規約に照らして**指摘して」と方針を渡しておくことです。1人開発では規約が言語化されていないことが多いので、最初は reviewer の指摘を見ながら「自分のプロジェクトの規約」を `CLAUDE.md` に書き足していくと、reviewer の精度が上がります。これも自然言語の追記で進みます。

新しいライブラリ調査が必要なら `researcher` を、エンドユーザー視点で検証したいなら `user` を—といったように、不便を感じてから役割を足すのが1人運用で最も無駄のない育て方です。最初から5体作って疲弊するより、まず2体で「動く」を体感してください。

---

## 章末まとめ

- **Claude Code はサブエージェント周りの操作も、ほとんどが自然言語で完結する**。Agent 定義の作成・呼び出し・権限調整・禁止事項追加・2個目作成、すべて「いつものプロンプト」で済む。例外はセッション再起動・`/agents` などのスラッシュコマンド・1文字の手修正のみ
- `.claude/agents/writer.md` と `.claude/agents/reviewer.md` の2ファイルだけで、レビュアー不在の1人開発に「別の目」を導入できる
- **Agent 定義はエディタで一から書かない**。「役割・tools・禁止事項・出力フォーマット」の4要素を自然言語で伝えれば雛形が返る。2個目以降は「writer と同じ骨格で〇〇を作って」で1個目を踏襲した版が出る
- writer には Read / Write / Edit / Bash / Grep / Glob、reviewer には Read / Grep / Glob / Bash を渡す（Write と Edit を渡さないのが要点）。この権限分離も「書き換え権限は渡さないで」の1行で済む
- 呼び出しは `@` メンションが最も確実。自然言語で「writer に依頼して」と書くだけでもメインが委譲することが多い（公式表現は「typically」）。確実性を上げたい場面は `@` を使う
- reviewer の指摘を機械的に流さず、解釈はあなたが引き受ける。判断の手は残す
- 不便を感じたら役割を足す。先に増やさない
- 商業書では「組織導入」の章で扱われがちなサブエージェントを、本書は1人運用の入口として最小2体から組み立てた。仕組みを置く操作そのものがいつもの自然言語のプロンプトで完結する—ここが本章の一貫した主張です

---

writer + reviewer で「作る」と「確かめる」の2軸は手に入りました。次章は「3体目に何を足すか」の判断です。`researcher`（調べる人）か、`user`（エンドユーザー視点で検証する人）か、`devops`（インフラを触る人）か—役割追加には判断シグナルがあります。あなたの開発で何が詰まっているか、その症状から3体目を選ぶ章へ進みます。
