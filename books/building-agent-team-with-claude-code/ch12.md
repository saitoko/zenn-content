# 第12章 Claude Code の Plan mode と並列実行—実装前に検証する

1人で開発していると、設計の相談相手がいません。「この方針で本当に合っているか」という問いを自分だけで判断し、結論が出なければ手を動かし始めます。多くの場合、方針のずれは実装が終わってから気づきます。

この章では、この問いを潰す方法（Plan mode）と、実装を速くする方法（並列実行）を扱います。

一見すると別々のテーマですが、この2つを同じ章で扱うのには理由があります。**設計は慎重に検証してから、実装は分担して速く**——この章の結論を先に言うと、Plan mode で設計を固め、その設計を並列実行で一気に片づける、という組み合わせが1人開発で最も効くからです。前半で2つの仕組みを個別に押さえ、後半でその合流点を扱います。読み終えたとき、あなたは「設計と実装を分ける」運用と、独立した作業を並列展開して時間を縮める運用を、自分の開発フローに組み込める状態になっています。

---

## Claude Code の Plan mode とは何か

### 通常モードとの違い

Claude Code の通常モードでは、依頼を受けたエージェントはファイルの読み取りも書き込みも、コマンド実行も、その場で実行します。「実装して」と言えば実装まで一気に進みます。速い反面、方針を確認するタイミングがありません。

**Plan mode** は、この流れを途中で止めるモードです。Plan mode に入ったエージェントは、コードベースを調べ、何をどう変更すべきかという **計画（プラン）を立てるところまで** で手を止めます。ファイルの書き込みやコマンド実行といった、状態を変える操作はしません。読み取りと調査だけを行い、「こういう手順で実装します」という計画をあなたに提示します。

| | 通常モード | Plan mode |
|---|---|---|
| 調査・読み取り | する | する |
| 計画の提示 | 省略されがち | 必ず提示する |
| 書き込み系ファイル操作・状態変更コマンド | その場で実行 | しない（承認まで保留） |
| 読み取り系コマンド（ls・find 等） | する | する |
| 向く場面 | 小さく明確な変更 | 影響範囲が広い・方針を固めたい変更 |

言い換えると、Plan mode は「いきなり手を動かさず、まず設計図を引いてもらう」モードです。設計図を見て納得してから実装に進めるので、方針のずれを実装前に潰せます。

（なお、上の表の挙動は私が2026年6月時点で確認したものです。仕様は更新されることがあるため、最新の正確な動作は公式ドキュメントで確認してください。）

### Plan mode の使い方

2026年6月時点では、Plan mode への入り方は主に2つです。

**1. キーボードで切り替える**

入力欄で Shift + Tab を押すと、Claude Code の動作モードが順に切り替わります（押すたびに動作モードが循環し、その中に Plan mode が含まれます）。Plan mode に入ると、入力欄付近にモード名が表示され、以降の依頼は計画立案として扱われます。

**2. 自然言語で頼む**

モードを明示的に切り替えなくても、「実装する前に、まず計画を立てて見せてください」「いきなり書き換えず、変更方針を提案だけして」と頼めば、計画提示を先行させられます。本書が一貫して伝えてきたとおり、ここでも特別な構文は不要です。


### Plan mode の承認・修正フロー—ファイル無変更での軌道修正

Plan mode の本質は、計画提示と実装のあいだに **あなたの承認** を挟む点にあります。流れはこうです。

1. **計画を依頼する**: Plan mode で「〇〇機能を追加したい」と伝える
2. **計画が返る**: エージェントが関連ファイルを調査し、「どのファイルをどう変えるか・どの順で進めるか・テストはどうするか」を手順として提示する
3. **計画を検証する**: あなたが計画を読む。方針が違えば「この部分は別のアプローチにして」と修正を依頼する。計画段階での修正はファイルを一切変えていないので、コストがほぼゼロです
4. **承認して実装に移る**: 計画に納得したら「この計画で実装を進めて」と承認する。ここで初めてファイル書き込みが始まります

このフローのうれしさは、3の「検証」と「修正」がノーリスクである点です。通常モードでは、方針のずれに気づくのは実装が終わってからでした。Plan mode では、まだ1文字も書き換えていない計画の段階で軌道修正できます。

「確認を挟むぶん、かえって遅くなるのでは」と感じるかもしれません。多忙なソロ開発者ほど、この懸念は当然です。しかしコストを並べると逆になります。計画段階の修正は会話1往復で済みます。一方、実装後に方針のずれが見つかると、変更済みファイルの巻き戻しと再実装がセットでかかります。承認のひと手間は、この重い手戻りを買い取る保険です。レビュー時間を取りにくい人ほど、安いほうのコストを先に払う意味があります。

> **事例: 実装が走り出してから止めた話**
>
> 私が既存の認証まわりに機能を足そうとしたとき、通常モードだと関連ファイルを次々書き換え始めました。途中で「想定と違うモジュールを触っている」と気づいて止めたものの、すでに数ファイルが変更済みで、戻すのに手間がかかりました。正直に言えば、私が一番こたえたのは、こうして手戻りで消えていった時間でした。限られた開発時間のなかで、それは思った以上に重い損失です。Plan mode で同じ依頼をやり直すと、最初に「この3ファイルをこの順で変更する」という計画が返ってきました。そこで「認証は別モジュールに分けたいので、新規ファイルを足す方針にして」と1文で直せました。実装が始まる前なので、修正は会話だけで済みます。

## 並列実行—Claude Code に複数の作業を同時に任せる

### Claude Code の並列実行とは

Claude Code の並列実行は、以下のような構造で動きます：

```
メインClaude Code
├── サブエージェントA（ファイル1を変更）
├── サブエージェントB（ファイル2を変更）
└── サブエージェントC（テストを実行）
         ↓ 全部同時に動く
   結果だけメインに返ってくる
```

ではその設計が固まったあと、実装はどう速くするか。ここで効くのが **並列実行**——メインの Claude Code が別のサブエージェントを起動し、複数の作業を同時に走らせる仕組みです。

> **用語メモ**
>
> この仕組みは Agent ツール（旧称 Task、2026年6月時点で両方動作）を使います。ドキュメントでは Agent/Task という名称で登場します。

ポイントは、メインの Claude Code が **複数のサブエージェントを同時に起動できる** ことです。各サブエージェントは独立したプロセス・独立したコンテキストで動き、結果だけをメインに返します。互いに依存しない作業であれば、1件ずつ順番に処理するより、まとめて並列に投げたほうが待ち時間が短くなります。

ここで判断軸を1つ持っておくと役立ちます。**作業が互いに独立しているか** です。

- **独立している**（あるファイルの変更が別ファイルの変更結果に依存しない）→ 並列に向く
- **依存している**（前の作業の結果を受けて次を決める）→ 順次のほうが安全

### 1人開発での活用例

並列実行が効く場面を、1人開発の文脈で2つ挙げます。

**例1: 複数ファイルへの独立した変更を並列展開する**

たとえば「全コンポーネントのファイル冒頭に、同じ形式のライセンスコメントを追加する」「3つの独立したユーティリティ関数に、それぞれ別々の機能を足す」といった作業です。各ファイルの変更が互いに影響しないなら、メインに「この3ファイルの変更を並列で進めて」と頼めます。

```
src/utils/ の date.ts・currency.ts・string.ts に、
それぞれ以下の関数を追加してください。各ファイルは独立しているので
並列で進めてかまいません。

- date.ts: formatRelativeDate（相対時刻表記）
- currency.ts: formatJPY（円表記、3桁区切り）
- string.ts: truncate（指定文字数で省略）
```

メインがこれを受けて、独立した変更を並列のサブエージェントに割り振ります。1件ずつ順に処理する場合と違い、待ち時間をまとめられます。私の場合、上のような独立した3ファイルの変更を並列にしたとき、1件ずつ順に頼んだときの体感でおよそ半分の待ち時間で全部が返ってきました。どれだけ縮むかは、各作業の規模やコンテキスト量、API のレート制限によって変わるため一概には言えませんが（私の数字もあくまで体感です）、独立した作業の件数が多いほど効果が出やすくなります。

**例2: 複数のテストを並列で実行する**

「フロントエンドのテストとバックエンドのテストを別々に走らせて、両方の結果を見たい」「3つのパッケージそれぞれで `npm test` を回したい」といった場面です。互いに独立したテストスイートなら、並列に実行して結果をまとめて受け取れます。

```
packages/api・packages/web・packages/shared の3つで、
それぞれ npm test を並列に実行し、失敗したテストだけ
パッケージごとにまとめて報告してください。
```

## Plan mode とサブエージェントの組み合わせ

Plan mode と並列実行は、組み合わせると最も効果が出ます。代表的なのが **「設計は Plan mode で固め、実装はサブエージェントへ委任する」** パターンです。

なお、ここからは第7章で用意した「実装役」（writer）と「検証役」（reviewer）の2つのサブエージェントを前提に進めます。**第7章を読んでいなくても本章は追えます**——writer はコードを実装する担当、reviewer は書かれたコードを批判的に検証する担当です（用意の手順は第7章を参照してください）。

### 設計から検証までの4ステップ

流れはこうです。

1. **Plan mode で設計を固める**: メインの Claude Code に Plan mode で「〇〇機能を追加したい」と依頼し、変更計画を立てさせる。あなたが計画を検証・修正し、承認する
2. **計画を実装単位に分ける**: 承認した計画を、独立した作業単位に分割する。「この3ファイルの変更」「このテストの追加」のように、互いに依存しない塊にする
3. **実装をサブエージェントに委任する**: 独立した単位を writer サブエージェントに割り振る。writer は、コードを書く役割を与えた専用サブエージェントです（第7章で、役割を記述した定義ファイルを置いて用意したもの。手元にまだなければ「コードを実装する担当」として臨時に依頼してもかまいません）。独立した単位どうしであれば並列に展開できる
4. **reviewer で検証する**: 実装が返ってきたら reviewer に「変更されたファイルをレビューして」と依頼し、品質ゲートを通す。reviewer は、書かれたコードを批判的に検証する役割を与えた専用サブエージェントです（同じく第7章で用意。実装した writer とは別プロセス・別コンテキストで動くので、身内びいきのない目で見られるのが利点）

### 役割が分かれることの利点

このパターンの利点は、**設計の検証と実装の実行が、別々の役割・別々のタイミングに分離される** ことです。メインが設計の全体像を持ち、writer が実装に集中し、reviewer が批判的に検証する。1人で全部を頭の中で同時に抱える必要がなくなります。

> **設計の判断はあなたが握る**
>
> 自動化が進むほど、設計の承認を惰性で通したくなります。しかし Plan mode の価値は「承認の手前で立ち止まれる」点にあります。計画が返ってきたら、少なくとも「どのファイルを触るか」「なぜその順序か」の2点は自分の目で確認してください。承認を機械的に押すなら、Plan mode を使う意味が薄れます。

## 「設計と実装を分ける」効果—1人でも設計レビューができる

ここまでの話を、1人開発という文脈で言い直します。

### 1人開発に欠けがちな設計レビュー工程

チーム開発では、実装に入る前に設計をレビューする工程があります。設計ドキュメントを書き、レビュアーが「この方針で進めていいか」を確認してから実装に移ります。手戻りを実装前に潰すための、コストの安い検証です。

1人開発では、この設計レビュー工程が抜け落ちがちです。レビュアーがいないので、頭の中で設計して、そのまま手が動き始めます。方針のずれは、たいてい実装が終わってから気づきます。

### Plan mode で設計レビュー工程を取り戻す

**Plan mode は、この設計レビュー工程を1人でも持てるようにする仕組みです。** Claude Code が立てた計画を、あなたがレビュアーとして検証する——役割が反転しているだけで、構造は設計レビューと同じです。「実装する自分」と「設計を検証する自分」を、Plan mode という境界で切り分けられます。第7章で実装役の writer と検証役の reviewer を別プロセスに分けたのと同じ発想を、設計フェーズに持ち込んだものだと考えてください。

そして、計画が承認されたあとの実装は、サブエージェントへの委任と並列実行で速くする。**「設計は慎重に・検証してから、実装は分担して速く」** という、チーム開発では当たり前のリズムを、1人でも再現できます。

## 「あなたの開発では」—まず1回、設計を先に見る

明日から使える判断基準: 影響範囲が2ファイル以上に及ぶ変更 → Plan mode。独立した作業が3件以上 → 並列実行。この2つを覚えるだけで十分です。

この章の内容を実際の開発に当てはめるなら、最初の一歩はこれです。

**次に影響範囲の広い変更をするとき、いきなり実装させず「まず計画だけ見せて」と頼む**

たとえば「既存のAPIにエンドポイントを1本足す」「状態管理の仕組みを差し替える」「複数の React コンポーネントをまたいで共通フックに切り出すリファクタをする」といった、複数ファイルに波及する変更のときです。日々のフロントエンド開発でいえば、明日一番手を付けたくない「影響範囲が読みきれない変更」がまさにこれにあたります。通常モードなら即座に書き換えが始まるところを、「実装する前に変更計画を提案して」と一言添えるだけで、設計を検証する余地が生まれます。計画を読んで違和感があれば、ファイルが1つも変わっていない段階で直せます。

並列実行のほうは、発火の目安をはっきり持っておきましょう。基準はシンプルに **「1件あたり5分以上（体感）かかる独立した作業が、3件以上たまったとき」** です。このタイミングで「これらは独立しているので並列で進めて」と頼みます。逆に、数秒で終わる小さな修正が数件あるだけなら、順番に頼むほうが安く速い。サブエージェントを複数起動する分のコスト（トークン消費）がかかるからです。これを下回るうちは順次でよく、超え始めたら並列を試す。なお、この5分という数字は私が個人開発で感じた目安であって、実測に基づく統計値ではありません。慣れたら自分の作業の中身に合わせて基準を上下させれば十分です。

> **並列はAPIのレート制限に注意**
>
> 1人で複数のサブエージェントを同時に起動すると、その分だけAPIへのリクエストが集中します。レート制限（一定時間あたりのリクエスト上限）に当たると、サブエージェントの実行が待たされ、件数によっては順次実行より遅くなることもあります。「並列にすれば必ず速い」わけではなく、同時に走らせる本数が多いほど制限に当たりやすい——この点も頭の片隅に置いて、まずは3件前後から試すのが無難です。

設計を先に固める運用も、慣れてから判断すれば十分です。理屈のうえでは、手戻りが減るほど、確保しにくい作業時間あたりの前進量は大きくなります。とくに副業などで時間が限られている人ほど、この効き目は体感しやすいはずです——少なくとも私自身は、手戻りで消えた時間が、限られた開発時間のなかで一番こたえました。

そして実際に設計レビュー工程が手元に戻ってくると、変わるのは時間だけではありません。「この方針で大丈夫か」という不安を抱えたまま手を動かす、あの落ち着かなさが消えます。検証済みの設計図があれば、次の feature ブランチを迷いなく切れる——この身軽さを一度体感すると、行き当たりばったりの実装にはもう戻れません。

## 章末まとめ

- **Plan mode** は、実装に進む前に「変更計画」を立てさせて止まるモード。書き込み系ファイル操作や状態を変えるコマンドはせず（読み取り・調査は行う）、計画提示までで手を止める
- 入り方は Shift + Tab のモード切り替え、または「実装前に計画を見せて」と自然言語で頼む方法（キー操作はバージョンで変わるため `/help`・公式ドキュメントを正典に）
- 計画は「検証 → 修正 → 承認 → 実装」の順で進める。修正は計画段階ならノーリスク
- **並列実行**（`Agent` ツール、旧称 `Task`）は、独立した複数の作業を同時に走らせる仕組み。独立した複数ファイル変更・複数テスト実行で待ち時間を縮める
- ただし並列はコストがかかる。「1件あたり5分以上 × 独立した作業3件以上」をいったんの基準に、それを超えたときだけ使う
- Plan mode で設計を固め、実装をサブエージェントに委任・並列展開するのが最も効く組み合わせ
- Plan mode は1人開発に「設計レビュー工程」を取り戻す仕組み。設計は慎重に、実装は分担して速く、というリズムを1人でも再現できる
- 明日の「影響範囲が広い変更」で試してみよう。いきなり実装させず「計画を見せて」の1文から始める

【今すぐ試せる行動セット】
1. 次に「複数ファイルをまたぐ変更」をするとき、「実装前に変更計画を見せて」と1文追加する
2. 「同じ変更を3ファイル以上に」するとき、「並列で進めて」と添える
3. どちらか1回試したら、所要時間の変化をメモする（計測することで次の判断基準が生まれる）
