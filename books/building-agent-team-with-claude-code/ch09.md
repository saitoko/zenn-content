# 第9章 委任プロトコル—指示書の5要素

writer と reviewer を置いて、いざ呼び出してみる。ところが返ってきた成果物が、思っていたものと違う。スコープ外まで書き換えられている、欲しかった形式で返ってこない、確認してほしかったファイルを見ていない——サブエージェントを使い始めた直後に、多くの人がこの壁に当たります。

原因の大半はサブエージェントの能力ではなく、依頼の仕方です。同じ writer に同じ作業を頼んでも、指示の組み立て方ひとつで成果物の質が変わります。この章では、サブエージェントへの委任を安定させる「指示書の5要素」を扱います。読み終えたとき、あなたは「なんとなく頼んで、なんとなく違うものが返ってくる」状態から、「狙った成果物が返ってくる依頼文」を組み立てられる状態になっています。

---

## なぜ「指示の質が成果の質を決める」のか

サブエージェントは、メインのセッションとは独立したプロセスで動きます。第7章で見たとおり、サブエージェントはメインのやり取りを引き継ぎません。依頼時に明示的に渡した情報だけを手元に、ゼロから作業を始めます。

ここが、同じセッション内で「続けてこれもやって」と頼むのと決定的に違う点です。メインのセッションには、それまでの会話の文脈——どのファイルを触っていたか、何を直そうとしていたか、なぜこの設計にしたか——が蓄積されています。あなたが「これ直して」と一言頼んでも、メインは直前の文脈を補って動けます。

サブエージェントにはその文脈がありません。「これ直して」だけを渡すと、「これ」が何を指すか、「直す」のゴールがどこか、何をしてよくて何をしてはいけないか——すべてをサブエージェント側が推測することになります。推測が当たれば良い成果物が返り、外れれば見当違いの成果物が返ります。

> **委任は「文脈ごと手渡す」作業**
>
> 私がサブエージェント運用を始めた頃、最初の数週間は成果物のブレに悩みました。原因を振り返ると、頭の中にある文脈を言葉にせず、自分にとっての「当たり前」を省いて依頼していたことに尽きます。人間の同僚なら職場の共通認識で補える省略が、文脈を共有しないサブエージェントには通じませんでした。委任を「作業を投げる」ではなく「文脈ごと手渡す」と捉え直してから、成果物のブレが目に見えて減りました。

委任の質を安定させるとは、この「推測に委ねる部分」をできるだけ減らすことです。そのために、依頼文へ最低限含めるべき要素を型として持っておきます。

---

## 指示書の5要素

サブエージェントへの委任は、次の5要素を含めると安定します。

| 要素 | 何を伝えるか | 省くとどうなるか |
|------|------------|----------------|
| 1. 背景 | なぜこの作業が必要か | スコープを取り違える・本質と違う部分を直す |
| 2. ゴール | 何を成果物として受け取りたいか | 「どこまでやれば完了か」がブレる |
| 3. 制約 | やってはいけないこと | スコープ外の変更・想定外の副作用が起きる |
| 4. 参照情報 | 読むべきファイル・ドキュメント | 既存規約を無視した成果物が返る |
| 5. 成果物フォーマット | 何をどの形式で返すか | 受け取ったあと自分で整形し直す手間が出る |

第7章で扱った「Agent 定義に含める4要素（役割・tools・禁止事項・出力フォーマット）」と混同しないでください。あれは**サブエージェントを一度作るときの定義**で、`.claude/agents/<name>.md` に書きます。この章の5要素は**毎回の委任ごとに渡す指示**です。定義は役割の常設ルール、委任はその場の作業依頼、という関係になります。

順に見ていきます。

### 1. 背景—なぜこの作業が必要か

「何をするか」の前に「なぜするか」を1〜2文添えます。背景があると、サブエージェントは作業の目的に沿った判断ができます。

たとえば「`date-format.ts` の `formatRelativeDate` を修正して」だけだと、サブエージェントは関数の何が問題なのか分かりません。「ユーザーから『投稿時刻が未来になる』というバグ報告があり、原因が `formatRelativeDate` のタイムゾーン処理にあると分かった」と背景を添えると、修正の方向（タイムゾーン処理を直す）が定まります。背景は、作業が脇道に逸れたときに「目的に照らして正しいか」を判断する錨になります。

### 2. ゴール—何を成果物として受け取りたいか

「どうなったら完了か」を具体的に書きます。ゴールが曖昧だと、サブエージェントは「ここまでで十分か、もっとやるべきか」を判断できません。

「テストを追加して」ではなく「タイムゾーンをまたぐ3ケース（UTC・JST・日付変更線付近）のテストを追加し、全ケースが pass する状態にして」と書きます。完了条件が観測可能な形（テストが pass する）で示されていると、サブエージェント自身が「ゴールに達したか」を確認できます。

### 3. 制約—やってはいけないこと

スコープの境界と禁止事項を明示します。サブエージェントは、頼まれた以上のことを「親切のつもり」でやることがあります。制約は、その善意の暴走を止める柵です。

- 「`formatRelativeDate` 以外の関数は触らない」
- 「ついでのリファクタリングをしない」
- 「依存パッケージを追加しない（必要なら提案として返す）」

第7章で扱ったとおり、Agent 定義の禁止事項にも同種のルールを書けます。定義側に常設の禁止事項を置き、委任側にはその作業固有の制約を置く、と使い分けます。

### 4. 参照情報—読むべきファイル・ドキュメント

サブエージェントが作業前に読むべきファイルを明示します。これを省くと、サブエージェントは既存コードの規約を知らないまま実装し、プロジェクトのスタイルから外れた成果物を返しがちです。

- 「既存の時刻処理は `src/utils/time.ts` に集約されている。まずこれを読んで方針を合わせて」
- 「命名規則は `CLAUDE.md` の『コーディング規約』節に従って」

参照先を渡すと、サブエージェントは推測ではなく実物を根拠に判断できます。第8章で触れた researcher のような調査役には、参照情報の指定が特に効きます。

### 5. 成果物フォーマット—何をどの形式で返すか

返してほしい形を指定します。フォーマットを指定しないと、返ってきた成果物を自分で整形し直すことになります。

- 「変更ファイル一覧・追加テスト概要・動作確認手順の3点を箇条書きで返して」
- 「レビュー指摘は 🔴 必須 / 🟡 推奨 / 🟢 良い点 の3段階で分類して」

フォーマットを揃えておくと、複数のサブエージェントの成果物を並べて比較するときにも扱いやすくなります。

## 5要素を適用した委任の例

第7章で作った writer と reviewer に、実際に5要素を適用してみます。`.claude/agents/writer.md` と `.claude/agents/reviewer.md` が置いてある前提です。

### writer への委任

```
@"writer (agent)" formatRelativeDate のバグを修正してください。

# 背景
ユーザーから「投稿時刻が『3時間後』のように未来表示になる」とバグ報告があった。
原因は formatRelativeDate のタイムゾーン処理で、UTC と JST の差を二重に補正している。

# ゴール
- 投稿時刻が正しく「X分前」「X時間前」と過去表示される
- タイムゾーンをまたぐ3ケース（UTC・JST・日付変更線付近）のテストを追加し、全ケース pass

# 制約
- formatRelativeDate と、そのテストファイル以外は触らない
- ついでのリファクタリングはしない
- 依存パッケージは追加しない（必要なら提案として返す）

# 参照情報
- 既存の時刻処理方針は src/utils/time.ts を読んで合わせる
- 命名・テスト配置は CLAUDE.md のコーディング規約に従う

# 成果物フォーマット
変更ファイル一覧 / 修正の要点 / 追加テスト概要 / 動作確認手順 の4点を箇条書きで返す
```

依頼文が長く見えるかもしれませんが、書くのはバグ報告を受けた直後の1回だけです。この型を一度作っておけば、次回からは背景とゴールを差し替えるだけで使い回せます。

### reviewer への委任

```
@"reviewer (agent)" 今 writer が修正した formatRelativeDate をレビューしてください。

# 背景
タイムゾーン二重補正のバグ修正。マージ前の品質ゲートとして見てほしい。

# ゴール
バグが再発しない実装になっているか・テストが修正の証明になっているかを判定する

# 制約
- ファイルは書き換えない（指摘のみ）
- 修正案を押し付けず、選択肢として提示する

# 参照情報
- 変更は formatRelativeDate とそのテストファイル
- 既存の時刻処理規約は src/utils/time.ts

# 成果物フォーマット
🔴 必須 / 🟡 推奨 / 🟢 良い点 の3段階で指摘を分類する
```

5要素のうち「成果物フォーマット」と一部の「制約」は、すでに `reviewer.md` の定義側にも書かれています。定義側に常設ルールがあるなら、委任側では省いても構いません。**定義に書いてあることは毎回繰り返さなくてよい**——これが定義と委任を分けておく利点です。委任文には、その作業に固有の背景・ゴール・参照情報だけを書けば済みます。

## 指示が曖昧だとどうなるか

5要素を省いた委任が、どんな成果物を生むかを1つの例で見ます。次の依頼を考えます。

```
@"writer (agent)" date-format.ts のバグを直しておいて。
```

背景（どのバグか）・ゴール（どうなれば完了か）・制約（どこまで触ってよいか）・参照情報・フォーマット、すべてが欠けています。サブエージェントは文脈を持たないので、この一言から推測で動きます。起こりがちな結果は次のようなものです。

- **取り違え**: `date-format.ts` には複数の関数がある。サブエージェントは「バグっぽい」と判断した別の関数を直してしまう。本来直したかった `formatRelativeDate` は手つかずのまま
- **スコープ超過**: ついでに「コードが古い」と判断し、ファイル全体を今風の書き方にリファクタリングする。差分が膨れ上がり、レビューが困難になる
- **規約違反**: 既存の時刻処理が `src/utils/time.ts` に集約されていることを知らず、`date-format.ts` 内に独自のタイムゾーン処理を書き足す。プロジェクトの方針から外れる
- **再整形コスト**: 「直しました」とだけ返ってきて、何をどう変えたか分からない。結局 diff を自分で読んで把握し直すことになる

> **事例: 「いい感じに直して」が生んだ余計な差分**
>
> 私が一度やってしまった失敗です。細かく書くのが面倒で、サブエージェントに「このファイル、いい感じに直しておいて」と頼みました。返ってきたのは、頼んだ覚えのない関数まで含めたファイル全体の書き換えでした。サブエージェントとしては「いい感じに」を最大限解釈した結果で、悪気はありません。曖昧な指示は、サブエージェントに「良かれと思って」の余地を与えすぎます。背景・ゴール・制約の3つだけでも書いておけば防げた手戻りでした。

曖昧な指示は、楽をしているようでいて、返ってきた成果物の確認・差し戻し・再依頼で結局時間を失います。5要素は、その往復を最初の依頼文に前払いしておく仕組みです。

## あなたの開発では

5要素をすべて毎回フルで書く必要はありません。作業の重さに応じて要素を取捨します。判断の目安はこうです。

**軽い作業（タイポ修正・1行の変更）**: ゴールと制約だけで足ります。「この typo を直す。他は触らない」で十分です。背景もフォーマットも要りません。

**中くらいの作業（バグ修正・小機能の追加）**: 背景・ゴール・制約の3つを書きます。参照情報は、既存規約に揃える必要があれば足します。この章の writer への委任例が、この粒度です。

**重い作業（設計を伴う実装・複数ファイルにまたがる変更）**: 5要素すべてを書きます。特に参照情報を厚くします。読むべきファイルを具体的に指定するほど、推測が減り、成果物が安定します。

迷ったら、まず背景・ゴール・制約の3つを書く習慣をつけてください。この3つは、作業の重さによらず効果が大きい要素です。参照情報とフォーマットは「あると成果物が整う」要素で、軽い作業では省けます。

そして——第7章と同じ原則ですが——この委任文そのものを Claude Code に下書きしてもらうこともできます。「formatRelativeDate のバグを writer に委任したい。5要素（背景・ゴール・制約・参照情報・フォーマット）の形で依頼文を組み立てて」とメインに頼めば、型に沿った依頼文の叩き台が返ります。それを確認して投げる、という運用が一番省力です。

運用が成熟してくると、この「下書きを頼む」ステップすら不要になります。`CLAUDE.md` に「サブエージェントへの委任は必ず5要素の形式で行う」と書いておけば、メインセッションが自律的に5要素を埋めた委任文を組み立て、あなたへの確認を挟んだ上でサブエージェントを呼ぶようになります。その段階では、あなたは委任文を自分で書きません。かわりに「メインセッションが組み立てた委任文の5要素が正しく揃っているか」を確認する目を持つことが、品質の歯止めになります。本章で5要素を体で覚えておく意味は、まさにここにあります。

## 章末まとめ

- サブエージェントはメインの文脈を引き継がない。委任は「作業を投げる」ではなく「文脈ごと手渡す」作業として組み立てる
- 委任の指示書には5要素を含める—**背景・ゴール・制約・参照情報・成果物フォーマット**
- 第7章の「Agent 定義の4要素」は役割の常設ルール、この章の5要素は毎回の作業依頼。定義に書いた制約・フォーマットは委任で繰り返さなくてよい
- 曖昧な指示は「取り違え・スコープ超過・規約違反・再整形コスト」を招く。楽に見えて往復で時間を失う
- 作業の重さで要素を取捨する。軽い作業はゴールと制約だけ、重い作業は5要素すべて。迷ったら背景・ゴール・制約の3つを書く
- 委任文の下書きも Claude Code に頼める。型に沿った叩き台を作らせて確認・投下するのが省力

---

5要素を押さえると、サブエージェントへの委任が安定します。ここまでの第3部で、最小2体構成・3体目の選び方・委任プロトコルという「役割で動かす」基礎が揃いました。第4部では、繰り返す作業を自動で発火させる Hooks をはじめ、2026年6月時点の最新機能を1人開発の文脈で扱っていきます。
