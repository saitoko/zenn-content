# 第13章 失敗のリアル—Claude Code を1人で使うと踏む地雷

Claude Code を1人で回していると、開発はむしろ快適です。AI が即座にコードを返し、自分のペースで進められる——その手応えのなかで、私は何度か足をすくわれました。チーム開発なら誰かのレビューで止まったはずの失敗が、1人運用では別の目を通らずにそのままコミットへ進むからです。「自分は確認しているから大丈夫」と思っているときほど、検証の網に穴が空いていました。

この章では、私自身が Claude Code を1人で運用するなかで踏んだ3つの地雷を扱います。3つの地雷はいずれも、1人運用という本書のテーマに合わせて私自身の運用観察から選んだ整理です。いずれもエンジニア向けに「失敗談」としてではなく「設計上の判断基準」として並べ直します。読み終えたとき、あなたはこの3つの地雷を「自分もいつか踏む前提」で、最初から設計に織り込めるようになります。

なお、前章までを読み飛ばして本章に入っても困らないよう、参照する仕組み（`CLAUDE.md`・スラッシュコマンド・writer/reviewer の2体構成）は本章内でも要点を一言ずつ添えます。

---

## 失敗を「設計」に変える

1人運用の失敗には共通する構造があります。AI の出力をそのまま信頼したこと、権限を絞らずに渡したこと、消えては困る情報を揮発する場所に置いたこと——この3つです。

これらは「気をつける」では防げません。気をつけても、忙しい日には必ず手を抜きます。防ぐ方法は、失敗が起きにくい構造を最初から作っておくことです。以下、3つの事故を順に扱います。1つ目と2つ目は「なぜ起きるか→どう設計し直すか」の順で、3つ目は実務で効く順番に合わせて「先に対策→あとで根拠」の形で見ていきます。

---

## 地雷1: Claude Code が存在しないライブラリの API を書く

最初の地雷は、ハルシネーション（もっともらしい嘘の生成）です。Claude Code に限らず、生成 AI は「存在しない関数・引数・メソッド」を自信を持って書くことがあります。

> **事例: 通らないはずのコードが「正しそう」に見えた**
>
> 個人プロダクトで日付処理を実装してもらったとき、Claude Code はあるライブラリのヘルパー関数を呼ぶコードを返しました。引数の渡し方も自然で、コメントまで付いていて、いかにも正しそうでした。私はそのままコミットしかけました。実行すると `TypeError: xxx is not a function`。そのライブラリにはその関数が存在しませんでした。AI は似た名前の実在 API から類推して、ありそうな関数を「合成」していたのです。

### なぜ起きるか（ハルシネーション）

生成 AI は確率的に「次に来そうなトークン」を選びます。実在する API と存在しない API の境界を、AI 自身は明確には区別していません。ハルシネーションが起きやすいと感じた場面を挙げます。

- マイナーなライブラリや、バージョン差で API が変わったライブラリを使うとき
- 学習データの時点より新しいバージョンの仕様を尋ねたとき
- 「ありそうだが実際にはない便利関数」を期待させる依頼をしたとき

いずれも「学習データに十分な実例がない領域を、それらしく埋めようとする」点が共通します（なお、ここに挙げたのは私が運用で踏んだ範囲の観察であって、発生確率を測ったものではありません）。厄介なのは、出力が**自然で正しそうに見える**ことです。明らかに変なコードなら気づけますが、ハルシネーションは「動きそうな顔」をしています。

### 設計変更: 生成コードは「ドキュメントか実行」で必ず裏を取る

対策は「AI の出力を信頼するかどうか」という心構えの話にしません。**検証を作業フローに組み込みます**。

1. **外部 API・ライブラリ呼び出しを含むコードは、実行（またはテスト）で必ず通す**。型が通るだけでは不十分です。実際に呼び出すテストを1つ書き、走らせて初めて「実在する」と確認できます
2. **見慣れない関数名が出たら、公式ドキュメントで実在を確認する**。これは Claude Code 自身に「この関数は実在しますか。公式ドキュメントの該当箇所を示してください」と聞き返すのが速いです
3. **`CLAUDE.md`（プロジェクト全体のルールを書く設定ファイル。第2章）に「実装後はテスト実行まで含めて完了とする」と書く**。完了の定義に「実行確認」を入れておくと、AI が型チェックだけで終わらせにくくなります

第7章で作った reviewer（コードを読んでレビューする専任のサブエージェント）に「外部 API 呼び出しが実在するか確認して」と観点を渡しておくのも有効です。書く AI と確かめる AI を分けておくと、ハルシネーションを2段構えで止められます。

## 地雷2: Claude Code の reviewer に書き換え権限を渡したら勝手に実装を修正した

2つ目は、権限設計の地雷です。第7章では、サブエージェント定義ファイルの `tools` フィールドに渡すツールを書き並べることで権限を分離できる、と扱いました。ここでは「その分離をサボると何が起きるか」を事故として整理します。

> **事例: 取り違えた修正が diff に無言で混ざる**
>
> この権限設計をサボった具体的な顛末は、第5章「読むだけの役に書き込み権限を渡した結果」で書いたとおりです（reviewer に tools を書かず全ツールを渡し、指摘リストと同時に該当ファイルを Edit で書き換えられた一件）。本章で踏み込みたいのは、その事故の「被害の出方」です。書き換えられた diff の中に、指摘の趣旨を取り違えた変更が1つ混じっていました。私がそれに気づいたのは数コミットあと——いったんマージされた修正を特定して巻き戻す手戻りが発生しました。レビューと修正を同じエージェントに同居させると、壊れたときの被害は「指摘の質」ではなく「無言で入った変更」として、しかも遅れて出てきます。これが、権限を絞らなかったことの本当のコストです。

### なぜ起きるか（権限設計）

サブエージェントは、渡された権限の範囲を使い切るように振る舞います。Write / Edit（ファイルを書き換えるツール）を持っていれば、指摘だけで止まらず書き換えにまで手を伸ばすことがあります。これは AI が意図や善意を持っているという話ではありません（LLM は確率的に次のトークンを選んでいるだけで、内心があるわけではありません）。ただ、振る舞いだけを外から見ると——あくまでメタファーとして言えば——「善意の暴走」のように映る、ということです。

1人運用では、この暴走を止める人がいません。チームなら「勝手に直すな」と誰かが言いますが、1人だと書き換えられた diff をそのままマージしてしまいます。レビューと修正が混ざり、「何を承認したのか」が曖昧になります。

### 設計変更: 役割で tools を絞る—読む人に書く権限を渡さない

対策は権限の最小化です。レビューする役割には、読み取り系のツールだけを渡します。

- **reviewer に渡す**: Read / Grep / Glob / Bash（ファイルを読み、検索し、テストやビルドを走らせて確認する。Bash は読み取り・実行確認のために渡し、書き換えはさせない）
- **reviewer に渡さない**: Write / Edit（書き換えは一切させない）

この `tools` の組み合わせは、第7章の reviewer 雛形（`tools: Read, Grep, Glob, Bash`）と同じです。本章でも雛形をそのまま踏襲しているので、両方を見比べても食い違いはありません。この設計だけで「レビューのつもりが勝手に直された」事故は構造的に起きなくなります。reviewer は Edit を持っていないので、物理的に書き換えられません。指摘の解釈はあなたが引き受け、修正は writer に依頼する——役割の境界が権限で固定されます。

そして、この権限設定はエディタで `tools` 行を手書きする必要すらありません。メインの Claude Code に「reviewer には書き換え権限を渡さないでください」と1行添えれば、`tools` から Write と Edit が外れた定義が返ってきます。第7章で「設計の意図を文章で渡せば構文への変換はメインが吸収する」と書いたのは、まさにこの操作のことです。**権限分離は気合いではなく構造で担保する**——これが2つ目の設計判断です。

## 地雷3: Claude Code のコンテキストを圧縮しすぎて前の指示が消えた

3つ目は状態管理の地雷です。長いセッションで会話履歴が詰まってくると、`/compact`（会話履歴を要約して圧縮するスラッシュコマンド）や `/clear`（会話履歴をすべて消すスラッシュコマンド。どちらも第3章で扱いました）でコンテキストを軽くします。ここに落とし穴があります。

> **事例: 「あれ、さっき決めた方針はどこ？」**
>
> 長時間の実装セッションで応答が遅くなってきたので `/compact` で要約をかけました。その後の実装で、Claude Code はセッション序盤に合意したはずの設計方針——「この層では例外を握り潰さず上位に投げる」というルール——を無視したコードを書き始めました。要約の過程でその決定が落ちていたのです。私は決定が生きている前提で進めていたので、しばらく気づけませんでした。

この地雷は、対策が先にわかっているほうが手を動かしやすい種類のものです。原因をたどると最後は「セッションは消える」という一点に着地するので、3つ目は**先に対策を出してから、なぜそれで効くのかを補強**する順で進めます。

### 設計変更: 消えては困る情報は外部ファイルに固定する

結論はシンプルです。状態の置き場所を「揮発する場所」と「永続する場所」に分けます。

- **プロジェクト全体で守るルール** → `CLAUDE.md` に書く。セッションをまたいで毎回読み込まれるので、圧縮で消えません
- **エージェントの恒久的な行動指針** → `.claude/agents/<name>.md` に書く（第7章で作ったサブエージェント定義ファイル）。サブエージェント起動時に必ず適用されます
- **セッション中に固めた設計方針** → `/compact` や `/clear` をかける前に、メモやファイルに書き出す

実務上の習慣として、**圧縮・リセットの前にひと呼吸置く**ことを勧めます。「今のセッションで決めたことのうち、次も効いていないと困るものは何か」を自分に問い、それを `CLAUDE.md` か作業メモに書き出してから `/compact` を打ちます。

### なぜそれで効くか—手元で1回試せば体感できる

対策の根拠は `/compact`・`/clear` の挙動にあります。`/compact` は会話履歴を要約して圧縮する操作で、何を残すかは要約の粒度しだいです（`/clear` は全消去）。私が試したかぎりでは、ファイルに書かれず会話の流れの中にしか存在しない決定ほど、圧縮で落ちやすいと感じました。これは手元で確かめられます——`/compact` をかける前にセッション内だけで決めたルールを1つ用意しておき、圧縮後に「さっき決めた○○のルールは何だったか」と訊き返してみてください。答えが曖昧になったり別の内容に化けたりすれば、それがこの地雷の起き方です（`/compact`・`/clear` の挙動そのものは第3章で扱ったとおりです）。

問題の本質は、**重要な決定をセッションという揮発する場所にしか置いていなかった**ことです。セッションはステートレスで、圧縮やリセットで消えます。だから対策は「消えないファイルに先に移す」一択になります。長いセッションを続けるほど十分に起こりうる地雷なので、痛い目を見る前に習慣化しておくのが安全です。第3章で「消えては困る情報は先に書き出してから `/clear` する」と書いたのは、この経験が下敷きになっています。

## 3つの地雷に共通する設計思想

3つの事故は別々に見えて、根は同じです。一言にすれば——**「検証されていない信頼を、いま自分はどこに置いているか」**。地雷1は AI の出力を確かめずに、地雷2はサブエージェントの判断を権限で縛らずに、地雷3はセッションという消える場所を永続する場所と思い込んで——いずれも「確かめていない信頼」を放置していた点で共通します。対策の方向もひとつに揃います。信頼の置き場所を、確かめる仕組みか、消えない場所へ移し替える。これだけです。

- **AI の出力を無条件に信頼しない**（地雷1: 検証をフローに組み込む）
- **権限は役割に必要な最小限に絞る**（地雷2: 読む人に書かせない）
- **消えては困る状態は外部に固定する**（地雷3: 揮発する場所に預けない）

1人運用では、これらを「気をつける」で守ろうとすると必ず破綻します。疲れている日、急いでいる日に手を抜くからです。だからこそ、検証ステップ・権限設定・ファイルへの書き出しという**構造**に変換します。構造にしておけば、あなたの集中力が切れている日でも地雷が作動しません。

### 踏む直前に鳴らすトリガー

構造はわかった、では「いつ」発動させるか。設計思想を「症状」と紐づけておくと、忙しい日でも手が勝手に動きます。次の感覚が走った瞬間が、対策を打つ合図です。

| こう感じた瞬間（症状） | いま打つ手（対策） |
|---|---|
| 「この関数、たぶん実在する」と確かめずに信じかけた | テストで1回だけ呼ぶ。または Claude Code に「公式ドキュメントの該当箇所を出して」と聞き返す（地雷1） |
| 「指摘するより直してもらったほうが速い」と reviewer に期待した | それは reviewer に Write を渡しているサイン。tools から Write / Edit を外す（地雷2） |
| セッションが重くなって `/compact` に指が伸びた | 押す前に「次も効いていてほしい決定」を `CLAUDE.md` か作業メモへ書き出す（地雷3） |

トリガーが「気をつける」より強いのは、抽象的な心構えではなく具体的な引き金に対策が結びついているからです。引き金を引いた自覚さえあれば、判断を毎回ゼロから組み立てずに済みます。

## 「あなたの開発では」—踏む前に仕込んでおく

設計思想は読んだだけでは効きません。いま開いているプロジェクトに当てはめて、手を動かして初めて構造になります。次の3つは、本を閉じる前の5分でそのまま実行できます。ここだけは流さず、エディタを開きながら読んでください。

**1つ目（いま `CLAUDE.md` を開く）: 完了の定義に「実行確認」を入れる。** たとえば次の1行を足すだけです。

```markdown
## 完了の定義
- 実装はテスト（または実際の呼び出し）が通って初めて「完了」とする。型チェックだけで完了にしない
```

次にコードを生成させた瞬間から、ハルシネーション由来のコードがコミットに紛れる確率が下がります。あとで、ではなく、次のプロンプトの前に効かせられます。

**2つ目（いま reviewer の定義ファイルを開く）: tools に Write / Edit が混ざっていないか確認する。** `.claude/agents/reviewer.md` の冒頭フロントマターを見て、`tools` 行が次の形になっているかだけ確かめます。

```yaml
tools: Read, Grep, Glob, Bash   # Write / Edit が無いこと
```

混ざっていたら「reviewer から書き換え権限を外して」とメインに頼むだけ。この30秒を惜しむと、次のレビューで「勝手に直された diff」をマージしてしまうかもしれません。確認は、事故が起きる前の今しかできません。

**3つ目（次に長いセッションを閉じる時から）: `/compact` の前に書き出す癖をつける。** 圧縮の前に、自分にこう問いを投げます——**「今決めたことで、次のセッションでも効いていないと困るものは何か」**。挙がったものを `CLAUDE.md` か作業メモに移してから `/compact` を打つ。まだ `/compact` で痛い目を見ていない今だからこそ、ノーコストで習慣にできます。一度手戻りを経験してから始めるのでは、すでに一度払ったあとです。

## 章末まとめ

- 1人運用の失敗は3つとも「確かめていない信頼の放置」に行き着く。気合いではなく構造で防ぐ
- 構造の中身は3つ——生成コードは実行/ドキュメントで裏を取る（地雷1）、レビュー役に Write / Edit を渡さない（地雷2）、消えては困る決定は `/compact`・`/clear` の前にファイルへ逃がす（地雷3）
- 地雷は「いつか踏むかも」ではなく「踏む前提」で設計に織り込む。一度の事故を、二度と起きない構造へ変える

---

地雷を踏まない構造が見えてきたところで、次に向き合うのは「お金」の話です。第14章では、Pro / Max 各プランの月額と、1人開発でそれぞれが投資として正当化できる境界——コストと ROI の考え方を扱います。構造で事故を防ぐのと同じく、コストも「感覚」ではなく「境界線」で判断する章へ進みます。
