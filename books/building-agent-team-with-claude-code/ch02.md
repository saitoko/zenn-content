# 第2章 `CLAUDE.md` を書く—プロジェクト記憶という発想

Claude Code を起動するたびに「このプロジェクトは TypeScript strict モードです。テストは Vitest。コミットメッセージは英語で」と毎回説明していませんか。あるいは、チームの規約とは違うスタイルでコードを提案されることに気づいていますか。

この問いの解決策が `CLAUDE.md` です。プロジェクトルートに置くこのファイルは、Claude Code が起動のたびに読み込む「プロジェクト記憶」として機能します。

この章では、`CLAUDE.md` が何をしてくれるか・どこに置くか・最小限の内容から始める書き方・育てていく方法を扱います。読み終えたとき、あなたは自分のプロジェクトに最初の `CLAUDE.md` を置ける状態になっています。

---

## `CLAUDE.md` とは何か

### プロジェクト記憶という概念

Claude Code のセッションはステートレスです。セッションを終了すると、その中でやり取りした内容は次回に引き継がれません。「前回こう決めたから今回もそれで」という文脈を、Claude Code は自分では持てません。

`CLAUDE.md` は、この問題に対する解答です。

- プロジェクトルートに `CLAUDE.md` というファイルを作る
- Claude Code は起動時にこのファイルを自動で読み込む
- ファイルに書かれた内容は、セッション全体のシステムプロンプトの一部として機能する

つまり `CLAUDE.md` は「このプロジェクトについて、毎回 Claude Code に伝えることをまとめたファイル」です。毎回説明し直す手間が消え、プロジェクトのルール・方針・文脈が常に有効な状態で作業が始まります。

### どこに置くか—読み込み階層

`CLAUDE.md` は複数の場所に置けます。読み込みの優先順位は以下の通りです。

```
~/.claude/CLAUDE.md          # ユーザーグローバル設定（全プロジェクト共通のルール）
<project-root>/CLAUDE.md     # プロジェクト固有の設定（最もよく使う）
<subdirectory>/CLAUDE.md     # サブディレクトリ固有の設定
```

**最初は `<project-root>/CLAUDE.md` だけで始める**のが実用的です。

`~/.claude/CLAUDE.md`（ユーザーグローバル）には「自分が常に好む書き方の方針」を書けます。「すべてのプロジェクトで、コードの説明は日本語で返して」といった内容です。プロジェクトごとに違うルールが必要なら、各プロジェクトルートの `CLAUDE.md` に書きます。

---

## 最小テンプレート

空の `CLAUDE.md` より、「最小限の4項目を書いたもの」から始める方が効果がすぐ体感できます。以下は最小テンプレートです。

```markdown
# プロジェクト概要

このリポジトリは [プロジェクト名] です。[1〜2文の説明]

# 技術スタック

- 言語: TypeScript 5.x / Node.js 20.x
- フレームワーク: Next.js 14
- テスト: Vitest
- パッケージ管理: pnpm

# コーディング規約

- TypeScript の strict モードを有効にしている
- 関数コンポーネント以外では React を使わない
- テストファイルは `src/` 直下の対象ファイルと同じディレクトリに `*.test.ts` として置く
- コミットメッセージは英語、Conventional Commits 形式（feat: / fix: / chore: 等）

# 禁止事項・注意事項

- `package.json` への依存パッケージ追加は、提案として返すこと（勝手に追加しない）
- セキュリティ上の理由から、シークレットや API キーをコードにハードコードしない
- 型エラーを `any` で隠蔽しない。適切な型を探す
```

このテンプレートのポイントは「Claude Code が判断に使う情報」に絞っている点です。コーディング規約をここに書いておくと、ファイルを生成・変更するたびに規約チェックが暗黙的に走ります。「禁止事項」を書いておくと、エージェントが暴走する前に踏み止まる手がかりになります。

## 書くべき内容・書かなくてよい内容

`CLAUDE.md` を育てていくにあたって、「何を書くか」の判断基準を示します。

### 書くべきもの

**プロジェクト固有の前提（外部から見えないもの）**

- プロジェクトの目的・ターゲットユーザー
- 技術スタックとバージョン
- ディレクトリ構成の意図（「`lib/` は汎用ロジック、`features/` は機能別」など）
- 社内・チーム固有の命名規則

**繰り返し確認されていること**

「コミットを出す前に lint を通してほしい」と毎回書いているなら、`CLAUDE.md` に1行書くと解消します。

**依存関係・外部サービスの制約**

「本番環境では PostgreSQL を使っているが、テスト環境は SQLite」「外部 API はモックを使う」など、Claude Code が推測できない制約。

**禁止事項**

サブエージェントに対しても有効です。「このプロジェクトでは〇〇はやらない」を書いておくと、エージェントへの委任時に改めて伝えなくて済みます。

### 書かなくてよいもの（書くと逆効果になるもの）

**公式ドキュメントと変わらない一般ルール**

「TypeScript では型を書く」「null チェックを忘れずに」——Claude Code は当然知っています。書いても効果がなく、ファイルが膨らんで読みにくくなります。

**毎回変わる情報**

「現在の作業は〇〇機能の追加」——これは `CLAUDE.md` に書かず、セッション開始時のプロンプトで伝えます。

**長すぎる文書**

`CLAUDE.md` は毎セッションのコンテキストを消費します。長すぎると他の作業に使えるコンテキストが減ります。数百行を超えてきたら、重要度の低い項目を削るか、詳細を別ファイルに分離して `CLAUDE.md` から参照する形を検討します。

> **「何を書くか」は Claude Code に聞ける**
>
> 書くべき内容に迷ったとき、Claude Code 自身に壁打ちできます。プロジェクトの特徴（使っている言語・フレームワーク・チームのルール等）を伝えると、典型的な `CLAUDE.md` の内容を提案してくれます。「`/init` を実行して自動生成する」方法もありますが（第3章で紹介します）、口頭で特徴を説明しながら対話的に作る方法も有効です。
>
> また「この内容、`CLAUDE.md` に書くべきか？」という問いにもそのまま答えてくれます。「毎回同じことを伝えているが、これは `CLAUDE.md` に入れるべきか、それともセッション開始時のプロンプトで十分か」——判断に迷ったときの確認相手として使えます。

## `CLAUDE.md` を育てる—Playbook として使う

`CLAUDE.md` は最小テンプレートから始め、使いながら育てるのが実用的です。

### 「毎回伝えていること」を移植する

Claude Code を数セッション使うと、「いつも最初に伝えること」がパターンとして見えてきます。それをそのまま `CLAUDE.md` に移植します。

具体的な例：

- 「エラーが出たら、まず原因を説明してから修正案を出して」→ `CLAUDE.md` の「行動方針」節に追加
- 「変更前に対象ファイルを必ず Read してから書き始めて」→ 「禁止事項・注意事項」節に追加
- 「テストを書くときは境界値のケースを必ず含めて」→ 「コーディング規約」節に追加

### 「事故が起きたとき」に更新する

Claude Code が思ったと違う挙動をしたとき、その原因が「ルールが伝わっていなかった」なら `CLAUDE.md` に追記します。

> **事例: 命名規則の混乱**
>
> 私がプロジェクトで経験した例です。コンポーネントファイルを作成してもらったところ、命名が `camelCase` と `PascalCase` で混在していました。既存コードが混在していたためです。「新規コンポーネントは PascalCase、ユーティリティ関数ファイルは camelCase」というルールを `CLAUDE.md` に1行追加したところ、それ以降の生成物で混乱がなくなりました。

### Playbook として使う

プロジェクトが複雑になってきたとき、`CLAUDE.md` に細かいルールをすべて書くより、「Playbook」ファイルに分離して参照させる方法があります。

```markdown
# ルール一覧

詳細なコーディングルールは `.claude/playbooks/coding.md` を参照してください。
デプロイ手順は `.claude/playbooks/deploy.md` を参照してください。
```

このように参照元を `CLAUDE.md` に書いておくと、Claude Code は必要に応じてその Playbook ファイルを読みに行きます。すべての情報を1ファイルに詰め込まず、用途別に管理できます。

第9章（委任プロトコル）では、サブエージェントへの指示書（Playbook）の書き方をさらに詳しく扱います。

## サブディレクトリの `CLAUDE.md`

大きなモノレポや、フロントエンド・バックエンドが同じリポジトリに入っている構成では、サブディレクトリごとに `CLAUDE.md` を置けます。

```
my-repo/
├── CLAUDE.md                    # プロジェクト全体のルール
├── frontend/
│   ├── CLAUDE.md                # フロントエンド固有のルール（React/Tailwind等）
│   └── src/
└── backend/
    ├── CLAUDE.md                # バックエンド固有のルール（Go/Postgres等）
    └── cmd/
```

Claude Code は作業対象のファイルに近い方の `CLAUDE.md` を優先して参照します。「フロントエンドのコードを触るとき」と「バックエンドのコードを触るとき」でルールセットを切り替えられます。

## 「あなたの開発では」—今日やること

この章の内容を実際の開発に当てはめる場合、最初のステップは次の1つです。

**自分のプロジェクトに `CLAUDE.md` を置き、技術スタックと禁止事項だけ書く**

完璧に書こうとしないことが重要です。「Node.js 20、テストは Jest、`package.json` は勝手に変えない」——この3行だけでも、次のセッションから毎回説明するコストが消えます。

次のセッションで「`CLAUDE.md` に書いていないのにいつも伝えていること」が出てきたら、その都度追記します。`CLAUDE.md` は書き上げるものではなく、使いながら育てるものです。

副業でプロダクトを作っている場合や、複数プロジェクトを掛け持ちしている場合は、`~/.claude/CLAUDE.md` に「どのプロジェクトでも共通する自分のスタイル」を書いておくと、プロジェクト固有の `CLAUDE.md` をシンプルに保てます。

---

## 章末まとめ

- `CLAUDE.md` はプロジェクトルートに置くファイル。Claude Code が起動時に毎回読み込む「プロジェクト記憶」として機能する
- まず「プロジェクト概要・技術スタック・コーディング規約・禁止事項」の4項目で始める
- 書くべきは「プロジェクト固有の前提」と「繰り返し伝えていること」。一般的なプログラミングルールは書かなくてよい
- `CLAUDE.md` は書き上げるのではなく、使いながら育てる。「毎回伝えていること」を移植し、「事故が起きたとき」に更新する
- 大きなプロジェクトは Playbook ファイルを別に作り、`CLAUDE.md` から参照する
- サブディレクトリごとに置けるので、モノレポや複数スタックの構成にも対応できる
- ファイルが長くなりすぎるとコンテキストを消費する。重要度の低い記述は定期的に削る

---

`CLAUDE.md` が整うと、「プロジェクトの文脈を覚えているセッション」で作業できます。次に覚えたいのは、よく使う操作を素早くコントロールする手段です。

長いセッションを続けると、コンテキストが詰まってくる感覚が出てきます。そのとき何をするか、繰り返し使う作業をコマンドとして登録する方法——第3章はスラッシュコマンドとカスタムコマンドを扱います。
