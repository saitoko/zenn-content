# 第5章 サブエージェントの仕組み—`.claude/agents/<name>.md`

第4章で「1体だけで使うと限界が来る」ことを確認しました。では、役割を持った別のエージェントを実際に置くには、何をどこに書けばいいのでしょうか。サブエージェントは魔法の仕組みではなく、リポジトリの中に1枚のテキストファイルを置くだけで動きます。

この章では、そのファイル——`.claude/agents/<name>.md`——の構造を、フィールドごとに分解して説明します。どこに置くか、何を書くか、なぜ権限を絞るのか、どのモデルを割り当てるか、どう呼び出すか。読み終えたとき、あなたはサブエージェント定義ファイルを「読んで理解できる」状態になります。実際に2体を置いて動かすのは第7章ですが、その前にこの章で「部品の地図」を手に入れておきます。

---

## `.claude/agents/` ディレクトリの役割

Claude Code は起動時に、いくつかの決まった場所を読みに行きます。第2章で扱った `CLAUDE.md`、第3章で扱った `.claude/commands/`、そしてこの章で扱う `.claude/agents/` です。

`.claude/agents/` は「このプロジェクトで使えるサブエージェントの定義置き場」です。このフォルダに `reviewer.md` というファイルを1枚置けば、Claude Code は起動時にそれを読み込み、「reviewer という名前のサブエージェントが使える」と認識します。フォルダがなければ自分で作ります。

```
your-repo/
├── CLAUDE.md                    # プロジェクト全体のルール（第2章）
├── .claude/
│   ├── commands/                # カスタムコマンド（第3章）
│   │   └── pre-commit.md
│   └── agents/                  # サブエージェント定義（本章）
│       ├── reviewer.md
│       └── researcher.md
└── src/
```

1ファイル = 1サブエージェントです。`reviewer.md` が reviewer エージェント、`researcher.md` が researcher エージェントになります。ファイルを増やせば役割が増え、減らせば役割が減る——この素直さが、サブエージェントが「重い仕組み」ではない理由です。

これらのファイルは `.claude/` 配下にあるので、Git でバージョン管理できます。チーム開発なら他のメンバーと共有でき、1人開発でも「自分のエージェント構成」をリポジトリの履歴として残せます。

## 定義ファイルのフォーマット

サブエージェント定義ファイルは、**YAML フロントマター + Markdown 本文**という2層構造です。`CLAUDE.md` や `.claude/commands/` のファイルと同じ発想です。

```markdown
---
name: reviewer
description: コードレビュー・実装検証を行う品質ゲートエージェント
tools: Read, Grep, Glob, Bash
model: sonnet
---

あなたはコードレビュアーです。実装を批判的に読み、改善点を指摘します。
コードは読みますが、書き換えはしません。

（以下、行動指針・受け取るもの・渡すものを書く）
```

上半分（`---` で囲まれた部分）がフロントマター、下半分が本文です。この2つは役割がはっきり分かれています。

### フロントマター—4つのフィールド

フロントマターは「このエージェントのメタ情報」を宣言します。基本となるフィールドは4つです。

| フィールド | 役割 | 注意点 |
|---|---|---|
| `name` | 呼び出し時に使う識別子 | ファイル名と一致させる（`reviewer.md` なら `name: reviewer`） |
| `description` | 何をするエージェントかの一行説明 | メインの Claude Code が「どの役割に任せるか」を判断する材料になる |
| `tools` | このエージェントに渡すツールのカンマ区切りリスト | 必要なものだけ渡す（後述） |
| `model` | 使用するモデル | 役割の重さに合わせて使い分ける（後述） |

`name` と `description` は、メインの Claude Code が「この依頼は誰に振るべきか」を判断するときに読まれます。特に `description` は重要で、ここが曖昧だと、メインが適切なサブエージェントを選べません。「コードレビューを行う」より「writer が書いた実装を批判的にレビューし、マージ前の品質ゲートとして機能する」のように、いつ・何のために呼ばれるかが分かる説明を書きます。

### 本文—システムプロンプト

フロントマターの下に書く Markdown 本文は、そのサブエージェントの**システムプロンプト**になります。つまり「このエージェントは、どういう人として、どう振る舞うか」を定義する指示書です。

ここに書くのは、普通の業務指示書だと考えて構いません。「あなたは何をする人か」「どんな手順で進めるか」「何を受け取り、何を返すか」「何をやってはいけないか」——これらを自然な日本語で書きます。プログラミング言語の知識は不要で、新しい記法を覚える必要もありません。

本文の書き方の型（担当業務・行動指針・受け取るもの・渡すもの・禁止事項）は、実際に writer と reviewer を組み立てる第7章で具体的に扱います。この章では「本文 = システムプロンプト」という対応関係だけ押さえておけば十分です。

## `tools` フィールド—権限を絞るという設計思想

4つのフィールドの中で、1人開発に最も効くのが `tools` です。ここはやや踏み込んで説明します。

### tools に書くもの

`tools` には、そのサブエージェントに渡すツールをカンマ区切りで列挙します。Claude Code の主なツールは次のとおりです。

| ツール | できること |
|---|---|
| `Read` | ファイルを読む |
| `Write` | ファイルを新規作成・上書きする |
| `Edit` | 既存ファイルの一部を書き換える |
| `Bash` | シェルコマンドを実行する |
| `Grep` | ファイル内容を検索する |
| `Glob` | ファイル名のパターン検索をする |

このほか `WebSearch`・`WebFetch`（Web 検索・取得）などもあります。

### 「何も書かない」と全部渡る

`tools` フィールドを省略すると、そのサブエージェントには**全ツールが渡されます**。一見すると楽ですが、これは推奨しません。理由は「権限を持つほど、間違った操作の影響が大きくなる」からです。

最も分かりやすい例が、レビュー役のエージェントです。レビューは「読んで指摘する」仕事であって、「書き換える」仕事ではありません。それなのにレビュー役に `Write` や `Edit` を渡してしまうと、レビューの最中に、指摘するだけで済むはずのコードを勝手に書き換えてしまうことがあります。

> **事例: 読むだけの役に書き込み権限を渡した結果**
>
> 私が個人プロジェクトで初めてレビュー役のエージェントを置いたとき、面倒だったので `tools` を省略し、全ツールを渡しました。最初のレビュー依頼で、そのエージェントは指摘リストを返したあと、ご丁寧に該当ファイルを `Edit` で書き換えていました。その書き換えには「指摘の趣旨を取り違えた修正」が混じっていて、これが厄介でした。指摘をどう反映するかは私が判断すべきことで、それをエージェントに勝手にやらせてしまったのが設計ミスです。翌日、定義ファイルの `tools` から `Write` と `Edit` を外したところ、そのエージェントは読むことに集中するようになりました。

### 必要なものだけ渡す

この経験から導かれる原則はシンプルです。**役割に必要なツールだけを渡す**。

- **実装する役**（コードを書く）→ `Read, Write, Edit, Bash, Grep, Glob`（`Write` が必須）
- **レビューする役**（読んで指摘する）→ `Read, Grep, Glob, Bash`（`Write` と `Edit` を渡さない）
- **調べる役**（情報を集める）→ `Read, Grep, Glob, WebSearch, WebFetch`（書き込み不要）

これは、人間のチームで「閲覧権限」と「編集権限」を分けるのと同じ発想です。読むだけの役に編集権限を渡さなければ、その役が誤ってファイルを壊すことは構造的に起きません。`tools` フィールドは、その権限分離をファイル1行で表現する仕組みです。

なお、`tools` で渡していなくても、システムプロンプト本文に「〇〇はしない」と書く「運用ルール」での抑止も併用できます。ただし本文の禁止事項は「お願いベース」で、`tools` から外す「権限ベース」のほうが強い制約です。確実に止めたいものは `tools` で外す、と覚えておいてください。

## `model` フィールド—用途別モデルの使い分け

`model` フィールドは、そのサブエージェントが使う Claude のモデルを指定します。2026年6月時点で、エージェント定義に書ける主な値は次のとおりです。

| 指定値 | 性格 | 向いている役割 |
|---|---|---|
| `haiku` | 速くて安い。定型処理向き | 単純な集計・定型変換・短い確認作業 |
| `sonnet` | バランス型。標準的な実装・レビュー | writer・reviewer など日常的に使う役割 |
| `opus` | 最も賢い。重い判断・長文向き | 設計・方針決定・長い文章のレビュー |
| `inherit` | メインセッションと同じモデルを使う | 役割ごとに固定したくないとき |

モデルの正式名称や料金は変動するため、最新の対応値は公式ドキュメントを確認してください（2026年6月時点では上記の短縮名が使えます）。

使い分けの考え方は「役割の重さに合わせる」です。サブエージェントは独立したコストを消費するので、全部を最上位モデルにすると費用が膨らみます。一方、重い判断を軽いモデルに任せると品質が落ちます。

- **軽い定型作業**（変更ファイル一覧の整形、テスト結果の要約など）→ `haiku` で十分なことが多い
- **標準的な実装・コードレビュー**→ `sonnet` が基準
- **設計判断・大きな構造変更の検討・長い仕様書のレビュー**→ `opus` を割り当てる価値がある

> **事例: レビュー役のモデルを上げた判断**
>
> 私は普段、レビュー役を `sonnet` で動かしています。コードの細かい指摘はこれで十分だからです。ただ、設計そのものの妥当性を問いたいとき——「この抽象化は将来の変更に耐えるか」のような判断——は、一時的に `model` を `opus` に切り替えることがあります。日常は安いモデルで回し、判断の重い局面だけ上げる。この使い分けで、品質とコストの両方を成り立たせています。

`model` を省略した場合の挙動はバージョンによって変わります（メインのモデルを引き継ぐ、または既定モデルが使われる）。意図を明示したいときは、省略せず値を書いておくことを勧めます。

## 起動方法—メインセッションから呼び出す

定義ファイルを置いたら、メインの Claude Code から呼び出します。呼び出し方は2つあり、どちらも自然言語が基本です。新しいコマンド体系を覚える必要はありません。

### 方法1: `@` メンションで指名する

プロンプト入力欄で `@` を1文字入力すると、使えるサブエージェントが補完候補（タイプアヘッド）として表示されます。そこから `reviewer` を選んで、続けて普段どおりの依頼を書きます。

```
@reviewer 今変更した src/utils/date-format.ts をレビューしてください。
意図: 相対日付を返すユーティリティの追加です。
```

補完を使わず手で書く場合は `@agent-reviewer` という形式になります（`agent-` というプレフィックスが付く点に注意してください）。確実に特定のエージェントを呼びたいときは、この `@` メンションが最も確実です。

### 方法2: 自然言語で「〇〇に頼んで」と書く

`@` を使わず、文章の中に役割名を混ぜるだけでも呼び出せます。

```
reviewer に、今変更したファイルのレビューを頼んでください。
```

この場合、メインの Claude Code が各エージェントの `description` を見て、適切なサブエージェントへ自動的に委譲します。ここで先ほどの「`description` をしっかり書く」が効いてきます。説明が的確なほど、メインは正しい相手を選べます。

ただし、この自動委譲は「必ず」ではありません。公式の説明でも「典型的には委譲する（typically delegates）」という留保つきの表現になっています。確実に呼びたい重要な場面では方法1（`@` メンション）を、カジュアルに頼む場面や複数体を一気通貫で動かしたい場面では方法2を、と使い分けるのが現実的です。

いずれの方法でも、呼び出しは「コマンドを実行する」のではなく「いつものプロンプトに役割名を添える」操作です。サブエージェントの起動は、あなたがすでに知っている自然言語の延長線上にあります。

> **注記: 定義の反映にはタイミングがある**
>
> サブエージェント定義は、原則としてセッション開始時に読み込まれます。エディタや手作業で `.claude/agents/reviewer.md` を新規作成・編集した場合、反映には Claude Code のセッションを一度終了して再起動する必要があります。一方、`/agents` コマンド（管理 UI）から作成・編集した場合は即時反映されます。「ファイルを置いたのに `@` で候補に出てこない」というつまずきの多くは、この再起動忘れが原因です。

## ローカル vs グローバル—2つの置き場所

サブエージェント定義は、プロジェクト内とユーザー全体の2か所に置けます。`CLAUDE.md` やカスタムコマンドと同じ階層構造です。

| 配置場所 | 有効範囲 | 用途 |
|---|---|---|
| `<project>/.claude/agents/<name>.md` | そのプロジェクトのみ | プロジェクト固有の役割。Git で共有できる |
| `~/.claude/agents/<name>.md` | すべてのプロジェクト | どこでも使いたい自分専用の役割 |

判断の目安はこうです。

**プロジェクト固有の知識が必要な役割は、プロジェクト内（`<project>/.claude/agents/`）に置く。** たとえば「このリポジトリのアーキテクチャ規約に照らしてレビューする reviewer」は、そのプロジェクトの文脈と結びついています。リポジトリに含めれば Git で履歴が残り、構成を後から振り返れます。

**プロジェクトを問わず使いたい汎用的な役割は、ユーザーグローバル（`~/.claude/agents/`）に置く。** たとえば「コミットメッセージを整える役」「英文を校正する役」のように、どのプロジェクトでも同じように働く役割は、グローバルに1つ置けば全プロジェクトで使えます。

両方に同じ名前のエージェントがある場合は、プロジェクト内の定義が優先されます。「グローバルに汎用版を置き、特定プロジェクトだけ上書きする」という使い方も可能です。

1人開発で複数のプロジェクトを掛け持ちしているなら、**まずはプロジェクト内に置いて試し、「どのプロジェクトでも使っている」と気づいた役割だけグローバルに昇格させる**のが無駄のない進め方です。最初から全部グローバルに置くと、プロジェクトごとの違いを吸収できなくなります。

## コピペできる最小定義ファイル

最後に、そのまま置いて動く最小の定義ファイルを1つ載せます。読むことに集中する「レビュー役」の最小例です。`<project>/.claude/agents/reviewer.md` として保存してください。

```markdown
---
name: reviewer
description: 実装を批判的にレビューし、マージ前の品質ゲートとして機能する。コードは読むが書き換えない
tools: Read, Grep, Glob, Bash
model: sonnet
---

あなたはコードレビュアーです。変更されたコードを批判的に読み、改善点を指摘します。
コードは読みますが、書き換えはしません（書き換え権限は渡されていません）。

## 進め方

1. 変更されたファイルを Read で読む
2. ロジック・命名・テストの妥当性を検証する
3. 既存コードの規約に照らして、気になる点を指摘する

## 指摘の出し方

- 影響の大きい指摘から先に出す。タイポは最後
- 「読みにくい」ではなく「この関数は3つの責務を持つので分けるべき」と具体的に書く
- 修正案は押し付けず、選択肢として提示する

## やらないこと

- ファイルの書き換え（権限として渡されていない）
- 自分の好みだけを根拠にした指摘
```

このファイルを置き、セッションを再起動すれば、`@reviewer` で呼べるようになります。フロントマター4行と本文だけで、コードは1行も書いていません。これがサブエージェントの最小単位です。

実際にこのファイルを一から手で書く必要はありません。第7章で説明するとおり、メインの Claude Code に「reviewer というサブエージェントを作って。書き換え権限は渡さないで」と頼めば、こうした雛形を生成してくれます。この章の最小例は、生成された雛形を読んで「これでよさそうか」を判断するための見本だと考えてください。writer とセットになった完成版（🔴/🟡/🟢 の出力フォーマット付き）は第7章に載せます。

## 「あなたの開発では」—まず1枚置いて読んでみる

この章はファイルの構造を解説しましたが、一番早い理解は「実際に1枚置いて中身を眺める」ことです。

おすすめの最初の一歩は、メインの Claude Code に「このリポジトリ用に reviewer のサブエージェント定義を `.claude/agents/reviewer.md` として作って。書き換え権限は渡さないで、model は sonnet で」と頼んでみることです。生成されたファイルを開き、`tools` 行に `Write` と `Edit` が入っていないこと、`description` が「いつ呼ばれる役か」を説明していること、本文が普通の業務指示書になっていることを、自分の目で確認してください。

確認できたら、その定義を読みながら「自分のプロジェクトの規約を1行足すなら何を書くか」を考えてみます。たとえば「テストは Vitest で書く規約に照らして指摘して」のような一文です。フロントマターの意味と本文の役割が腹落ちすれば、第7章で writer + reviewer の2体を実際に動かす準備は整っています。複数プロジェクトを持っているなら、汎用的に使えそうな役割を1つだけ `~/.claude/agents/` に置いてみると、グローバル配置の効き目も体感できます。

## 章末まとめ

- サブエージェントは `.claude/agents/<name>.md` という1枚のテキストファイルで定義する。1ファイル = 1役割で、Git 管理できる
- ファイルは **YAML フロントマター（`name` / `description` / `tools` / `model`）+ Markdown 本文（システムプロンプト）** の2層構造
- `tools` は必要なツールだけを渡す。レビュー役に `Write` / `Edit` を渡さないなど、権限分離が1人開発の事故を構造的に防ぐ
- `model` は役割の重さに合わせる。日常は `sonnet`、定型作業は `haiku`、重い判断は `opus`（2026年6月時点の短縮名）
- 呼び出しは `@` メンション（確実）か、自然言語で「〇〇に頼んで」（カジュアル・自動委譲）。ファイル直編集後はセッション再起動が必要
- 置き場所はプロジェクト内（`<project>/.claude/agents/`）とユーザーグローバル（`~/.claude/agents/`）。固有の役割はプロジェクト内、汎用の役割はグローバル

ここまでで「サブエージェントをどう定義するか」という仕組みは手に入りました。残るのは「では、どんな役割を、何体置くべきか」という判断です。やみくもに役割を増やすと、かえって管理が重くなります。次章では、サブエージェントを1つ増やすかどうかを見極める4つの軸——反復性・専門性・非重複性・独立性——を扱います。
