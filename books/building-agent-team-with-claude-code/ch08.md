# 第8章 3体目に何を足すか—researcher / user / devops

新しいライブラリの仕様を調べはじめたら、気づけば API ドキュメントの読み込みでコンテキストが埋まり、肝心の実装に入る前にセッションが重くなって思考が散らかっていた——フロントエンドを1人で書いていると、こんな崩れ方に覚えはないでしょうか。Claude Code に writer + reviewer の2体を持たせて回していても、あるとき「この2体だけでは届かない作業」に出くわします。けれど、詰まるたびに役割を増やしていくと、すぐに5体・6体に膨らみ、どれを呼べばいいか分からなくなります。

この章で扱うのは「3体目を足すかどうか」の判断です。結論を先に言うと、**2体で足りているうちは足しません**。足すのは、特定の症状が繰り返し出てきたときだけです。読み終えたとき、あなたは「どんな詰まり方をしたら、どの役割を足すべきか」を症状から逆引きできる状態になっています。候補は researcher（調べる役）・user（ユーザー視点で検証する役）・devops（実行系を回す役）の3つで、それぞれの最小定義ファイルをそのまま使えるよう用意しました。

---

## 原則—2体で足りているうちは足さない

役割を増やすことには見えにくいコストがあります。

- **判断コスト**: 体が増えるほど「今の作業は誰に頼むか」を毎回考える手間が増えます
- **設計コスト**: 1体ごとに定義ファイル（システムプロンプト・tools・禁止事項）を保守する必要があります
- **形骸化リスク**: 「作ったけど月に1回しか呼ばない役割」は、定義が古びても気づかれず放置されます

第6章で、役割を増やすときの4つの軸を扱いました。念のため簡単に再掲すると、**反復性**（同じ詰まりが繰り返し出るか）・**専門性**（独立した観点や知識が要るか）・**非重複性**（既存の役割と仕事が被らないか）・**独立性**（メインの流れと切り離して任せられるか）の4つです。3体目の判断もこの4軸に乗ります。とくに効くのは**反復性**——「同じ詰まりが繰り返し出ているか」です。一度きりの困りごとなら、その場でメインの Claude Code に頼めば済みます。役割として固定するのは、その困りごとが**毎週のように再来する**ときだけです。

> **事例: 5体作って3体しか呼ばなかった話**
>
> 私は最初、便利そうな役割を先回りで5体作りました。researcher・user・devops に加え、ドキュメント専任とリリースノート専任です。1ヶ月後に呼び出し履歴を振り返ると、後の2体は一度も呼んでいませんでした。「あったら便利」で作った役割は、実際の詰まりに紐づいていないので呼ばれません。それ以降は「2週続けて同じ詰まりが出たら足す」というルールに切り替えました。

---

## 3体目を検討するシグナル—症状から逆引きする

3体目は「機能の名前」からではなく「自分の詰まりの症状」から選びます。次の表は、典型的な症状とそれに対応する役割の対応です。

| あなたの開発で起きている症状 | 足すべき3体目 |
|---|---|
| 新しいライブラリ・API の仕様を調べるのに毎回セッションが長くなり、本題の実装が後ろにずれる | researcher |
| 実装は通るが、ユーザーが実際に使うときの体験（エラーメッセージの分かりにくさ・導線の不自然さ）が抜け落ちる | user |
| テスト実行・ビルド・デプロイ確認のたびに手作業のコマンドを打っていて、その結果を読むのに時間が溶ける | devops |

ポイントは「writer でも reviewer でもやれなくはないが、毎回そこで詰まる」という症状が出ていることです。writer に調査をさせると実装の集中が切れ、reviewer にユーザー視点を求めると本来のコードレビューが薄まります。私の経験でも、reviewer に「ついでにユーザー目線も見て」と頼んだセッションでは、コードのバグ指摘が手薄になり、後から別のレビューで拾い直す羽目になりました。私が繰り返し観察したかぎりでは、**1つの役割に異質な観点を二重持ちさせると、どちらも精度が落ちやすい**——これが3体目を分離する根拠です。

逆に、これらの症状が出ていないなら3体目は不要です。たとえば普段から使い慣れたスタックだけで開発していて調査がほぼ発生しないなら、researcher を作っても呼ぶ場面がありません。

まずは、ここまでの表を自分の直近2週間に当てはめてみてください。「この症状、先週もあったな」と思い当たるものがあれば、それがあなたの3体目の最有力候補です。

---

## 候補1: researcher—調査を実装から切り離す

### どんなときに効くか

researcher は、コードベースの調査・外部情報（ライブラリのドキュメント・API 仕様・エラーの原因）の収集を専門にする役割です。writer に調査もさせると、調査で集めた大量の情報がそのまま実装セッションのコンテキストに残り、本題の実装判断が薄まります。researcher を分けると、調査は調査で完結し、writer には「調べた結論」だけが渡ります。

tools には読み取り・検索系を渡し、書き換え系（Write / Edit）は渡しません。調査役が勝手にコードを書き換える必要はないからです。外部情報を集める場合は `WebSearch` / `WebFetch` を加えます（2026年6月時点で利用可能なツールです）。

### 最小定義ファイル

```markdown
---
name: researcher
description: コードベース調査・外部情報収集を担当する調査エージェント
tools: Read, Grep, Glob, WebSearch, WebFetch
model: sonnet
---

あなたは調査担当です。コードの該当箇所・外部仕様・原因を調べ、
実装に必要な「結論」を簡潔に返します。コードは書き換えません。

## 担当業務
- 指定されたライブラリ・API の仕様、使い方、注意点の調査
- コードベース内で関連する実装・定義箇所の特定
- エラー・不具合の原因調査

## 行動指針
- 結論を先に1〜2文。詳細は箇条書きで補足する
- 出典（ドキュメントの URL・該当ファイルのパス）を必ず添える
- 推測と確認済みの事実を書き分ける（「未確認」を明示する）

## 渡すもの
- 調査結論 / 根拠（出典つき）/ 実装時の注意点 / 未確認の論点
```

調査結果に出典を添えさせるのは、後で writer が実装するときに「その情報が本当に正しいか」を追えるようにするためです。生成 AI が事実と異なる内容をもっともらしく出力する現象は「ハルシネーション」と呼ばれ、Anthropic も公式ドキュメントで対策の必要性に触れています。私自身も、存在しない API メソッドを researcher が自信たっぷりに提示してきた場面に何度か出くわしました。だからこそ、出典の有無が品質の歯止めになります。

## 候補2: user—エンドユーザー視点で出口を検証する

### どんなときに効くか

「動いた」のに、自分以外の誰かに使わせた瞬間につまずかれる——1人開発でいちばん見えにくいのが、この出口のズレです。user は、成果物を「作り手」ではなく「実際に操作するエンドユーザー」の視点で検証する役割です。reviewer がコードの内部品質（バグ・命名・テスト）を見るのに対し、user は**出口の品質**を見ます。エラーメッセージが利用者に伝わるか、CLI の出力が読みやすいか、ドキュメントが初見の人に分かるか——こうした「使う側の体験」は、コードが正しく動いているだけでは担保されません。

reviewer と user は観点が違うので別々に持つ価値があります。reviewer は「正しく動くか」、user は「使って気持ちよいか」を見ます。1人開発では後者が抜け落ちやすいので、出口品質を上げたいときに効きます。user も確認するだけの役割なので書き換え権限は渡しません。

### 最小定義ファイル

```markdown
---
name: user
description: エンドユーザー視点で成果物の出口品質を検証するエージェント
tools: Read, Grep, Glob
model: sonnet
---

あなたは成果物を「初めて使うエンドユーザー」として操作します。
作り手の前提を持たず、利用者がつまずく箇所を指摘します。

## 担当業務
- エラーメッセージ・CLI 出力・ドキュメントが利用者に伝わるかの検証
- 利用者が迷う導線・分かりにくい説明の指摘
- 「動くが使いにくい」箇所の洗い出し

## 行動指針
- コードの内部品質（バグ・命名）は見ない。それは reviewer の担当
- 「自分なら何が分からないか」を具体的に書く
- 指摘は「どこが・なぜ伝わらないか・どう変えると伝わるか」の順で書く

## 渡すもの
- 利用者がつまずく箇所のリスト / 改善案
```

user に「コードの内部品質は見ない」と明記しているのは、放っておくと reviewer と同じ指摘を返し始めて役割が重複するからです。第6章の**非重複性**の軸が、ここで効いています。

## 候補3: devops—実行系を分離する

### 先に注意—devops は最後に検討する

3候補のなかで、devops だけは導入を急がないでください。コマンド実行権限を持つぶん、他の2体より誤動作のコストが高いからです。まずは researcher と user で2体目・3体目を回し、それでも実行系の手間が無視できなくなってから足す——この順番を勧めます。

### どんなときに効くか

lint・型チェック・ビルド確認のたびに、同じコマンドを手で打ち、流れてくるログを目で追っている。私の場合、フロントエンドを1人で書いていると、この往復に地味な時間を取られていました。devops は、こうした**実行系の操作**を引き受ける役割です。writer に実装させながら毎回テストも回させると、コマンドの出力（数百行のログ）が実装セッションに流れ込み、コンテキストを圧迫します。devops を分けると、実行と結果の読み取りは devops の中で完結し、writer には「テストは何件通って何件落ちた、落ちた原因はこれ」という要約だけが返ります。

devops は実行系なので `Bash` が中心です。テストやビルドを走らせるためにコマンド実行権限は必須なので、本書の入門段階では「読み取り + Bash」に絞ります。デプロイのように元に戻しにくい操作まで任せたくなったら、その手前であなた自身の承認を挟む設計にしてください。CI/CD への踏み込み（GitHub Actions の設定など）は、この役割が安定してから少しずつ広げれば十分です。

### 最小定義ファイル

```markdown
---
name: devops
description: テスト実行・ビルド・実行結果の要約を担当するエージェント
tools: Read, Grep, Glob, Bash
model: sonnet
---

あなたは実行系の担当です。テスト・ビルド・型チェックを実行し、
結果を要約して返します。コードの修正は writer に委ねます。

## 担当業務
- テスト・lint・型チェック・ビルドの実行
- 実行結果の要約（通過/失敗の件数、失敗の原因の特定）
- ログの中から「次に直すべき箇所」を抽出する

## 行動指針
- 生ログを全文貼らない。結論（件数・原因）を先に要約する
- 失敗したら「原因の仮説」までは書くが、実装の修正はしない
- 本番デプロイなど不可逆な操作は、実行前に必ず確認を求める

## 禁止事項
- アプリケーションコードの書き換え（修正は writer に委ねる）
- 承認なしの本番環境への操作
```

devops に「生ログを全文貼らない」と書いているのは、この役割の存在価値が「実行結果のノイズをメインから切り離すこと」だからです。要約せずにログをそのまま返すなら、わざわざ役割を分ける意味が薄れます。

---

## 「あなたの開発では」

3体目を決めるとき、まず先週・先々週の自分の作業を思い出してください。「同じ種類の詰まりで2回以上時間を溶かした」場面があれば、それが3体目の候補です。調査で実装が後ろ倒しになったなら researcher、動いたのに使いにくくて手戻りしたなら user、テスト結果の読み取りに毎回時間を取られたなら devops です。

3つ全部を一度に作る必要はありません。最も頻度の高い症状に対応する1体だけを足し、しばらく運用してから次を検討してください。私の場合、新しい役割を足すと最初の数日は物珍しさで呼びがちで、それが実際の詰まりに紐づいているかは2〜3週間ほど回さないと見えてきませんでした。だから「次を足すかどうか」の判断はそれくらいの期間を置いてからにしています。個人開発では、役割は「あったら便利」で増やすと形骸化します。「これがないと毎週詰まる」という痛みに紐づいたものだけが、実際に呼ばれて働きます。

定義ファイルは、第7章と同じく自然言語で生成できます。「researcher というサブエージェントを作って。tools は Read / Grep / Glob / WebSearch / WebFetch、書き換え権限は渡さないで」とメインの Claude Code に頼めば、本章の最小定義に近い雛形が返ってきます。本章のファイルは、その出力を確認するための見本として使ってください。

---

## 章末まとめ

- **2体で足りているうちは3体目を足さない**。Claude Code の役割を増やすと判断・設計・形骸化のコストがかかる
- 3体目は「機能名」ではなく「繰り返し出る症状」から選ぶ。一度きりの困りごとは役割化しない
- **researcher**: 調査が実装を後ろ倒しにするとき。読み取り + Web 検索系、書き換え権限なし
- **user**: 動くが使いにくい、出口の体験が抜けるとき。reviewer（内部品質）とは観点が違う
- **devops**: テスト・ビルドの実行とログ読み取りに時間が溶けるとき。実行結果を要約して返す
- まず1体だけ足し、2〜3週間ほど運用して呼ばれ方を見極めてから次を検討する

---

役割を足したら、次に効いてくるのは「その役割にどう仕事を頼むか」です。同じ researcher でも、渡す指示の質で返ってくる調査結果の精度は大きく変わります。次章では、サブエージェントへの委任を安定させる「指示書の5要素」を扱います。
