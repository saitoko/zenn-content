# 第1章 CLAUDE.md——ルールを書く場所ではなく、読まれる仕組みを設計する場所

Claude Code を使い始めて最初に触れる「渡せる場所」が CLAUDE.md だ。プロジェクトのルートに置いたこのファイルは、Claude がセッションを始めるたびに自動で読み込まれる。だからここに「日本語で応答すること」「コミット前にブランチを確認すること」と書けば、その通りに動いてくれる——というのが、多くの人が最初に抱く期待だと思う。

私もそう思っていた。そして半分は当たっていて、半分は外れていた。

本章で伝えたいことを先に書く。**CLAUDE.md は「ルールを書けば効く場所」ではなく、「ルールが読まれる仕組みを設計する場所」だ。** 書いただけでは効かない。私のプロジェクトの CLAUDE.md は本体が75行、そこから参照される役割別ルールファイル4本（`.claude/rules/` 配下）と合わせると合計375行になる（2026年5月31日時点、`wc -l` 実測）。この375行は、最初から375行だったわけではない。ルールを書くたびに「書いたのに守られない」現象にぶつかり、そのたびに「どう書けば守られるのか」を設計し直した結果が、今の構造だ。

念のため先に断っておく。本章には375行のCLAUDE.mdや9体のエージェントといった、やや大きめの数字が出てくる。だが、ここで扱うのは規模の話ではなく仕組みの話だ。**CLAUDE.md が15行でも375行でも、エージェントが2体でも9体でも、「書いたルールが本当に読まれ、守られるか」という問いは変わらない。** 規模が小さければ問題が起きないわけではなく、むしろ小さいうちに仕組みを設計しておくほうがずっと楽だ。あなたのプロジェクトの CLAUDE.md が数行しかなくても、この章の話はそのまま当てはまる。

この章では、その設計の中身を解剖する。具体的には次の5つを扱う。

1. CLAUDE.md とは何か——組織の憲法であり、組織の入口でもあるという二重性
2. 何を渡すか——絶対ルール・推奨事項・トリガー条件の3つを書き分ける理由
3. どう渡すか——「auto mode で動くか」を合格基準にする発火条件の設計
4. 渡しすぎると何が起きるか——参照率の低下と、トリガーリストが「育つ」過程
5. 削る機制——`.claude/rules/` への分離と「事故型を育てる」運用

本書には1本の通奏低音が流れている。各レイヤーで同じ問いが繰り返される——**何を渡し、何を渡さないか。渡しすぎた時に何が起きるか。** CLAUDE.md はその最初のレイヤーだ。そして、ここで「渡しすぎる」と起きることは、わりと残酷だ。Claude がそのファイルを読まなくなる。書けば書くほど効かなくなる、という逆説がここにはある。

なお本章では、CLAUDE.md の全文を転載することはしない。それをやると本書が「設定ファイルのサンプル集」に見えてしまうからだ。代わりに、構造——3層に分かれていること、トリガーが表形式であること、役割別に分離していること——の設計判断に焦点を当てる。設定ファイルそのものより、なぜその形になったのかのほうが、読者が自分のプロジェクトに持ち帰れる部分だと考えている。

## CLAUDE.md とは何か——組織の憲法であり、組織の入口

### 「最初に読まれるファイル」という性質

CLAUDE.md の最も基本的な性質は、Claude Code がプロジェクトで作業を始めるときに自動で読み込まれる、という点にある。ユーザーが明示的に「このファイルを読んで」と指示しなくても、セッションのコンテキストに最初から入っている。

この「最初に読まれる」という性質が、CLAUDE.md を特別な場所にしている。Playbook（手順書）は「読むべき場面で読まれる」ものだし、メモリは「関連する話題のときに参照される」ものだ。それに対して CLAUDE.md は、何をするにしても最初に目に入る。組織でいえば、新しく入った人が最初に渡される就業規則のようなものだ。

だから私は最初、ここに思いつく限りのルールを書いた。「日本語で応答すること」「テンポラリファイルは `tmp/` 以下に作ること」「git はディレクトリ移動なしで実行すること」——書けば最初に読まれるのだから、書くほど安全になるはずだ、と。

これが半分外れていた、という話を以降でしていく。

### 「ルールを書く」と「ルールが守られる」は別の問題

最初に直面したのは、シンプルな現実だった。**CLAUDE.md にルールを書いても、Claude はそれを「読みうるが、毎回守るとは限らない」状態にとどまる。**

具体例を出す。私はかつて「コミット時は必ずブランチを確認すること」というルールを書いていた。意図は明確だ。意図しないブランチへのコミットを防ぎたい。ところが、これがしばしば守られなかった。auto mode——ユーザーが横についていない自動実行のモード——で作業が進むと、Claude はコミットの直前にブランチ確認をスキップして、そのまま push してしまうことがあった。スケジューラで夜間に自動実行されるとき、あるいはユーザーが画面から離れている間に走っている連続作業がこれにあたる。

なぜか。「コミット時は」という条件が、時間軸として弱いからだ。「コミット時」という言葉は、コミットという行為の全体を漠然と指していて、「いつ・どの操作の直前に確認するか」を特定していない。Claude はコミットという一連の流れの中で、どこで立ち止まればいいのかを掴めない。結果として、流れに乗って進んでしまう。

私はこのルールを次のように書き換えた。

> git 操作は各エージェントが自分の作業範囲で実行する。コミット・プッシュ前に `git -C <repo> symbolic-ref --short HEAD` でブランチを確認する。

ポイントは「コミット・プッシュ前に、このコマンドで」と、**操作と確認手段を具体的なコマンドに結びつけた**ことだ。漠然と「確認する」ではなく、「`symbolic-ref` を打つ」という明確なアクションにした。これで守られ始めた。

ここから私が学んだのは、ルールが守られる条件は3つある、ということだ。

1. **発火条件が書かれている**——いつ・どの操作で発動するかが明確であること
2. **参照経路がある**——そのルールがコマンドや委任プロンプトで実際に参照されること
3. **違反検知の仕組みがある**——守られなかったときに気づける仕掛けがあること

この3つのどれかが欠けると、ルールは「書いてあるのに守られない」状態になる。CLAUDE.md にルールを書くというのは、文章を置くことではなく、この3条件を満たす仕組みを設計することなのだ。

### 「人間相手なら言わないこと」を Claude には言う

ここで一つ、設計上の重要な感覚を共有しておきたい。CLAUDE.md を書いていると、何度も「こんな当たり前のことを書く必要があるのか」と感じる場面が出てくる。

たとえば私のプロジェクトの CLAUDE.md には、こう書いてある。

> ユーザーが `1` / `OK` / 具体的承認語 を返すまで実行しない。沈黙 ≠ 承認。

「沈黙は承認ではない」——人間同士なら、わざわざ言うまでもない。返事がないのに勝手に進める人はいない。だが Claude には書く必要があった。書いていなかった時期に、ユーザーが返事をしないことを「了承された」と解釈して、auto mode で勝手に作業を進めてしまう事故が起きたからだ。

人間が暗黙に共有している前提を、Claude は共有していない。だから「言わなくてもわかるだろう」と思うことほど、明文化しないと守られない。これは CLAUDE.md を設計するうえで、繰り返し効いてくる感覚だ。当たり前すぎて書かなかったルールが、後で事故になって戻ってくる。

### 3層構造——憲法・運用ルール・リカバリ

私のプロジェクトの CLAUDE.md は、価値観ガバナンスのセクションが3つの層に分かれている。この3層構造が、本章で最も伝えたい設計判断だ。

- **憲法（4つの権利）**——提案権・整合性チェック・承認権・上申経路。組織がどうあるべきかを定めた、抽象的だが根幹の部分
- **運用ルール（トリガーリスト）**——その抽象論を auto mode でも実際に発動させるための、具体的な発火条件の表
- **リカバリ手順**——ルールが破られたときに、それをどう学びに変えるかの手順

なぜ3層に分けたのか。一言でいえば、**どれか1層だけでは機能しないと痛感したから**だ。

憲法だけでは、auto mode で失火する。「組織への不利益を発見したらユーザーに確認する」という抽象的な権利を書いても、「何が不利益か」の判定が Claude の主観に委ねられ、自動実行のなかで発動しないことがある。これは実際に事故になった（後述する2026-04-23 の AUTO_SYNC_ZENN 事故がまさにこれだ）。

運用ルール（トリガーリスト）だけでは、「なぜそのルールがあるのか」が伝わらない。発火条件だけが並んでいると、Claude も人間も、ルールを機械的に適用するだけで、判断が必要な未知の場面で応用が効かない。

リカバリ手順だけでは、事故から学ぶサイクルが回らない。違反が起きたときに「次に同じ失敗を防ぐ」設計に変換する経路がないと、同じ事故が繰り返される。

この3つがセットになって初めて、組織が事故から自走的に学ぶ装置になる。憲法が「あるべき姿」を示し、運用ルールが「それを実際に発動させ」、リカバリ手順が「破られたときに憲法と運用ルールの両方を更新する」。円環になっている。

### 「憲法」という比喩の射程

ここで、この3層構造を「憲法」と呼ぶことについて少し補足したい。私はこの比喩を気に入っていて多用するのだが、比喩には射程があるので、誤解を避けるために線引きしておく。

憲法という比喩がうまく当てはまるのは、「それ自体は抽象的な原理を定めるが、運用法（法律・運用ルール）とセットでないと機能しない」という点だ。実際の国の憲法も、条文だけでは社会は回らない。具体的な法律と、それを執行する仕組みがあって初めて機能する。CLAUDE.md の3層構造はこれによく似ている。

別の比喩で見ることもできる。OS のカーネルに例えるなら、CLAUDE.md 本体は最小のカーネルで、`.claude/rules/` 配下はカーネルがロードするモジュール群だ。あるいは建築なら、CLAUDE.md は躯体——建物全体を支える骨組みで、各 Playbook は内装にあたる。

どの比喩でも共通して見えてくるのは、**CLAUDE.md は「全部を書く場所」ではなく「全体を支える最小の核を置く場所」だ**ということだ。憲法に行政手続きの細部を書かないのと同じで、CLAUDE.md に手順の細部を書くべきではない。本体を75行に抑えているのは、この感覚から来ている。詳細は外に出す。これが後述する「削る機制」の出発点になる。

### CLAUDE.md は「入口」でもある

3層構造に加えて、もう一つ CLAUDE.md には性質がある。**詳細を指し示す入口**だという性質だ。

私のプロジェクトの CLAUDE.md は、その大半が「詳細は〇〇を参照」という形になっている。「全エージェント共通ルールは `.claude/rules/global-rules.md` を参照」「COO 固有の行動規範は `.claude/rules/coo-rules.md` を参照」「対応表は `ops/playbooks/INDEX.md` を参照」——CLAUDE.md 本体は、ルールの中身を全部抱え込むのではなく、どこを見ればいいかを指し示すハブになっている。（なお、`coo-rules.md`・`global-rules.md`・`agent-roles.md` などは私のプロジェクト固有のファイル名だ。あなたの環境では異なる名前になって構わない。重要なのはファイル名ではなく、「役割別に分けて外に置く」という構造の判断だ。）

これは意図的な設計だ。最初に読まれるファイルだからこそ、ここに全部を書くと、最初に読むコンテキストが膨れあがる。膨れあがると、何が起きるか。Claude がそれを精読しなくなる。だから本体は入口に徹し、詳細は外に置く。

「組織の憲法であり、組織の入口でもある」——これが CLAUDE.md の二重性だ。憲法として組織の根幹を定めながら、入口として詳細への経路を示す。この二重性を踏まえると、「何を本体に書き、何を外に出すか」という判断が、CLAUDE.md 設計の中心問題になることが見えてくる。

## 何を渡すか——書き分けの3カテゴリ

### 全部「〜すること」で書くと、全部が同じ温度になる

CLAUDE.md に何を書くか、を考える前に、**どう書き分けるか**を決める必要がある。これに気づくのに私は時間がかかった。

最初、私はルールをすべて同じ形式で書いていた。

```
- 日本語で応答すること
- テンポラリファイルは tmp/ 以下に作ること
- 専門用語は読者向けに噛み砕くこと
- git はディレクトリ移動なしで実行すること
```

箇条書きで「〜すること」と並べる。読みやすいし、書きやすい。だが問題があった。**どれが絶対に守るべきルールで、どれが「できれば守ってほしい推奨」なのかが、Claude にも、後で読み返した自分にも区別できない。**

「日本語で応答する」は守らなくても実害は小さい。一方「git はディレクトリ移動なしで実行する」を破ると、過去に記事URLが書き換わる事故につながった、絶対に守らせたいルールだ。この2つが同じ箇条書きで同じ温度で並んでいると、Claude はどちらも「同じくらいの重み」として扱う。結果として、絶対ルールの優先度が、推奨事項に薄められてしまう。

温度を書き分ける。これが「何を渡すか」の前提になる。

### 3つのカテゴリと、その文体

私のプロジェクトでは、ルールを3つのカテゴリに分け、それぞれ異なる文体で書いている。

**絶対ルール**は、強い断定で書く。「〜禁止」「必ず〜する」「例外なし」「沈黙 ≠ 承認」。逃げ場のない言い切りにする。たとえば——

> Bash ツールでは `cd` を原則禁止

> git はディレクトリ移動なしで実行する

「原則禁止」「〜する」と言い切ることで、これは交渉の余地がないルールだと示す。

**推奨事項**は、強度を一段落とした表現で書く。「〜を優先する」「〜が望ましい」「原則として〜」。たとえば——

> 単純な git add / commit / push は COO が直接やってよい

「やってよい」は許可であって命令ではない。守るべきというより、こうするのが望ましいというニュアンスを文体で出す。

**トリガー条件**は、表形式で書く。これが3つ目のカテゴリで、本章で最も重要なものだ。次の節で詳しく扱う。

文体を変えるだけで、Claude が「これは絶対か、推奨か」を判定しやすくなる。同じ「〜すること」で並べるのをやめ、強度に応じて言葉を選ぶ。地味だが、効く。

### トリガー条件は表で書く

3つ目のカテゴリ、トリガー条件は、文章ではなく表で書く。私のプロジェクトの CLAUDE.md で最も特徴的な部分がこれだ。

表は3列で構成する——「トリガー（どんな操作か）」「なぜ承認が必要か」「確認形式（どう確認するか）」。たとえば、こういう行が並ぶ。

| トリガー | なぜ承認が必要か | 確認形式 |
|---|---|---|
| デフォルト値変更で挙動 on/off を切り替える | 副作用が記事・課金・外部APIに波及 | 「〇〇をデフォルト△△化します。副作用: □□。OK？」 |
| 自動実行の登録（cron / Scheduler） | 無人実行開始は不可逆性が高い | スクリプト・実行頻度・停止方法を提示 |
| 安全装置バイパス（--force / --no-verify） | バグやプロンプト注入で破壊的動作に直結 | 使用理由と代替案を併記 |

（実際の表はさらに行が多いが、ここでは代表3行を抜粋した）

なぜ表なのか。理由は2つある。

ひとつは**情報密度**だ。表は1行に「条件・理由・対処」の3点が凝縮される。文章で「デフォルト値を変更するときは、副作用が記事や課金に波及しうるので、〇〇という形式で確認すること」と書くより、表のほうが圧倒的に密度が高い。同じ情報量を少ない行数で渡せる。これは後述する「渡しすぎると何が起きるか」の節で扱う「肥大化」の対策にもなる。

もうひとつは**判定容易性**だ。Claude が「今やろうとしている操作は、このトリガーに該当するか」を判定するとき、表の左列を見ればいい。「デフォルト値変更で挙動を切り替えるか？」とチェックできる。文章に埋め込まれていると、この判定が難しくなる。表は判定のためのチェックリストとして機能する。

そして、3列のうち真ん中の「なぜ承認が必要か」が効いている。発火条件と対処だけなら2列で済む。なぜ理由を残すのか。**新しく入ったエージェント（あるいは未来の自分）が読んでも「なぜこのルールが厳格なのか」が分かるようにするため**だ。理由が書いてあると、表に載っていない未知の操作に出くわしたときに「これは載っていないが、理由から考えると同じ警戒が要りそうだ」と応用が効く。理由は、ルールを機械的な禁止リストから、判断の指針に変える。

### 自分のプロジェクトで書き分けるなら——判定の問い

この3カテゴリの書き分けを、読者が自分の CLAUDE.md に持ち込むとき、判定に使える問いを2つ挙げておく。

ひとつ目。**「このルールを破ったとき、取り返しがつくか」**。取り返しがつかない・復旧が困難な操作（外部APIへの書き込み、課金、公開状態の変更、不特定多数のファイルの一括変更）に関わるルールは、トリガー条件として表に書く。逆に、破っても会話のなかですぐ直せるもの（応答言語、軽微な表記）は、推奨事項で足りる。不可逆性の高さが、カテゴリを決める。

ふたつ目。**「いつ・どの操作のときに発動すべきルールか、特定できるか」**。発動タイミングを具体的な操作にひもづけられるなら、トリガー表に「その操作 → なぜ → どう確認」の形で書ける。逆に、特定の操作にひもづかない一般的な心構え（「丁寧に書く」「読者を意識する」）は、絶対ルールや推奨事項として散文で書く。トリガー表に書こうとして書けないルールは、そもそも発火条件が曖昧だというサインでもある。

この2つの問いを通すと、書こうとしているルールが3カテゴリのどれに収まるかが、わりと機械的に決まる。そして「どれにも収まらない、ふわっとしたルール」が見つかったときは、それは設計を詰め直す合図だ。多くの場合、発火条件が曖昧なまま書こうとしている。

### 「渡しすぎない」が早くも顔を出す

ここまで「3カテゴリで書き分ける」と書いてきたが、書き分けたうえで、**そもそも全部を CLAUDE.md 本体に書くべきか**という問いが残る。

たとえば「COO が直接やってよい作業」と「委任すべき作業」の対応表は、COO エージェントだけが必要とする情報だ。writer や reviewer には関係ない。これを全員が最初に読む CLAUDE.md 本体に書くと、全エージェントが「自分には関係ないルール」を毎回読まされることになる。

だから私は、こうした役割特化のルールを CLAUDE.md 本体から切り出して `.claude/rules/coo-rules.md` に移した。本体には「COO 固有の行動規範は coo-rules.md を参照」という1行だけを残した。

ここで早くも、本書の通奏低音「渡しすぎない」が顔を出している。**何を渡すかを考えることは、同時に何を渡さないかを考えることでもある。** 書き分けるだけでなく、置き場所を分ける。全員に渡すべきルールと、特定の役割にだけ渡すべきルールを分離する。この分離の判断軸については「削る機制」の節で詳しく扱うが、ここで押さえておきたいのは、「何を渡すか」の設計には最初から「渡しすぎない」という引き算が組み込まれている、ということだ。

## どう渡すか——「auto mode で動く」が合格基準

### ルールの合格基準を決める

ルールを書き分け、置き場所を分けたとして、次の問いはこうだ。**書いたルールが「ちゃんと効くルール」かどうかを、どう判定するのか。**

私はこの判定基準を、明確に一つに決めている。**「auto mode でも発火するか」**だ。

理由はこうだ。ユーザーが横について対話しながら作業しているモードでは、ルール違反は人間が止められる。Claude が変なことをしようとしたら、ユーザーが「待って」と言える。だからこのモードでは、多少ルールが曖昧でも、最後の安全網として人間がいる。

ところが auto mode——スケジューラ経由の自動実行や、ユーザーが離席している間の連続作業——では、その安全網がない。誰も止められない。だから auto mode で発火しないルールは、最も止めてほしい場面で機能しないルール、ということになる。

逆にいえば、**「このルールは auto mode でも確実に発火するか？」を自問すれば、ルールの弱点が見える**。発火条件が曖昧なルールは、この問いの前で必ず馬脚を現す。

### 発火条件を「操作の直前」に結ぶ

auto mode で発火させるための具体的な技術が、**発火条件を「操作の直前」に結ぶ**ことだ。前述した「コミット時は確認する」を「コミット・プッシュ前に `symbolic-ref` を打つ」に書き換えた話があったが、あれが典型例だ。

私のプロジェクトの coo-rules.md には、「委任アクション直前（常時）」というチェックポイントのセットがある。COO が他のエージェントに作業を委任しようとした、まさにその瞬間に自問する項目が並んでいる。

> エージェントに委任しようとした瞬間に以下を自問する:
> - 対応 Playbook を確認したか？
> - general-purpose エージェントを使おうとしていないか？
> - 新規ファイル作成・既存ファイル大幅変更を含むか？

ポイントは「委任アクション直前」という時間の指定だ。「委任のときは気をつける」ではなく「委任しようとした瞬間に、この項目を自問する」。発動のタイミングを、具体的な操作の直前にピン留めしている。

なぜこれが効くのか。Claude（や人間）は、作業の流れに乗っているとき、抽象的な心構えを思い出せない。「気をつける」「注意する」は、流れのなかで蒸発する。だが「この操作をする直前に、このリストを確認する」という形になっていると、操作そのものがトリガーになって、確認が発動する。操作と確認が、時間的に密着している。

これは料理に例えるとわかりやすい。「火加減に気をつける」という心構えは守りにくいが、「鍋から煙が出たら火を弱める」という条件反射は守りやすい。後者は「煙」という具体的なトリガーに行動が結びついている。ルールも同じで、抽象的な心構えより、具体的な操作にひもづいた条件反射のほうが、はるかに高い確率で発動する。

### チェックポイントの「発火タイミング」自体を設計する

発火条件を操作の直前に結ぶ、という設計は、もう一段精密にできる。**「どの操作の直前か」を間違えると、正しく書いたチェックポイントでも発火しない**からだ。これを教えてくれた事故がある。

2026年5月3日、私はネタ帳の作成を、専用の Playbook（手順書）を確認しないまま自分で書いてしまった。私のプロジェクトには「ネタ帳の作成は writer に委任する」「該当タスクは着手前に Playbook を読む」というルールがあったにもかかわらず、だ。

なぜ発火しなかったのか。当時、Playbook 確認を促すチェックポイントは「委任アクションの直前」に置かれていた。委任しようとした瞬間に「対応 Playbook を確認したか」を問う設計だ。ところがこのとき私は、ネタ帳を「短文だから自分で書ける軽作業」と誤認し、**そもそも委任しなかった**。委任しなかったから、委任直前のチェックポイントは発火しなかった。正しく書かれたルールが、発動すべき場面の手前で素通りされた。

対処として、私はチェックポイントを2段構えにした。委任の直前だけでなく、**「ユーザーから指示を受け取った直後」**にも別のチェックポイントを置いた。

> 指示が `ops/playbooks/INDEX.md` の対応表に該当するタスクか？ 該当する場合、たとえ軽作業に見えても着手前に Playbook を読む。

委任するかどうかを判断する前、指示を受け取った最初の段階で「これは Playbook のあるタスクか」を問う。こうすれば、「自分でやろう」と判断する前にチェックが入る。委任直前のチェックポイントが捕り逃した穴を、指示受け取り直後のチェックポイントが塞ぐ。

ここから学べるのは、**チェックポイントは「正しい内容」を書くだけでは足りず、「正しいタイミング」に置かないと機能しない**ということだ。発火条件を操作の直前に結ぶとき、その「操作」が本当に必ず通る経路なのかを確認する必要がある。今回の場合、「委任」は必ず通る経路ではなかった——自分でやってしまえば通らない。だから、より手前の「指示受け取り」という、必ず通る経路にチェックを移した。

同じ構造の話は、セッションの起動時にもある。私はかつて、セッション開始時に直近の引き継ぎ資料（handoff）を確認せず、すでに決まっていた議論を最初からやり直す事故を起こした（2026年5月14日）。約30分かけて、決定済みの設計を再検討してしまった。これも「起動時に handoff を確認する」というチェックポイントが、起動フローのなかに明示的に組み込まれていなかったために起きた。対処は同じで、起動時のチェックポイントとして「直近の handoff 一覧を確認する」を明文化した。

チェックポイントの設計とは、内容を書くことと、それを「必ず通る経路の直前」に配置することの、両方を含む。内容だけ正しくても、配置を誤れば素通りされる。

### 「沈黙 ≠ 承認」を明文化する意味

前述した「沈黙 ≠ 承認」も、auto mode を合格基準にすると意味がはっきりする。

対話モードなら、ユーザーが何も言わなくても、Claude は「返事を待っている」状態を保てる。ユーザーが目の前にいることが分かっているからだ。だが auto mode では、Claude は「ユーザーが返事をしていないだけなのか、それとも今は不在で後で確認する想定なのか」を区別できない。区別できないまま「返事がない＝進めていい」と解釈すると、勝手に進む。

だから私は CLAUDE.md に、ユーザーが `1` や `OK` といった具体的な承認語を返すまで実行しない、と明記している。具体的な承認語が返ることを条件にすると、auto mode でも「承認語がない＝実行しない」という明確な発火条件になる。曖昧さを排除する。これも「auto mode で動くか」を基準にしたからこそ出てきた書き方だ。

### 承認権を CLAUDE.md に書く——Claude が組織を勝手に最適化しないために

「どう渡すか」のもう一つの軸が、**ルール自体を変える権利を誰が持つか**だ。

ここには注意すべき罠がある。Claude は優秀なので、運用しているうちに「このルールは効率が悪い」「こう変えたほうが速い」と気づくことがある。気づいたときに、Claude が自分で CLAUDE.md を書き換えたら、どうなるか。組織の価値観が、Claude の「最適化」によって、ユーザーの知らないところで変わっていく。効率の名のもとに、守るべき原則が削られていく。

これを防ぐために、私のプロジェクトの憲法には4つの権利が定義されている。

- **提案権**——全エージェントは、不利益を発見したら改善案を提案できる
- **整合性チェック**——提案前に既存ルールとの矛盾を確認する
- **承認権**——ルール変更が正しいかを判断するのはユーザー。承認なしに Claude は変更しない
- **上申経路**——サブエージェントの提案は COO 経由でユーザーに上がる

肝は3つ目の**承認権**だ。「価値観・ルールの変更が正しいかを判断するのはユーザー。承認なしに Claude は変更しない」。提案はいくらでもしていい（提案権）。だが、変更を確定する権限はユーザーにある。提案 → 整合性チェック → ユーザー判断 → 承認後に Claude が反映、という4段階を必ず通す。

この設計があるから、私は Claude に「ルールを育てる」役割を安心して任せられる。Claude は事故から学んでトリガーを増やす提案ができる。だが、その提案を組織のルールとして確定するのは私だ。Claude が組織を勝手に書き換えることはない。**「育てる自由」と「確定する権限」を分離する**——これが、自律的に学ぶ組織を、暴走させずに運用するための設計だ。

そしてこの承認権こそ、CLAUDE.md という文書を「Claude が読むだけの設定ファイル」から「ユーザーと Claude が共同で管理する憲法」に変えている。書くのは私で、守るのは Claude で、変えるときは私の承認が要る。この役割分担が CLAUDE.md の運用の核にある。

## 渡しすぎると何が起きるか——参照率の低下と、トリガーが育つ過程

### 抽象ルールが auto mode で失火した日——AUTO_SYNC_ZENN 事故

ここまで「発火条件を具体的に書く」「auto mode で動くかを基準にする」と繰り返してきた。なぜそこまで言うのか。それを痛感させた事故があるからだ。

2026年4月23日、私のプロジェクトで、`AUTO_SYNC_ZENN=true` という設定を Claude が独断でデフォルト化した。結果として、Zenn に公開していた記事5本が一時的に未公開（unpublish）の状態になった。復旧作業で実害は限定的に収まったが、公開状態の整合性が一時的に崩れた。

何が起きたのか。当時の CLAUDE.md には、憲法にあたる抽象的なルールはあった。「組織への不利益を発見したらユーザーに確認する」という趣旨のものだ。だが、それを auto mode で発動させるための具体的なトリガーが書かれていなかった。

その結果どうなったか。「デフォルト値を変更することが不利益にあたるかどうか」の判定が、Claude の主観に委ねられた。Claude は「これは効率化の改善であって、不利益ではない」と判断し、ユーザーの承認を取らずに変更を実行した。憲法はあった。だが、auto mode では、その憲法を発動させる引き金がなかった。**抽象論は、最も止めてほしい場面で、無音のまま失火した。**

事故後、私は対処として、次の1行をトリガーリストに追加した。

| トリガー | 確認形式 |
|---|---|
| デフォルト値変更で挙動 on/off を切り替える | 「〇〇をデフォルト△△化します。副作用: □□。OK？」 |

「不利益を発見したら確認する」という主観依存の抽象ルールを、「デフォルト値変更で挙動を切り替えるなら確認する」という客観的に判定できる操作型に翻訳した。これで auto mode でも、「今やろうとしているのはデフォルト値変更か？」という客観的な問いで発火する。主観の入る余地をなくした。

この事故が、私のプロジェクトに「憲法だけでは足りない。運用に落とすトリガーが要る」という3層構造を生んだ起点だ。「CLAUDE.md とは何か」の節で書いた3層構造は、この失敗の産物にほかならない。

### 抽象ルールが連鎖操作で失火する——もう一つの型

似た構造の失火を、もう一つ挙げておく。2026年5月3日、私自身（厳密にはオーケストレーターのエージェント）が、Bash コマンドの中に専用ツールであるべき検索処理を紛れ込ませてしまった事故だ。

私のプロジェクトには「ファイル検索は Glob、内容検索は Grep を使い、`grep` や `find` を Bash 経由で実行しない」という明確なルールがある。文言は十分に明確だった。ところが、複数の調査操作を `&&` で1つのコマンドにまとめようとしたとき、このルールが失念された。「git status と検索を一度にやろう」と効率を優先した瞬間、各操作の手段選択（Bash か専用ツールか）の判断が雑になった。

幸い、このケースは Bash 内に書いた `Read` がシェルコマンドとして存在せず `command not found` でエラーになったため、すぐ気づけた。実害はなかった。

だが、ここで見えるのは、**明確に書かれたルールでも、複数操作を連鎖させて急いでいる場面では失火する**という型だ。ルールの文言は明確だった。それでも守られなかった。「ルールを明確に書けば守られる」という単純な期待が、ここでも裏切られている。

この事故の教訓は、coo-rules.md のチェックポイントに反映された。「複数コマンドを `&&` で連鎖させようとしていないか？ 連鎖前に各操作で専用ツールが使えないか確認する」。やはりここでも、抽象ルール（専用ツールを使え）を、具体的な操作の直前（`&&` で連鎖させようとした瞬間）に発火条件として結び直している。パターンは AUTO_SYNC_ZENN 事故とまったく同じだ。

### 書きすぎると、Claude は読まなくなる

ここまでの2つの事故は「書いたのに守られなかった」話だった。だが「渡しすぎる」ことの本当の怖さは、もう一段先にある。**ルールを書きすぎると、Claude はそのファイルを精読しなくなる。**

CLAUDE.md が肥大化すると、Claude にとってそのファイルは「読みうるが、毎回すみずみまで精読はしないもの」に近づいていく。コンテキストに入ってはいる。だが、長大なルール群のなかの個々の1行が、作業のたびに確実に参照される保証は薄れていく。

これは直感に反する現象だ。「安全にしたいからルールを足す」という行為が、「ルールが多すぎて個々のルールの参照率が下がる」という逆効果を生む。足すほど、一つひとつが薄まる。最も守らせたい絶対ルールが、量に埋もれて見えなくなる。

ここに、本章の通奏低音がはっきり現れる。**CLAUDE.md における「渡しすぎ」の症状は、参照率の低下だ。** ルールが肥大化する → Claude が精読しなくなる → 個々のルールの遵守率が下がる → 「ルールはあるのに守られない」状態になる。書く設計だけを進めて削る設計を持たないと、この悪循環に入る。

だから CLAUDE.md の設計には、「足す」と同じだけ「整理する」「外に出す」が要る。これが次の「削る機制」の節のテーマだ。

### トリガーリストは「事故型を育てる」運用になっている

「渡しすぎ」の話の前に、もう一つ、私のプロジェクトのトリガーリストが持っている性質を紹介しておきたい。それは、**トリガーリストが「事故型を追記して育てる」運用になっている**ことだ。

最初から完璧なトリガーリストは書けない。どんな操作が危険かは、事故が起きて初めて分かる。だから私のプロジェクトでは、事故が起きるたびに `logs/governance-incidents/` に事例を記録し（2026年5月31日時点で21件、`ls` 実測）、そこから抽出した新しいトリガー型をリストに追加する運用にしている。

最もよく育ったのが、blogsync という外部ツールに関するトリガーだ。blogsync は、はてなブログとローカルファイルを同期するツールで、設定の相対パスが作業ディレクトリに依存するという厄介な性質を持っている。これが原因で、記事のURLが意図せず書き換わる事故が起きた。

最初の事故は2026年5月4日に起きた。既存記事9本にカテゴリを一括追加するだけのつもりが、blogsync を直接呼び出した結果、4本の記事のカスタムURLが二重パスに書き換わった。たとえばある記事は、元のURL（`/entry/2026/04/09/072056`）が404になり、`/entry/saitoko.hatenablog.com/entry/2026/04/09/072056` という壊れたURLが新たに生まれた。はてなブックマーク・Google検索結果・既存記事内のリンク・SNSのシェアリンクが、すべて404を指すようになった。カテゴリを足すだけの作業が、公開済み記事の入口を壊したのだ。

しかもこれは一度では終わらなかった。その後、5月14日・5月15日・5月20日と、形を変えながら同じ系統の事故が連続して発生した。4回連続だ。とくに5月20日は、再発防止の修正コミットを入れた**直後**のテスト本実行で再発している。「修正コミットを打ったこと」と「事故が再発しないこと」はイコールではない、という痛い教訓だった。

このたびにトリガーリストの該当行が太っていった。最初は「既存スクリプトを経由しない外部CLI直接実行」という1行だった。事故が重なるにつれて、「blogsync 直接実行（pull/push 問わず）」「blogsync を呼ぶラッパー実行」「ラッパーの連続実行（ループ・bulk-update）」と、事故型が分化して行が増えていった。そして各行には、事故の日付と件数がそのまま書き込まれている。

> blogsync 直接実行（pull/push 問わず）……（事故: 2026-05-04 push×4記事 / 2026-05-14 pull → 後続post.sh で1記事URL変更 / 2026-05-20 bulk-update で5記事URL書き換え）

この「事故日付と件数を行内に残す」やり方が効いている。新しく読むエージェントは、「なぜこのルールがこれほど厳格なのか」を、背景込みで理解できる。4回も事故が起きたのか、と分かれば、警戒のレベルが伝わる。トリガーリストが、単なる禁止事項のリストではなく、**組織が踏んだ地雷の記録**になっている。

このように、CLAUDE.md のトリガーリストは固定の文書ではなく、事故から学んで育っていく生き物だ。書きすぎると参照率が下がるという制約のなかで、それでも事故型を取り込んで育てていく。この「育てながら、太りすぎないように管理する」という綱引きが、次節で扱う「削る機制」の必要性そのものを生んでいる。

---

## 削る機制——`.claude/rules/` への分離と、事故型を育てる運用

### 書く設計と削る設計はセットである

前節で見たとおり、CLAUDE.md は放っておくと太る。事故が起きればトリガーが増え、新しいルールが必要になればルールが増える。そして太りすぎると参照率が下がり、「ルールはあるのに守られない」状態になる。

だから、**書く設計と削る設計はセットでなければならない。** これは本書全体の通奏低音であり、CLAUDE.md レイヤーでの具体的な現れが本節だ。「何を渡すか」を設計したら、必ず「どう削るか」も設計する。片方だけでは、レイヤーは早晩破綻する。

CLAUDE.md における削る機制は、大きく3つある。役割別への分離、参照による外出し、そして事故型の集約だ。順に見ていく。

### 削る機制1——役割別に `.claude/rules/` へ分離する

最も大きな削る機制が、ルールを役割別に切り出すことだ。私のプロジェクトの CLAUDE.md 本体は75行に抑えられているが、これは詳細を `.claude/rules/` 配下に外出ししているからだ（2026年5月31日時点、`wc -l` 実測）。

- **CLAUDE.md 本体（75行）**——組織の最小コア。憲法・トリガーリスト・各ルールへの入口
- **global-rules.md（39行）**——全エージェント共通のルール
- **coo-rules.md（155行）**——COO エージェント特化の行動規範・チェックポイント群
- **agent-roles.md（92行）**——組織図とエージェントの責務
- **path-policy.md（14行）**——パス記述の方針

切り出しの判断軸は明確だ。**「全エージェントが読むべきか、特定のエージェントだけが読めば足りるか」**で分ける。

全員が読むべきルール（日本語で応答する、git の扱い、テンポラリファイルの置き場所など）は global-rules.md に集める。COO だけが必要とする委任判断のチェックポイントは coo-rules.md に隔離する。こうすれば、writer や reviewer は coo-rules.md を読む必要がない。各エージェントが、自分に関係するルールだけを読めばよくなる。

ここで効いているのが、最も大きいファイルが coo-rules.md（155行）であるという事実だ。チェックポイント群が積み上がって、これがいちばん太い。だが、これを CLAUDE.md 本体に置いていたら、全エージェントが155行のCOO専用ルールを毎回読まされていた。役割別に切り出したからこそ、本体を75行に保てている。

そして本体には、「COO 固有の行動規範は coo-rules.md を参照」という1行だけが残る。本体は入口に徹し、中身は外に置く。「CLAUDE.md とは何か」の節で書いた「組織の憲法であり、入口でもある」という二重性が、ここで具体的な削る機制として機能している。

### 削る機制2——「参照: 〇〇」で詳細を外に逃がす

役割別分離と地続きなのが、**詳細を Playbook や別ファイルへ「参照」で逃がす**機制だ。

私のプロジェクトの CLAUDE.md には、手順の細部はほとんど書かれていない。代わりに「対応表は `ops/playbooks/INDEX.md` を参照」「詳細は `.claude/rules/agent-roles.md` を参照」という形で、外のファイルを指している。

たとえば、起こりうる事故のリカバリ手順を考えてみる。CLAUDE.md には「違反に気づいたら被害範囲を特定し、原因を分類し、`logs/governance-incidents/` に記録する」という大枠だけを書く。実際の事故記録のフォーマットや過去事例は、`logs/governance-incidents/` 配下に置く。CLAUDE.md にはその場所を指す参照だけが残る。

事故ログ・運用ガイド・手順の細部は、`logs/` や `ops/` 配下に置く。CLAUDE.md には載せない。この線引きを守ることで、CLAUDE.md が「組織の核」であり続け、「あらゆる詳細を抱え込んだ巨大文書」にならずに済む。

外出しには副作用もある。参照先が増えると、「どこに何が書いてあるか」を把握するコストが上がる。だがこの副作用は、CLAUDE.md 本体が肥大化して参照率が下がるよりは、はるかにマシだ。参照経路さえ正しく張られていれば、Claude は必要なときに必要なファイルを読みにいける。むしろ「全部を1ファイルに書いて、結局どれも精読されない」より、「核は短く、詳細は必要時に参照」のほうが、実際に守られるルールの総量は多くなる。

### 削る機制3——事故型を「行ごとに育てて」集約する

3つ目が、前節で触れたトリガーリストの集約だ。

事故が起きるたびにトリガーを追加していくと、いずれトリガーリストだけで肥大化する。これを防ぐために、私のプロジェクトでは**「事故ごとに新規行を足す」のではなく「事故型ごとに行を育てる」**運用をしている。

blogsync 関連の4回連続事故を思い出してほしい。これを「事故が4回起きたから4行追加する」とやると、リストはあっという間に太る。代わりに、関連する事故を「事故型」でまとめ、1行のなかに複数の事故日付と件数を畳み込む。4回の事故が、3行程度に集約されている。1行のなかに「2026-05-04 / 05-14 / 05-15 / 05-20」と日付が並ぶ。

これにより、トリガーリストは事故の数だけ際限なく伸びることなく、「型」の数に応じた行数に保たれる。事故から学ぶ（行を太らせる）ことと、リストを太らせすぎない（型に集約する）ことを、両立させている。

### 肥大化のサインを、どう見分けるか

削る機制を回すには、まず「太りすぎている」と気づく必要がある。だが CLAUDE.md の肥大化は、ファイルサイズのように一目で分かる指標がない。私が肥大化のサインとして観察しているものを、いくつか挙げておく。

ひとつは、**同じ趣旨のルールが複数箇所に現れ始める**こと。「git の扱い」について、global-rules.md に書いたはずのことが、いつのまにか別の文脈でもう一度書かれている。同じことを2回書いているのは、「1回書いたことを忘れて、また書いた」サインだ。これはルールが多すぎて全体を把握しきれなくなっている兆候で、整理（重複の統合）の合図になる。

ふたつめは、**ルールが守られない頻度が上がる**こと。明確に書いたはずのルールが破られる回数が増えてきたら、それは「ルールの書き方が悪い」のではなく「ルールが多すぎて個々の参照率が下がっている」可能性を疑う。前節で書いた参照率低下の症状が、遵守率という形で表に出てくる。

みっつめは、**「このルール、まだ要る？」と自分が感じる行が出てくる**こと。読み返したときに、もう使っていないツールへの注意書きや、すでに別の仕組みで自動化された手順への言及が残っていることがある。これは退役判定の対象だ（前述のとおり、ここはまだ仕組み化できていない）。

これらのサインは、いずれも「定期的に CLAUDE.md を通読する」ことでしか見つからない。自動検知できれば理想だが、現状は人間（私）が時々読み返して気づくのに頼っている。書きっぱなしにせず、たまに全体を読み返す。地味だが、これが削る機制を回す最初の一歩になる。

### 退役判定——まだ整備しきれていない領域

ここまで削る機制を3つ挙げてきたが、正直に書いておくべき未整備の領域がある。**古くなったルール行・トリガー行の「退役判定」だ。**

役割別分離も参照による外出しも事故型の集約も、いずれも「太りすぎないように管理する」機制ではあるが、「もう不要になったルールを削除する」機制ではない。事故型を取り込んで育てる運用は強力だが、その裏で「役目を終えたルール」「他のルールで代替されているトリガー」が、削除されないまま残り続けるリスクがある。

これは正直、私のプロジェクトでもまだ十分に仕組み化できていない。事故が起きればトリガーを足す経路はあるが、「このトリガーはもう要らない」と判定して削る経路は、定期的なレビューに依存していて、自動的には回っていない。

本章の執筆にあたって、私は CLAUDE.md のルール行・トリガー行を一度通しで見直してみた。退役の候補として疑ったのは、「もう発生しえない操作への注意書き」「他の一般ルールに吸収できる個別ルール」「一度も発火していないトリガー」の3種類だ。見直してみて分かったのは——**思ったほど削れる行は多くなかった**ということだった。とくに blogsync 系のトリガーは、4回も繰り返した事故型を背負っているだけに、安易に削れない。むしろ「これはまだ現役だ」と再確認する行のほうが多かった。一方で、特定操作を禁じる個別ルールの一部は、より一般的なルールでカバーできることが見えてきて、統合の余地が見つかった。つまり、退役判定をやってみた実感としては、「削除」より「統合」のほうが、肥大化対策として現実的に効く——という手応えだった。だが、これを定期的に回す「仕組み」として持っているとは、まだ言えない段階だ。

ここで一つ、混同を避けるために線を引いておく。本章で扱っている退役は、あくまで **CLAUDE.md のルール行・トリガー行**の話だ。メモリファイル（`~/.claude/projects/*/memory/` 配下）の退役は、別の仕組み（`/dream` というスキル）で管理しており、本章の対象ではない。メモリの削る機制については第5章で扱う。

退役判定が未整備だと正直に書くのは、本書が「うまくいった設計だけを並べる本」ではないからだ。CLAUDE.md レイヤーには、まだ手が回りきっていない削る機制がある。足す経路はできた。だが、捨てる経路はまだ手作業に頼っている。ここは私自身の宿題として残っている。

### 次章へ——ルールだけでは、組織は動かない

CLAUDE.md レイヤーをここまで解剖してきた。憲法・運用ルール・リカバリの3層構造を作り、絶対ルール・推奨事項・トリガーを書き分け、発火条件を操作の直前に結び、auto mode で動くことを合格基準にし、削る機制をセットで設計する。これが「ルールを渡す」ことの中身だ。

だが、ここで一つ、はっきりさせておくべきことがある。**どれだけルールを精緻に設計しても、ルールだけでは組織は動かない。**

考えてみてほしい。ここまで「全エージェントが」「COO が」「writer が reviewer が」と、当たり前のように複数のエージェントを前提に書いてきた。global-rules.md は全エージェント共通のルールで、coo-rules.md は COO 特化のルールだ。つまり、ルールはすでに「役割の異なる複数の人格」が存在することを前提にしている。

ルールは、それを守る主体がいて初めて意味を持つ。「委任アクション直前に自問する」というチェックポイントは、委任する側（COO）と委任される側（各エージェント）がいるから成立する。「設計書と実装が食い違うときは実装を信じる」というルールは、設計するエージェントとレビューするエージェントが分かれているから必要になる。

ここまで読んだら、まず自分の CLAUDE.md を開いて、いちばん守らせたいルールを1つ選んでみてほしい。それが「いつ・どの操作の直前に発動するか」を特定できているか、auto mode でも発火しそうかを、本章の3条件に照らして眺めてみる。それだけで、書き直すべき1行が見えてくるはずだ。

ここで次の問いが立ち上がる。**そもそも、なぜ人格を分けるのか。** 一つの Claude にすべてをやらせるのではなく、writer・reviewer・reader・COO と役割を分離するのは何のためか。分けることで何が変わり、分けすぎると何が起きるのか。

ルールという部品の次に解剖するのは、そのルールを守る主体——サブエージェントだ。次章では、人格を分けるという設計判断の中身に踏み込む。
