# 第5章 メモリ——「次に同じ失敗をしない」を渡す

Claude Code のメモリは、Claude が自分で書き留め、次のセッションで自分で読み返す覚え書きの置き場だ。私のプロジェクトでは現在、索引ファイルである `MEMORY.md` が38行、その先にぶら下がる本体ファイルが38本ある（2026年5月31日に `wc -l` と `ls` で実測した値）。本章では、このメモリ層に何を書き、何を書かないかの設計を扱う。先に結論を言っておくと、メモリは「Claude に人格を教える」場所ではなく、「次に同じ失敗をしないため」の場所だ。この一点を取り違えると、メモリはあっという間に肥大化し、かえってコンテキストを圧迫して判断を鈍らせる。

ここまでの章で、私は CLAUDE.md にルールを渡し、サブエージェントに役割を渡し、スキルに手順を渡し、Playbook に判断の地図を渡してきた。メモリはその次に来る層だ。前の4層が「あらかじめ設計して書いておくもの」だとすれば、メモリは「動かしてみて、つまずいたあとに書き足すもの」という性格が強い。設計と運用のあいだに位置する層、と言ってもいい。

そして本章でも、本書の通奏低音である「渡しすぎない」が顔を出す。メモリは便利だからこそ、何でも覚えさせたくなる。だが覚えさせたものは全部、毎セッションのコンテキストに読み込まれる。渡しすぎたメモリは「賢くなる装備」ではなく「重くなる荷物」になる。この章は、何を覚えさせ、何を忘れさせるかという取捨選択の話である。

## メモリとは何か——「次の失敗を防ぐ」場所

### 人格を教える場所ではない

Claude Code を使い込み始めると、メモリを「Claude を自分好みに育てる場所」だと考えたくなる瞬間がある。「もっと砕けた口調にしたい」「私の好みを覚えさせたい」——その気持ちはわかる。だが私は、メモリをそういう用途には使っていない。

私がメモリに書いているのは、ほぼすべて「一度やらかして、二度とやりたくないこと」だ。たとえば私のメモリには `feedback_first_person_in_article.md` というファイルがある。中身を要約するとこうだ。

> 記事本文・書籍本文・ネタ帳など、読者向けに公開する文章の一人称は「私」を使う。「ぼく」「俺」「自分」等は使わない。

これは抽象的な好みを書いたものではない。このファイルには、2026年5月15日に writer エージェント（記事執筆を担当する私のサブエージェント）が「ぼく」を14箇所使った草稿を出してきて、私がそれを指摘し即座に直した、という具体的な経緯が記録されている。つまりこのメモリは「私の文体の好み」ではなく「過去に起きた1つの事故と、その再発防止策」なのだ。


この違いは小さく見えて、実は設計判断を大きく左右する。「人格を教える」つもりでメモリを書き始めると、書ける内容は無限にある。好み、口調、価値観、文体——いくらでも書けてしまう。一方、「次の失敗を防ぐ」を基準にすると、書く対象は「実際に起きた失敗」に限定される。書ける量が自然に絞られる。これがメモリ肥大化に対する最初の歯止めになる。

判定基準は一つだけ持っておけばいい。**「これを覚えさせれば、次に同じ失敗をしなくなるか?」** イエスなら書く。「あったほうが雰囲気が出る」「なんとなく賢くなりそう」程度ならば、書かない。

### 3種類の粒度——feedback / project / reference

メモリの本体ファイルは、私のプロジェクトでは命名で3種類に分けている。実測すると、`feedback_` が19本、`project_` が12本、`reference_` が5本、そのほか `user_` が2本で、合計38本だ。

- **feedback_*.md**: ユーザーから受けたフィードバック・価値観・嗜好。変わりにくい
- **project_*.md**: 進行中のプロジェクトの状態・制約。時期によって変わる
- **reference_*.md**: 外部の固有名詞・正式表記など、事実ベースの参照情報

なぜ分けるのか。一番の理由は「いつ更新すべきかが、ファイル名を見ただけで判断できる」からだ。

`project_zenn_posting_limit.md`（Zenn は1日1投稿までという制約を記録したファイル）は、Zenn がその仕様を変えたら更新が必要になる。プロジェクト側の事情が変われば書き換える前提のメモリだ。一方、`feedback_first_person_in_article.md`（一人称は「私」）は、私の文体の方針が変わらない限りずっと有効で、めったに触らない。`reference_zenn_book_titles.md`（自分の電子書籍の正式タイトル一覧）は、新刊を出したときだけ追記すればいい。

種類を分けずに全部を一つの箱に放り込むと、メモリを見直すたびに「これは今も生きている情報か? それとも古い状態を引きずっているだけか?」を一件ずつ吟味しなければならなくなる。種類で分けておけば、「project_ 系だけ月次で見直す」「reference_ 系は事実が変わったときだけ触る」といった更新リズムを種類単位で決められる。これは小さな工夫だが、メモリが30本を超えてくると効いてくる。

ちなみにこの3分類は Claude Code の公式仕様ではなく、私が運用の中で決めたファイル名の規約にすぎない。読者が真似する場合、分類の軸は自分のプロジェクトに合わせて変えてかまわない。重要なのは「分類があること」自体ではなく、「いつ更新すべきかが名前から判断できること」だ。

### MEMORY.md は索引、各ファイルが本体

ここで `MEMORY.md` の役割をはっきりさせておきたい。`MEMORY.md` は本体ではなく、索引だ。実測38行で、中身は各メモリファイルへのリンクと1行サマリの羅列になっている。冒頭の数行を抜粋するとこうだ。

```
- [記事の一人称は「私」](feedback_first_person_in_article.md) — 「ぼく」「俺」等は使わない。委任時に明示する
- [家族の固有名詞は記事・公開文章に出さない](feedback_family_name_privacy.md) — 妻・息子・親族は一般名詞で
- [Zenn Book 公式タイトル一覧](reference_zenn_book_titles.md) — Vol.1「作るまで」/Vol.2「回すまで」/Vol.3「書き続けるまで」
```

1行あたりの情報は「タイトル・本体ファイルへのリンク・ごく短い要約」だけだ。詳しい経緯や適用方法は、すべて本体ファイル側に書いてある。

なぜこの構造にするのか。理由はコンテキストの効率だ。Claude はセッション開始時にこの索引を読む。もし索引そのものに各メモリの全文を書いてしまうと、38本ぶんの詳細がいきなりコンテキストに流れ込み、最初から窓を圧迫する。索引を1行サマリに抑えておけば、Claude はまず「どんな記憶があるか」の全体像だけを把握し、必要になったメモリだけを本体ファイルとして深く読みにいける。

これは Playbook 層の設計と同じ発想だ。第4章で、私は分厚い Playbook の全文を CLAUDE.md に書かず、「該当する Playbook を読め」という参照だけを残す設計を説明した。メモリも同じで、索引は「どこに何があるか」を示す地図に徹し、中身は本体に預ける。索引と本体を分けることで、`MEMORY.md` 自体が肥大化しない。

## 何を渡すか——トリガー語と価値観の保存

### トリガー語のメモリ化で Playbook 参照を自動化する

メモリが単体で効く場面は、実はそれほど多くない。メモリが本当に威力を発揮するのは、他の層と組み合わさったときだ。代表例が「トリガー語のメモリ化」である。

私のメモリには `feedback_quality_gate.md` というファイルがある。中身を要約するとこうだ。

> ユーザーの指示に「採点 / スコア / 品質ゲート / SEO評価 / 100点満点 / 合格判定 / 公開GO」といった語が含まれたら、委任プロンプトを書き始める前に `ops/playbooks/article/quality-gate.md` を必ず開く。

これは「特定の言葉を見たら、特定の Playbook を読みにいけ」という指示だ。つまりメモリが Playbook への参照を発火させる引き金になっている。メモリ層と Playbook 層が手を組んで初めて機能する仕組みである。

このファイルが生まれた経緯ははっきりしている。2026年5月14日、私が「スコアもつけて」という趣旨の指示を出したとき、Claude（COO 役のエージェント）は既存の品質ゲート Playbook を参照せず、その場で思いついた独自の採点尺度でレビューを走らせてしまった。実際には正規の3軸品質ゲート Playbook が既に存在していたのに、それを開かないまま独自基準で動いた。結果として、その採点は組織内の過去スコアと比較できない孤立したものになった。

この事故の本質は「Playbook はあったのに、それを開く引き金がなかった」ことにある。Playbook をいくら整備しても、「いつそれを開くか」が設計されていなければ参照されない。そこで私は「採点系の語を見たら必ず該当 Playbook を開く」という引き金を `feedback_*.md` として保存した。以降、Claude はセッション開始時にこの索引を読むので、採点系の語に反応する準備ができた状態でセッションに臨む。

ここに、メモリ層の固有の価値がある。同じ「引き金」をサブエージェントの定義ファイルに書くこともできる。だがメモリに置くと、Claude が毎セッション必ず読み込む索引の一部になる。「定義ファイルに書いたが、たまたまその定義を読まないセッションでは効かなかった」という取りこぼしが起きにくい。メモリは「毎回必ず目を通す覚え書き」という性格を持つから、引き金の置き場として相性がいい。

### 価値観メモリは影響範囲を意識して扱う

メモリに保存できるもののなかで、最も慎重に扱うべきなのが「価値観」だ。

私のメモリには `feedback_family_name_privacy.md` がある。「家族(妻・息子・親族)の固有名詞は、記事・公開文章に出さない。呼び方は一般名詞に統一する」という内容だ。これは2026年5月15日、Claude が TODO のメモから家族の固有名詞を拾って派生ネタ案に使ってしまった事故を受けて保存したものだ。

このメモリは強力だ。一度書くと、記事執筆・ネタ提案・草稿・対話のほぼすべての出力に影響する。「次の失敗を防ぐ」という意味では理想的なメモリだが、同時にこういう価値観メモリは、書いた瞬間からすべての出力を支配することを意識しておく必要がある。

だから私は、価値観に類するメモリを増やすときは、影響範囲を一度立ち止まって考えることにしている。「この一文は、今後あらゆる出力に効く。本当にそれでいいか?」を確認する。プロジェクトの憲法にあたる CLAUDE.md には「価値観・ルールの変更を承認するのはユーザーである」という原則を置いているが、価値観メモリの追加はこの原則に近い重みを持つ。技術的には Claude がいつでも書き込めてしまうからこそ、書く側が慎重さを持つ必要がある。

### 「覚えさせない」判断も設計のうち

ここまで「何を渡すか」を書いてきたが、メモリ設計でそれと同じくらい重要なのが「何を渡さないか」だ。

判断基準はシンプルで、**毎回その場で調べたほうが正確で速いものは、覚えさせない**。たとえば次のような情報だ。

- 今日の日付
- 最新のコミットハッシュ
- 直近の PR の状態
- 記事の現在の本数

これらをメモリに書くと、書いた瞬間から陳腐化が始まる。今日の日付は明日には間違いになる。コミットハッシュは次のコミットで古くなる。記事本数は1本書けばずれる。こういう「時間とともに必ず変わる事実」は、メモリに固定するのではなく、実行時に `date` コマンドや `git log` や `wc` で取得すべきだ。

実際、本章を書くにあたっても、ネタ帳には「MEMORY.md は34行」と書いてあったが、執筆直前に実測したら38行だった。ネタ帳作成日と執筆日のあいだに記憶が4行増えていたのだ。これがまさに「変わる数字はメモリに固定してはいけない」ことの実例で、私は本章では実測値の38行を採用している。もしこの「34行」をメモリに固定していたら、Claude はずっと古い数字を信じ続けたはずだ。

覚えさせるべきは「変わらない事実」と「変わりにくい価値観」に限る。逆に言えば、変わるものを覚えさせないだけで、メモリの肥大化はかなり防げる。「覚えさせない」は、メモリ設計における立派な設計判断なのだ。

## 渡しすぎると何が起きるか——肥大化と削る機制

### メモリが膨らむとコンテキストを圧迫する

メモリの怖いところは、増やすコストが極端に低いことだ。「これも覚えさせておくと便利かも」と思った瞬間に1ファイル増やせる。罪悪感もほとんどない。だからこそ、気づくとメモリは際限なく膨らむ。

膨らんだメモリは、3つの形で害をなす。

第一に、コンテキストの圧迫だ。索引も本体も、必要に応じて Claude のコンテキストウィンドウに読み込まれる。メモリが多いほど、本来タスクそのものに使うべき窓が覚え書きで埋まる。これはサブエージェント層やスキル層、MCP 層でも繰り返し出てくる、本書全体に通底する害だ。渡したものは全部、窓の容量を食う。

第二に、古いメモリが判断ミスを誘発する。完了したプロジェクトの状態や、もう変わってしまった制約が `project_*.md` として残っていると、Claude はそれを今も生きている前提として読んでしまう。間違った前提から出発した判断は、間違った結論に着く。

第三に、境界が曖昧になる。メモリが増えるほど、「これは記憶として持つべきか、CLAUDE.md のルールにすべきか、それとも Playbook に書くべきか」の線引きが曖昧になる。同じ趣旨のことがメモリにもルールにも書かれている、という重複が生まれ始める。

### 削る機制——200行・3分類・索引・「覚えさせない」、そして /dream

では、肥大化にどう対抗するか。私は4つの構造的な歯止めと、1つの能動的な整理機制を持っている。

構造的な歯止めはこれまで本章で説明してきた通りだ。(1) `MEMORY.md` の行数に上限の目安を設ける（公式仕様でも `MEMORY.md` の冒頭200行または25KBを超えた分はセッション開始時に自動読み込みされない——書きすぎると読まれなくなる、という第1章の話のメモリ版だ。私のプロジェクトは現状38行と余裕があるが、この200行という数字は「超えたら圧迫するかもしれない」ではなく「超えたら黙って読み込まれなくなる」上限だと意識しておくほうがいい）。(2) 3種類の粒度に分けて更新リズムを管理する。(3) 索引と本体を分けて深掘り読みにする。(4) 「覚えさせない」判断を設計に組み込む。

そして5つ目、これらの歯止めだけでは防ぎきれない「重複の蓄積」と「古い記憶の残存」に対処するために、私は `/dream` というスキルを運用している。

`/dream` は、メモリファイル群(`~/.claude/projects/*/memory/` 配下)に対して、次の3つの整理操作を行うスキルだ。

- **重複マージ**: 同じ行動ルール・制約が複数ファイルに散らばっていたら、より詳細・最新のファイルに統合する
- **矛盾更新**: 古い記述と新しい記述が食い違っていたら、新しいほうに揃える
- **新インサイト抽出**: 直近のセッションから、まだメモリ化されていない再発防止策を拾う

名前のとおり、人間が眠っているあいだに記憶を整理する睡眠のメタファーで、メモリの「掃除」を担う。重要なのは、`/dream` がデフォルトで dry-run(変更案の提示のみ・書き込みなし)で動くことだ。実際に書き換えるには `--apply` を明示的に付ける必要がある。メモリという「Claude の判断の土台」を自動でいじる操作だからこそ、提案と実行を分け、人間が中身を確認してから適用する設計にしている。第6章で扱う「安全装置」の考え方が、ここでも効いている。

ここで第1章(CLAUDE.md)との混同を避けておきたい。`/dream` が整理するのは、あくまで `memory/` 配下のメモリファイルだ。CLAUDE.md に書いた古いルール行やトリガー行の退役は、`/dream` の守備範囲ではない——第1章で正直に書いたとおり、そちらはまだ定期的な手動レビューに頼っている段階だ。「記憶の掃除」と「ルールの掃除」は、対象も機制も別物として分けている。両方を一つのスキルで賄おうとすると、どちらの整理も中途半端になる。

### 全部覚えさせるのではなく、覚えるべきものだけ覚えさせる

メモリ層を一言でまとめるなら、設計の要諦は「全部覚えさせる」ではなく「覚えるべきものだけ覚えさせる」に尽きる。

覚えるべきものとは、「次に同じ失敗をしないために必要な、変わらない事実と変わりにくい価値観」だ。覚えさせないものとは、「毎回調べたほうが速い変動情報」と「あれば雰囲気が出る程度の好み」だ。この線引きを持ったうえで、3分類で更新リズムを管理し、索引と本体を分けてコンテキストを節約し、`/dream` で定期的に重複と古い記憶を掃除する。これがメモリ層の「渡しすぎない」設計の全体像になる。

ただし正直に書いておくと、「いつ削るか」のリズムは、私のプロジェクトでもまだ定常運用に乗りきっていない。`/dream` という整理の道具は手元にあるが、それを「毎週走らせる」のか「メモリが何行を超えたら走らせる」のか、発火条件の自動化はこれからの課題だ。現状は、メモリが増えてきたと感じたタイミングで手動で `/dream` を回す、という事象ベースの運用にとどまっている。削る道具は揃ったが、削るタイミングの仕組み化は道半ば——これが本章執筆時点(2026年5月末)の正直なところだ。

それでも、削る道具を持っていることと持っていないことの差は大きい。次に読者が自分のメモリを設計するときの目安として、「`/dream` のような整理スキルを最初から用意しておき、まずは手動でいいから定期的に回す」ところから始めるのを勧めたい。発火条件の自動化は、運用しながら見えてくる。

### 次の章への接続

ここまで、私は Claude Code に5つのものを渡してきた。CLAUDE.md でルールを、サブエージェントで役割を、スキルで手順を、Playbook で判断の地図を、そして本章のメモリで「次に同じ失敗をしないための記憶」を渡した。

だが、これだけではまだ足りないものがある。「Claude が何をしてよくて、何をしてはいけないか」の境界線だ。どれだけ良い記憶を渡しても、Claude が触れてはいけないものに触れられる状態のままでは、いつか事故が起きる。逆に、許可を絞りすぎれば Claude は動けなくなる。

次の第6章では、その境界線を引く層——設定・権限を扱う。何を許し、何を禁じるか。`settings.local.json` に最小権限をどう設計し、過剰な許可がどんな事故を生むのか。記憶を渡したあとに引くべき、最後の防護壁の話である。
