# 第6章 設定・権限 ——「何をしていいか」を渡す

この章で扱うのは、Claude Code に「何をしていいか」の境界線を渡す場所、`settings.local.json` だ。前の章までで渡してきたもの——CLAUDE.md のルール、サブエージェントの人格、スキルの手順、Playbook の判断地図、メモリの記憶——は、どれも「Claude に何かを足す」操作だった。能力を増やし、判断材料を増やし、再現手順を増やす。だが設定・権限だけは方向が逆を向いている。ここで渡すのは能力ではなく、**境界**だ。「ここまではやっていい、ここから先はやってはいけない」という線を引く。

具体的に言えば、私のプロジェクトには `settings.local.json` が10箇所ある。プロジェクトルートに1つ、ワークスペース共通設定に1つ、COO専用に1つ、各サブエージェントのワークスペースに1つずつ（reader はワークスペースを持たないため、permissions を持つのは7体ぶん）。それぞれが、そのエージェントに「許す操作」のリストを抱えている。reviewer は読み取りとレビュー出力の書き込みだけ、writer は記事ファイルの書き込みあり、devops は権限管理のためほぼ全域に書き込みあり——というように、責務に応じて許可範囲が違う。この章では、その境界線の引き方と、引き方を間違えたときに何が起きるかを扱う。

通奏低音は本書の他の章と同じ「渡しすぎない」だ。ただし設定・権限のレイヤーでは、この通奏低音がもっとも素直な形で現れる。なぜなら、ここで渡しすぎることは即「過剰許可」を意味し、過剰許可はそのまま事故の入り口になるからだ。後半で実際に起きた事故——2026年4月のZenn記事一時非公開と、4回連続したブログ記事URL書き換え——を解剖しながら、「渡しすぎないこと自体が設計である」という本書の主題を、このレイヤーで確かめていく。

## 設定・権限とは何か——「境界線」を渡す場所

### 能力を足すのではなく、境界を引く

第7章で扱うMCPと並べると、設定・権限の性格がはっきりする。MCPは「何ができるか」を増やす仕組みだ。Gmailに繋げばメールが読めるようになり、カレンダーに繋げば予定が操作できるようになる。能力の追加である。

一方、設定・権限は「何をしていいか」を絞る仕組みだ。`settings.local.json` の `permissions.allow` に並ぶのは、「このコマンドの実行を許可する」というリストであって、新しい能力ではない。Claude Code はもともと `git` も `npm` も `rm` も実行できる。設定でやっているのは、その実行可能な操作のうち「このエージェントには、この範囲だけ許す」と線を引くことだ。

この違いは小さく見えて、設計の向きを決める。MCPの設計は「足し算」で考える——必要なものを繋いでいく。設定・権限の設計は「引き算」で考える——デフォルトで許される範囲を、必要な分まで絞り込んでいく。同じ「渡す」という動詞でも、足す方向と引く方向は正反対だ。この向きを取り違えると、「便利そうだから全部許可しておこう」という発想が生まれ、それが事故の温床になる。後半で見る事故は、ほぼすべてこの取り違えから始まっている。

### `settings.local.json` の中身

`settings.local.json` は、プロジェクトやエージェントごとに「許可する操作」と「環境変数」を記述するJSONファイルだ。中級者なら見たことがあるだろうが、構造を簡単に確認しておく。中心になるのは `permissions.allow` というリストで、ここに許可するツール・コマンドのパターンを並べる。たとえば私のレビュー担当エージェント（reviewer）のファイルはこうなっている（抜粋）。

```json
{
  "permissions": {
    "allow": [
      "Bash(gh issue:*)",
      "Bash(git log:*)",
      "Bash(git diff:*)",
      "Bash(grep:*)",
      "Read(...)",
      "Write(.../content/reviews/**)"
    ]
  }
}
```

ここでは私のレビュー担当エージェントを例に書くが、読者の環境では「コードレビュー役のエージェント」や「テスト実行役のエージェント」に置き換えて読んでほしい。重要なのは中身の思想だ。`Bash(git log:*)` は「`git log` で始まるコマンドを許可する」、`Write(.../content/reviews/**)` は「レビュー結果の保存先ディレクトリ以下への書き込みを許可する」という意味になる。

注目すべきは、ここに `Write` の対象がレビュー結果の保存先**だけ**で、記事本文の保存先が入っていないことだ。reviewer は記事を評価する役割であって、記事を書き換える役割ではない。だから書き込み権限を、レビュー結果の出力先だけに絞ってある。これが「境界線を渡す」ということの具体だ。reviewer に「記事を直しておいて」と頼んでも、権限がないので物理的に書き換えられない。役割と権限が一致している。

### 最小権限の原則を、組織に適用する

セキュリティの世界には「最小権限の原則」という古典的な考え方がある。あるアクターには、その仕事に必要な最小限の権限だけを与える、という原則だ。私はこれを、Claude Code のエージェント組織にそのまま適用している。

なぜ全エージェントに同じ広い権限を与えないのか。理由は単純で、**暴走したときの被害が、与えた権限の広さに比例する**からだ。仮にすべてのエージェントに「どこへでも書き込んでよい」という権限を与えていたとする。レビュー担当が何かの拍子に——プロンプトの誤解、想定外の指示の連鎖、あるいは私のミスで——記事本文を消そうとしたら、止めるものは何もない。だが reviewer に書き込み権限がレビュー結果の保存先だけしか渡されていなければ、それ以外の場所は物理的に守られる。

権限は「信頼」ではなく「設計」だ。エージェントを信頼するかどうかと、権限を絞るかどうかは別の話である。信頼しているからこそ、信頼が裏切られる事態に備えて境界を引く。これは人間の組織でも同じで、経理担当を信頼していても、全員に経理システムの全権限を渡したりはしない。役割に応じて触れる範囲を決める。Claude Code のエージェント組織でも、考え方は変わらない。

私の組織では、おおまかに次のような濃淡で権限を配っている。

- **読み取り中心**（reviewer など）：Read と一部の参照系コマンド、レビュー結果の出力先への Write
- **書き込みあり**（writer など）：記事ファイルの保存先への Write を追加
- **権限管理も担う**（devops）：設定ファイルの編集を含む広い範囲への Write

実測で確認すると、各ワークスペースの `settings.local.json` の行数はばらついている。読み取り中心の reviewer は32行、書き込みを伴う writer は56行、権限管理を担う devops は56行、調査範囲が広い researcher は91行といった具合だ（2026-05-31 時点、`wc -l` で実測）。行数そのものに意味はないが、責務が広いエージェントほど許可リストが長くなる傾向は読み取れる。プロジェクトルートの共通設定は619行と突出して長い。ここは全エージェントが共有する土台なので、git 操作・参照系コマンド・環境変数など、組織全体で使うものが集まっている。

責務と許可の対応を、もう少し具体的に見てみよう。調査担当の researcher は、外部のWebページを取得する権限が必要だ。実際、researcher の許可リストには `WebFetch(domain:*)` という「あらゆるドメインへのアクセスを許可する」パターンが入っている。一見すると「渡しすぎ」に見えるかもしれないが、調査がそのエージェントの責務である以上、調査先のドメインを事前に列挙しきることはできない。だから researcher にはWebアクセスを広く許す。一方、レビュー担当の reviewer の許可リストでは、`WebFetch` の対象を `zenn.dev`・`qiita.com`・`note.com` のように、レビューで参照する可能性が高いドメインに限定している。同じWebアクセスの権限でも、責務が「調査」か「レビュー」かで広さが違う。

ここに「責務に応じた許可」の本質がある。広く許すか狭く許すかは、エージェントの偉さや信頼度で決まるのではない。**その責務を果たすために、どこまでの範囲が本当に必要か**で決まる。researcher にWebアクセスを広く許すのは researcher を特別扱いしているからではなく、調査という仕事がそれを要求するからだ。reviewer のWebアクセスを絞れるのは、レビューという仕事が参照先を予測できるからだ。許可リストを書くとき、私はいつも「この権限は、この責務に本当に必要か」を自問する。必要なら広く、不要なら狭く。判断軸は責務であって、信頼ではない。

ここで一つ、私自身がまだやれていないことを正直に書いておく。許可リストは「足すのは簡単だが、剥がすのは忘れやすい」。一度 `allow` に追加した権限は、使われなくなっても消されずに残りがちだ。本来は、使われていない権限を定期的に棚卸しして剥がす「監査」が必要なのだが、私の組織ではこれを定期作業として仕組み化できていない。後述する devops エージェントが権限管理を担っているので、いずれは「使われていない許可ルールを検出して提案する」工程を組み込みたいと考えているが、現時点では手作業の気づきに頼っている。最小権限の原則は「絞る」と「絞り続ける」の両方が要るのに、私はまだ前者しかできていない。これは本章の後半で繰り返し出てくる「渡しすぎ」の、自分自身の現在地でもある。

## 何を渡すか——許可と禁止の書き方

### 権限パターンには $HOME も ~ も展開されない

設定・権限のレイヤーで最初につまずくのは、たいてい「書いたのに効かない」という現象だ。`allow` に許可パターンを書いたのに、実行しようとすると許可されていない扱いになる。原因の多くは、**パスの書き方**にある。

実測で確かめた事実を一つ共有する。`settings.local.json` の権限パターンの中では、`$HOME` も `${HOME}` も `~` も**展開されない**。たとえばホームディレクトリ以下の `.claude` への編集を許可しようとして、こう書いたとする。

```json
"Edit(~/.claude/**)"
```

これは効かない。`~` がホームディレクトリのパスに展開されず、文字どおり `~/.claude/**` という文字列として扱われるため、実際のパスにマッチしないのだ。私はこれを2026年4月に実測で確認し、本書のプロジェクトでは「パス記述方針」というルールファイルに記録した。ホームディレクトリ以下を指定したい場合は、`/Users/ユーザー名/.claude/**` のようにフルパスで書く必要がある。

なぜこれを「実測で確認した」とわざわざ書くかというと、設定・権限のレイヤーでは**ドキュメントの記載と実機の挙動がずれることがある**からだ。「環境変数が使えるはず」という思い込みで書いて、効かない理由が分からず時間を溶かす——これは設定レイヤー特有の沼だ。だから私は、権限パターンの前提条件は推測で書かず、一度小さく試して挙動を確かめてから本採用する、という運用にしている。`settings.local.json` は記述しても即座にエラーを出してくれるわけではなく、「マッチしないので許可されない」という形で静かに失敗する。静かな失敗ほど厄介なものはない。

ちなみに、フルパスを書く必要があるのはホームディレクトリ以下のような「プロジェクト外」を指す場合だ。プロジェクト内を指すなら**相対パスが使える**。`Edit(.claude/**)` や `Write(content/**)` のように、プロジェクトルートを基準にした相対パスで書ける。プロジェクト内は相対パス、プロジェクト外（ホームディレクトリ等）はフルパス——この使い分けを覚えておくと、無駄な「効かない」に悩まずに済む。

> **Windows 環境の注意**：本書は Mac 環境を前提に書いている。Windows でも `settings.local.json` の `$HOME`・`~` 非展開は同じだが、パスの書き方が異なる（`/c/Users/ユーザー名/...` のような形式や、バックスラッシュのエスケープ）。Windows で運用する場合は、パス区切りとドライブ表記を環境に合わせて読み替えてほしい。

### パターンの書き方で挙動が変わる——`git -C` の話

許可パターンは、書き方ひとつで実行時の挙動に影響する。私の組織で実際に効いている例を挙げる。

プロジェクトルートの共通設定には、git の操作を細かく許可するパターンが並んでいる。`Bash(git add:*)`、`Bash(git commit:*)`、`Bash(git log:*)`——というように、サブコマンド単位で許可している。そして、この中に `Bash(git -C:*)` というパターンが含まれている。

`git -C <パス>` は「指定したディレクトリで git コマンドを実行する」というオプションだ。なぜわざわざこれを許可リストに入れているかというと、本書のプロジェクトには「Bash ツールの中で `cd` を使わない」という運用ルールがあるからだ。`cd` で作業ディレクトリを移動すると、その移動が次以降の Bash 呼び出しにも引き継がれてしまい、ディレクトリ依存のツールが壊れる。だから別のディレクトリで git を操作したいときは、`cd path && git ...` ではなく `git -C path ...` を使う。

ここに権限パターンの機微がある。`Bash(git -C:*)` という許可パターンを置いておくことで、「ディレクトリ移動なしの git 操作」が確実に許可される。逆に言えば、もしこのパターンを書かずに `Bash(git:*)` のような大雑把な許可だけにしていたら、許可は通るかもしれないが、運用ルール（`cd` 禁止）と権限設計が連動しない。許可パターンは、ただ通すためだけでなく、「どういう書き方を推奨するか」を権限のレベルで誘導する道具でもある。

逆の例として、`Bash(*)`——あらゆる Bash コマンドを許可する——のような網羅指定は、最小権限の原則からは避けるべきだ。これを書いた瞬間に、「何を許して何を許さないか」という境界線が消える。あらゆるコマンドが通るなら、設定・権限のレイヤーは存在しないのと同じになる。許可リストを書く意味は、書かれていないものは許されない、という非対称性にある。`Bash(*)` はその非対称性を自ら放棄する書き方だ。

### 環境変数を仕込むのも、権限設計のうち

`settings.local.json` には `permissions` のほかに `env` というセクションがある。ここで環境変数を定義しておける。私のプロジェクトルートの設定には、こういう環境変数を仕込んである（抜粋）。

```json
"env": {
  "PROJECT_ROOT": "/Users/ユーザー名/workspace/000-partner",
  "HATENA_DIR": "/Users/ユーザー名/workspace/hatena-content"
}
```

`PROJECT_ROOT` を定義しておくと、スクリプトを呼び出すときに `bash "$PROJECT_ROOT/scripts/..."` という形で書ける。これがなぜ重要かというと、`cd` を使わずにプロジェクト内のスクリプトを確実に呼べるからだ。前項で「`cd` を使わない」という運用ルールに触れたが、その代替手段の一つがこれだ。作業ディレクトリがどこにあっても、`$PROJECT_ROOT` を頭に付ければ目的のスクリプトに辿り着ける。

環境変数の定義は、一見すると「権限」とは関係なさそうに見える。だが私は、これも広い意味での権限設計の一部だと考えている。なぜなら、`$PROJECT_ROOT` や `$HATENA_DIR` を仕込むこと自体が、「エージェントにどういう実行コンテキストを渡すか」を決める行為だからだ。次の節で詳しく見るが、実行コンテキスト——どこから・どういう環境で実行するか——の設計を怠ると、許可は正しく与えていても事故が起きる。環境変数を「安全に参照できる起点」として仕込んでおくことは、許可リストを絞ることと同じくらい、境界線の設計に効いてくる。

## どう渡すか——非対称ルールと環境別運用

### devops だけは「事後報告でいい」——非対称ルールの設計

ここまで「最小権限」「絞る」という話をしてきたが、その原則に一見すると矛盾するルールが、私の組織には一つある。権限管理を担当する devops エージェントだけは、**自分自身の権限を、事前承認なしに拡張してよい**ことになっている。ただし条件があって、拡張したら**事後に報告する義務**を負う。

このルールは非対称だ。整理するとこうなる。

- **devops が、自分の `settings.local.json` の権限を拡張する**：事前承認は不要。ただし作業完了時に「何の権限を、なぜ追加したか」を報告する義務がある
- **devops が、他のエージェントの `settings.local.json` の権限を拡張する**：事前承認が必須

同じ「権限を拡張する」操作なのに、対象が自分か他人かで、求められる手続きが正反対になっている。なぜこんな非対称を設けているのか。

導入のきっかけは、2026年5月のある場面だった。devops が作業中に、編集ツールの権限が足りずに手が止まった。ホームディレクトリ側のパスへの編集権限が、その時点では許可リストに入っていなかったのだ。devops は自分の設定ファイルにそのパスを追記して権限不足を解消し、作業を続けた。後から私（ユーザー）がそれを承認した。この事例から、「権限管理が本来の責務である devops に、毎回自己権限の事前承認を求めるのは、機動性を損なうわりに得るものが少ない」という判断が固まった。

非対称にする理屈はこうだ。devops が**自分の**権限を拡張するのは、影響範囲が devops 自身に閉じている。失敗しても被害は局所的だ。しかも devops の本来の責務に「権限管理」が含まれているので、自己権限の調整は職務の範囲内とみなせる。だから事前承認のハードルを下げ、事後報告で透明性だけ担保する。

一方で、devops が**他の**エージェントの権限を拡張するのは、影響範囲が組織全体に波及する。あるエージェントの許可リストを広げれば、そのエージェントが暴走したときの被害が広がる。これは局所的な判断で済ませてよい話ではないので、事前承認を必須にする。

この非対称設計が教えてくれるのは、「最小権限の原則」は機械的に全員へ一律適用するものではない、ということだ。権限の自己調整がそのエージェントの職務に含まれていて、かつ影響が局所的なら、手続きを軽くしてよい。影響が組織に波及するなら、手続きを重くする。**影響範囲の広さで手続きの重さを決める**——これが、絞ることと機動性を両立させる勘どころだ。一律に厳格化すると組織が止まり、一律に緩めると事故が起きる。境界線は、影響範囲という軸で引く。

読者が自分の組織にこれを取り入れるとき、参考になる問いはこうだ。「あるエージェントに権限の自己調整を許すとして、その調整の影響はどこまで及ぶか」。影響が自分のワークスペースに閉じるなら事後報告で足りる。影響が他のエージェントや共有設定に及ぶなら事前承認を要る。この「影響の届く範囲」を見極める習慣があれば、手続きの軽重を自分で設計できる。最小権限の原則を「全員に同じ厳しさ」で適用しようとすると、機動性が必要な役割が窒息する。原則は守りつつ、影響範囲という軸で例外を設計する——この柔らかさが、運用を回し続けるコツだ。

### どこから実行するかで、許される権限が変わる

権限のもう一つの機微は、「同じ操作でも、どこから実行するかで結果が変わる」ことだ。これを私は、Claude Code をCLIから使う場合とWeb版（Claude Code on Web）から使う場合の違いで思い知った。

私の組織では、CLIから実行する場合、デフォルトブランチ（master）へ直接コミットして push してよいことになっている。ローカル環境からの操作なので、権限上の制約がない。ところがWeb版から同じことをやろうとすると、デフォルトブランチへの直 push が**権限制限で拒否される**。HTTP 403 が返ってくるのだ。これは2026年5月に、実際にWeb版での作業中に弾かれて判明した。

対処は、実行環境ごとに運用ルールを分けることだった。

- **CLI環境**：デフォルトブランチへ直接 commit・push してよい
- **Web環境**：デフォルトブランチへの直 push は拒否されるので、作業用のブランチ（`claude/<識別子>`）へ push し、そこからデフォルトブランチへのプルリクエストを作ってマージする

ここで面白いのは、「同じコミット操作」が、実行環境によって許される/許されないに分かれることだ。権限は `settings.local.json` だけで決まるのではない。実行環境（CLIかWebか）という、設定ファイルの外側にある条件も、何が許されるかを左右する。私はこれを「メタな権限設計」と呼んでいる。`settings.local.json` に書いた許可がすべてだと思っていると、環境側の制約に弾かれて「なぜ通らないのか」と悩むことになる。権限は、設定ファイルと実行環境の**両方**で決まる。

### 実行コンテキストの罠——CWD依存

実行環境が権限に影響する、という話の延長線上に、本章でもっとも厄介な事故が控えている。「作業ディレクトリ（CWD）依存」の問題だ。これは6.4節の事故解剖の伏線になるので、ここでは仕組みだけ押さえておく。

私の組織では、はてなブログとの同期に `blogsync` という外部ツールを使っていた時期がある。`blogsync` の設定ファイルには、`local_root` という記事の保存先を指定する項目があり、これが**相対パス**で書かれていた。相対パスは「現在の作業ディレクトリからの相対」で解決される。つまり、ツールを実行したときのCWDが想定とずれていると、相対パスの解決結果もずれる。

ここに、前述の「Bash ツールで `cd` を使わない」ルールが効いてくる。Bash ツールの中で `cd` を実行すると、そのCWDの変更が次以降の Bash 呼び出しに引き継がれる。すると、CWD依存の外部ツールを呼んだときに、想定外のディレクトリで相対パスが解決され、おかしなパスが生成される。**権限は正しく与えているのに、実行コンテキスト（CWD）の設計を誤ると壊れる**——これがこの罠の本質だ。

対処は二段構えだった。一つは、外部ツールを呼ぶときはサブシェルで隔離すること。`( cd $HATENA_DIR && ツール実行 )` のようにカッコで囲むと、`cd` の効果がカッコの内側に閉じ込められ、外側のCWDに漏れない。もう一つが、前節で触れた `$PROJECT_ROOT` のような環境変数を仕込んで、`cd` そのものを避けることだ。

「許可を与える」だけでは、設定・権限のレイヤーは完成しない。**どこで・どういうコンテキストで実行されるか**まで設計して、ようやく境界線が機能する。次の節で、この設計を怠ったときに何が起きたかを、実際の事故記録から解剖する。

## 渡しすぎると何が起きるか——AUTO_SYNC_ZENN とブログURL 4連発

ここまで「境界線の引き方」を扱ってきた。最後に、境界線を引き損ねたとき——渡しすぎたとき——に実際に何が起きたかを、二つの事故から解剖する。一つは「過剰なデフォルト値」が招いた事故、もう一つは「実行コンテキストの見落とし」が4回繰り返された事故だ。どちらも、設定・権限のレイヤーが「渡しすぎない」ことの大切さを、痛みとして教えてくれた事例である。

### 事故1：AUTO_SYNC_ZENN——「便利だから on」が招いた一時非公開

2026年4月23日、私の組織で記事の同期に関わる設定値 `AUTO_SYNC_ZENN` が、独断で `true`（自動同期を有効）にデフォルト化された。その結果、Zenn に公開していた記事5本が、一時的に非公開（unpublish）状態になった。復旧作業で実害は限定的に収まったが、公開状態の整合性が一時的に崩れた。（この事故は第1章でも取り上げた。第1章ではルール設計——抽象ルールが auto mode で失火するという観点から解剖した。本章では設定レイヤーから見た構造を扱う）

事故の構造を分解すると、こうなる。当時の私の組織には、「ユーザーや組織への不利益を発見したらユーザーに確認する」という抽象的なルールしかなかった。問題は、この「不利益かどうか」の判定が、Claude 側の主観に委ねられていたことだ。設定値のデフォルトを変えることが「不利益になりうる操作」だと、その場で判定されなかった。だから自動モードで実行が進み、誰も止めないまま記事が非公開になった。

ここで重要なのは、これが**設定レイヤーの事故**だという見方だ。`AUTO_SYNC_ZENN=true` というデフォルト値の変更は、まさに「設定で挙動の on/off を切り替える」操作である。そして、デフォルトを `true` にするということは、「確認なしに自動で動く」という権限を、暗黙のうちに渡したことを意味する。「便利だから on にしておこう」「デフォルトで動くようにしておけば手間が省ける」——この発想こそが、設定レイヤーにおける「渡しすぎ」の典型だ。便利さと引き換えに、確認のステップという境界線を一つ取り払ってしまった。

では、どう直したか。興味深いことに、この事故の再発防止策は、設定レイヤーそのものではなく、第1章で扱ったCLAUDE.md のレイヤーに入った。CLAUDE.md のトリガーリストに、こういう一行を加えたのだ——「デフォルト値変更で挙動 on/off を切り替える」操作は、自動モードでも必ず停止してユーザーに確認する。

なぜ設定レイヤーで起きた事故を、CLAUDE.md レイヤーで防ぐことになったのか。理由は、`settings.local.json` の許可リストでは「デフォルト値を変える判断そのもの」を縛れないからだ。許可リストはコマンドやパスへのアクセスを縛れるが、「便利だから on にしよう」という**判断**は縛れない。判断を縛るのは、CLAUDE.md に書いた「いつ立ち止まるか」のトリガーの仕事だ。つまり、設定レイヤーで防げなかった事故を、その上位のCLAUDE.md レイヤーのトリガー追加で結果的にカバーした。

これは本書の主題である「レイヤーは連動する」の好例でもある。各レイヤーは独立しているように見えて、ある事故は複数のレイヤーにまたがる。設定で防ぎきれない判断は、CLAUDE.md のトリガーで止める。一つのレイヤーで完結させようとせず、レイヤー間で守りを補い合う——この多層防御の発想が、設定・権限を考えるうえで欠かせない。

### 事故2：ブログURL書き換え4連発——実行コンテキストの見落とし

もう一つは、もっと粘り強く繰り返された事故だ。はてなブログとの同期に使っていた `blogsync` という外部ツールが、記事のカスタムURLを書き換えてしまう事故が、2026年5月の間に**4回**起きた。5月4日、5月14日、5月15日、5月20日。発生間隔がだんだん短くなっていったのが、当時の私には不気味だった。対策を入れても、入れた先から次の事故が起きる。（この事故は第1章でルール設計の側から解剖している。本章では設定・権限レイヤーの視点で同じ事故を見直す）

事故の表面的な症状はこうだ。記事のURLが `/entry/2026/04/19/095933` のような正常な形から、`/entry/saitoko.hatenablog.com/entry/2026/04/19/095933` のように、ドメイン名が途中に挟まった「二重パス」に書き換わる。最大の被害となった5月20日の事故では、これが5記事で同時に起きた。URLが変わるということは、既存のアクセス・SNSの被リンク・検索エンジンのインデックスが一時的に分断されることを意味する。地味だが、公開済みの記事にとっては痛い。

根本原因は、6.3節で伏線を張った「CWD依存」だった。`blogsync` の設定ファイルにある記事保存先の指定が相対パスで書かれていて、作業ディレクトリが想定とずれると、相対パスの解決結果がずれ、二重パスが生成される。だが、それだけでは4回も繰り返した説明がつかない。4回目の事故の調査で、もっと厄介な真因が判明した。

一度二重パスが生成されると、ローカルの記事ファイルの中に書かれた「URLフィールド」自体が、二重パス形式に**汚染される**。そして、その汚染されたファイルを次に同期すると、ツールが汚染済みのURL値をそのままサーバーに送信し、はてな側のURLが**再び**書き換わる。つまり、最初の事故が次の事故の種を仕込んでいた。作業ディレクトリを正しく直しても、データの方が汚染されているので再発する。原因が「実行コンテキスト」から「汚染されたデータ」へとすり替わっていたために、対策がなかなか効かなかったのだ。

そしてこの事故が、本章の主題にとって特に重い教訓を残した。それは——**「修正した」と「事故が再発しないと実証された」は別物だ**、という教訓だ。

5月20日の事故対応では、修正コミットを入れた直後に、念のため1記事だけテスト実行した。理論上、修正で直っているはずだった。ところが、その1件目のテスト実行で、修正前と完全に同じ事故が再発した。当時の私（と組織）は「修正したのだから、テスト実行を承認してよい」と判断していた。だがその判断こそが甘かった。修正コミットがあっても、それが真の修正である保証はない。特に、過去に同型の事故を起こした操作を再実行するときは、修正コミット直後の1件目こそ、もっとも警戒すべきフェーズだったのだ。

この教訓から、運用ルールが変わった。同期ツールのような「過去に事故型がある操作」を再実行するときは、一括で回さない。「1件だけ本実行 → 異常がゼロだと確認 → 残りを再承認」という段階を必ず踏む。1件目で異常が出たら、その時点で全部止める。一括で5件を回していたから5件とも壊れたのであって、1件ずつ刻んでいれば被害は1件で止められた。

最終的にツール側には、同期の前にURLフィールドの汚染を検査して、汚染があれば処理を中止する防御や、同期の後にURLの書き換えを検出して即座に残りの処理を止める防御が追加された。だが、これらの技術的な防御以上に効いたのは、運用面の「段階実行を必須にする」というルールだった。技術で塞ぎきれない穴を、運用の慎重さで埋める。これも一種の境界線の引き方である。

### 削る機制——絞り続けるための仕組み

二つの事故に共通するのは、「渡しすぎ」が事故の入り口になったことだ。AUTO_SYNC_ZENN は「便利だから自動で動く権限」を渡しすぎた。ブログURLの事故は「実行コンテキストへの注意」を払わずに一括実行する裁量を渡しすぎた。では、渡しすぎを防ぐ「削る機制」として、私の組織には何があるか。整理しておく。

- **最小権限の原則を組織に適用する**：各エージェントに、責務に必要な最小限の権限だけを与える。reviewer に書き込みをレビュー結果の保存先だけに絞る、というあれだ
- **CLAUDE.md のトリガーリストと連動させる**：設定の許可リストでは縛れない「判断」を、CLAUDE.md のトリガーで止める。デフォルト値の変更、一括操作、自動実行の登録などは、自動モードでも立ち止まる
- **影響範囲で手続きの重さを変える**：devops の自己権限拡張は事後報告、他エージェントの権限拡張は事前承認。一律に厳格化も緩和もしない
- **環境別の運用ルール**：CLI と Web で許される操作を分ける。実行環境という外側の条件まで含めて境界を引く
- **段階実行を強制する**：過去に事故型のある操作は、一括で回さず1件ずつ刻んで、異常がゼロだと確認してから次へ進む

ただし、6.1節で正直に書いたとおり、これらの「削る機制」のうち、定期的な棚卸し（使われていない許可ルールを剥がす監査）は、私の組織ではまだ仕組み化できていない。許可を絞って与えることはできていても、与えたあとに「もう要らなくなった許可」を剥がし続ける工程が回っていない。最小権限の原則は「絞って与える」と「絞り続ける」の両輪で初めて完成するのに、私はまだ片輪で走っている。これは次に手を付けるべき宿題として、本書に書き残しておく。当面は devops の権限管理の役割を拡張する形で、不要な許可ルールの検出と剥がしを定常作業に組み込んでいくのが、現実的な次の一歩だと考えている。

### 次の章へ——境界線の次は、能力そのもの

この章では、Claude Code に「何をしていいか」の境界線を渡す方法を見てきた。許可リストで操作を絞り、影響範囲で手続きの重さを変え、実行コンテキストまで設計する。そして、渡しすぎると——便利さに引きずられて境界線を一つ取り払うと——事故の入り口になる。設定・権限のレイヤーは、本書の通奏低音「渡しすぎない」が、もっとも素直に、もっとも痛みを伴って現れる場所だった。

ここまで6つのレイヤーで渡してきたものは、ルール・人格・手順・判断・記憶・境界——どれも「Claude Code の内側」に仕込むものだった。だが、Claude Code が一人で——いや一組織で——できることには限界がある。外の世界に繋がなければ、メールも読めないし、カレンダーも操作できない。最後に渡す部品は、内側に仕込むものではなく、外の世界への「接続口」そのものだ。

次の第7章では、その接続口——MCP——を扱う。設定・権限が「何をしていいか」の境界線だったのに対し、MCPは「何ができるか」の能力追加だと、この章の冒頭で書いた。能力を足す方向の設計には、境界線を引く設計とはまた別の「渡しすぎない」が待っている。繋げすぎると、何が起きるのか。次の章で確かめよう。
