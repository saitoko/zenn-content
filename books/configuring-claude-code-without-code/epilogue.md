# エピローグ 削る設計こそが、渡す設計だった

本書は7つのレイヤーを一つずつ降りてきた。CLAUDE.md、サブエージェント、スキル、Playbook、メモリ、設定・権限、そして MCP。だが章を書き終えてみると、私はずっと同じ一つの問いを繰り返していたことに気づく。何を渡し、何を渡さないか——それだけだ。このエピローグでは、各章に散らばっていたその問いを一本に束ね直す。あわせて序章で予告した「本書は何の本だったのか」の種明かしをし、最後に、本書を閉じたあと最初にやってほしい一手を渡して終える。

## 結局、どの章でも同じ問いを繰り返していた

序章で私は、本書を「道具を順番に紹介するカタログのように見えるかもしれないが、そうではない」と書いた。読み終えた今なら、その意味がもう少し具体的に伝わるはずだ。

7つの章を並べてみると、扱った対象はまるで違う。CLAUDE.md は行動規範の置き場所で、MCP は外部ツールへの接続だ。スキルは実行手順で、メモリは失敗の記憶だ。レイヤーごとに渡す中身も、書く形式も、壊れ方も異なっていた。

それなのに、各章の後半で私が立てた問いはほとんど同じ形をしていた。このレイヤーには何を渡せるか。どこまで渡すか。渡しすぎたとき、何が起きるか。そして、どうやって削るか。対象が変わっても、設計の問いそのものは変わらなかった。

しかも「渡しすぎたときに何が起きるか」の中身は、レイヤーごとに固有のメカニズムを持っていた。ここで一度、章をまたいで並べておきたい。

- **CLAUDE.md**: ルールを書きすぎると、AI が読まなくなる。長さそのものが参照率を下げる。
- **サブエージェント**: 役割を分けすぎると、「誰に頼むか」の判断コストが増える。
- **スキル**: 「あとで使うかも」で作ったスキルは、使われないまま積み上がる。
- **Playbook**: 分岐を書き込みすぎた手引きは保守が追いつかず、古くなっても誰も気づかない。
- **メモリ**: 記憶を溜めすぎると、読み込みのたびにコンテキストを圧迫する。
- **設定・権限**: 「とりあえず全部許可」は、そのまま事故の入口になる。
- **MCP**: 繋ぎすぎると、ツールの定義そのものがコンテキストを食い続ける。

形は違うが、どれも「足したぶんだけ何かが重くなる」という同じ構造をしている。足し算には必ずコストがつくのだ。だから各章には、それを打ち消す「削る機制」を必ず一つ添えた。冗長ルールの整理、エージェントの統廃合、スキルの退役判定、Playbook の更新サイクル、メモリの上限管理、最小権限の原則、不要な MCP を外すこと。渡す技術と削る技術は、別々の話ではなかった。同じ設計の表と裏だった。

ここに、本書を貫いてきた一行の結論がある。**削る設計こそが、渡す設計だった。** 何を渡さないかを決めることは、渡すものを機能させるための前提条件であって、後始末ではない。渡しすぎたものは、渡したものまで巻き添えにして効きを悪くする。長すぎる CLAUDE.md の中では、本当に守ってほしい一行も埋もれてしまう。だから削ることは、渡すことの一部なのだ。

## 「カタログのフリ」の種明かし——これは設計書だった

ここで、序章で預けておいた約束を回収したい。

序章で私は、本書が「道具を順番に紹介するカタログのように見えるかもしれないが、足し算のカタログではなく、足し算と引き算の両方を含んだ設計書だ」と書いた。各章はたしかに「このレイヤーには何があるか」という道具紹介から入る。読み始めたときの体感は、Claude Code の機能を順に並べたカタログに近かったはずだ。だが種明かしをすると——本書は最初からカタログではなかった。設計書だった。

違いはこうだ。カタログは「何があるか」を網羅する。読者が持ち帰るのは、選択肢の一覧だ。一方、設計書が伝えるのは「同じ問いが、場所を変えてどう現れるか」である。本書で読者が7章を通じて体験したのは、後者だった。CLAUDE.md で出会った「渡しすぎると効かなくなる」という問いが、サブエージェントでも、スキルでも、Playbook でも、形を変えて何度も戻ってきた。レイヤーが違っても問いが同じだと気づいた瞬間、読者の手元には道具の一覧ではなく、**レイヤーをまたいで使える設計の判断軸**が残る。

カタログの体裁から入ったのは、回り道のためではない。判断軸というものは、抽象的に「渡しすぎるな」とだけ言われても身につかないからだ。CLAUDE.md という具体物で一度つかみ、サブエージェントという別の具体物で「あ、ここでも同じだ」と再確認し、それを7回繰り返して初めて、軸は読者の中で一般化する。カタログのフリは、その反復のための器だった。

だから、本書を読み終えた読者は、8つめのレイヤーに出会っても——たとえばこの先 Claude Code に新しい設定の置き場所が増えても——同じ問いを自分で立てられるはずだ。ここには何を渡せるか。どこまで渡すか。渡しすぎたら何が起きるか。どう削るか。実際、hooks（PreToolUse / PostToolUse といったツール実行の前後に処理を挟む仕組み）は、本書に一度も登場しなかったが「渡す場所」として機能する。本書を読み終えた後で hooks に出会っても、問いは同じだ。その問いを立てられるようになったなら、本書は設計書としての役割を果たしたことになる。

## 「装備の付与」とは、チームを信じられる状態にすることだった

序章でもう一つ立てた問いがある。本書が扱うのは「業務の肩代わり」ではなく「装備の付与」だ、という宣言だ。これも回収しておきたい。

7章を書き終えて、私の中で「装備の付与」の意味は、序章で書いたときより少しはっきりした。装備を渡すとは、結局のところ、**自分のチームを信じられる状態にすること**だった。

信じられないチームには、いくら業務を渡しても不安が残る。きちんとやってくれただろうか、勝手に何か壊していないか、と毎回確認するなら、それは渡したことにならない。確認のコストが、渡して浮いたコストを食い尽くしてしまう。

逆に、信じられるチームには、業務をいちいち手渡さなくても仕事が流れていく。なぜ信じられるのか。本書のあちこちで触れてきた失敗——設定を渡しすぎて Zenn 記事を一時的に非公開にしてしまった AUTO_SYNC_ZENN の事故や、外部 CLI への依存が原因で記事 URL を書き換えてしまった blogsync の連続事故——を経て、私は「危ない操作の前では必ず止まる」というトリガーを CLAUDE.md に積み上げてきた。事故のたびに一行ずつ増やしてきたそのリストがあるから、今では危険な一括操作を AI に任せても、勝手に走り出さないと信じられる。同じように、使われないスキルを3本退役させたことで、棚卸しのたびに「これは何のためにあるんだったか」と悩む手間が消えた。削った結果として、残った仕組みをより信じられるようになる——それが「装備の付与」の実感だ。CLAUDE.md に行動規範が書いてあり、危険な操作の前には必ず止まるトリガーが効いていて、サブエージェントの責務が分かれていて、Playbook に判断の地図があり、設定で権限が絞られているからこそ、安心して任せられる。本書が7章かけて渡し方を解剖してきた部品は、突き詰めれば「安心して任せられる土台」を組むための部品だった。

「装備の付与」は、便利な道具を渡すことではなかった。任せても大丈夫だと自分が思える状態を、自分の手で組むことだった。コードを一行も書けない私が Claude Code を動かし続けられている理由も、結局ここにある。私は AI に難しいことをさせているのではない。安心して任せられる土台を、少しずつ整えてきただけだ。

## 部品論はここまで——運用論は Vol.5「任せる」へ

本書はここで完結する。ただし、完結するのは「部品が何か」までだ。

7つの部品を一つずつ解剖してきたが、本書はあえて「これらを組み合わせると全体としてどう回るか」には踏み込まなかった。CLAUDE.md とサブエージェントと Playbook が噛み合って、一日の仕事がどう流れていくか——その全体の運用は、本書の射程の外に置いた。部品の設計と、部品を組み合わせた運用は、別の解像度の話だからだ。一つの本に詰め込むと、どちらも中途半端になる。

部品の設計が終わったら、次は「どう仕事を回すか」の設計に移る。タスクをどう集め、どう仕分け、どこで AI に判断を委ね、どこで自分が握るか。その運用の仕組みを、GTD という考え方を軸にして、Claude Code を組み込んだ自分専用の仕事管理として組み上げていく——それが、続く Vol.5 で扱う「任せる」話になる。本書が「渡す」までだとすれば、次は整えた仕組みに仕事の回し方そのものを「任せる」段になる。

シリーズの動詞を並べると、こうなる。作る(Vol.1)、回す(Vol.2)、書き続ける(Vol.3)、渡す(Vol.4・本書)、そして任せる(Vol.5)。本書は階段の4段目にあたる。前の3段で作り・回し・書き続けてきたチームに、本書で部品という装備を渡した。次の段では、その装備を着けたチームに、仕事の流れごと任せていく。

ただ、Vol.5 を待つ必要はない。むしろ待たないでほしい。本書で7つの部品を見てきた読者なら、組み合わせ方は自分の手で試せるはずだ。次巻は「私はこう組み合わせた」という一つの実例にすぎない。あなたの組み合わせは、あなたの仕事に合わせて、あなたが決めればいい。

## 本書が語れなかった課題——削る機制はまだ手探りのまま

7章を書き通して気づくのは、私自身が「削る側」でまだ手探りを続けているという事実だ。本書のなかで何度か「まだ未整備」と正直に書いた箇所がある。退役判定が自動で回っていないスキル、更新サイクルが手作業に頼っているPlaybookの棚卸し、整理しきれていない設定ファイル。これらは本書を書き終えた今も未解決のまま残っている。渡す設計を語った本の書き手が、削る側ではまだ後手に回っている——その非対称を隠したくはなかったから、各章の末尾に都度書いた。束ねてみると、これらはすべて「削る行為を仕組み化できているか」という問いに集約される。本書を書き終えた今も、その答えは出ていない。

## 読み終えたら、CLAUDE.md を一行だけ直す

最後に、本書を閉じたあと最初にやってほしい一手を渡して終わりたい。

自分の CLAUDE.md を開いて、**一行だけ直す**ことだ。

ここで「直す」と書いて、「足す」と書かなかったのには理由がある。本書の通奏低音は、ずっと「渡しすぎない」だった。その本を読み終えた最初の一手が「一行足す」では、話が合わない。だから最初の一歩は、足すのでも削るのでも整えるのでもいい、要するに「一行に手を入れる」ことに置く。

具体的には、たとえばこんな一手がある。どれか一つでいい。

- **使われていないルールを一行削る**。書いた当時は必要だったが、もう発火していないルール。それを消すだけで、残りのルールの密度が上がる。
- **抽象的なルールに「いつ発火するか」を一行書き足す**。「丁寧に確認する」のような曖昧な指示に、「〇〇のときは必ず止まる」という発火条件を添える。本書の第1章で見たとおり、条件が書かれていないルールは、自動実行のなかで黙って素通りされる。
- **サブエージェントの責務境界を一行はっきりさせる**。「このエージェントはここまで」という線を一本引き直すだけで、「誰に頼むか」の迷いが減る。

どれも数分で終わる、ごく小さな一手だ。だがこの一手を打つかどうかが、本書を「読んで閉じた本」にするか、「自分の仕組みをいじり始める起点」にするかを分ける。設計書は、読み終えてからが本番だ。読んだだけで何も変えなければ、あなたの CLAUDE.md は昨日と同じままで、本書はただの読み物で終わる。それが、私が最も避けたい結末だ。

序章の最後に、私は「CLAUDE.md から始めよう」と書いた。本書はそこから出発し、7つのレイヤーを巡って、また CLAUDE.md に戻ってきた。今度はあなたが、自分の CLAUDE.md を開く番だ。

問いはずっと一つだった。あなたのチームに、何を渡し、何を渡さないか。その答えを、まず一行から書き始めてほしい。
