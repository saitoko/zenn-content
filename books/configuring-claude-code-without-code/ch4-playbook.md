# 第4章 Playbook——手順を渡す場所ではなく、判断の地図を渡す場所

前章で予告した通り、本章はスキルのすぐ隣にある「Playbook」というレイヤーを解剖する。スキルが「その場で実行する手順」だとすれば、Playbook は「いつ・なぜ・どこで分岐するか」を書いた判断の地図だ。両者はよく似ていて、私自身、最初は区別がついていなかった。だが運用していくうちに、この二つは別の場所に置くべきだとはっきり分かれてきた。

本章で伝えたいことを先に書く。**Playbook は「手順を書けば守られる場所」ではなく、「判断が必要な場面で参照される仕組みを設計する場所」だ。** 私のプロジェクトには現在 90 個の Playbook がある（`ops/playbooks/` 配下の `.md` ファイル、2026年5月31日時点、`find ... | wc -l` 実測）。これだけの数を書けたのは、事故やつまずきのたびに「次はどう判断すべきだったか」を文書化してきたからだ。だが同時に、90個という数そのものが新しい問題を生む。**誰も90個を覚えていられないし、書いた本人ですら、どれが今も実態と合っているか分からなくなる。**

この章では、その90個をどう設計し、どう参照させ、どう腐らせないかを扱う。具体的には次の5つだ。

1. Playbook とは何か——スキルとの違いと、「全体ハブ＋各論」の階層設計
2. 何を渡すか——分岐の粒度と「事故型を追記して育てる」運用
3. どう渡すか——「Playbook を読む」という指示がないと誰も読まない、という参照経路の設計
4. 渡しすぎると何が起きるか——90個の罠と、古い文書が「整合しているから」信じられてしまう問題
5. 削る機制——乖離を検知するフィードバックループと、まだ手をつけられていない退役判定

本書を貫く通奏低音は「渡しすぎない」だ。各レイヤーで同じ問いが繰り返される——何を渡し、何を渡さないか。渡しすぎた時に何が起きるか。Playbook というレイヤーでこの問いは、ひときわ皮肉な形をとる。**渡しすぎたPlaybookは、CLAUDE.md のように「読まれなくなる」だけでは済まない。古くなっても整合した文書として残り、間違った判断を裏付ける根拠になってしまう。** 本章はそこまで掘り下げる。

なお、本章でも90個のPlaybookを羅列することはしない。それをやると本書が「手順書のカタログ」になってしまう。代わりに、それらをどう束ね、どう参照させ、どう腐り検知しているかという構造に焦点を当てる。中身を一つずつ紹介するより、束ね方のほうが読者の持ち帰りになると考えているからだ。

## Playbook とは何か——判断の地図を渡す場所

### スキルは「実行」、Playbook は「判断」

前章で、スキルは「その場で実行する手順」だと書いた。`/todo` と打てば GitHub Issue の操作が一連の流れで走る、`/org-health` と打てば組織の健全性チェックが走る——スキルは、起動した瞬間に何をするかが決まっている。引数を渡せば、あとは手順通りに実行される。

Playbook はそうではない。Playbook は、**作業を始める前に読むもの**だ。そこに書いてあるのは「こうしろ」という一本道の手順ではなく、「こういう場面ではこう判断する」「ここで分岐する」「この条件のときは止まる」という判断の地図である。

具体例で言おう。私のプロジェクトに `ops/playbooks/article/publish.md` という記事公開のPlaybookがある。これは「公開ボタンを押せ」という手順書ではない。「はてなブログに先に公開し、24時間後に Zenn と Qiita へクロスポストする」という順序の根拠、「なぜその順序でなければならないか」、「クロスポスト時にどの確認を挟むか」といった**判断の前提**が書かれている。実際の公開操作そのものは、別途スキルやスクリプトが担う。Playbook は、そのスキルを呼ぶ前に「いま自分は正しい順序・正しい条件にいるか」を確認するために読む。

この違いを一文にすると、こうなる。

> スキルは「いま実行する手順」、Playbook は「実行する前に確認する判断の地図」。

前章の最後で、私はこう書いた——「スキルが判断を抱え込んだら、その判断は Playbook に切り出すべきだった」と。これがその回収だ。スキルの中に「もし○○なら△△、そうでなければ□□」という分岐が増えてきたら、それはスキルが判断を抱え込み始めたサインだ。判断はPlaybookへ、実行はスキルへ。この切り分けができていないと、スキルは分岐で膨らんでメンテナンス不能になるか、Playbook が単なる手順の写しになって判断の部分が抜け落ちるか、どちらかが起きる。

### 「両方必要」なのは、実は少数派だった

正直に書くと、私は最初、スキルとPlaybookの境界をうまく引けていなかった。スキルを作るたびに「対応するPlaybookも要るのだろうか」と迷い、念のため両方そろえようとしていた時期がある。実行手順と判断の地図を、ほとんどのタスクでセットにしようとしていた。

だが、運用しながら整理してみると、実態は違った。私のスキル群を見直したとき、判断の地図（Playbook）まで本当に必要だったのは、全体の一部に過ぎなかった。多くのスキルは、起動したら手順通りに走るだけで、その前に読むべき「判断の地図」を必要としなかった。引数を渡せば結果が決まる単純な操作に、わざわざ分岐の地図を添えるのは、ただの過剰装備だった。

では、どういうスキルが「両方必要」だったか。それは、**実行の前に複雑な判断を要するもの**——記事の公開フロー、セッションの引き継ぎ、週次のレビューといった、実行そのものよりも「いつ・どの条件で・何を確認してから実行するか」のほうが重い作業だった。これらは、実行手順（スキル）と判断の地図（Playbook）が両輪で初めて回る。逆に、単純な操作に判断の地図を添えても、読まれない地図が一枚増えるだけだった。

この線引きは、最初から見えていたわけではない。「念のため両方」から始めて、運用の中で「ここは判断の地図が要る／要らない」を一つずつ仕分けて、ようやく見えてきた線だ。理想形を最初に描けたのではなく、試行錯誤の結果として境界が浮かび上がった。だから読者にも、最初から完璧な切り分けを目指すより、「このスキルは実行する前に判断が要るか？」を一つずつ問うことを勧めたい。判断が要るなら地図（Playbook）を添え、要らないなら添えない。それだけで、無駄なPlaybook の量産を防げる。

### なぜ「地図」という比喩なのか

判断の地図、という言い方をしているのには理由がある。地図は、目的地までの一本道を示すものではない。「ここに分岐がある」「ここは行き止まり」「この道は通れるが遠回り」といった、**判断に必要な情報**を示すものだ。実際にどの道を選ぶかは、その場の状況——天候、時間、同行者——によって変わる。地図は選択を肩代わりしない。選択を助けるだけだ。

Playbook も同じだ。良いPlaybookは、すべての分岐に答えを用意しようとしない。「ここで判断が要る」「この分岐は過去に事故が起きた」「ここは止まって確認せよ」というポイントを示し、あとは実行者（私のプロジェクトでは Claude や私自身）の判断に委ねる。逆に、すべての分岐に答えを書き込もうとすると、地図は実物大の地図になる。実物大の地図は、地図としては役に立たない。

この「すべてを書かない」という節度こそが、本章で繰り返し出てくる論点だ。Playbook は書けば書くほど精密になるように見えて、ある点を超えると、精密さが保守コストと参照コストに化ける。どこまで書くかの判断軸は次節で詳しく扱う。

### 「全体ハブ＋各論」という二層構造

90個のPlaybookを、私はフラットに並べているわけではない。単一の巨大なPlaybookに全部を詰め込むと、誰も最後まで読まない。かといって90個をバラバラに置くと、どれを読めばいいか分からない。だから**「全体ハブ＋各論」の二層**で束ねている。

記事制作の例で説明する。記事を書いて公開するまでの全工程を束ねるハブが `ops/playbooks/article/quality-gate.md`（258行、`wc -l` 実測）だ。これは「いつ・どの工程で・誰が・どの各論Playbookを呼ぶか」の地図になっている。制作フローの全体像と、各工程の担当エージェントと、対応する各論Playbookへのポインタが一枚に収まっている。

その下に各論がぶら下がる。執筆の手順は `writing.md`、事実確認は `fact-check.md`、読者視点のレビューは `reader-review.md`、公開は `publish.md` ——というように、工程ごとに各論Playbookが分かれている。ハブは「いつどれを呼ぶか」を示し、各論は「呼ばれたときに何をするか」を示す。

この二層構造は、第1章で書いた CLAUDE.md と `.claude/rules/` の分割と同じ思想だ。入口になる薄いファイル（ハブ）が全体の地図を持ち、詳細は役割別・工程別の各論に分離する。入口を薄く保つことで、最初に読まれる場所が肥大化して読み飛ばされるのを防ぐ。Playbook でも同じ設計判断が効いている。

ハブと各論を分けることのもう一つの効用は、**読む範囲を絞れる**ことだ。記事の事実確認だけをするなら、ハブで「いま自分は fact-check の工程だ」と位置を確認し、`fact-check.md` だけを読めばいい。執筆や公開のPlaybookまで読む必要はない。90個すべてに目を通すのは不可能だし、意味もない。自分のタスクに該当する各論だけを読む——この「読みすぎない」設計が、二層構造によって自然に実現する。これは「どう渡すか」の節でもう一度詳しく扱う。

## 何を渡すか——分岐の粒度と「事故型を追記して育てる」運用

### 分岐は細かく書くほど保守コストが上がる

Playbook の本体は「判断の地図」だと述べた。では、その地図にどこまで細かく分岐を書き込むべきか。これがこのレイヤーの最初の悩みどころだ。

直感的には、分岐を細かく書くほど親切に思える。「Aの場合はこう、Bの場合はこう、Cの場合はこう」と全パターンを網羅すれば、実行者は迷わない。だが実際には逆のことが起きる。**分岐を細かく書くほど、Playbook の保守コストが上がる。** 状況が少し変われば、書き込んだ分岐の一つひとつが実態とずれていく。10個の分岐を書けば、10個の「いつか古くなる箇所」を抱えることになる。そして後述するが、古くなった分岐ほど厄介なものはない。

もう一つの問題は、細かすぎる分岐は読まれないことだ。判断の地図に細部を書き込みすぎると、地図は実物大に近づく。実物大の地図を広げて道を探す人はいない。詳細すぎるPlaybookは、CLAUDE.md が肥大化したときと同じ運命をたどる——誰も最後まで読まなくなる。

### 書く粒度の判断軸——「事故が起きた分岐」と「auto mode で失火する分岐」

では何を基準に分岐を書くか。私が運用の中でたどり着いた判断軸は、こうだ。

> **明文化するのは「過去に事故が起きた分岐」と「無人実行（auto mode）で判断を誤りやすい分岐」のみ。それ以外は実行者の判断に委ねる。**

この基準は、裏返せば「事故が起きていない分岐はわざわざ書かない」ということだ。一見すると手抜きに見えるかもしれない。だが、これには明確な理由がある。Claude はそれなりに賢く、書かれていない一般的な判断は自分で下せる。わざわざ書く価値があるのは、**Claude の素の判断では間違える場所**、つまり過去に実際に間違えた場所と、人間が見ていない無人実行で間違えやすい場所だけだ。

無人実行で失火する分岐、というのが少し分かりにくいかもしれない。私のプロジェクトには、夜間や早朝に人間が見ていない状態で走る自動タスクがいくつかある。そういう場面では、「ここは人間に確認すべき」という判断が、確認相手がいないために素通りされてしまう危険がある。だから、無人実行でも必ず止まるべき分岐——たとえば外部APIに不可逆な変更を加える操作や、多数のファイルを一括で書き換える操作——は、Playbook と上位ルールに明示的に書き込んでおく。書いておかないと、無人実行という条件下で判断が発火しないからだ。

ここには、一見すると矛盾する事情がある。Claude は賢いのだから、確認相手がいない無人実行でも「これは危ない操作だから止まろう」と判断できそうに思える。だが、「危ないかどうか」の判定そのものが、Claude 側の主観に依存してしまうのが問題だ。何を「不利益」と見なすかが曖昧なまま無人で走ると、その日の文脈によって判断がぶれる。だから、抽象的に「危ない操作は止まれ」と書くだけでは機能しない。「**どの操作が**、**どの条件で**発火するか」まで具体的に書き込まなければ、無人実行下では発火しない。実際、私のプロジェクトでは過去に、ある同期設定を独断でデフォルト変更してしまい、複数の公開記事が一時的に非公開になる事故を起こしたことがある。「副作用が大きい変更は確認する」という抽象ルールはあったが、「デフォルト値の変更で挙動を切り替える操作は確認対象」という具体的な発火条件が書かれていなかったために、判断が発火しなかったのだ。抽象論では止まらない。具体的な発火条件まで書いて初めて、無人実行でも分岐が機能する。

逆に言えば、人間が横で見ている場面で、その都度判断すれば済むことは、わざわざ分岐として書かない。書く労力と保守コストに見合わないからだ。**「全パターンを網羅する」のではなく「素の判断で間違える場所だけを補強する」**——これが、私が分岐の粒度について学んだことだ。

### 「最初から完璧」を目指さず、「事故型を追記して育てる」

この判断軸には、運用上の含意がある。それは、**Playbook を最初から完璧に書こうとしない**、ということだ。

事故が起きた分岐だけを明文化するなら、明文化すべき分岐は事故が起きるまで分からない。つまり、Playbook は最初から完成形では存在しえない。事故やつまずきが起きるたびに、「この型の失敗を次は防ぐ」という一行を追記して育てていく——これが現実的な運用だ。

この「事故型を追記して育てる」運用の例として、私のプロジェクトにある blogsync 関連のPlaybookが挙げられる（事故の詳細な経緯と設定面の解剖は第6章に譲る。ここでは「Playbook がどう育つか」という観点だけを取り出す）。

### blogsync 事故が繰り返され、Playbook がその都度育った

この事故は2026年5月に複数回繰り返された。そして、**繰り返されるたびに Playbook へ新しい一行が書き足された**。ラッパー経由なら安全だと思っていたら、ラッパー経由でも事故が起きた。ループ実行は禁止にしたら、修正コミット直後のテストで同型の事故が再発した。その都度、「次はここで止まる」という分岐が一つずつ追記されていった。

この連鎖が示すのは、Playbook の本質的な性格だ。**Playbook は、最初から正しく書けるものではない。同じ型の失敗を繰り返しながら、その都度「次はここで止まる」という一行を足して育てるものだ。** 一度で完璧な手順書を書けるなら、何度も事故は起きていない。書けないからこそ、事故型を追記して育てるしかない。

さらに、この連鎖から一つ重要な教訓が生まれた——**「修正済み」と「事故の再発防止が実証された」は別物**。修正コミットがあっても、それが真の修正である保証はない。修正直後の1件目こそ、最も警戒すべきフェーズだ。事故記録には「対策のキャッチアップが事故発生に追いつかなくなっている」と書かれていた。正直な敗北の記録だが、Playbook がどう育つかの最も誠実な実例でもある。

### dry-run の件数一致は、書き込み内容の正当性を保証しない

もう一つ、書き込み系の操作に関する重要な教訓がある。これは別の事故から学んだものだ。

2026年5月11日、ネタ帳ファイルを一括で補完するスクリプトを本実行したところ、**26個のファイルが空ファイルになった**。原因は、スクリプト内で使っていたテキスト処理コマンドが、改行を含む値を正しく扱えず、処理を途中で中断していたことだった。幸い、まだコミット前だったので即座に元に戻せて、実害はゼロだった。

この事故の教訓は、原因そのもの（コマンドのバグ）ではない。教訓は、**事前の dry-run では問題を検知できなかった**という点にある。本実行の前に dry-run を走らせ、「対象は26ファイル」という件数を確認していた。件数は本実行と一致した。だが、dry-run が確認していたのは「何件のファイルを処理するか」だけで、「処理した結果ファイルがどうなるか」ではなかった。件数は合っていたが、書き込まれる中身は壊れていた。

ここから、書き込み系スクリプトの実行Playbookに次の段階が加わった。

> dry-run の件数確認だけでは不十分。本実行の前に、**1ファイルだけ実際に書き込んでみて、変更前と変更後の差分を目視で確認する**（サンドボックステスト）。それを確認してから残りを本実行する。

「件数が合っているからOK」は通用しない。書き換える中身そのものを、小さくてもいいから実際に一度書き込んで目で見る。この段階を挟むためのPlaybook（`ops/playbooks/article/blogsync-sandbox-test.md`、約13KB）が後に整備された。これも、事故が一行を追記させた例だ。

### 二次情報を根拠に書き込みを判断しない

書き込み系の判断について、もう一つ。私のプロジェクトには `content/article-status.md` のような「集計ビュー」がある。各記事の公開状況を一覧で見られる便利な生成物だ。

2026年5月14日、この集計ビューの表示を根拠にクロスポストのスクリプトを実行したところ、古くなった集計情報が、記事の本物のステータスを上書きしてしまう事故が起きた。集計ビューは生成物——つまり二次情報だ。生成されたタイミング以降の変更や、集計ロジックのバグによって、実態とずれることがある。

ここから、書き込み操作の前のルールが一つ増えた。

> 集計ビュー（二次情報）の表示を根拠に書き込みを実行しない。書き込み操作の前には、必ず各記事のフロントマター（一次情報）を直接確認する。

一次情報と二次情報を区別し、書き込みの判断は必ず一次情報に当たる。当たり前に聞こえるが、便利な集計ビューが目の前にあると、つい二次情報を根拠にしてしまう。だから、これも明文化して分岐に組み込んだ。

ここまでで挙げた事故——blogsync の繰り返し事故、空ファイル化、集計ビュー上書き——は、いずれも「書き込み系の操作」という共通点を持つ。読み取りでつまずいても、たいていはやり直せる。だが書き込みは、外部に波及すると取り返しがつかないことがある。だからこのレイヤーの分岐は、書き込み系の操作に厚く張られている。**何を渡すか、の答えは「素の判断で間違える、取り返しのつかない場所」に集中させる**、ということだ。

## どう渡すか——「Playbook を読む」という指示がないと誰も読まない

### 書くことと、読まれることは別の設計責務

ここまで「何を書くか」を扱ってきた。だが、Playbook には、書くこと以上に難しい問題がある。**書いただけでは、誰も読まない。**

これは、私がこのレイヤーで最も痛感したことだ。90個のPlaybookをファイルとしてリポジトリにきれいにそろえても、それだけでは参照されない。ファイルが存在することと、必要な場面でそのファイルが読まれることは、まったく別の話だ。「Playbook を書く」と「Playbook が参照される」は、別の設計責務として扱わなければならない。

CLAUDE.md は最初に自動で読み込まれる。メモリも関連する話題のときに参照される。だが Playbook は、「読め」という指示がない限り、コンテキストに入ってこない。90個のファイルが静かにリポジトリに眠っているだけ、という状態に簡単に陥る。

この「読まれない」という落とし穴に、私は何度も落ちている。象徴的なのは、ある作業を「軽い作業だから」とCOOが直接やってしまった一件だ。ネタ帳を1本作る、という小さなタスクだった。短い文書を作るだけなので、わざわざ手順を確認するまでもないと思い、対応するPlaybook を読まずに着手した。だが実際には、ネタ帳の作成にはちゃんとPlaybook があり、そこには「出典のタグを付ける」「関連する既存ネタ帳へのリンクを張る」「frontmatter の必須項目を埋める」といった、私が知らなかった——正確には、その場で思い出さなかった——手順が書かれていた。Playbook を読まずに作ったネタ帳は、それらをすべて欠いた状態で保存された。

この失敗が教えてくれたのは、「**軽い作業だから読まなくていい**」という判断こそが、Playbook を読まない最大の原因だということだ。重い作業なら、人は慎重になってPlaybook を確認する。だが軽く見える作業ほど、確認の動線が発火しない。そして、軽く見える作業にもPlaybook がある。「これは対応表に載っているタスクか？」を、軽作業に見えても着手前に問う——この確認動線を、私は事故のあとにルール化した。「読まれない」の半分は、書いた側の問題ではなく、「軽いから読まなくていい」という読む側の油断から来ている。

### 委任プロンプトに「読むべき Playbook」を明示する

私が採っている対策の一つ目は、作業を委任するときのプロンプトに、**「読むべき Playbook: ○○」と明記する**ことだ。

私のプロジェクトでは、メインのセッション（COO）が各サブエージェントに作業を委任する。その委任プロンプトに、「この作業の前に `ops/playbooks/○○.md` を読むこと」という一行を必ず入れる。これがないと、サブエージェントは自分の素の判断で作業を始めてしまい、Playbook に書いた判断の地図が使われない。


たとえば執筆役エージェントに章の執筆を委任するとき、私は委任プロンプトに「`ops/playbooks/article/writing-guidelines.md` を読んでから書くこと」と必ず添える。このガイドラインには、過去のレビューで繰り返し指摘されたパターン——冒頭に結論の要約を置く、問題提起で終わる記事には見通しを添える、独自用語には注釈を入れる——が集約されている。委任プロンプトでこれを参照させないと、せっかく蓄積したルールが使われず、後の品質チェックで同じ指摘が再発する。実際、参照させ忘れた回には、冒頭要約の欠落・締めの宙吊り・固有名詞の誤記といった、すでにガイドラインに書いてあったはずの指摘が再発した。書いてあっても、読ませなければ効かない。

実際の委任プロンプトは、たとえばこんな具合だ（要点だけ抜粋する）。

```
記事の第4章を執筆してください。

【必ず最初に読むこと（着手前必須）】
- ops/playbooks/book/writing.md — 書籍執筆の全体フロー
- ops/playbooks/article/writing-guidelines.md — 文体・構造・品質ルール
- （章のネタ帳ファイル）

【文体・一人称】
- 一人称は「私」
- 冒頭に結論要約段落を置く（物語フックで始めない）
```

「必ず最初に読むこと」という見出しと、読むべきPlaybook のパスの列挙——この一塊が、委任プロンプトの背骨になっている。これを入れたときと入れなかったときで、返ってくる原稿の質が変わる。入れた場合、執筆役エージェントは書き始める前にガイドラインを読み、冒頭に要約段落を置き、独自用語に注釈を添えた原稿を返してくる。入れなかった場合、それらの蓄積されたルールが反映されず、後のレビューで「冒頭に要約がない」「この用語の説明がない」と指摘される。同じエージェント、同じモデルなのに、判断の地図を渡したかどうかで出力が変わる。これが「参照させる」ことの効果だ。

### トリガー語をメモリに保存して、参照を自動発火させる

委任プロンプトへの明示は有効だが、弱点がある。それは、**明示するのを忘れる**ことだ。

2026年5月14日、私はある記事のレビューを進めていて、ユーザーから「採点して」という指示を受けた。その瞬間、私は独自の採点尺度でレビューを組み立ててしまった。本来なら、品質ゲートのPlaybook（`quality-gate.md`）に組織共通の採点基準が定義されている。それを読まずに独自の尺度で採点したため、出した点数が組織内の過去のスコアと比較不能になってしまった。ユーザーから「なぜ品質ゲートのPlaybook を読んでいないのか」と指摘されるまで、ミスに気づかなかった。

この事故が示したのは、「Playbook の存在は知っているのに、特定の場面でその参照が発火しない」という問題だ。知っていることと、適切な瞬間に思い出すことは違う。

対策として採ったのは、**トリガー語をメモリに保存する**ことだった。「採点」「スコア」「品質ゲート」「SEO評価」「合格判定」といった語が指示に含まれたら、作業を組み立て始める前に必ず `quality-gate.md` を開く——というルールを、メモリファイルとして保存した。メモリはセッションの最初に読み込まれるので、これらのトリガー語に反応してPlaybookを参照する動作が、半ば自動的に発火するようになる。

ここに、レイヤー同士の連携が現れている。Playbook 単体では「読め」という指示がないと参照されない。その指示の発火を、メモリというレイヤーが補強する。**Playbook は、メモリと組み合わせて初めて確実に参照される。** これは次章（メモリ）で詳しく扱うテーマだが、ここで予告しておく。Playbook を「読むべき場面で読ませる」設計の一部は、Playbook レイヤーの外——メモリレイヤーに置かれている。

### 90個を覚えさせない——対応表という参照経路

委任プロンプトへの明示も、トリガー語のメモリ化も、「個別のPlaybookをどう思い出すか」の対策だ。だがそもそも、90個のPlaybookの中から「いまどれを読むべきか」を毎回探すのは大変だ。

ここで効くのが、**タスク種別とPlaybookの対応表**だ。私のプロジェクトでは `ops/playbooks/INDEX.md`（116行、`wc -l` 実測）が、「このタスクならこのPlaybookを読む」という対応関係を一覧にしている。記事執筆なら `writing.md`、クロスポストなら `crosspost.md`、GTD収集なら `collect.md`——というように、タスク種別から該当Playbookへ一発で引ける。

この対応表の設計思想は、「**90個すべてを覚える」のではなく「タスクが発生したら対応表を引く**」だ。覚える必要をなくすのが、対応表の役割である。人間が電話帳の番号をすべて暗記しないのと同じで、引けるようにしておけば、覚える必要はない。

そして対応表は、冒頭の節で触れた「読みすぎない」設計にも貢献する。対応表を引けば、自分のタスクに該当するPlaybookだけが分かる。関係のないPlaybookまで読み込むと、コンテキストを無駄に消費する。「全部に目を通せ」は不可能であり、かつ意味がない。対応表は「必要な一枚だけを引く」ための索引であり、無駄な読み込みを防ぐフィルターでもある。

### 参照経路の設計こそ、Playbook 設計の本体

ここまでをまとめると、Playbook を「どう渡すか」は、突き詰めれば**参照経路をどう設計するか**に尽きる。

- 委任プロンプトに「読むべき Playbook」を明示する（個別指定）
- トリガー語をメモリに保存して参照を自動発火させる（発火の補強）
- 対応表でタスク種別から該当Playbookを引けるようにする（索引）
- 自分のタスクに該当する各論だけを読む（読みすぎない）

良い判断の地図を書くことと、その地図を必要な場面で開かせることは、別の仕事だ。そして、参照されない地図は存在しないのと同じだ。**Playbook 設計の本体は、内容そのものより、参照経路の設計のほうにある**——これが、このレイヤーで私が最も強く学んだことだ。

## 渡しすぎると何が起きるか——90個の罠と「整合しているから信じられる」問題

### 古い Playbook は「読まれない」では済まない

通奏低音である「渡しすぎ」を、このレイヤーで直視する。

CLAUDE.md のレイヤー（第1章）では、渡しすぎると「読まれなくなる」という症状が出た。Playbook でも参照率の低下は起きる。だが、Playbook の渡しすぎには、もっと厄介な症状がある。**古くなった Playbook は、読まれなくなるだけでは済まない。古くなっても文書としては整合しているため、間違った判断の根拠になってしまう。**

これがどういうことか、説明する。Playbook は文書だ。一度きちんと書けば、内容が実態と合わなくなっても、文書としての体裁は崩れない。読むと筋が通っているように見える。手順が並んでいて、分岐が示されていて、根拠も書いてある。**実態とずれていても、文書の中だけ見れば整合している。** 人は——そしてAIは——「整合している文書」を信じる傾向がある。だから、古いPlaybook を読んで、それが今も正しいと信じて、実態に合わない判断を下してしまう。

「読まれないPlaybook」は、せいぜい「無駄な文書」で済む。だが「古くなったのに読まれてしまうPlaybook」は、**積極的に間違いを誘発する**。これが、Playbook を渡しすぎることの本当の怖さだ。書いたPlaybookは、書いた瞬間から腐り始める。そして腐ったことに、誰も気づかない。

### 「沈黙の繰越」——整合した文書を信じてしまう実例

この「整合しているから信じてしまう」問題が、Playbook そのものではなく、隣接する文書で表面化した実例がある。引き継ぎ資料（handoff）だ。

私のプロジェクトでは、セッションをまたいで作業を引き継ぐとき、引き継ぎ資料を書く。そこには「未対応」「繰越」といった項目が並ぶ。問題は、前回の引き継ぎ資料から「未対応」項目を新しい引き継ぎ資料へ転記するときに起きた。

2026年5月5日に発覚した事故では、ある権限の問題が「未対応」として4日連続で繰り越されていた。ところが実際には、その問題は**4月30日のコミットで既に解決済み**だった。引き継ぎ資料を書くたびに、前回の「未対応」という記載を、現状を確認せずにそのまま転記していたのだ。文書としては整合している——「未対応」と書かれた前回資料を、「未対応」と新資料に写すのは、文書操作としては矛盾がない。だが実態とはずれていた。解決済みの問題が、整合した文書の中で生き続けていた。

これは Playbook の腐りとまったく同じ構造だ。文書が整合していることと、文書が実態と合っていることは別だ。前者は後者を保証しない。

### 設計書を疑い、実装を信じる

この「整合した文書を信じてしまう」問題には、もう一つの顔がある。設計書とコード（実装）が食い違ったとき、どちらを信じるか、という問題だ。

私のプロジェクトでは、あるとき、レビュー役のエージェントが「設計書に書かれた定数と、実装の定数が一致していない」と指摘してきた。私は最初、その指摘を信じて、実装側を直そうとした。だが、よく確認すると、ずれていたのは**設計書のほう**だった。実装が正しく、設計書が古かったのだ。設計書という整合した文書を、つい正しいものとして扱ってしまった。

この経験から、私は一つの原則を明文化した——**実装（ソースコード）が唯一の正典（SSoT）であり、設計書は二次情報**。両者が食い違ったら、まず設計書のほうを疑う。そして、レビュー役のエージェントが指摘してきたときも、その指摘を鵜呑みにせず、指摘された両側のソースを自分で直接確認してから判断する。

ここにも、文書を盲信する罠が潜んでいた。設計書は整合した文書だ。Playbook も、handoff も、設計書も——きれいに書かれた文書は、それだけで「正しそう」に見える。だが、文書の整合性は、実態との一致を何も保証しない。Playbook を信じるとき、handoff を繰り越すとき、設計書を参照するとき、私はいつも「これは今も実態と合っているか」を一度問うようにしている。整合した文書ほど、疑う習慣が要る。

### handoff-rollover-check.md——腐り検知を運用化する

この事故への対策として生まれたのが、`ops/playbooks/handoff-rollover-check.md`（95行、`wc -l` 実測）というPlaybookだ。名前の通り、引き継ぎ項目の繰越（rollover）をチェックする手順を定めている。

このPlaybook が要求するのは、シンプルなことだ。前回の引き継ぎ資料から「未対応」「繰越」「再掲」といった項目を新資料に転記する直前に、**現状を検証してから書く**。具体的には、(a) その項目に関連するコミットが前回以降にないかを確認し、(b) 該当ファイルや設定の現状を実際に見て、(c) 検証結果に応じて記載を変える。

このPlaybook の核心は、最後に置かれた一文に集約されている——**「沈黙の繰越禁止」**。ステータスを書かずに前回の文面をそのままコピーするのは禁止だ、というルールである。繰越項目には必ず「未対応／解決済み／再対応必要／検証中」のいずれかのステータスと、検証日と、何を見て判定したか（コミットハッシュやファイルパス）を添えなければならない。

「沈黙」とは、現状を確認せずに前回の文面を黙って写すことを指す。沈黙の繰越は、整合した文書を盲信する行為そのものだ。それを禁じ、必ず一度実態に当たることを義務づける。これが、文書の腐りに対する具体的な防御策になっている。

そして、ここに自己言及的な含みがある。**この腐り検知の発想は、handoff だけでなく Playbook 自体にも必要だ。** 引き継ぎ資料の「未対応」を実態検証してから繰り越すように、Playbook の手順も「これは今も実態と合っているか」を定期的に検証してから信じるべきだ。handoff には検証Playbook ができたが、Playbook 自体の腐り検知は、正直に言えば、まだ仕組みとして整っていない。これは次節で扱う未整備課題だ。

### 「分岐の細かさ」が保守コストを膨らませる、再び

「何を渡すか」の節で「分岐を細かく書くほど保守コストが上がる」と書いた。この保守コストの正体が、ここでようやく見えてくる。

分岐を細かく書くということは、「いつか古くなる箇所」を細かく量産するということだ。10個の分岐を書けば、10個それぞれが独立に腐りうる。そして腐っても整合しているように見えるので、気づかない。つまり、**細かい分岐は、腐ったとき発見しにくい間違いの種を、文書のあちこちに埋め込む行為**でもある。

これが、「何を渡すか」の節で「事故型と無人実行の失火だけを書く」という節度を強調した理由だ。書く分岐を絞るのは、単に労力を惜しむためではない。書いた分岐は腐り、腐っても整合して見え、間違いを誘発する。だから、**腐ったときの被害が大きい場所——取り返しのつかない書き込み操作や、無人実行で発火しない判断——だけに、分岐を集中させる**。それ以外を書かないのは、腐る箇所を増やさないための積極的な選択だ。

### 渡しすぎの症状を整理する

このレイヤーの「渡しすぎ」の症状を、改めて整理しておく。

- **覚えきれない**: 90個のPlaybookを全部把握しているエージェントも人間もいない。どれを読むべきか分からなくなる
- **腐っても気づかない**: 古くなったPlaybook が整合した文書として残り、間違った判断の根拠になる
- **保守コストが膨らむ**: 分岐を細かく書くほど、独立に腐る箇所が増え、メンテナンスが追いつかなくなる

これらはいずれも、「書きすぎる」ことから生まれる。Playbook は書けば書くほど守りが厚くなるように見えて、ある点を超えると、書いた量そのものが負債になる。書く設計と同じだけ、書かない設計・更新する設計に手をかけなければならない。次節で、その「削る機制」を扱う。

## 削る機制——乖離検知のフィードバックループと、未整備の退役判定

### 乖離が起きたら必ず記録する——フィードバックループの定常化

Playbook が腐る、という問題への第一の対策は、**腐っているサインを定常的に集める仕組み**だ。

私のプロジェクトの全エージェント共通ルールに、こういう一文がある。作業中に「Playbook 記載の手順どおりに進められなかった」「Playbook に書かれたコマンドやパスや前提が実態と合わなかった」「スクリプトがエラーを返したので回避ルートで代替した」——このいずれかが起きたら、成果物のヘッダーに**必ず記録する**、というものだ。

ここで重要なのは、「気づいたら記録する」ではなく「**該当する事象が起きたら必ず記録する**」という発火条件だ。「気づいたら」は主観に依存し、忙しいときに発火しない。「該当事象が起きたら」は客観的な条件なので、漏れにくい。記録する内容は、何が起きたか・どう回避したか・Playbook やスクリプトのどこを直すべきか、の三点だ。

この記録が、フィードバックループになる。Playbook が実態とずれていれば、それを使った作業の中で「手順どおりに進められなかった」事象が起きる。その事象が必ず記録される。記録が集まれば、「このPlaybook は腐っている」というサインが、待っていなくても向こうからやってくる。腐りを能動的に探すのではなく、腐りが自己申告される仕組みを作る——これが、乖離検知の基本設計だ。

なぜ「気づいたら」ではなく「事象が起きたら必ず」という発火条件にこだわるのか。それは、第1章でルールの発火条件について書いたことと同じ理由だ。「気づいたら記録する」という条件は、結局のところ「記録する気になったら記録する」と同義で、忙しいときや、その場をやり過ごしたいときには発火しない。腐りのサインは、ちょうど発火してほしくないとき——作業が立て込んでいて、回避ルートで急いで片付けたいとき——に現れる。だから条件を主観から切り離し、「該当する事象（手順どおり進められなかった／コマンドがエラーを返した／前提が実態と合わなかった）が起きたら」という観測可能な事実に紐づける。観測可能な事実なら、記録するかどうかの裁量が入り込まない。この設計のおかげで、私のプロジェクトでは「Playbook に書いてあったパスが存在しなかった」「指定されたコマンドが動かなかった」といった小さなずれが、作業の成果物のヘッダーに自動的に溜まっていく。それが、次にそのPlaybook を直すときの一次情報になる。

一つだけ正直に付け加えると、この必須記録ルールには負荷の問題もある。あらゆる小さなずれを毎回記録すると、運用が重くなりすぎる。だから、記録対象を「Playbook 乖離・エラー回避」という具体的なカテゴリに限定し、それ以外の気づきは任意にしている。何でもかんでも記録させると、今度は記録という行為そのものが腐る。ここでも「渡しすぎない」——記録の義務を負わせすぎない——という同じ節度が効いている。

前節で挙げた blogsync 4連発も、空ファイル化も、品質ゲートの採点ミスも、すべてこの「事象が起きたら記録する」運用の産物だ。事故が記録され、その記録が再発防止策に変換され、Playbook の新しい一行になる。記録がなければ、同じ事故が記録されないまま繰り返される。記録という入口があるから、Playbook が育つ。

### 退役判定——スキルでは回せたが、Playbook ではまだ

第3章で、スキルには「退役判定」があると書いた。使われなくなったスキルを見極めて畳む判断だ。実際、2026年5月17日に3本のスキルを退役と判定した実績がある。直近で使われていないこと、代替手段があること、発火する場面がないことを基準に、不要なスキルを組織から外した。

Playbook にも、同じ退役判定が必要だ。古くなって、もう参照されず、実態とも合わなくなったPlaybook は、残しておくと「整合した文書」として間違いを誘発する。畳むか、書き直すべきだ。

だが正直に書くと、**Playbook の退役判定は、まだ仕組みとして整っていない。** スキルは「`/○○` と呼ばれたか」で利用頻度を比較的とらえやすい。だがPlaybook は「読まれたかどうか」を機械的にとらえる仕組みが今のところない。委任プロンプトに書かれたか、トリガー語で発火したか——参照の経路が複数あるぶん、「このPlaybook は最近参照されていない」を自動で検知するのが難しい。

想定している設計はある。対応表（INDEX.md）と連動して、各Playbook が直近どのくらいの頻度で委任プロンプトに登場したかをトラッキングし、一定期間まったく参照されていないPlaybook を「腐り候補」として浮かび上がらせる、というものだ。だが、これはまだ構想段階で、実装していない。だから現状、Playbook の腐り検知は、前述の「事象が起きたら記録する」フィードバックループに依存している。乖離が作業中に表面化したときに初めて、そのPlaybook が腐っていたと分かる。能動的な棚卸しの仕組みは、これからの課題だ。

ここは正直に「まだやれていない」と書いておく。本書は「うまくいった設計の紹介」だけの本ではない。各レイヤーの「渡しすぎ」と「削る機制」を対で見せるのが本書の趣旨であり、削る機制が未整備なレイヤーでは、未整備であることそのものが読者の持ち帰りになると考えている。Playbook を増やすのは、つまずくたびに自然に進む。だが、増えたPlaybook を畳む仕組みは、意識して作らなければ永遠に手をつけられない。**書く設計には手が伸びるが、畳む設計には手が伸びない**——これは前章のスキルとも、第1章のCLAUDE.md とも共通する、このプロジェクト全体の弱点だ。

### 余談——この本もまた、Playbook である

ここで一つ、自分自身に跳ね返ってくる問いを正直に置いておきたい。本章で私は「判断の地図は、描くほど腐り、読まれなくなる」と繰り返してきた。だが、よく考えると、**この本そのものが Playbook の一種**だ。「Claude Code に仕組みをどう渡すか」という判断の地図を、読者に向けて書いているのだから。

ということは、本書もまた、本章で述べた罠から自由ではない。書きすぎれば読まれなくなる。時間が経てば実態とずれて腐る。整合した文書として、間違った判断の根拠になるかもしれない。私が90個のPlaybook について語ったことは、そっくりそのまま、この一冊にも当てはまる。

だから本書は、各章で「私のプロジェクトでは現在こうなっている」という現在地を、日付と実測値とともに書くようにしている。「2026年5月31日時点、`wc -l` 実測」という但し書きを何度も挟んでいるのは、この本もいつか実態とずれる前提だからだ。読者がこの本を半年後に読むなら、私の数字はもう古い。仕組みも変わっているだろう。だが、変わらないのは「何を渡し、何を渡さないか」という問いの立て方のほうだ。具体的な数値や手順ではなく、その問いの立て方を持ち帰ってほしい——という願いが、この本を「腐りにくいPlaybook」にする唯一の方法だと考えている。判断の地図は、細部を描くほど腐る。だから本書も、細部の写経ではなく、判断軸を渡すことに重心を置いている。

### このレイヤーの「渡しすぎない」を一言で

Playbook というレイヤーの「渡しすぎない」を一言でまとめると、こうなる。

> **判断の地図は、細かく描くほど、腐ったときに見えにくい間違いを増やす。だから、素の判断で間違える場所だけを描き、描いた以上は腐り検知の仕組みとセットで持つ。**

90個という数は、事故から学んできた証でもあり、同時に、誰も全体を把握できないという負債でもある。この両面を引き受けながら、私は次の三つに手をかけている。

第一に、**書く分岐を絞る**。事故が起きた分岐と、無人実行で失火する分岐だけを明文化し、それ以外は実行者の判断に委ねる。腐る箇所を増やさない。

第二に、**参照経路を設計する**。書いただけでは読まれないという前提に立ち、委任プロンプトへの明示・トリガー語のメモリ化・対応表という三段構えで、必要な地図が必要な場面で開かれるようにする。

第三に、**乖離が自己申告される仕組みを持つ**。「手順どおりに進められなかった」事象が起きたら必ず記録する、というルールで、腐りのサインを待たずに集める。

退役判定という最後のピースは、まだ欠けている。だが、欠けていることを認識し、暫定的にフィードバックループで代替している——その状態こそが、このレイヤーの現在地だ。

## 次のレイヤーへ——「読め」と毎回言わずに済ませる場所

本章では、Playbook を「書くこと」より「読まれること」のほうが難しい、という点を繰り返し強調した。判断の地図は、必要な場面で開かれて初めて意味を持つ。そして、開かせるための仕組み——委任プロンプトへの明示、対応表、トリガー語——が、Playbook の内容そのものと同じくらい重要だった。

このレイヤーの「渡しすぎない」を改めて一言で言えば、**判断の地図は、描くほど腐り、腐っても整合して見える。だから、描く場所を絞り、腐り検知とセットで持つ**ということだった。書く設計と同じだけ、書かない設計と更新する設計に手をかける。それが、Playbook というレイヤーで私が学んだ、渡し方の節度だ。

ここで一つ、次章への伏線を置いておきたい。本章で何度か触れた「トリガー語をメモリに保存して参照を自動発火させる」という設計を、思い出してほしい。Playbook は「読め」と毎回明示しないと読まれない。だが、毎回明示するのは忘れるし、煩わしい。そこで一部の発火条件を、Playbook の外——**メモリ**というレイヤーに逃がしていた。

「採点」という語を聞いたら品質ゲートのPlaybook を開く。この反応を、私はメモリに刻んでいる。つまり、Claude に「毎回読め」と言う代わりに、「これを覚えていてほしい」と渡している場所がある。次章は、その「メモリ」というレイヤーを解剖する。何を覚えさせ、何を忘れさせるか。記憶を渡すことと、文脈を汚すことの境界はどこにあるのか。Playbook の参照を支えていたメモリそのものを、次は正面から見ていく。
