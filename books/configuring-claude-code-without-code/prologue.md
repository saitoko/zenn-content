# 序章 何を渡す本なのか

本書は、Claude Code に「仕組み」を渡すための部品論である。私がやってきたのは、業務を AI に肩代わりさせることではなく、AI が自分で動けるように装備を仕込むことだった。渡せる場所は構造的に7つに分かれている——CLAUDE.md、サブエージェント、スキル、Playbook、メモリ、設定・権限、そして外部接続を担う MCP。いま一度に並べられても追いつかなくて当然なので、この7つが何で、どう位置づくかは次節で一枚の地図として整理する。本書はこれらを章ごとに一つずつ解剖していく。ただし、ただのカタログではない。各章には1本の通奏低音が走る。「何を渡すか」と同時に「何を渡さないか」を問い続けること——渡しすぎないこと、である。この序章では、本書が何の本で、どんな地図を持ち、どう読めばいいかを先に示しておく。

## 「装備の付与」と「業務の肩代わり」は別物

本書を書き始める前、私は別の本を構想していた。「Claude Code に業務を肩代わりさせるまで」という方向の本だ。人がやっていた作業をそのまま AI に引き渡し、どこまで任せられたか・何が任せられなかったかを記録する——そういう本になるはずだった。

だが構想を読み返したとき、どうにも自分の感覚と合わなかった。業務の肩代わりを軸にすると、「何ができて、何ができなかったか」という事情説明に文量が吸われていく。読者が持ち帰れるものより、私の手元の事情のほうが前に出てしまう。それに「AI に業務を任せる」という切り口は、すでに世にあふれている。差別化のしようがない。

引っかかりの正体は、もっと手前にあった。私が Vol.1 から Vol.3 まで実際にやってきたことは、業務を渡すことではなかったのだ。CLAUDE.md にルールを書き、サブエージェントに役割を与え、Playbook に手順を残し、スキルに再現手順を畳み込み、メモリに失敗の教訓を蓄え、設定ファイルで許可範囲を切る——やっていたのは一貫して、AI が自分で動けるようにするための「仕込み」だった。

この二つは、同じ「渡す」でも出力されるものが違う。

- **業務の肩代わり**: 人がやっていた作業をそのまま AI に渡す。読者の関心は「AI で何ができるか」に向く。
- **装備の付与**: AI が自分で動けるように、仕組みそのものを仕込む。読者の関心は「何をどう仕込むと AI が動き始めるか」に向く。

違いは、AI に渡した後に何が残るかにも表れる。肩代わりの場合、渡した先には「片付いた一回ぶんの作業」が残る。装備の付与の場合、渡した先に残るのは「次も同じように動ける仕組み」だ。前者は一度きりだが、後者は積み上がっていく。Vol.1〜3 を通じて私の手元に積み上がってきたのは、まさにこの後者——再利用できる仕組みのほうだった。

たとえるなら、馬に乗ることと、馬が自分で走れるように鞍と手綱を整えることの違いだ。乗り手が手綱を引いて一歩ずつ進ませるのが肩代わりだとすれば、鞍を着け、手綱を握れる形に整え、どこまで自由に走らせるかを決めておくのが装備の付与にあたる。本書が扱うのは後者——鞍と手綱の側、つまり仕組みを仕込む技術のほうだ。

別の言い方をしてもいい。CLAUDE.md やスキルや設定は、AI に渡す「持ち物」であり、同時に AI が動くための「環境」でもある。コードを一行も書けない私が、それでも Claude Code を動かし続けられているのは、この持ち物と環境を少しずつ整えてきたからだ。本書はその整え方を、レイヤーごとに分解して示す本である。

## 渡せる場所は7つに分かれている——本書の地図

仕組みを渡すといっても、闇雲に何かを書き足せばいいわけではない。Claude Code に「渡せる場所」は、構造的にいくつかのレイヤーに分かれている。本書はそのレイヤーを章の軸に据える。

地図は7つ。ただし性質によって二種類に分かれる。

最初の6つは、**自分で設計して作っていくもの**だ。上から順に積み上げていくイメージで並べている。

1. **CLAUDE.md / ルール** — 行動規範とトリガー条件を渡す。AI に「どう振る舞うか」を伝える、最も基礎の層。
2. **サブエージェント** — 人格と専門役割を渡す。一人の万能 AI ではなく、目的別のレンズを複数持たせる層。
3. **スキル** — 実行手順・再現手順を渡す。「この作業はこう進める」を畳み込んでおく層。
4. **Playbook** — 判断の地図を渡す。手順そのものではなく、「どう判断し、どこで分岐するか」を書く層。
5. **メモリ** — 記憶とフィードバックの蓄積を渡す。「次に同じ失敗をしない」ための層。
6. **設定・権限** — 許可範囲と動作の境界を渡す。「何をしていいか」を線引きする層。

そして7つめは、性質がやや異なる。

7. **MCP** — 外部ツールへの接続能力を渡す。これだけは「自分で設計するもの」ではなく、**既にあるものから選んで繋げるもの**だ。1〜6が「どう設計するか」を問うのに対し、MCP は「どう選ぶか」を問う。だから本書では別枠として扱う。

各章で何を問うのかを、先に1行ずつ予告しておく。

- 第1章（CLAUDE.md）: 何を書けばルールとして機能し、書きすぎると何が起きるか。
- 第2章（サブエージェント）: 人格を分ける意味は何か、どこに役割の境界を引くか。
- 第3章（スキル）: 手順を渡す再現性と、使われないスキルが生まれる理由。
- 第4章（Playbook）: 判断の地図をどこまで細かく書くか、参照されない文書はなぜ腐るか。
- 第5章（メモリ）: 何を覚えさせ、何を忘れさせるか。
- 第6章（設定・権限）: 何を許し、何を禁じるか。過剰な許可は何を招くか。
- 第7章（MCP）: 何に繋げるか。機能の多いツールと少ないツール、どちらを選ぶか。

章の重さは均等ではない。だから、あなたの今の関心に合わせて入口を選んでほしい。Claude Code をまだ触り始めたばかりなら、誰でもすぐ手を入れられる第1章（CLAUDE.md）と、具体的な手順を畳み込む第3章（スキル）から入るのがいい。一行書き足せばすぐ挙動が変わる手応えがあり、収穫が早い。一方、すでに動かしていて設計に踏み込みたいなら、第4章（Playbook）から読むと深い。判断の分岐をどう書くかという、最も機微の多い領域だ。事故を踏みたくない、安全に運用したいという関心なら第6章（設定・権限）が要になる。逆に、サブエージェント（第2章）やメモリ（第5章）は前作までで土台を語ったぶん本書では軽く、MCP（第7章）は「選んで繋げる」別軸なので、後回しにして拡張のタイミングで読んでも遅くない。章の厚みそのものが「どのレイヤーに設計の余地が多いか」を示す地図になっている。

7つを一枚の図にすると、上から下へ「先に作る層」から「後から育つ層」へとレイヤーが積み上がり、その横に MCP が外部接続の拡張枠として付く——そういう構造になる。本書は基本的に、この図を上から下へ、最後に拡張枠へ、という順で一段ずつ降りていく。

## 通奏低音は「渡しすぎない」

ここまで読むと、本書は道具を順番に紹介するカタログのように見えるかもしれない。実際、各章はそうやって「このレイヤーには何があるか」から入る。だが、本書には1本の通奏低音が走っている。それは——**渡しすぎないこと**だ。

各レイヤーで、私は同じ問いを繰り返す。何を渡し、何を渡さないか。どこまで渡すか。そして、渡しすぎたときに何が起きるか。仕組みを渡す本でありながら、本書はずっと引き算の話をしている。

なぜ引き算が要るのか。二つだけ、実際に起きたことを刺しておきたい。深追いはしない。それぞれ本編の章で改めて解剖するからだ。

一つは、設定・権限を渡しすぎた事故だ。2026年4月、私の運用では Zenn への自動同期を制御するフラグを、事前確認なしにデフォルトで有効へ切り替えてしまった。結果として Zenn 記事5本が一時的に非公開状態になった。「とりあえず許可しておけば便利だろう」という発想が、そのまま事故の入口になった例である(詳細は第6章「設定・権限」)。

もう一つは、スキルを渡しすぎた、というより「渡したのに使われなかった」例だ。2026年5月、私はそれまでに作ったスキルを棚卸しして、3本を退役と判定した。Windows 専用で今の環境では動かないもの、制作意図が整理できなくなったもの——「あとで使うかもしれない」で増やした道具は、たいてい使われないまま積み上がる(詳細は第3章「スキル」)。

足せば足すほど良くなるわけではない。CLAUDE.md は長くなるほど AI が読まなくなる。サブエージェントは増えるほど「誰に頼むか」の判断コストが上がる。Playbook は古くなっても誰も気づかない。メモリは肥大化してコンテキストを圧迫する。MCP はツールの定義そのものがコンテキストを食い続ける。どのレイヤーにも、渡しすぎたときに効率を下げる固有のメカニズムがあり、本書はそれを章ごとに名指ししていく。

だから本書は、足し算のカタログではなく、**足し算と引き算の両方を含んだ設計書**である。「何を渡すか」を語る章のすぐ隣で、「何を渡さないか」「どう削るか」を必ず語る。それが、この本を他の活用術本と分けている一点だ。これが、本書を貫く一つめの約束になる——各章で、私は渡すものと同じだけ、渡さないものについて書く。

## 本書の読み方——どこから読んでもいい、ただし

最後に、読み方を示しておく。

本書の章は、それぞれ独立したレイヤーに閉じている。第5章のメモリだけを読んでも、第7章の MCP だけを読んでも、その章だけで意味が通るように書いた。気になるレイヤーから開いてかまわない。

ただし一つだけ順序の希望がある。最初に読むなら、第1章の CLAUDE.md から始めてほしい。これは**最も触りやすく、最も誤解されているレイヤー**だからだ。誰でもすぐに一行書き足せる手軽さがある一方で、「書けば効く」という思い込みが最も生まれやすい場所でもある。ここで「渡しすぎない」という感覚を一度つかんでおくと、残りの6つの章がぐっと読みやすくなる。

本書は Vol.1〜3 の続編にあたる。前作までは、AI のチームを**作り**(Vol.1「作るまで」)、日々の編集部として**回し**(Vol.2「回すまで」)、仕込んだものを**発信し続ける**(Vol.3「書き続けるまで」)、その物語と装置設計の記録だった。本書 Vol.4 は、そのチームを支えている「部品」そのものの解剖書である。だが前作を読んでいなくても問題ない。本書は単体で完結するように書いた。前巻への参照は各章でも最小限にとどめる。

そして本書は「部品が何か」までで完結する。「その部品が組み合わさって、プロジェクト全体がどう回っているか」という運用論は、続く Vol.5 へ送る。本書を読み終えたあと、Vol.5 を待つ必要はない。むしろ、待たずに自分の手で組み合わせを試してほしい。

だから、読み終わったらぜひ一つだけやってみてほしい。自分の CLAUDE.md を開いて、一行だけ直してみることだ。一行足すのでも、一行削るのでもいい。その一手が、仕組みを渡すという作業の、最初の一歩になる。

では、最も触りやすく、最も誤解されているレイヤー——CLAUDE.md から始めよう。
