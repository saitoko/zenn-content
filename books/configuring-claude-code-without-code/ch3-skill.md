# 第3章 スキル ——「手順」を渡す場所

私の Claude Code には現在、26個のスキルが登録されている。`/todo` でタスクを管理し、`/publish` で記事を公開し、`/cal` で予定を確認する。スラッシュひとつで決まった手順が走る。便利だ。だがこの章で私が伝えたいのは「26個も作れて便利」ではない。むしろ逆で、**この26個に至る過程で、3個のスキルをすでに退役させた**し、過去には COO が独断で作った約220行のスキルが「設計の作法を踏み外している」と指摘されて作り直しになったこともある。

スキルは「実行する手順を渡す場所」だ。Playbook が「判断の地図」を渡すのに対して、スキルは「今すぐ走らせる手順」を渡す。この区別が曖昧なままスキルを増やすと、スキルは判断ロジックを抱え込んで太り、SSoT（Single Source of Truth：設計の正本を一か所に定めること）が二か所に分裂し、「あとで使う」つもりで作ったまま一度も呼ばれないスキルが溜まっていく。この章では、26個のスキルを運用してきた実体験から、**何を渡し、何を渡さないか・どう渡すか・渡しすぎると何が起きるか** を解剖する。一人称は「私」だが、実際にスキルを呼ぶのは Claude Code 上のエージェントたちであることを先に断っておく。

本書では、`/` で呼ぶ定型手順を総称して「スキル」と呼ぶ。公式用語では「カスタムスラッシュコマンド」にあたり、別途 SKILL.md ベースの「Agent Skills」機能も存在する。本章でのスキルは前者（カスタムスラッシュコマンド）を指している。

なお、この章で挙げる「26個」「Playbook 参照あり10個」「退役3本」といった数値は、執筆時点（2026年5月31日）に `~/.claude/commands/` を実測した値である。記憶や設計書の数字ではなく、その場で `ls` と `grep` で数えた。

## スキルとは何か ——「実行する手順」を渡す場所

### スキルと Playbook は別物

最初に、本書で最も重要な区別を置く。

- **スキル**: 実行する手順を Claude に渡したもの。今すぐ走らせられる。例: `/todo add "原稿を書く"` でタスクが1件追加される
- **Playbook**: 判断の地図。「いつ・なぜ・どこで分岐するか」を含む。実行はしない、読んで判断する

たとえるなら、スキルは「レンジでチンする」という操作そのもので、Playbook は「冷凍食品か作り置きか、来客があるか、何分待てるか」を判断する献立ガイドだ。レンジを回す操作にレシピ全体を書き込もうとすると、操作が肥大化して扱いにくくなる。

この区別は、私が最初から分かっていたわけではない。むしろ後述するとおり、**スキルと Playbook の境界はこの組織の運用の中で何度も引き直されてきた**。最初は「便利な手順は全部スキルにすればいい」と思っていた。だが手順の中に「この場合はこっち、あの場合はあっち」という分岐が増えてくると、スキルの中身が判断ロジックで膨らみ、読みにくく・直しにくくなる。そのとき初めて「これはスキルではなく Playbook に切り出すべき判断だった」と気づく。

判断の合図はシンプルだ。**スキルの中に「いつ・なぜ・どの場合は」という分岐が増えてきたら、その分岐は Playbook に切り出すべきサインである。** スキルは手順、Playbook は判断。これを混同するとスキルが太る。

### 26個のスキル群 ——規模感の提示

私の `~/.claude/commands/` には、執筆時点で26個の `.md` ファイルがある。いくつか挙げると次のようなものだ。

- `/todo` — GitHub Issue を GTD 式タスクリストとして管理する
- `/publish` — 記事をはてなブログに公開する
- `/cal`・`/mail` — カレンダー確認・メール処理
- `/org-health` — 組織の健全性点検
- `/blog-status` — 記事の公開状況（Zenn・はてな・Qiita）をダッシュボード化する
- `/handoff` — セッション引き継ぎ資料を作る
- `/dream` — 自動記憶ファイルを整理・改善する

この26という数を見て「多い」と感じるか「そんなものか」と感じるかは人それぞれだろう。私が伝えたいのは、**この数を維持するために削る作業が要る**ということだ。便利そうなスキルは作ろうと思えばいくらでも作れる。問題は、作ったスキルが本当に呼ばれるか、そして呼ばれなくなったスキルをどう片付けるか、にある。

ここで面白い実測値がある。26個のスキルのうち、本文に「Playbook」という語を含むもの——つまり Playbook を参照しながら動くスキルは10個だけだった。**残りの約6割は Playbook を一切参照せず、単体で完結している**。`/cal` で予定を見る、`/mail` でメールを処理する、`/org-health` で組織を点検する、といった定型操作や道具系のスキルは、判断の地図を必要としない。手順だけで足りる。

Playbook を参照している残り（10個）を見ると、`/publish`（記事公開）・`/handoff`（引き継ぎ）・`/weekly-review`（週次レビュー）といった、**手順だけでは済まず「いつ・どの条件で・どの順序で」という判断を伴うもの**が並んでいる。記事を公開するには「クロスポストはいつ・どのプラットフォームへ」という判断が要る。引き継ぎ資料を作るには「何を繰り越し、何を完了扱いにするか」の判断が要る。これらは手順（スキル）の外側に判断の地図（Playbook）を必要とした。

**この「約6割は単体完結」という数字**は、後で出てくる「スキルと Playbook の境界をどこに引くか」という設計の話に効いてくる。先に種を撒いておくと、**Playbook が併設されているのは、複雑な判断フローを持つ一部のスキルに限られていた**。最初から境界を理屈で引けたわけではなく、26個を運用した結果、後から見えてきた線引きだ、というのが正直な経緯だ。

### スキルとサブエージェントの境界

前章でサブエージェントを扱った。スキルとサブエージェントは、どちらも「Claude に何かを任せる」装置だが、渡しているものが違う。

- **スキル**: その場で実行する手順。短時間・少状態。Claude の応答1〜2ターンで完結するもの
- **サブエージェント**: 長時間の判断・複数ステップ・別コンテキストを必要とするもの

判定の目安は「Claude の応答1〜2ターンで完結するか」だ。`/todo add` はその場で1件追加して終わるからスキルでいい。一方、記事の章を執筆するのは、ネタ帳を読み、構成を組み、本文を書き、数値を実測し……と複数ステップにわたるから、writer というサブエージェントに委ねる。

この境界を間違えると、コストが見合わなくなる。スキルで済む軽作業をわざわざサブエージェントに委任すると、エージェント起動のオーバーヘッド（プロンプト準備・権限判定・往復）のほうが、直接実行するより重くなる。前章で触れたとおり、私のプロジェクトでは過去に、機械的な GitHub Issue 操作をサブエージェントに委任して失敗し、オーケストレーター側で再実行したせいでトークン消費が2倍になった事例がある。**スキルで済むものはスキルで、判断が要るものはサブエージェントで** ——この使い分けは、便利さの問題ではなくコストの問題だ。

## 何を渡すか ——ガードを一元管理する設計

### スキル化の本当の効用は「便利さ」ではない

スキルを作る理由を尋ねられたら、多くの人は「便利だから」「毎回打つのが面倒だから」と答えるだろう。それは間違いではないが、**運用が一定規模を超えると、スキルの本当の効用は別のところに移る。それは「ガードを一元管理できる」ことだ。**

ここで言うガードとは、安全装置・検証・形式チェックのことだ。同じ操作を毎回手で打っていると、人間（あるいは AI）はそのつど少しずつ違うやり方をしてしまう。引数の順序を間違える、必須のチェックを飛ばす、フォーマットがぶれる。スキルにまとめておけば、その操作に必要なガードを一か所に集約でき、誰が呼んでも同じ安全装置が効く。

これは「便利さ」とは似て非なる効用だ。便利さは「速く・楽に」の話だが、ガードの一元管理は「壊さない・ぶれない」の話だ。後者のほうが、運用が大きくなったときに効いてくる。

別の言い方をすると、ひとりで・一度きりの作業なら、ガードはたいして要らない。間違えてもその場で気づいて直せる。だが、複数のエージェントが・繰り返し・無人で（auto モードで）同じ操作をするようになると、話が変わる。誰がいつ呼んでも同じ安全装置が効いていないと、ぶれがそのまま積み重なって整合が崩れていく。スキル化の効用が「便利さ」から「ガードの一元管理」へ移るのは、ちょうどこの「ひとり・一度きり」から「複数・繰り返し・無人」へ運用が育つ境目だ。私がスキルを増やし始めた動機は確かに「面倒だから」だったが、運用が育つにつれて、スキルを維持する本当の理由は「ガードを守るため」に変わっていった。

### `/todo` スキルが GitHub Issue 操作を一元化する設計

具体例として `/todo` スキルを見てみる。これは私のタスク管理の中核で、GitHub Issue を GTD（Getting Things Done）式のタスクリストとして扱うスキルだ。実測すると本文は305行ある。なぜこんなに長いかというと、このスキルが大量のガードを抱え込んでいるからだ。

`/todo` が一元管理しているガードは、たとえば次のようなものだ。

- **GTD ラベル体系**: `next`・`waiting`・`someday`・`project`・`inbox`・`routine` といったカテゴリラベルの付与ルール
- **リカレンス処理**: 繰り返しタスク（毎週・毎日）の再生成ロジック
- **due / estimate / recur の形式バリデーション**: 締切や見積もりの記述フォーマットを検証する

私のプロジェクトのルールには、こう明文化してある。

> GitHub Issue のタスク登録・更新は `/todo` スキル経由。`gh issue create` / `gh issue edit` 等で直接操作しない。理由: GTD ラベル体系・リカレンス処理・due/estimate/recur の形式・バリデーションを `/todo` が一元管理しており、直接操作すると整合が崩れる。

つまり、`gh issue create` という公式コマンドを直接叩けば Issue は作れる。だがそれをやると、GTD ラベルが付かなかったり、due の形式がぶれたりして、`/todo` が前提にしている整合が崩れる。`/todo` 経由なら、これらのガードが必ず通る。**スキル化の効用は「GitHub Issue を作るのが楽」ではなく「GitHub Issue を作るときに必ず GTD の作法が守られる」ことにある。**

### 「直接実行」がガードをバイパスする ——blogsync の事例

ガードの一元管理がなぜ重要か、痛い思いをして学んだ事例がある。記事をはてなブログに同期する `blogsync` というツールの直接実行で、私のプロジェクトは同じ型の事故を複数回繰り返した（詳細な事故の経緯・設定面の解剖は第6章で扱う。ここでは「スキル化＝ガード集約」という効用の側面に絞る）。

結果だけ言うと、ラッパースクリプトを経由せずに `blogsync` を直接実行すると、設定ファイルのパスが作業ディレクトリに依存して二重になり、**公開済み記事の URL が書き換わってしまう**。一度 URL が変わると外部リンクが切れ、検索エンジンの評価もリセットされる不可逆な被害だ。

**手順をラッパーやスキルに集約しておけば、パス依存の吸収・実行前確認・パラメータ検証といったガードを一か所に閉じ込められる。** 直接実行を許すと、そのガードを誰もが（AI も含めて）うっかりすり抜けられてしまう。

ただし、正直に書いておくと、**ラッパー化すれば事故が防げるわけではなかった**。ガードを一か所に集めるということは、**そのガードがバグると一斉に壊れる**ということでもある。だから私のプロジェクトでは、ラッパーを信頼しきらず、「1件だけ本実行 → URL が変わっていないことを確認 → 残りを再承認」という段階実行を必須にした。スキル化は万能の盾ではない。集約したガード自体を疑い続ける運用が要る。

ここまでで、ガードの一元管理には2つの顔があることが見える。`/todo` のガードは「フォーマットを正しく揃える」という**整える**ガードだった。blogsync のラッパーのガードは「事故を起こさせない」という**守る**ガードだった。整えるガードは、間違っても致命傷にはならないが、放っておくと整合がじわじわ崩れる。守るガードは、間違えると一発で不可逆な被害が出る。スキルにどちらのガードを集約するかで、設計の慎重さの度合いも変わってくる。守るガードを集約したスキルほど、前述のとおり「ガード自体がバグると一斉に壊れる」リスクを抱えるので、段階実行や実行前確認といった二重の安全装置を組み込んでおく必要がある。**スキル化は「便利な手順をまとめる」ことに見えて、実は「どの種類のリスクをどこに集約するか」という設計判断**なのだ。

## どう渡すか —— SSoT と「30行ルール」

### ワークスペースと `~/.claude/` の「2階建て」

スキルを作るとき、ファイルは2つの場所に関わる。

- **SSoT（正本）**: `workspaces/skill-dev/<skill>/SKILL.md`。スキルの設計と実装の正本がここにある
- **デプロイ先**: `~/.claude/commands/<skill>.md`。Claude Code が実際に読み込んで実行する場所

この「2階建て」が要点だ。`~/.claude/` 配下はあくまでデプロイ先であり、編集の対象ではない。正本はワークスペースにあり、ワークスペースからデプロイ先へ片方向に同期する。私のプロジェクトのルールでは、デプロイ（ワークスペース → `~/.claude/` への同期）は devops エージェントが担い、SSoT の更新は skill-dev エージェントが担う、と責務を分けている。

なぜわざわざ2階建てにするのか。**SSoT を決めないと、スキルの定義は必ず分裂するからだ。** 緊急のバグ修正で `~/.claude/` のファイルを直接いじると、その変更はワークスペースの正本には反映されない。次に正本からデプロイし直したとき、緊急修正は旧定義に上書きされて消える。あるいは逆に、ワークスペースだけ直してデプロイし忘れると、実際に動くのは古い定義のまま、ということが起きる。

「正本」と「動いているもの」が一致している保証がないと、修正が効いているのかどうかすら確かめられなくなる。これはソースコードを Git で管理するのと同じ発想だ。手元で動いているバイナリではなく、リポジトリのソースが正本であり、ビルドはそこから一方向に流れる。スキルも同じで、正本はワークスペースにあり、`~/.claude/` はそこからデプロイされた「ビルド成果物」だと捉える。この捉え方が腹落ちすると、「動いているファイルを直接いじる」ことが、なぜ事故を呼ぶのかが見える。直接いじるのは、ビルド成果物を手で書き換えて「直った」と言い張るのと同じだ。

責務を devops と skill-dev で分けているのにも理由がある。SSoT の更新（設計を変える）と、デプロイ（変えた設計を反映する）は、性質の違う作業だ。前者は判断を伴い、後者は手順だ。両方を1人（1エージェント）が握っていると、「ちょっと直してそのまま反映」が習慣になり、正本を更新しないまま動くものだけ変える、という近道に流れやすい。あえて担い手を分けることで、「正本を更新する」という工程を飛ばしにくくしている。これも、ガードを仕組みで支える設計のひとつだ。

このプロジェクトのルールには「緊急パッチ等でやむを得ず `~/.claude/` を直接変更した場合は、直後にワークスペースへ取り込んで SSoT を最新化する」と書いてある。緊急対応そのものは許すが、**正本との同期を後回しにしない**、という運用だ。

ここにも、まだ決めきれていない部分がある。2階建ての両側が食い違ったことを、どう検知するか、だ。今のところ私のプロジェクトには、ワークスペースとデプロイ先の差分を自動で見張る仕組みはない。緊急修正の同期忘れは、たいてい「あれ、直したはずの挙動が直っていない」と気づいたときに初めて発覚する。差分監視のスクリプトを入れるべきか、それとも手作業の規律で足りるのか ——ここは答えを出していない。運用規模が今の26スキル程度なら、規律で回せている。だが、これが増えていけば、同期ずれの検知は仕組みで支える必要が出てくるかもしれない。スキルを「どう渡すか」の設計は、渡す数が増えるほど重くなる、ということでもある。

### 「30行ルール」が生まれた事故

SSoT の設計がなぜ大事かを、私は事故から学んだ。2026年5月11日、私のプロジェクトでこんなことが起きた。

ユーザーから「AI の成果物をレビューするとき、読みやすいように HTML に変換できる?」と相談を受けた。本来この種の実装は skill-dev エージェントに委任すべきものだ。ところがオーケストレーターである COO は、設計フェーズ（Plan mode）を終えた勢いのまま、**自分で `/preview` というスキル一式を実装してしまった**。

実装の中身は、スキル定義1行に加えて、シェルスクリプト約100行・HTMLテンプレート約120行。合計で約220行あった。これが何の問題もなく動いてしまったのが、かえって厄介だった。動いたので「できた」と思った。だがユーザーからこう指摘された。

> skill-dev に依頼せずに COO が作ったから、本番にしか開発物がないんじゃない?

そのとおりだった。COO が直接作ったので、実装ファイルは `~/.claude/` 側（デプロイ先）にしか存在せず、**SSoT であるワークスペースには正本が一切なかった**。さらに skill-dev の開発フローに含まれるレビューの工程も飛ばしていた。動くけれど、設計の作法を踏み外した状態だった。

この事故の後、ふたつのルールが生まれた。

ひとつは **SSoT 配置ルール**。「スキル定義 + 実装ファイルの合計が30行を超える場合は、ワークスペースに SKILL.md を SSoT として用意する」。軽量なスキル（1行委譲だけで実装ファイルがない、あるいは既存スクリプトの薄いラッパ）は SSoT を省略してよい。

もうひとつが、その閾値そのものを使った **「30行ルール」**。「スキル定義 + 実装ファイルの合計が30行を超える新規作成・大幅変更は、skill-dev に委任する。30行未満の軽微修正は COO 直接でよい」。`/preview` の約220行は、明らかにこの境界の向こう側だった。

30行という数字に深い理論的根拠はない。**「軽微な修正」と「設計を伴う実装」を分ける体感の境界**だ。30行を超えると、SSoT の配置・テスト・デプロイの責務分離が必要になる規模だ、という運用上の目安にすぎない。だが目安であっても、明文化された閾値があることで「これは自分でやっていい範囲か」を毎回考え直すきっかけになる。事故は「軽微だと独断で判断した」ことから起きた。閾値はその独断を止めるための装置だ。

事後リカバリとして、skill-dev に委任し直して、ワークスペースに `SKILL.md`（正本）が作られた。執筆時点で確認すると、`workspaces/skill-dev/preview/SKILL.md` は実在している。事故から正本が回復された記録として残っている。

### スキル作成・修正は skill-creator を経由する

もうひとつ、どう渡すかに関わる運用ルールがある。**スキルの新規作成・修正・デバッグには、最初に skill-creator スキルを呼ぶ。** 手動編集で試行錯誤しない。

これも失敗から来ている。あるスキルのフォーマット修正で、手動編集を2回繰り返してしまったことがあった。skill-creator を最初から使えば、正しいフォーマットを一発で出せたはずだった。手動編集の怖いところは、**2階建ての片側だけを直してしまいがち**なことだ。デプロイ先だけ直して正本を忘れる、あるいはその逆。skill-creator のように SSoT 配置・デプロイ・テンプレート適用を一気通貫で扱う道具を経由すれば、片側だけ直すミスを構造的に避けられる。

### 試作 → 実証 → 定常化のフロー

新しいスキルは、最初から作り込まない。私のプロジェクトでは、次の3段階を踏む。

1. **試作**: まず仮の形で作って動かしてみる（HTML 成果物なら `tmp/preview/` に試作する、など）
2. **実証**: 実際に使ってみて、効果があるか・本当に呼ぶかを確かめる
3. **定常化**: 効果が確認できたら、正式なスキルとして仕立てる

実例が `/blog-status` スキルだ。これは Zenn 記事の公開状況を確認するスキルで、当初は CLI でテキストのサマリーを出すだけだった。その後、`/blog-status html` という引数を渡すと、HTML のダッシュボードを生成してブラウザで開く機能が加わった。この HTML 版は、いきなり定常機能として作ったのではなく、**まず試作で出してみて、ダッシュボードとして実際に役立つと確認できてから定常化した**。実測すると、`/blog-status` のスキル定義は31行で、`html` 引数のときだけ Python スクリプトを呼んでダッシュボードを生成する、という素直な分岐になっている。

この3段階を踏むメリットは、「呼ばれるかどうか」を作り込む前に確かめられることだ。試作は捨てやすい。`tmp/` に置いた試作スクリプトは、効果がなければそのまま消せばいい。SSoT を整え、デプロイし、ルールに組み込んで……と作り込んだ後で「やっぱり呼ばれなかった」と気づくのは、はるかに痛い。試作 → 実証のステップは、「作り込むコストを払う前に、呼ばれる見込みを検証する」関門として機能する。

逆に、この試作 → 実証のステップを飛ばして「便利そうだから」といきなり定常化したスキルは、次の節で扱う「あとで使う」スキル ——つまり、作ったけれど呼ばれないスキルになりやすい。退役させた3本のうち `obsidian-link` / `obsidian-sync` は、環境（Windows）の前提が変わって動かなくなった例だが、`powerup-ja` のように「意図不明」と整理されたスキルは、まさに発火条件を設計せずに作って、呼ばれる場面が定義されないまま残っていたケースだ。試作 → 実証を通っていれば、「呼ばれる場面がない」ことは定常化の前に見えていたはずだった。

## 渡しすぎると何が起きるか ——退役判定と削る機制

### 「あとで使う」で作ったスキルは使われない

ここまで「どう渡すか」を見てきた。最後は通奏低音である「渡しすぎると何が起きるか」だ。

スキルを渡しすぎたときの最初の症状は、**「あとで使う」つもりで作ったスキルが、一度も呼ばれないまま溜まっていく**ことだ。

「便利そう」で作ったスキルは、たいてい発火条件が曖昧だ。いつ・どんな状況で呼ぶのかが設計されていない。だから、いざその場面になっても呼ばれない。人間が「そういえばあのスキルがあったな」と思い出す前に、手で済ませてしまう。AI のエージェントも同じで、発火条件が定義されていないスキルは選ばれにくい。

これは便利さの問題ではなく、設計の問題だ。スキルを作るときに「これはいつ呼ばれるのか」「どんなキーワードや状況で発火するのか」を一緒に設計しないと、そのスキルは「あとで使う」棚の肥やしになる。前節の `/blog-status html` が定常化できたのは、試作の段階で「実際に呼ばれる」ことを確認できたからだ。

ここで「自虐ではなく、設計の判断軸として」書いておきたいことがある。「あとで使うスキルを作ってしまうのは怠慢だ」と言いたいのではない。むしろ、便利そうなものを思いついたら作ってみる、という動き自体は健全だ。問題は、作った後にそれを「呼ばれているか」で評価し直す仕組みがないことだ。作る判断と、残す判断は別物である。作るのは試作として気軽でいい。だが、定常のスキルとして `~/.claude/commands/` に置き続けるかどうかは、「実際に呼ばれているか」という別の基準で判定する。この2つの判断を分けて持つことが、スキルを増やしつつ太らせない設計の核心だ。

### 退役判定 ——3本のスキルを退役させた実例

呼ばれないスキルが溜まると、何が悪いのか。`~/.claude/commands/` に並ぶスキルが増えるほど、Claude Code が読み込む選択肢が増え、コンテキストを圧迫する。「どのスキルを使うか」の判断ノイズも増える。**使われないスキルは、ただ存在するだけでコンテキストを汚し続ける。**

このメカニズムは少し説明が要る。スキルには「いつ呼ぶか」を Claude に伝えるための説明文（description）が付いている。`/todo` の説明文を実測すると、「タスク・todo・GTD・Inbox・next actions……」と発火キーワードがびっしり並んでいて、それ自体がそれなりの長さを持つ。スキルが1個増えるということは、この説明文が1個分、Claude が毎回読む対象に加わるということだ。呼ばれないスキルでも、説明文は読み込まれ続ける。しかも、似た説明文のスキルが複数並ぶと、「このタスクはどのスキルの担当か」という判断が曖昧になり、間違ったスキルが選ばれたり、どれも選ばれなかったりする。**呼ばれないスキルは、自分が呼ばれないだけでなく、隣のスキルが正しく呼ばれる確率まで下げる。** これが「コンテキストを汚す」の実態だ。第1章で CLAUDE.md が肥大化すると Claude が読まなくなる、という話をしたが、スキルでも同じことが起きる。装備は、増やすほど効くわけではない。

だから削る。私のプロジェクトでは2026年5月17日に、未デプロイのスキルを棚卸しして、**3本のスキルを退役させた**。

- `powerup-ja` — 棚卸しの過程で「意図不明」と整理され、ユーザーが明示的に「不要」と判断した
- `obsidian-link` — Windows 専用（robocopy / powershell.exe に依存）で、現在の Mac 環境では動作しない
- `obsidian-sync` — 同上、Windows 専用で Mac では動かない

退役の判定基準を一般化すると、次のあたりになる。

- **直近で一度も呼ばれていない**: 使われていないスキルは、まず退役候補
- **同等の機能を別のスキル・別のルートが提供している**: 重複しているなら片方は要らない
- **発火条件が曖昧で「いつ使うか」が定義されていない**: 設計の時点で呼ばれる見込みがないもの
- **環境が変わって動かなくなった**: `obsidian-link` / `obsidian-sync` のように、OS 移行で前提が崩れたもの

ここで運用上のニュアンスをひとつ。退役させたといっても、**3本のスキルのワークスペース（SSoT）は削除していない**。実測すると、`~/.claude/commands/` 側（デプロイ先）には3本とも存在しないが、`workspaces/skill-dev/` 配下のディレクトリは残してある。退役とは「デプロイしない（実際に読み込ませない）」ことであって、「正本を消し去る」こととは別だ。将来また環境が変わって `obsidian-link` が再び役立つかもしれない。そのときのために設計の記録は残す。**コンテキストから外すことと、記録を捨てることは違う。** この線引きは、削る作業を恐れずに行うための安全弁でもある。

### 退役判定の「開いている問い」 ——まだ決めきれていないこと

正直に書くと、退役判定の運用にはまだ決めきれていない部分がある。本書のネタ帳を作る段階で、私自身が「これはまだ答えが出ていない」と書き残した問いがふたつある。

ひとつは **退役判定の頻度**だ。「年1回」「月1回」と定期的に棚卸しするのか、それとも「コンテキストが圧迫されてきたと感じたら」という事象ベースで回すのか。私のプロジェクトは現状、後者の事象ベースで運用している。2026年5月17日の棚卸しも、「未デプロイスキルが溜まってきた」という気づきから始まった、定期的でない一度きりの判断だった。定期化すべきかどうかは、まだ答えを出していない。

もうひとつは **退役判定の境界線**だ。「直近で呼ばれていない」を機械的な絶対基準にしてしまうと、利用周期が長いスキルが誤判定される。たとえば年次レビューのように年に1回しか呼ばないスキルは、3か月単位で見れば「使われていない」ように見えてしまう。スキルごとに利用周期を申告する仕組みが要るのかもしれないが、そこまでの仕掛けが本当に必要かは、まだ判断していない。

この2つを「未解決のまま」書いておくのには理由がある。**退役判定は、機械的なルールで自動化しきれる種類の判断ではない**、というのが現時点での私の見立てだからだ。「90日呼ばれていなければ自動退役」のような単純なルールは、季節性のあるスキルを誤って切ってしまう。かといって人間が毎月棚卸しするのもコストがかかる。だから今は、コンテキスト圧迫を感じたタイミングで、人間の判断を交えて事象ベースで回している。これが最適解だと言い切るつもりはない。むしろ「削る機制をどう設計するか」自体が、まだ育てている途中の運用だ、というのが正直なところだ。

待つ間にできることは明確だ。スキルを新しく作るたびに「これはいつ呼ばれるのか」を設計に書き添えておくこと。発火条件を明示しておけば、後から退役判定をするとき「設計どおりに呼ばれているか」を照らし合わせられる。退役の精度は、作るときの設計の解像度に依存する。

### スキルが太ったら、Playbook へ切り出す

この章を、冒頭の問いに戻して閉じたい。「スキルと Playbook は別物だ」と書いた。その境界は、この組織の運用の中で何度も引き直されてきた、とも書いた。

最初、私は境界を理屈で引けなかった。「便利な手順は全部スキルにすればいい」と思っていた。だが運用してみると、**26個のスキルのうち約6割は Playbook を参照せず単体で完結していた**一方で、`/publish`・`/handoff`・`/weekly-review` といった**複雑な判断フローを持つ一部のスキルだけが Playbook を併設していた**。これは事前に設計した比率ではない。26個を作って動かした結果、後から見えてきた線引きだ。

ここから学べることはこうだ。**スキルの中に「いつ・どの場合は・なぜ」という判断が増えてきたら、それはそのスキルが太りすぎているサインであり、判断の部分を Playbook に切り出すべき合図である。** 手順はスキルに、判断は Playbook に。`/publish` がスキルでありながら公開フローの Playbook を参照しているのは、「公開という操作」は手順だが「いつ・どの順序で・どの条件なら公開するか」は判断だからだ。両者を1つのスキルに詰め込もうとすると、スキルは判断ロジックで膨らみ、読みにくく直しにくくなる。

そして、ここが次章への入口になる。スキルが判断を抱え込んだとき、その判断を渡す場所が必要になる。それが Playbook ——「判断の地図」だ。スキルが「今すぐ走らせる手順」を渡す場所なら、Playbook は「いつ・なぜ・どう分岐するか」を渡す場所だ。次の章では、その判断の地図をどう描き、どう腐らせず、どう参照させ続けるかを解剖する。スキルを太らせないために手放した判断は、どこへ行くのか ——その行き先が、次の章のテーマである。
