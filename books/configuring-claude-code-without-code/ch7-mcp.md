# 第7章 MCP — 繋げる場所、繋げすぎない設計

これまでの6つのレイヤーは、すべて「私が文章を書いて渡す」ものだった。CLAUDE.md にルールを書く、Playbook に手順を書く、メモリに記憶を書く。設定・権限ですら、何を許し何を禁じるかを私が書いて決めていた。

MCP（Model Context Protocol）だけは性質が違う。これは書くものではなく、**既にあるものを選んで繋ぐ**ものだ。Google Drive を操作する MCP、GA4 のデータを取ってくる MCP——世の中に公開されているサーバーから「これを繋ぐ」と決めて設定ファイルに1ブロック足すと、Claude Code が新しい能力を1つ手に入れる。

まだ MCP を1つも繋いだことがなくても、この章を読む価値はある。本章でするのは「繋ぎ方」の手順説明ではなく、「**何を選び、どこで止めるか**」という設計の話だからだ。これから初めて1つ繋ぐ人ほど、最初の1つを選ぶ前に読んでおいてほしい。

本章の結論を先に言う。MCP は「能力を増やす場所」であり、第6章で扱った設定・権限が「能力を狭める場所」だったのとちょうど逆を向いている。だからこそ、本書の通奏低音である「渡しすぎない」は、MCP では「**繋げすぎない**」という形で立ち現れる。繋げば繋ぐほど Claude はできることが増える——のではなく、繋げすぎると、繋いだはずの能力が使われないまま、応答の品質だけが静かに落ちていく。本章ではこの逆説を、実際に私が繋いでいる4つの MCP を例に解いていく。

なお、これまでの6章が「どう設計するか」を問う章だったのに対し、本章だけは「**どう選ぶか**」を問う章だ。書く対象ではなく選ぶ対象だから、問いの軸そのものが違う。6 + 1 という構造で、MCP を最後に1つだけ別枠で置いているのはそのためだ。

## MCP とは何か——「能力追加」を渡す場所

### 設定・権限が「境界線」なら、MCP は「能力」

第6章で、設定・権限は「何をしてよいか」を狭める場所だと書いた。`settings.local.json` に許可パターンを並べる作業は、本質的に引き算だった。デフォルトで何でもできてしまう状態から、危ないものを禁じ、必要なものだけ許す。最小権限の原則とは、能力を絞り込んでいく作業のことだった。

MCP はその逆だ。Claude Code は素のままだと、ファイルを読んだりコマンドを実行したりはできても、たとえば GA4 のアクセス解析データを取ってくることはできない。そこに analytics-mcp という MCP を繋ぐと、「GA4 のレポートを取得する」という能力が1つ増える。Google Drive を操作したければ google-drive MCP を繋ぐ。検索流入を見たければ Google Search Console の MCP を繋ぐ。

つまり、

- **設定・権限**: できることの範囲を狭める（引き算）
- **MCP**: できることそのものを増やす（足し算）

同じ「渡す」でも向きが真逆だ。第6章までずっと「削れ」と言ってきた本書が、ここで初めて「足す」レイヤーに到達する。だからこそ注意が要る。足し算のレイヤーでは引き算の習慣が効かない。意識して止めないと、人はいくらでも足してしまう。

### 私が実際に繋いでいる4つの MCP

抽象論だけでは掴みにくいので、私の手元の `.mcp.json` を見せる。このプロジェクトには現在、4つの MCP が繋がっている。

```json
{
  "mcpServers": {
    "google-drive": { "command": "npx", "args": ["-y", "@piotr-agier/google-drive-mcp@2.2.0"] },
    "analytics-mcp": { "command": "uvx", "args": ["analytics-mcp"] },
    "blacktwist":    { "type": "http", "url": "https://blacktwist.app/api/mcp" },
    "gsc-mcp":       { "command": "uvx", "args": ["mcp-gsc"] }
  }
}
```

※認証情報のパスや `env` などは省略している（後述）。

見慣れない `npx` と `uvx` について半行だけ補足しておく。`npx` は Node.js 系ツールの実行コマンド、`uvx` は Python 系ツールの実行コマンドだ。どちらも事前にインストールせずにツールを呼び出せるショートカットだと思えばよい。また、`blacktwist` のように URL を直接指定する MCP は、エンドポイントが変更される場合がある。最新のエンドポイントはサービス提供元で確認してほしい。

それぞれが渡している「能力」はこうだ。

- **google-drive**: Google Drive のファイルを読み書きする能力
- **analytics-mcp**: GA4 のアクセス解析データを取得する能力
- **gsc-mcp**: Google Search Console の検索パフォーマンスを読む能力
- **blacktwist**: 外部サービス（HTTP 経由）の機能を呼ぶ能力

ここで本章のルールを1つ決めておく。**この4つを1つずつ詳しく紹介することはしない**。それをやると本書は「使える MCP カタログ」になる。本書が問うのは「何を繋ぐか」ではなく「どう選び、どこで止めるか」だ。4つは「能力を足すとはこういうことだ」という見本にすぎない。

繋いだ瞬間、Claude のシステムプロンプトには、その MCP が提供するツールの一覧と、それぞれの引数の説明（ツールスキーマ）が読み込まれる。4つ繋げば4つ分のツール定義が、毎回の会話の冒頭に積まれる。この「毎回積まれる」性質が、次の節の選定基準すべての出発点になる。

## 何を渡すか——「機能の少ない方を選ぶ」

### 同じ能力なら、ツールが少ない MCP を選ぶ

MCP を選ぶとき、誰でも一度はこの罠にはまる。同じ目的の MCP が複数あったとき——たとえば Gmail を操作する MCP は世の中に複数存在する——つい「**機能が多い方**」を選んでしまう。せっかく繋ぐなら、できることが多い方がお得に見える。後から「あの機能も欲しかった」とならずに済む。

これは罠だ。私の経験上、選ぶべきはむしろ**機能が少ない方**、正確に言えば「自分が実際に使うツールだけを提供している方」だ。

理由は、さっき触れた「毎回積まれる」性質にある。MCP が提供するツールは、1つ1つが名前・説明・引数のスキーマを持つ。それらは Claude が会話を始める前に、コンテキストウィンドウ——一度に読める文章の枠——へ読み込まれる。20個のツールを持つ高機能 MCP を繋げば、20個分の定義が毎回の会話の頭に積まれる。実際に使うのが3個でも、残り17個分の定義はずっと枠を占有し続ける。

コンテキストウィンドウは有限だ。ツール定義が積まれるほど、本来の作業に使える余白は減る。そして経験上、コンテキストが圧迫された Claude は応答の質が落ちる。指示の細部を取りこぼしたり、長い文脈の前半を忘れたりする頻度が上がる。

> ここで断っておくと、「ツール定義が何トークン消費して、応答品質が何%落ちる」といった**確定した数値を私は持っていない**。MCP ごとのスキーマのサイズも、それが応答に与える影響も、正確に測ろうとすると条件依存が大きすぎる。だから本章で「コンテキストを食う」「品質が落ちる」と言うのは、あくまで運用を続けてきた**実感値**として読んでほしい。数値で殴る話ではなく、設計の向きの話だ。

### 「機能比較表」ではなく「必要ツールリスト」から選ぶ

この実感を選定の手順に落とすと、こうなる。

多くの人は MCP を選ぶとき、候補を並べて**機能比較表**を作る。A は20機能、B は8機能、C は12機能……となれば、A が一番強そうに見える。だがこの比較表は「多い方が良い」という前提でできているので、罠にまっすぐ突っ込む。

正しい順序は逆だ。先に**自分が必要なツールのリスト**を書く。「私が MCP に求めるのは、GA4 のレポートを期間指定で取ってくること。それだけ」と書く。その上で、そのリストを過不足なく満たす MCP を選ぶ。20機能の MCP が必要な3機能を含んでいても、3機能だけの MCP があるなら後者を選ぶ。残り17機能は、私にとっては「使わないのにコンテキストを占有し続ける重り」でしかない。

「能力 = 善」ではない。これが本章で一番伝えたいことだ。足し算のレイヤーだからこそ、「多い方が得」という直感を意識的に裏切る必要がある。

### 繋いだだけでは、使われない

選定の話の裏側に、もう1つ重要な事実がある。**MCP は繋いだだけでは使われない**。

これは第3章のスキルで書いた「あとで使うと思って作ったスキルは使われない」問題と、まったく同じ構造だ。analytics-mcp を `.mcp.json` に足した瞬間、Claude は「GA4 のデータを取れる」能力を手に入れる。だが、能力を持つことと、能力が使われることは別だ。「誰が・いつ・何のために」呼ぶのかが決まっていなければ、その MCP は繋がったまま一度も呼ばれずに眠る。

私の場合、analytics-mcp が実際に機能し始めたのは、それを呼ぶ Playbook を用意してからだった。Vol.3「書き続けるまで」で、毎週 GA4 の指標を3つだけ見るルーティンを作った話を書いた。「週次でアクセス解析をするとき、この MCP でこの指標を取り、こう判断する」という段取りを Playbook 側に書いて初めて、繋いだ能力が仕事として回り始める。MCP 単体は能力の受け皿でしかない。それを呼ぶ位置——Playbook の手順なり、スキルの一工程なり——が用意されて、ようやく一つの仕事になる。

だから MCP の設計は MCP の中だけで完結しない。「繋げば使われる」と思って数を増やすと、呼び出し位置のない能力ばかりが溜まる。繋ぐ前に「これは誰が、どの手順の中で呼ぶのか」を一度問う。答えられないなら、まだ繋ぐ時ではない。

### 認証情報の置き場所に注意する

選び方の最後に、安全の話を1つだけ。MCP の多くは外部サービスに繋ぐので、認証情報（OAuth のクレデンシャルや API キー）が必要になる。

stdio 型の MCP（`command` で起動するもの）では、認証情報そのものではなく、認証情報が置いてある**ファイルへのパス**を `env` で指定できる。

```json
"analytics-mcp": {
  "command": "uvx",
  "args": ["analytics-mcp"],
  "env": { "GOOGLE_APPLICATION_CREDENTIALS": "/path/to/credentials.json" }
}
```

クレデンシャル本体は git の管理外に置く。`.mcp.json` には「鍵のありか」だけを書き、鍵そのものは書かない。

一方、HTTP 型の MCP（`type: "http"` で URL を直接指定するもの）は、認証ヘッダーにトークンを書く構成になりがちだ。HTTP 型を使う場合は、トークンを設定ファイルに直書きしないよう環境変数参照などを検討しておく必要がある。

これは第6章の設定・権限の話と地続きだ。MCP は外部サービスへの扉を1つ開ける行為でもある。扉を開ける以上、その鍵をどこに置き、誰が触れるかは、能力を足す前に決めておく。能力追加のレイヤーが、唯一はっきりと「狭める」設計を必要とするのが、この認証情報の置き場所だ。

## 渡しすぎると何が起きるか——コンテキスト圧迫と差し替え連鎖

### 繋げすぎは、静かに進む

ここまでで「機能の少ない方を選べ」「呼ぶ位置がないなら繋ぐな」と書いてきた。それでも繋げすぎは起きる。なぜなら、繋げすぎの害は**派手な事故として現れない**からだ。

CLAUDE.md を書きすぎれば Claude が読まなくなる。権限を広げすぎれば、いつか事故が起きる。これらは比較的気づきやすい。だが MCP を繋げすぎたときに起きるのは、「なんとなく応答の精度が落ちた気がする」という、原因の特定しづらい鈍い劣化だ。1つ足したくらいで体感は変わらない。だから人は気軽に2つ目、3つ目を足す。気づいたときには、使っていない MCP のツール定義が会話のたびに積まれ、コンテキストの余白を恒常的に削っている。

ここに足し算レイヤーの本当の怖さがある。MCP は「無料の追加機能」ではない。繋いだ瞬間から、使う・使わないにかかわらず、ツールスキーマ分のコンテキストというコストを**毎回払い続けている**。サブスクの幽霊会員のように、使っていないのに料金だけ引き落とされている状態だ。

### 後で差し替えると、依存していたものが壊れる

繋げすぎのもう1つの帰結が、差し替えの連鎖だ。

仮に、いま使っている google-drive MCP を別の高機能な Drive 操作 MCP に差し替えたくなったとする。能力としては上位互換だから繋ぎ替えるだけに見える。ところが、ツールの**名前や引数の形**は MCP ごとに違う。同じ「Drive のファイルを取得する」操作でも、片方は `get_file(id)`、もう片方は `download(fileId, format)` だったりする。

すると、その MCP を呼んでいた Playbook やスキルが軒並み壊れる。「この手順の中で、この MCP のこのツールをこう呼ぶ」と書いてあった段取りが、ツール名の変わった新しい MCP では通らない。MCP を1つ差し替えただけなのに、依存していた他レイヤーを芋づる式に直す羽目になる。

これは「MCP は他レイヤーと連動して初めて機能する」という性質の裏返しだ。呼び出し位置を持った MCP を差し替えると、その位置を抱えている全レイヤーに影響が波及する。だから MCP の選定は「いま動けばいい」ではなく、「将来これを差し替えるとき、何が一緒に壊れるか」まで見て決める。繋ぐ数が増えるほど、この連鎖の面積も広がる。

### エージェントごとに分けるか、一元化するか——まだ答えのない問い

最後に、正直に「まだやれていない」ことを1つ書く。

このプロジェクトでは、`.mcp.json` がプロジェクトルートに1つだけ置かれている。つまり**全エージェントが同じ4つの MCP を共有**している。COO も researcher も writer も、全員が同じツール定義を会話の頭に積んで動く。

だが冷静に考えると、writer に GA4 の解析能力はほぼ要らない。GA4 を見るのは researcher の仕事だ。理屈の上では、エージェントごとに必要な MCP だけ持たせれば、それぞれのコンテキストはもっと軽くなる。これが「機能の少ない方を選ぶ」を組織に適用した姿だろう。

ではなぜやっていないか。エージェントごとに構成を分けると設定ファイルが分散し、管理コストが上がる。そして今のところ、一元化による品質劣化が「直さないとまずい」レベルでは体感できていない。

判断軸はここにある。「**コンテキスト圧迫の実害が出ているか**」。出ていないうちは、管理コストを払ってまで分ける必要はない。実感として品質が落ちてきたら、その時点でエージェント別分離に踏み込む。これは設計の不備ではなく、「まだ削る必要が出ていないから削っていない」という本書らしい判断の保留だ。その節目は、繋いだ MCP が5つ、6つと増え、応答の取りこぼしが体感できるようになったときだろう。

## この章のまとめ——そして7つのレイヤーを巡り終えて

MCP は能力を足すレイヤーだ。だからこそ、本書で唯一「足し算が前提」の章になった。そこで繰り返し言ってきたのは、足し算のレイヤーでも引き算の頭を手放すな、ということだった。

- 同じ能力なら、ツールの少ない MCP を選ぶ（コンテキストを食わせない）
- 機能比較表ではなく、必要ツールリストから選ぶ（「多い方が得」を裏切る）
- 繋いだだけでは使われない。呼ぶ位置を先に設計する
- 差し替えると依存レイヤーが連鎖で壊れる。将来の壊れ方まで見て選ぶ
- 分けるかどうかは「実害が出ているか」で決める

そして、ここまで書いて気づくことがある。これは MCP に固有の話だっただろうか。

CLAUDE.md では「書きすぎると読まれなくなる」、サブエージェントでは「増やすほど誰に頼むか迷う」、スキルでは「あとで使うつもりのものは使われない」、Playbook では「古くなっても誰も気づかない」、メモリでは「肥大化するとコンテキストを圧迫する」、設定・権限では「許しすぎると事故になる」と書いた。そして MCP では「繋げすぎると静かに品質が落ちる」。

7つのレイヤーは、渡す対象も、書くものか選ぶものかも、足し算か引き算かも、それぞれ違っていた。それなのに、各章の終わりにたどり着く問いはいつも同じ形をしていた。**何を渡し、何を渡さないか。渡しすぎたとき、何が起きるか**。

私は7つの違う部品を解剖してきたつもりだった。だが解剖を終えてみると、その奥に同じ1本の問いが通っていた。次のエピローグでは、その問いを正面から取り出す。カタログだと思って読み始めたこの本が、なぜ最初から設計書だったのか——その種明かしをして、本書を閉じたい。
