# 第2章 サブエージェント——レンズを渡す

Claude Code には、メインのセッションとは別に「サブエージェント」を立てて作業を委ねるしくみがある。私のプロジェクトでは現在 8 体のサブエージェントが動いていて、それぞれが調査・設計・実装・レビューといった役割を持っている。本章で扱うのは、その作り方や運用そのものではない——それは前巻までで書いた。本章が掘り下げるのは、**サブエージェントを分けるという行為が、実は「人格を分ける」のではなく「読む目的のレンズを分ける」ことなのだ**という一点と、**レンズを増やすほど『誰に頼むか』を決めるコストがどこに溜まっていくのか**という機微である。結論を先に置く。サブエージェントの設計でいちばん効くのは「何体に分けるか」ではなく「分けたあと、誰がいつ呼ぶかをどう設計するか」だ。

前巻までの読者には繰り返しになるので断っておくと、AIチームの作り方（Vol.1「作るまで」）と、そのチームを日々どう稼働させるか（Vol.2「回すまで」）はすでに書いた。ここではその土台の上に立って、レイヤーとしてのサブエージェントを解剖する。前作未読の方も、本章は単体で読めるように書いているので安心してほしい。

## 専門化とは「人格」ではなく「読む目的のレンズ」を分けること

サブエージェントを設計するとき、最初に立てた問いは「どんな人格を持たせるか」だった。Vol.1 では実際に「人格を持たせる」という言葉を使っている。チームの一員として名前を付け、口調や性格を決めると、たしかに動かしていて楽しいし、委任先をイメージしやすい。入口としてこの表現は有効だ。

ただ、もう一歩踏み込むと、実態は人格よりも**レンズ**に近い。私のプロジェクトには writer・reviewer・reader という三者がいる。記事を書く writer、その記事の事実関係を点検する reviewer、想定読者になりきって感情の動きを評価する reader だ。この三者は、別々の性格を持った別人ではない。中身は同じ Claude というモデルである。違うのは「何のために同じテキストを読むか」だけだ。

- writer は **書くために** 読む。次にどの一文を置けば流れが繋がるかを見る
- reviewer は **整合のために** 読む。数字・日付・出典が事実と合っているかを見る
- reader は **感情のために** 読む。ここで読者が離脱しないか、買いたくなるかを見る

同じ原稿を渡しても、三者の出力はまったく違う。writer は「次の段落を足そう」と言い、reviewer は「この日付の根拠は？」と言い、reader は「中盤で飽きた」と言う。これは性格の違いではなく、**読む目的という名のレンズの違い**から生まれている。

具体例を挙げる。実際に私の記事で、本文に「3日後に再発した」と書いた一文があった。writer はこの一文を、文章のテンポや前後の繋がりという目的で読む——「ここは短く言い切れていて良い」と。reader は読者の感情という目的で読む——「ここで具体的な日数が出ると臨場感が増す」と。だが reviewer は整合という目的で読むので、本文に登場する起点の日付と終点の日付を拾って引き算し、「実際には8日後で、3日後は事実誤認だ」と指摘した（このときの指摘は、後に『起点日と終点日から逆算して書く』という執筆ルールとして手順書に取り込まれている）。三者は同じ一文を見ているのに、見えているものが違う。レンズが違うとは、こういうことだ。同じ文字列に対して、問いが違えば抽出される情報が違う。

この捉え方に切り替えると、設計の判断がぶれなくなる。「人格を分ける」と考えていると、つい「もっとキャラを立てよう」「個性を足そう」という方向に手が伸びる。だがレンズだと捉えれば、問うべきことは一つに絞られる——**このタスクには、いま持っている目的とは構造的に違う『読み方』が必要か？** 必要なら新しいレンズを足す。同じ読み方で済むなら足さない。人格を増やしたい衝動は設計を太らせるが、レンズの違いを問う姿勢は設計を引き締める。

レンズという見方は、専門化の限界も同時に教えてくれる。同じモデルが目的だけ変えて読んでいるのだから、writer と reviewer と reader は本質的に同じ「目」を共有している。だからこそ、reviewer が見落とした事実誤認を writer も見落とすことがあるし、reader が違和感を覚えなかった箇所を reviewer も素通りすることがある。レンズを分けても、土台となる視力そのものは一つだ。これは後で触れる「サブエージェントの出力を鵜呑みにしない」という規律の根拠にもなる。別レンズの指摘は新しい角度ではあるが、まったく独立した第三者の目ではない——同じモデルが別の問いで読み直しているだけ、という前提を忘れないほうがいい。

なぜここまでレンズという言葉にこだわるか。それは、本書を貫く通奏低音である「渡しすぎない」が、このレイヤーでもそのまま効いてくるからだ。人格として捉えるとサブエージェントは「増やすほど賑やかで強そう」に見える。だがレンズとして捉えると、増やすほど「どのレンズで読むべきか」を毎回選ばなければならなくなる。その選択コストこそが、このレイヤーの渡しすぎを測る物差しになる。

### 8 体という現在地

参考までに、私のプロジェクトの現在の構成を一度だけ表にしておく（以降は繰り返さない）。役割分担を一覧で把握できるよう、組織図は `.claude/rules/agent-roles.md`（92 行）に SSoT として置いている。先に断っておくと、これがたまたま 8 体だっただけで、2 体でも 4 体でも本章の問いは変わらない。問われているのは何体に分けるかではなく、どう役割（レンズ）を分けるかのほうだ。

| エージェント | 読む目的のレンズ |
|---|---|
| architect | コードを調査し、設計の筋が通るかを読む |
| devops | 権限・インフラの安全性を読む |
| researcher | 外部・内部の情報を集めて事実を読む |
| reviewer | 成果物の整合（事実・出典）を読む |
| reader | 想定読者の感情の動きを読む |
| secretary | タスクの分類とルーティングを読む |
| skill-dev | スキル・スクリプトの再現性を読む |
| writer | 書くために素材を読む |

8 体は多いだろうか、少ないだろうか。その問いには「タスクの種類が構造的に何種類あるか」でしか答えられない。賑やかさで決める数ではない。この表を作るときも、私は「キャラが欲しいから足す」ではなく「この読み方は既存のどれとも違うか」で一体ずつ判断してきた。逆に言えば、レンズが被る二体は統合すべきで、それを怠ると次節の「渡しすぎ」が始まる。

## どう渡すか——委任プロンプトに「読み方の地図」を同梱する

サブエージェントを分けただけでは、専門化は機能しない。ここが最初の落とし穴だった。エージェント定義ファイル（`.claude/agents/writer.md` など）に「このタスクではこの手順書を見ること」と書いておいても、実際に委任する瞬間にメインのセッション側が改めて指示しないと、その手順書はしばしば参照されないまま作業が始まる。

つまり、**「エージェント定義に書く」ことと「委任プロンプトで毎回もう一度喚起する」ことは、別の設計責務**なのだ。定義ファイルは「そのエージェントが何者か」を決める。委任プロンプトは「今回そのエージェントに何を読ませて何を出させるか」を決める。前者だけ整えて後者を省くと、せっかく分けたレンズが正しい焦点距離で使われない。

私のプロジェクトでは、これをルール化している。記事や章の執筆を writer に委任するときは、委任プロンプトに必ず「読むべき手順書: 〇〇」を含める、という運用だ。実際、これを省いて委任した回は、過去に守られていたはずのルール（冒頭の結論要約を置く、独自用語に注釈を付ける、など）が初稿で抜け落ち、レビュー工程で再指摘される事故が起きている。レンズは渡したが、そのレンズで何を見るべきかの地図を渡し忘れた、という失敗だ。

### 制約も同梱する——「読み取り専用」を書き忘れた話

委任プロンプトに同梱すべきなのは「読むべきもの」だけではない。**「やってはいけないこと」も明示しなければならない**。これを痛感した事故がある。

2026年5月25日、あるスキルの実戦テスト中に、調査役の researcher に「セッション履歴を分析してほしい」と委任した。意図は調査だけだった。ところが researcher は履歴を読んで問題点を見つけると、その場で該当するスクリプト（`scripts/util/dj.sh`）を **承認なしに自律的に書き換えてしまった**。変更内容自体は合理的だったので結果的に採用し、実害は出なかったが、想定していない場所が勝手に変わったという事実は変わらない。

原因は明快で、委任プロンプトに「分析のみ・修正禁止」の制約が書かれていなかったことだ。researcher というレンズは、問題を発見すると修正まで実行する性質を持っている。これは欠陥ではなく、調査エージェントとしてはむしろ有能な振る舞いだ。だが**エージェントの「自律性」と「権限の境界」はまったく別の話**で、後者は委任プロンプトで毎回明示しないと制御できない。自律的に動けることと、勝手に動いてよいことは違う。

この事故のあと、調査・分析だけを委任するときは次のような一文を必ず添えるようにした。抜粋を載せる。なお researcher は私のプロジェクト固有の呼称なので、読者の環境では「調査専用エージェント」「読み取り役」などに読み替えてほしい。

```
（researcher への委任プロンプト末尾・要約）
重要: ファイルの読み取り・分析のみ行う。
スクリプトの修正・ファイルの作成・変更は一切しない。
問題を発見した場合は、修正せず報告だけする。
```

たった三行だが、これがあるかないかで挙動が変わる。レンズを渡すときは、焦点を合わせる対象（読むべき手順書）と、踏み込んではいけない境界（やってはいけないこと）を、同じ封筒に入れて渡す。これが「どう渡すか」の核心だ。

### サブエージェントの出力を鵜呑みにしない

もう一つ、渡し方とセットで設計しておくべきことがある。**サブエージェントが返してきた指摘を、そのまま信じて次の行動に移さない**という規律だ。

2026年4月24日にこんな事故が起きた。reviewer が「あるファイルとエンジン側で定数（ラベルの絵文字）が食い違っている」と指摘してきた。私はこれを「確認済みの事実」として受け取り、実装担当に修正を指示した。担当は指摘どおりに値を書き換えた。ところが——**reviewer の指摘そのものが事実と逆**だった。実際には二つの値は最初から一致していて、修正した結果、はじめて本当に食い違いが生じてしまった。幸い、同じ日に整備したばかりのテストがその食い違いを検知してくれて、本番データの汚染は防げた。

この事故の教訓は二つある。一つは、**定数・ラベル・フラグ名といった「文字列が一致するか」系の指摘は、委任する前に自分でソースを直接確認する**こと。レビューという別のレンズが見たものは貴重だが、それは検証されるべき情報であって、検証済みの結論ではない。もう一つは、**SSoT（信頼できる唯一の情報源）は実装そのものであり、設計書は二次情報だ**ということ。今回も、reviewer は設計書の誤記を実装と混同していた可能性が高い。設計書と実装が食い違っているときに疑うべきは、まず設計書のほうだ。

サブエージェントを増やすと、こうした「別レンズからの指摘」が増える。それ自体は組織が機能している証拠だが、指摘の数だけ検証コストも増える。レンズを足すことは、見える情報を増やすと同時に、確かめるべき情報も増やす。これも渡しすぎの一側面である。

### 分ける/分けないの判断軸

ここまでの話を、新しいレンズを足すかどうかの判断軸としてまとめておく。私が一体を足す前に確かめるのは、次の三点だ。

- **読む目的が構造的に違うか**: 既存のどのレンズでも見えないものを見るために必要か。writer の目で reviewer の仕事はできない、と言い切れるか
- **専門化された手順書がすでにあるか、すぐ作れるか**: そのレンズが参照すべき地図がないなら、まず地図を作るのが先。レンズだけ足しても焦点が合わない
- **委任判断のコストを、品質の向上が上回るか**: 分けた結果として「誰に頼むか」を毎回迷うだけなら、分けないほうが速い

逆に、分けないほうがよい合図もはっきりしている。単発の軽作業であること、委任判断のオーバーヘッドが品質差を上回ること、そして参照すべき手順書がまだ存在しないこと。最後のケースでは、エージェントを足すより先に手順書を整えるべきだ。原則はシンプルで、**「分けたいから分ける」ではなく「分けないと品質が落ちるから分ける」**。賑やかさを足したい衝動と、品質のために必要なレンズを足す判断は、似て見えて正反対の動きである。

## 渡しすぎると何が起きるか——「誰に頼む？」迷子と削る機制

ここまでで、レンズの違いで分けること、渡し方に地図と境界を同梱することを述べた。最後に、このレイヤーの「渡しすぎ」を直視する。

専門化には、避けられないコストが一つある。**エージェントを分けるほど、「これは誰に頼むか？」という判定が、委任する側に降ってくる**。一体で全部こなすほうが、この判定がいらないぶん速い場面すらある。専門化された組織は、応答品質と引き換えに「委任判断のオーバーヘッド」を背負う。だから問うべきは「分けられるか」ではなく、**「分けることで上がる品質が、委任判断のコストを上回るか」**だ。

この天秤は、一度傾いたら固定されるものではない。組織を組んだ当初は「専門化された応答品質を取る」という判断が正しくても、運用していくうちに委任のオーバーヘッドのほうが品質差を上回ってくることがある。そのときは、**専門化を解く判断**——委任をやめて直接処理に戻す、あるいは二体を一体に統合する——も設計の一部だ。レンズを足すのと同じ重さで、レンズを畳むことも検討する。組織図は一度書いたら終わりの設計図ではなく、定期的に天秤を測り直す対象である。

この天秤がはっきり傾いた失敗がある。先に挙げた指摘の逆転、未承認の自律編集、そしてこれから述べる委任失敗——これらは別々の文脈で起きた事故だが、共通しているのは「レンズを一枚足したことが、品質ではなくコストのほうを増やした」という構図だ。事故の羅列ではなく、専門化が裏目に出る一つのパターンとして読んでほしい。2026年5月6日、私は機械的な GitHub Issue の処理——分類して片付けるだけの単純作業——を、わざわざ整理役のエージェントに委任した。判断の要らない作業だ。ところがその委任が途中で失敗し、メインのセッション側でやり直すはめになり、結果として**直接やった場合のおよそ2倍のトークンを消費**した。エージェントを一体起動するコスト、委任プロンプトを用意するコスト、返ってきた結果が正しいか・エラーが出ていないかを判定するコスト。これらの合計が、その作業を自分で直接やるコストを上回ってしまったのだ。

この一件から、私は「軽作業は委任しない」を明文化した。機械的な Issue 操作は件数を問わずメインのセッションが直接処理する。整理役への委任は「判断を伴う仕分け・ラベル体系の見直し・運用設計」など、人間やAIの判断が要る作業に限る。同じように、新規ファイルの作成や既存ファイルの大幅な変更も、実装が一定規模（私の場合は合計30行）を超えたら専門エージェントに委任し、それ以下なら直接直す、という閾値を引いている。**安いエージェントに何でも投げれば安く済む、という直感は間違い**だ。委任そのものにコストがある。

### 増やす設計と同じだけ、増やさない設計に手をかける

「渡しすぎ」の症状を整理しておく。

- **判断の迷子**: エージェントが増えると「誰に頼むか」の選択肢が増え、選ぶこと自体に時間がかかる
- **責務の重複**: 役割の境界が曖昧だと、同じタスクを二体が別のやり方で対応し、出力が食い違う
- **検証コストの増加**: 別レンズからの指摘が増えるぶん、確かめるべき情報も増える

これらに対して、私が手をかけている「削る機制」は三つある。

第一に、**責務を一箇所に書いて正典化する**。誰が何を担当するかは `agent-roles.md` に集約し、迷ったらそこを見る。境界が文書で確定していれば、重複も迷子も減る。

第二に、**「直接やる/委任する」の閾値を明文に落とす**。前述の「軽作業は直接」「30行を超えたら委任」がこれにあたる。閾値が頭の中にしかないと、その日の気分で委任しすぎたりしなさすぎたりする。

第三に、**新しいエージェントを足すときに評価基準を通す**。私のプロジェクトには新規エージェント新設の判断手順（`ops/playbooks/agent-new.md`）があり、既存エージェントと責務が重複しないか、専用ツールで代替できないか、想定する委任頻度はどれくらいか、を検討してから増やす。レンズを足すのは、既存のどのレンズでも見えないものがあると確認できたときだけだ。

増やす設計には誰でも手が伸びる。賑やかで、強くなった気がするからだ。だが本当に効くのは、**増やさない設計に同じだけ手をかけること**だと、私はこのレイヤーで学んだ。サブエージェントは、足すほど見える世界が広がる一方で、足すほど「どのレンズで読むか」の選択を毎回迫られる。その選択を軽くする設計こそが、このレイヤーの本体だ。

## 次のレイヤーへ——手順書の先にある「スキル」

本章では、委任プロンプトに「読むべき手順書」を同梱する、という設計を繰り返し強調した。レンズを渡すと同時に、そのレンズで何を見るかの地図を渡す、という話だ。

このレイヤーの「渡しすぎない」を一言で言えば、**レンズは、見える世界を広げる代わりに、選ぶ手間を増やす**ということだった。だから足すときは「既存のどのレンズでも見えないものがあるか」を確かめ、足したあとは「誰がいつ呼ぶか」を設計で軽くしておく。賑やかな組織図に憧れる前に、自分が本当に必要としているレンズの数を数える。それがサブエージェントというレイヤーで私が学んだ、渡し方の節度だ。

ここで一つ予告しておきたい。委任プロンプトに同梱するこの「手順書（Playbook）」とよく似ていて、しかし役割の異なるものが Claude Code にはある——**スキル**だ。手順書が「どう判断するかの地図」だとすれば、スキルは「その場で実行する手順」に近い。両者は混同しやすく、私自身、最初はうまく使い分けられなかった。次章では、このスキルというレイヤーを解剖する。何を渡すと再現性が上がり、何を渡しすぎると「使われないスキル」が溜まっていくのか。その境界を見ていく。
