---

**この章の出来事（2026年4月）**：私は「GitHubをバックエンドにしたGTDスキル作って」と一言だけClaude Codeに頼んだ。要件定義はしていない。試しに言ってみただけだ。それでも30以上のコマンドと145以上のテストが付いたタスク管理ツールが最初の版として出てきて、その65分後には頼んでもいない「デイリーレビュー」機能まで追加されていた。

あの日から、何かが変わった気がしている。

## やることが多すぎて、頭がいっぱいになる

「あれもやらなきゃ、これもやらなきゃ」――そう思いながら、結局どれも手につかない日がありませんか。

頭の中にタスクが散らばっていると、それだけで疲れます。買い物のメモ、返信しないといけないメール、いつか読もうと思った記事、来週までの締め切り。覚えておこうとするほど、別のことが手につかなくなる。忘れてはいけないという緊張が、ずっと頭の片隅で電気を食い続けている感覚です。

世の中にはこれを解決するための仕組みがたくさんあります。タスク管理アプリ、手帳、付箋。私もいろいろ試してきました。けれど、どれも長くは続きませんでした。続かない理由はだいたい同じで、「入力がめんどくさい」からです。

思いついた瞬間にアプリを開いて、新規作成ボタンを押して、タイトルを入れて、カテゴリを選んで、期限を設定する。この一連の操作をやっているうちに、最初の「あ、これメモしておこう」という小さなやる気が冷めてしまう。結局、頭の中に戻していく。そしてまた、頭がいっぱいになる。

## 試しに「作って」と言ってみた

2026年の4月、私はClaude Codeというツールを使っていました。コードを書くのを手伝ってくれるAIアシスタントです。私自身はバリバリのプログラマーというわけではなく、込み入ったコードを一から書ける自信はありません。それでも、Claude Codeには日々いろいろなことを頼んでいました。

ある日、ふと思いついて、こう打ち込みました。

> 「GitHubをバックエンドにしたGTDスキル作って」

GTDというのは「Getting Things Done」の略で、頭の中のタスクをいったん全部外に出して整理する、有名なタスク管理の方法です。GitHubは本来プログラムのソースコードを保管する場所ですが、そこにある「Issue」という機能をタスクの保管庫として使えないかと考えました。

正直に言うと、これは要件定義でもなんでもありません。「こういうものが欲しい」と仕様を詰めて渡したわけではない。ただ試しに言ってみただけです。どんなものが返ってくるか半分くらいは様子見でした。

## 一言で、使えるものが出てきた

返ってきたものに、私は少し驚きました。

詳しく要件を詰めなかったのに、そのまま使えるものができていたのです。作業の記録（コミット履歴）で確認すると、最初の版の時点で、30以上のコマンドと145以上のテストが揃っていました。タスクを追加する、一覧を見る、期限で絞り込む――ひととおりのことが最初からできました。

さらに驚いたのは、その65分後のことです。作業の記録を見ると、「デイリーレビュー」という機能が追加されていました。朝に今日の計画を立て、夜にその日を振り返る――そういう一日のリズムを支える機能です。私はそんなものを頼んだ覚えはありません。GTDという方法に必要なものを、向こうが補ってきたのだろうと思います。

この日のことは、私の記憶だけでなく、ツールの作業履歴として残っています。プログラムの変更を保存すると、その記録が日時つきで積み重なっていく仕組みがあるのですが、そこを後から覗くと、たしかにこう刻まれていました。

```
2026-04-06  最初の版：/todo — Claude Code GTD タスク管理スキル
（65分後）  ダッシュボード・デイリーレビュー・カスタムビュー・レポート出力を追加
```

最初の版が完成し、その65分後にはデイリーレビューを含む機能が足されている。「いきなり使えた」というあの感覚は、私の思い出のなかだけで膨らんだものではなく、こうして記録として残っていました。あの一言から何かが始まった日が、たしかにあったのです。

「いきなり使えた」というのが、そのときの率直な感想でした。

## 「外にある」世界なら、こうはいかなかった

「いきなり使えた」この感じは、これまでのやり方では味わえなかったものです。タスク管理の仕組みが自分の「外にある」世界、と言い換えてもいい。その世界では、こうはいきませんでした。

もし私が、その「外にある」世界にいたら、まず既存のツールを探すところから始まったはずです。GTDに対応したアプリを調べて、機能を比較して、一番近いものを選ぶ。その使い方を覚えて、自分の手で入力していく。仮に何かを作ってもらおうとしても同じで、GTDとはどういう方法なのか、GitHubのIssueをどう使いたいのか、その両方を私自身が言葉にして渡さなければなりませんでした。知識は私の側にあり、それを噛み砕いて説明する手間が、必ず挟まったでしょう。

ところが今回は、その手間がまるごと要りませんでした。

## なぜ、一言でつながったのか

あとから振り返って、私はこう考えました。

> 「GTDとGitHub Issueの両方の知識をClaude Codeが持っていたからだろうね」

GTDという方法論の知識も、GitHubのIssueの使い方の知識も、どちらもClaude Codeの「中」に入っていた。だから、私が両方を言葉にして渡さなくても、向こうがその二つを結びつけて、形にしてくれた。私が頼んでもいないデイリーレビューが付いてきたのも、「GTDならこれが要るはずだ」という知識が中にあったからでしょう。

つまり、この出来事は、仕組みが自分の「外にある」世界から、「中にある」世界へ移ったことの、最初のしるしだったのではないか。

向こうがGTDのことも、GitHub Issueのことも知っていたから、私が説明しなくて済んだ。それがすごく大きかったと思っています。

もしこの見立てが当たっているなら、頭の中のタスクをどう扱うかという話は、根っこから変わってしまうことになります。

## 「GTD・AI・私」を一つの装置として見る

ここで、本書を通して使う見方を一つだけ先に渡しておきます。「装置」という言葉です。

このとき生まれたものは、ただのタスク管理アプリではありませんでした。GTDという整理の構造があり、それを知っているAIがいて、そこに話しかける私がいる。この三つがそろって初めて、「一言で使えるものが出てくる」という出来事が成立していました。どれか一つが欠けても、こうはならなかったはずです。

そこで本書では、この三つをばらばらに見るのをやめて、ひとまとめにして「装置」と呼ぶことにします。

> **GTDの構造 + AI + 自分自身 = 一つの装置**

ふつう、AIの話というと「人間 対 AI」――どちらが賢いか、どこまで任せられるか、という構図で語られがちです。けれど私が体験したのは、そういう対立ではありませんでした。GTDという構造を間にはさんで、AIと私が同じ一つの仕組みの中で動いている。そんな感覚に近いものでした。だから本書では、人間とAIを向かい合わせにするのではなく、構造もAIも自分も含めた全体を一つの装置として眺めていきます。「任せる」というのは、この装置そのものを信頼するということです。

もっとも、「任せる」には一種の落とし穴があります。AIに頼んでいると、「判断もClaudeに出してもらおう」という流れになりやすい。しかしそれをやり続けると、やがて「自分は何がしたいのか」がわからなくなっていきます。本書で言う「任せる」は、考えることを渡すことではなく、段取りを渡すことです。実際に使っているうちにわかってきたのは、考える順番はClaudeが先でも、最後に何を採るかは自分が決めるという感覚です。これがいまのところ、装置を長く使い続けるための一番の勘どころな気がしています。

装置の中では、ゆるやかな役割分担があります。タスクを集めたり、仕分けたり、置き場所を整えたりといった手間のかかる作業は、AIと構造のほうが引き受ける。私のほうに残るのは、「これは要る・これは要らない」と決める判断の部分です。何もかもAIに渡してしまうわけではなく、決めるところは自分の手に残る。本書を通して、この「どこまでが装置の仕事で、どこからが私の仕事か」の線引きを、場面ごとに少しずつ確かめていきます。

## 「水のような心」は、努力目標ではないのかもしれない

話を、一言でタスク管理ツールが出てきたあの驚きに戻します。あのとき私が感じた「いきなり片づいた」という軽さには、もう一つ思い当たることがありました。もう一つ、ここで小さな伏線を置かせてください。

GTDを提唱したデビッド・アレンは、頭の中が片づいた理想の状態を「mind like water（水のような心）」と呼びました。心配ごとや「あれをやらなきゃ」という焦りが頭から消えて、水面のように静かな状態。GTDを実践する人にとって、これは一種のゴールのように語られてきました。

ただ、これまではこの「水のような心」は、自分を律して手順を守り続けた人がたどり着く到達点――つまり努力目標として扱われてきたように思います。

ところが、装置に一言で話しかけてタスクが片づいていく体験をしているうちに、私はふと、別の可能性を感じました。

もしかすると、「水のような心」は頑張ってたどり着くゴールではなく、装置がきちんと回っているときに自然と出てくる出力結果なのではないか――。

これが当たっているのかどうかも、いまはまだ言い切れません。ただ、これも本書を貫くもう一つの問いとして、頭の片隅に置いておいてもらえればと思います。

## Claude Codeに「仕事」を任せると、何が変わるのか

本書では、私がClaude Codeに日々の「仕事」を任せていった過程を追っていきます。まず本書の前半で、タスクを集める「収集」、それを処理して整理する場面、実際に手を動かす「実行」、そして一日を「振り返る」場面――この四つを順に見ていきます。どれも特別なことではなく、誰もが毎日やっていることです。

ただ、装置の話をきれいごとだけで終わらせるつもりはありません。後半では、装置がうまく回らなくなる瞬間――AIが勝手に動いてしまったり、文脈を取りこぼしたりする場面を正直に書きます。あわせて、Claude Codeの「外側」にある会社のパソコンや紙のメモ、対面のやりとりをどう装置の入口につなぐか、その境界の引き方も扱います。そして終盤では、こうした装置を読者ご自身がゼロから作るための最小構成を、ひとまとめにしてお見せします。最後に、装置と一緒に過ごしてきた今をエピローグで振り返ります。

そのひとつひとつで、私は「めんどくさいから話しかけた」だけでした。ただし、話しかけて返ってきたものを、私はそのまま鵜呑みにしたわけではありません。出てきたものを見て、これは使う・これは要らないと選び、自分の使い方に合わせて受け取っていく。考える順番はClaudeが先でも、最後に何を採るかを決めるのは私のほうでした。話しかけるたびに、そんな小さな気づきがありました。その気づきを積み重ねていった先に、序章で立てたこの問いの答えがあるはずです。

そして、もしあなたがこの装置を自分でも持ってみたいと思ったら、必要なのはたった一言です。Claude Codeに「GTDに則ったタスク管理ツールを作って」と話しかける。それだけで始まります。コードを書く必要はありません。セットアップの手順を覚える必要もありません。私自身は「GitHubをバックエンドにしたGTDスキル作って」と言いましたが、最初はこのくらいの一言でも十分始まります。本書は、その一言から始まる装置の育て方を、最初から最後までお見せする本です。

――なぜ、一言でつながったのか。そして、「水のような心」は努力目標なのか、それとも装置の出力なのか。

この二つの問いへの答えは、最後のエピローグまで取っておくことにします。まずは、頭の中のタスクを「話しかけるだけ」で外に出していく、最初の場面から始めましょう。
