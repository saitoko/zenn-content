**この章の出来事（2026年6月）**：私はGTDの振り返り――とりわけ週に一度の週次レビュー――を、ずっと飛ばし続けていました。「振り返りが大事」だと頭ではわかっているのに、いざ始めようとすると「何を振り返ればいいのか」がわからず、結局やらない。それが、Claude Codeに「今日のレビューをしよう」と話しかけるだけで、まず日々の振り返り（デイリー）から回るようになりました。あるデイリーレビューの日のやりとりを大意で振り返ると、Claudeが先延ばしにしていたタスクを拾い上げて「これ、今日着手できますか？」と問いを立て、私はそれに短く答えるだけ（2026-06-02のログより。所要は約5分）。問いを立てる手間が、まるごと消えていました。

本章では、Claude Codeと一緒に「振り返り」を回した体験を追います。収集・処理・実行と任せてきた流れの、いちばん最後の場面です。ここで起きたのは、振り返りが「義務」から「会話」に変わったことでした。

## GTDの振り返りが大事と知っていても、やらない

GTDというタスク管理の方法には、たまったタスクを見直す「振り返り」の工程があります。なかでも有名なのが、一週間にいちど行う「週次レビュー」です。終わったものを片付け、積み残しを来週に回し、頭の中をいったん空にする。GTDを実践している人なら誰もが「これがいちばん大事」と口を揃える工程です。

正直に打ち明けると、私はこの振り返りを――とりわけ週次レビューを――ほぼやっていませんでした。「やらなきゃ」とは思っている。大事だということも知っている。それでも続かない。「やる気がないから」と言ってしまえばそれまでですが、振り返ってみると、続かない理由はもう少し具体的なところにありました。

振り返りは、始めるのがいちばん重いのです。

タスクを一件追加するのは簡単です。思いついたことを書けばいい。けれど振り返りは違います。机に向かって、さあ始めようとした瞬間に、「で、何を振り返ればいいんだっけ？」という問いが立ちふさがる。今週は何が終わったのか。何が積み残ったのか。先週気になっていたあの件はどうなったのか。これらの問いを、まず自分で組み立てなければなりません。

この「問いを立てる」工程が、思いのほか重い。重いから、後回しにする。後回しにしているうちに一週間が過ぎ、また次の週が来る。そうやって、私の振り返りは――日々のものも、週に一度のものも――ずっと飛ばされ続けてきました。

## 問いを立てるのがいちばん重い

外のタスク管理ツール——手帳でも、アプリでも——を使っていたとき、振り返りはいつも私ひとりの作業でした。

ツールは、タスクの一覧を見せてはくれます。けれど、それを前にして「さて、何から考えよう」と問いを設計するのは、私の仕事です。少なくとも私が使っていた範囲では、ツールは答えを記録する場所ではあっても、問いを出してくれる相手ではありませんでした。

考えてみれば当たり前のことです。私の手帳は「先週の懸念は解決したか」とは聞いてきませんでした。アプリも「このタスク、もう一週間動いていませんよ」とは言ってくれません。問いはいつも、私の側から出すものでした。

そして私は、その問いを出すのが面倒で、いつも振り返りそのものをやめてしまっていたわけです。記録する道具はたくさん持っていたのに、問いを立てる相手がいなかった。これが、私が振り返りを続けられなかった本当の理由だったのだと思います。

「やる気の問題」だと思っているうちは、解きようがありません。気合いを入れても、来週にはまた同じところでつまずく。詰まっていたのはやる気ではなく、振り返りの入口に置かれた「何を考えればいいのか」という、たった一つの問いだったのです。

## Claude Codeに「今日のレビューをしよう」と言うだけ

Claude Codeに「仕事」を任せるようになってから、この風景が変わりました。

私がやることは、「今日のレビューをしよう」と話しかける。それだけです。すると、Claudeのほうから問いが返ってきます。2026年6月2日のログをもとに、その日のやりとりを大意で再現してみます（タスクを指す内部の番号は一般化しています。鉤括弧は逐語の引用ではなく、やりとりの趣旨を私がまとめたものです）。

Claudeはまず、今すぐ手をつけるべきタスクを並べて、今日着手できるかと尋ねてきました。私は、今日やる予定のままでいい、という意味で「そのまま」と答えます。

次に、Claudeはしばらく動いていなかったタスクを見つけて、今日やるかどうかを尋ねてきました。私は「やる」と答え、別の一件には「今日」と期限を切りました。

私がやったのは、これだけです。今日やる予定のものは「そのまま」、動いていなかったものには「やる」、もう一件には「今日」。短い返事を三つ。問いはすべてClaudeのほうから出てきました。「何を振り返ればいいんだっけ」と頭を抱える、あの重い工程が、まるごとなくなっていたのです。

このやりとりは、後から見返せるように一件のログとして自動で残ります。そのとき残ったログの一部を、そのまま引いてみます（実際のログには本書では伏せている業務上のタスク名が含まれるため、その箇所は「あるタスク」と置き換えています。タスクの番号も一般化しています）。

```
## 実行時刻
18:44 JST 開始 → 18:44 JST 完了（所要約5分）

## 着手・変更したタスク
- あるタスク → そのまま（本日着手予定）
- あるタスク → そのまま（本日着手予定）

## 仕分け
- 統合ネタ帳を作るタスク → 期限を今日に設定して「計画中」へ昇格
- その他9件 → そのまま維持
```

ログの読み方を補足しておきます。冒頭の「実行時刻」は、このレビューを始めて終えるまでにかかった時間です。次の「着手・変更したタスク」は、私がClaudeの問いに「そのまま」と答えた結果がそのまま記録されたもの。最後の「仕分け」は、しばらく動いていなかったタスクのうち、一件だけ「今日やる」と期限を切って前に出し、残り9件は手をつけずに置いておく、と私が決めた判断の記録です。

このログで注目してほしいのは、最初の一行です。開始時刻と完了時刻が、同じ「18:44」になっている。レビュー全体は約5分でしたが、私が問いに答える正味の時間は、分単位の解像度では同じ一分の中に収まってしまったということです。机に向かって問いを組み立てていた頃には、始める前にあきらめていた作業でした。それが、話しかけて答えるだけの数分になっていました。

## 「まとめて処理しますか？」に、YesともNoとも答える

振り返りで返ってくる問いは、一件ずつのものばかりではありません。ときどき、Claudeのほうが先に気づいて、こんな提案をしてくることがあります。「似たようなタスクが何件かあります。まとめて処理しますか？」――以下は、その場面がどんなふうに進むかを運用イメージとして書いたものです（特定の日の逐語ログではなく、こういう提案が起きうるという例として読んでください）。

たとえば、あちこちに散らばっていた「あとで読む」系のタスクが何件かたまっていたとします。Claudeはそれを束ねて「これらはまとめて一つに整理できそうですが、そうしますか？」と尋ねてくる。私は中身を見て、たしかに一つにまとめてしまっていいと判断すれば「お願い」と答えます。すると一括で処理が進む。これがYesの場面です。問いに答えるだけで、散らかっていた何件かが一度に片付きます。

この提案がありがたいのは、私が「似たものをまとめよう」と意識すらしていなかったところに、向こうから声がかかる点です。振り返りで一件ずつ眺めているだけでは、離れた場所にあるタスク同士のつながりに、なかなか自分では気づけません。それをClaudeが先に拾い上げてくれる。

けれど、いつでもYesと言うわけではありません。別の日には、Claudeが「これらは関連しているので、まとめて同じ扱いにしますか？」と提案してきても、私は「いや、これは一件ずつ判断したい」と断ることがあります。見た目は似ていても、一つだけ事情が違って、急いで進めたいものが混じっている。あるいは、まとめてしまうと後で見失いそうで、あえて分けておきたい。そういうときは、まとめずに個別に見ていく。これがNoの場面です。

ここで大事なのは、断ることが「失敗」でも「装置の故障」でもない、ということです。Claudeは関連に気づいて提案を出す。その提案を受けるか受けないかを決めるのは、私です。まとめていいのか、一件ずつ見るべきなのか――それを知っているのは、タスクの中身と自分の都合をわかっている私だけだからです。Yesと言うのも判断、Noと言うのも判断。問いに答えるだけでなく、提案を断る判断もまた、最後まで私の手元に残っています。

## なぜ、振り返りの問いはClaudeが立てられるのか

ここで効いているのは、収集から実行まで、すべての記録がClaude Codeの「手元」にたまっていることだと思います。

私はこれまで、思いついたことを話しかけて集め、朝に「今日どうする」をClaudeと決め、タスクの番号を渡して動いてもらってきました。その一つひとつが、ぜんぶ記録として残っています。だからClaudeは、振り返りのときに「今すぐのタスクはこれ」「これはしばらく動いていない」と、過去の経緯を踏まえた問いを立てられる。

外のツールが問いを出せなかったのは、能力が足りなかったからではありません。記録する場所と、問いを立てる相手が、別々だったからです。手帳に書いた内容を、別のアプリが知ることはありません。アプリに溜めたタスクを、手帳が見直してくれることもない。記録はあちこちに散らばり、それを束ねて問いに変える役目だけが、いつも私に残されていました。

Claude Codeでは、その二つが同じところにあります。タスクを集めた相手が、そのまま振り返りの問いも立ててくれる。だから、私はもう問いを作らなくていい。

さきほどの「これらはまとめて処理できそうです」という提案も、同じ理屈で出てきます。Claudeがそう言えるのは、複数のタスクのあいだにある関連――似たもの同士であること、片方が片方の前提になっていること――に気づいたからです。そして関連に気づけるのは、ひとえに、これまでの記録が同じ手元にたまっているからにほかなりません。バラバラの場所に散っていたら、何と何が似ているのかを見比べることすらできません。

これは振り返りに特有の仕掛けではなく、本書の第2章で見た「処理・整理を任せる」場面とまったく同じメカニズムです。たまったタスクを仕分けるときも、振り返りで「まとめませんか」と提案するときも、Claudeは蓄積された記録から関連を読み取って動いている。場面は違っても、土台は一つです。

だとすれば、自然な帰結があります。記録がたまるほど、関連は見えやすくなる。つまり、使えば使うほど、振り返りでの提案は的を射たものになっていくということです。使い始めの頃は、関連の薄いタスクしかなくて提案も控えめかもしれません。けれど集め続け、任せ続けるうちに、Claudeのほうから「これとこれは一緒に見たほうがいい」と差し出してくる場面が増えていく。最初から全部が自動で回るわけではなく、こちらが記録を預け続けることで、振り返りの相手がだんだん頼もしくなっていく――そういう育ち方をします。

## 週次レビュー（週に一度の振り返り）にも、同じやり方が効く

ここまでは日々の振り返り（デイリーレビュー）の話でした。けれどGTDがいちばん大事だとするのは、冒頭で書いたとおり、週に一度の週次レビューのほうです。

私は当初、こちらこそ続かないだろうと思っていました。日々のものより範囲が広く、見直すタスクの数も多い。問いを立てる重さも、その分だけ増えるはずだからです。

ところが、やり方はまったく同じでした。「今週のふりかえりをしよう」と話しかける。あとは返ってくる問いに答えていくだけ。範囲が広くなったぶん問いの数は増えますが、一つひとつ答えるという動作は変わりません。

実際の週次レビューのログを一つ引いてみます。2026年5月30日に行ったものです。

```
## 実行時刻
17:xx JST 開始 → 17:25 JST 完了

## たまったタスクの棚卸し
- 受信トレイの処理: 0件（処理するものがなかった）
- 「次にやる」の確認: 期限切れ5件を翌日に繰り直し
- 「待ち」の確認: 期限切れ1件 → 完了扱いに
- 定期タスク: 2件 → どちらも今朝すでに実施済み
- 「いつかやる」から「次にやる」への昇格: 3件
```

ここで私の目を引いたのは、一行目の「受信トレイの処理: 0件」でした。受信トレイ――つまり思いついたことを放り込んでおく場所――が、週末の時点でからっぽになっていた。処理すべきものが一件も残っていなかったということです。

これは、本書がここまで追ってきた流れがひとつにつながった瞬間でした。日々、気づいたことをその場で受信トレイに放り込む（収集）。それが毎日の処理で適切な箱に振り分けられていく（処理・整理）。だから週末に振り返ろうとしたとき、たまっているはずの未処理が、もう残っていない。週次レビューが「重い片付け作業」ではなく「すでに整っているものの最終確認」になっていたのです。

残りの行も、私がやったのは判断だけです。期限切れのタスクを翌日に繰り直すか、もう完了として閉じるか、「いつかやる」に寝かせていたものを「次にやる」に引き上げるか――Claudeが一件ずつ状況を示し、私が短く答えていく。問いを立てる工程は、ここでもまるごとClaudeの側にありました。

最後の「『いつかやる』から『次にやる』への昇格: 3件」という行にも、少し触れておきます。これは、いつか手をつけたいと寝かせていたタスクのうち三件を、「来週は実際に動かす」と私が引き上げた記録です。週次レビューの値打ちは、終わったものを片付けることだけではありません。寝かせておいたものの中から「そろそろやる時期だ」と感じたものを前に出す――その判断の場でもあります。日々のデイリーレビューが「今日どうするか」を扱うのに対して、週次レビューは「来週どこに重心を置くか」を扱う。だから、扱う高さが少し違うのです。

ここでも、どのタスクを引き上げるかを決めたのは私でした。Claudeは「いつかやる」に入ったままのタスクを並べて見せてくれますが、「今がその時期だ」と感じるかどうかは、私の中の都合や手応えにしか答えがありません。問いはClaudeが並べ、選ぶのは私。日々の振り返りで見たYes/Noの構図が、週次でもそのまま生きていました。

ただし、正直に書いておきたいことがあります。このログには「リンク付け（ステップ3）」という続きの工程があって、その日は「中断（時間切れ）」で終わっていました。週次レビューは範囲が広いぶん、最後までやり切れない日もある。それでも、いちばん重い棚卸しの部分は数十分で片付いていました。完璧に終えることより、入口でつまずかずに始められることのほうが、続けるうえでは効いている――そう感じています。

## 「続けられている」と、正直に書ける範囲

ここで、誠実に書いておきたいことがあります。

私はまだ、週次レビューを「何ヶ月も欠かさず続けている」と胸を張って言える段階にはいません。本書を書いている時点で、ログとして残っている週次レビューは数回ぶんです。日々のデイリーレビューも、毎日もれなく、というほどには定着していません。

それでも、以前との違いははっきりしています。かつての私は、週次レビューを「ほぼやっていなかった」。机に向かう前に、問いを立てる重さに負けて、始めることすらできなかった。今は、思い立ったときに「ふりかえりをしよう」と話しかければ、ともかく始められる。始められれば、数十分で一周する。

「ずっと続けられるようになった」のではなく、「始められるようになって、続いている途中だ」。これが、いま正直に書ける範囲です。問いを立てる重さが消えたことで、続けることのハードルが下がった――その手応えは確かにあります。けれど、それが半年後、一年後にも続いているかは、これから先の私が証明することです。

問いの入口が軽くなったからといって、続ける意志まで装置が肩代わりしてくれるわけではありません。装置が引き受けてくれたのは「何を振り返るか」を組み立てる工程まで。「振り返るかどうか」を決めるのは、相変わらず私の側に残っています。

## 考えるのはClaude、判断するのは私

問いを立てること——つまり「何を考えるか」を決める工程を、Claudeが先に引き受けてくれました。「このタスク、今日やりますか？」という問いは、私が作ったものではありません。Claudeが記録を見て、組み立てて、差し出してきたものです。

では、私には何が残ったのか。答えることです。「そのまま」なのか「やる」なのか「今日」なのか——それを決めるのは、最後まで私の仕事でした。Claudeは問いを立てますが、どう答えるかまでは決めません。今日このタスクに手をつけるかどうかを知っているのは、私だけだからです。「まとめて処理しますか？」という提案にYesと答えるのも、Noと答えるのも、同じことです。提案を出すのはClaude、それを受けるか断るかを決めるのは私。答えるだけでなく、断る判断もまた、こちら側に残されています。

考えるのはClaudeが先で、判断するのは私。本書を通して何度か顔を出してきたこの分け方が、振り返りの場面でいちばんはっきりと形になりました。重かったのは「問いを立てる」工程だったのだと、任せてみて初めてわかりました。そこを手放したら、振り返りは「義務」ではなく「会話」になり、まず日々のデイリーレビューから始められるようになりました。

ここで効いている「問いはClaudeが立てる」という構造は、日々の振り返りでも、週に一度の週次レビューでも、変わりません。だから、デイリーで始められたやり方は、そのまま週次にも広げていけます。週に一度たまったものを見直したいときも、まずは「今週のふりかえりをしよう」と話しかけるところから始められる。問いはClaudeのほうから出てくるので、こちらは答えるだけ。重い入口は、もう向こうが引き受けてくれます。

## あなたの装置では：他のAIツールでもタスクの振り返りは手放せる

ここまでは、Claude Codeという私の手元の道具で起きたことです。けれど、この章で起きていることの芯は、特定の道具に縛られていません。あなたが別のAIツールを使っているとしても、同じ仕組みを組み直すことができます。私の話はここまでです。あなたのツールで試すなら、一つだけ伝えておきます。

振り返りが続かない理由が「やる気」ではなく「問いを立てる重さ」にある、という見立ては、ツールを問わずたぶん共通です。タスクの一覧を眺めること自体は難しくありません。難しいのは、その一覧を前にして「今週は何が終わったか」「何が積み残ったか」「あの懸念はどうなったか」という問いを、自分でゼロから組み立てる工程のほうです。ここを動かせる相手がいれば、振り返りは回り始める。その相手は、これまでのタスクの経緯を知っていて、過去をふまえた問いを出せる必要があります。だから、タスクを集めた場所と振り返りの問いを立てる相手が、同じところにある――それが効きどころです。

私の手元では、収集・処理・実行のすべてのやりとりが、同じClaude Codeの会話の中に記録されていました。だからレビューのときに、過去をふまえた問いがそのまま返ってきた。私がやったのは「今日のレビューをしよう」「今週のふりかえりをしよう」と話しかけ、返ってくる問いに「そのまま」「やる」「今日」と短く答えることだけ。その答えが、そのまま一件のログとして残っていく。この章で引いた二つのログは、その実物です。

もしあなたが対話型のAIツール（チャット型のものでも構いません）を使っているなら、タスクの一覧をその会話に渡したうえで、「振り返りの問いをあなたが立てて、一件ずつ私に聞いてほしい。私はYes/Noで答える」と頼んでみてください。具体的には、こんなふうに渡せます。

```
（タスクの一覧をここに貼る）

上のタスクについて、週次の振り返りをします。
あなたが一件ずつ「これは今週やりますか / 来週に回しますか /
いったん寝かせますか」と聞いてください。
私はそれに短く答えるだけにします。まとめて聞かず、一件ずつでお願いします。
```

ここで大事なのは、タスクの一覧をその会話に「渡せる」状態にしておくことです。タスクを別のツールに溜めているなら、その内容を書き出して貼り付ける一手間が要ります。逆に言えば、その一手間さえあれば、ツールが何であれ「問いを立てる工程を相手に渡す」という芯は再現できます。

そして、振り返りで返ってくる提案――「これらはまとめて処理できそうです」「関連するものを一緒に見ますか」――の精度は、相手が持っている記録の厚みに比例します。使い始めはタスクが少なく、関連も見えにくいので、提案は控えめでしょう。それは故障ではなく、まだ材料が薄いだけです。記録を預け続けるうちに、相手はだんだん的を射た問いを差し出すようになります。最初から完璧を期待せず、「問いを立てる重さだけは、もう自分で抱えない」――そこから始めてみてください。
