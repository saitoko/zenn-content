title: "第7章 あなたの装置を作る — AIに話しかけるだけでGTDタスク管理ツールができる"
---

**この章でやること**：ここまで読んできたあなたが、自分の装置を作るための最小構成を渡します。難しい話はしません。最初の一歩は、AIに「GTDに則ったタスク管理ツールを作って」と話しかけるだけ——コードは一行も書きません。そのうえで、できあがった装置がどんな部品でできているのか、最小で何が必要なのかを、私の手元の実物を開きながら解説します。後半では「タスクの置き場所は何でもいい」という応用と、コピーしただけの装置を「自分専用」に育てる方法までをひとまとめにします。この章を読み終えるころには、あなたの手元でも装置を立ち上げられる状態になっているはずです。

前の章では、装置を会社のPCや紙の書類とどう接続するか、その「境界」の引き方を扱いました。境界の話は、すでに装置を持っている人の悩みです。けれどこの章で向き合うのは、もっと手前の問い——**そもそも、その装置はどう作るのか**です。ここからは、まだ装置を持っていないあなたに向けて書きます。

## 最初の一歩は、話しかけるだけ

結論から言います。あなたの装置を立ち上げる最初の一歩は、これだけです。

> 「GTDに則ったタスク管理ツールを作って」

AIに、こう話しかける。たったそれだけです。

セットアップの手順を覚える必要はありません。設定ファイルを書く必要もありません。ましてやプログラムを書く必要は、まったくありません。本書のタイトルは「コードを書けない私が」で始まっていますが、それはこの最初の一歩においても、最後まで変わらない事実です。

実を言うと、私の最初の一歩も、これとまったく同じでした。序章で書いたとおり、私はある日、AIに似た一言を投げただけです。それが、いまの装置のすべての始まりでした。記録をたどると、その一言から生まれた最初の版が世に出たのは、ある日の昼の十二時四十六分。

```
12:46  /todo — GTDタスク管理スキルの初版を公開
```

そして驚くべきは、その先です。同じ日の記録を追っていくと、わずか六十五分後の十三時五十一分に、もう次の記録が刻まれていました。

```
13:51  デイリーレビュー機能などを追加
```

初版が生まれて一時間あまりで、もう「毎日の振り返り」を助ける機能が付け足されていたのです。私が一行ずつコードを書いていたら、こんな速さは出せません。話しかけて、できたものを見て、「ここにこういう機能が欲しい」とまた話しかける。その往復だけで、装置は最初の数時間で形になっていきました。

だから、身構えないでください。完成図を頭に描いてから始める必要はないのです。「GTDに則ったタスク管理ツールを作って」と話しかける。返ってきたものを使ってみる。足りないと感じたら、また話しかける。あなたの装置も、その往復の中で育ち始めます。

ここで一つ、正直に書いておきたいことがあります。最初の一言で出てくるものは、たいてい完璧ではありません。私の初版も、いま思えば素っ気ない作りでした。タスクを足す、一覧を見る、完了にする——その程度の、ごく素朴な道具です。それでいいのです。むしろ、いきなり高機能なものを目指すと、何が動いていて何が動いていないのか分からなくなって、かえって続かない。素朴なところから始めて、使っていて「ここが不便だな」と感じた箇所を、その都度AIに直してもらう。不便を起点に話しかける——これが、装置を育てる最も自然なやり方です。

## できあがるGTDタスク管理ツールは、四つの部品でできている

とはいえ、「話しかけたら何かができた」だけでは、自分が何を手にしたのか分からないままです。中で何が動いているのかが見えていたほうが、後で困ったときに直しやすい。そこで、話しかけた結果できあがる装置が、どんな部品でできているのかを開いてみます。

煎じ詰めると、装置は次の四つの部品でできています。

| 部品 | ひとことで言うと | 役割 |
|---|---|---|
| ①行動規範 | AIへの「こう振る舞え」という指示書 | タスクの言葉を聞いたらどう動くかを決める |
| ②スクリプト | 置き場所への実際の読み書きをする道具 | タスクを置き場所に書いたり、読んだりする |
| ③自分のルール | 「私の仕事のやり方」を書いた設定 | AIにあなた固有の事情を教える |
| ④置き場所 | タスクが実際に貯まる場所 | 集めたタスクをためておく永続的な記憶 |

一つずつ、実物を見ながら説明します。コードの全文は載せません。見せ場になる短い一文と、「それが何をする部品か」だけを取り出します。

### ①行動規範 — AIへの「こう振る舞え」

まず一つ目。装置の心臓にあたるのが、AIへの行動規範です。これは「ユーザーがこういう言葉を口にしたら、こう動け」という指示を書いた、ひとつのテキストファイルです。

私の装置で、その指示書の冒頭はこう始まっています（実物は英語で書かれているので、要点を訳して示します)。

> GitHubのIssueを、GTD式のTODOリストとして管理せよ。inbox / next / waiting / someday / project / routine のカテゴリ、期限、繰り返し、優先度（p1/p2/p3）……を扱う。ユーザーが「タスク」「TODO」「GTD」「Inbox」「次にやること」「待ち」「いつかやる」……といった言葉に触れたら、たとえ明示的に道具の名前を呼ばなくても、この技能を使え。

ここで列挙されているカテゴリには、この後で説明する箱の一覧（inbox / next / waiting / someday / project / reference）にはない `routine`（繰り返しタスク）が顔を出しています。逆に、ここには `reference`（参照情報）が出てきません。これは食い違いではなく、同じ装置を別の角度から書いたファイルだから、列挙の仕方が少し違うだけです。実物の装置には、後で見る六つの箱に加えて `routine` というラベルもあり、合わせると七種類になります。ここでは「行動規範ファイルから見たときの並べ方」だと思って読み進めてください。箱の全体像は、このすぐ後の節で改めて表に整理します。

長く見えますが、言っていることは単純です。**「タスクっぽい言葉が出てきたら、黙って仕事を始めろ」**——それだけです。

この一行に、本書で何度も触れてきた手触りの正体が詰まっています。第1章で「この件をタスクにしておいて」と話しかけるだけでInboxに登録された、あの体験。なぜそれが成り立っていたかというと、ここに「タスクという言葉に触れたら動け」と書いてあったからです。私がいちいち「タスク管理ツールを起動して、新規作成して……」と操作していなかったのは、この行動規範が、私の何気ない一言を仕事の起点として拾うように仕込まれていたからでした。

面白いのは、この行動規範が「明示的に道具の名前を呼ばなくても」と断っている点です。私は「タスク管理ツールを起動しろ」とは一度も言いません。「これ、あとでやらなきゃ」とこぼすだけ。それでも装置が動くのは、ここに「タスクっぽい言葉に触れたら動け」という幅広い合図が書いてあるからでした。裏を返せば、この行動規範をどう書くかで、装置がどれだけ気を利かせてくれるかが決まります。神経質に「正しいコマンドを打たないと動かない」道具にするか、こぼした一言を拾ってくれる道具にするか——その性格は、この一つ目の部品の書きぶりで決まるのです。

これが装置の一つ目の部品です。難しく言えば「AIの行動規範」ですが、要するに**AIへの口の利き方の取り決め**だと思ってください。

### ②スクリプト — 置き場所への読み書き

二つ目は、タスクを置き場所に実際に書き込んだり、読み出したりする道具です。これは小さな台本のようなもので、行動規範（①）が「タスクを登録せよ」と決めたとき、実際にその手足となって動きます。

私の装置では、この役目を二つのファイルが分担しています。表向きの窓口になる短い台本と、その裏で本当の読み書きを担う大きな台本です。次に行数を出しますが、げんなりしないでください——これは、あなたが書くものではありません。

```
窓口の台本   : 166行
読み書きの台本: 4,122行
```

ここで「四千行以上」という数字を見て、改めて身構えてしまったかもしれません。でも大丈夫です。**この四千行を、あなたが書く必要はありません。** AIに「GTDに則ったタスク管理ツールを作って」と話しかけたとき、この部分はAIが書きます。あなたは中身を一行も読まなくていい。私自身、この四千行を頭から読んで理解したことは一度もありません。

大事なのは行数ではなく、「この部品が何をしているか」だけです。やっていることはたった二つ——**置き場所にタスクを書く。置き場所からタスクを読む。** ②はその読み書きの往復を、あなたに代わって黙々とこなす道具です。あなたが意識する必要はほとんどありませんが、装置が動くためには、この手足が要る、ということだけ覚えておいてください。

### ③自分のルール — 「私の仕事のやり方」

三つ目は、あなた自身の仕事のルールを書いた設定です。①の行動規範が「タスク管理ツールとして普遍的にどう動くか」を決めるのに対し、③は「**この私の場合は**どうしてほしいか」を書く場所です。

たとえば「私は平日の朝に振り返りをする」「このプロジェクトの作業は丁寧めに記録を残してほしい」「期限が近いものは強めに知らせてほしい」——そういった、あなた固有の事情です。AIはここを読んで、はじめてあなた向けの動きをするようになります。

この章の後半でもう一度触れますが、実はこの③こそが、装置をあなた専用にしていく一番大事な部品です。ここがほとんど空っぽのうちは、装置は誰が使っても同じ「汎用ツール」です。逆にここにあなたのルールが書き溜まっていくと、装置は少しずつあなた専用になっていきます。

### ④置き場所 — タスクが貯まる場所

四つ目は、集めたタスクが実際に貯まる場所です。私の場合、これはGitHubのIssue（課題管理の仕組み）でした。本書で何度も出てきた「#1509」のような通し番号が振られている、あの場所です。

これは装置の記憶にあたります。会話を閉じても、パソコンを再起動しても、ここに書き込まれたタスクは消えません。だから私は安心して「一旦忘れる」ことができました。第1章で書いた「open loops（未決の気がかり）が頭から消える」感覚は、忘れても大丈夫な置き場所が、頭の外にちゃんとあったからこそ成り立っていたのです。

この四つ——行動規範・スクリプト・自分のルール・置き場所。これが装置の最小構成です。そして繰り返しますが、このうち**あなたが手を動かして用意するのは、ほとんど③の「自分のルール」だけ**です。①②④は、最初の一言から、AIがあらかた組み上げてくれます。

> 部品のひとつひとつを、もっと深く知りたい人へ。それぞれの部品が何であり、どう設計するとよいかは、前作『コードを書けない私がClaude Codeに「仕組み」を渡すまで』で一つずつ丁寧に扱いました。本章はあくまで「装置として動かす最小構成」に絞っています。

## GTDのタスク仕分けは、六つの箱で考える

装置の骨格が分かったところで、もう少しだけ中身に踏み込みます。GTDの肝は「集めたタスクを、適切な箱に仕分けること」にあります。私の装置では、その基本の箱を六つ用意していました（先ほどの行動規範に出てきた `routine` は、この六つに付随する七つ目のラベルです。すぐ後で触れます）。

| 箱 | 何を入れるか |
|---|---|
| inbox | とりあえず放り込んだ、まだ仕分けていないもの |
| next | 次に手をつける、具体的なアクション |
| waiting | 自分以外の誰か・何かを待っている状態のもの |
| someday | いつかやるかもしれない、急がないもの |
| project | 複数の手順がぶら下がる、大きめの塊 |
| reference | 行動はしないが、取っておきたい参照情報 |

GTDを実践したことのある人なら、見覚えのある分類だと思います。inbox / next / waiting / someday / project / reference という基本の箱は、David Allen が原典で示した仕分けの考え方に倣ったものです（後で足す `routine`＝繰り返しタスクは原典にはなく、私が運用上あとから付け足したラベルです）。装置は、Inboxに放り込まれたタスクを、この六つのどこに入れるかをあなたと相談しながら決めていきます。

ここで思い出してほしいのが、第2章で見た「自分は答えるだけ」の手触りです。「これはWaitingですね」「次にやることに入れますか」——装置が箱の候補を先に出し、あなたはYesかNoかを返す。その仕分けが成り立っていたのは、装置の側に、この六つの箱があらかじめ用意されていたからでした。

この六つの箱に加えて、私の装置にはいくつか暮らしを楽にする仕組みも付いています。先ほどから何度か顔を出している `routine` が、その筆頭です。毎日・毎週・毎月といった周期で繰り返すタスク——「週に一度、振り返りをする」のような定例は、いちいち手で足し直さなくても、片づけると次の周期で自動的に戻ってきます。第1章でお見せした一覧のサマリー行に `routine: 4件` と並んでいたのが、まさにこれです。あるいは「自宅でしかできないこと」「外出中にできること」のように、場所や状況でタスクを絞り込む仕組みもあります。これらは最初から全部要るわけではありません。使っていて「これがあると楽だな」と感じたときに、AIに頼んで足していけばいい。`routine` も、私が「繰り返しの定例を毎回手で足すのが面倒だ」と感じてから付け足したものでした。

なお、これらの箱や仕組みは、あくまで私の装置の例です。あなたが「待ち」の箱は要らないと思えば省けばいいし、「買い物リスト」のような独自の箱を足してもかまいません。箱の数や名前を決めるのも、③の「自分のルール」に書いておけることの一つです。

## 体験を大きく変える、二つの追加部品

ここまでの四つの部品があれば、装置は最低限動きます。ただ、最初しばらくは便利だけどどこか他人行儀な感じがしていました。それが変わったのは、次に挙げる二つの追加部品を足してからでした。最小構成には含めませんが、ぜひ早いうちに足すことをおすすめします。

ひとつ目は、**セッションをまたいで知識を貯める記憶**です。先ほどの③「自分のルール」が「常に守ってほしい決まりごと」だとすれば、こちらは「使ううちに分かってきた、あなたの癖や好み」を貯めていく場所です。たとえば「この人はこういう書き方を好む」「前にこの判断で失敗したから次は気をつける」——そういった学びが、会話を閉じても残っていく。これがあると、装置は使うほどにあなたを知っていきます。

ふたつ目は、**振り返りのリズムを定義した部品**です。本書の第4章で、デイリーレビューや週次レビューが「5分で終わる」と書きました。あれが軽く終わったのは、「振り返りのとき、AIはこういう順番でこれを聞け」という段取りが、あらかじめ部品として書かれていたからです。毎回ゼロから「さて、何を振り返ろうか」と考えていたら、5分では終わりません。リズムを部品として持っておくと、振り返りが習慣として定着しやすくなります。

この二つを足すかどうかで、装置の手触りはずいぶん変わります。記憶がないと、装置は毎回はじめましての顔をします。振り返りのリズムがないと、せっかく集めたタスクが一覧に積み上がるだけで、立ち止まって見直す機会を逃します。逆にこの二つがあると、装置は「前にこう言っていましたね」と返してくれたり、「そろそろ振り返りの時間です」と知らせてくれたりする。いま振り返ると、私が本書でこの装置を「パートナー」と呼んだのも、この二つの部品があってからのことだったと気がします。

この二つは、装置が「育つ」ための土壌です。次の節で、その「育てる」話に進みます。

## コピーしただけでは、まだあなたの装置ではない

ここまでの部品をそっくりコピーすれば、明日から同じ装置が動く——そう思うかもしれません。半分は当たっていて、半分は違います。

部品をコピーすれば、装置は確かに動きます。タスクを集め、仕分け、実行を頼むことはできます。けれどそれは、まだ**誰が使っても同じ**「汎用ツール」にすぎません。私の手元で動いている、あの「自分のことを分かってくれている」感覚は、コピーしただけでは付いてきません。

では、汎用ツールが「あなた専用」に変わるのは、いつか。それは、先ほど触れた③「自分のルール」と、追加部品の「記憶」に、あなた自身の仕事のやり方が書き溜まったときです。

最初は、その二つはほとんど空っぽです。だから装置は、当たり障りのない一般的な動きしかしません。けれど使っていくうちに、「私はこう呼ばれたい」「この種の作業は急がなくていい」「前にこうして失敗した」——そうしたあなた固有の事情が、少しずつそこに書き溜まっていく。その積み重ねが、ある日「あ、この装置は私のことを分かっている」という手触りに変わります。

育て方は、難しくありません。何か特別な作業をするわけではなく、**使っているうちに気づいたことを、その場でAIに伝える**だけです。「いまの呼び方、堅苦しいから砕けた感じにして」「この種のタスクは急がなくていいから、そう覚えておいて」——そうやって口にしたことが、③のルールや記憶に書き留められていく。意識して「さあ育てるぞ」と机に向かう必要はなく、日々の使用そのものが、そのまま育成になっています。私の場合も、改まって設定を書き込んだ記憶はほとんどありません。使いながら「ここはこうしてほしい」とこぼし続けた、その積み重ねでした。

最初から完璧に自分専用の装置が手に入るわけではない——この点だけは、正直に書いておきます。私の装置も、二ヶ月かけて少しずつ私を知っていきました。

## 応用 — 置き場所は、AIが読み書きできれば何でもいい

最後に、最も大事な応用を渡します。ここまで私は、タスクの置き場所（④）としてGitHubのIssueを例に挙げてきました。けれど、第3章でも触れたとおり、**置き場所はGitHubである必要はまったくありません**。

置き場所に求められる条件は、煎じ詰めるとたったひとつです。

**AIが、その場所を読み書きできること。**

これだけです。タスクの中身がそこに「書かれて」いて、AIがそれを読みにいける。実行した結果や完了の印を、AIがそこに書き戻せる。この読み書きの往復さえ成り立てば、置き場所が何であろうと、装置は同じように動きます。

たとえば、いちばん素朴な例として、**ただのテキストファイル**を置き場所にすることもできます。考え方はこうです——ひとつのフォルダを用意して、その中に置くテキストファイル一枚を、タスク一件とみなす。ファイルの名前がタスクのタイトルになり、中身に背景や期限を書く。「次にやること」「待ち」といった箱は、フォルダを分けることで表せます。完了したら、そのファイルを「完了」のフォルダに移すか、印を書き込む。

これなら、GitHubのような外部の仕組みすら要りません。あなたのパソコンの中の、フォルダとテキストファイルだけで成り立ちます。AIがそのフォルダを読み書きできさえすれば、「この件をタスクにしておいて」と話しかけたとき、AIは新しいテキストファイルを一枚作る。それだけで、本書で見てきた手触りの骨格は再現できるはずです。（ここで示したのは、こう作れるという考え方の見取り図です。私自身がこの方式を運用しているわけではありません。)

この応用が効くということは、ひとつ大きな含みを持っています。本書の装置は、特定のAIツールに縛られていない、ということです。私はたまたまある特定のツールの上で組みましたが、置き場所が「AIが読み書きできる場所」でさえあればよいのなら、別のAIツールを使っている人でも、同じ原理で自分の装置を組めます。本書がずっと言ってきた「作業する場所とタスクを置く場所を、ひとつの空間にまとめる」という原理は、道具の銘柄を選びません。

整理すると、こういうことです。

- **原理**（誰にでも当てはまる）：作業する場所と、タスクを置く場所を、AIが行き来できる一つの空間にまとめる
- **実装**（私の場合）：ある特定のAIツールの上で、GitHubのIssueをタスクの置き場所にした
- **応用**（あなたの場合）：あなたの手元のAIツールと、AIが読み書きできる置き場所を選べばいい。テキストファイルでも、別のメモの仕組みでも

なぜ、これほど「銘柄を選ばない」と言い切れるのか。それは、装置を成り立たせている部品が、どれも特別な技術ではないからです。①の行動規範はただのテキストの取り決め、③の自分のルールもただのテキスト、④の置き場所も「AIが読み書きできる場所」でありさえすればいい。唯一それらしく見えた②のスクリプトすら、AIが書いてくれる以上、あなたが理解する必要はありません。つまり装置は、特別な仕組みの集まりではなく、**ありふれた部品を、AIが行き来できる一つの空間に並べただけ**のものなのです。だからこそ、どんなAIツールを使っていても、同じ並べ方さえすれば再現できる。本書がずっと「コードを書けない私が」と言い続けてこられたのも、突き詰めれば、装置がこの程度に素朴な作りだったからでした。
