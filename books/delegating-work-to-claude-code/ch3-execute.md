**この章の出来事（2026年6月のある日）**：私はチャット欄に「#1509 やる」とだけ打ち込みました。タスクの番号をひとつ渡しただけです。すると文章を書く担当のエージェントが動き出し、二分足らずで指示どおりの統合ファイルを作り、作業の記録まで残してくれました。要件の説明はひとつもしていません。番号だけです。仕事をひとつ動かすのに、これほど身軽でいいのかと拍子抜けするほどでした。

つまり本章で言いたいことを一文にすると、こうです——**Claude Codeにタスク番号を渡すだけで、段取りから実行・記録までが完結する**。収集して、整理して、いざ手を動かす段になったとき、私がやったのは番号を渡すことだけでした。何をどう実行するかを先に組み立てるのはClaude、最後に「やる」と言うのが私。この章は、本書のタイトル「任せるまで」が最も素朴な形で立ち上がってくる場面です。

## 正直に言うと、最初はサボりたかっただけ

立派な動機があったわけではありません。

> 「正直に言うと、最初はサボりたかっただけだ。アプリを切り替えるのが面倒だから、隣にいるAIに話しかけた。それが習慣化につながった」

これが本当のところです。自分で手を動かすのがめんどくさくて、隣にいるAIに「これやっといて」と話しかけた。その軽い気持ちが、いつのまにか毎日の習慣になっていました。

気負って「さあ、AIを使いこなすぞ」と構えたわけではないのです。むしろ逆で、構えなかったからこそ続いたのだと思います。新しいツールを使い始めるとき、私たちはつい「正しい使い方」を覚えようとして、それが面倒になって離れてしまう。でも今回は、覚えることが何もありませんでした。めんどくさいことを、めんどくさいまま誰かに渡せる。その手軽さが入口でした。

## 番号を渡すだけで動いてくれる

ある日のことです。やるべきタスクのひとつに、ある作業を割り当てたい場面がありました。私は管理しているタスク一覧から、その作業の番号を確認し、こう打ち込みました。

> 「#1509 やる」

それだけです。「番号を渡す」というと身構えるかもしれませんが、難しいことは何もありません。一覧にずらりと振られた通し番号を見て、「これやって」と指さすだけ。「#1509」はその通し番号で、私が日々使っているGitHubのIssue（課題管理の仕組み）の番号です。やってほしいことの中身は、ひとことも説明していません。

それでもClaude Codeは動き出しました。文章を書く担当のエージェントが起動し、番号の中身を読み取り、二分足らずで指示どおりの統合ファイルを作り上げ、作業の記録として残しました。私が次に画面を見たときには、頼んだものが、もうそこにありました。

### 「#1509」の中身を、開いてみる

「番号を渡すだけ」と言われても、番号の中に何が入っているのか見えなければ、ピンとこないかもしれません。そこで、私が指し示したその#1509という番号を、実際に開いてみます。中身はこうなっていました。

```
番号:    #1509
タイトル: Vol.5: 処理+整理統合ネタ帳を作成する
状態:    完了（CLOSED）
ラベル:  次にやること / 優先度3
---
（説明欄）
参照: #1508
対象: （第2章にあたる原稿ファイル群）
統合後の体験核心:「朝に聞くだけで、今日が始まっている」
```

たったこれだけです。タイトルが一行、説明が数行。私が「#1509 やる」と打ち込んだとき、Claude Codeはこの中身を読みにいきました。「Vol.5の、処理と整理を統合したファイルを作る作業だな」「核にしたい感覚は『朝に聞くだけで、今日が始まっている』か」——番号の先にぶら下がっていたこの情報を手がかりに、実行担当のエージェントは段取りを組み立てたわけです。

注目してほしいのは、この説明欄を**私が手で丁寧に書き込んだわけではない**ことです。これは前の章で見たとおり、収集の段で「この件をタスクにしておいて」と話しかけた結果、Claudeがタイトルと背景を補って置いてくれたものでした。つまり番号の中身は、過去の私とClaudeの対話が、そのまま実行の指示書として残っていたのです。集めた時点の文脈が、実行の時点でそっくり効いてくる。番号ひとつが通じる背景には、この「文脈の持ち越し」がありました。

## なぜ番号を渡すだけでClaude Codeは動くのか

なぜ番号だけで通じたのか。からくりは単純です。いま見たとおり、#1509という番号のタスクには、もともとタイトルと説明が書き込まれていました。「Vol.5: 処理+整理統合ネタ帳を作成する」という具合に、何をしてほしいかが番号の側にぶら下がっている（「ネタ帳」というのは、記事の下書きメモにつけている私の呼び名です）。だから私は、番号を指し示すだけでよかった。説明は、すでに番号の中に入っていたのです。

序章で頼んだ「GTDスキルを作って」のときは、私が言葉で中身を渡しました。けれど今回は、中身を渡す手間すらいりません。番号という、いちばん短い合図で足りた。これが「実行を任せる」ということの、具体的な手触りでした。

世の中のタスク管理アプリでも、タスクにはたいてい番号がふられています。けれどあの番号は、たいてい「画面に表示するための番号」でしかありません。番号を眺めても、タスクが勝手に動き出すわけではない。結局はその画面を開き、内容を読み、自分の手で着手する――という別の動作が要ります。番号と、実行とのあいだに、ひとまたぎの溝があるのです。一言でいえば、ふつうのアプリの番号は「表示用の見出し」でしかなく、Claude Codeの番号は「言えば仕事が始まる指示」になっている――この差です。

ところがClaude Codeの中では、その溝がありません。番号は「表示のための番号」ではなく、「実行を頼むための合図」になっている。番号を指し示すことが、そのまま着手の指示になる。タスクを管理する場所と、タスクを実行する場所が、同じひとつのチャット欄の中にあるからこそ、番号を渡すだけで話が通じるのだと思います。

もう少し踏み込むと、ここで番号は「指示の最小単位」になっています。本来なら「あの統合ファイルを、こういう要件で、こう作って」と一段落かけて伝えるところを、「#1509」というたった数文字に畳み込めている。なぜそんなことができるのかというと、その数文字の先に、タイトルも背景も完了の条件も、ぜんぶぶら下がっているからです。私は要件を毎回言葉にし直す必要がなく、いちばん短い合図だけを置けばいい。番号が、指示のいちばん小さな単位として機能している――この感覚は、ふつうのタスク管理アプリを使っていたころには、一度も味わったことのないものでした。

そして、これが成り立つ条件は、思っているより素朴です。タスクの中身がどこかに「書かれて」いて、その場所をAIが読みにいける――ただそれだけ。私の場合はたまたまGitHubのIssueという仕組みに番号と中身を置いていますが、それでなければならない理由は、実のところありません。タスクの置き場所は、テキストのファイルでも、別のメモの仕組みでも、AIが読み書きできる場所でありさえすれば、同じことが起きるはずです。「管理する場所」と「実行する場所」が同じ装置の中で地続きになっていること――肝はそこであって、置き場所そのものの銘柄ではない。だからこの手触りは、私が使っている道具に固有のものではなく、AIと一緒に仕事をしている人なら、自分の手元の道具で組み直せるものだと思っています。

### 「二分足らず」の正体——記録に残った所要時間

ところで、先ほどから私は「二分足らずで作り上げた」と書いてきました。読んでいて「ずいぶん威勢のいい数字だな、本当か」と引っかかった人がいるかもしれません。これは体感で盛った数字ではなく、記録に残っています。

実行担当のエージェントは、作業を終えると変更内容をひとまとめにして記録（コミット）を残し、同時にそのタスクを「完了」の状態に切り替えます。#1509の場合、その二つの記録の時刻はこうでした。

```
タスクを「完了」に切り替えた時刻: 18:47
作業内容を記録（コミット）した時刻: 18:49
```

その記録には、こんな見出しが残っていました。

```
ネタ帳にch番号付与・処理+整理を統合ファイルに一本化

- 処理と整理を1つの統合ファイルに統合
  （体験核心「朝に聞くだけで、今日が始まっている」軸）
- 各ファイルを章構成順にリネーム
- 旧ファイルを削除
```

完了に切り替えてから記録を残すまで、わずか**二分あまり**。「二分足らず」というのは、私がストップウォッチで測った印象ではなく、実行担当のエージェントが手を動かしてから後始末を終えるまでの、記録に刻まれた所要時間でした。私が「#1509 やる」と打ってから完了するまでの全体には、当然これより長い時間がかかっています。ここで「二分足らず」と呼んでいるのは、**エージェントが実際に作業に着手して、ファイルを統合し、記録を残し終えるまで**の正味の時間です。

体感の数字を裏づけにすると、たいてい後で食い違います。だからここでは記録の方を正典にしました。番号を渡してから実行が完結するまでの速さは、誇張ではなく、装置の挙動として記録に残っている――それだけのことです。

### 置き場所の条件は、たったひとつ

ここまで「GitHubのIssue」という、聞き慣れない人には少し身構える名前が何度か出てきました。けれど、本章の手触りにとって、その名前はほとんど本質ではありません。番号を渡すだけで実行が始まる仕組みが成り立つために、タスクの置き場所に求められる条件は、煎じ詰めるとたったひとつです。

**AIが、その場所を読み書きできること。**

これだけです。タスクの中身が「書かれて」いて、AIがそれを読みにいける。実行した結果や完了の印を、AIがそこに書き戻せる。この読み書きの往復さえ成り立てば、置き場所がIssueであろうと、ただのテキストファイルであろうと、別のメモの仕組みであろうと、起きることは変わりません。番号(あるいは見出し、あるいは一行のタイトル)を指し示すだけで、その先にぶら下がった文脈ごと実行に渡せる――この構造に、置き場所の銘柄は関係ないのです。

私がこの章で見せているのは、私の手元でたまたまこうなっている、という一例にすぎません。「#1509」という番号はGitHub Issueという仕組みに固有の見た目で、これでなければならない理由はない。けれど本当に持ち帰ってほしいのは、その一例の向こうにある話です。**作業する場所と、タスクを置く場所を、AIが行き来できる一つの空間にまとめる**。その原理さえ押さえれば、番号を渡すだけで動く手触りは、銘柄を問わず再現できます。

逆に言えば、AIで仕事をしているのに、タスクだけはAIが読み書きできない別の場所に置いている――そういう状態だと、この手触りは決して立ち上がりません。番号を眺めても、AIにはその先が見えない。「表示用の見出し」と「言えば動く指示」を分けていた、あの溝が、そこに残り続けるからです。

## 手を止めずに、次のタスクをClaude Codeに渡せる

番号で動いてくれることのありがたさは、もうひとつ別の場面でも感じます。何かの作業の最中に、ふと別のタスクに気づいたときです。

たとえば記事を書いていて、「あの章の構成、あとで見直したほうがいいな」と気づく。こういうとき、これまでなら、手を止めてメモアプリを開き、思いついたことを書き留め、また元の作業に戻る――という寄り道が必要でした。その寄り道のあいだに、いま集中していたことの糸が切れてしまう。

ところがClaude Codeに任せていると、こうなります。たとえば執筆の途中で、別の章の直しがふと気になったとき――手を止めず、ひとこと声をかけるだけでいいのです。

> 「第2章の構成、あとで見直したい。それだけでいい。Claudeが Issue を作って Next に積んでくれる。今の作業は中断しない。」

気づいたことをそのまま口に出すだけで、Claudeがそれをタスクとして登録し、「あとでやること」の列に並べてくれる。私は手を止めません。いま向き合っている作業の糸も切れません。気づきを取りこぼさずに、しかも集中を保ったまま、次の仕事へと渡せる。

集める場面（第1章）で「話しかけるだけで忘れられる」ことを味わいましたが、実行の場面では、それがさらに進みます。集めたものを、手を止めずに実行へ渡せる。収集と実行が、ひとつの流れの中でつながっていくのです。

## 「まとめて完了にしますか？」に、Yesと言う日とNoと言う日

任せていると、Claudeのほうから一歩踏み込んだ提案が返ってくることがあります。ひとつのタスクを片づけ終えたあと、こう聞かれる場面です。なお、ここで紹介するやりとりは私が日々任せている運用の雰囲気を伝えるための例で、特定の日の逐語記録ではありません。

ある作業を終えたとき、Claudeが「関連するこのあたりのタスクも、まとめて完了にしておきますか？」と尋ねてきたとします。たしかに、ひとつの作業を仕上げると、それにぶら下がっていた小さなタスクが一緒に用済みになることはよくあります。中身を確かめて「ああ、これはもう全部終わったものだ」と納得できれば、私は「うん、まとめて完了にして」と答える。すると関連するタスク群が一度に片づき、一覧がすっきりします。手で一件ずつ消していく手間が、ひとことで済む。これがYesと言う日です。

なぜClaudeが「まとめて完了にしますか？」と聞けるのかというと、タスクが一覧として並んでいて、そこに「これは何の作業の一部か」「どのタスクと関連しているか」がぶら下がっているからです。たとえばある朝の時点では、私のタスク一覧は、おおまかにこんな状態で並んでいました（件数は日々変わるので、あくまでそのときのスナップショットです）。

```
次のアクション（next）   : 22件
受信トレイ（inbox）       : 0件（からっぽ）
待ち（waiting for）       : 10件
いつかやる（someday）     : 81件
```

Claudeはこの並びを眺めて、「いま完了にしたタスクと近いものが、次のアクションの中に何件かありますね」と気づき、声をかけてくる。私はその気づきに対して、YesかNoかを返すだけ。能動的に関連を探しにいくのはClaude、最後に「まとめる/まとめない」を決めるのは私――役割がきれいに分かれています。

けれど、いつもYesではありません。同じように「まとめて完了にしますか？」と聞かれても、並んだタスクを見て「いや、あれはまだ残っている」と引っかかることがあります。見た目は関連していても、片方はまだ手をつけていなかったり、別の判断が要る件だったり。そういうときは「それは違う、こっちはまだ残しておいて」と、個別に切り分けて答えます。Claudeの提案を断る瞬間です。

断ったからといって、何かが壊れたわけではありません。むしろ逆で、ここがいちばん大事なところだと思っています。実行も完了の処理もClaudeに任せている。けれど「何をもって終わりとするか」――その線引きだけは、最後まで私が握っている。「まとめて完了にしますか？」というひとつの問いに、YesとNoの両方で応じられること自体が、私がまだちゃんとハンドルを持っている証拠なのだと思います。

## 考えるのはClaude、「やる」と言うのは私

ここまでの場面を並べてみると、ひとつの分かれ目がはっきり見えてきます。

番号を渡したあと、何をどんな順番で進めるか――どのファイルを読み、何を書き、どう記録に残すか――その段取りを組み立てたのはClaudeでした。私はその中身に、いちいち口を出していません。けれど「#1509 やる」の「やる」だけは、まぎれもなく私が言った言葉です。やるのか、やらないのか。その一語の判断だけは、最後まで私の手に残っていました。

考える順番はClaudeが先、進めるかどうかを決めるのは私。本書を通して何度か顔を出してきたこの分業が、実行の場面では最も鮮明な形で立ち上がります。段取りという「考える」部分をまるごと預けても、「やる」という最後のひと押しは手放さない。預けることと、手放すことは違う。任せても、決めるのは自分。そのことが、番号ひとつのやりとりの中に、ぎゅっと詰まっていました。

## タスクを渡すだけで、仕事をしてくれる

こうして毎日、私は番号を渡し、気づきを口に出し、Claudeはそれを実行に移していきました。

> 「タスクを渡すだけで、仕事をしてくれる。すっかり仕事のパートナーになっている」

番号を渡せば動く。気づきを言えば積んでくれる。やると言えば、最後までやり切ってくれる。サボりたくて話しかけただけのはずなのに、隣にいるAIを「パートナー」と呼びたくなる何かが、たしかに芽生えていました。ただ、なぜそう感じるのか――どうして単なる便利な道具ではなく、パートナーのように思えるのか――この時点では、まだうまく言葉にできていませんでした。

「任せる」という言葉が、ここでようやく実感に変わったのは確かです。本書のタイトル「任せるまで」が指していたのは、たぶんこの瞬間のことだろう、とも思います。

もし試してみたいなら、入口はひとつでかまいません。いま手元にあるタスクをひとつ選んで番号を振り、「これやって」と渡してみる。たったそれだけで、この章で書いた手触りの片鱗は確かめられます。

## あなたの装置では

この章の手触りは、先に書いた唯一の条件さえ満たせば、道具の銘柄を問わず再現できます。手元の環境に合わせて、入り口を選んでみてください。

- AIと同じ画面でテキストファイルを開いて作業しているなら、**そのファイルにタスクを箇条書きで書き、行を指して「この行をやって」と言う**ところから始められます。番号も特別な仕組みも要りません。
- チャット型のAIを使っているなら、**会話の中にタスクのリストを貼り、「3番をやって」と番号で渡してみる**。リストの各項目に背景を一行添えておけば、それがそのまま実行の指示書になります。
- 大事なのは、タスク管理を「AIが触れない外側の別アプリ」に置きっぱなしにしないことです。まずはタスクをひとつ、AIの届く場所に移してみる。それが最初の一歩になります。

ただ、なぜサボりたいだけの軽い始まりが「パートナー」にまで育ってしまったのか――その手前にあるものを、私はまだ言葉にできていません。それは、収集から振り返りまでをひととおり通り抜けたあと、最後にもう一度立ち止まって考えてみることにします。次は、一日を「振り返る」場面です。
